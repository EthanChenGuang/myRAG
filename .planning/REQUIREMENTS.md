# Requirements: myRAG RAG 全链路升级

**Defined:** 2026-11-22
**Core Value:** 用户问知识库里有答案的问题，能拿到正确、带准确引用的回答；问知识库里没有答案的问题，系统明确说不知道，不硬编。并且这两点都能用评估分数证明。

All requirements are written so they can be checked. "Behind a switch" means an env flag that is mirrored in `scripts/init-env.js`, `src/lib/env.ts`, `scripts/config-server.js` and the Config UI, and that restores current behavior when off.

**Language scope (LANG-01):** wherever a requirement names Chinese, English and Italian (zh/en/it), it means the languages enabled by `RAG_SUPPORTED_LANGUAGES`; zh/en/it is the language set of the committed fixture corpus and of CI.

**Domain neutrality (owner rule, 2026-11-25):** every capability is domain-agnostic. Examples used to motivate a requirement (travel limits, leave days, salaries, restaurants, FAQs and similar) are illustrations, not product content: no product code, configuration default, prompt, lexicon, rule or Config UI copy may contain domain words or values from them, and anything domain-specific comes only from a tenant's own documents, data or admin settings. Fixture and eval items are described by their structure and use neutral, synthetic, varied content that does not reuse those examples.

## v1 Requirements

### Evaluation (EVAL)

- [ ] **EVAL-01**: A Python sidecar service exists in `rag-sidecar/` (FastAPI, Python 3.12, `pydantic>=2.14.4`), with health and readiness endpoints, a Dockerfile, and shared-secret auth that uses a constant-time compare and fails closed when the secret is unset
- [x] **EVAL-02**: All structured contracts (sidecar requests/responses, golden-set items, eval results, LLM structured outputs) are defined once as Pydantic v2 models; the TypeScript side uses Zod schemas generated from their JSON Schema, and CI fails when the generated Zod schemas are out of date
- [x] **EVAL-03**: Golden-set items carry span-based gold evidence (document, section, quoted text), language, category (multi-turn, compound, exact term, table, scanned, no-answer) and review status — never chunk IDs
- [x] **EVAL-04**: A synthetic fixture corpus and fixture golden set covering Chinese, English and Italian are committed, so CI can run without customer data
- [ ] **EVAL-05**: Tooling drafts a 50–200 item golden set from a real knowledge-base workspace (Claude-drafted plus Ragas-generated items) for the user to review; real-document items are stored outside git (gitignored path or a dedicated Supabase eval workspace), with a frozen dev/test split; Ragas generation spreads items across query styles (poor grammar, keyword-only, misspelled) and personas, and generated items are tagged `ragas_generated` and treated as coverage tests, not as representative of real users
- [x] **EVAL-06**: An authenticated internal endpoint (`POST /api/internal/rag/run`, disabled in production unless explicitly enabled) runs the real TypeScript retrieval pipeline and returns a trace (query transforms, candidates, scores, final context, answer, citations)
- [x] **EVAL-07**: The eval runner computes deterministic retrieval metrics (Recall@k, MRR, matched by gold span) and refusal metrics (correct-refusal rate and false-refusal rate, reported separately) without an LLM judge
- [ ] **EVAL-08**: The eval runner computes Faithfulness, Answer Relevance and Context Recall with DeepEval and Ragas using a pinned judge model from a different family than the generator, with telemetry disabled, and reports results per language and per category
- [x] **EVAL-09**: A baseline of the current system is recorded (three runs, config hash per run, mean and spread), and later phases compare against it with paired differences
- [ ] **EVAL-10**: CI (new `.github/workflows`) runs a PR smoke tier (deterministic metrics on the fixture corpus, schema parity, config check, type-check) and a nightly full tier (judge metrics); a PR fails when a deterministic metric drops beyond the baseline noise band
- [x] **EVAL-11**: `npm run test-rag` runs the eval smoke tier (the missing `scripts/test-rag-system.js` reference is fixed)
- [x] **EVAL-12**: Characterization tests lock today's behavior: strict mode returns "information not available" with no context, webSearch + strict uses Exa results, `source_images` stream and persist, `{{context}}` substitution in `RAG_SYSTEM_PROMPT`
- [x] **EVAL-13**: A config manifest lists every RAG env var once, and a `check-config` script (run in CI) fails when any of the five config locations is missing an entry

### Pipeline & Tenancy (PIPE)

- [x] **PIPE-01**: One retrieval pipeline module (`src/lib/rag/`) is the only code that calls embedding providers, retrieval backends and rerankers; text chat, embedded chat and voice all call it
- [x] **PIPE-02**: Every retrieval call requires a branded `TenantScope` that only `resolveTenantScope()` can create, after verifying workspace or organization membership server-side; an `organizationId` from the request body is never trusted directly
- [x] **PIPE-03**: Embedded chat resolves its tenant from the embed widget's server-side configuration (the owning workspace), never from the caller
- [x] **PIPE-04**: Voice retrieval resolves its tenant from a signed, expiring token minted by the app, not from a bare caller-supplied `userId`, and never falls back to a global search
- [x] **PIPE-05**: Context assembly (dedupe, grouping, source labels, links section, image handling) lives in the pipeline and is shared by all three entry points, without per-chunk N+1 lookups
- [x] **PIPE-06**: The pipeline returns a discriminated status (`ok | empty | error | degraded`); only a verified `empty` result may trigger the "information not available" refusal, and errors are logged and surfaced as errors
- [x] **PIPE-07**: Each pipeline stage has its own switch, timeout and degrade-to-skip path; an `AbortSignal` flows through all stages
- [x] **PIPE-08**: Unused retrieval modules (`retrieval-strategies.ts`, `optimized-search.ts`, `adaptive-retrieval.ts`, `reranker-adapter.ts`, never-called parts of `thinking-rag-enhancer.ts`) are removed; still-used logic is re-homed under `src/lib/rag/`
- [x] **PIPE-09**: With all new switches off (`RAG_PIPELINE=legacy`), the eval results reproduce the baseline within its noise band
- [x] **PIPE-10**: Node.js 22 is the documented and enforced runtime (`engines`, docs, CI), as required by the Weaviate and Qdrant clients

### Data Layer (DATA)

- [ ] **DATA-01**: One shared `ingest()` path and chunk writer serve chat/Config UI uploads, Nango sync, scrapers and image uploads
- [ ] **DATA-02**: Every chunk stores the same metadata: tenant, document ID, version, `is_current`, source, document type, document date, language, page or section, content hash, parser used, and the existing URL metadata
- [ ] **DATA-03**: The user can pick a document type per file at upload (financial/accounting report, contract/legal, invoice/receipt, product/technical, scanned/image), with a pre-selected default they can change; the default comes from DATA-10, and unclassified documents fall back to `general`
- [ ] **DATA-04**: The document type selects a processing profile (parser options, chunk size and boundaries, OCR, metadata extraction such as dates and financial figures), and profiles are defined as data, not branching code
- [ ] **DATA-05**: Docling runs in the sidecar as an async parse job (HybridChunker with table headers repeated in each chunk, explicit tokenizer, OCR languages for zh/en/it) and is switchable with LlamaParse; LlamaParse failure or a missing key falls back to Docling, and `parser_used` is recorded; OCR languages come from `RAG_SUPPORTED_LANGUAGES` through the LANG-02 registry, the legacy upload paths stop hard-coding LlamaParse `language: "en"`, and a fixture scan with Chinese text and Italian accents (è, più, già) comes out character-exact (delta delivered by Phase 3.2)
- [ ] **DATA-06**: Uploading a file whose normalized content hash already exists in the same tenant does not create duplicate chunks; hashes are never compared across tenants
- [ ] **DATA-07**: Uploading a new version of a document replaces the old one atomically (new version inserted, `is_current` flipped in one transaction, old version soft-superseded so existing message citations still resolve); retrieval returns current versions only
- [ ] **DATA-09**: An `invoice` document type extracts invoice fields into structured metadata defined by a Pydantic model (invoice number, issue and due dates, supplier and buyer names and VAT/tax IDs, currency, net, tax and gross totals, line items), keeps line-item tables intact in one chunk with their header, treats invoice numbers and tax IDs as exact terms, and makes supplier, date range and amount range filterable; extraction failures leave the document searchable as plain text and are reported
- [ ] **DATA-10**: Admins set default document types in the Config UI: a tenant-wide default (a fixed type or "auto-detect") and optional per-source defaults (chat upload, Config UI upload, each Nango connection or folder, scrapers, image upload); precedence is the type picked for the file, then the source default, then the tenant default, then `general`; admins can also change the type of an existing document, which re-processes it through the shared `ingest()` path as a new version
- [ ] **DATA-11**: PDFs that contain images (charts, photos, scanned pages inside a digital PDF) have those images extracted with their page number, captioned through the existing image-RAG captioning, and stored as image chunks linked to the document and page, so they are retrievable and appear as `source_images` like uploaded images
- [ ] **DATA-12**: Tiered parse routing (`RAG_PARSE_ROUTING=fixed|tiered`, default `fixed` = Phase 3 behavior): a sidecar preflight probe classifies each **page** with cheap rules (L1: pypdfium2 + pdfplumber — text layer, chars, image ratio, ruled tables, multi-column), sends only uncertain pages to the Docling layout model (L2) and, when `RAG_PARSE_VLM_DETECT=true` and cloud is allowed, to a VLM (L3), and routes each page range to the cheapest tier that fits, merging the ranges back in page order — `native` (existing extractors for txt/md/csv/html/docx), `fast` (Docling on pypdfium2, OCR and table structure off), `structured` (Docling full with TableFormer and zh/en/it OCR) or `premium` (LlamaParse) — within the document-type profile's `min_tier`/`max_tier`; a post-parse quality check (empty text, low chars per page, garbled-character ratio, language mismatch, tables hinted but missing, partial conversion) escalates one tier at a time, at most twice, and every attempt with its reason is recorded (spec: `.planning/specs/ingestion-routing.md`)
- [ ] **DATA-13**: Hard constraints come before quality, cost and speed: `RAG_PARSER_ALLOW_CLOUD=false` guarantees no file is sent to a cloud parser; a monthly premium-page budget per tenant and a per-document page cap stop tier-3 use when exceeded; a document that cannot reach the tier its check asks for keeps its best result and is marked `needs_review`; budget use is shown in the Config UI
- [ ] **DATA-14**: An `ingestion_jobs` ledger (RLS, server role only) records per document its status (queued … ready, failed, quarantined, needs_review, skipped_duplicate), class, tier, parser and version, attempts, pages, estimated cost, embedding profile, retries, error and per-stage timings; every stage is idempotent; parser output is cached per tenant by file hash, parser version and options, so re-chunking, the CHK-05 sweep and retries make zero parser calls
- [ ] **DATA-15**: Incremental ingestion is asynchronous: upload and sync routes return 202 with a job id at once; jobs are claimed from the ledger with `FOR UPDATE SKIP LOCKED` and a lease by a worker in the sidecar (no Redis/Celery); documents have a stable identity (tenant, source, source key) so an unchanged hash is skipped, a changed hash becomes a new version (DATA-07) and a deletion at the source (Nango) soft-deletes the current version; retries back off exponentially up to 3 times and failed jobs are listed in the Config UI with retry; the UI shows status until "ready"; a ≤ 20-page digital PDF is ready within 60 s p95 with fake providers; optional `RAG_PARSE_PROGRESSIVE` publishes a provisional fast-tier version first and replaces it with the routed tier
- [ ] **DATA-16**: Bulk backfill (`npm run rag:backfill`): hashes and deduplicates within the tenant before parsing; a required dry run on a 1% sample (at least 20 files) reports class shares, projected pages per tier, cost and wall time, and the run refuses to start without `--budget`; jobs run at low priority with a `batch_id` and bounded concurrency so uploads are not starved; chunk rows are written in batches; a killed run resumes by skipping ready jobs; `RAG_EMBED_BATCH_MODE=batch_api` sends backfill embeddings through the OpenAI Batch API (≤ 50,000 inputs per batch, polled and resumable); a backfill into a new embedding profile goes live only through the EMB-05 gate; an optional `--runner ray` (Ray Data, off by default, optional sidecar dependency group) distributes the same per-document stages across a Ray cluster while the ledger, budget, dedup, priority and resume rules stay identical, and the default `--runner worker` needs no Ray
- [ ] **DATA-17**: A parser test set (digital text, table, multi-column, scanned zh/en/it, invoice fixtures with expected table grids, reading order and headings) scores each tier on text similarity, table cell F1, structure accuracy, seconds per page and cost per page, and golden items on those documents report Recall@k per tier; routing thresholds are chosen on the dev split, and `tiered` must not lower Recall@k or correct-refusal against `fixed` beyond the noise band while the report shows premium page share and projected cost per 1,000 pages
- [ ] **DATA-08**: Retrieval can filter by date range, source, document, document type and language
- [ ] **DATA-18**: Documents can carry scope tags (`applies_to`: region, legal entity or branch, department) from a tenant-defined vocabulary edited in the Config UI; tags are set at upload or by an admin, may be suggested by a small model at ingestion for admin confirmation, are copied to every chunk as a filterable column, and become a DATA-08 filter (`scopes`), so a question that names a scope (a region, entity, branch or department) can be limited to documents tagged for it
- [ ] **DATA-19**: Cross-document supersession: DATA-07 only supersedes an earlier version with the same identity (tenant, source, source key), so an older version uploaded as a different file stays current next to the newer one; at upload a user or admin can mark a document as replacing another, and ingestion flags likely older versions (same document type, a normalized title that differs only by year or version markers, or high content similarity with conflicting numbers) as "possible newer version of X" for admin confirmation in the Config UI; confirming supersedes X through the DATA-07 transaction (`is_current` false, `superseded_by` set), and nothing is superseded without confirmation
- [ ] **DATA-20**: Documents carry optional `effective_from` and `effective_to` dates, extracted from the text by a small model with a confidence or set by an admin; with `RAG_EFFECTIVE_DATES` on, "current" means `is_current` and an effective window that contains today, a policy whose `effective_from` lies in the future is not used until that date, and an expired one is treated as historical (RET-11)
- [ ] **DATA-21**: Near-duplicate chunks across different documents of one tenant (the same FAQ pasted into 30 handbooks and wikis) are grouped at ingestion: exact duplicates by the normalized chunk `content_hash` (Phase 3), near-duplicates by MinHash/SimHash or an embedding similarity above a calibrated threshold (start 0.95); each chunk records a `dup_cluster_id` and the cluster keeps the list of source documents; every chunk row stays (versioning, deletes and citations keep working per document), clusters never span tenants, deleting or replacing a source document recomputes its clusters, and existing documents get cluster ids through a backfill job; behind `RAG_DUP_CLUSTERS` (off by default)
- [ ] **DATA-22**: Connector permissions are synced: documents from Nango sources (Google Drive, Notion, Dropbox) map the source's sharing (users and groups) to tenant access groups on every sync, a permission change at the source updates the document's groups on the next sync, and a source permission that cannot be mapped makes the document visible only to its uploader and the tenant admins (fail closed)

### Embeddings (EMB)

- [ ] **EMB-01**: Embedding providers are switchable: OpenAI `text-embedding-3-small` (kept), Voyage `voyage-4-large` (with `input_type`), and Qwen3-Embedding-8B through a hosted inference API (DeepInfra primary, OpenRouter fallback; query-side instruction prefix; MRL truncation and re-normalization)
- [ ] **EMB-02**: Each embedding profile (model + dimension) is stored side by side (`halfvec` where needed, partial HNSW index per profile), and switching the active profile is a pointer flip that can be rolled back
- [ ] **EMB-03**: The query-time embedding model is derived from the active index profile, and a model or dimension mismatch fails loudly at startup and per request
- [ ] **EMB-04**: A re-embedding job reads stored chunk text only (never re-parses), runs in batches, resumes from where it stopped, supports dry-run, and can roll back (extends `scripts/rag/reprocess-documents.js`)
- [ ] **EMB-05**: A new embedding profile can only be activated when it is complete and proven: (a) during a re-embed, every new or replaced document is written to both the active and the target profile (dual-write), so documents uploaded mid-migration are not missing; (b) activation refuses unless 100% of current chunks have a vector in the target profile — a query never searches a mix of old- and new-model vectors; (c) activation refuses unless the eval run on the target profile shows no regression beyond the noise band versus the active profile, with Recall@k reported separately for documents ingested before the migration; (d) every vector row records its `embedding_model` and dimension, and a same-dimension model mismatch (which pgvector would not reject) fails the EMB-03 check
- [ ] **EMB-06**: One model catalog holds, for every embedding model the app may use, provider, model id, supported dimensions, whether a dimension parameter may be sent, maximum input tokens, tokens per request, input types and list price, taken from the vendor's official documentation with the date read; Voyage `voyage-law-2` and `voyage-finance-2` (1024 dimensions, 16K and 32K input tokens) are available as embedding profiles served by the existing Voyage key, and every model check (startup, ingest, query) compares against the profile's own model
- [ ] **EMB-07**: A document type can be bound, deployment-wide or for one tenant (the tenant binding wins), to a profile scoped to that type; a scoped profile never becomes the global active profile, holds vectors only for its doc types, is filled by a re-embed run limited to its doc types and tenant scope, and while its binding is staged or active ingestion also writes it for new and replaced documents of that type and tenant (a failure records gaps and does not fail the document); the chunk stays in the global profile (additive), so removing a binding needs no re-embed
- [ ] **EMB-08**: In the v2 pipeline each active, non-stale binding in the request's tenant adds one dense leg, embedded with its profile in parallel with the global query embedding and fused with RRF under its own weight; the leg is restricted to its doc type and to the request's filters and tenant, its scores are never compared with the global profile's (similarity floor and refusal calibration ignore them), it has a timeout and a cap on legs per query, and a failing leg degrades the search stage instead of failing the request; voice and the legacy pipeline are unchanged; behind `RAG_DOMAIN_EMBEDDINGS` (default off)
- [ ] **EMB-09**: A binding is activated only through a gate that refuses unless every current chunk of its doc type in scope has a vector of the profile with its model and dimensions, a completed scoped re-embed run exists, and evidence recorded after the newest vector names the current global profile and the current binding as baselines, passed the comparison, holds at least 30 real (production or human) items of that doc type with no language sub-slice regressing, and shows no other slice regressing; rollback restores the previous binding when still complete, deactivation returns to global-only at any time, a binding whose evidence names an older global profile is skipped at query time until re-proven, and all of it is operable from the CLI and the admin Config UI by admins only
- [ ] **EMB-10**: A reproducible comparison per doc type runs, on one fixture or real database and one golden file, a baseline arm (global profile), a control arm (global profile plus a doc-type-filtered extra leg, no new vectors) and one arm per candidate profile, and reports Recall@k, MRR and refusal rates per doc type, language and cross-lingual pair with corpus, golden, noise, parameter and catalog hashes and the re-embed run ids; a candidate is recommended only if it beats both baseline and control on its doc type beyond the noise band without any regression elsewhere; the output is a validated contract that the gate consumes; public leaderboards are never used as evidence

- [ ] **EMB-11**: BGE-M3 (BAAI, MIT licence, 1024 dimensions, 8192-token input) is an open-source fallback embedding profile next to the EMB-01 profiles, activated through the EMB-05 gate like any other profile, so the knowledge base is not tied to one vendor: by default it runs through a hosted inference API (DeepInfra), and the same profile can instead be served by the Python sidecar on CPU for deployments that must keep text in-house; both serving modes return identical dense vectors for the same input (checked in CI on fixture text), so switching between them needs no re-embedding; only the dense output is used, because the lexical path (RET-03) already covers sparse matching; it is compared with the other profiles on every slice, including `cross_lingual` per language pair, and the report includes ingestion throughput, query latency and cost of both serving modes
### Embedding Fine-tuning (FT)

- [ ] **FT-01**: Fine-tuning is opt-in per tenant: an operator records `private` (models serving only that tenant) or `deployment` (shared models too) consent with an evidence reference (`rag_finetune_consent`); export, vector export, model registration and fine-tune bindings refuse any tenant whose consent does not cover the purpose; a tenant-private model is served only through Phase 3.1.1 bindings of that tenant, a shared model needs every trained tenant's `deployment` consent and an explicit tenant list; revoking consent taints every model version trained on that tenant in the same transaction, removes the evidence of its bound non-active slot so activation refuses, deactivates its bindings, and reports an active tainted model with rollback steps; master switch `RAG_FINETUNE=off` (off = today's behaviour)
- [ ] **FT-02**: The corpus export reads only the listed tenants' current, ready chunks with the service key, assigns a document-level split (sha256 of tenant and content hash or document id, 80/10/10; never pair-level), forces every document with gold evidence of a golden `test` item into the test split, and writes a bundle whose manifest and reports carry ids, hashes and counts only
- [ ] **FT-03**: An LLM writes about three queries per chunk (keyword, question, colloquial) in the chunk's language (zh/en/it), plus a configurable cross-language share, as Pydantic-validated tool output, cached by chunk content hash and prompt version, with a required budget and a dry-run cost projection
- [ ] **FT-04**: Queries are filtered in order: shape and language; verbatim copy (normalized character 5-gram containment ≥ 0.6 or longest common substring ≥ 0.7 of the query); near-duplicates (character 3-gram Jaccard ≥ 0.8); overlap with any golden question; an LLM answerability judge (round-trip filtering optional, off by default); every drop is reported by reason and language
- [ ] **FT-05**: Expert-confirmed failed-query pairs exported by Phase 5.1.1 (its `TrainingPair` contract, masked queries, chunk ids only) are imported for the bundle's tenants only with text resolved from the tenant's bundle; `held_out` pairs never train; the expert-rejected hard negatives are used first; pairs pass the rule filters and decontamination, are up-weighted, are clustered so near-identical queries share the strictest split, and are reported as a separate "real" slice
- [ ] **FT-06**: Hard negatives are mined per tenant with the production model (stored chunk vectors plus query vectors computed through `@/lib/rag`) or a sentence-transformers model (`mine_hard_negatives`), with a relative margin (default 0.05), rank range, neighbour-chunk and duplicate-content guards, negatives for train pairs from train documents only, and an LLM-audited false-negative rate whose 95% upper bound must not exceed 0.15
- [ ] **FT-07**: Training is reproducible on an operator GPU box or a hosted GPU container from a test-free kit, a pinned training image and lock: sentence-transformers `CachedMultipleNegativesRankingLoss` by default (GISTEmbed and Matryoshka optional), `NO_DUPLICATES` batching, pinned base model revision, seed and recorded library versions; CPU tests use fakes and a tiny in-test model
- [ ] **FT-08**: Offline evaluation on the held-out documents reports Recall@10, MRR@10 and nDCG@10 per language, language pair and source for the base, fine-tuned and production models with paired intervals; a model registers only if it beats production by the noise band, regresses no language slice beyond it, and beats the base; activation still goes only through the EMB-05 gate on the domain golden set (real items once they exist, EVAL-14) including the cross-lingual and general slices
- [ ] **FT-09**: A fine-tuned model is served from an OpenAI-compatible endpoint through one of two fixed 1024-dimension halfvec slot profiles with their own partial HNSW indexes; binding refuses an active, rollback-target or non-empty slot; a probe check proves the endpoint serves exactly the registered weights and prompts before any vector is written; the slot is filled by `npm run rag:reembed` and activated and rolled back by the existing pointer flip, or scoped and served through Phase 3.1.1 bindings, so one index never holds two models' vectors
- [ ] **FT-10**: A model registry (`embedding_model_versions`) records each version's base model and revision, tenant keys, dataset and config hashes, offline metrics, prompts, probe vectors, artifact location (no credentials) and status (`registered`, `bound`, `retired`, `tainted`); text-bearing bundle files are pruned after 30 days or when a tenant revokes consent; reports and logs never contain chunk or query text

### Retrieval (RET)

- [ ] **RET-01**: Retrieval backends are switchable — pgvector (kept permanently, default), Weaviate and Qdrant — behind one `RetrievalBackend` interface that only accepts a `TenantScope`
- [ ] **RET-02**: Each backend runs hybrid retrieval (lexical + vector, filters applied before search) and the results are fused with reciprocal rank fusion
- [x] **RET-03**: Lexical search works for Chinese, English and Italian on all three backends using one shared application tokenizer that writes a `lexical_text` field; a Chinese exact-term test (model numbers, IDs, names) passes on every backend
- [ ] **RET-04**: The pgvector hybrid function is callable only by the server role, never by `anon`
- [ ] **RET-05**: Supabase stays the only source of truth; a trigger-fed outbox and a drain worker sync inserts, updates, deletes (including cascade deletes) and re-embeds to Weaviate and Qdrant, and a reconcile job detects and repairs drift
- [ ] **RET-06**: Weaviate uses one tenant per workspace; Qdrant uses a shared collection per embedding profile with an `is_tenant` index and a tenant filter injected by the adapter on every query and prefetch
- [ ] **RET-07**: Chunk IDs returned by Weaviate or Qdrant are re-validated against Supabase under the caller's scope before use
- [ ] **RET-08**: A cross-tenant canary test suite (personal vs organization, null organization, removed member, after delete, after version replace, after re-embed) runs against every backend in CI and is a release gate
- [ ] **RET-09**: Each tenant and backend has an index-ready state; if an external backend is not ready or fails, retrieval falls back to pgvector and reports `degraded`
- [ ] **RET-10**: Filtered vector search does not lose results when the filter is selective (tenant, document type, date, `documentRefs`): pgvector runs with `hnsw.iterative_scan` (pgvector ≥ 0.8) so a filtered HNSW scan keeps going until it has k matching rows; when the filter matches fewer rows than a configurable cutoff, retrieval does an exact (brute-force) scan over the matching rows instead of the graph; Qdrant creates its payload indexes (tenant, doc type) before data is loaded and uses ACORN for combined strict filters; Weaviate keeps its default ACORN with `flatSearchCutoff`; the eval adds a `selective_filter` category (a small tenant or a rare document type, ≤ 3% of rows) whose Recall@k must match the unfiltered exact-search answer
- [ ] **RET-11**: Version-aware retrieval: the default stays `is_current` only (Phase 4 D-05); a `versions: current | all | range` filter lets a query include superseded versions only when it explicitly asks about history or a comparison between periods (set by QRY-10 or by an explicit user filter); superseded chunks enter the context labelled with their version and effective dates, citations show the version, tenant scope and `status = 'ready'` still apply, and the semantic cache bypasses such queries
- [ ] **RET-12**: Structured table lookup (`RAG_TABLE_LOOKUP`, off by default): tables found by the parser are also stored as typed rows (column names from the header, tenant columns, document, version, `is_current`, chunk ids; RLS, server role only); a deterministic lookup leg matches query terms against column values (the values named in the question, whatever the table holds) within the verified `TenantScope` and adds the chunks of the matching rows as an extra RRF list, following the Phase 4 D-24 `exact_id_lookup` pattern; the matching row reaches the context together with its header; the LLM never writes SQL
- [ ] **RET-13**: Result diversity in the v2 pipeline (`RAG_RESULT_DIVERSITY=off|collapse|mmr`, default off): `collapse` keeps only the best-ranked chunk of each DATA-21 duplicate cluster in the final top-k and lists the other source documents of that cluster under its citation; `mmr` also applies maximal marginal relevance after rerank (lambda chosen by an eval sweep, recorded) so the top-k covers different content; it runs after rerank and before Phase 6 D-07 sub-question reservation, never removes the only chunk of a sub-question, and is promoted from the Phase 4 backlog item "MMR diversity after rerank"

### Rerank & Context (RNK)

- [ ] **RNK-01**: Rerankers are switchable — Cohere `rerank-v5.0-pro` / `rerank-v5.0-fast` and Voyage `rerank-3` (with `rerank-2.5` as the multilingual fallback), plus the existing local BM25 reranker — and run after hybrid retrieval on an enlarged candidate pool
- [ ] **RNK-02**: The candidate pool size and final top-k are chosen by an eval sweep, not hard-coded; the sweep grid includes a pool of 25 (with 50, 75 and 100) and the report adds nDCG@k, where k is the number of chunks actually sent to the LLM (delta delivered by Phase 4.2)
- [ ] **RNK-03**: The most relevant chunks are placed at the start and end of the context; adjacent chunks from the same document are merged; the context respects a token budget
- [ ] **RNK-04**: Context compression (relevant-span extraction where the reranker supports it) is available behind a switch
- [ ] **RNK-05**: The system refuses to answer when the top rerank score is below a threshold calibrated per reranker provider and language on the dev split and checked on the holdout split
- [ ] **RNK-06**: When the reranker times out or fails, the fused order is used and threshold refusal is disabled for that request
- [ ] **RNK-07**: Refusal operating points per RAG mode: `rag_eval.calibrate refusal` records for each cell the full sweep (every candidate threshold with its false-answer rate, i.e. no-answer items answered, and its false-refusal rate, on dev and holdout) and picks one threshold per mode from targets in `eval/config/refusal-calibration.json`: strict mode caps the false-answer rate (default 5%) and takes the lowest false-refusal threshold that meets it; balanced and flexible keep today's false-refusal target, because a refusal there only removes knowledge-base context and the general-knowledge answer is labelled; the cell key gains the mode, a mode without its own calibrated threshold uses today's single threshold (so with the new targets unset the result equals Phase 4 D-18), cells stay invalidated when the reranker or embedding model or the tokenizer changes (D-17), and the report states which error each mode favours

### Retrieval Defaults (DFLT)

- [ ] **DFLT-01**: With no retrieval variable set, every entry point runs the v2 pipeline with hybrid search, `RAG_RERANKER=auto`, threshold refusal on and the eval-chosen fallback floor, and `RAG_PIPELINE=legacy` restores the previous behaviour exactly (zero paired differences against the legacy baselines, legacy characterization unchanged)
- [ ] **DFLT-02**: `RAG_RERANKER=auto` reranks with Cohere when `COHERE_API_KEY` is set and with an eval-chosen local fallback (local BM25 or fused order) otherwise; a missing key under `auto` never marks a request degraded, and Voyage is used only when named
- [ ] **DFLT-03**: While no calibrated rerank cell applies, v2 refuses with the legacy relevance rule (`RAG_REFUSAL_FLOOR=legacy_rule`) or the similarity floor, whichever the pre-registered rule picks; strict mode's "information not available" stays correct and false refusals do not rise beyond the noise band
- [ ] **DFLT-04**: When `RAG_PIPELINE` is unset and the database lacks `hybrid_search_chunks`, the process serves the legacy pipeline with one error log; an explicit `RAG_PIPELINE=v2` keeps failing loudly
- [ ] **DFLT-05**: The new defaults are adopted only after a gate pre-registered in `eval/config/defaults-gate.json` passes on both fixture modes against the baselines in force (slices within the noise band, ingest Recall@10 at least 0.6195, refusal rates, categories with n of at least 8, latency budgets), with and without fixture cells; the decision is recorded with its numbers and is re-run on the real golden dev split once it reaches the live minimums
- [ ] **DFLT-06**: The new switch and value are mirrored in every config location and the eval pin; CI keeps two legacy smoke tiers with zero paired differences next to the default tiers; AGENTS.md and the deployment guide state the defaults, the vendor data flow under `auto`, the upgrade steps and the switch back
- [ ] **DFLT-07**: Real Cohere and Voyage rerankers are measured once on the fixture dev split within a 600-request cap (quality against the local paths, p95 latency for 75 candidates against the chat and voice budgets), report-only, and the decision record takes an entry point off hosted rerank when it fails

### Query Layer (QRY)

- [ ] **QRY-01**: Follow-up questions in text chat are rewritten into standalone queries using the conversation history (LlamaIndex condense-question method), keeping the user's language and numbers, names and IDs verbatim; standalone questions pass through unchanged; when the terminology dictionary is on, the rewrite prompt receives the matched dictionary entries (surface form → canonical, kind) as a glossary and keeps canonical terms verbatim in the rewritten query; the original query is still retrieved (amended 2026-11-24 by Phase 4.1.1)
- [ ] **QRY-02**: Multi-query expansion generates several query variants and fuses their results with reciprocal rank fusion (LlamaIndex `QueryFusionRetriever` method); dictionary-derived variants (TERM-07) count toward the multi-query variant cap, and multi-query does not re-generate a variant equal to the terminology variant (amended 2026-11-24 by Phase 4.1.1)
- [ ] **QRY-03**: HyDE (LlamaIndex `HyDEQueryTransform` method) is available, off by default, never used in voice; HyDE receives the same terminology glossary as QRY-01 so the hypothetical document uses the canonical terms (amended 2026-11-24 by Phase 4.1.1)
- [ ] **QRY-04**: Compound questions are decomposed into at most four sub-questions (LlamaIndex `SubQuestionQueryEngine` method), producing sub-questions only — never a synthesized answer
- [ ] **QRY-05**: A router reuses the existing query classifier to decide per query which transforms run; each transform has its own switch, timeout and latency budget, and the original query is always retained in retrieval
- [ ] **QRY-06**: The LlamaIndex implementation (default) is native TypeScript following LlamaIndex's algorithms and prompts, with no framework call at query time; both implementations use structured outputs defined by the Pydantic/Zod contract
- [ ] **QRY-08**: An admin can switch the query layer between LlamaIndex (default) and LangChain (`@langchain/classic`, confined to one adapter that wraps `src/lib/rag/` as a retriever, with its zod 4 isolated from the app's zod 3) in the Config UI (`RAG_QUERY_FRAMEWORK=llamaindex|langchain`); both produce the same transform outputs and are compared in eval
- [ ] **QRY-07**: Voice uses a reduced profile (history rewrite, hybrid retrieval, optional fast reranker) that stays within its latency budget
- [ ] **QRY-09**: Decomposition completeness: every protected token and every named entity, year and scope term (from the rewrite-gate lexicon and the DATA-18 vocabulary) in the original question must appear in at least one sub-question; when one is missing, a sub-question for it is added (within the limit of four) or the decomposition is discarded and the original query is used, and the trace records the check
- [ ] **QRY-10**: Per-sub-question filters (`RAG_QUERY_SUBQ_FILTERS`, off by default): the decomposer may attach a filter to each sub-question, chosen only from allowlisted fields (date range, RET-11 version scope, DATA-18 scope tags, document type, language) and validated by Zod; such filters can only narrow the server-verified `TenantScope`, never widen it or change the RAG mode or tool use; a filtered sub-question that returns nothing falls back to the same sub-question without its filter; this is the only exception to the Phase 6 rule that query rewriting never changes filters other than the R2 date range, and it applies only while the switch is on
- [ ] **QRY-11**: The fixture golden set gains `version_compare` (the same policy in two periods) and `scoped_compound` (a question that also names a region or branch) categories in zh/en/it with gold evidence per sub-question; the eval reports all-evidence recall (the share of items where the gold span of every sub-question is retrieved) and sub-question coverage, the switches ship only if these improve over single-pass retrieval, and no other slice drops beyond the noise band
- [ ] **QRY-12**: Follow-up fallback without an LLM: every turn stores its standalone query (the condensed query, or the original when no condensing was needed) in the message metadata; when the rewrite gate asks for `condense_history` but `condense` is skipped (timeout, error, protected token lost; Phase 6 D-28), retrieval adds a deterministic variant made of the previous turn's standalone query plus the current follow-up (the previous standalone question followed by the elliptical follow-up), fused with RRF next to the original, so a skipped condense never leaves only the bare follow-up; the variant is traced and does not count against the LLM variant limit
- [ ] **QRY-13**: The WhatsApp channel passes conversation history to the chat pipeline: today `src/lib/whatsapp/webhook-handler.ts` sends only the current message ("Always fresh context, no history"), so an elliptical follow-up is retrieved without context; behind `RAG_WHATSAPP_HISTORY` (off by default) the handler sends the last turns of that WhatsApp conversation (the Phase 6 D-16 window: 6 turns, each truncated to 1,000 characters, assistant turns stripped of sources), scoped to the same sender and session, the existing reset command clears it, and the fixture `multi_turn` items also run through the WhatsApp entry point
- [ ] **QRY-14**: Knowledge-base scope gate (`RAG_SCOPE_GATE`, off by default): after the embed stage and before search, a check with no LLM call (under 5 ms) compares the query embedding with per-tenant scope centroids built at ingestion from document types and DATA-18 scope tags, with no built-in topic list (what is in scope is learned only from each tenant's own documents and tags, and an admin may add tenant-specific out-of-scope examples in the Config UI), and labels the query `in_scope`, `out_of_scope` or `unsure`; only `out_of_scope` above a confidence threshold calibrated on the fixture answerable and no-answer items (with the RNK-07 false-refusal target of the mode) skips retrieval: strict mode gives the "information not available" text (or calls webSearch when it is on), balanced and flexible answer without knowledge-base context and label it; `unsure` always retrieves; the label and score are on the trace; voice keeps it off until its latency is measured within budget; the fixture set gains synthetic off-domain no-answer items in zh/en/it (questions about a topic none of the fixture documents cover, against a corpus with topically adjacent passages), and the switch ships only if correct refusals rise and false refusals stay within the noise band

### Terminology (TERM)

- [ ] **TERM-01**: Domain terminology lives in Postgres in two layers: a deployment-wide shared layer and a per-tenant workspace layer that can add entries and suppress shared ones; single-tenant deployments use the shared layer only; the tables are service-role only (RLS on, no browser access), and a tenant's effective dictionary never contains another tenant's entries (two-tenant tests)
- [ ] **TERM-02**: Every dictionary change increments its layer's version in the same transaction as an append-only audit row (actor, action, before/after, version); writes carry the expected version and fail on a stale one; the effective version used by a request is recorded in its trace and, when the dictionary is on, in its `retrievalConfigHash`
- [ ] **TERM-03**: Admins (AGENTS.md §12 admin auth, workspace scope verified server-side) list, create, edit, delete and suppress entries, read versions and audit, and preview a query's expansion through Zod-validated admin routes; the body can never name an actor or tenant
- [ ] **TERM-04**: Every write and import is validated before it reaches SQL: conflicting mappings, chains, cycles, overlapping equivalence sets, one-character Han variants, stopword-only or tokenless variants and limit violations are rejected with row-level issues; cross-layer overrides are reported
- [ ] **TERM-05**: Admins import a dictionary from CSV with a dry-run report (create/update/unchanged/delete, issues) and an atomic apply that re-checks the version, and export it as formula-safe CSV; files are limited to 1 MB and 5,000 rows
- [ ] **TERM-06**: Under `RAG_PIPELINE=v2` with `RAG_TERMINOLOGY` on, matched entries (Han substring longest-match with ≥ 2 characters, Latin token-boundary phrases, identifier forms) expand the query one hop into a separate lexical RRF list with its own weight and hard caps, leaving the original dense and lexical lists unchanged; a dictionary failure degrades the request instead of failing it; switched off, candidates and the config hash are identical to today's; voice runs the expansion within its stage budget
- [ ] **TERM-07**: With `RAG_TERMINOLOGY_DENSE` on, one dense-only query variant with canonical terms substituted is added after translated variants (never in voice), within `MAX_QUERY_VARIANTS`
- [ ] **TERM-08**: The query stage exposes the matched entries (surface form, canonical, kind, language) and the dictionary version for the Phase 6 query transforms
- [ ] **TERM-09**: With `RAG_TERMINOLOGY_MINING` on, missed requests (empty, refused, degraded without candidates; never eval) are recorded per tenant with a PII-masked query, kept 30 days (interim source until Phase 5.1.1's retrieval log replaces it); `npm run rag:terms:mine` proposes candidate terms (support ≥ 3, absent or rare in that tenant's corpus, not already in the dictionary) for expert review; candidates are never applied automatically and are accepted only by creating an entry through the validated path
- [ ] **TERM-10**: The golden set holds colloquial-term items in zh, en and it whose wording does not occur in the corpus, identifier-alias items and no-answer controls containing dictionary terms; the eval compares dictionary off and on and the phase is complete only if the colloquial-term slice improves and no other slice, language or category drops beyond the noise band and no-answer refusals are unchanged; all three switches stay off until real (`production`/`human`) colloquial items pass the gate
- [ ] **TERM-11**: Admins maintain the dictionary in a Config UI Terminology panel (layer and workspace, entries, validation issues, import/export, preview, versions/audit, mined candidates), designed from a UI-SPEC

### Generation (GEN)

- [ ] **GEN-01**: When the selected chat model is Claude, the answer is generated through the direct Anthropic API with Citations enabled (one plain-text document per chunk), using an OpenRouter-to-Anthropic model ID map kept in the five model locations; tools, MCP and webSearch keep working or the turn falls back to the existing path
- [ ] **GEN-02**: For other models, the prompt asks for chunk-ID citations, and the server parses them from the stream, drops unknown IDs and validates each against the context actually sent
- [ ] **GEN-03**: Both paths produce the same persisted `citations[]` record with a snapshot of the cited text, so citations still resolve after documents are re-chunked or replaced
- [ ] **GEN-04**: Structured output is used for the non-Claude citation list and for helper calls; it is never combined with Claude Citations in one request
- [ ] **GEN-05**: After the answer streams, the sidecar scores groundedness: HHEM-2.3 via the Vectara API when the Vectara key is set and opt-in is on (Chinese and English); HHEM-2.1-Open locally for English when there is no key; Italian and other unsupported cases are recorded as "not checked"
- [ ] **GEN-06**: The score and its status are stored in message metadata and logs, and the UI shows a three-state badge (verified / possibly unreliable / not checked) in strict and balanced modes only; answers are never blocked
- [ ] **GEN-07**: Existing behavior is unchanged: strict-mode "information not available", webSearch + Exa, `source_images`, `{{context}}`, refusal text in the user's language; refusal and fixed-notice texts come from the LANG-09 registry in the language of the question, and today's English text stays byte-identical
- [ ] **GEN-08**: Partial-answer rule (`RAG_PARTIAL_ANSWER_RULE`, off by default): in strict mode a localized instruction (zh/en/it) with one worked example is appended after the `{{context}}` substitution, without changing `RAG_SYSTEM_PROMPT`: answer the parts the context covers, state explicitly for each uncovered part that the documents do not say ("文档中没有说明"), and never fill a gap with general knowledge; when strict mode calls webSearch because the context is insufficient (current rule, kept), the answer keeps what the documents say and what the web says in separate, labelled parts; balanced mode keeps its design but must label any general-knowledge supplement
- [ ] **GEN-09**: Every factual sentence must carry a citation: the citation instruction (Phase 5 D-04) asks for one per factual sentence, the eval adds `uncited_sentence_rate` next to `citation_coverage`, and the UI marks answer sentences that carry no valid citation
- [ ] **GEN-10**: After the answer streams, claim-level grounding (`RAG_CLAIM_CHECK`, off by default) splits the answer into sentences, checks each against the context blocks sent (HHEM per sentence, or the GEN-11 judge), and marks unsupported sentences as "not confirmed by the documents" in the message metadata and UI; it never deletes or blocks text (blocking stays out of scope), and unsupported sentences are counted on the trace and can send the answer to the review queue
- [ ] **GEN-11**: Languages HHEM does not support (Italian and any other enabled language without HHEM) can be scored by an LLM judge from a different model family than the generator, opt-in (`RAG_GROUNDEDNESS_LLM_JUDGE`, off by default, which keeps "not checked"), with its own calibrated threshold and cost and latency reported
- [ ] **GEN-12**: The fixture golden set gains a `partial_answer` category (zh/en/it) where the documents answer only part of the question (e.g. a limit is stated but not what happens above it); the eval reports the share of answers that add content absent from the documents on these items, gated at 0 in CI, and checks that the covered part is still answered
- [ ] **GEN-13**: When a question was decomposed, the answer is organized per sub-question (for a comparison: each period, then the differences, then the impact on the named scope), every part cites its own blocks, and a sub-question with no supporting block says the documents do not cover it (GEN-08 rule) instead of being dropped silently
- [ ] **GEN-14**: Version-aware answers: every context block carries its document version and effective date (a version label and an effective date, rendered in the answer language); when blocks from documents of the same type and topic give conflicting values, the answer uses the latest effective version and names it, mentions an older version only when the question asks about history, never gives both conflicting values as alternatives, and the conflict is traced and sends both documents to the admin review queue as a DATA-19 supersession candidate
- [ ] **GEN-15**: Relevance rule in the answer prompt: behind `RAG_CONTEXT_RELEVANCE_RULE` (off by default), an instruction added outside the admin's `RAG_SYSTEM_PROMPT` (the `{{context}}` placeholder and the admin's text unchanged) tells the model that context about a neighbouring topic does not answer the question (a passage on an adjacent subject retrieved for a question that no document covers): strict mode gives the LANG-09 "information not available" text (or calls webSearch when it is on), balanced and flexible must not present such context as the answer and label any general-knowledge answer; fixture `off_topic_context` items (no-answer questions whose top chunks are topically adjacent, with scores both below and above the refusal threshold) report the share of answers that repurpose adjacent context, gated at 0 in CI with the fake model and measured nightly with the judge; with the switch off the EVAL-12 strict characterization stays byte-identical
- [ ] **GEN-16**: Calculation tool (`RAG_CALC_TOOL`, off by default): a deterministic, sandboxed tool in the chat tool loop next to `useDocument` and `webSearch` (reached by embed, WhatsApp and voice through the same routes) evaluates a structured calculation and never runs free-form code: named operands, each with value, unit and source (`question`, or a chunk id from the context actually sent), and a fixed set of operations (add, subtract, multiply, divide, min, max, per-item cap, sum, percentage, rounding with a stated rule, difference between dates) in decimal arithmetic; it rejects mixing units or currencies unless a conversion factor is itself a sourced operand, caps operand count and nesting depth, and returns the result with every step; it is offered when the query classifier or the rewrite-gate protected-token rules find quantities in the question or the context, and then an instruction outside the admin's `RAG_SYSTEM_PROMPT` asks the model to extract operands and rules into the tool and list each item's step before the total; the tool holds no domain knowledge (every rule it applies comes from a cited passage or the question), values from SEC-05 fact tools take precedence over document values, and models without tool support use the GEN-17 structured trace instead
- [ ] **GEN-17**: Calculation check (`RAG_CALC_CHECK`, off by default): an answer that states a computed number carries a structured calculation trace (operands with sources, operations, result; a Pydantic contract with generated Zod), from the GEN-16 tool call or from structured output; the server recomputes it deterministically, checks that every document operand appears in its cited chunk and every user operand in the question (numbers normalized per language: digit grouping, decimal marks, full-width digits, units), and that the number stated in the answer equals the recomputed result; on a mismatch it appends a correction notice from the LANG-09 registry with the recomputed value (streamed text is never silently rewritten), stores both values in the message metadata, marks the trace and sends the answer to the review queue; an operand it cannot locate marks the answer "calculation not verified"; voice speaks the recomputed value

### Chunking (CHK)

- [ ] **CHK-01**: Every chunk stores its section path (`metadata.section_path`, e.g. "第5条 适用范围") and the path is prefixed to the text used for embedding and `lexical_text`, not repeated in the text sent to the LLM; this fixes `src/lib/document-processor.ts` keeping only `chunk.content` and dropping section/subsection; Docling fills the same field from its heading hierarchy (deterministic form of former v2 RQ-01)
- [ ] **CHK-02**: The contract/legal profile recognizes clause numbering ("第X条", "1.", "(一)", "Art.", "Article") and keeps a clause — including "但以下情况除外：" and its list — in one chunk where possible; an over-long clause is split by item, and every piece carries the clause heading (former RQ-03)
- [ ] **CHK-03**: Parent-child retrieval: ingestion stores parent chunks (whole clause or section) and child chunks (128–256 tokens); only children are vector- and lexically indexed; a child hit returns its parent, a parent hit several times is included once, parents count against the RNK-03 token budget and are filtered by `TenantScope`; switch `RAG_PARENT_CHILD`, compared on/off in eval (former RQ-02)

### Security (SEC)

- [ ] **SEC-01**: Ingestion scans for prompt-injection phrasing in Chinese, English and Italian ("忽略之前的指令", "你现在是", "ignore previous instructions", "ignora le istruzioni precedenti", …) using rules stored as data; matching documents are marked `quarantined`, excluded from retrieval, and can be released or deleted by an admin in the Config UI
- [ ] **SEC-02**: Retrieved content is wrapped in `<documents><doc id="…">…</doc></documents>` (with same-name tags inside documents escaped) and the system prompt states that tagged content is reference material, never instructions; the `{{context}}` placeholder of `RAG_SYSTEM_PROMPT` is kept and wrapping happens before substitution; the Claude Citations path carries the same statement; the statement also forbids outputting links or contact addresses that appear only in retrieved material and asking the user for passwords, codes or log-ins (delta delivered by Phase 5.2; the fixed `<documents>` tag with escaping is kept as decided in Phase 5.1 D-02)
- [ ] **SEC-03**: Retrieved chunks are checked for injection before reaching the LLM: SEC-01 rules by default, plus pluggable detectors (Meta Prompt Guard run locally in the sidecar, Lakera Guard via API), each behind a switch; flagged chunks are dropped or down-weighted and recorded in the trace and logs
- [ ] **SEC-04**: The fixture golden set gains an `injection` category with zh/en/it injection documents (a planted instruction to ignore earlier instructions and state a false fact); the attack-success rate is reported and gated at 0 in CI, and no other category gets worse
- [ ] **SEC-05**: A design document (no implementation in this milestone) describes how critical facts such as prices and stock are read from the database through tools/MCP instead of from document text
- [ ] **SEC-06**: The generated answer is checked before it reaches the user (`RAG_OUTPUT_GUARD`, off by default), extending the Phase 5.1 image-host allowlist (`src/lib/safe-image-hosts.ts`) to all links: a streaming-safe filter holds back a URL, domain or e-mail address until it is complete, keeps it only if its domain is on `RAG_OUTPUT_LINK_ALLOWLIST` (plus the app's own domain and same-turn webSearch result URLs whose result was not flagged), and otherwise replaces it with a neutral placeholder; a link that appears only in retrieved document text is not trusted for that reason; credential and account requests (zh/en/it rules stored as data) are blocked with a fixed notice when they occur together with a removed link or come from flagged content, and otherwise add a warning; WhatsApp replies pass through the same filter and the Baileys service stops fetching server-side link previews for non-allowlisted hosts (folds in backlog Phase 999.1); every removal, block or warning is traced and sends the source chunk to the review queue; SEC-04 counts a phishing link or credential request in the answer as a successful attack
- [ ] **SEC-07**: Ingestion detects hidden text: text whose colour matches or nearly matches its background, very small font sizes, text outside the visible page area or behind other objects, zero-width characters, and hidden or vanished runs and comments in Word files; detected text is kept out of embedding, `lexical_text` and the LLM text, and the document goes to `quarantined` with the hidden spans shown to the admin; parser paths that cannot report styles (for example a plain-text LlamaParse result) record `hidden_text_check = not_checked` on the document instead of passing it

- [ ] **SEC-09**: Upload approval (`RAG_UPLOAD_APPROVAL=off|members|all`, default off): when on, uploads from members (or from everyone) enter a `pending_review` state on every ingestion path (chat and Config UI upload, Nango sync, scrapers, image upload, WhatsApp), are excluded from retrieval and the semantic cache, and become searchable only after an organization admin (in single-tenant mode, the deployment admin) approves them in the Config UI; admins can exempt named connectors or uploaders; every document and chunk keeps its uploader (`documents.user_id`) and approver

- [ ] **SEC-11**: Red-team runs: beyond the Phase 5.1 D-14 nightly attack-success run, a red-team run can also be started from the Config UI, replays the SEC-04 set plus a growing attack corpus (new published techniques, hidden-text and link variants, cases promoted from production) against the full pipeline, reports attack success per technique and language, and opens a review-queue case for every success
- [ ] **SEC-12**: Document access groups inside a tenant (`RAG_DOC_ACCESS_GROUPS`, off by default): today every member of an organization can retrieve every organization document; with the switch on, admins define access groups per tenant (in single-tenant mode for the deployment's users), each document carries `access_groups` (default `all`, which keeps today's behaviour) set at upload or by an admin and copied to its chunks, parents, translations and table rows, and retrieval filters by the caller's groups **before** ranking (pre-filter inside `hybrid_search_chunks` and every other retrieval leg, server role only, on pgvector and through the Phase 7 adapters for Weaviate and Qdrant); the caller's groups are resolved on the server from the verified session or signed scope token, never from the request body; embedded chat visitors only see `all` documents unless the embed configuration names a group; a group is never wider than the tenant
- [ ] **SEC-13**: Every derived store respects access groups: the semantic cache key includes a hash of the caller's effective group set (and answers built from restricted chunks are only served to the same group set), the retrieval log, review queue and traces show restricted content only to members of its groups or admins, and after generation every cited chunk is checked against the caller's groups as defence in depth (a mismatch drops the citation, flags the answer and logs a security event); the prompt is never the control

### Language support (LANG)

- [ ] **LANG-01**: The supported languages are one deployment-level setting chosen when the project is set up, not a silent default: `RAG_SUPPORTED_LANGUAGES` (one or more language codes from the LANG-02 registry; choosing one language is monolingual mode, which skips query-language detection, query translation and the cross-lingual slices) and `RAG_PRIMARY_LANGUAGE` (one of the chosen languages, used as the fallback when a language cannot be detected and for captions of images without a document), mirrored in the five config locations; first-run setup offers a single- or multi-select language picker in two places — `scripts/init-env.js` when it runs in an interactive terminal and the value is unset, and a first-run step in the Config UI — listing only registry languages whose pack is complete and suggesting the languages already present in existing documents, and writes the choice to `.env.local`; non-interactive deployments (Vercel, CI) set the two variables directly, and CI and the fixtures use `zh,en,it`; until the languages are chosen, `RAG_PIPELINE=legacy` works exactly as today and reads neither variable; when the pipelines are also unset (so a newer default such as Phase 4.1 DFLT-01 would select v2), the deployment keeps serving the legacy pipelines with one startup warning and a persistent Config UI banner pointing to the picker, and only an explicitly set `RAG_PIPELINE=v2` or `RAG_INGEST_PIPELINE=unified` without languages fails with `languages_not_configured` (owner decision 2026-11-25, same rule as DFLT-04); tenants cannot widen the set, and tenant-level language settings (XLG-04 translation targets, XLG-05 glossary) can only pick subsets of it
- [ ] **LANG-02**: A language-pack registry is defined once as Pydantic v2 data (with generated Zod): per language its script, sentence-ending punctuation, word segmentation method, stemmer, accent and elision folding, stopwords, OCR codes per parser (Docling engines, LlamaParse), rewrite-gate lexicon, refusal and fixed-notice texts, groundedness (HHEM) support, and whether a fixture corpus and golden slices exist; the language fields of the contracts (`golden.py`, the eval corpus and drafting tools) and the rewrite-gate `Lang` type validate against the registry instead of a hard-coded `zh|en|it` literal; adding a language means adding a registry entry, not a code branch
- [ ] **LANG-03**: Saving a language set is validated, and the Config UI refuses to save with a hard error when a chosen language lacks a complete registry pack (segmentation, OCR codes, lexicon, refusal text, fixture corpus and golden slice), when the active embedding profile or the active reranker does not declare support for every chosen language (the local BM25 reranker shares the lexical tokenizer, so it covers every language the tokenizer supports), when the primary language is not in the set, or when the set is empty; a language without groundedness support is a warning and is recorded as "not checked" (GEN-05)
- [ ] **LANG-04**: Ingestion-side and query-side settings are classified once: the existing per-chunk versions (parser, `lexical_version`, `embedding_text_version`, profile version; Phase 3 D-07) and the Phase 3.1 settings snapshot (`ocr_languages`) are combined into one ingestion fingerprint; changing an ingestion-side setting makes the Config UI show the number of affected documents, warn, and start a side-by-side rebuild of only those documents through the existing re-embed, relex and chunking-profile mechanisms, activated by a pointer flip after the eval passes and rollbackable; query-side settings take effect on save
- [ ] **LANG-05**: The language of every chunk is detected at ingestion with a confidence score, choosing only among the enabled languages: a document's language is the dominant language of its chunks, a mixed-language document keeps a per-chunk `language` and lists all its languages, and a chunk that cannot be detected is stored as `und` (today the document-level detector in `src/lib/rag/ingest/stages/enrich.ts` writes null and there is no chunk-level language) and processed with the primary language's pack; the detected languages feed the XLG-01 knowledge-base language shares
- [ ] **LANG-06**: Chunking on every ingestion path splits at the sentence-ending punctuation of the chunk's language from the LANG-02 registry (。！？ for Chinese, .!? for English and Italian) instead of the shared `SENTENCE_END` set, and keeps counting with `cl100k_base` as Phase 3 D-22 decided; the legacy routes that still split on spaces and estimate four characters per token are routed through `ingest()` or fixed the same way
- [ ] **LANG-07**: The Phase 4 D-07 lexical tokenizer (`Intl.Segmenter` plus Han bigrams, accent folding, Italian elision splitting, `LEXICAL_VERSION`, `rag:relex`) uses the Phase 4.1.1 TERM terminology dictionary (TERM-01..TERM-11) as its custom dictionary, with the XLG-05 glossary terms merged into it, so each tenant's own terms match as one term; Italian Snowball stemming is added behind a switch and turned on only if the eval shows a Recall gain on the it slice with no other slice dropping beyond the noise band (D-07 'no stemming unless the eval shows it is needed'); a dictionary or stemming change bumps `LEXICAL_VERSION` and rebuilds `lexical_text` as a LANG-04 ingestion-side change; fixture tests cover a synthetic multi-character dictionary term and an Italian singular/plural pair
- [ ] **LANG-08**: Query-language detection (today `src/lib/rag/lang/detect.ts` with its `confident` flag) reports a confidence and chooses only among the enabled languages; when confidence is low (short queries, codes, mixed scripts), a stronger detector (fastText language ID in the sidecar) is used, or the language the rewrite/translation model reports when that call runs anyway, and otherwise the language of the conversation's previous turn, then the user's UI language if it is enabled, then the primary language; the fixture set gains short, accent-free and mixed-script detection cases (two- or three-word queries without accents or with mixed scripts) in every enabled language
- [ ] **LANG-09**: The strict-mode refusal and every fixed notice (SEC-06 notices, groundedness badge texts) come from the LANG-02 registry for each enabled language and are chosen by the answer language, i.e. the language of the question; the UI language is used only when the question's language is not enabled; today's English text stays byte-identical for English answers
- [ ] **LANG-10**: Traces add the languages of the retrieved chunks next to the query language, its confidence and the answer language; on top of the existing `by_language` and `by_language_pair` eval reports, online judge scores (EVAL-15), helpful votes (EVAL-16) and the "information not available" rate are reported per language, with an alert when one language drops while the overall average holds
- [ ] **LANG-11**: Ingestion-side changes and language additions roll out gradually: a new embedding profile or ingestion configuration can be activated for chosen tenants or a traffic share first (today profiles switch globally; the Phase 7 tenant canaries are leak tests, not rollouts) (for example 10%) with per-language monitoring (LANG-10) before full activation, and rolled back per tenant; adding a language requires its registry pack and golden slice and records its baseline first, then reprocesses only documents stored as `und`, scanned documents and documents whose fingerprint is out of date, and requires switching first to an embedding profile that supports it; removing a language changes only the query side (no detection, translation or gate for it) and deletes no data, and the Config UI says that its documents stay searchable

### Cross-language & Cache (XLG, CACHE)

- [ ] **XLG-01**: The query language (script ratio plus zh/en/it stopword scores, mixed-language queries classified by dominant script) and the languages of the tenant knowledge base (share per language from the DATA-02 `language` field) are detected; when the query language is not a knowledge-base language above a 20% share, the query is translated by a small fast model into up to two knowledge-base languages, keeping protected tokens verbatim (rewrite-gate R7/R8); original and translated queries are retrieved in parallel and fused with RRF; the answer is written in the asker's language while cited quotes stay in the source language; translation has its own switch, timeout and budget, and can be turned off per embedding profile when the eval shows the multilingual embedding alone is enough; supported under both query frameworks (former RQ-04)
- [ ] **CHK-04**: Parent-child sizes are configurable in the Config UI per document-type profile: child size (tokens), parent mode (document structure — whole clause or section — with a token cap, or fixed size) and parent size, starting from child 256 / parent 1024 with presets 128/512, 256/1024 and 256/2048 plus custom values; the UI validates the choice — child must fit the active embedding profile's maximum input (hard error), parent must be at least twice the child (hard error), a parent/child ratio outside 4–8 and top-k × parent size above the RNK-03 context budget are warnings; a size change creates a new chunking profile that is re-chunked and re-embedded side by side from stored document text and activated by a pointer flip that can be rolled back (same mechanism as EMB-02/EMB-04); the maximum input is read from the EMB-06 model catalog, and for a doc type with an active EMB-07 binding the child must fit the smaller of the global and the binding profile's maximum input (amended 2026-11-24 by Phase 3.1.1)
- [ ] **CHK-05**: A chunk-size sweep runs the golden set against each candidate chunking profile and reports Recall@k, MRR, refusal rates, judge answer correctness, context tokens sent and latency, overall and per document type, language and question category (fact lookups versus context-heavy questions); the admin sees the comparison in the Config UI and picks the profile per document type, and the decision is recorded with its numbers
- [ ] **CHK-06**: A table cut across chunks always repeats its header row in every processing profile, not only `financial_report` and `invoice` (today `config/rag/processing-profiles.json` sets `repeat_table_header: false` for `general`, `contract_legal`, `product_technical` and `scanned_image`); a table continued on the next page without its own header row carries the last header forward; the change is an ingestion-side change (LANG-04) rebuilt side by side, and the eval shows the `table_split` slice improving with no other slice dropping beyond the noise band
- [ ] **CHK-07**: Row serialization (`RAG_TABLE_ROW_SERIALIZATION`, off by default): for table chunks, the embedding text and `lexical_text` also carry one "column = value" line per row (each column name joined to its cell value with the language pack's separators), while the text sent to the LLM keeps the Markdown table with its header; it ships on only if the `table_split` and `table` slices gain Recall or answer correctness
- [x] **EVAL-14**: The golden set also covers how real users ask: new categories `colloquial` (wording that differs from the document's terms), `ambiguous` (short or underspecified) and `typo` (misspellings, missing accents, mixed scripts), next to the existing ones; every report also splits results by provenance (`production`, `human`, `claude_draft`, `ragas_generated`, `synthetic_fixture`), and once real-user items exist the gate is computed on them, with synthetic items reported for coverage only
- [x] **EVAL-15**: A configurable share of production requests (sampled, PII-masked, tenant-tagged) is pulled from their Langfuse traces into a review queue, and an online judge scores a sample of them (faithfulness, answer relevance) with the scores attached to the Langfuse trace, so quality is measured after release and not only before it
- [ ] **EVAL-16**: Every RAG answer has a helpful / not helpful control (with an optional reason); the vote is stored with the message and sent to Langfuse as a score, and "not helpful" votes and "possibly unreliable" groundedness results automatically enter the review queue
- [ ] **EVAL-17**: Admins and per-tenant domain experts work the review queue in the Config UI (database-backed, tenant-isolated by RLS): they see the question, answer, retrieved chunks and trace, write the expected answer and span evidence, and promote the case into the golden set with provenance `production` (stored only in the gitignored private path, split assigned by the frozen document-group rule for domain sets (the item hash rule stays for existing sets), near-duplicates detected); promoted cases are never removed, so every production failure becomes a permanent regression test; a periodic report lists new failures by layer and category (amended 2026-11-24 by Phase 5.1.1; moved from Phase 7)
- [ ] **EVAL-18**: The fixture golden set gains a `table_split` category (zh/en/it): long tables (about 60 rows) whose answer row lies beyond the first chunk, with gold evidence on the row and its header; the eval scores whether the answer gives the right value with the right column meaning (the asked column, not a neighbouring column of the same row) and gates the slice in CI
- [ ] **EVAL-19**: The fixture golden set gains a `stale_version` category (zh/en/it): two versions of one policy uploaded as separate documents with the old one not deleted (the same rule with different values in an older and a newer version); the answer must give the current value and name its version, an answer that mixes both values counts as a failure, and the slice is gated in CI
- [ ] **EVAL-20**: The fixture golden set gains a `duplicate_flood` category (zh/en/it): one intent of a compound question has many near-identical chunks across documents (one passage copied into many documents) while the other intent has one relevant document; the eval reports per item the top-k redundancy (share of top-k chunks in the same duplicate cluster) and whether every intent's gold evidence is retrieved, gates both, and the weekly report (FBK-10) adds the production top-k redundancy rate per tenant
- [ ] **EVAL-21**: The cross-tenant canary suite (RET-08) gains same-tenant cross-group cases on every backend: a member outside a restricted access group asking about a document only that group may see (in zh/en/it) gets the information-not-available refusal with no restricted chunk in retrieval, context, cache, citations or logs, including after a group change, after a document re-upload and when the request body claims another group; a member of the group gets the answer; the suite is a release gate
- [ ] **EVAL-22**: Golden-set composition and absolute gates: every gated set (fixture and the FBK-08 real sets) keeps a no-answer share of at least 15% per language (target 20%), including off-domain (QRY-14) and adjacent-topic (GEN-15) items, and a set below the minimum fails the run; on top of the EVAL-10 noise-band regression, CI and `ship_check` fail on absolute ceilings in `eval/config/quality-gates.json`: false-answer rate per RAG mode (default 5% for strict), false-refusal rate (default 25%), and faithfulness and answer-relevance floors on the nightly tier
- [ ] **EVAL-23**: Changes made outside CI are gated too: saving a RAG-affecting setting in the Config UI (`RAG_SYSTEM_PROMPT`, RAG mode, chat model, embedding or reranker profile, refusal switches and any other `RAG_*` entry of the env manifest) runs the eval smoke tier against the proposed configuration (fixture set, plus the tenant's private real set when present) and shows the gate result before applying; saving a failing configuration needs a typed reason and is recorded with the config hash and the result and listed in the next weekly report (FBK-10); finishing a bulk import (`rag:backfill` batch) or a re-embedding run starts the nightly tier on that tenant's real set; changing the reranker, embedding model or tokenizer marks the affected refusal cells `uncalibrated` with a Config UI warning until `rag_eval.calibrate refusal` is rerun
- [ ] **EVAL-24**: LLM judge calibration: the nightly and online judges (EVAL-08, EVAL-15, GEN-12) are checked every month against a human-labelled sample of at least 100 cases per language from the FBK review queue; agreement (Cohen's kappa and accuracy per metric) is recorded, a length-bias check compares judge scores of paired long and short correct answers, and a judge below the agreement floor in `eval/config/quality-gates.json` becomes report-only for that language and metric until a recalibration (prompt, rubric or model change) is recorded with its agreement numbers; the judge stays from a different model family than the generator
- [ ] **EVAL-25**: Release gate: production promotion requires passing checks on the exact commit: `pr-smoke` is a required status check on the trunk and `main` branches, and a `rag-release-gate` check (the nightly tier and `ship_check` on that commit, or a pre-release run of both) must pass before a Vercel production deployment is promoted (Vercel Deployment Checks or an equivalent promotion step); a tier skipped because its keys or private data are missing reports `skipped`, which counts as not passed for release instead of passing silently as today's nightly judge tier does; judge metrics that pass EVAL-24 gate on their EVAL-22 floors; an emergency override needs an admin, a typed reason and is listed in the weekly report
- [ ] **EVAL-26**: The fixture golden set gains a `multi_step_calc` category (zh/en/it, synthetic neutral content): questions that combine values given in the question with a rule stated in a document (per-item caps, thresholds, percentages, tiered rates, date differences), with exact expected numbers and tolerances; every item has at least three paraphrases, and the eval reports numeric correctness and paraphrase consistency (all paraphrases give the same number); a fake model scripted to skip the per-item rule fails CI with GEN-17 off and is corrected with it on; the nightly tier measures the live error rate with and without the GEN-16 tool, and the switches ship only if numeric correctness rises with no other slice dropping beyond the noise band
- [ ] **XLG-02**: The fixture golden set gains a `cross_lingual` category: questions in English and Italian about Chinese documents, in Chinese and Italian about English documents, and in Chinese and English about Italian documents (at least 4 per direction pair, with span gold evidence in the source document); the slice is scored under today's configuration (`RAG_PIPELINE=legacy`) to record its baseline, reported per query-language/document-language pair, and gated like the language slices from then on; items drafted or machine-translated into Chinese or Italian count only after a native speaker has reviewed them, recorded in their review status (delta delivered by Phase 3.2)
- [ ] **XLG-03**: Cross-language paths work end to end beyond the embedding: the lexical (BM25) path and the local BM25 reranker use the translated query when the query and document languages differ, the hosted rerankers are multilingual models, and the RNK-05 refusal threshold is calibrated on a cross-lingual slice too so cross-language questions are not falsely refused
- [ ] **XLG-04**: Ingestion-time document translation (`RAG_DOC_TRANSLATION`, off by default, set per tenant and target language): each chunk is translated by a small fast model into the chosen knowledge-base languages, and each translation is stored as an extra retrieval-only representation (its own embedding and `lexical_text`, tagged with its language and linked to the source chunk), keeping protected tokens verbatim and applying the XLG-05 glossary; a hit on a translation returns the source chunk, so the LLM, citations and snapshots always use the original text; translations are rebuilt when a document is replaced or re-chunked and deleted with it, and count toward the RET-08 tenant canaries; it is turned on only when the cross-lingual slice shows that the multilingual embedding plus query translation (XLG-01) is not enough, and the eval reports the Recall gain against the added storage, translation cost and ingestion time
- [ ] **XLG-05**: Each tenant has a translation glossary (stored as per-language translation pairs in the Phase 4.1.1 TERM terminology dictionary, so there is one dictionary, not two) (source term → required translation per language), edited by admins in the Config UI and stored under `TenantScope`; query translation (XLG-01), document translation (XLG-04) and query rewriting must use the glossary term whenever the source term appears, and a translated query that misses a required term is corrected or discarded like a dropped protected token; glossary terms are also merged into the LANG-07 tokenizer dictionary; the fixture golden set gains `glossary` items whose answers depend on a company-specific term in zh/en/it
- [ ] **XLG-06**: Image captions (image RAG and DATA-11) are generated in the language of their document, or the tenant's main knowledge-base language when the document has none, instead of always in English as the caption prompt in `src/lib/rag/ingest/captioner.ts` does today; text visible in the image is quoted in its original language; the caption chunk's `language` field records the language actually written, and existing English captions can be regenerated by the EMB-04 re-embedding job without re-parsing the document
- [ ] **XLG-07**: Voice handles cross-language questions within its latency budget: the voice profile (QRY-07) may add query translation only when the eval shows it fits the voice budget and improves the cross-lingual slice, otherwise voice relies on the multilingual embedding alone; either way, the `cross_lingual` slice is also run through the voice entry point, reported per language pair, and gated like the text-chat slice
- [ ] **CACHE-01**: A semantic answer cache as locked in `.planning/specs/semantic-cache.md`: default backend is a pgvector table in Supabase with a RedisVL-style `check`/`store` contract, RedisVL `SemanticCache` in the sidecar is the optional backend (`RAG_SEMANTIC_CACHE=off|pgvector|redisvl`, default off); keys are scoped by `TenantScope`, answer language, RAG mode, generator model, retrieval-config hash and query framework, and use the condensed standalone query; a strict distance threshold calibrated on the dev split; questions with protected tokens (exact codes, amounts, quotes), personal data, relative time, webSearch/MCP/images or an unreliable groundedness status bypass the cache; TTL plus invalidation on any document insert, replace or delete in the tenant; a `semantic_cache` Langfuse span; `cache_paraphrase` and `cache_near_miss` golden pairs with the near-miss wrong-hit rate gated at 0; cross-tenant cache leakage is part of the RET-08 canary suite

### Feedback Loop (FBK)

- [ ] **FBK-01**: Every knowledge-base retrieval from chat, embed and voice is recorded in a Postgres `rag_retrieval_log` row written after the response (never on the request path): trace id, tenant key, user, organization and chat ids, channel, RAG mode, pipeline, `retrieval_config_hash`, query language, the masked query (only in `masked_query` mode), up to 50 retrieved chunk ids with document ids, ranks and scores and their kept flag, top score, retrieval status, refusal decision and reason, the outcome the user saw (answered, refused, knowledge base unavailable, degraded), total and per-stage latency; switchable with `RAG_RETRIEVAL_LOG=off|ids|masked_query` (default off); eval, media and incognito (ghost) chats are never logged; with the switch off, responses are byte-identical
- [ ] **FBK-02**: The retrieval log minimises personal data: it never stores answer text, chunk text, document names, IPs or user agents; queries pass through the PII masker and are capped; rows are readable and writable only by the service role (RLS on, no client grants), are deleted with their user, organization or chat, and are purged after `RAG_RETRIEVAL_LOG_RETENTION_DAYS` (default 30); each tenant can lower its level to `ids` or `off`; no raw customer data appears in fixtures, logs or reports
- [ ] **FBK-03**: In web chat, behind `RAG_REFUSAL_FEEDBACK` (default off), a strict "information not available" or knowledge-base-unavailable message offers "I expected an answer" / "Correct, not in my documents" with optional reason chips, stored on the user's own log row; behind `RAG_SOURCE_OPEN_SIGNAL` (default off), opening a source or citation is counted on the row as a weak signal; another user's retrieval cannot be voted on
- [ ] **FBK-04**: In the embed widget and embed window, behind `RAG_EMBED_FEEDBACK` and a 32+ character `RAG_EMBED_FEEDBACK_SECRET` (both default off/empty), visitors rate answers (helpful / not helpful with chips, no free text) through a signed per-answer token bound to one trace and one tenant, with the embed CORS rules and rate limiter
- [ ] **FBK-05**: A weekly mining job (`npm run rag:feedback-loop mine`, an admin route, optional `pg_cron`) selects failed queries per tenant — negative votes (embed and Phase 5 web votes), disputed refusals, refusals despite high scores, zero-result and low-score retrievals, possibly-unreliable groundedness, and answered-with-no-source-opened only together with another reason — deduplicates them by query fingerprint, caps them per tenant (default 50) and inserts them idempotently into a tenant-keyed review queue that survives the log purge
- [ ] **FBK-06**: Domain experts are granted per tenant by operator admins (`rag_domain_experts`); database RLS on the review queue shows each expert only the tenants they were granted (in multi-tenant mode admins included, no implicit access); experts read cases, chunk text (only of the case's tenant), search their tenant for missing evidence, and label cases in a Config UI panel with exact evidence spans, an expected answer, category, language and a PII check; every read of chunk text is logged without text; switchable with `RAG_DOMAIN_EXPERT_REVIEW` (default off)
- [ ] **FBK-07**: Labelled cases are triaged into dictionary candidates (observed term, canonical term, relation, language, occurrences) for Phase 4.1.1, training pairs (masked query, positive chunk and span, up to 10 hard negatives from the logged candidates, document group, train or held_out) for Phase 6.1, knowledge-base gaps, and golden candidates; exports carry ids and no chunk text, and no training pair uses a document that belongs to the domain test split; dictionary candidates (`DictionaryCandidate` JSONL, relation synonym/abbreviation/translation/misspelling) are imported through Phase 4.1.1's import dry run and apply (TERM-05), never written to the dictionary tables directly; once `rag_retrieval_log` exists, the Phase 4.1.1 term miner reads its missed retrievals instead of `rag_term_misses`, and `RAG_TERMINOLOGY_MINING` recording is retired (amended 2026-11-24 by Phase 4.1.1)
- [ ] **FBK-08**: A real domain test set of 100–300 items per gated tenant is built from approved golden candidates by the single Python promotion (`review_queue promote-db`): provenance `production` (or `human` when the expert paraphrased the question), PII re-checked, near-duplicates confirmed, span evidence without chunk ids, stored only under `eval/golden/private/`, with a dev/test split frozen by document group and near-duplicate cluster (new manifest rule; existing manifests unchanged), append-only
- [ ] **FBK-09**: `eval/config/gate-population.json` (default `legacy`, today's rule) switches the gate to real items (`production` and `human`, approved, gated split) with a minimum size (default 100) that fails the run instead of falling back; `ship_check` passes only when both reports are on the real population and the same manifest, no slice regresses beyond the noise band and the paired bootstrap 95% interval of the target metric is above zero; once the population is real, switching any `RAG_*` default on or activating an embedding profile requires a passing ship check
- [ ] **FBK-10**: A weekly report (`rag_eval.weekly_report`, scheduled in CI where private data exists) shows per tenant hash the retrievals, refusal, zero-result and low-score rates, votes by channel, items mined, labelled and exported, the metric trend of the last eight private eval runs on each domain set, and new failures by layer and category (`rag_eval.failure_report`), with counts, ids and hashes only
