<objective>
Add section outlines: a domain-neutral, data-driven pre-pass that turns known numbered section markers into Markdown headings before chunking, so `section_path` follows a document's own outline and one file that holds several products is split into variants.

Purpose: Docling's parse output runs most numbered headings into long paragraphs, so line-start heading and clause patterns miss them and many chunks have an empty `section_path`. The outline data lives in an operator file outside the repo; the mechanism here knows nothing about any domain.

Output: the `src/lib/rag/ingest/outline/` module, the `RAG_SECTION_OUTLINES` switch synced everywhere, the ingest and rechunk call sites wired with the document's tenant key, `metadata.section_outline` on chunks, the `chunk_prep.section_outline` fingerprint part, and tests on neutral synthetic fixtures. With the variable unset every output byte and every hash is today's.
</objective>

Planner decisions on points the description leaves open (each is implemented below; change them only by asking):
- PD-1: an outline applies only when at least one marker is kept; otherwise the input is returned unchanged with a null report, so nothing downstream changes.
- PD-2: "monotonic sequence" is the longest strictly increasing run per variant, so one stray forward mention does not drop the real sections after it.
- PD-3: a TOC run "covers most" level-1 sections when it names more than half of the outline's level-1 keys.
- PD-4: a cross-reference prefix counts when the `prefix.length + 3` characters before the marker contain it, case-insensitive.
- PD-5: existing ATX headings after the first kept marker are re-levelled below the outline heading they follow; a heading line that itself holds a kept marker is replaced. Without this a Docling heading inside a section would replace the outline section in `section_path`.
- PD-6: outlines are tried for chunker kinds `markdown_sections`, `table_aware` and `legal_clauses`. `rule_sections` (the tenant's own rule set matched), `invoice` and `image_caption` are left alone.
- PD-7: no unified-pipeline gate on the variable. The legacy ingest path has no chunk stage, and `rag:rechunk` works from stored parse output.
- PD-8: any invalid entry turns the whole file off.
- PD-9: report field `variants` is the list of variant labels in document order. Labels are document text: they are never logged.
- PD-10: the outline file is app-only operator configuration, validated by a hand-written Zod schema as the description asks (like `src/lib/rag/feedback-loop/config.ts`); only the fingerprint part is a Pydantic contract.

export const SectionOutlineFileSchema: z.ZodType<SectionOutlineFile>; // z from 'zod/v3', strict objects
export interface CompiledOutline {
  id: string;
  version: number;
  tenantKeys: string[] | null;          // lower-cased; null: every tenant
  detect: RegExp;                       // flags 'iu'
  withinChars: number;
  sections: Array<{ key: string; level: 1 | 2 | 3; pattern: RegExp }>; // flags 'giu'
  variantStart: number;                 // index into sections
  variantLabel: 'body' | 'title';
  crossRefPrefixes: string[];           // lower-cased
  tocMaxSpanChars: number | null;
}
export type SectionOutlineSet = readonly CompiledOutline[];
export interface SectionOutlineReport {
  outline_id: string;
  version: number;
  variants: string[];
  markers_found: number;
  markers_kept: number;
  markers_dropped: number;
}
export interface SectionOutlineInput { outlines: SectionOutlineSet | null; tenantKey: string | null }

// load.ts
export function compileSectionOutlines(raw: unknown): SectionOutlineSet;                    // throws on invalid input
export function loadSectionOutlines(filePath: string | null | undefined): SectionOutlineSet | null;
export function resetSectionOutlinesForTests(): void;

// normalize.ts
export function normalizeWithOutline(markdown: string, input: SectionOutlineInput | null | undefined): { markdown: string; report: SectionOutlineReport | null };
