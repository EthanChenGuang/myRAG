**Gap 15 / T-05.3-391 (blocker).** Covers SECURITY fixes 1 to 5.
- The workflow is split into `status-pending` → `gate` → `status-final`.
  - `gate` and `status-pending` refuse a sha that is not on main (`git merge-base --is-ancestor "$GATE_SHA" origin/main`) right after checkout and before any repository code runs. The gate checkout uses `fetch-depth: 0`.
  - Every checkout sets `persist-credentials: false`.
  - The gate job has `contents: read` and `checks: read` only (see the deviations section) and posts no status.
- Only the two status jobs hold `statuses: write`.
  - They check out the workflow's own `github.sha` (no ref) and read no secrets.
  - `status-final` installs and runs no gate code. It only `gh run download "$GITHUB_RUN_ID" -n rag-release-gate`, then runs `post-release-status.mjs`. A missing result posts failure.
- Both statuses carry `target_url=$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID`. The poster refuses to post without a valid run id or https server URL.
- `run-name: rag-release-gate ${{ inputs.sha || github.sha }}`.
- `promote-production.mjs` `acceptedStatus` handles a bot status like this:
  - It parses the run id from `target_url`, which must be exactly this repository's `/actions/runs/<id>`.
  - It calls `GET /actions/runs/{id}` and `GET /repos/{repo}` (for the default branch).
  - It requires all of: `path` = `.github/workflows/rag-release-gate.yml` (also accepted with an `@<default branch>` suffix, as the API returns it); `head_branch` = the default branch; `event` push or workflow_dispatch; `status` completed and `conclusion` success; `repository.full_name` = this repository.
  - Extra binding: `display_title` must equal `rag-release-gate <sha>`, and a push run's `head_sha` must equal the sha. Without this, a valid run URL could be replayed onto another commit.
  - A bot status without a run URL is refused. An admin-posted status is unchanged.
  - `promote-production.yml` gains `actions: read`.
- Lint: `check_release_gate` was rewritten for the three jobs. `PROMOTE_JOB_PERMISSIONS` now includes `actions: read`.

## Deviations

- The gate job keeps `checks: read` next to `contents: read`. `rag_eval.release_gate` reads the commit's check runs for its `pr_smoke` part, and that part would fail without the permission. The permission is read-only. The gate job holds no write permission and posts no status.
- Statuses are posted by two jobs (`status-pending` before the gate, `status-final` after it), not one. A single job cannot post before and after another job. Both run only this workflow's own sha, read no secrets, and are the only jobs with `statuses: write`. The lint pins both.
- The `display_title` / push `head_sha` binding in `acceptedStatus` goes beyond SECURITY fix 5. It stops replaying one run URL onto another commit.
- `check_monitor_job` already existed. It was extended rather than added.
- The 05.3-48 SUMMARY edit is handed to the train-40 builder (see gap 4).
