## Plan 04.4-16 in short

- **Switch:** `RAG_LEXICAL_DF_MODE=raw|cluster`, default `raw` (today's behaviour exactly). `cluster` needs effective `bm25` scoring and `RAG_DUP_CLUSTERS=true`, else it resolves to `raw` with one warning. Config hash gains `df_mode` only when `cluster` is effective.
- **Statistics:** a second corpus `chunks_cluster` in `rag_lexical_df` and `rag_lexical_corpus`. A duplicate cluster counts once per chunking profile and language (the member chunk with the smallest id is the unit). Kept only for tenants that enable it.
- **Maintenance:** triggers stage signed rows for cluster-less chunks and append-only markers for touched clusters; compaction reconciles marked clusters against a ledger under the tenant lock; the drift check tests two exact invariants.
- **Query:** `p_df_mode` on `rag_bm25_search_chunks`, rebuilt from the 0932 body. Cluster statistics not ready: raw BM25 with a trace code; then the existing fallback to `ts_rank_cd`. Never a refusal.
- **Migrations:** two files, numbers claimed at execution (statistics in 0905–0919; search function after 0932). Idempotent, both modes, empty `search_path`, service role only. Re-run rules: after 0904, re-run 0932 and then the new search file; after 0901 to 0903, re-run the new statistics file.
- **Eval:** the ingest fixture mode builds duplicate clusters for a run that asks for them; `phase44-comparison.json` is not edited (hash pinned); a derived spec with the same gates and bands is committed before any cluster run; the gate is run and recorded as measured.
- **Outcome rule:** gate (b) passes: record, owner decides, flip is a separate plan. Any offender remains: record, stop. No default changes either way.

## Planner choices for the owner or orchestrator to confirm

1. **Derived spec instead of editing the spec.** The cluster run needs other run environments, so the plan adds `eval/config/phase44-cluster-df-comparison.json`, equal to the pre-registered spec in every gate and threshold and enforced by a test (D-50). The alternative was an env-overlay flag on the gate tool.
2. **04.4-15 now waits for 04.4-16** (D-52). Both edit the decision record, and option B puts the default decision after the cluster-DF re-run. If the live comparison should not wait, 04.4-15 can run first with raw DF only; then revert its `depends_on` and wave.
3. **`cluster` requires `RAG_DUP_CLUSTERS=true`** (D-45), so a later flip to cluster DF would also have to turn that switch on by default.
4. **One plan, nine tasks.** The brief asked for one plan. It is large (estimate 420k tokens); every task ends in a commit so execution can stop and resume at a task boundary. Splitting it into several plans is an option before execution.
5. **`scanned` (ingest, Recall@10) is not a duplicate effect.** Cluster DF is not expected to change it, so gate (b) may still fail on it after `duplicate_flood` is fixed. The plan reports the two separately and stops; it does not propose an override.
6. **The decision ids skip D-43** to avoid confusion with Phase 4.2's D-43, which the context cites; the owner decision is D-43a.
