# Phase 5.2.1 Plan 10: Trailing calculation block

**For models without tool support, the trailing `<calc_trace>…</calc_trace>` block is held back, removed from what users and later transforms see, and parsed with the generated `CalcRequestSchema`. The result goes to an `onTrace` callback. The streamed and whole-text paths give the same text and events for every split point. A document can no longer plant the tags through the context while a calculation switch is on.**

## Deviations from Plan

1. **The calculation switches are read through a field probe, not a typed field.** `readAnswerConfig` on this base has no `calcTool` or `calcCheck`, because plan 05.2.1-02 (not a dependency) adds them. `calcTagNeutralizationOn(config)` reads them structurally, and the test mocks the reader. After 05.2.1-02 merges, nothing else is needed. Optional cleanup: give the parameter the `AnswerConfig` type.
2. **The builder input stays the Phase 5.2 `calcBlock` slot.** It is widened to `Transform | CalcBlockOptions | null` and was not replaced with a new `{ onTrace, stripMarkers }`-only field. The options form is the plan's input. The Transform form keeps the existing Phase 5.2 order test valid.
3. **The whole-text pipeline also takes `calcBlock`.** This keeps `applyAnswerPipelineToText` a twin of the chain (Phase 5.2 Pitfall 21). It is additive and absent by default.
4. **The count is on `AssembleOutput.calcTagsNeutralized`, not on `RagTrace`.** The `RagTrace` contract has no such field, and the Phase 5.2 sentinel count (`neutralizedSentinels`) also stops at `AssembleOutput`. Adding the field to the contract belongs to a contract plan.
