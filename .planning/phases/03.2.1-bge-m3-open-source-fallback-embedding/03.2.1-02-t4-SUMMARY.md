# 03.2.1-02 Task 4 rerun: BGE-M3 identity proof and nightly job

The owner topped up DeepInfra, and the proxy supplies the key. This rerun records the hosted half of the D-26 fixture, adds the CI identity test and adds the nightly job. That closes gaps G1 and G2.

## G1: hosted recording and compare

- **Recording:** `record_bge_m3.py`'s `record()` and `hosted_embedder()` were run, unchanged, from a small driver kept in the scratch directory (not committed).
  - The driver adds a 2 s pause between calls and stops at 50 calls.
  - It stops on HTTP 402 or 429; neither happened.
  - `DEEPINFRA_API_KEY=proxy-injected`; the proxy put in the real key.
  - Input: the committed synthetic fixture texts `bge-m3-texts.json` (sha256 `dee4c15a…518e`, 5 texts each in zh, en and it). No customer data.
  - 15 calls in total.
- **Compare:** `record_bge_m3.py --compare bge-m3-hosted.json bge-m3-sidecar.json` exited **0**, with 15/15 texts within the D-26 tolerance (cosine ≥ 0.9999, every component within 1e-3).
  - Lowest cosine: **0.99999316** (zh-long-1).
  - Largest component difference: **3.680e-04** (en-long-1).
  - Short texts: cosine ≥ 0.99999833, difference ≤ 2.43e-04.
- **Recording file:** checked for any key or bearer string before it was committed (none). It holds the model, revision, mode, date, text-file hash and vectors.
- **`tests/rag/bge-m3-identity.test.ts`:** runs offline on the two committed recordings.
  - Checks model `BAAI/bge-m3`, the pinned revision (`BGE_M3_SIDECAR_REVISION`), both modes, 1024 dims, and that the text-file sha256 matches the fixture.
  - Checks that each recording covers exactly the fixture ids.
  - Asserts for each text, after L2 normalization, cosine ≥ 0.9999 and largest difference ≤ 1e-3.
  - Pins the comparison operators: exactly at the tolerance passes; just beyond it on cosine or on a component fails. A synthetic 1024-dim pair with high cosine and one component 2e-3 off fails.
  - When a recording file is missing, the test fails with ENOENT instead of skipping (checked by moving the file away).

## G2: nightly job `bge-m3-identity` (report only)

- **Sidecar check:**
  - Builds `docker build --target bge-m3`, in a step with id `bge_m3` that skips with a notice if the build fails.
  - Runs `record_bge_m3.py --mode sidecar` inside the image with `--network none`, using the baked weights.
  - Compares the result with the committed hosted recording.
- **Live hosted check:**
  - Runs only when the `DEEPINFRA_API_KEY` repository secret is set (job flag `HAS_DEEPINFRA_KEY`); otherwise a notice says it was skipped.
  - The key reaches the step through step `env` from `secrets.DEEPINFRA_API_KEY`. It is never written into `run` and never stored in the repository.
  - Records the hosted vectors again and compares them with the committed hosted recording. That is 15 calls per night.
- **Report only:**
  - A compare that fails records its exit code and emits a `::warning`; the job does not fail.
  - The sidecar recording step has `continue-on-error`.
  - The compare output (ids and numbers only, no text) goes to the step summary and to the artifact `bge-m3-identity-report`.
- **Lint:** `check_bge_m3_identity` in `check-workflows.py` enforces the job's shape. It checks:
  - the build target, the sidecar recording, the compare against the hosted file, `--network none` and both skip notices;
  - the secret flag;
  - that the only secret is DEEPINFRA_API_KEY, passed by name through step env and gated on the flag;
  - that no key is echoed;
  - that every compare uses `|| status=$?`;
  - that the job does not commit or push.

  It has 8 unit tests in `scripts/tests/test_check_workflows.py`.
