# 03.2.1-02 SUMMARY: BGE-M3 served by the sidecar, recording script, sidecar vectors (hosted recording pending)

## What was built

- **Task 1: sidecar serving mode, no hosted fallback** (`c27d2310` RED, `cbfda2f1` GREEN). `rag_sidecar/embed/bge_m3.py` holds `BgeM3Embedder`. It takes the first-token state of the last hidden state, L2-normalizes it in double precision (a zero vector is an error), and calls the tokenizer with `truncation=False`. An input above 8192 model tokens fails with `EmbedInputTooLong` before anything reaches the model. Vectors come back in input order, and one lock means one batch at a time. `router.py` serves `POST /v1/embed`: body capped at 4 MiB, `EmbedRequest` validation (422 `invalid_embed_request`), 422 `embed_input_too_long: limit 8192 tokens`, and 503 `model_unavailable` when there is no model, when the model fails, or when the vectors are unusable. Logs carry counts and latency only. It is registered in `main.py`; `create_app(embedder=...)` is injectable, and the default `resolve_embedder` returns `None` unless `BGE_M3_MODEL_DIR` is set. In `bge-m3.ts`, `RAG_BGE_M3_SERVING=sidecar` posts batches of up to 32 inputs to `${RAG_SIDECAR_URL}/v1/embed` with `x-sidecar-secret`. The provider checks the model, revision and dimension, normalizes, and returns `host: 'sidecar'`.
- **Task 2: extra, loader, bake, recording script** (`1286afcd` RED, `5950c4c2` GREEN). The `bge-m3` extra uses exactly the `hhem` pins. `uv lock` changed only extra metadata: still 134 packages, no version changed, and `uv lock --check` passes. `eval/uv.lock` gets the same metadata lines because eval depends on the sidecar by path; without them `uv sync --locked` in eval fails. `load_from_baked_dir` refuses with `download_refused`, `revision_mismatch` (requested revision or REVISION marker), `model_dir_missing`, `file_missing` or `file_hash_mismatch`. `python -m rag_sidecar.embed.bake <dir>` downloads the pinned files, checks their hashes, copies them, writes the marker and loads offline. The new Dockerfile target `bge-m3` (before `runtime`, which stays the default) bakes into `/opt/models/bge-m3` and sets `HF_HUB_OFFLINE=1`. `record_bge_m3.py` makes one call per text and writes `{model, revision, mode, recorded_on, texts_sha256, dims, vectors}` without the key. `--compare` uses the standard library only, prints id, cosine and max difference (never the text), and exits 1 beyond tolerance and 2 when the recordings are not comparable (different ids, revision, text-file hash, or a missing file).
- **Task 3 (checkpoint), partly done.** See the checkpoint answer below. Sidecar vectors were recorded with the real model (`238ef65b`).

## Behaviour changes

- With defaults (`RAG_BGE_M3_SERVING=hosted`, no `BGE_M3_MODEL_DIR`) nothing changes: the hosted provider behaves as before, the sidecar serves `/v1/embed` only as 503 `model_unavailable`, and the base image imports neither torch nor transformers.
- With `RAG_BGE_M3_SERVING=sidecar`, every BGE-M3 embedding goes to the sidecar, and a sidecar failure fails the embedding instead of reaching DeepInfra.
- New sidecar-only variable `BGE_M3_MODEL_DIR`, set by the image. It is not an app `.env.local` variable, so the five-place sync does not apply; it follows `PROMPT_GUARD_MODEL_DIR`, which is also only in `settings.py`.
- No migration, no SQL function, no new store, so no `rag_purge_hook_*` or inventory entry is needed.
