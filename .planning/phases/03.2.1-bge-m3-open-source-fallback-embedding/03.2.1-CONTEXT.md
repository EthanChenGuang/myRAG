<domain>
## Phase Boundary

BGE-M3 (`BAAI/bge-m3`, MIT, 1024 dimensions, 8192 input tokens, dense output only) becomes one more embedding profile, `bge-m3-1024`: seeded available, never activated by a migration, served by the hosted API by default or by the sidecar on CPU for deployments that keep text in-house, with recorded proof that both serving modes return the same vectors. It joins the Phase 3.1.1 model catalog with its supported languages, every catalog model declares its languages, and the language validator of Phase 3.2 is fed with the active profile's declaration at every entry point. It is compared with the other profiles like any other arm and activated only through the unchanged EMB-05 gate.

**Depends on Phase 3.1.1** (not on trunk at planning time):
- `src/lib/rag/embeddings/catalog.ts` with `EMBEDDING_MODEL_CATALOG` and `catalogEntry(provider, model)` (plan 03.1.1-01)
- the `embedding_profiles.doc_types` column and its scope guard, migration `0440_embedding_bindings.sql` (plan 03.1.1-04)
- the model-aware lookup `getEmbeddingProviderFor(provider, model)` at every call site (plans 03.1.1-01 and 03.1.1-16)

**Depends on Phase 3.2** (all of it runs first):
- the switch `RAG_BGE_M3_SERVING` in the five config locations and the hidden `bge` settings group (plan 03.2-03)
- the contracts `EmbedRequest` and `EmbedResponse` (plan 03.2-06)
- the validator `validateLanguageSettings` with its embedding-profile rule and the three entry points (plans 03.2-07 and 03.2-09)
- `chunk_translation_embeddings` (plan 03.2-48), the sidecar `hidden-text` extra and routers (plans 03.2-35 to 03.2-37), migrations 0801 to 0810 on the live database (plan 03.2-65), the closing gates and `AGENTS.md` (plan 03.2-68)

Out of this phase: everything else of Phase 3.2, and any change to a Phase 3.1.1 planning file.
</domain>

## Implementation Decisions

The numbers are Phase 3.2's. Each line names the part this phase implements; read the full decision in `03.2-CONTEXT.md` before planning or executing against it.

### BGE-M3 (EMB-11)

- **D-25:** Carried whole. Catalog entry for provider `bge-m3`, one unscoped profile `bge-m3-1024` seeded `available` by migration with its partial HNSW index over `halfvec(1024)`; nothing activated by a migration; activation through the EMB-05 gate unchanged.
- **D-26:** Carried: the hosted provider, the sidecar route `POST /v1/embed` behind the optional `bge-m3` extra, the serving switch in the provider, the definition of "identical" (cosine at least 0.9999 and every component within 1e-3 after L2 normalization), recorded vectors compared in CI, the optional nightly real run. Phase 3.2 already delivered the variable `RAG_BGE_M3_SERVING` and the two contracts.
- **D-27:** Carried whole. BGE-M3 as one more arm of the per-profile comparison, with ingestion throughput, query latency and cost for both serving modes; fixture runs are wiring proof.

### Carried in part

- **D-07:** The part that needs the catalog: `supported_languages` declared on every model of the Phase 3.1.1 catalog, and the three entry points passing the active profile's declaration to the validator. The validator rule itself (`embedding_profile_unsupported`, "not verified against the active profile") is Phase 3.2's.
- **D-48:** The rules for migration `0811_bge_m3_profile.sql`, which keeps its number in the `0801` to `0839` block: additive, idempotent, schema-qualified, not folded into the setup files, applied after 0801 to 0810.
- **D-50:** The Embedding profiles part: two more fields on the existing admin list answer and the extended (not redesigned) Config UI panel with the serving-mode setting, built from `03.2-UI-SPEC.md` section 6.10.
- **D-52:** Tests without live services: a fake sidecar for `/v1/embed`, recorded BGE-M3 vectors, deterministic fixture texts; no live call in CI.
- **D-54:** The BGE-M3 live items: a real hosted call and a real sidecar run compared under D-26's tolerance, with throughput, latency and cost. The other live items stay in Phase 3.2 (plan 03.2-53).

### Claude's Discretion

- File names of the recorded vectors and of the live-verification record, the sizing note for CPU serving, and the wording of the operator documentation.

</decisions>
