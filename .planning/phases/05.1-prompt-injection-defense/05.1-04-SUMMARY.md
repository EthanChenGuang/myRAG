# Phase 05.1 Plan 04: prompt-injection switches and config reader

**Nine Phase 5.1 switches and keys, all off or empty, sit in the five config places, the manifest and one Config UI card. Later plans read them through `readSecurityConfig`.**

## What was built

- **Variables (Task 1).** `RAG_CONTEXT_TAGGING=false`, `RAG_INJECTION_CHECK=off`, `RAG_INJECTION_PROMPT_GUARD=false`, `RAG_INJECTION_LAKERA=false`, `LAKERA_GUARD_API_KEY=` (empty), `LAKERA_GUARD_BASE_URL=` (empty means `https://api.lakera.ai`), `RAG_INJECTION_LAKERA_MULTI_TENANT_ACK=false`, `RAG_TOOL_RESULT_GUARD=off` and `NEXT_PUBLIC_RAG_IMAGE_ALLOWLIST=false`. They are in `src/lib/env.ts`, a commented "PROMPT-INJECTION DEFENSE" section of `scripts/init-env.js`, all three `scripts/config-server.js` templates and `scripts/rag/env-manifest.json`, where all nine are managed and listed alphabetically. `eval/config/rag-eval-env.json` was regenerated with `eval-env.mts --write`, which adds the seven `RAG_*` defaults.
- **Config UI card.** A "Prompt-injection defense" card follows the Citations and groundedness card. It holds:
  - checkboxes for context tagging, Prompt Guard, Lakera, the multi-tenant acknowledgement and the image allowlist;
  - selects for the injection check and the tool result guard;
  - a masked Lakera key with the reveal button, and the base URL.
  The help text says that `drop` is the recommended mode and `downweight` is weaker than drop, that regional hosts are allowed, that the acknowledgement should be ticked only after the retention terms are recorded, and that `NEXT_PUBLIC_RAG_IMAGE_ALLOWLIST` is inlined at build time, so a change needs a rebuild (I5). A fixed warning says that Lakera sends chunk text to a third party and is listed for the ADM-04 vendor inventory.
- **Reader (Task 2).** `readSecurityConfig(source = process.env)` reads the variables on every call and returns a frozen view. A boolean is on only for a trimmed literal `true`. An unknown mode becomes `off` with `invalid_injection_check` or `invalid_tool_result_guard`. The base URL must be https, with http allowed only for loopback, and has its trailing slashes removed. A blank key gives `null`. `anyNonDefault` is false when every variable is unset or at its init-env default. Warning messages name the variable and never contain the configured value or the key.

## Deviations

- The plan listed only `type="password"` for the key. `LAKERA_GUARD_API_KEY` was also added to the 32-character short-secret warning lists in `scripts/config-server.js` and the Config UI, following the "added to the short-secret handling" instruction.
- The ADM-04 note was first built as an alert box and moved into help text after the Impeccable pass (see Design skills).
- The reader adds a fourth warning code, `invalid_lakera_base_url`, for a base URL that does not parse or that carries credentials, a query or a fragment. The plan listed only `insecure_lakera_base_url`. Rejecting credentials stops a `user:pass@` URL from sending a secret to the Lakera host.
- No migration in this plan.
