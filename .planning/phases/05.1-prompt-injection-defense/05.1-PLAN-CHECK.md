## BLOCKERS

**05.1-01, B1 [verify_command_format]: the rule-count acceptance gate must fail at HEAD.**
- Evidence: the Task 1 `node -e ... rules.length>=16 && every lang>=4` check is noted `[HEAD=1]`. Re-measured at af0a695 it exits 0. Plan 03-20 is merged and already ships 16 rules (zh 5, en 6, it 4, any 1). The gate passes before any work is done.
- Example fix: require at least 22 rules, or at least 2 new `inj-<lang>-NN` ids per language beyond the 03-20 set (zh>=7, en>=8, it>=6). Update the HEAD notation.

**05.1-18, B2 [packages/checkpoints]: no executor task may install or lock packages; only the orchestrator does that, after the user approves.**
- Evidence: in Task 2 the executor must "regenerate the lock with uv", and its verify runs `uv sync --locked` and `uv run --extra promptguard`, which installs torch, transformers and huggingface-hub. Approval in Task 1 does not change who runs the install.
- Example fix: after the Task 1 approval, the orchestrator runs the lock and sync. Task 2 edits pyproject.toml only and runs tests against the environment the orchestrator prepared, and its precondition checks that the lock already contains the promptguard extra.

**05.1-14 (with 05.1-13), B3 [context_compliance D-10/D-01/D-06]: released-rule exemptions must hold under both graphs, scoped to the tenant, with a two-tenant test.**
- Evidence: 05.1-13 passes the per-document released-rule set into `runInjectionCheck`, but only through the legacy `fetch-rows.ts`. 05.1-14 calls the stage on v2 with the 05.1-06 API and says "Do not modify injection-check.ts". It never reads `metadata.quarantine` and has no v2 two-tenant test. Under `RAG_PIPELINE=v2`, an admin-released document gets dropped again.
- The two plans share wave 3 with no `depends_on` between them.
- Example fix: have 14 depend on 13. In v2, read the released set only from rows returned under the caller's scope, pass it in, and add a v2 two-tenant PGlite case.

**05.1-08 / 05.1-21, B4 [cross-tenant/off-state]: no Lakera request in multi-tenant mode unless both the opt-in and the acknowledgement are set.**
- Required condition: `RAG_INJECTION_CHECK != off` AND `RAG_INJECTION_LAKERA=true` AND (single-tenant OR `RAG_INJECTION_LAKERA_MULTI_TENANT_ACK=true`). Each combination needs a test that zero requests are sent.
- Evidence: `lakeraAllowed({multiTenant, ack})` only covers the acknowledgement. The 21 tests cover "multi-tenant without ack: not called; with it, runs", but nothing tests:
  - ack=true with the Lakera switch off;
  - check=off with both switches on;
  - multi-tenant mode resolved through the real deployment-mode path rather than a parameter.
- The fetch fake must record zero calls in each of these cases.
- Example fix: add a truth-table test (fetch call count == 0 for every disallowed combination) at stage level. Add one route-level multi-tenant case.
