# 06.3-21 Summary: purge mode, admin-purge tombstones and the reconcile's purge follow-ups

A file deleted at the source of a connection in `purge` mode is now purged from every store through `purgeLineage`, with the connection's source sync as the actor. An admin-purged connector file is not re-ingested while it still exists at the source, in every sync path. The scheduled reconcile finishes what a purge could not do at once: it re-scrubs recent purges and retries pending objects. No migration, no new switch, no new env variable.

## Behaviour changes

- **Purge mode (D-08, D-11, D-13).** For a connection with `deletion_mode = 'purge'`, `applySourceDeletions` calls `purgeNangoLineages`. That function collects the file's lineages with `collectNangoLineageIds` inside the owner's tenant and checks that `nangoOwnerScope` gives the same tenant. Then, for each lineage, it calls `purgeLineage(scope, lineageId, { kind: 'source_sync', id: <nango_connections.id> }, { code: 'source_deleted' }, { signal: AbortSignal.timeout(120_000) })`.
  - On the first failure it returns false, so the sync record is kept and the batch reports `failed`. After every lineage succeeds, the sync record is deleted (the SQL purge has normally removed it already).
  - Errors are logged under `Nango` with ids only.
  - The interim "purge mode not available" warning is gone. NULL and `soft` modes are unchanged, and the 06.3-03 characterization replays identically.
  - Changing a connection to `purge` purges nothing by itself; only deletions found after the change are purged.
- **Tombstones (D-35).** A new module, `src/lib/nango/purge-tombstone.ts`, provides `purgeTombstoneCheck(userId, connectionId)(fileId)`, which returns `'clear' | 'withdrawn' | 'unknown'`, and `skipByTombstone`. It calls `isPurgeTombstoned(ownerScope, <Nango connection_id>, fileId)` with a 10 s timeout.
  - Where the check runs: right before the sync-record upsert in all five sync-manager sites (Drive folder, Drive by id, Notion by id, the generic folder loop used by Dropbox and the records fallback, and the generic multi-folder loop), and in SharePoint/OneDrive `ingestFile` before the download.
  - A withdrawn file gets no sync record, no download and no ingest, and is counted in the new optional `SyncStats.withdrawn`. That count flows through the multi-folder and Notion merges and through the SharePoint return.
  - A failed lookup skips the file for this sync, counts it as `skipped` and logs the connection id only. In SharePoint it also leaves the delta link uncommitted, so the item comes back on the next run.
  - Files that are unchanged and already synced are skipped before the check, so they cost no extra RPC.
  - A source-sync purge leaves no tombstone, so a file restored at the source is ingested again.
- **Reconcile follow-ups (D-15, C-10).** `runSourceReconcile` first runs `rescrubRecentPurges`, then `retryPendingPurgeObjects({ limit: 50 })`, and only then starts the connection loop.
  - Each step gets at most half of the time left before the deadline, combined with the caller's signal. A step that has no time left, or is aborted, counts in `purgeSkipped`. A step that fails counts in `purgeFailed` and is logged with counts and a code; the connection loop runs either way.
  - The result, the CLI line (`purge_retried=… purge_still_pending=… purge_rescrubbed=… purge_skipped=… purge_failed=…`) and the internal route JSON gain `purgeRetried`, `purgeStillPending`, `purgeRescrubbed`, `purgeSkipped` and `purgeFailed`.
  - Tests inject the steps through the new `deps.purge`.

Chat, strict mode, webSearch with Exa, `source_images`, `{{context}}`, voice and embed are untouched.

## Deviations

1. **Shared tombstone helper.** The check lives in `src/lib/nango/purge-tombstone.ts`, which is not in the plan's file list. It serves sync-manager and sharepoint/sync, so the six sites share one fail-closed implementation. Because of that, the plan's grep for `isPurgeTombstoned` in sync-manager.ts reads 0. All five sync-manager sites and the SharePoint site are covered by tests, one per path.
2. **Step order.** The reconcile runs the re-scrub before the retry, not after as the plan wrote it. With the plan's order, the retry stored its check while a stale tab's quote was still in the chat, so a record whose objects were all removed read `remaining` and stored `failed`. With the re-scrub first, the stored check reads `verified`. The PGlite case covers this.
3. **Time budget.** Each follow-up step gets at most half of the time left, so the purge work cannot use up the connection loop's deadline.
4. **Failed tombstone lookups.** These count as `skipped`, not `withdrawn`, and in SharePoint they keep the delta link uncommitted. This is fail-closed and the file is retried.
5. **Test-only fixes outside the plan's file list.** I added `isPurgeTombstoned` (which answers not tombstoned) and the missing `recomputeDirtyDupClusters` to the `@/lib/rag` mocks of the connector tests: listing-completeness, permission-sync-loops, reconcile, drive-listing-orphans, webhook-deletions, default-deletion-characterization and source-deletions, plus three tests under `tests/rag/ingest/`. I also updated the reconcile CLI and route count fixtures and added the purge clock reads to the reconcile deadline test. The SharePoint tombstone cases are in `tests/nango/sharepoint-sync.test.ts`.
6. **Branch recovery.** A stray `git checkout` detached HEAD onto train 41 mid-task. I put the two commits made there back onto `exec/06.3-21` with cherry-pick, so history is linear. Nothing was force-pushed.
