# Phase 6.3 Plan 29: Daily cap on change-feed purges Summary

**A connection in Purge mode can now withdraw at most `RAG_SOURCE_PURGE_DAILY_CAP` files per UTC day through its change feed. The allowance is reserved atomically in SQL before anything is purged. Files above it keep their sync records and wait in one paused run (`pause_reason = 'purge_daily_cap'`), which an admin confirms or dismisses through the existing Source sync flow. The default 0 changes nothing.**

## What was built

### Migration 0729 (one common file, not folded, idempotent)
- `rag_source_reconcile_runs.pause_reason` (NULL, `share`, `purge_daily_cap`; named CHECK added in a catalog-guarded `DO` block) and `rag_source_reconcile_runs.daily_cap` (NULL or > 0: the cap that held a run, so the panel sentence names the cap in force at the time even if the setting changes later). Existing rows and share pauses keep both NULL.
- `rag_source_purge_daily_usage (connection_id, usage_day, tenant_key, purged_count, updated_at)`, PK `(connection_id, usage_day)`, `ON DELETE CASCADE` from `nango_connections`, tenant-key regex CHECK, `purged_count >= 0`. RLS on, no policy, REVOKE ALL from PUBLIC/anon/authenticated/service_role, service_role SELECT only. It references no document, so it is not a purge store (`rag_purge_store_inventory()` unchanged).
- Three functions, all `SECURITY DEFINER SET search_path = ''`, `public.`-qualified, guard order `rag_ingest_assert_tenant_key` → `invalid_argument` (22023) → `not_found` → owner key via `rag_nango_owner_tenant_key` or `tenant_mismatch`; no overloads; service_role only (also added as guarded entries to 0410):
  - `rag_source_purge_reserve(p_tenant_key, p_connection_id, p_requested, p_cap) → integer`: deletes the connection's rows older than 30 days, `INSERT … ON CONFLICT DO NOTHING`, then `SELECT … FOR UPDATE` on the day row and grants `least(requested, greatest(cap - used, 0))` under the row lock.
  - `rag_source_purge_release(p_tenant_key, p_connection_id, p_count) → integer`: lowers the current UTC day's count, never below 0.
  - `rag_source_purge_hold(p_tenant_key, p_connection_id, p_file_ids, p_cap) → uuid`: `pg_advisory_xact_lock` on the connection, expires stale awaiting runs, appends new ids (dedup, order kept) to the connection's open `change_feed` + `purge_daily_cap` run created the same UTC day, or inserts one (`awaiting_confirmation`, `expires_at` +24 h); ids past 2,000 are not stored and `candidate_count` keeps the true total; sets `nango_connections.last_reconcile_status = 'paused'`. A share pause of the same connection is never reused as the cap run.

### The cap in `applySourceDeletions`
- `sourcePurgeDailyCap()` reads `env.RAG_SOURCE_PURGE_DAILY_CAP` through `parsePurgeDailyCap` (digits only; `abc`, `-1`, `2.5` → 0 with one `[Source Reconcile]` warning).
- Only the `purge` arm, only `origin === 'change_feed'`, only cap > 0 and at least one record: reserve `records.length` → hold `records.slice(granted)` → purge `records.slice(0, granted)` in input order → release the failed count → one `raiseSourceAlert(connection, 'paused', { held, cap })`.
- Hold runs before purging so a failing hold purges nothing. Fail closed: a reserve error (or a non-integer answer) or a hold error purges nothing, gives back any reservation and returns `failed = batch`, so every sync record is kept and the cursor stays.
- `held` is an optional field set only when something was held; every other return is unchanged, so the exact-equality assertions of 06.3-05/09/12/21 hold unchanged.
- Cap 0, soft, NULL mode, `reconcile` and `admin` origins run the 06.3-21 code unchanged and issue no new RPC (tested).

### Cursor callers with held files
- `handleSyncWebhook` (`webhook-deletions.ts`) and `syncSharePointConnection` (`sharepoint/sync.ts`) gate the cursor on `failed > 0 || deferred > 0` only. An absent or set `held` does not block the cursor, so the same deletions do not create a new held run on every delivery. No caller change was needed.

### Admin list and panel
- `listSourceSyncConnections` reads every open awaiting run of the listed connections in one service-role select (`status = 'awaiting_confirmation'`, `expires_at` in the future, the row's tenant key) and returns them as `paused_runs`, newest first. `paused_run` stays the newest of them (fallback: the SQL list's newest run when the select fails). Each run carries `pause_reason` (`share` for NULL), `daily_cap` on cap runs, and `file_ids` (≤ 20 candidate ids) only when no file name could be read, which closes the 06.3-18 deferred item. `limits.purge_daily_cap` is added. No existing field changed.
- `source-sync.js`: `buildSourceSyncRowView` builds `pausedRuns` from `paused_runs` (falls back to `paused_run`), `pausedRun` is the first; the table renders one paused block per run, each with its own sentence, Remove documents… and Dismiss run. Blocks carry `data-source-sync-run` and `aria-describedby` on their sentence; focus after a dismiss or a failed confirm returns to the block of that run. `paused.bodyCap` (en/zh/it, already added by 06.3-18 with the plan's exact strings) is chosen when `pause_reason === 'purge_daily_cap'`. A share pause view is unchanged.
- Confirming a cap run uses the existing confirm route (origin `admin`, the connection's mode, not capped); dismissing purges nothing and leaves the files to the next full reconcile.
