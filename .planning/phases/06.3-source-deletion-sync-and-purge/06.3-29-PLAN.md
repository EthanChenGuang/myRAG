<objective>
Add the per-connection daily cap on change-feed purges that the owner decided on 2026-11-25 for DATA-23 (D-49): `RAG_SOURCE_PURGE_DAILY_CAP`, off by default and admin-configurable; above the cap, purges wait for admin confirmation.

Purpose: change-feed deletions are exempt from the mass-delete share guard (D-09, D-33) because the source reports them file by file. On a connection in `purge` mode that exemption means a compromised source account or a provider bug can withdraw an unbounded number of documents irreversibly in one day. The cap bounds it per connection and turns the excess into the same paused run an admin already confirms or dismisses for the share guard (plans 06.3-04, 06.3-16, 06.3-18), so no new confirmation flow is added.
Output: migration 0729, the cap in `applySourceDeletions`, the variable in every config location with one Config UI field in the existing settings block, the pause reason in the admin list and the panel, and four test files.

Design recorded here (Claude's discretion within D-49):
- Window: the UTC calendar day (`(now() AT TIME ZONE 'utc')::date`), per connection; counter rows older than 30 days are deleted by the reserve function.
- Counted unit: one purged file id (one sync record), whatever the number of lineages behind it.
- Reservation before purge, release of failed ones after; the counter therefore equals successful purges.
- Held ids go into the connection's open `change_feed` awaiting run of the day when one exists and has not expired (appended without duplicates up to the 2,000-id limit of 0721), otherwise into a new one; ids past 2,000 keep their sync records and are left to the next full reconcile, and the run's `candidate_count` holds the true total.
- A migration is needed because the reservation must be atomic across concurrent webhook deliveries; counting audit rows in the app would race.

Standing rules: (1) trunk moves (D-01): locate `applySourceDeletions`, the purge arm and `purgeNangoLineages` (plan 06.3-21), `DELETION_BATCH_SIZE`, `raiseSourceAlert`, `rag_source_reconcile_run_record` and the `rag_source_reconcile_runs` table (0721), `rag_nango_owner_tenant_key` (0721 mode files), `rag_ingest_assert_tenant_key`, `listSourceSyncConnections` and the limits it returns (plan 06.3-16), `buildPausedRunView` and `SOURCE_SYNC_LABELS` (plan 06.3-18), the `rag-source-sync-settings` markers in `index.html`, and the `RAG_SOURCE_RECONCILE_MAX_DELETE_SHARE` entry in each config location, by name; never by line number; (2) `[HEAD=…]` values were measured at 4b4a488: re-measure each count gate at plan start and stop if one already passes; (3) migration number 0729 only (the phase block is 0720–0739); idempotent, not folded (D-02); (4) style (D-44): 4 spaces and `logger` in `src/lib/nango/*`; logs carry ids and counts only; copy domain-neutral; (5) plain `git commit` with the attribution lines of the executor's own session.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| source change feed to irreversible purge | the source, or whoever controls the source account, decides what is withdrawn |
| concurrent webhook deliveries to the counter | two requests for one connection at the same time |
