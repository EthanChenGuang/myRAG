## What was built

- **Providers (D-24, D-40).** `'sharepoint-online' | 'one-drive'` in `SupportedProvider`; `PROVIDER_CONFIG` entries "SharePoint Online" and "OneDrive for Business" (neutral descriptions, no `syncName`, `fileModel: 'files'`), `integrationId` from `NANGO_SHAREPOINT_INTEGRATION_KEY` / `NANGO_ONEDRIVE_INTEGRATION_KEY`, defaulting to the provider id. Icons: `onedrive.svg` (exists) and `default.svg` for SharePoint (no SharePoint icon in `public/icons/connectors/`). `getProviderDownloadConfig` gains `/v1.0/drives/{drive}/items/{item}/content` with `responseType: 'arraybuffer'`; the drive id comes from a new optional `NangoFileRecord.drive_id` (A5). The generic proxy call passes `responseType` only when set, so the other providers' calls are unchanged. The tsc run flagged no other exhaustive use of `SupportedProvider`.
- **config.ts.** `isSharePointEnabled()` reads `NEXT_PUBLIC_NANGO_SHAREPOINT_ENABLED` at call time (default off). `sharePointIntegrationKey(provider)`.
- **graph.ts (D-21, T-06.3-18, Pitfall 16).** `pathAndQueryOf(link)` accepts only `https://graph.microsoft.com` with no port or user info and a `/v1.0/` path, and returns path plus query; `graphEndpointOf` also accepts a stored `/v1.0/…` path (no `//`, `..`, backslash or control characters). `graphGet` honours `Retry-After` (seconds or HTTP date, default 1 s, at most 60 s per wait, 120 s total, 6 attempts) on 429 and 503, abortable; a wait that would pass the caller's deadline throws `GraphDeadlineError` instead of waiting. `nangoGraphTransport` is one `nango.proxy` GET with no proxy-side retries; an upstream non-2xx is read from the proxy error's `response.status` (A3) and returned. Error words: `graph_link_refused`, `graph_http_<status>`, `graph_deadline`.
- **delta.ts (D-21).** `GraphDeltaFeed implements SourceChangeFeed`, one drive per feed. It pages `@odata.nextLink` until `@odata.deltaLink`, keeps the last occurrence per item id, skips the root item (its id goes to `rootIds`), maps files to `etag` (from `eTag`), `modifiedAt` (from `lastModifiedDateTime`), `name`, `parentId`, `driveId`, `siteId`; deleted items carry only `fileId`, `deleted`, `kind` and `driveId`. No `deltaExcludeParent` and no `Prefer` header is ever sent. It never writes a cursor. 410 on a stored delta link or resumable link calls `onResync` (the caller clears the row) and restarts without a token; the result has `resynced: true` and `fullListing: true`. 410 on a token-less request throws. At the deadline (checked before every request, and for throttling waits) it returns `complete: false` with the in-progress link. `readDeltaCursor` / `commitDeltaCursor` / `clearDeltaCursor` use `rag_source_delta_tokens` (feed `graph_delta`, feed_key drive id, keyed by `nango_connections.id`): a complete page sets `delta_link` and clears `next_link`; an incomplete one sets only `next_link`.
- **scope.ts (D-22, Pitfall 15).** `DriveSelection` (sites, drives, folders with drive id). `parentMapOf(changes, stored, rootIds)` merges newer parents over the stored map, drops deleted items, maps roots to null. `scopeOf` returns `in` for a selected site or drive, or a chain that reaches a selected folder of the same drive; `out` for an unselected drive or a chain ending at a root; `unknown` for a missing parent, a cycle, or (with a site selected) an item without its site id. `scopeRemovals` returns previously synced files that are provably `out`, including files under a folder that moved out and files of a drive no longer selected.

## Behaviour changes

None with the switch off: no route, UI, sync path or default changed. The only code reachable today is the type union, two `PROVIDER_CONFIG` entries and a `getProviderDownloadConfig` case that nothing calls yet.

## Deviations

1. **TDD granularity.** Task 2's feed behaviours (410, resume, throttling, host check) were written into the same RED commit as Task 1 because they share the test file and module; then one implementation commit (a11e92b3e) covers both tasks' feed parts, and the scope part is its own RED/GREEN pair. RED failed on assertions and stub errors, never on a missing module.
2. **Resumable state input.** `GraphDeltaReadInput.nextLink` (extends `SourceChangeFeedReadInput`) instead of encoding two links in one cursor string; the `ChangePage` contract is unchanged.
3. **Full listing across resumed reads.** A token-less enumeration that is resumed reports `fullListing: true` on the read that reaches the delta link; that page holds only the items of the last read. Plan 12 must union the file ids of every read since the token-less start before it diffs a listing (documented on the class).
4. **Scope `unknown`** (not in the plan): an item whose chain cannot be walked is not synced and not a removal candidate, so an incomplete parent map never deletes anything.
5. `GraphChangePage.rootIds` (additive) so the caller's parent map can terminate walks.

## Threat model

- T-06.3-18 (SSRF): only path and query reach the proxy; tests refuse a foreign host, `http:`, a host-less link, a look-alike host, a port and user info; a foreign `@odata.nextLink` stops the read before any further request.
- T-06.3-19 (lost deletions): cursor committed only by the caller after apply; 410 restart is a full listing; resumable `next_link` kept separate from `delta_link`.
- T-06.3-20 (fixtures): the three recordings are hand-written: ids `drive-a`, `site-a`, `item-folder-1`, `item-file-a…c`, `item-gone-1`, names `Folder 1`, `file-a.pdf`, `file-b.docx`, `file-c.txt`, zero GUIDs in eTags; the 410 body is the documented error shape. Nothing copied from a tenant.
- T-06.3-SC: no package added (no Graph SDK).
