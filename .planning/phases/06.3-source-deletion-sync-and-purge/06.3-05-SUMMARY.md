# Phase 6.3 Plan 05: one source-deletion entry point Summary

**Every Nango removal now goes through `applySourceDeletions` (D-03): the owner, tenant and deletion mode come from the `nango_connections` row, the unset mode runs today's loop body unchanged (the 06.3-03 fixture replays byte-identical in all four pipeline/async combinations), `soft` soft-deletes in either pipeline, large listing diffs pause for confirmation, listings report completeness, and documents record when their source last showed them.**

## Branch

`exec/06.3-05` from `origin/exec/06.3-04`, then `git merge --no-ff origin/ci/merge-train-40` (authorized by the orchestrator; no conflicts). No other branch merged.

## What was built

- **Entry point (D-03, D-08).** `applySourceDeletions(connection, fileIds, origin, options)`:
  - loads the sync records with today's filter (`connection_id`, `user_id`, `status in (completed, processing)`, `file_id in (…)`) unless the caller passes the records it already loaded (the sync's listing diff does, so the recorded call list is unchanged);
  - `deletion_mode` NULL → `applyDefaultDeletion` per record: the body of today's `for (const record of batch)` loop moved verbatim (only `continue` → `return deleted` and `deletedCount++` → `deleted = true`); unified owner key via `nangoOwnerScope`, legacy by the record's document id;
  - `soft` → `softDeleteNangoLineages` with the owner's tenant key in either pipeline, then the sync record delete;
  - `purge` → the whole batch is reported `failed` and every sync record kept (purge arm lands in 06.3-21);
  - a sync record is deleted only after its lineage removal succeeded; a repeat call removes nothing and reports no error;
  - `change_feed` and `admin` calls are cut at `DELETION_BATCH_SIZE` (50); the rest is returned as `deferred` (the caller keeps its cursor). `reconcile` (listing diff) calls are not cut, as today. Each `change_feed` call records one `change_feed` run (`completed`, or `failed` with `error_code = removal_failed`).
- **Mass-delete pause (D-09, D-33).** `guardListingRemoval` pauses when `orphans >= 5` and `orphans > share × total sync records`; share from `RAG_SOURCE_RECONCILE_MAX_DELETE_SHARE` (number in (0, 1], otherwise 0.3 with one `[RAG Config]` warning). Paused: one `awaiting_confirmation` run with the candidate file ids (capped at 2,000, the count keeps the full number), `raiseSourceAlert(connection, 'paused', { candidates, total })`, nothing removed. Not paused: one `completed` run (`incomplete` when the listing was cut) with the caller's origin (`sync` inside a sync, `scheduled` for `removeOrphans`). Bookkeeping RPC failures are logged with their code and never change the decision. Change-feed deletions are not share-guarded.
- **`deleteOrphanedDocuments`** keeps steps 1–3 (owner check, record load, orphan diff), then the guard, then `applySourceDeletions(connection, orphanFileIds, 'reconcile')`, and returns the same count. The connection row comes from the existing connection read in `syncDocumentsForConnection` (its select now also reads `id, provider, deletion_mode`; on `42703` — 0720 not applied — it re-reads the old columns and the unset mode applies), threaded through `syncGoogleDriveDocuments`. A connection with an explicit mode, or a `scheduled` call, removes nothing from an incomplete listing (D-31).
- **Completeness (D-31).** `fetchFilesForProvider` returns `{ files, complete }`: Dropbox `has_more`, the records fallback `next_cursor` (a failed call is `complete: false`), Notion search `has_more`/error/child-fetch failure, the proxy Drive path `files.length < 100`; the non-Drive multi-folder loop tracks it per folder. On the unset mode inside a sync these flags change no removal (the characterization still replays).
- **Reconcile exports (plan 06.3-11).** `listConnectionFiles(row)` lists every supported provider with the sync's listing code and ingests nothing (named Drive files and Notion page selections never remove today, so they return `complete: false` except the Notion workspace listing); `removeOrphans(row, currentFileIds, origin, { complete })` runs the guarded removal.
- **Source columns (D-07).** `markSourceSeen` issues one `update` on `documents` (never a select) wherever a listed file with a document is processed or skipped as unchanged (all five `processDocumentWithMetadata` sites and their skip branches): `source_last_seen_at`, plus `source_modified_at` and `source_etag` (Dropbox `rev`, new optional `NangoFileRecord.etag`) when reported. Unified: `tenant_key`, `source = 'nango'`, `source_connection_id`, `source_key = file id`, `is_current`; legacy: the record's document id with `user_id` and `source`. Failures are logged at debug and ignored.

## Known defect for the owner (D-31)

The unset (NULL) deletion mode inside a sync still removes orphans from an incomplete listing for Dropbox, the records fallback, Notion's generic path and the non-Drive multi-folder loop (only Google Drive was guarded before). The flags now exist; D-48 (owner decision) makes the default path require `complete === true`, which is plan 06.3-28.

## Decisions

- `applySourceDeletions` returns `{ removed, failed, deferred }` (`deferred` added for the batch cut so the webhook keeps its cursor; the plan named `{ removed, failed }`).
- Batch cut applies to `change_feed` and `admin` origins only; `reconcile` keeps today's full processing in batches.
- A completed `sync` run is recorded on every complete, unpaused listing, including one with no orphans and one with no sync records (advances `last_full_reconcile_at`).
- `loadSourceConnection(admin, connectionId, userId, { admin? })` filters by owner; another user id reads nothing.
- `markSourceSeen` under unified stamps by identity only; pre-unified rows without `source_connection_id` are not stamped under unified (no select is allowed there).
