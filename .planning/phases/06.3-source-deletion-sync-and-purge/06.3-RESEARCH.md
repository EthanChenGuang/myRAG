A store that does not exist on trunk at execution time is handled by the guard in D-14, not by inventing its schema here.

#### Migrations
- **D-02:** Phase 7 uses 0701–0707 inside the 0700–0719 block, so Phase 6.3 uses **0720–0739**. Migrations are idempotent, common file first with `.single-tenant.sql` / `.multi-tenant.sql` only where the mode differs, and are **not folded** into the setup files. All new functions are `SECURITY DEFINER`, `SET search_path = ''`, service_role only, with tests asserting anon and authenticated cannot execute them (Phase 3 / Phase 4 pattern). — **Reversibility:** one-way — new columns and tables on `documents`, `nango_connections` and new audit tables need a migration to undo.

#### Change-feed deletions (DATA-23)
- **D-03:** One deletion entry point, `applySourceDeletions(connection, fileIds, origin)` in `src/lib/nango/` (origin: `change_feed` | `reconcile` | `admin`), replaces the per-call choice inside `deleteOrphanedDocuments`. It resolves the tenant from the connection owner (`nangoOwnerScope`), finds lineages by identity (`collectNangoLineageIds`: `source_key` / `source_file_id` of this connection, never the sync record's `document_id`), applies the connection's deletion mode (D-08), is idempotent, and deletes the sync record only after the lineage removal succeeded (today's retry semantics).
- **D-04:** Change feeds are read through a small `SourceChangeFeed` interface per provider: Nango sync records with the deleted filter (where a Nango sync with records exists for the provider) and Microsoft Graph delta (SharePoint/OneDrive, D-20). Providers whose sync is a proxy listing with no change feed (today's Google Drive, Dropbox, Notion paths) rely on the scheduled reconciliation as before; adding provider-native change APIs for them is deferred.
- **D-05:** `/api/nango/webhook` handles sync webhooks that report deletions: after signature verification it reads the deleted records since the stored cursor and calls `applySourceDeletions` inline, bounded per request (Vercel 60 s limit); the cursor is persisted only after the batch succeeded, so an unfinished batch is picked up by the next webhook or sync. Duplicate deliveries are harmless because deletion is idempotent. Unknown connection ids are acknowledged without effect (no oracle).

#### Scheduled reconciliation (DATA-23)
- **D-06:** The existing full-listing orphan removal is also run on a schedule: `npm run rag:reconcile` plus an authenticated internal route (`POST /api/internal/rag/reconcile`, shared-secret auth like the other internal routes, off in production unless enabled), each call bounded and processing connections that are due; an optional Vercel cron entry is documented, not enabled by default. Cadence `RAG_SOURCE_RECONCILE_INTERVAL_DAYS=7`. Same shape as the OBS-03 job (CLI, admin route, optional scheduler).
- **D-07:** New columns: `nango_connections.last_full_reconcile_at`, `last_reconcile_status`, `deletion_mode`; `documents.source_last_seen_at`, `source_modified_at`, `source_etag` (nullable, set by every sync that sees the file). Only a listing that completed may remove documents or advance `last_full_reconcile_at` (the existing listing-complete guard stays). — **Reversibility:** one-way — columns on shared tables.
- **D-08 (deletion mode):** `nango_connections.deletion_mode` is nullable with values `soft` | `purge`. **NULL means today's behaviour, unchanged code path** (the current pipeline-dependent choice: soft-delete under unified + async, hard delete of all versions otherwise). `soft` forces `rag_soft_delete_document` (versions kept for citations and history); `purge` runs DATA-24. Changing the mode affects future deletions only; nothing is purged retroactively. *(Wording change requested for DATA-23 — see Specifics.)*
- **D-09 (mass-delete pause):** Any full-listing removal (scheduled or inside a sync) that would remove more than `RAG_SOURCE_RECONCILE_MAX_DELETE_SHARE` (default `0.3`) of a connection's documents, and at least a small fixed floor of documents (planner's choice, e.g. 5, so a 1-of-2 removal is not paused), records a reconcile run in `awaiting_confirmation` with its candidate file ids, removes nothing, and raises an alert. An admin confirms or dismisses in the admin UI; a confirmation older than 24 h is refused and needs a fresh run. Change-feed deletions (explicit per-file delete events) are not subject to the share guard.
- **D-10 (reconcile-age alert):** A connection whose `last_full_reconcile_at` is older than `RAG_SOURCE_RECONCILE_MAX_AGE_DAYS` (default 7, NULL counts from `connected_at`) raises an alert and shows a warning in the admin UI. Alerts go through a thin `raiseSourceAlert` adapter: if the OBS-03 alert store from Phase 5.3 exists on trunk at execution, it writes there; otherwise it records the alert on the connection row (`last_reconcile_status`) and logs `[Source Reconcile]`.

#### Purge (DATA-24)
- **D-11:** One server-only SQL function `rag_purge_lineage(p_tenant_key, p_lineage_id, p_actor, p_reason)` removes every version of the lineage from every database store in **one transaction**: chunks and parent chunks, vectors in every embedding profile, stored translations, table rows, duplicate-cluster memberships (with the cluster recompute the owning phase defines), parse-cache entries (only when no other live document of the tenant shares the content hash), semantic-cache entries (`rag_cache_invalidate` with the version ids), citation snapshots (D-13), then the `documents` rows; it writes the audit row (D-12) and returns per-store counts. The tenant is asserted with the existing tenant-key guard. — **Reversibility:** one-way — purge destroys data by design.
- **D-12 (audit):** New table `rag_purge_audit` (tenant key, lineage id, version ids, source, source key, actor kind and id — admin user or `source_sync` with connection id —, reason code plus free text, started/finished times, per-store counts, verification result, pending object paths). It stores ids and hashes only, never titles or text of the withdrawn content. RLS on, service_role writes, tenant admins read their tenant's rows through a server route.
- **D-13 (withdrawn marker):** Citation snapshots in `rag_answer_records.citations` and any persisted message sources of the purged versions have their text replaced by a flag (`withdrawn: true`, `withdrawn_at`) with the snapshot text removed; the UI renders a localized "source withdrawn" string at display time (translations for every UI language already in `src/translations/`). The marker is a flag, not stored prose.
- **D-14 (stores owned by other phases):** Each purge step for a store owned by an unmerged phase (table rows, cluster memberships, translations, golden items) is guarded so the migration applies whatever order phases land in (existence check by relation name, dynamic SQL with quoted identifiers). The executor re-reads trunk and names the real tables; a verification test fails when a store listed in DATA-24 exists on trunk but has no purge step.
- **D-15 (objects and external backends):** Originals and parse files in the private `rag-originals` bucket are removed by the app after the transaction commits (reuse `removeDocumentObjects`); failures are recorded as pending paths on the audit row and retried by the next reconcile run. External backends need no extra call: the Phase 7 outbox delete triggers on `document_chunks`/`documents` enqueue the deletes; a test asserts a purge produces outbox delete events for every chunk id (the RET-05 delta).
- **D-16 (verification):** `rag_purge_verify(p_tenant_key, p_lineage_id)` returns the remaining row count per store (same guarded store list); a purge is reported successful only when every count is zero and pending objects are empty. The admin UI shows the result; the audit row stores it.
- **D-17 (golden items):** Purge marks golden items with evidence in the lineage `stale` through the EVAL-29 hook if Phase 5.3 has landed; otherwise the audit row is the record the EVAL-29 nightly stale check reads (the planner adds a reader contract only if 5.3 is on trunk).
- **D-18 (admin entry):** A new admin-only `POST` purge route for a document (reason required, owner-or-admin rules as the existing document routes, tenant-scoped, unknown and other-tenant ids answer the same 404). The existing `DELETE /api/documents/[id]` is unchanged.

#### Source-of-truth recheck (RET-14)
- **D-19:** `RAG_SOURCE_RECHECK=false` by default. When on, `runRetrieval` (inside `@/lib/rag`, both legacy and v2 pipelines) runs one batched server-only RPC `rag_source_recheck(p_tenant_key, p_chunk_ids)` after search and fusion and before rerank, keeping only chunks whose document exists in the tenant as current, ready and not quarantined (and passes the access-group filter when Phase 4.3 is on trunk). Dropped chunks are counted on the trace as `stale_index_drop` (Pydantic trace contract → generated Zod). One indexed query; it counts against the retrieval stage of the latency budget.
- **D-20 (external backends):** On Weaviate and Qdrant the recheck is always on and is Phase 7's `rag_validate_chunks` re-validation; its drops are reported in the same `stale_index_drop` counter, with no second query. A non-zero drop asynchronously requests the RET-05 reconcile for those ids (external backends) or logs and counts for OBS-03 (pgvector); it never blocks the request.

## Summary

The repository already has the two deletion behaviours this phase must keep (`softDeleteNangoLineages` and `deleteNangoLineages` in `src/lib/nango/sync-manager.ts`), the server-only soft delete (`rag_soft_delete_document`), an audited single-version delete to copy (`rag_delete_quarantined` with `rag_admin_audit`), tenant-wide cache invalidation by trigger (0603), and Phase 7's change capture (0701–0703). What does not exist is any automatic trigger: `syncDocumentsForConnection` is called only on connect, from the manual `POST /api/nango/sync`, and from a webhook branch that real Nango payloads cannot reach. `NANGO_SYNC_INTERVAL_HOURS` is defined and never read. Today a source deletion reaches the knowledge base only when a user presses Sync. [VERIFIED: grep of `syncDocumentsForConnection` and `NANGO_SYNC_INTERVAL_HOURS` callers this session]

Twelve findings change how the phase must be planned; they are listed in "Corrections the planner must act on" below. The three with the largest effect: (1) Phase 7 plan 07-13 already claims the npm script name `rag:reconcile` for the external-backend reconcile, which collides with D-06; (2) the webhook handler's payload types and signature check do not match Nango's documented contract, so D-05 needs a new header, a new `type: "sync"` branch and a decision on what to do with the legacy branches; (3) `CitationRecord` is a strict contract with `quote` of minimum length 1, so the D-13 marker needs a contract change that ships before any SQL writes the flag, otherwise withdrawn citations silently disappear from the UI instead of showing the marker.

For the unmerged phases (4.2, 4.3, 5.3) there is nothing to read: `.planning/phases/04.2-*`, `04.3-*`, `05.3-*` do not exist on this checkout and the branches `claude/plan-04.2`, `claude/plan-04.3`, `claude/plan-05.3` are not on `origin`. Research for their stores is limited to the requirement texts, and this document names seams, not schemas.

**Primary recommendation:** Build in this order: contracts and env first; a characterization test of today's deletion calls recorded before any refactor; migrations 0720+; `applySourceDeletions` as a pure move of the existing loop body plus two explicit modes; purge SQL modelled on `rag_delete_quarantined`; the recheck as an `exact_id_lookup`-style conditional stage; SharePoint through `nango.proxy` with no new npm package; the Graph permission plan last behind a 4.3 checkpoint.

## Answers to the planner's questions

### Q1. Deletion paths today and where `applySourceDeletions` slots in

All in `src/lib/nango/sync-manager.ts` unless stated. [VERIFIED: file read in full with the Read tool this session]

**Call graph today**

```
syncDocumentsForConnection(connectionId, provider)
 ├─ google-drive, multi-folder  → syncGoogleDriveDocuments(..., skipOrphanDeletion=true) per folder
 │                                 then deleteOrphanedDocuments(...) once, only if every folder listing was complete
 ├─ google-drive, file ids      → syncGoogleDriveFilesByIds(...)            (no orphan deletion)
 ├─ google-drive, single folder → syncGoogleDriveDocuments(...)             (deleteOrphanedDocuments only if listing.complete)
 ├─ notion (all three modes)    → syncNotionPagesByIds / syncNotionPageWithChildren   (no orphan deletion at all)
 └─ any other provider          → fetchFilesForProvider(...) then deleteOrphanedDocuments(...) unconditionally
                                   (multi-folder: a folder whose fetch threw is logged and skipped, deletion still runs)

deleteOrphanedDocuments(connectionId, userId, currentFileIds, supabaseAdmin)
 1. tenantKey = scopeKey(nangoOwnerScope(owner))   only when nangoPipeline() === 'unified'; otherwise null
 2. load nango_sync_records of (connection_id, user_id) with status in ('completed','processing')
 3. orphans = records whose file_id is not in currentFileIds
 4. per orphan, batches of DELETION_BATCH_SIZE (50):
      tenantKey !== null → orphanUsesSoftDelete() ? softDeleteNangoLineages(...) : deleteNangoLineages(...)
                           false result → continue (sync record kept, next sync retries)
      tenantKey === null and record.document_id → delete documents by id + user_id + source='nango'
      then delete the nango_sync_records row; deletedCount++
```

- `orphanUsesSoftDelete()` is `nangoPipeline() === 'unified' && queueConfigFromProcessEnv().ingestAsync`, with a `catch` that returns false.
- `collectNangoLineageIds(admin, tenantKey, connectionId, fileId)` runs two selects on `documents` (`source_key` then `source_file_id`), each filtered by `tenant_key`, `source = 'nango'`, `source_connection_id`.
- `softDeleteNangoLineages` calls `softDeleteLineage(owner.scope, lineageId, 'nango', { signal: AbortSignal.timeout(120_000) })` from `src/lib/rag/ingest/soft-delete.ts`, which is the only application entry to `rag_soft_delete_document`.
- `deleteNangoLineages` selects the version rows, deletes `document_chunks` by `document_id`, deletes `documents` by `lineage_id` + `tenant_key` + `source`, then calls `removeDocumentObjects({ tenantKey, rows })`.
- The legacy branch (default `RAG_INGEST_PIPELINE=legacy`) deletes the document row named by the sync record and relies on a cascade for chunks. Single-tenant has no such cascade (Q3), so that delete fails with a foreign-key error, the error is logged, and the sync record is deleted anyway. - `rag_cache_invalidate(p_tenant_key text, p_document_ids uuid[] DEFAULT NULL) RETURNS integer`: deletes all of the tenant's rows when the array is NULL, otherwise rows whose `source_versions` reference one of the ids. `SECURITY INVOKER`, `SET search_path = ''`, service_role only, and it calls `rag_assert_tenant_key` first.

- Updates to the new `documents.source_last_seen_at`, `source_modified_at`, `source_etag` columns fire the update trigger but change none of the compared columns, so they do not flush the cache.

**Drive delta** [CITED: learn.microsoft.com/graph/api/driveitem-delta, page updated 2026-06-06]

- Requests: `GET /drives/{drive-id}/root/delta`, `/sites/{siteId}/drive/root/delta`, `/me/drive/root/delta`, `/users/{id}/drive/root/delta`, `/groups/{id}/drive/root/delta`. Every documented form is on `root`.
- `token` parameter: absent enumerates the current state; `latest` returns an empty page with the latest delta link; a previous token returns changes since it. A URL-encoded timestamp is accepted as a token on OneDrive for Business and SharePoint only.
- Page until there is no `@odata.nextLink`; the final page has `@odata.deltaLink`. Apply the changes after the whole set was received, then store the delta link (this is D-21's "updated only after the page set was applied").
- Deleted items carry the `deleted` facet. On OneDrive for Business a deleted item omits `ctag` and `name`. Created or modified items omit `ctag` on OneDrive for Business.
- The same item can appear more than once; use the last occurrence. The feed shows the latest state per item, not each change.
- `parentReference` has no `path` in delta responses; track items by id.
- By default the response includes the parent items of changed items; the request header `deltaExcludeParent` turns that off.
- A folder should be removed locally only if it is empty after all changes were applied.
- When the service cannot serve a token it answers `410 Gone` with error code `resyncChangesApplyDifferences` or `resyncChangesUploadDifferences` and a `Location` header holding a fresh `nextLink`. After the full enumeration, the first code means: replace local items with the server's version, deletes included.
- Permissions: delegated `Files.Read` (least), `Sites.Read.All` higher; application `Files.Read.All`.
- `Prefer: deltashowsharingchanges` requires two more Prefer values and `Sites.FullControl.All`. Do not use it.
- No token lifetime is stated on the page. Treat 410 as the only signal.

**Scanning guidance** [CITED: learn.microsoft.com/onedrive/developer/rest-api/concepts/scan-guidance, updated 2026-05-14]

- Each document library of a site is a drive: `GET /sites/{site}/drives`. Each user's OneDrive is one drive.
- `delta` is the only way to guarantee a complete enumeration; paging `children` is not, when writes happen during the enumeration.
- 429 and 503 mean throttling: wait for `Retry-After` and pause all requests to the tenant.
- A periodic delta check no more than once a day is the suggested fallback when no notifications arrive.
- Delegated permissions restrict the app to content the signed-in user can access.

**Item permissions** [CITED: learn.microsoft.com/graph/api/driveitem-list-permissions, updated 2025-07-23]

- `GET /drives/{drive-id}/items/{item-id}/permissions`; delegated `Files.Read` (least); application `Files.Read.All`.
- Each permission has `id`, `roles`, either `grantedToV2` (with `user`, `siteUser`, and group forms) or a `link` (`type`, `webUrl`), and `inheritedFrom` when it comes from an ancestor. `grantedTo` is deprecated in favour of `grantedToV2`.
- "For a non-owner caller, only the sharing permissions that apply to the caller are returned." An item owner or co-owner sees all of them.
- The `permissions` relationship cannot be expanded on a driveItem or a collection: one request per item.

**Picker endpoints.** Verified from fetched pages: `GET /v1.0/sites` (the Nango SharePoint quickstart example, and the scan guidance for application permissions), `GET /v1.0/sites/{site}/drives`, `GET /v1.0/me/drives` (the Nango OneDrive quickstart). Folder browsing (`/drives/{d}/root/children`, `/drives/{d}/items/{i}/children`), delegated site search (`/sites?search=`), and download (`/drives/{d}/items/{i}/content`) are from training knowledge: tagged A4.

**eTag / cTag.** `eTag` changes when the item's metadata or content changes; `cTag` changes with content only (the scan guidance recommends `cTag` for download decisions). Delta does not return `cTag` on OneDrive for Business, so `documents.source_etag` should hold `eTag`. The ingest path already decides "unchanged" by hash (`file_hash_dedup` and `content_hash_dedup` stages), so the ETag is a pre-download skip, not the source of truth.

**Scope filtering by folder.** Because delta has no `path`, "is this item inside a selected folder" must be answered by walking `parentReference.id` up to a selected folder id or the root. Ancestors of changed items are in the same response unless `deltaExcludeParent` is sent, so do not send it.

**Item id uniqueness.** `source_key` is the drive item id (D-22). The lineage identity index is `documents_lineage_identity_ux (tenant_key, source, source_key) WHERE is_current` and `nango_sync_records` is `UNIQUE (user_id, file_id)`; neither includes the drive. Whether SharePoint item ids can collide across two drives of one tenant is not stated on the pages fetched: tagged A5, with the drive id stored in sync-record metadata as a cheap safeguard.

### Anti-patterns to avoid

- **Rewriting the default deletion path "equivalently".** D-28 says byte-for-byte; move the code.
- **Trusting the webhook body for anything but "look now".** The owner comes from the `nango_connections` row; the file ids come from the Nango records API; the body only names the connection.
- **Treating any listing as complete.** Only Google Drive's listing reports completeness today.
- **Deleting documents before chunks without a cascade.** Fails in single-tenant.
- **Writing the withdrawn flag before the contract change is deployed.** Citations disappear.
- **A `.mts` test outside the three CI globs.** It never runs.
- **Calling ledger or parse-cache tables through PostgREST.** The `ledger-table-write` and `cache-rpc` boundary rules forbid it; the purge does it in SQL.
- **An overloaded `rag_*` function.** The fake edge refuses it.
- **Example content in fixtures.** Describe fixtures by structure; synthetic neutral names and ids only.

## Common Pitfalls

### Pitfall 1: The webhook branch never runs
**What goes wrong:** deletions "handled in the webhook" never happen in production. **Why:** header and payload mismatch (Q2). **Avoid:** read `x-nango-hmac-sha256`, branch on `type === 'sync'`; test with a synthetic body signed the way `packages/webhooks/lib/utils.ts` signs it. **Warning sign:** `[Nango Webhook] Invalid signature` on every delivery.

### Pitfall 2: Fixing the webhook changes default behaviour
**What goes wrong:** once verification passes, the legacy `sync.success` code would start a full `syncDocumentsForConnection` on every Nango sync — new behaviour with every switch off. **Avoid:** the new `sync` branch does the deletion read only; leave the unreachable legacy branches as they are, or remove them by an explicit decision. Also note the legacy branch starts the sync without awaiting it, which a serverless function may cut off; D-05's inline, bounded processing is the right shape.

### Pitfall 3: Incomplete listings read as deletions
**What goes wrong:** documents removed because a listing was cut short. **Where:** Dropbox (`has_more` ignored, one page of `MAX_FILES_PER_SYNC`), the records fallback (`next_cursor` ignored), multi-folder mode for non-Drive providers (a failed folder is skipped and deletion still runs), `listNotionPages` (returns `[]` on error). **Avoid:** the scheduled job reconciles a connection only when its provider's listing reports completeness; an empty completed listing for a connection that has synced records pauses for confirmation.

### Pitfall 4: Nango "deleted" is a diff, and Nango says not to act irreversibly on it
See C-8. **Avoid:** route Nango-records deletions through the share guard; in `purge` mode consider soft-delete first and purge after confirmation.

### Pitfall 5: Cursor saved before the work is done
**What goes wrong:** a timeout after the cursor was stored loses deletions permanently. **Avoid:** persist the cursor / delta link after `applySourceDeletions` returned for the whole batch (D-05, D-21); test by aborting between the two steps.

### Pitfall 6: Admin purge undone by the next sync
See C-9. **Warning sign:** a purged connector document reappears with a new lineage id.

### Pitfall 7: Foreign-key failure in single-tenant
**What goes wrong:** `DELETE FROM documents` fails. **Why:** no cascade to `document_chunks`. **Avoid:** explicit chunk delete; run every purge test in both modes.

### Pitfall 8: Ledger rows and public pictures survive
**What goes wrong:** `rag_purge_verify` reports zero while the file name sits in `ingestion_jobs.filename` and page pictures stay publicly readable by URL. **Avoid:** rows 8, 9, 20, 21, 22 of the inventory are part of the purge and of the verification.

### Pitfall 9: In-flight ingest recreates data
**What goes wrong:** a worker finishes a job for the lineage after the purge. **Avoid:** the purge locks the lineage's document rows and deletes its ledger rows; later writer calls then fail with `tenant_mismatch` because the document row is gone. Add a test with a job in `parsing`.

### Pitfall 10: Verification with nothing to look up
**What goes wrong:** `rag_purge_verify` cannot find version ids after the purge. **Avoid:** read them from the audit row (Q3).

### Pitfall 11: Scanning `chats` for every purge
**What goes wrong:** a jsonb scan of all chats. **Avoid:** bound by tenant (`organization_id` / `user_id`, mode-specific like 0502), test for the document id with a jsonb path predicate before rewriting, and run inside the purge transaction only for the purged tenant.

### Pitfall 12: Audit table that cannot be finished
**What goes wrong:** an append-only trigger like `rag_admin_audit_immutable` blocks storing the verification result and clearing pending paths. **Avoid:** allow updates of `verification`, `pending_object_paths`, `finished_at` only, through a definer function; reject deletes and changes to identity columns.

### Pitfall 13: `cTag` expected from delta
See C-7. **Avoid:** store `eTag`; rely on the content hash for change detection.

### Pitfall 14: Incomplete permission lists look complete
**What goes wrong:** a delegated, non-owner connection sees only its own permissions, the mapping produces a narrow group set, and nothing signals the gap. **Avoid:** document the precondition (owner / site admin, or the client-credentials provider) in the permission plan; when in doubt the document is visible to uploader and admins only (D-23).

### Pitfall 15: Items that move out of the selected scope
**What goes wrong:** D-22 ignores out-of-scope items, so a file moved out of a selected folder stays in the knowledge base. **Avoid:** an item that was synced and now resolves outside the selection is a removal candidate; the full enumeration is the backstop.

### Pitfall 16: Throttling and long enumerations
**What goes wrong:** a first enumeration of a large library exceeds 60 seconds. **Avoid:** persist the in-progress `nextLink` as resumable state, separate from the delta link; honour `Retry-After`; the Nango provider config retries on that header.

### Pitfall 17: A disabled stage still leaves a trace record
See Q6. **Avoid:** `if (config.sourceRecheck)` around the stage; assert trace equality with the switch off.

### Pitfall 18: Config hash and pin drift
**What goes wrong:** `tests/eval-env-pin.test.ts` fails, or the gate reports a config mismatch against the committed baseline. **Avoid:** regenerate the pin, re-record the baseline, show a zero paired difference.

### Pitfall 19: Generated files during a merge train
**What goes wrong:** conflicts in `contracts.generated.ts`, `samples.json`, the five config files and `package.json`, which Phases 3.1.1, 3.2, 5, 5.1, 6 and 7 are also editing. **Avoid:** small edits located by symbol; regenerate after every rebase; contract and env plans go first and stay narrow.

### Pitfall 20: Benign drops raise a security log
See Q5. **Avoid:** tell the Phase 7 owner; do not silence it here.

### Webhook signature the way Nango signs it

```ts
// Source: github.com/NangoHQ/nango packages/webhooks/lib/utils.ts (HMAC over the raw body, hex digest)
import crypto from 'node:crypto';
function nangoHmacOk(header: string | null, rawBody: string, signingKey: string): boolean {
  if (!header || !signingKey) return false;
  const expected = crypto.createHmac('sha256', signingKey).update(rawBody).digest('hex');
  const a = Buffer.from(header), b = Buffer.from(expected);
  return a.length === b.length && crypto.timingSafeEqual(a, b);   // timingSafeEqual throws on unequal lengths
}
```

The existing helper already computes this digest; only the header it is compared with is wrong. Verify against the raw body, before `JSON.parse`.

### Threat model

| # | Threat | STRIDE | Severity | Mitigation |
|---|--------|--------|----------|------------|
| T1 | Purge or soft delete reaches another tenant's lineage (wrong tenant key, forged lineage id, a sync record pointing at another lineage) | Elevation of privilege / Tampering | critical | Tenant key from `nangoOwnerScope` or the verified admin, never from a request; `rag_assert_tenant_key`; every statement predicates on `tenant_key`; lineages found by identity within the connection; two-tenant SQL tests where tenant A purges with tenant B's lineage id and nothing changes; mode-mismatched key rejected |
| T2 | Admin purges a tenant they do not administer | Elevation of privilege | high | SQL re-checks `admin_users` and `rag_admin_tenant_keys(p_actor)`; route passes only the verified id |
| T3 | Forged webhook triggers deletions | Spoofing | high | HMAC required; body names only the connection; file ids come from the Nango API; owner from the connection row; unknown connection → no effect and no oracle |
| T4 | Replayed webhook | Spoofing / Denial of service | medium | Idempotent deletion; data re-read from Nango, so a replay cannot reintroduce old state; per-connection minimum interval between feed reads; bounded batch |
| T5 | Webhook signing key confusion (API key used as signing key, or the legacy header accepted) | Spoofing | medium | Accept only `x-nango-hmac-sha256`; document which dashboard value goes into `NANGO_WEBHOOK_SECRET`; never fall back to the length-extension-prone legacy scheme |

| T7 | Unauthenticated or internet-facing reconcile route | Elevation of privilege / Denial of service | high | 404 in production unless enabled; 32+ character secret, constant-time compare; bounded work per call; no tenant or connection id taken as authority beyond an optional filter |
| T8 | Audit tampering or a purge without an audit row | Repudiation | high | Audit insert in the purge transaction; append-only trigger; only verification, pending paths and finish time updatable through one definer function; no delete; RLS on, no client policy; tenant admins read through a server route scoped by `rag_admin_tenant_keys` |
| T9 | Audit or logs leak withdrawn content | Information disclosure | medium | Ids and hashes only; reason free text is the admin's own words, length-capped; test that the audit row and log lines contain no file name or chunk text |
