# Phase 6.3 Plan 09: Nango sync webhook applies deletions Summary

**A signed Nango `type: 'sync'` webhook now reads the deleted records since the stored cursor and removes them through `applySourceDeletions` inside the request, in batches of 50, storing the cursor only after a batch applied cleanly; full-sync diffs go through the share guard, forgeries get 401, unknown connections look exactly like known ones, and no webhook starts a full sync.**

## What was built

- **Signature (D-32, T-06.3-21).** The route reads `x-nango-hmac-sha256` and checks it against the raw body with the existing `verifyWebhookSignature` (HMAC-SHA256 hex, `timingSafeEqual`; a length mismatch throws inside and is caught as false). Without that header, or with only the legacy `X-Nango-Signature`, it answers 401, also when the legacy header carries the right HMAC. A body that is not JSON after a valid signature answers 400. Nango disabled is still 503, missing admin still 500.
- **`NangoRecordsFeed` (D-04).** `listRecords({ providerConfigKey, connectionId, model, filter: 'deleted', cursor, limit: 100 })`, paged until `next_cursor` is null (complete), the deadline, the signal or 200 pages (incomplete). Each change carries the record's `_nango_metadata.cursor`; a record whose `last_action` is not `DELETED` is reported `deleted: false`. `nextCursor` is the last position read, or null when nothing was read. It never writes a cursor and has no database import. The SDK client is injectable (`client`), defaulting to `getNango()`.
- **`handleSyncWebhook` (D-05).**
  - Ignores anything but `type 'sync'` with `success === true` and a non-empty connection id, integration key and model (≤ 256 chars, the feed_key limit).
  - Owner: reads `user_id` of the `nango_connections` row by `connection_id` (unique), then `loadSourceConnection(admin, connectionId, owner)`; owner and deletion mode come only from that row. No row → `unknown_connection`, no records call. The body's `providerConfigKey` must equal the row's provider or its configured integration id, otherwise nothing is read.
  - Reads the stored cursor; a read failure stops before any Nango call.
  - Deleted ids are de-duplicated (last occurrence wins, feed order kept) and applied in batches of `DELETION_BATCH_SIZE` (50) with origin `change_feed`, so each batch records one `change_feed` run (06.3-05). After a batch with `failed === 0` and `deferred === 0` the cursor is upserted: the position of the batch's last record, or the feed's `nextCursor` for the last batch of a complete read. A failed batch stops and leaves the cursor; the overall deadline (15 s from the route, half of it for reading) stops between batches.
  - An empty complete read advances the cursor when it moved.
- **Full-sync guard (D-33, T-06.3-24).** `fullListing` = `checkpoints.from === null`, or no `checkpoints` and no stored cursor for that model. A full listing that was cut removes nothing (`incomplete_listing`). A complete one goes through `guardListingRemoval` (origin `sync`, denominator = the connection's sync records in `completed`/`processing`); paused → one `awaiting_confirmation` run, one source alert, nothing removed, cursor kept. Incremental deletions are not share-guarded.
- **Route branches.** `case 'sync'` awaits `handleSyncWebhook` inside the request; any thrown error is logged with its code only. `case 'auth'` logs the operation word (`creation | override | refresh | deletion | other`) and the success flag. Every handled delivery answers 200 `{ received: true }` — the same body for unknown, refused, paused, failed and applied (no oracle, T-06.3-23).
- **Logs.** `[Nango Webhook]` lines carry the connection row id, status and counts; no record payload, file name or cursor value.

## Behaviour changes

1. **The webhook becomes live.** Before, every real Nango delivery failed verification (wrong header), so the route was inert (RESEARCH A1). Now a correctly signed `type: 'sync'` delivery removes the files Nango reports deleted, with the connection's deletion mode (NULL → today's default deletion body). There is no switch for this; the plan makes it the default path (D-05). Deployments with no Nango records sync (google-drive, dropbox and notion list through the proxy, RESEARCH Q2) see empty deleted-record reads, so nothing changes for them.
2. **Legacy `sync.success` no longer starts `syncDocumentsForConnection`** (decision below). It still updates `last_sync_at`. `sync.error` and `auth.token_expired` are unchanged.
3. `NANGO_WEBHOOK_SECRET` must now hold Nango's webhook signing key (Environment Settings), not the API secret — documented by plan 06.3-24. No new variable.

## Decisions

- **Legacy `sync.success` call removed.** The plan says to leave the legacy cases unchanged, but its must-have truth and the behaviour list say a webhook must never start a full sync, and with the new header a signed body of type `sync.success` would reach that branch. Pitfall 2 allows removing it "by an explicit decision"; I removed only the un-awaited `syncDocumentsForConnection(...)` call and kept the `last_sync_at` update.
- **Per-record cursors.** Without them a deletion burst above 50 would re-read the same cursor forever (each request applies the first 50 and can never advance). The cursor advances per applied batch to the last applied record's position; a later re-read re-applies nothing (idempotent).
- **Read budget** is half of the remaining deadline so the batches have time to apply; the cursor never passes an unapplied record.
- **Cut full-sync read removes nothing** (a partial diff would understate the share the guard sees).
- **Same 200 body for every handled delivery,** including feed or bookkeeping failures, so Nango's retry is not used; the next webhook or sync resumes from the stored cursor.

## Deferred

- A full-sync diff that stays paused is re-guarded by every later webhook for that model (one awaiting run and alert each time) until an admin confirms; deduplicating repeated pause runs belongs with the confirmation flow.
- If the first stored cursor came from an incremental run and a later run is a full sync, the guard decision uses the payload's `checkpoints`; a webhook delivered out of order could apply full-sync deletions as incremental. Nango sends in order per connection; a sequence check was not added.
- The OBS-03 alert rule for source sync is still missing (06.3-05 deferred item).
