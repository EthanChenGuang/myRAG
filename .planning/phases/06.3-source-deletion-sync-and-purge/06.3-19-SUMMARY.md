# 06.3-19 Summary: purge store inventory, catalog coverage test and guarded foreign-store steps

`rag_purge_lineage` now reaches the stores that other phases own (translations, table rows, duplicate clusters, supersession, rebuild and recaption items, scope tags, identifiers), and `rag_purge_verify` counts what is left in each of them. It does this only when the store's hook or relation exists, so 0728 applies in any order with those phases. `rag_purge_store_inventory()` lists every store that references documents, chunks or parents. A catalog-driven test fails CI when a table with such a reference is missing from that list.

## Behaviour changes

- `rag_purge_lineage` (0727) already called `rag_purge_foreign_stores` when that function existed. It now exists, so a purge also empties the lineage's rows in the stores listed above, and the counts gain their keys. `rag_purge_verify` gains their rows. Nothing in the app calls the purge yet (06.3-20), so chat, strict mode, webSearch, `source_images`, voice and embed are unchanged. No switch or env variable was added.
- On a database without the other phases' stores (migrations through 0728 only), the purge succeeds and reports none of those keys.
- Duplicate clusters are not deleted. The 0853 hook removes the purged documents from each cluster and marks it dirty, and the cluster is recomputed later.

## Deviations

1. The plan's test scaffolding assumed the other phases' stores were absent, so the test would create `public.chunk_translations` itself. They are present on this branch, so the tests cover both cases. With every migration applied, the tests seed the real `chunk_translations`, `rag_table_rows` and `rag_dup_clusters`. On a database with migrations through 0728 only (new `createWorld(mode, { migrationsThrough })` option in `tests/helpers/purge-fixture.mts`), the tests create the stand-in table and hook functions from the plan.
2. `tests/rag-db/purge-lineage.test.mts` (not in the file list) used to pin the exact counts object and verify store list. It now pins the 0727 stores and allows the foreign keys from 0728.
3. `supabase/migrations/0410_security_definer_rpc_grants.sql` (not in the file list) gained three guarded service_role-only entries for the new functions. This follows the 06.3-15 precedent.
4. The coverage regex is broader (prefixed columns), and the inventory is SECURITY INVOKER. Both are explained under key-decisions.
5. Beyond the three store ids the plan names, the purge also calls the shipped 3.2 hooks (supersession, rebuild, recaption, scope_tags, translation_gaps) and the 4.2 identifiers hook. The brief's standing rule says every 3.2 and 4.2 store's hook must be reached by the purge.

## Notes for later phases

- A phase that adds a table with a document, chunk or lineage reference (by foreign key, or by a column named like `*_document_id(s)`, `*_chunk_id(s)` or `*_lineage_id(s)`) must add a row to `rag_purge_store_inventory()` in a later migration (CREATE OR REPLACE of the full list). If the table holds per-document data, the phase also ships `rag_purge_hook_<name>(text, uuid, uuid[])` and a step in `rag_purge_foreign_stores` / `rag_purge_foreign_leftovers`. Otherwise `purge-store-coverage.test.mts` fails.
- Phase 5.3: ship `rag_purge_hook_golden_items(p_tenant_key text, p_lineage_id uuid, p_document_ids uuid[]) RETURNS integer|bigint` (service_role only, `SET search_path = ''`), and the purge then marks items stale through it.
