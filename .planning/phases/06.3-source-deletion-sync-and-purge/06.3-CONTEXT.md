# Phase 6.3: Source Deletion Sync & Purge - Context

**Gathered:** 2026-11-25
**Status:** Ready for planning
**Mode:** `--auto` (owner's standing rule: take the recommended option; every choice is logged in `06.3-DISCUSSION-LOG.md`)

<domain>
## Phase Boundary

A document deleted or withdrawn at its source stops being retrieved, cited or served from cache within one sync; withdrawn content can be purged from every store in one audited flow; SharePoint Online and OneDrive for Business libraries can be connected through Nango with Microsoft Graph delta.

Requirements: DATA-23 (change-feed deletions, scheduled reconciliation, reconcile-age alert, mass-delete pause, per-connection deletion mode), DATA-24 (purge across every store, withdrawn marker, audit, verification), DATA-25 (SharePoint/OneDrive connector), RET-14 (source-of-truth recheck before rerank), EVAL-31 (deletion canaries in CI).

Not in this phase: the Weaviate/Qdrant adapters, outbox drain and reconcile job (Phase 7; this phase relies on their delete triggers and `rag_validate_chunks`), access-group enforcement itself (Phase 4.3), the golden-set lifecycle itself (Phase 5.3), table rows and duplicate clusters themselves (Phase 4.2), stored translations themselves (Phase 3.2), the OBS-03 monitor itself (Phase 5.3).

</domain>

<decisions>
## Implementation Decisions

### Dependency status at planning time
- **D-01:** Phases 4.2, 4.3 and 5.3 are planned on branches that have not merged into trunk; Phases 6 and 7 are executing on trunk. This phase is planned against their requirement texts (RET-12, DATA-21, DATA-22, SEC-12/13, EVAL-29, OBS-03, XLG-04, RET-05, RET-07, CACHE-01). Every plan step that touches a store owned by another phase must locate it by table or function name on trunk at execution time and re-read the newest definition, never by line number. A store that does not exist on trunk at execution time is handled by the guard in D-14, not by inventing its schema here.

### Migrations
- **D-02:** Phase 7 uses 0701–0707 inside the 0700–0719 block, so Phase 6.3 uses **0720–0739**. Migrations are idempotent, common file first with `.single-tenant.sql` / `.multi-tenant.sql` only where the mode differs, and are **not folded** into the setup files. All new functions are `SECURITY DEFINER`, `SET search_path = ''`, service_role only, with tests asserting anon and authenticated cannot execute them (Phase 3 / Phase 4 pattern). — **Reversibility:** one-way — new columns and tables on `documents`, `nango_connections` and new audit tables need a migration to undo.

### Change-feed deletions (DATA-23)
- **D-03:** One deletion entry point, `applySourceDeletions(connection, fileIds, origin)` in `src/lib/nango/` (origin: `change_feed` | `reconcile` | `admin`), replaces the per-call choice inside `deleteOrphanedDocuments`. It resolves the tenant from the connection owner (`nangoOwnerScope`), finds lineages by identity (`collectNangoLineageIds`: `source_key` / `source_file_id` of this connection, never the sync record's `document_id`), applies the connection's deletion mode (D-08), is idempotent, and deletes the sync record only after the lineage removal succeeded (today's retry semantics).
- **D-04:** Change feeds are read through a small `SourceChangeFeed` interface per provider: Nango sync records with the deleted filter (where a Nango sync with records exists for the provider) and Microsoft Graph delta (SharePoint/OneDrive, D-20). Providers whose sync is a proxy listing with no change feed (today's Google Drive, Dropbox, Notion paths) rely on the scheduled reconciliation as before; adding provider-native change APIs for them is deferred.
- **D-05:** `/api/nango/webhook` handles sync webhooks that report deletions: after signature verification it reads the deleted records since the stored cursor and calls `applySourceDeletions` inline, bounded per request (Vercel 60 s limit); the cursor is persisted only after the batch succeeded, so an unfinished batch is picked up by the next webhook or sync. Duplicate deliveries are harmless because deletion is idempotent. Unknown connection ids are acknowledged without effect (no oracle).

### Scheduled reconciliation (DATA-23)
- **D-06:** The existing full-listing orphan removal is also run on a schedule: `npm run rag:reconcile` plus an authenticated internal route (`POST /api/internal/rag/reconcile`, shared-secret auth like the other internal routes, off in production unless enabled), each call bounded and processing connections that are due; an optional Vercel cron entry is documented, not enabled by default. Cadence `RAG_SOURCE_RECONCILE_INTERVAL_DAYS=7`. Same shape as the OBS-03 job (CLI, admin route, optional scheduler).
- **D-07:** New columns: `nango_connections.last_full_reconcile_at`, `last_reconcile_status`, `deletion_mode`; `documents.source_last_seen_at`, `source_modified_at`, `source_etag` (nullable, set by every sync that sees the file). Only a listing that completed may remove documents or advance `last_full_reconcile_at` (the existing listing-complete guard stays). — **Reversibility:** one-way — columns on shared tables.
- **D-08 (deletion mode):** `nango_connections.deletion_mode` is nullable with values `soft` | `purge`. **NULL means today's behaviour, unchanged code path** (the current pipeline-dependent choice: soft-delete under unified + async, hard delete of all versions otherwise). `soft` forces `rag_soft_delete_document` (versions kept for citations and history); `purge` runs DATA-24. Changing the mode affects future deletions only; nothing is purged retroactively. *(Wording change requested for DATA-23 — see Specifics.)*
- **D-09 (mass-delete pause):** Any full-listing removal (scheduled or inside a sync) that would remove more than `RAG_SOURCE_RECONCILE_MAX_DELETE_SHARE` (default `0.3`) of a connection's documents, and at least a small fixed floor of documents (planner's choice, e.g. 5, so a 1-of-2 removal is not paused), records a reconcile run in `awaiting_confirmation` with its candidate file ids, removes nothing, and raises an alert. An admin confirms or dismisses in the admin UI; a confirmation older than 24 h is refused and needs a fresh run. Change-feed deletions (explicit per-file delete events) are not subject to the share guard.
- **D-10 (reconcile-age alert):** A connection whose `last_full_reconcile_at` is older than `RAG_SOURCE_RECONCILE_MAX_AGE_DAYS` (default 7, NULL counts from `connected_at`) raises an alert and shows a warning in the admin UI. Alerts go through a thin `raiseSourceAlert` adapter: if the OBS-03 alert store from Phase 5.3 exists on trunk at execution, it writes there; otherwise it records the alert on the connection row (`last_reconcile_status`) and logs `[Source Reconcile]`.

### Purge (DATA-24)
- **D-11:** One server-only SQL function `rag_purge_lineage(p_tenant_key, p_lineage_id, p_actor, p_reason)` removes every version of the lineage from every database store in **one transaction**: chunks and parent chunks, vectors in every embedding profile, stored translations, table rows, duplicate-cluster memberships (with the cluster recompute the owning phase defines), parse-cache entries (only when no other live document of the tenant shares the content hash), semantic-cache entries (`rag_cache_invalidate` with the version ids), citation snapshots (D-13), then the `documents` rows; it writes the audit row (D-12) and returns per-store counts. The tenant is asserted with the existing tenant-key guard. — **Reversibility:** one-way — purge destroys data by design.
- **D-12 (audit):** New table `rag_purge_audit` (tenant key, lineage id, version ids, source, source key, actor kind and id — admin user or `source_sync` with connection id —, reason code plus free text, started/finished times, per-store counts, verification result, pending object paths). It stores ids and hashes only, never titles or text of the withdrawn content. RLS on, service_role writes, tenant admins read their tenant's rows through a server route.
- **D-13 (withdrawn marker):** Citation snapshots in `rag_answer_records.citations` and any persisted message sources of the purged versions have their text replaced by a flag (`withdrawn: true`, `withdrawn_at`) with the snapshot text removed; the UI renders a localized "source withdrawn" string at display time (translations for every UI language already in `src/translations/`). The marker is a flag, not stored prose.
- **D-14 (stores owned by other phases):** Each purge step for a store owned by an unmerged phase (table rows, cluster memberships, translations, golden items) is guarded so the migration applies whatever order phases land in (existence check by relation name, dynamic SQL with quoted identifiers). The executor re-reads trunk and names the real tables; a verification test fails when a store listed in DATA-24 exists on trunk but has no purge step.
- **D-15 (objects and external backends):** Originals and parse files in the private `rag-originals` bucket are removed by the app after the transaction commits (reuse `removeDocumentObjects`); failures are recorded as pending paths on the audit row and retried by the next reconcile run. External backends need no extra call: the Phase 7 outbox delete triggers on `document_chunks`/`documents` enqueue the deletes; a test asserts a purge produces outbox delete events for every chunk id (the RET-05 delta).
- **D-16 (verification):** `rag_purge_verify(p_tenant_key, p_lineage_id)` returns the remaining row count per store (same guarded store list); a purge is reported successful only when every count is zero and pending objects are empty. The admin UI shows the result; the audit row stores it.
- **D-17 (golden items):** Purge marks golden items with evidence in the lineage `stale` through the EVAL-29 hook if Phase 5.3 has landed; otherwise the audit row is the record the EVAL-29 nightly stale check reads (the planner adds a reader contract only if 5.3 is on trunk).
- **D-18 (admin entry):** A new admin-only `POST` purge route for a document (reason required, owner-or-admin rules as the existing document routes, tenant-scoped, unknown and other-tenant ids answer the same 404). The existing `DELETE /api/documents/[id]` is unchanged.

### Source-of-truth recheck (RET-14)
- **D-19:** `RAG_SOURCE_RECHECK=false` by default. When on, `runRetrieval` (inside `@/lib/rag`, both legacy and v2 pipelines) runs one batched server-only RPC `rag_source_recheck(p_tenant_key, p_chunk_ids)` after search and fusion and before rerank, keeping only chunks whose document exists in the tenant as current, ready and not quarantined (and passes the access-group filter when Phase 4.3 is on trunk). Dropped chunks are counted on the trace as `stale_index_drop` (Pydantic trace contract → generated Zod). One indexed query; it counts against the retrieval stage of the latency budget.
- **D-20 (external backends):** On Weaviate and Qdrant the recheck is always on and is Phase 7's `rag_validate_chunks` re-validation; its drops are reported in the same `stale_index_drop` counter, with no second query. A non-zero drop asynchronously requests the RET-05 reconcile for those ids (external backends) or logs and counts for OBS-03 (pgvector); it never blocks the request.

### SharePoint / OneDrive (DATA-25)
- **D-21:** Connector through Nango (Microsoft provider integration) using the Nango proxy to call Microsoft Graph. Changes come from `/drives/{drive-id}/root/delta`; the `@odata.deltaLink` is stored per drive in a new `rag_source_delta_tokens` table (connection, drive id, delta link, updated at), updated only after the page set was applied. `resyncRequired` (HTTP 410) restarts enumeration, and a completed enumeration counts as a full listing for reconciliation.
- **D-22:** Admins pick sites, document libraries (drives) or folders; the selection is stored on the connection. Items with the `deleted` facet go to `applySourceDeletions`; added or changed `file` items go through the existing ingest path with `source = 'nango'`, `source_key` = drive item id, `source_connection_id`, content hash, `source_modified_at` and `source_etag` (eTag/cTag). Out-of-scope items are ignored.
- **D-23 (permissions):** Item permissions are read from Graph and mapped to DATA-22 access groups exactly like the other connectors (Phase 4.3 mapping); a principal that cannot be mapped makes the document visible only to its uploader and tenant admins (fail closed). The permission plan comes after Phase 4.3 lands; if 4.3 is not on trunk at execution, that plan stops at a checkpoint instead of inventing an access model.
- **D-24 (switch):** `NEXT_PUBLIC_NANGO_SHAREPOINT_ENABLED=false` plus its settings (Nango integration key for the Microsoft provider), in all five config locations and the env manifest. Off: no route, UI or sync path changes.
- **D-25 (tests):** Graph delta, permission and item responses are hand-written synthetic recordings with neutral names and ids (no real tenant data, no domain content), served by a 127.0.0.1 fake following the Phase 1 edge-fake pattern.

### Admin UI
- **D-26:** The admin surface is the Config UI (`scripts/config-ui/`), consistent with earlier RAG admin surfaces: per-connection deletion mode selector, reconcile status (last full reconcile, age warning, paused run with confirm/dismiss), document purge with a required reason and the verification result, SharePoint switch and site/library/folder picker. The in-app connector card shows only a read-only warning when reconciliation is overdue or paused. The UI phase (`/gsd-ui-phase 6.3`) decides layout and copy; copy stays domain-neutral.

### Deletion canaries (EVAL-31)
- **D-27:** A test-only fake connector implements the listing and change-feed interfaces from fixtures. On the PGlite fixture database (Phase 1 pattern) the canary ingests a synthetic document, answers from it, stores a semantic-cache entry, deletes it at the fake source, runs the next sync, then asserts no retrieval candidate, context block, citation text, cache entry, table row (when RET-12 exists) or outbox-pending vector remains — once with `soft` and once with `purge`; the purge run also asserts the withdrawn marker. Two more cases: a listing that keeps failing raises the reconcile-age alert; a listing that would remove most documents pauses. The external-backend tier joins Phase 7's container job when it exists. Runs in the PR smoke tier.
- **D-28 (baseline equivalence):** With every new switch off and every connection's `deletion_mode` NULL, behaviour matches the latest recorded baseline on trunk (Phase 6.2's when recorded, otherwise the newest earlier one); a characterization test proves the default deletion paths are byte-for-byte the current code paths.

### New env vars (five config locations + env manifest)
- **D-29:** `RAG_SOURCE_RECHECK=false`, `RAG_SOURCE_RECONCILE_INTERVAL_DAYS=7`, `RAG_SOURCE_RECONCILE_MAX_AGE_DAYS=7`, `RAG_SOURCE_RECONCILE_MAX_DELETE_SHARE=0.3`, `NEXT_PUBLIC_NANGO_SHAREPOINT_ENABLED=false` and the SharePoint integration key setting.

- Whether the change-feed cursor lives on `nango_connections` or in `rag_source_delta_tokens` for Nango record feeds.
- Plan split and wave layout, as long as SQL lands before the app code that calls it and the SharePoint permission plan comes last.

## Specific Ideas

**Wording changes requested (not applied — planning workers do not edit REQUIREMENTS.md/ROADMAP.md):**
- DATA-23: "each connection has a deletion mode, `soft` (today's behaviour …) or `purge` (DATA-24), defaulting to today's behaviour" → today's behaviour is pipeline-dependent (hard delete of all versions except under unified + async, where it soft-deletes), so the default is an unset mode that keeps that exact path; `soft` and `purge` are explicit choices. Suggested: "each connection has a deletion mode: unset (today's behaviour), `soft` (versions kept for citations and history) or `purge` (DATA-24)".
- ROADMAP Phase 6.3 SC5: "with every new switch off and connections in `soft` mode" → "… and connections in the default deletion mode".

**Human checkpoints (live verification, not automatable):**
- Register the Microsoft (SharePoint/OneDrive) integration in the Nango dashboard and connect a real SharePoint test site.
- Delete and restore a file on that site and confirm the answer stops and resumes.
- Purge a document on the live database and run `rag_purge_verify`.
