# 06.3-20 Summary: the purge's application side

An admin can now purge a document through `POST /api/rag/admin/documents/[id]/purge`. The library calls the one-transaction SQL purge of plan 06.3-15, removes the stored objects after commit from the three storage locations, invalidates the RedisVL cache when that backend is on, and stores a check on the audit row. Admins can list their tenants' purge records and run the check again. Only `purge.ts` may call the purge SQL.

## Wire fields for plan 06.3-22

`POST /api/rag/admin/documents/{id}/purge`, body `{ reason_code, reason_note }` (strict; `reason_code` one of `owner_request`, `added_in_error`, `retention_ended`, `legal_or_policy`, `restricted_content`, `other`; `reason_note` string ≤ 500 or null, required and non-blank for `other`).

- 200: `{ success: true, record_id, removed: { <store>: n }, check: { left: { <store>: n }, pending_files, queued_external, result }, checked_at }`, `Cache-Control: no-store`.
- `result`: `verified` | `pending` | `remaining`.
- 400: `{ success: false, error: 'invalid_request', details }`. 404: `{ success: false, error: 'not_found' }` (unknown and other-tenant ids answer the same). 503: `{ success: false, error: 'purge_unavailable' }`. 401/403/503 from the admin guard as on every admin route.

Store ids in `removed` and `left`, in server order: the SQL stores (`documents`, `chunks`, `vectors`, `parents`, `ingestion_jobs`, `parse_cache`, `semantic_cache`, `answer_citations`, `chat_messages`, `sync_records`, plus any foreign stores 06.3-19 adds), then `original_files`, `parse_cache_files`, `page_images`, `uploaded_image` (in `left`; in `removed` only when an image was removed), then `external:<target>` rows (left 1 only when the target is dead; a pending target counts in `queued_external`). `pending_files` counts the pending items, including a pending RedisVL invalidation.

`GET /api/rag/admin/purges?limit=1..100&offset=0..` (strict query; default 50/0) → `{ success, limit, offset, has_more, items: [{ id, started_at, actor_kind, actor_id, provider, workspace_key, reason_code, reason_note, lineage_id, version_count, result, removed, left, pending_files, checked_at }] }`. `result` here can also be `unchecked`. `provider` is the connection provider for `source_sync` records, null for admins. No file name, path or hash is sent.

`POST /api/rag/admin/purges/{id}/verify` → `{ success: true, record_id, check: { left, pending_files, queued_external, result }, checked_at }`; unknown or foreign id: the same 404; non-uuid: 400.

## Deviations

1. `ObjectStore.list` and the public-store methods needed changes in `src/lib/rag/ingest/object-store.ts` (not in the plan's file list): the store had no listing, and without one the parse-cache objects (whose names the deleted cache row held) and the check's object counts could not be found. `tests/helpers/fake-object-store.ts`, `tests/rag-db/reembed.test.mts` and `tests/rag-db/relex.test.mts` got the matching `list`.
2. The image_upload object sits outside `rag/` in `chat-images`, so `PublicImageStore` got `removeUpload` and `listUploads` next to the plan's `remove` and `list`, with their own key guard (`<user uuid>/<name>`).
3. A retry stores no new object counts (`p_object_counts` `{}`), because `rag_purge_audit_pending` does not return the stored counts and `rag_purge_audit_finish` overwrites keys it receives. The record's `removed` therefore shows what the purge pass removed, not what a later retry removed.
4. The list route uses `limit` and `offset` (the plan), not the UI-SPEC proposal's `cursor`, and answers `has_more`.
5. The purge-rpc rule exempts `rag_purge_retrieval_log` (Phase 6 retention job in `src/lib/rag/feedback-loop/purge.ts`).
6. Added fix commit pair (be95cb606, 38514b0c6) for the abort-during-commit case found in self-review.
