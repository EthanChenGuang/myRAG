# Phase 4.1 Plan 16: Deterministic ingest mode and mapped filter ids Summary

**v2 ingest runs are now reproducible and selective-filter items filter on the documents ingest mode wrote: `category:selective_filter` Recall@10 goes from 0.000 to 0.875 (n 8) in ingest mode, and three runs are identical apart from latency fields.**

## Diagnosis

Run: `npm run test-rag -- --run-config eval/config/runs/v2-default.json --fixture-mode ingest --no-gate --out eval/out/p41-16-diag/run{1,2,3}` and prechunked twice (`pre1`, `pre2`), on the trunk code.

**Finding 3 (selective_filter returns nothing in ingest mode).** All 12 items carrying `retrieval_filters.document_ids` are `category:selective_filter`. They name three ids, each the prechunked derivation `uuidFromDigest('doc:' + relpath)`:

| Items | Golden id | Corpus file | Ingest-mode id (run1 / run2) |
| --- | --- | --- | --- |
| en-selective-filter-001..004 | `4dda7ba2-…7e40` | en/warehouse-floorplan.en.md | `0aaa6b41-…7377` / `d3edcc69-…7a61` |
| it-selective-filter-001..004 | `b0f11cff-…2da72` | it/scanned-receipt.it.md | random per run |
| zh-selective-filter-001..004 | `1338762a-…f3cc` | zh/scanned-contract.zh.md | random per run |

No golden id ever matches an ingested id: ingest() gets each id from `gen_random_uuid()` in `rag_begin_document_version`, so a v2 request filtered on the golden id matches no document and the item is refused (run1: Recall@10 0.0, n 8). Only `src/lib/rag/v2/stages/query.ts` and `search.ts` read `retrievalFilters`; legacy ignores them, which is why legacy "finds some" (R@10 0.625, unfiltered).

**Finding 4 (v2 ingest non-determinism).** run1 vs run2 differ on 69 of 225 items, run1 vs run3 on 52 (ranked lists compared by document name, content and fused score). The first differing item in file order is `en-colloquial-001` (category colloquial), first differing rank 4; the first differing stage is **search**, the lexical leg of `hybrid_search_chunks`: two chunks of refund-policy.en.md with the same lexical score swap lexical ranks 4 and 5 between runs, which changes their RRF scores. `en-compound-001` shows the same at ranks 1 and 2. Source: the lexical leg orders `ORDER BY score DESC, c.id` and the dense leg `ORDER BY dist, hid` (0802), and `rrf()` breaks ties by `chunkId`. Those keys are stable, but chunk ids are `sha256(document_id:chunk_index)` (0812 `rag_write_chunks`) and the document id is random, so every tie flips at random. Metric effect seen: `category:typo` MRR 0.667 / 0.5 / 0.667 (n 3) across runs. Prechunked `pre1` vs `pre2` differ only in `p50_ms`/`p95_ms` latency fields.

Plan assumption corrected: the ingest deps `randomId` is declared but never called by ingest(); time, concurrency and insertion order played no part (inline ingest is sequential). No product-code tie-break depends on unordered input, so `src/lib/rag/fusion/rrf.ts` is unchanged.

`run_id`, `created_at`, `latency_ms`, `stage_latency_ms`, `p50_ms`, `p95_ms`

## Deviations

1. **Seam**: the plan's `randomId` ingest-deps seam does not reach any id (unused by ingest()). Deterministic ids come from a harness-only redefinition of `rag_begin_document_version` in the PGlite fixture database (`installDeterministicDocumentIds`, fails with `DeterministicIngestIdsError` if the declaration it replaces is not found exactly once). No product file changed.
2. **UUID bits**: the derived id sets the v4 version and variant bits; without them the queued (`--routing`) builds failed in `rag_enqueue_ingestion_job` (`invalid_row`, the ledger validates UUIDs). Caught by `tests/rag-db/ingest-mode-routing.test.mts` before commit.
3. **`eval/harness/pglite-supabase.mts`** (not in files_modified): the new optional `ingestDocumentIds` field on `FixtureDatabase`.
4. **`tests/rag-db/ingest-mode.test.mts` not edited**: its cases pass unchanged; the new guarantees live in the determinism test.
5. **Task 3 filter** extended by `p50_ms` and `p95_ms` (see Outcome).
