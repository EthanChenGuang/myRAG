<objective>
Make an implicit v2 default safe: one resolver decides when a defaulted v2 serves legacy instead, for a database without the Phase 4 functions and for a deployment that has not chosen its supported languages.

Purpose: CONTEXT D-07 (amended) and D-24, research F-5, F-6, F-13 and F-14. After the flip, deployments that never set `RAG_PIPELINE` run v2. Without the Phase 4 migrations every request would end in `backend_error`, which strict mode reports as "knowledge base temporarily unavailable", and every unified ingest would fail on its dual write. Without chosen languages, LANG-01 (Phase 3.2 D-02) says the deployment keeps serving legacy. A default should degrade to today's behaviour, not to an outage; an explicit choice keeps failing loudly. Both cases need the same decision, "was v2 chosen or defaulted", so one function makes it.
Output: `DEFAULT_PIPELINE` and `pipelineSource`, the readiness state, the resolver, its consumers on the retrieval and ingest paths, tests.

Depends on 04.1-03 (config.ts order). Before the flip `DEFAULT_PIPELINE` is `legacy`, so nothing changes on trunk; tests use the setter. This plan needs nothing from Phase 3.2: the language state enters through a deps seam that reports "no reader" until plan 04.1-13 connects Phase 3.2's reader. This plan reads neither language variable (Phase 3.2 D-01: only its settings module does) and words no log, banner or error code of Phase 3.2.

Code is named by symbol. Re-read the newest definition of each symbol at execution time, because other phases are editing these files on trunk (CONTEXT D-27).

Commit rule for every task: plain `git commit`; the message ends with the attribution lines (Co-Authored-By and the session link) that the executor's own session supplies; never copy them from a plan. No model identifiers in code comments or commit messages; no secrets.
</objective>
