# Phase 4.1 Plan 15: CI negative controls on the v2 eval path Summary

**Under v2-default both CI negative controls now fail the gate as designed (prechunked: degrade exit 10, overall MRR margin 0.439; max-results 1 exit 10, 11 offenders), and the plain control run passes. Non-eval profiles, legacy and unset-option eval runs are unchanged.**

## What changed

- `src/lib/rag/v2/stages/rank.ts`: `evalDegrade` / `dropTopCandidate`. With profile `eval` and `degrade: 'drop_top_candidate'`, the first hit of the final order (after fusion, dedupe and rerank) is removed together with its entry in the gate's reranked score list, before `applyRefusal`. Refusal, sub-question coverage, survivors and `preRefusalHits` all see the reduced list (legacy drops after `legacy_rank`, before its relevance filter: same position). Refusal stage detail gets ` degrade=drop_top_candidate`.
- `src/lib/rag/v2/stages/context.ts`: `evalResultCap` / `evalFinalTopK`. With profile `eval` and `options.maxResults` defined, the cap is `resolveFinalResultCount(maxResults, RAG_FINAL_RESULT_COUNT)` (the legacy function) and the context stage takes `min(final_top_k, cap)` hits. Assemble stage counts get `max_results`.
- `src/lib/rag/v2/pipeline.ts`: the coverage top-k uses `evalFinalTopK`; the pre-refusal candidates of a refused eval item are sliced to the cap.
- `src/app/api/internal/rag/run/route.ts`: passes `maxResults` only when the request sets `max_results` (see Deviations).

Voice keeps its own `matchCount` handling. No run-config key, env variable or RAG-mode key. `src/lib/rag/v2/stages/query.ts`, `eval/config`, `eval/baselines` and `.github` are untouched.

## Deviations

1. **Eval route edited** (`src/app/api/internal/rag/run/route.ts`, not in files_modified). The route always sent `maxResults: options.max_results ?? parseInt(RAG_FINAL_RESULT_COUNT || '25')`, so `options.maxResults` was never unset on the route path, and "only when set" would have capped every v2 eval run. The route now sends it only when `max_results` is set. Legacy resolves the same value through `resolveFinalResultCount` for every valid `RAG_FINAL_RESULT_COUNT`. For a malformed value such as `10x`, `parseInt` gave 10 and legacy now uses the default 25 with its warning. Route test added in `tests/rag/degrade.test.ts`.
2. **Cap also applied to the sub-question coverage top-k**, so coverage reserves within the capped final top-k. No effect when `max_results` is unset.
