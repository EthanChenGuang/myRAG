# Phase 4.1 Plan 08: Capped live rerank quality and latency Summary

**The capped live check is built and tested, and the offline references are recorded; the real Cohere and Voyage passes are one operator command away and have not run.**

## What exists now

- Four run configs (`eval/config/runs/live-*.json`): v2, lexical on, threshold refusal off, floor `legacy_rule`, `RAG_RERANKER` cohere or voyage, the vendor key `proxy-injected`, the vendor base URL, `overrides.rerank_model` naming the model (the fast models go through the override because the eval profile uses the chat tier). The Voyage configs also clear `COHERE_API_KEY`.
- `rag_eval.live_rerank_probe` (stdlib `urllib`, no new package):
  - `plan_requests`: `min(dev items, 120)` items per pass, 4 passes plus 4 probes of 30; refused above 600.
  - `select_items`: the whole split when it fits, else the first 120 by sha256 of the item id (same subset for all four models and the references).
  - `RequestBudget`: every vendor request, retries included, is taken before it is sent. A harness pass reserves its item count; its trace count (traces whose rerank stage was attempted) must not exceed it, else the run aborts.
  - `run_probe`: 30 requests of 75 fixture chunks per model; a 429, 5xx or network error is retried once while the cap allows; keeps durations, status counts and counts only; refuses to start when the requests exceed the remaining cap.
  - `run`: dev-only golden, offline references, four harness passes (with `NODE_USE_ENV_PROXY=1` so the in-process app fetch goes through the proxy), four probes, stop at the first error rate above 10%, then `result.json` and `report.md` with the G7 verdicts and the Task 3 decision.
