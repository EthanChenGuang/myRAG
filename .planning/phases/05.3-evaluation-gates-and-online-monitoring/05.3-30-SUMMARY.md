# Phase 5.3 Plan 30: Release gate and tenant nightly runners

**`rag_eval.release_gate` (run, override, post) decides and posts the `rag-release-gate` commit status, and a skip never becomes success. `rag_eval.tenant_nightly --drain` answers backfill and re-embed requests with a nightly run on the tenant's private set. Both use the shared `run_nightly_tier`.**

## Accomplishments

- `run_nightly_tier` runs the harness, scoring, the judge tier and the absolute gate as argument lists. It turns their exit codes into `nightly_absolute` and `judge_floors` parts and never raises. When the judge keys are missing it starts no later paid step.
- `release_gate run` refuses a sha that is not HEAD. It computes all four required parts and hashes the three gate files, comparing them with `--previous`. It then writes a contract-validated `ReleaseGateResult`.
- `release_gate override` checks the actor's permission through the GitHub API. Only an `admin` answer writes an override result.
- `release_gate post` maps the result through `status_for` and posts it with the caller's token. For a local prerelease it also records the change in the app.
- `tenant_nightly --drain` claims requests, runs the tenant's private set against the app and closes each request with counts only.

## Deviations

1. **Score step added.** `rag_eval.runner score` runs between the nightly harness and the judge. Without it there is no `report.json` and the absolute gate could not run. nightly.yml has the same gap today: its absolute step reads a report.json that run-nightly.mts does not write. Plan 05.3-38 should run the shared runner or add the step there.
2. **Live tier for base_url.** The tenant run against the app uses `run-smoke.mts --base-url --no-gate`, because run-nightly.mts has no `--base-url`. With `--base-url`, run-smoke does not use the fake answer generator, so the judge scores whatever the app answers.
3. **Extra `run` and `post` flags.** `run` also takes `--source`, `--golden`, `--ship-result`, `--ship-candidate`, `--ship-candidate-manifest` and `--github-api`; `post` also takes `--actor` and `--github-api`. They carry the O-2 ship-check evidence, the local-prerelease login and a test hook for the API base.
4. **Override record.** `post` also records an override (`release_override`) when `--base-url` is given, which follows D-36.
