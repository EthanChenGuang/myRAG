# Phase 5.3 Plan 33: Drift app side Summary

**Test items can be placed in a tenant's production clusters without storing any text, the drift tool can read production shares and online rates as numbers, and a posted weekly drift report is re-judged on the server, stored per tenant and week, alerts when the test set stops being representative, and feeds the coverage view and the next sample's drift_fill.**

## Performance

- **Duration:** about 75 min
- **Tasks:** 3
- **Files:** 10 created, 6 modified

## Accomplishments

- `assignTestItems` (clusters.ts) and `POST /api/rag/admin/monitor/assign-clusters`: strict body `{ tenant, items: [{ item_id, question }] }` (1 to 500 items, distinct id tokens, questions up to 2000 characters). Each question goes through `maskPII`, is embedded through `embedQueries` (the active embedding profile, inside `@/lib/rag`) and assigned with `assignNearest` against the current set's centroids and distance threshold. The answer is `{ set_id, embedder, assignments: [{ item_id, cluster_id }] }`; the log line has the tenant hash and counts.
- `driftInputs` and `GET /api/rag/admin/monitor/drift-inputs?tenant=` / `rag:monitor -- drift-inputs --tenant <key>`: `rag_monitor_cluster_shares` over the last 30 days (counts and shares per cluster, novel included) and the `rag_monitor_daily` sums per slice. The CLI needs `RAG_REPRESENTATIVE_SAMPLE=true` (notice and exit 0 without a client otherwise) and returns 2 for a missing or invalid tenant key.
- `storeDriftReport`, `latestDrift` and `GET|POST /api/rag/admin/monitor/drift`: validation with `DriftReportSchema`, recomputation (above), `rag_drift_weekly_upsert` with the week's Monday, and with `RAG_MONITOR` on `driftAlerts` candidates through `upsertAlerts` (webhook channel queued when configured). GET returns the latest week, the trend of the 8 weeks up to it (missing weeks absent, newest first), clusters sorted by production share, limits from the config and the optional scores, gaps and rates.
- `0978`: `rag_monitor_alerts.cluster_ids text[]` (id tokens, at most 64) and `rag_monitor_alert_upsert` replaced with the 0963 body plus `cluster_ids`; `toUpsertPayload` sends `cluster_ids`.

## Deviations from Plan

1. **[Rule 2 - Missing critical functionality] Migration 0978.** The plan lists no migration, but `rag_monitor_alerts` (0963) has no column for `cluster_ids` and `toUpsertPayload` dropped them, so a stored `test_set_not_representative` alert could not name the under-covered clusters (must-have, D-45). The UI-SPEC's `breakdown` has no cluster key (contract `by_channel | by_doc_type | by_mode`, strict), so a column was the smallest change. 0978 was the next free number across all origin branches (0960-0977 used) and was pushed first. It replaces `rag_monitor_alert_upsert` (still SECURITY INVOKER, `SET search_path = ''`, service_role only, already in `PHASE53_SERVICE_ROLE_FUNCTIONS`). Older payloads without `cluster_ids` store `{}`; on a database without 0978 the extra key is ignored.
2. **[Interpretation] "naming c-07 in its breakdown"** is implemented as the alert's `cluster_ids` (the MonitorAlert contract field), for the reason above.
3. **[Rule 2] 409 `embedder_mismatch`** in the assignment route when the running embedder differs from the set's.
4. **[Rule 2] Shared route helper** `src/app/api/rag/admin/monitor/_lib.ts` (not in the plan's file list) holds the Bearer guard and the tenant admission used by the three Python-tool handlers.
5. **TDD note:** the 0978 migration commit preceded its test commit by one commit (both pushed before the GREEN work); the test was verified to fail without the file.
