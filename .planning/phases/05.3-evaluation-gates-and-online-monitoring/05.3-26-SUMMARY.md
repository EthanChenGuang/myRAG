# Phase 5.3 Plan 26: Monitor rule engine, statistics and rule-kind registry Summary

## Deviations from Plan

1. **Extra file `src/lib/rag/monitor/rule-kinds.ts`.** The per-kind evaluators live there so that `rule-registry.ts` can map kinds to evaluators and `rules.ts` can import the registry without a runtime import cycle. `rules.ts` still provides `evaluateRules`, `driftAlerts`, `dedupKey` and re-exports `AlertCandidate`.
2. **Extra exports:** `parseMonitorAlertsConfig` and `resetMonitorAlertsConfigCache` (tests; `loadMonitorAlertsConfig(raw)` validates a passed payload without touching the cache); `isoWeekLastDay` and `ALL_LANGUAGES` in `rules.ts`; an optional `registry` and `day` input on `evaluateRules` / `driftAlerts`.
3. **`TOP_SCORE_BINS` and `LATENCY_BIN_EDGES_MS` in `stats.ts`.** The generated Zod has no constants, so TS mirrors the Pydantic values; a test parses `rag-sidecar/src/rag_sidecar/contracts/monitor.py` and fails when they differ.
4. **Bug found during GREEN:** the generated `DriftReportSchema` leaves `clusters` and `gaps` optional, so `driftAlerts` treats a missing array as empty (first run threw `report.gaps is not iterable`).
5. **Plan's own verify command `npm run typecheck:new`** was run in addition to the brief's full tsc gate.
