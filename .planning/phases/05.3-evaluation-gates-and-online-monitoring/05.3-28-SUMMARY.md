# Phase 5.3 Plan 28: Alert delivery, the rag:monitor CLI, the run route and the optional schedule Summary

**Alerts now reach the operator through three channels: the stored banner, a guarded and HMAC-signed webhook, and a Langfuse score on each sample trace. The outcome is recorded per channel and retried on the next run, up to five attempts. Operators run the monitor from `npm run rag:monitor`, from `POST /api/rag/admin/monitor/run`, or schedule the aggregation alone with an opt-in pg_cron file.**

## Accomplishments

- `deliverAlerts(alerts, { settings, fetch, lookupHost, now, langfuse, timeoutMs })` returns, per alert, the banner outcome, the new `delivered` map and the channels attempted.
  - Webhook: only with a valid https `RAG_MONITOR_WEBHOOK_URL`. Every delivery calls `assertPublicUrl` first, which rejects non-https URLs, URL credentials, local or internal names and any private DNS answer. The request is a POST of the contract JSON with `redirect: 'manual'` and a 10-second time box; 2xx counts as delivered.
  - Headers: `x-myrag-timestamp` (unix seconds) always, plus `x-myrag-signature: sha256=<hex>` (HMAC-SHA256 over `<timestamp>.<body>`) when the secret has 32 or more characters.
  - Langfuse: `postLangfuseScores` with a value-1 NUMERIC score `rag_monitor_alert` on each sample trace. The id is `scoreId(traceId, 'rag_monitor_alert')` and the metadata holds `alert_id`, `rule` and `severity`. It runs only when `isLangfuseUsable`.
  - Never throws. `[Monitor]` logs carry the alert id, channel and attempt count only.
- `deliverStoredAlerts(admin, deps)` reads non-resolved alerts page by page (200 per page, at most 2000 rows), oldest day first. It maps each row to the contract with `fromAlertRow`, delivers every alert that still has a channel to try, writes the `delivered` map back and returns counts per channel.
- `assertPublicUrl` is now a named export; there is still only one outbound guard. Its `lookupHost` and `signal` parameters gained defaults, and the backfill caller passes both as before.
- `rag:monitor` CLI (`tsx src/lib/rag/monitor/cli.ts`), built like the feedback-loop and re-embed CLIs (`main(argv, io, deps)`, the entry guard loads `.env.local`, exit codes 0/1/2):
  - `daily` (the default) runs `runDaily` with source `cli`, then `deliverStoredAlerts`. It prints the day, `days_aggregated`, `groups_checked`, `alerts_opened`, `alerts_updated`, `alerts_suppressed` and the per-channel delivery counts.
  - `record-change --keys A,B --reason <10..500> [--before-hash] [--after-hash]` writes one change record with source `cli` through `buildChangeRecord` and `insertChangeRecord`. It prints the record id and the key count, never the reason.
  - `test-alert --tenant <key>` delivers a synthetic alert and prints one line per channel. It stores nothing.
  - With `RAG_MONITOR` off, `daily` and `test-alert` print one notice and return 0 without creating a client.
- `POST /api/rag/admin/monitor/run` returns 404 while `RAG_MONITOR` is off, then applies `requireAdminOrDeny`. It runs `runDaily` with source `route` and the delivery, and returns `{ success, ran, day, days_aggregated, alerts_opened, alerts_updated, delivery }` with `Cache-Control: no-store`.
- `supabase/optional/monitor-schedule.sql` holds an opt-in header and one commented `cron.schedule` job (01:23 UTC) that re-aggregates each of the last 7 UTC days through `public.rag_monitor_aggregate`, plus a commented `cron.unschedule`. It contains no secret, and no setup script, harness or test applies it.

## Deviations from Plan

1. **[Contract] `not_configured` → `disabled`.** The contract's `DeliveryState` has no `not_configured`, so a channel without configuration is stored as `disabled` with the time. The contract was not changed.
2. **[Contract] Banner not stored in `delivered`.** The Python contract keys `delivered` by `webhook | langfuse`, so the banner outcome appears only in the delivery report and CLI output.
3. **[Core] Actor `cli`, not `local-cli`.** `buildChangeRecord` accepts `local-config-ui`, `cli`, `ci` or a user id, and 0960 has the same rule.
4. **[Boundary] Barrel exports added to `src/lib/rag/index.ts`.** The boundary check forbids deep imports from routes, so the route imports `monitorSettings`, `runDaily` and `deliverStoredAlerts` from `@/lib/rag`.
5. **[Test helper] `single()` on `tests/helpers/pglite-admin.ts`.** `insertChangeRecord` uses `.select('id').single()`. The change is additive, and every test that imports the helper was rerun.
6. **[Design] Missing channel = never tried.** `daily.ts` still queues only `webhook` for new alerts. The delivery step treats an absent `langfuse` entry as untried, so `daily.ts` did not need to change (05.3-27's note suggested adding it to `channelsFor`).
7. **[CLI] Off check without `@/lib/env`.** The off notice reads `RAG_MONITOR` with the same rule as `monitorSettings`. Importing the env module first would fail on unrelated missing keys (`OPENAI_API_KEY`). When the monitor is on and the environment is incomplete, the CLI prints the missing variable's name and exits 1.
8. **[CLI] Extra options.** `record-change` accepts `--before-hash` and `--after-hash`, as the 05.3-21 SUMMARY anticipated for this caller.
9. No migration was needed, so no number was claimed.

## Decisions for STATE

- Delivery retry: at most 5 attempts per channel, one per run. `disabled` and `delivered` are final.
- `record-change` is independent of `RAG_MONITOR` and records `gate_result` `skipped`.
- The run route is deployment-admin only (`requireAdminOrDeny`), and 404 while off is checked before the guard.
