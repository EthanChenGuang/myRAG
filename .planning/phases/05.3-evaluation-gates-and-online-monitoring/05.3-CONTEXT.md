# Phase 5.3: Evaluation Gates & Online Monitoring - Context

**Gathered:** 2026-11-25
**Status:** Ready for planning
**Mode:** `--auto` (single pass; every gray area took the recommended option, see `05.3-DISCUSSION-LOG.md`)

<domain>
## Phase Boundary

This phase adds four things on top of the Phase 1 noise-band gate and the Phase 5.1.1 feedback loop:

1. **Absolute gates and set composition (EVAL-22, EVAL-29).** A gated test set must keep enough no-answer questions, must not be stale, and a run fails on fixed ceilings and floors even when the noise-band rule passes.
2. **Gates outside pull requests (EVAL-23, EVAL-25).** A Config UI save of a RAG-affecting setting is checked by the smoke tier before it applies. A commit cannot be promoted to production unless the release gate passed on that exact commit; "skipped" is not "passed".
3. **Judges that are checked (EVAL-24).** LLM judges gate only for the language and metric where they agree with human labels.
4. **Monitoring after release (OBS-03, EVAL-27, EVAL-28, EVAL-30).** A daily job raises alerts on drift of refusals, scores, votes, knowledge-base failures and latency; a weekly job draws a representative sample of production questions, measures how far the test set has drifted from production, and supports cold-start question sources.

Not in this phase: the retrieval log, the review queue, expert grants, the real test set promotion, `ship_check`, the weekly report and the gate population switch (Phase 5.1.1); `off_topic_context` items and the relevance rule (Phase 5.2); per-mode refusal operating points (Phase 4.2); off-domain scope-gate items (QRY-14, Phase 6.2); the per-language alert content of LANG-10 (Phase 7, it plugs into the rule engine built here).

Every new behaviour is behind a switch that defaults to off. With every switch off, chat, embed and voice responses, Config UI saves and CI results are unchanged, except for the absolute gates and the set checks in CI (D-06), which are CI rules and have no runtime effect.

Domain neutrality applies: no fixture, prompt, rule, default or UI text in this phase contains domain content. Fixtures are synthetic, neutral, and described by structure.

</domain>

No hand-written Zod twin. The `schema-parity` job covers them.
- **D-02:** New committed config files, each validated by its contract in a pr-smoke test:
  - `eval/config/quality-gates.json` (hand-edited through pull requests);
  - `eval/config/monitor-alerts.json` (hand-edited through pull requests);
  - `eval/config/release-gate.json` (hand-edited through pull requests);
  - `eval/config/judge-calibration.json` (written only by `rag_eval.judge_calibration`, same rule as `refusal-thresholds.json`).

### B. Absolute gates and set composition (EVAL-22)
- **D-04:** Shape of `eval/config/quality-gates.json` (`schema_version: 1`):
  ```json
  {
    "composition": {
      "no_answer_share_min": 0.15,
      "no_answer_share_target": 0.20,
      "excluded_categories": ["small_talk"],
      "required_no_answer_kinds": [],
      "min_items_per_language": 20
    },
    "ceilings": {
      "false_answer_rate": { "strict": 0.05, "balanced": null, "flexible": null },
      "false_refusal_rate": { "strict": 0.25, "balanced": 0.25, "flexible": 0.25 },
      "min_n": 10
    },
    "floors": {
      "smoke": {},
      "nightly": { "faithfulness": 0.85, "answer_relevance": 0.75 }
    },
    "judge": {
      "kappa_floor": 0.6, "accuracy_floor": 0.8,
      "min_labels_per_language": 100, "seed_min_labels_per_language": 50,
      "pass_threshold": { "faithfulness": 0.8, "answer_relevance": 0.7 },
      "length_bias_max_delta": 0.1, "perturbation_max_delta": 0.1,
      "max_age_days": 35
    },
    "lifecycle": { "max_stale_share": 0.10, "re_review_days": 90 },
    "provenance": { "source": "defaults" }
  }
  ```
  `null` means report-only. The nightly floors are defaults with `provenance.source = "defaults"`; live verification ratifies or changes them through a pull request.
- **D-05:** `false_answer_rate` becomes an explicit metric: the share of unanswerable items (same population as `correct_refusal_rate`) that were answered. It is `1 - correct_refusal_rate` and is added to `SliceMetrics` with its `n`. The ceiling is compared with the point estimate, no interval and no slack: 3 of 20 is 0.15 and fails 0.05. It is checked on `overall` always and on each `language:` slice with at least `min_n` unanswerable items; smaller slices are listed as `insufficient_n`, never as passed.
- **D-06:** Composition with the EVAL-10 noise-band rule. A new module `eval/src/rag_eval/absolute_gate.py` evaluates composition, ceilings, floors and stale share from one `EvalReport` (plus the judge report on the nightly tier) with no baseline. `rag_eval.gate` gains `--gates <quality-gates.json>` and runs it after the noise-band check; `gate.json` gains an `absolute` block and `gate.md` a section. Both must pass. Exit codes: internal 70, mismatch 2, composition or stale-share failure 12, absolute ceiling or floor failure 11, noise-band regression 10; when several apply the first in that order is returned and all are printed. The absolute checks also run when the baseline mismatches, so a mismatch never hides a ceiling failure in the output. `--gates` becomes mandatory in `npm run test-rag`, pr-smoke and nightly in the same plan that adds the file.
- **D-07:** A ceiling is selected by the RAG mode of the run (`request_options`). The smoke tier stays on the pinned strict mode. When Phase 4.2's per-mode cells exist, the nightly tier adds a balanced run; until then balanced and flexible are report-only.
- **D-08:** No-answer share is computed per language over the gated population (approved, gated split, the active gate population, lifecycle status `active`): items with `answerable = false` whose category is not in `excluded_categories`. Below `min` fails with exit 12; between `min` and `target` prints a warning. The report lists the count per no-answer kind (`no_answer`, `off_topic_context`, off-domain). `required_no_answer_kinds` starts empty; the closing plan of Phase 5.2 appends `off_topic_context`, Phase 6.2 appends its off-domain category. If excluding `small_talk` drops a fixture language below 15%, this phase adds neutral synthetic no-answer items (the fixture is at about 20% per language today, counted with every unanswerable item).
- **D-09:** Judge floors apply only on the nightly tier and only for a language and metric whose calibration cell is `gating` (D-29). Everything else is printed as `report_only` with the reason. A metric of form `holistic` can never carry a floor: the contract validator rejects it.

### C. Config UI pre-save gate (EVAL-23)
- **D-10:** Switch `RAG_CONFIG_GATE=off|warn|enforce`, default `off` (save path byte-identical to today). `warn` runs the check and shows the result but never blocks. `enforce` requires a passing check or a recorded override. Second switch `RAG_CONFIG_GATE_LIVE=false`: adds a live-model layer (D-13).
- **D-11:** Which keys are "RAG-affecting": `scripts/rag/env-manifest.json` gains a boolean `ragAffecting` on every entry. Rule checked by `scripts/check-config.mjs`: every `RAG_*` entry must state it explicitly. True for: `RAG_SYSTEM_PROMPT`, `RAG_PRE_CONTEXT`, `RAG_POST_CONTEXT`, `RAG_BEHAVIOR_MODE`, `RAG_PIPELINE` and every retrieval, rerank, refusal, context, query, citation and groundedness switch, the chat provider and model entries, `OPENAI_EMBEDDING_MODEL`, the embedding and reranker profile entries, `NEXT_PUBLIC_MYRAG_DEPLOYMENT_MODE`. False for: secrets (a rotated key does not change behaviour), `LANGFUSE_*`, the monitor, log, feedback and gate switches themselves, UI theme entries.
- **D-12:** Config hash for records: `rag_settings_hash` = sha256 of the canonical JSON of the sorted `ragAffecting` name/value pairs, with each secret replaced by `set` or `unset` and `RAG_SYSTEM_PROMPT` replaced by its own sha256. One implementation with a shared test vector, usable from `scripts/config-server.js` (CommonJS) and from the app. It is a different thing from `retrieval_config_hash` (pipeline only); the record stores both when the second can be computed.
- **D-13:** Where the check runs. The Config UI is a local operator tool (`scripts/config-server.js` on port 3333, `/config` answers 404 on Vercel), so the check runs on the same machine: the config server spawns the smoke tier as a child process with the proposed values overlaid on the pinned eval env (`eval/harness/run-smoke.mts` gains `--env-overlay <file>`; fixture-only pins such as the fixture embedder and the fakes stay). Two layers:
  - deterministic layer (always): the fixture smoke tier with the gates of D-06. The harness fake generator gains an instruction-sensitive mode: on a no-answer item with adjacent context it produces an unsupported answer unless the effective system prompt carries a refusal directive. Directive detection uses generic patterns per language in `config/rag/prompt-directives.json` (no domain words). This makes "the edited prompt dropped the refusal instruction" fail on the false-answer ceiling without a model call.
  - live layer (`RAG_CONFIG_GATE_LIVE=true` and keys present): the no-answer items and a fixed sample of answerable items are answered by the proposed chat model. Result is shown next to the deterministic one; a failure here also counts as failing.
  - the tenant's private real set is also run when `eval/golden/private/domain/<tenant_hash>/` exists on the machine and the eval endpoint is enabled; settings that cannot be expressed as `RagRunOptions` are listed as `not_evaluated_on_real_set`.
- **D-14:** Async behaviour. `POST /api/config/rag-gate/check` (config server) returns 202 with a `check_id`; the UI polls `GET /api/config/rag-gate/check/:id`. One check at a time per machine; results are cached by `rag_settings_hash` for 30 minutes. Timeout 600 seconds. Timeout, crash or a missing toolchain gives result `error`, which counts as not passed.
- **D-15:** Server-side enforcement, not only UI. `POST /api/config` (config server) and the app route behind `POST /api/config/rag-prompt` compute the diff of `ragAffecting` keys. When the diff is non-empty and the mode is `enforce`, the save needs either a `check_id` whose hash equals the proposed `rag_settings_hash` and whose result is `pass`, or an override `{ reason }` (typed, 10 to 500 characters). Otherwise the answer is 409 `rag_gate_required` and nothing is written. A save that changes no RAG-affecting key is never checked.
- **D-16:** Records. Migration 0960 adds `public.rag_config_change_records`: `id`, `created_at`, `actor` (admin user id or `local-config-ui`), `source` (`config_ui | cli | release_override | local_prerelease | profile_activation`), `changed_keys text[]` (names only, never values), `before_hash`, `after_hash`, `retrieval_config_hash null`, `gate_result` (`pass | fail | error | skipped | not_required`), `gate_summary jsonb` (counts and offender metric names), `override_reason text null`, `uncalibrated_cells text[]`. Service-role only, RLS on with no policy. An override that cannot be recorded is refused. `npm run rag:monitor -- record-change --keys <names> --reason <text>` records a change made in a host's environment settings (Vercel), which the Config UI never sees. — **Reversibility:** one-way — new table and grants on real projects.
- **D-17:** Weekly report. `WeeklyReport` (Phase 5.1.1) gains optional sections fed by a new admin route `GET /api/rag/admin/config-changes?since=`: overrides (date, actor id, changed key names, hashes, result, the typed reason capped at 200 characters), all other config changes as counts, release overrides (D-33), open alerts by rule, judge calibration status, drift score. The override reason is operator-written text, not customer data, and is the only free text in the report.
- **D-18:** `uncalibrated` marking is derived, never written into `eval/config/refusal-thresholds.json` (only the calibration tool writes that file). `refusalCalibrationStatus` in `src/lib/rag/refusal/status.ts` gains a `pending` input: a cell is shown `uncalibrated` when a change record of the reranker model, embedding model or tokenizer is newer than the cell's `recorded_at` and the cell does not match the new value. The Config UI shows the warning in the pre-save dialog (for the proposed values) and as a standing warning until `rag_eval.calibrate refusal` records a matching live cell. At runtime nothing new is needed for a reranker or tokenizer change (the cell key and the version check already stop the cell being applied). For an embedding model change the cell contract gains an optional `embedding_model`; the runtime gate does not apply a cell whose value differs, and cells without the field behave as today.
- **D-19:** Backfill and re-embed completion start the tenant nightly through a request row, not a direct CI call. Migration 0961 adds `public.rag_eval_run_requests` (`tenant_key`, `reason: backfill_completed | reembed_completed | manual`, `ref_id`, `status: pending | running | done | skipped | failed`, `result_summary jsonb`). The backfill end report (`orchestrate.ts`, status `completed`) and the re-embed report (`reembed/run.ts`, status `completed`) insert one row per tenant, idempotent on `(tenant_key, reason, ref_id)`. `python -m rag_eval.tenant_nightly --drain` runs the nightly tier on that tenant's real set and closes the row; a tenant without a real set gets `skipped` with `no_real_set`, shown in the Config UI and the weekly report. The drain runs in a new `tenant-nightly` job of `nightly.yml` (skip notice without private data, the Phase 5.1.1 weekly-job pattern) and by hand. An optional immediate `repository_dispatch` is left to the planner.

### D. Daily monitor (OBS-03)
- **D-20:** Runtime is TypeScript in the app, like mining: `npm run rag:monitor` (`tsx src/lib/rag/monitor/cli.ts`, service-role client, default subcommand `daily`; other subcommands `sample`, `drift-inputs`, `record-change`), `POST /api/rag/admin/monitor/run` (admin guard), and `supabase/optional/monitor-schedule.sql` for `pg_cron`. Aggregation is one service-role SQL function `rag_monitor_aggregate(p_day date)`.
- **D-21:** `RAG_MONITOR=false` by default. Off means: the CLI prints a notice and exits 0 without a query, the routes answer 404, the Config UI does not request alerts, the optional schedule is not installed. The monitor needs `RAG_RETRIEVAL_LOG` at `ids` or `masked_query`; with the log off it prints a notice and writes nothing.
- **D-22:** Storage (migrations 0962, 0963). `rag_monitor_daily`: one row per `(tenant_key, day, language, rag_mode, channel, doc_type)` holding counts only (retrievals, refused, kb_unavailable, degraded, error, zero_result, below_threshold, helpful, not_helpful, judged, judge score sums per metric, groundedness_flagged) and two fixed-bin histograms (top score, latency). Counts and histograms make every roll-up exact and let the 30-day baseline outlive the log's retention window. `doc_type` is the type of the top kept candidate's document at aggregation time, `unknown` when it is gone. Rows are kept 400 days. `rag_monitor_alerts`: `id`, `tenant_key`, `rule`, `language`, `day`, `severity`, `status: open | acknowledged | resolved`, observed and baseline counts, the band crossed, `breakdown jsonb` (by mode, channel, doc type), `companions jsonb` (the other metrics of the same cell), `sample_trace_ids text[]` (at most 10), `config_changes jsonb` (record ids, changed key names, config-hash transitions), `suggestion`, `delivered jsonb`, `dedup_key unique`. Both service-role only. — **Reversibility:** one-way — new tables and grants.
- **D-23:** Online judge scores reach the monitor through the database. `rag_eval.online_judge` keeps posting to Langfuse and also posts numbers (`trace_id`, metric, score, judge id) to `POST /api/rag/admin/monitor/judge-scores`, stored in `rag_online_judge_scores` (0964). Groundedness flags come from `rag_answer_records`, votes from the log row. The monitor therefore works with Langfuse off and never reads text from Langfuse.
- **D-24:** Band math, configured per rule in `eval/config/monitor-alerts.json`:
  - rate rules (refusal, zero-result, below-threshold, not-helpful, groundedness-flagged, kb_error, kb_degraded, kb_unavailable): the evaluation window is 1 day, widened to 3 then 7 days until it holds `min_sample` rows (default 50); below that the cell is `insufficient_sample` and raises nothing. The baseline is the pooled rate of the 30 days before the window, with its own minimum (default 200). An alert needs all of: ratio at or above `ratio` (default 2.0), absolute change at or above `min_abs_delta` (default 0.05), and a two-proportion z at or above `min_z` (default 3);
  - top-score distribution: population stability index against the baseline histogram, warning at 0.10, alert at 0.25; the alert carries `suggestion: recalibrate_refusal` and the refusal status shows the matching cells as possibly stale (derived, D-18 mechanism);
  - latency: p95 from the histogram against the baseline p95 (ratio 1.5) and against the OBS-02 budget;
  - online judge mean: drop of at least 0.10 with the minimum sample.
- **D-25:** Alert grain is `(tenant, language, rule)`; mode, channel and document type are in `breakdown`. A tenant-wide alert (`language = all`) is raised only when no single language explains it. One open alert per `dedup_key`; a later day updates it instead of adding one. This is what makes the seeded case (refusal rate 12% to 38% on day 5, votes flat) raise exactly one alert. The LANG-10 rule (one language drops while the average holds) is a rule entry in the same file, delivered by Phase 7.
- **D-26:** Alert content and channels. An alert carries ids, counts, rates, rule names, key names and hashes; no query, answer, chunk, document name or user text. The `MonitorAlert` contract has no free-text field and a test asserts that. Channels: the Config UI banner and alert list (`GET /api/rag/admin/monitor/alerts`, acknowledge and resolve actions), an admin webhook (`RAG_MONITOR_WEBHOOK_URL`, HTTPS only, the existing outbound URL guard, body is the contract JSON, signed with HMAC-SHA256 when `RAG_MONITOR_WEBHOOK_SECRET` of 32+ characters is set), and a Langfuse score `rag_monitor_alert` on the sample traces when Langfuse is usable. Delivery is recorded per channel and retried on the next run. Email is not built (the requirement allows webhook or email).
- **D-27 (config correlation):** Each alert lists what changed in its window (the evaluation window plus two days before): rows of `rag_config_change_records`, embedding and chunking profile activations (read from their tables), and every first appearance of a new `retrieval_config_hash` for that tenant in the log. A hash change with no matching record is listed as `unrecorded_config_change`. The knowledge-base `degraded` spike of success criterion 6 uses this.

### E. Judge calibration (EVAL-24)
- **D-28:** Tool: `python -m rag_eval.judge_calibration run [--seed-only] [--tenant <key> --base-url <url>]`. It scores a labelled sample with each configured judge role (`nightly`, `online`), binarises the judge score at `judge.pass_threshold`, and writes per `(judge fingerprint, role, language, metric)`: Cohen's kappa, accuracy, n, recall and precision on the cases humans marked as containing unsupported content, the length-bias delta (mean score of long minus short paired correct answers), the two perturbation deltas (expanded version, more assertive version of the same answer), `status`, `source: seed | review_queue | mixed`, `recorded_at`. The judge fingerprint is the hash of model id, prompt and rubric text, library versions and temperature.
- **D-29:** Status rule. `gating` needs: n at or above the minimum (100 per language from the review queue, or 50 from the seed set while the queue is short), kappa and accuracy at or above their floors, both probe deltas and the length-bias delta within tolerance, and labels reviewed by a human. Otherwise `report_only` with reasons. A cell older than `max_age_days` (35, the monthly cycle plus slack) or with a fingerprint different from the running judge counts as `uncalibrated`, which also means report-only. So a judge change, a skipped monthly run or a missing key demotes the judge instead of leaving it gating. `assert_judge_family_differs` is unchanged.
- **D-30:** Consumption. `rag_eval.absolute_gate` reads `eval/config/judge-calibration.json` and enforces a nightly floor only for `gating` cells (D-09). The judge report prints the status per language and metric. Only claim-level faithfulness (Ragas and DeepEval, unsupported claims over total claims) and the 0–1 answer-relevance score can gate; any 1–5 holistic score is reported and has no floor.
- **D-31:** Label sources.
  - Seed set: `eval/fixtures/judge-calibration/seed.jsonl`, at least 50 cases per language in zh/en/it, synthetic and neutral: question, contexts, answer, expected verdict per metric, an `unsupported_content` flag, pair ids for long and short correct answers, and perturbation groups. Labels are constructed with the case and then confirmed by a human; unconfirmed cases carry `review_status: draft` and cannot produce a `gating` cell (human checkpoint H-5).
  - Review queue: this phase adds an "answer check" to the expert panel: per case the expert marks the answer as supported or not, relevant or not, and whether it contains unsupported content. Stored in `rag_judge_labels` (0965: `review_item_id`, `tenant_key`, verdicts, `labelled_by`, `labelled_at`), readable and writable under the `rag_is_domain_expert(tenant_key)` helper of Phase 5.1.1. The calibration pulls cases through `GET /api/rag/admin/judge-calibration/export?tenant=` (admin Bearer), which re-reads answer and context text under the item's tenant at request time; text stays in memory or under `eval/golden/private/`. The committed calibration file holds numbers only and no tenant id.
- **D-32:** Schedule: a monthly `judge-calibration.yml` workflow (and `workflow_dispatch`), with a skip notice when keys are absent (enforced by `scripts/ci/check-workflows.py`). The result is committed through a pull request, like the refusal cells.

### F. Release gate (EVAL-25)
- **D-33:** `rag-release-gate` is a commit status with that context name, set by a new workflow `.github/workflows/rag-release-gate.yml` (`workflow_dispatch` with a `sha` input, and `push` to `main`; `permissions: statuses: write, contents: read`). The job checks out the exact commit, runs the nightly tier with the gates of D-06 and, when `gate-population.json` is `real`, `ship_check`, then writes a `ReleaseGateResult` artifact and sets the status:
  - `passed` → state `success`;
  - `failed` → state `failure`;
  - `skipped` (judge keys missing, or private data missing while the population is `real`) → state `failure` with description `skipped: <reason>`. GitHub has no skipped state for a commit status, and a missing status must also block, so the promotion step requires `success`;
  - `ship_check` is `not_applicable` while the population is `legacy`; that value is printed and is the only non-run that does not block.
  `eval/config/release-gate.json` lists the required parts. Today's nightly judge job keeps its notice-and-exit-0 behaviour for the schedule; the release gate is what turns a skip into a block.
- **D-34:** Private-data path. When the population is `real` and CI has no private data, an admin runs `python -m rag_eval.release_gate run --sha <sha>` on a machine that has it and posts the status with their own GitHub token (`... post`); the record has `source: local_prerelease` and the report hashes.
- **D-35:** Promotion step in the repo: `scripts/ci/promote-production.mjs` and a `promote-production.yml` workflow (`workflow_dispatch`, input `sha`). It reads the `rag-release-gate` status of the commit and promotes the Vercel deployment only on `success`; anything else stops before any Vercel call. Tested with stubbed GitHub and Vercel clients. Vercel Deployment Checks, when the owner enables them, enforce the same status on the Vercel side.
- **D-36:** Emergency override: `rag-release-gate.yml` accepts `override_reason`; the job verifies through the GitHub API that the actor has the `admin` permission on the repository, then sets `success` with description `override by <actor>`. GitHub (status and workflow run) is the authoritative record; the job also posts a `release_override` row to `rag_config_change_records` through an admin route when the app URL and admin token are configured. The weekly report lists both sources.
- **D-37:** `pr-smoke` as one required check: `pr-smoke.yml` gains a final job named `pr-smoke` with `needs` on every other job and `if: always()`, failing unless each needed job is `success` (a skipped job is not success). `on.push.branches` adds the trunk branch next to `main`. `check-workflows.py` asserts both. `scripts/ci/check-branch-protection.mjs` only reads (through `gh api`) whether `pr-smoke` is required on trunk and `main` and prints the result.
- **D-38:** Repository and Vercel settings are owner actions. No plan, script or agent in this phase changes branch protection, required checks, repository secrets or Vercel project settings. They are human checkpoints H-1 to H-3.

### G. Representative sampling (EVAL-27)
- **D-39:** Switch `RAG_REPRESENTATIVE_SAMPLE=false`. Weekly, per tenant, `npm run rag:monitor -- sample` (also an admin route and the optional schedule). It needs the log in `masked_query` mode and `RAG_DOMAIN_EXPERT_REVIEW=true`; otherwise notice and no write.
- **D-40:** Clusters. The log stores no embedding, so the job embeds the masked queries of the last 30 days through `@/lib/rag` (`embedBatch`, the active embedding profile; the boundary check stays green), at most 5000 per tenant (seeded random subsample above that). Clustering is seeded spherical k-means in TypeScript with k-means++ initialisation, `k = clamp(round(sqrt(n / 2)), 4, 40)`, clusters under 5 members merged into the nearest. Centroids are refit monthly; weekly runs assign to the nearest existing centroid, and a query farther than the distance threshold from all of them goes to a `novel` bucket. A refit keeps a cluster's id when its new centroid has cosine at least 0.85 with an old one. Migration 0966: `rag_query_cluster_sets`, `rag_query_clusters` (centroid as `real[]`, member count; no vector index, so no pgvector dimension limit applies) and `rag_query_cluster_assignments` (by log row id, deleted with the log row). All per tenant; a cluster never spans tenants.
- **D-41:** Sample. Strata are cluster × language × channel. Allocation is proportional with largest remainder and at least 1 per non-empty stratum while the cap allows, default cap 30 per tenant per week, seed derived from tenant and week, query fingerprints already in the queue excluded. Items enter `rag_review_items` with reason `representative`; stratum, sampling weight and source (`representative | pilot | drift_fill | historical`) are kept in `rag_review_item_strata` (0967) so Phase 5.1.1's table shape is not changed.
- **D-42:** Quotas and weighted scores. `python -m rag_eval.representativeness` assigns each real-set item to a cluster through `POST /api/rag/admin/monitor/assign-clusters` and writes `strata.json` next to the private set. A cluster whose test share differs from its 30-day production share by more than the tolerance (default 0.10 absolute) is reported and gets priority in the next sample; it does not fail the gate, because the set is append-only. Every report on a real set gives the unweighted score (the gated one) and the production-weighted score (report-only), and lists the production share that has no test item.

### H. Test-set drift (EVAL-28)
- **D-43:** Weekly, per tenant. The app side (`rag:monitor drift-inputs`, admin route) returns production cluster shares, online judge means, vote and refusal rates per slice as counts. `python -m rag_eval.drift` (in the weekly workflow next to `weekly_report`, where private data exists) combines them with the test set and the latest offline report, writes a `DriftReport` under `eval/golden/private/reports/` and posts the numbers back to `POST /api/rag/admin/monitor/drift` (stored in `rag_drift_weekly`, 0968, for the trend of the last 8 weeks).
- **D-44:** Metrics and bands (in `eval/config/monitor-alerts.json`): Jensen–Shannon divergence (base 2) between production and test cluster shares including the `novel` bucket, warning 0.10, alert 0.20; a cluster is under-covered when its production share is at least 0.05 and its test share is under half of that; the offline–online gap is the offline judge score minus the online judge mean on the same slice, alert at 0.15 with the minimum sample. Vote and refusal rates are shown next to the offline refusal metrics without an alert rule of their own.
- **D-45:** Crossing a band raises the OBS-03 alert `test_set_not_representative` (so it needs `RAG_MONITOR` on) naming the cluster ids, and the next sample reserves up to half of its cap for the under-covered clusters (`drift_fill`).

### I. Golden-set lifecycle (EVAL-29)
- **D-46:** Every set gets a `GoldenSetManifest` file next to its JSONL (`eval/fixtures/golden.manifest.json`; private sets in their private directory): `set_id`, integer `version`, per item `item_sha256`, `status: active | stale | retired`, `stale_reason`, `stale_since`, `retire_reason`, `last_reviewed_at`, a changelog entry per version (added, changed, retired ids) and `manifest_sha256`. Tool `python -m rag_eval.golden_set bump | verify | stale-scan | relabel | retire | register`. pr-smoke runs `verify`: a golden file that differs from its manifest fails. `EvalReport` and every rendered report gain `golden_set_version`, `golden_manifest_sha256`, `stale_count` and `stale_share`. — **Reversibility:** costly — every baseline and report reader has to know the new fields.
- **D-47:** Baselines are tied to the version. A report on a newer version may be gated against an older baseline only when the difference is items that became stale or retired (the gate then compares the items both have, with the existing paired logic); any added or changed item is a mismatch (exit 2) until the baseline is re-recorded.
- **D-48:** Stale detection:
  - scan (`stale-scan`, in the nightly tier and on demand): for every gold span the document must exist as a current version and the quote must be found in it after `normalize_text`; otherwise the item is `stale` with reason `document_missing | document_superseded | quote_not_found`. Fixture sets are checked against the fixture corpus; real sets through `POST /api/rag/admin/golden/evidence-check` under the item's tenant;
  - ingestion and supersession hook: `golden_set register` writes ids and hashes of each real item's evidence into `rag_golden_evidence_index` (0969: `tenant_key`, `set_id`, `item_id`, `document_id`, `quote_sha256`, `needs_check`). An `AFTER` trigger on `documents` sets `needs_check` when a registered document gets a new current version, is superseded or is deleted. It does nothing for tenants without index rows. The next scan verifies the flagged items first.
  — **Reversibility:** one-way — a trigger on `documents` on real projects.
- **D-49:** Stale and retired items leave the gate population. A run whose stale share (stale over active plus stale, in the gated split) exceeds `lifecycle.max_stale_share` fails with exit 12 `stale_share_exceeded`. A stale item returns only through `relabel` (an expert fixes the evidence, new item hash, version bump) or `retire` (reason required). Nothing is deleted, in line with the append-only rule of Phase 5.1.1.
- **D-50:** Re-review: items whose `last_reviewed_at` is older than `re_review_days` (90) are listed in the weekly report and queued for the expert with reason `re_review`, capped per week. Overdue items stay in the gate; only staleness removes an item.

### J. Cold start (EVAL-30)
- **D-51:** Historical import: `npm run rag:questions-import -- --tenant <key> --file <csv|jsonl> [--column <name>] [--dry-run]` and an admin route used by a Config UI upload. Each question passes `maskPII`, is capped at 2000 characters, language-detected, fingerprinted and deduplicated, then inserted into `rag_review_items` with source `historical` and no log row. A row that still matches a PII pattern after masking is rejected and counted. The file is read in place and never copied into the repository; output is counts only. `review_queue promote-db` maps the source to `provenance = 'historical'`; `gate-population.json` lists `historical` as a real provenance, so an expert-labelled historical item counts as real.
- **D-52:** Pilot users: `rag_pilot_users (tenant_key, user_id)` (0970, service-role only) managed through an admin route and the Config UI. The sampler gives pilot rows a weight multiplier (default 5) with at most 40% of the weekly cap; the stored sampling weight keeps the weighted score unbiased. Access groups as a way to name pilots wait for Phase 4.3.
- **D-53:** Paraphrased variants: `python -m rag_eval.draft paraphrase --set <path> --styles colloquial,situation` uses the existing Claude drafter and the model pinned in `eval/config/draft.json`, writes items with `provenance = 'paraphrased'`, a `paraphrase_of:<id>` tag and the parent's split and document group (no leakage). They are never in a gate population and appear only in the coverage tables.
- **D-54:** `implicit_condition` fixture items: at least 4 per language in zh/en/it, with new neutral synthetic corpus passages. Structure: a passage states a rule that depends on a named condition; the question describes the asker's situation without naming the condition; the gold span is the rule; at least one item per language describes a situation that does not meet the condition. The corpus hash changes, so the plan re-records the three-run baseline; the category is report-only (it is not in `gated_slice_prefixes`).

## Specific Ideas

- The seeded tests named by the success criteria are the acceptance tests: 3 of 20 no-answer items answered fails on the ceiling while the noise band passes; a set at under 15% no-answer in one language fails; refusal rate 12% to 38% on day 5 with flat votes gives exactly one alert; a shifted top-score histogram flags recalibration; a seeded `degraded` spike lists the flipped switch and sample trace ids; a judge seeded to disagree becomes report-only and the nightly gate ignores it; a skipped nightly blocks promotion; replacing a gold document makes the item stale and removes it from the gate.
- A skip must be visible everywhere: `skipped` is its own value in every result contract and is never folded into `passed`.
- Failure direction is always the safe one: an expired or mismatched judge calibration demotes the judge, an errored config check counts as not passed, a missing release status blocks.
- Alerts and reports identify clusters by id and sample trace ids. Cluster names are never generated from query text.
- Defaults in the new JSON files are marked `provenance.source = "defaults"` until live verification ratifies them (the latency-budget precedent).
