<objective>
Enforce the setting check on the two config-server writers of `.env.local`, record each RAG-affecting change, and prove with the real child process that a prompt without the refusal directive fails its check and cannot be saved (D-10, D-13, D-15, D-16).

Purpose: `enforce` must not be bypassable from the config server, every override is recorded with the config hash and the result, and success criterion 2 ("a Config UI prompt edit that drops the refusal instruction fails before it applies") has an automated end-to-end proof (EVAL-23).
Output: the config-server guard and its use in two routes and two proxies, tests for both writers, and the end-to-end test with the real child process.

Orchestrator decision O-4: enforcement covers all five writers; this plan guards the two config-server writers and the proxies, plan 05.3-51 guards the three app writers (split from this plan in revision 2 for executor context); the Config UI dialog (plan 05.3-42) covers the three Config UI paths. Planner resolution: in `warn` mode a record failure is logged and the save proceeds (warn never blocks, D-10); in `enforce` mode an override that cannot be recorded is refused (D-16), while a save with a passed check proceeds and logs the failed record.

Writers left unguarded on purpose, in both processes: the config server's `POST /api/admin/setup` (writes `ADMIN_EMAIL` and `ADMIN_PASSWORD`), and in the app `updateEnvFile` from `src/lib/env-utils.ts` (called by `/api/config/upload-logo` for `NEXT_PUBLIC_HEADER_LOGO_URL` or `NEXT_PUBLIC_AI_RESPONSE_LOGO_URL` and by `/api/config/upload-favicon` for `NEXT_PUBLIC_FAVICON_URL`) and `src/lib/mcp/custom-servers-store.ts` (writes `MCP_CUSTOM_SERVERS`). Each writes only fixed names that are not RAG-affecting, so the guard would always answer "not required" for them (D-15); tests in this plan (config server) and in plan 05.3-51 (app) assert that none of these names is in the generated RAG-affecting list.
