# Phase 5.3 Plan 38: rag-release-gate workflow and status poster

**`.github/workflows/rag-release-gate.yml` runs the release gate on the exact commit and posts the `rag-release-gate` commit status. Only a passed run or a verified admin override turns it green. Skipped, failed and missing results post failure. `check_release_gate` in the workflow lint enforces these rules.**

## Accomplishments

- `scripts/ci/post-release-status.mjs` maps a `ReleaseGateResult` to a commit status and posts it once through the GitHub REST API with `fetch` (no new package).
- The workflow has one job, `gate`, with job-level `contents: read`, `statuses: write`, `checks: read`. The top level stays `contents: read`. It runs on `workflow_dispatch` (inputs `sha`, `override_reason`) and on push to `main`.
- `check_release_gate` and its 17 unittest cases, one failing example per rule.

## Deviations

1. **[Rule 2, correctness] Job permission `checks: read` added** next to `contents: read` and `statuses: write`. `release_gate run` reads the `pr-smoke` check runs of the commit (`pr_smoke_part`, plan 05.3-30), and with an explicit permissions block the job token has no checks access. Without it `pr_smoke` would always be skipped and the gate could never pass. It is read-only and job-level; the top level is unchanged. The lint pins the exact set of three.
2. **`--out eval/out/release` instead of `--out eval/out/release/release-gate-result.json`.** The 05.3-30 CLI takes an output directory and writes `release-gate.json` in it, so the poster reads `eval/out/release/release-gate.json` (`RESULT_FILE` in the job env).
3. **The override step also passes `--out eval/out/release`**, so both paths write the same file.
4. **The new node test is not yet run by `pr-smoke.yml`.** That file is not in this plan's files and other executors edit it. The merge train or plan 05.3-39 (which adds its own node test for `promote-production.mjs`) should add `scripts/tests/post-release-status.node-test.mjs` to the `ts-checks` node test step. The workflow lint itself already runs in `ts-checks`.

## Threats

T-05.3-381 to T-05.3-385 are mitigated as planned (env-only inputs, sha pattern check, job `gate`, job-level write only, statusFromResult, secrets through step env), and each one is enforced by a lint rule or a test. Residual risk, unchanged by this plan: the gate runs the commit's own tooling. A user with write access can run a modified workflow from their own branch, and the `GITHUB_TOKEN` then has `statuses: write`. The status creator check in 05.3-39 and branch protection (H-1 to H-3) address this.
