## Open threats (blocking)

### T-05.3-391: release gate status can be spoofed (Spoofing, high)

**What is wrong.** `scripts/ci/promote-production.mjs:31` accepts any `rag-release-gate: success` status whose creator is `github-actions[bot]`. Every workflow that runs with `GITHUB_TOKEN` posts as that bot. So a collaborator with write access can push a branch whose workflow has `statuses: write`, post success on a main commit whose gate failed, and then promote it.

The dispatch path of `.github/workflows/rag-release-gate.yml` has a second problem:
- It accepts any 40-hex sha. The check at lines 44-49 is a regex only.
- It checks that sha out with persisted credentials.
- It then runs that commit's own `post-release-status.mjs` and `rag_eval.release_gate` with `statuses: write` and the model-API secrets (lines 34-37, 91-107).
- The posted status carries no `target_url` (`post-release-status.mjs:71`).

I checked the root cause myself: `acceptedStatus` trusts the bot login with no provenance check.

**Fix (agent, in a new plan or a follow-up):**
1. Before any repository code runs, require `git merge-base --is-ancestor "$GATE_SHA" origin/main`.
2. Set `persist-credentials: false` on the checkout.
3. Post the statuses from a separate job. That job checks out the workflow's own `github.sha`, reads only the result artifact, and is the only job with `statuses: write`.
4. Post a `target_url` that points to the workflow run.
5. In `acceptedStatus`, for a bot status, resolve the run from `target_url` and require all of the following:
   - workflow path `.github/workflows/rag-release-gate.yml`
   - head branch equal to the default branch
   - event `push` or `workflow_dispatch`
   - conclusion `success`

   Refuse a bot status that has no run URL.
6. Owner (H-3, plan 49): put `promote-production` behind a GitHub Environment that has required reviewers and holds `VERCEL_TOKEN`.

Alternative: the owner records an accepted risk, on the condition that the repository has no write collaborators who are not admins.

T-05.3-302 (no override by non-admins) is closed for main shas (`eval/src/rag_eval/release_gate.py:448-461,491`). The same root cause undermines it on the dispatch path, and the fix above covers that too.

## Unregistered flags (warnings, not blocking)

- **W-1 (medium): `RAG_CONFIG_GATE` can turn itself off.** It is not in `rag-affecting.generated.json`, so a save can lower enforce to off with no check and no change record (`config-server-rag-gate.js:823-826`, `guard.ts:50-53`). **Fix:** in enforce mode, a save that lowers the mode needs an override reason and writes a change record.
- **W-2 (medium): tenant text goes to judges without an acknowledgement.** Review-queue judge calibration sends tenant question, answer and context text to OpenRouter and OpenAI (`judge-calibration.yml:56-68`). Multi-tenant mode has no acknowledgement switch, unlike the Vectara and Lakera paths. **Fix:** add `RAG_JUDGE_CALIBRATION_MULTI_TENANT_ACK`, checked by the export route.
- **W-3:** the dispatch path runs untrusted code with secrets. This is part of T-05.3-391.
- **Advisories:**
  - The webhook is sent unsigned when the secret is unset (`deliver.ts:100`). Refuse to deliver, or warn in the Config UI.
  - There is a DNS-rebinding window between the check and the fetch. Low risk: the URL is admin-configured.
  - `phase53-migrations.test.mts:55-57` has a stale `NOT_PHASE_OWNED_FUNCTIONS` entry.
  - The 6.3 coverage part of T-05.3-521 is deferred to plan 06.3-19.
