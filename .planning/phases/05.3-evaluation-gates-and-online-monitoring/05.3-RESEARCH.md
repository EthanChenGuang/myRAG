### B. Absolute gates and set composition (EVAL-22)
- **D-04:** Shape of `eval/config/quality-gates.json` (`schema_version: 1`):
  ```json
  {
    "composition": {
      "no_answer_share_min": 0.15,
      "no_answer_share_target": 0.20,
      "excluded_categories": ["small_talk"],
      "required_no_answer_kinds": [],
      "min_items_per_language": 20
    },
    "ceilings": {
      "false_answer_rate": { "strict": 0.05, "balanced": null, "flexible": null },
      "false_refusal_rate": { "strict": 0.25, "balanced": 0.25, "flexible": 0.25 },
      "min_n": 10
    },
    "floors": {
      "smoke": {},
      "nightly": { "faithfulness": 0.85, "answer_relevance": 0.75 }
    },
    "judge": {
      "kappa_floor": 0.6, "accuracy_floor": 0.8,
      "min_labels_per_language": 100, "seed_min_labels_per_language": 50,
      "pass_threshold": { "faithfulness": 0.8, "answer_relevance": 0.7 },
      "length_bias_max_delta": 0.1, "perturbation_max_delta": 0.1,
      "max_age_days": 35
    },
    "lifecycle": { "max_stale_share": 0.10, "re_review_days": 90 },
    "provenance": { "source": "defaults" }
  }
  ```
  `null` means report-only. The nightly floors are defaults with `provenance.source = "defaults"`; live verification ratifies or changes them through a pull request.
- **D-05:** `false_answer_rate` becomes an explicit metric: the share of unanswerable items (same population as `correct_refusal_rate`) that were answered. It is `1 - correct_refusal_rate` and is added to `SliceMetrics` with its `n`. The ceiling is compared with the point estimate, no interval and no slack: 3 of 20 is 0.15 and fails 0.05. It is checked on `overall` always and on each `language:` slice with at least `min_n` unanswerable items; smaller slices are listed as `insufficient_n`, never as passed.
- **D-06:** Composition with the EVAL-10 noise-band rule. A new module `eval/src/rag_eval/absolute_gate.py` evaluates composition, ceilings, floors and stale share from one `EvalReport` (plus the judge report on the nightly tier) with no baseline. `rag_eval.gate` gains `--gates <quality-gates.json>` and runs it after the noise-band check; `gate.json` gains an `absolute` block and `gate.md` a section. Both must pass. Exit codes: internal 70, mismatch 2, composition or stale-share failure 12, absolute ceiling or floor failure 11, noise-band regression 10; when several apply the first in that order is returned and all are printed. The absolute checks also run when the baseline mismatches, so a mismatch never hides a ceiling failure in the output. `--gates` becomes mandatory in `npm run test-rag`, pr-smoke and nightly in the same plan that adds the file.
- **D-07:** A ceiling is selected by the RAG mode of the run (`request_options`). The smoke tier stays on the pinned strict mode. When Phase 4.2's per-mode cells exist, the nightly tier adds a balanced run; until then balanced and flexible are report-only.
- **D-08:** No-answer share is computed per language over the gated population (approved, gated split, the active gate population, lifecycle status `active`): items with `answerable = false` whose category is not in `excluded_categories`. Below `min` fails with exit 12; between `min` and `target` prints a warning. The report lists the count per no-answer kind (`no_answer`, `off_topic_context`, off-domain). `required_no_answer_kinds` starts empty; the closing plan of Phase 5.2 appends `off_topic_context`, Phase 6.2 appends its off-domain category. If excluding `small_talk` drops a fixture language below 15%, this phase adds neutral synthetic no-answer items (the fixture is at about 20% per language today, counted with every unanswerable item).
- **D-09:** Judge floors apply only on the nightly tier and only for a language and metric whose calibration cell is `gating` (D-29). Everything else is printed as `report_only` with the reason. A metric of form `holistic` can never carry a floor: the contract validator rejects it.

### C. Config UI pre-save gate (EVAL-23)
- **D-10:** Switch `RAG_CONFIG_GATE=off|warn|enforce`, default `off` (save path byte-identical to today). `warn` runs the check and shows the result but never blocks. `enforce` requires a passing check or a recorded override. Second switch `RAG_CONFIG_GATE_LIVE=false`: adds a live-model layer (D-13).
- **D-11:** Which keys are "RAG-affecting": `scripts/rag/env-manifest.json` gains a boolean `ragAffecting` on every entry. Rule checked by `scripts/check-config.mjs`: every `RAG_*` entry must state it explicitly. True for: `RAG_SYSTEM_PROMPT`, `RAG_PRE_CONTEXT`, `RAG_POST_CONTEXT`, `RAG_BEHAVIOR_MODE`, `RAG_PIPELINE` and every retrieval, rerank, refusal, context, query, citation and groundedness switch, the chat provider and model entries, `OPENAI_EMBEDDING_MODEL`, the embedding and reranker profile entries, `NEXT_PUBLIC_MYRAG_DEPLOYMENT_MODE`. False for: secrets (a rotated key does not change behaviour), `LANGFUSE_*`, the monitor, log, feedback and gate switches themselves, UI theme entries.
- **D-12:** Config hash for records: `rag_settings_hash` = sha256 of the canonical JSON of the sorted `ragAffecting` name/value pairs, with each secret replaced by `set` or `unset` and `RAG_SYSTEM_PROMPT` replaced by its own sha256. One implementation with a shared test vector, usable from `scripts/config-server.js` (CommonJS) and from the app. It is a different thing from `retrieval_config_hash` (pipeline only); the record stores both when the second can be computed.
- **D-13:** Where the check runs. The Config UI is a local operator tool (`scripts/config-server.js` on port 3333, `/config` answers 404 on Vercel), so the check runs on the same machine: the config server spawns the smoke tier as a child process with the proposed values overlaid on the pinned eval env (`eval/harness/run-smoke.mts` gains `--env-overlay <file>`; fixture-only pins such as the fixture embedder and the fakes stay). Two layers:
  - deterministic layer (always): the fixture smoke tier with the gates of D-06. The harness fake generator gains an instruction-sensitive mode: on a no-answer item with adjacent context it produces an unsupported answer unless the effective system prompt carries a refusal directive. Directive detection uses generic patterns per language in `config/rag/prompt-directives.json` (no domain words). This makes "the edited prompt dropped the refusal instruction" fail on the false-answer ceiling without a model call.
  - live layer (`RAG_CONFIG_GATE_LIVE=true` and keys present): the no-answer items and a fixed sample of answerable items are answered by the proposed chat model. Result is shown next to the deterministic one; a failure here also counts as failing.
  - the tenant's private real set is also run when `eval/golden/private/domain/<tenant_hash>/` exists on the machine and the eval endpoint is enabled; settings that cannot be expressed as `RagRunOptions` are listed as `not_evaluated_on_real_set`.
- **D-14:** Async behaviour. `POST /api/config/rag-gate/check` (config server) returns 202 with a `check_id`; the UI polls `GET /api/config/rag-gate/check/:id`. One check at a time per machine; results are cached by `rag_settings_hash` for 30 minutes. Timeout 600 seconds. Timeout, crash or a missing toolchain gives result `error`, which counts as not passed.
- **D-15:** Server-side enforcement, not only UI. `POST /api/config` (config server) and the app route behind `POST /api/config/rag-prompt` compute the diff of `ragAffecting` keys. When the diff is non-empty and the mode is `enforce`, the save needs either a `check_id` whose hash equals the proposed `rag_settings_hash` and whose result is `pass`, or an override `{ reason }` (typed, 10 to 500 characters). Otherwise the answer is 409 `rag_gate_required` and nothing is written. A save that changes no RAG-affecting key is never checked.
- **D-16:** Records. Migration 0960 adds `public.rag_config_change_records`: `id`, `created_at`, `actor` (admin user id or `local-config-ui`), `source` (`config_ui | cli | release_override | local_prerelease | profile_activation`), `changed_keys text[]` (names only, never values), `before_hash`, `after_hash`, `retrieval_config_hash null`, `gate_result` (`pass | fail | error | skipped | not_required`), `gate_summary jsonb` (counts and offender metric names), `override_reason text null`, `uncalibrated_cells text[]`. Service-role only, RLS on with no policy. An override that cannot be recorded is refused. `npm run rag:monitor -- record-change --keys <names> --reason <text>` records a change made in a host's environment settings (Vercel), which the Config UI never sees. — **Reversibility:** one-way — new table and grants on real projects.
- **D-17:** Weekly report. `WeeklyReport` (Phase 5.1.1) gains optional sections fed by a new admin route `GET /api/rag/admin/config-changes?since=`: overrides (date, actor id, changed key names, hashes, result, the typed reason capped at 200 characters), all other config changes as counts, release overrides (D-33), open alerts by rule, judge calibration status, drift score. The override reason is operator-written text, not customer data, and is the only free text in the report.
- **D-18:** `uncalibrated` marking is derived, never written into `eval/config/refusal-thresholds.json` (only the calibration tool writes that file). `refusalCalibrationStatus` in `src/lib/rag/refusal/status.ts` gains a `pending` input: a cell is shown `uncalibrated` when a change record of the reranker model, embedding model or tokenizer is newer than the cell's `recorded_at` and the cell does not match the new value. The Config UI shows the warning in the pre-save dialog (for the proposed values) and as a standing warning until `rag_eval.calibrate refusal` records a matching live cell. At runtime nothing new is needed for a reranker or tokenizer change (the cell key and the version check already stop the cell being applied). For an embedding model change the cell contract gains an optional `embedding_model`; the runtime gate does not apply a cell whose value differs, and cells without the field behave as today.
- **D-19:** Backfill and re-embed completion start the tenant nightly through a request row, not a direct CI call. Migration 0961 adds `public.rag_eval_run_requests` (`tenant_key`, `reason: backfill_completed | reembed_completed | manual`, `ref_id`, `status: pending | running | done | skipped | failed`, `result_summary jsonb`). The backfill end report (`orchestrate.ts`, status `completed`) and the re-embed report (`reembed/run.ts`, status `completed`) insert one row per tenant, idempotent on `(tenant_key, reason, ref_id)`. `python -m rag_eval.tenant_nightly --drain` runs the nightly tier on that tenant's real set and closes the row; a tenant without a real set gets `skipped` with `no_real_set`, shown in the Config UI and the weekly report. The drain runs in a new `tenant-nightly` job of `nightly.yml` (skip notice without private data, the Phase 5.1.1 weekly-job pattern) and by hand. An optional immediate `repository_dispatch` is left to the planner.

### D. Daily monitor (OBS-03)
- **D-20:** Runtime is TypeScript in the app, like mining: `npm run rag:monitor` (`tsx src/lib/rag/monitor/cli.ts`, service-role client, default subcommand `daily`; other subcommands `sample`, `drift-inputs`, `record-change`), `POST /api/rag/admin/monitor/run` (admin guard), and `supabase/optional/monitor-schedule.sql` for `pg_cron`. Aggregation is one service-role SQL function `rag_monitor_aggregate(p_day date)`.
- **D-21:** `RAG_MONITOR=false` by default. Off means: the CLI prints a notice and exits 0 without a query, the routes answer 404, the Config UI does not request alerts, the optional schedule is not installed. The monitor needs `RAG_RETRIEVAL_LOG` at `ids` or `masked_query`; with the log off it prints a notice and writes nothing.
- **D-22:** Storage (migrations 0962, 0963). `rag_monitor_daily`: one row per `(tenant_key, day, language, rag_mode, channel, doc_type)` holding counts only (retrievals, refused, kb_unavailable, degraded, error, zero_result, below_threshold, helpful, not_helpful, judged, judge score sums per metric, groundedness_flagged) and two fixed-bin histograms (top score, latency). Counts and histograms make every roll-up exact and let the 30-day baseline outlive the log's retention window. `doc_type` is the type of the top kept candidate's document at aggregation time, `unknown` when it is gone. Rows are kept 400 days. `rag_monitor_alerts`: `id`, `tenant_key`, `rule`, `language`, `day`, `severity`, `status: open | acknowledged | resolved`, observed and baseline counts, the band crossed, `breakdown jsonb` (by mode, channel, doc type), `companions jsonb` (the other metrics of the same cell), `sample_trace_ids text[]` (at most 10), `config_changes jsonb` (record ids, changed key names, config-hash transitions), `suggestion`, `delivered jsonb`, `dedup_key unique`. Both service-role only. — **Reversibility:** one-way — new tables and grants.
- **D-23:** Online judge scores reach the monitor through the database. `rag_eval.online_judge` keeps posting to Langfuse and also posts numbers (`trace_id`, metric, score, judge id) to `POST /api/rag/admin/monitor/judge-scores`, stored in `rag_online_judge_scores` (0964). Groundedness flags come from `rag_answer_records`, votes from the log row. The monitor therefore works with Langfuse off and never reads text from Langfuse.
- **D-24:** Band math, configured per rule in `eval/config/monitor-alerts.json`:
  - rate rules (refusal, zero-result, below-threshold, not-helpful, groundedness-flagged, kb_error, kb_degraded, kb_unavailable): the evaluation window is 1 day, widened to 3 then 7 days until it holds `min_sample` rows (default 50); below that the cell is `insufficient_sample` and raises nothing. The baseline is the pooled rate of the 30 days before the window, with its own minimum (default 200). An alert needs all of: ratio at or above `ratio` (default 2.0), absolute change at or above `min_abs_delta` (default 0.05), and a two-proportion z at or above `min_z` (default 3);
  - top-score distribution: population stability index against the baseline histogram, warning at 0.10, alert at 0.25; the alert carries `suggestion: recalibrate_refusal` and the refusal status shows the matching cells as possibly stale (derived, D-18 mechanism);
  - latency: p95 from the histogram against the baseline p95 (ratio 1.5) and against the OBS-02 budget;
  - online judge mean: drop of at least 0.10 with the minimum sample.
- **D-25:** Alert grain is `(tenant, language, rule)`; mode, channel and document type are in `breakdown`. A tenant-wide alert (`language = all`) is raised only when no single language explains it. One open alert per `dedup_key`; a later day updates it instead of adding one. This is what makes the seeded case (refusal rate 12% to 38% on day 5, votes flat) raise exactly one alert. The LANG-10 rule (one language drops while the average holds) is a rule entry in the same file, delivered by Phase 7.
- **D-26:** Alert content and channels. An alert carries ids, counts, rates, rule names, key names and hashes; no query, answer, chunk, document name or user text. The `MonitorAlert` contract has no free-text field and a test asserts that. Channels: the Config UI banner and alert list (`GET /api/rag/admin/monitor/alerts`, acknowledge and resolve actions), an admin webhook (`RAG_MONITOR_WEBHOOK_URL`, HTTPS only, the existing outbound URL guard, body is the contract JSON, signed with HMAC-SHA256 when `RAG_MONITOR_WEBHOOK_SECRET` of 32+ characters is set), and a Langfuse score `rag_monitor_alert` on the sample traces when Langfuse is usable. Delivery is recorded per channel and retried on the next run. Email is not built (the requirement allows webhook or email).
- **D-27 (config correlation):** Each alert lists what changed in its window (the evaluation window plus two days before): rows of `rag_config_change_records`, embedding and chunking profile activations (read from their tables), and every first appearance of a new `retrieval_config_hash` for that tenant in the log. A hash change with no matching record is listed as `unrecorded_config_change`. The knowledge-base `degraded` spike of success criterion 6 uses this.

### E. Judge calibration (EVAL-24)
- **D-28:** Tool: `python -m rag_eval.judge_calibration run [--seed-only] [--tenant <key> --base-url <url>]`. It scores a labelled sample with each configured judge role (`nightly`, `online`), binarises the judge score at `judge.pass_threshold`, and writes per `(judge fingerprint, role, language, metric)`: Cohen's kappa, accuracy, n, recall and precision on the cases humans marked as containing unsupported content, the length-bias delta (mean score of long minus short paired correct answers), the two perturbation deltas (expanded version, more assertive version of the same answer), `status`, `source: seed | review_queue | mixed`, `recorded_at`. The judge fingerprint is the hash of model id, prompt and rubric text, library versions and temperature.
- **D-29:** Status rule. `gating` needs: n at or above the minimum (100 per language from the review queue, or 50 from the seed set while the queue is short), kappa and accuracy at or above their floors, both probe deltas and the length-bias delta within tolerance, and labels reviewed by a human. Otherwise `report_only` with reasons. A cell older than `max_age_days` (35, the monthly cycle plus slack) or with a fingerprint different from the running judge counts as `uncalibrated`, which also means report-only. So a judge change, a skipped monthly run or a missing key demotes the judge instead of leaving it gating. `assert_judge_family_differs` is unchanged.
- **D-30:** Consumption. `rag_eval.absolute_gate` reads `eval/config/judge-calibration.json` and enforces a nightly floor only for `gating` cells (D-09). The judge report prints the status per language and metric. Only claim-level faithfulness (Ragas and DeepEval, unsupported claims over total claims) and the 0–1 answer-relevance score can gate; any 1–5 holistic score is reported and has no floor.
- **D-31:** Label sources.
  - Seed set: `eval/fixtures/judge-calibration/seed.jsonl`, at least 50 cases per language in zh/en/it, synthetic and neutral: question, contexts, answer, expected verdict per metric, an `unsupported_content` flag, pair ids for long and short correct answers, and perturbation groups. Labels are constructed with the case and then confirmed by a human; unconfirmed cases carry `review_status: draft` and cannot produce a `gating` cell (human checkpoint H-5).
  - Review queue: this phase adds an "answer check" to the expert panel: per case the expert marks the answer as supported or not, relevant or not, and whether it contains unsupported content. Stored in `rag_judge_labels` (0965: `review_item_id`, `tenant_key`, verdicts, `labelled_by`, `labelled_at`), readable and writable under the `rag_is_domain_expert(tenant_key)` helper of Phase 5.1.1. The calibration pulls cases through `GET /api/rag/admin/judge-calibration/export?tenant=` (admin Bearer), which re-reads answer and context text under the item's tenant at request time; text stays in memory or under `eval/golden/private/`. The committed calibration file holds numbers only and no tenant id.
- **D-32:** Schedule: a monthly `judge-calibration.yml` workflow (and `workflow_dispatch`), with a skip notice when keys are absent (enforced by `scripts/ci/check-workflows.py`). The result is committed through a pull request, like the refusal cells.

### F. Release gate (EVAL-25)
- **D-33:** `rag-release-gate` is a commit status with that context name, set by a new workflow `.github/workflows/rag-release-gate.yml` (`workflow_dispatch` with a `sha` input, and `push` to `main`; `permissions: statuses: write, contents: read`). The job checks out the exact commit, runs the nightly tier with the gates of D-06 and, when `gate-population.json` is `real`, `ship_check`, then writes a `ReleaseGateResult` artifact and sets the status:
  - `passed` → state `success`;
  - `failed` → state `failure`;
  - `skipped` (judge keys missing, or private data missing while the population is `real`) → state `failure` with description `skipped: <reason>`. GitHub has no skipped state for a commit status, and a missing status must also block, so the promotion step requires `success`;
  - `ship_check` is `not_applicable` while the population is `legacy`; that value is printed and is the only non-run that does not block.
  `eval/config/release-gate.json` lists the required parts. Today's nightly judge job keeps its notice-and-exit-0 behaviour for the schedule; the release gate is what turns a skip into a block.
- **D-34:** Private-data path. When the population is `real` and CI has no private data, an admin runs `python -m rag_eval.release_gate run --sha <sha>` on a machine that has it and posts the status with their own GitHub token (`... post`); the record has `source: local_prerelease` and the report hashes.
- **D-35:** Promotion step in the repo: `scripts/ci/promote-production.mjs` and a `promote-production.yml` workflow (`workflow_dispatch`, input `sha`). It reads the `rag-release-gate` status of the commit and promotes the Vercel deployment only on `success`; anything else stops before any Vercel call. Tested with stubbed GitHub and Vercel clients. Vercel Deployment Checks, when the owner enables them, enforce the same status on the Vercel side.
- **D-36:** Emergency override: `rag-release-gate.yml` accepts `override_reason`; the job verifies through the GitHub API that the actor has the `admin` permission on the repository, then sets `success` with description `override by <actor>`. GitHub (status and workflow run) is the authoritative record; the job also posts a `release_override` row to `rag_config_change_records` through an admin route when the app URL and admin token are configured. The weekly report lists both sources.
- **D-37:** `pr-smoke` as one required check: `pr-smoke.yml` gains a final job named `pr-smoke` with `needs` on every other job and `if: always()`, failing unless each needed job is `success` (a skipped job is not success). `on.push.branches` adds the trunk branch next to `main`. `check-workflows.py` asserts both. `scripts/ci/check-branch-protection.mjs` only reads (through `gh api`) whether `pr-smoke` is required on trunk and `main` and prints the result.
- **D-38:** Repository and Vercel settings are owner actions. No plan, script or agent in this phase changes branch protection, required checks, repository secrets or Vercel project settings. They are human checkpoints H-1 to H-3.

### G. Representative sampling (EVAL-27)
- **D-39:** Switch `RAG_REPRESENTATIVE_SAMPLE=false`. Weekly, per tenant, `npm run rag:monitor -- sample` (also an admin route and the optional schedule). It needs the log in `masked_query` mode and `RAG_DOMAIN_EXPERT_REVIEW=true`; otherwise notice and no write.
- **D-40:** Clusters. The log stores no embedding, so the job embeds the masked queries of the last 30 days through `@/lib/rag` (`embedBatch`, the active embedding profile; the boundary check stays green), at most 5000 per tenant (seeded random subsample above that). Clustering is seeded spherical k-means in TypeScript with k-means++ initialisation, `k = clamp(round(sqrt(n / 2)), 4, 40)`, clusters under 5 members merged into the nearest. Centroids are refit monthly; weekly runs assign to the nearest existing centroid, and a query farther than the distance threshold from all of them goes to a `novel` bucket. A refit keeps a cluster's id when its new centroid has cosine at least 0.85 with an old one. Migration 0966: `rag_query_cluster_sets`, `rag_query_clusters` (centroid as `real[]`, member count; no vector index, so no pgvector dimension limit applies) and `rag_query_cluster_assignments` (by log row id, deleted with the log row). All per tenant; a cluster never spans tenants.
- **D-41:** Sample. Strata are cluster × language × channel. Allocation is proportional with largest remainder and at least 1 per non-empty stratum while the cap allows, default cap 30 per tenant per week, seed derived from tenant and week, query fingerprints already in the queue excluded. Items enter `rag_review_items` with reason `representative`; stratum, sampling weight and source (`representative | pilot | drift_fill | historical`) are kept in `rag_review_item_strata` (0967) so Phase 5.1.1's table shape is not changed.
- **D-42:** Quotas and weighted scores. `python -m rag_eval.representativeness` assigns each real-set item to a cluster through `POST /api/rag/admin/monitor/assign-clusters` and writes `strata.json` next to the private set. A cluster whose test share differs from its 30-day production share by more than the tolerance (default 0.10 absolute) is reported and gets priority in the next sample; it does not fail the gate, because the set is append-only. Every report on a real set gives the unweighted score (the gated one) and the production-weighted score (report-only), and lists the production share that has no test item.

### H. Test-set drift (EVAL-28)
- **D-43:** Weekly, per tenant. The app side (`rag:monitor drift-inputs`, admin route) returns production cluster shares, online judge means, vote and refusal rates per slice as counts. `python -m rag_eval.drift` (in the weekly workflow next to `weekly_report`, where private data exists) combines them with the test set and the latest offline report, writes a `DriftReport` under `eval/golden/private/reports/` and posts the numbers back to `POST /api/rag/admin/monitor/drift` (stored in `rag_drift_weekly`, 0968, for the trend of the last 8 weeks).
- **D-44:** Metrics and bands (in `eval/config/monitor-alerts.json`): Jensen–Shannon divergence (base 2) between production and test cluster shares including the `novel` bucket, warning 0.10, alert 0.20; a cluster is under-covered when its production share is at least 0.05 and its test share is under half of that; the offline–online gap is the offline judge score minus the online judge mean on the same slice, alert at 0.15 with the minimum sample. Vote and refusal rates are shown next to the offline refusal metrics without an alert rule of their own.
- **D-45:** Crossing a band raises the OBS-03 alert `test_set_not_representative` (so it needs `RAG_MONITOR` on) naming the cluster ids, and the next sample reserves up to half of its cap for the under-covered clusters (`drift_fill`).

### I. Golden-set lifecycle (EVAL-29)
- **D-46:** Every set gets a `GoldenSetManifest` file next to its JSONL (`eval/fixtures/golden.manifest.json`; private sets in their private directory): `set_id`, integer `version`, per item `item_sha256`, `status: active | stale | retired`, `stale_reason`, `stale_since`, `retire_reason`, `last_reviewed_at`, a changelog entry per version (added, changed, retired ids) and `manifest_sha256`. Tool `python -m rag_eval.golden_set bump | verify | stale-scan | relabel | retire | register`. pr-smoke runs `verify`: a golden file that differs from its manifest fails. `EvalReport` and every rendered report gain `golden_set_version`, `golden_manifest_sha256`, `stale_count` and `stale_share`. — **Reversibility:** costly — every baseline and report reader has to know the new fields.
- **D-47:** Baselines are tied to the version. A report on a newer version may be gated against an older baseline only when the difference is items that became stale or retired (the gate then compares the items both have, with the existing paired logic); any added or changed item is a mismatch (exit 2) until the baseline is re-recorded.
- **D-48:** Stale detection:
  - scan (`stale-scan`, in the nightly tier and on demand): for every gold span the document must exist as a current version and the quote must be found in it after `normalize_text`; otherwise the item is `stale` with reason `document_missing | document_superseded | quote_not_found`. Fixture sets are checked against the fixture corpus; real sets through `POST /api/rag/admin/golden/evidence-check` under the item's tenant;
  - ingestion and supersession hook: `golden_set register` writes ids and hashes of each real item's evidence into `rag_golden_evidence_index` (0969: `tenant_key`, `set_id`, `item_id`, `document_id`, `quote_sha256`, `needs_check`). An `AFTER` trigger on `documents` sets `needs_check` when a registered document gets a new current version, is superseded or is deleted. It does nothing for tenants without index rows. The next scan verifies the flagged items first.
  — **Reversibility:** one-way — a trigger on `documents` on real projects.
- **D-49:** Stale and retired items leave the gate population. A run whose stale share (stale over active plus stale, in the gated split) exceeds `lifecycle.max_stale_share` fails with exit 12 `stale_share_exceeded`. A stale item returns only through `relabel` (an expert fixes the evidence, new item hash, version bump) or `retire` (reason required). Nothing is deleted, in line with the append-only rule of Phase 5.1.1.
- **D-50:** Re-review: items whose `last_reviewed_at` is older than `re_review_days` (90) are listed in the weekly report and queued for the expert with reason `re_review`, capped per week. Overdue items stay in the gate; only staleness removes an item.

## Summary

Almost everything this phase needs already has a precedent in the repository: the gate module with exit codes, committed JSON config validated by a Pydantic contract, the tsx CLI plus admin route plus optional `pg_cron` file, service-role-only tables with the 0410 grant lock, the workflow lint script, the PII masker, the seeded stratified sampler and the Langfuse score poster. No new package is needed in any ecosystem: the statistics (Cohen's kappa, Jensen–Shannon divergence, population stability index, two-proportion z, largest remainder) are a few lines of standard-library code each, and D-40 fixes k-means as hand-written TypeScript. numpy and scipy are in `eval/uv.lock` only as transitive dependencies of the `judge` and `draft` extras, and scikit-learn is not in either lockfile, so nothing in this phase may import them.

The research found five facts that change how the phase must be planned. (1) On the fixture corpus the refusal metrics are far outside the ceilings of D-04 when refusal is counted at the retrieval level, in every pinned configuration: the false-answer rate is 0.33 on the legacy pipeline and 0.67 on v2, against a ceiling of 0.05, and the legacy false-refusal rate is 0.40 against 0.25. Making `--gates` mandatory without first deciding how the fixture tier counts an answered no-answer item turns `pr-smoke` red for every pull request. (2) The RAG mode is not part of `RagRunOptions` or `EvalReport`; the harness hard-codes `strict`. (3) `check-workflows.py` requires top-level `permissions` to be exactly `contents: read` and SHA-pinned actions, so the release-gate workflow must raise `statuses: write` at job level. (4) `.vercelignore` excludes `scripts/`, so the app cannot import the env manifest or a shared hash module from there. (5) Five routes write `.env.local`, not the two named in D-15, and the Config UI auto-saves the whole config on every change.

Three contracts recorded for Phase 5.1.1 differ from its plans: `ship_check` needs a baseline report, a candidate report and a target metric and passes only on a proven improvement; `GatePopulationConfig.provenances` rejects `historical`; and the expert panel has answer text only for web-chat items whose chat still exists. Each has a fallback inside the locked decisions, listed under "Dependency contracts checked".

**Primary recommendation:** Plan a measurement task first (run every CI smoke invocation with the D-04 gates in report-only mode and record the numbers), settle Open Question 1 with the owner before the plan that makes `--gates` mandatory, then follow the D-60 order with the fixture additions and every hash-pinned artifact regenerated in one serialized plan.

## Critical Findings

### F-1: The fixture tier is outside the D-04 ceilings today (blocks D-06 as written)

Committed measurements, all on the dev split, 21 unanswerable and 86 answerable items [VERIFIED: `eval/baselines/fixture-baseline.json`, `eval/reports/phase-04/comparison.md` section "(b) v2-recommended"]:

| Configuration | correct refusal | false answer (1 − correct refusal) | false refusal | D-04 strict ceilings (0.05 / 0.25) |
|---|---|---|---|---|
| legacy, prechunked (today's pinned smoke tier) | 0.6667 | 0.3333 | 0.3953 | both fail |
| legacy, ingest mode (n = 26 / 117) | 0.5000 | 0.5000 | 0.2222 | false answer fails |
| v2 all switches off | 0.3333 | 0.6667 | 0.0465 | false answer fails |
| v2 recommended (the Phase 4.1 default candidate) | 0.3333 | 0.6667 | 0.0116 | false answer fails |

Why: `refused` on the trace is decided before generation. In the eval route it is `result.refusalCandidate || result.refusal?.decision === 'refuse'` [VERIFIED: `src/app/api/internal/rag/run/route.ts:298`], and `metrics.score_items` copies `trace.refused` into `ItemResult.refused` [VERIFIED: `eval/src/rag_eval/metrics.py`, `score_items`]. The fixture's near-miss no-answer items are built to retrieve adjacent context, so retrieval does not refuse them; the model is expected to. The smoke tier runs without `include_answer` unless `--citations` or `--groundedness` is passed [VERIFIED: `eval/harness/run-smoke.mts`, `main`], so no answer exists to inspect.

D-13 already implies the answer: the fake generator's instruction-sensitive mode "produces an unsupported answer unless the effective system prompt carries a refusal directive", and that failure is meant to show "on the false-answer ceiling". That only works when the scored `refused` value includes the generator's refusal. See Open Question 1 for the options and Pattern 1 for the recommended shape. The legacy false-refusal rate (0.3953) is a second, separate violation that answer-aware scoring does not fix; it disappears only if Phase 4.1 has changed the pinned defaults before this phase runs, and Phase 4.1 D-16 keeps legacy baselines and legacy CI tiers [CITED: `.planning/phases/04.1-.../04.1-CONTEXT.md` D-16].

The seeded acceptance test of success criterion 1 (3 of 20 answered fails the ceiling while the noise band passes) does not depend on any of this: it is a pytest unit test that builds an `EvalReport` and a `Baseline` which both carry 17 of 20, so the noise band sees no change and the absolute gate returns exit 11.

### F-2: The RAG mode is not on the report

D-07 selects a ceiling "by the RAG mode of the run (`request_options`)". `RagRunOptions` has no mode field; `rag_mode` is a field of `RagRunRequest`, and the harness sends the constant `rag_mode: 'strict' as const` [VERIFIED: `rag-sidecar/src/rag_sidecar/contracts/eval_run.py`, classes `RagRunOptions` and `RagRunRequest`; `eval/harness/run-eval.mts:506`]. `RunManifest` and `EvalReport` do not record it either. The plan must add `rag_mode: Literal["strict","balanced","flexible"] = "strict"` to `RunManifest` and `EvalReport` (additive, default keeps every committed report and baseline valid), have `run-eval.mts` write it, and add it to `gate._mismatches`. Adding it to `RagRunOptions` instead would change `run_config_hash` of every existing run, so do not.

### F-3: `check-workflows.py` constrains the three new workflows

`check_common` runs on every workflow it loads and fails unless top-level `permissions` equals `{"contents": "read"}` [VERIFIED: `scripts/ci/check-workflows.py:85-87`, quoted: `if perms != {"contents": "read"}:`]. It also requires every `uses:` to be pinned to a 40-hex commit with a `# vX.Y.Z` comment, `setup-uv` pinned to the Dockerfile's uv version, and forbids `pull_request_target`. `check_nightly` forbids the `push` trigger in `nightly.yml`. `check_pr` forbids any `secrets.` reference in `pr-smoke.yml` and requires the eight jobs of `PR_JOBS` [VERIFIED: `scripts/ci/check-workflows.py:25`, quoted: `PR_JOBS = ["ts", "sibling-types", "voice-agent", "schema-parity", "python", "eval-smoke", "gate-negative-control", "docker-build"]`]. It asserts `test "$code" -eq 10` in both negative-control steps.

Consequences:
- `rag-release-gate.yml` keeps top-level `permissions: contents: read` and sets `permissions: { contents: read, statuses: write }` on the job that posts the status. GitHub allows `permissions` per job, and any permission not listed becomes `none` [CITED: docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax].
- No new third-party action. Post and read statuses with `gh api` (preinstalled on hosted runners) or `fetch` in a `.mjs` script; call Vercel through its REST API with `fetch`. This avoids new SHA pins and a new npm package.
- `main()` loads only `PR`, `NIGHTLY` and `RAY_OPTIONAL`. Each new workflow needs a path constant, a `check_*` function and a call in `main()`, plus cases in `scripts/tests/test_check_workflows.py`.
- The negative-control jobs must still exit 10 after `--gates` is mandatory. D-06 returns 12 or 11 before 10, so a negative-control run that also crosses a ceiling exits 11 and the lint-enforced assertion fails. Measure this in the same task as F-1.

### F-4: The app cannot import from `scripts/`

`.vercelignore` excludes `scripts/` and `scripts/**` [VERIFIED: `.vercelignore:2-3`], and `tests/`. `scripts/rag/env-manifest.json` is therefore absent from the Vercel build. A static import of the manifest or of a hash module under `scripts/` from `src/` would break the production build. D-12 ("one implementation ... usable from `scripts/config-server.js` (CommonJS) and from the app") and D-15 (the app route computes the diff of `ragAffecting` keys) must be built the other way round:
- the canonical `rag_settings_hash` implementation lives under `src/lib/` as a dependency-free CommonJS file (`allowJs` is on in the root `tsconfig.json`), `scripts/config-server.js` requires it (the config server only runs from a full checkout), and a typed TypeScript wrapper re-exports it for the app;
- the list of `ragAffecting` names reaches the app as a generated file under `src/lib/` produced from the manifest, with a `--check` mode in `scripts/check-config.mjs` (the `eval-env.mts --check` and `contracts.generated.ts` precedents).

### F-5: Five routes write the env file, and the Config UI auto-saves

D-15 names `POST /api/config` on the config server and the app route behind `POST /api/config/rag-prompt`. The writers that can change a RAG-affecting key are [VERIFIED: route files listed, symbol `writeEnvUpdates` in `src/lib/env-file.ts`]:

| Writer | File | RAG-affecting keys it can change |
|---|---|---|
| `POST /api/config` (config server, port 3333) | `scripts/config-server.js` | every key (rewrites `.env.local` from the posted config) |
| `POST /api/config/create` with `force` (config server) | `scripts/config-server.js` | every key (template overwrite) |
| `POST /api/config/rag-prompt` (app, proxied by the config server) | `src/app/api/config/rag-prompt/route.ts` | `RAG_PRE_CONTEXT`, `RAG_POST_CONTEXT` (the route never writes `RAG_SYSTEM_PROMPT`) |
| `POST /api/config/models` (app, proxied by the config server) | `src/app/api/config/models/route.ts` | the chat model lists |
| `POST /api/config` (app, in-app admin settings) | `src/app/api/config/route.ts` | the names in `CONFIG_WRITABLE_ENV_NAMES`, which include `RAG_BEHAVIOR_MODE`, `OPENAI_EMBEDDING_MODEL`, `NEXT_PUBLIC_AI_PROVIDER`, both model lists and about 30 `RAG_*` thresholds |

All three app writers go through `writeEnvUpdates`, which is the one place to enforce. On the config server the two writers need the same guard function. Leaving any of the five ungated makes `enforce` bypassable from the product's own UI.

The Config UI calls `saveConfig()` from about a dozen change handlers ("Trigger auto-save") and posts the whole config object each time [VERIFIED: `scripts/config-ui/index.html`, `configManager.saveConfig`]. The diff must be computed on the server against the current file (D-15 says so), and in `enforce` mode the single `saveConfig()` function needs one 409 `rag_gate_required` handler that opens the pre-save dialog; otherwise every toggle shows a failed-save toast.

The prompt editor edits pre-context and post-context, and the eval pins exclude all three prompt variables [VERIFIED: `eval/harness/eval-env.mts:10`, quoted: `const EXCLUDED_NAMES = new Set(['RAG_SYSTEM_PROMPT', 'RAG_PRE_CONTEXT', 'RAG_POST_CONTEXT', 'RAG_EMBED_TENANT']);`]. Success criterion 2 ("an edited `RAG_SYSTEM_PROMPT` that drops the refusal instruction") is exercised in practice through `RAG_PRE_CONTEXT` and `RAG_POST_CONTEXT`; the directive detector must run on the assembled template returned by `resolveEvalPromptTemplate` in `src/lib/rag-eval/answer.ts`, not on one variable.

### Pattern 1: Absolute gate as a pure function with a result contract

**What:** `absolute_gate.evaluate(report, gates, *, judge_report=None, calibration=None, manifest=None) -> AbsoluteGateResult`. No I/O, no baseline. `gate._main` calls it after `evaluate_gate` and also when `_mismatches` is non-empty; a separate `python -m rag_eval.absolute_gate` entry serves the nightly tier, which has no noise-band baseline today (the nightly `judge` job runs the harness and `rag_eval.judge.run` only [VERIFIED: `.github/workflows/nightly.yml`]).

**When to use:** every tier. The result lists each check as `passed`, `failed`, `insufficient_n`, `report_only` or `skipped`, never folding one into another (the "skip must be visible" rule in CONTEXT).

**Exit codes:** the existing constants are `EXIT_PASS = 0`, `EXIT_MISMATCH = 2`, `EXIT_REGRESSION = 10`, `EXIT_INTERNAL = 70` [VERIFIED: `eval/src/rag_eval/gate.py:13-16`]. D-06 adds 12 (composition or stale share) and 11 (ceiling or floor) with the order 70, 2, 12, 11, 10. `run-smoke.mts` returns the gate's code unchanged, so `npm run test-rag` exits with it.

**Answer-aware refusal (recommended resolution of F-1, needs the owner's confirmation):**

refused = trace.refused or is_refusal_answer(trace.answer, item.language)   # answer is None in retrieval-only runs

`npm run rag:monitor` is `tsx src/lib/rag/monitor/cli.ts` with the service-role client (the `rag:reembed` shape); the admin routes use `requireAdminOrDeny` or `checkAdmin` from `src/lib/admin-route-auth.ts`, `runtime = 'nodejs'`, `Cache-Control: no-store`, structured JSON errors, and Zod from `zod/v3`. The Config UI reaches every `/api/rag/*` route through the config server's generic proxy (`app.all('/api/rag/*path', ...)`), so new admin routes need no config-server change. `supabase/optional/monitor-schedule.sql` holds commented, opt-in `cron.schedule` statements that call service-role SQL functions only (the 5.1.1 plan 08 wording: "is not applied by any setup script or migration test, and contains no secret").

### Anti-Patterns to Avoid
- **A job named `rag-release-gate`.** A workflow job produces a check run with the job's name. A check run and a commit status with the same context are both "status checks" for branch protection and for Vercel; the job would finish `success` after posting a `failure` status. Name the job differently (for example `gate`). Vercel's docs warn that equal names across workflows collide [CITED: vercel.com/docs/deployment-checks, "Limitations"].
- **Interpolating `inputs.sha` or `inputs.override_reason` into `run:`.** Pass them through `env:` and validate `sha` against `^[0-9a-f]{40}$` in the script. The lint already forbids secrets in `run:`; add the same rule for inputs.
- **`github.actor` for the override check.** On a re-run the user who started it is `github.triggering_actor`. Check that login's permission and record both [ASSUMED].
- **Computing drift or kappa with numpy.** It is not a declared dependency of `eval`.
- **Editing `refusal-thresholds.json`, baselines or calibration files by hand** to make a gate pass (AGENTS.md section 6; Phase 4.1 D-13).
- **Reading text from Langfuse in the monitor** (D-23) or putting any text field into `MonitorAlert` (D-26).

## Statistics Used by This Phase

All verified with standard-library simulations in this session (seeded; scripts not kept in the repo).

**Cohen's kappa** (binary, judge verdict against human verdict): `p_o` = share of agreeing cases; `p_e = p_j * p_h + (1 - p_j)(1 - p_h)`; `kappa = (p_o - p_e) / (1 - p_e)`. When `p_e = 1` (both raters gave one class to every case) kappa is undefined: report `kappa: null`, status `report_only`, reason `kappa_undefined`. Measured sampling noise with 60% positive cases:

| True agreement (kappa) | n | SD of the estimate | Share of runs measured below 0.6 |
|---|---|---|---|
| 0.875 (0.74) | 50 | 0.099 | 9.1% |
| 0.875 (0.74) | 100 | 0.068 | 2.3% |
| 0.85 (0.69) | 50 | 0.105 | 20% |
| 0.85 (0.69) | 100 | 0.073 | 11% |
| 0.90 (0.79) | 50 | 0.088 | 2.3% |

So with the 50-case seed set a good judge is demoted about one run in ten by noise alone. That is the safe direction (D-29), but the report must print `n` and an interval next to kappa so the owner can tell noise from a real drop, and the kappa sample must be balanced (roughly 40% to 60% positive per metric) because kappa falls when one class dominates. Variants of one answer (the long version, the expanded and the assertive probe) are not independent cases: count each base case once in the kappa sample and keep the variants for the bias and probe deltas only.

**Jensen–Shannon divergence, base 2:** `JSD(P, Q) = H(M) - (H(P) + H(Q)) / 2` with `M = (P + Q) / 2`, `H` in bits, `0 * log 0 = 0`; range 0 to 1; no smoothing needed. It is the divergence, not its square root. Two samples from the same distribution still give a positive value. Measured null level (K clusters including `novel`, n test items, m production queries):

| K | n | m | mean JSD with no drift | 95th percentile | D-44 bands |
|---|---|---|---|---|---|
| 21 | 100 | 3000 | 0.042 | 0.067 | below warning 0.10 |
| 21 | 50 | 3000 | 0.092 | 0.139 | above warning in many runs |
| 41 | 100 | 5000 | 0.093 | 0.130 | at the warning band |
| 41 | 70 | 5000 | 0.135 | 0.183 | above warning, near alert 0.20 |
| 41 | 200 | 5000 | 0.042 | 0.060 | below warning |

With `k = clamp(round(sqrt(n / 2)), 4, 40)` a tenant with 3200 or more queries gets 40 clusters, and a 100-item real set (the 5.1.1 `min_items`) has about 70 dev items. Its drift score sits above the warning band with no drift at all. Keep the D-44 bands, and add to the rule a minimum number of test items and a seeded permutation null: raise the alert only when the score is above the band and above the 95th percentile of the score obtained by drawing n items from the production shares. Print the null level in the `DriftReport`. This is the same idea as `min_z` in D-24 and lives in `monitor-alerts.json`.

**Population stability index:** `PSI = sum_i (a_i - e_i) * ln(a_i / e_i)` over bins, shares smoothed by 0.5 per bin so an empty bin is finite. Measured null level:

| Bins | window rows | baseline rows | mean PSI with no shift | 95th percentile | D-24 bands (0.10 / 0.25) |
|---|---|---|---|---|---|
| 20 | 50 | 1500 | 0.33 | 0.50 | false alert almost every day |
| 10 | 50 | 1500 | 0.16 | 0.29 | false warnings and alerts |
| 10 | 200 | 3000 | 0.046 | 0.091 | just below warning |
| 10 | 300 | 3000 | 0.032 | 0.059 | clear |
| 5 | 100 | 1500 | 0.037 | 0.092 | just below warning |

A real shift of 0.10 in score gives about 0.45 in every row, so 10 bins lose nothing. Store 20 fine bins in `rag_monitor_daily` (exact roll-up) and compute PSI on 10 merged bins with a rule-level `min_sample` of 300 and a baseline minimum of 1000; the default 50 of the rate rules must not apply to this rule.

**Two-proportion z:** pooled `p = (x1 + x2) / (n1 + n2)`, `z = (p1 - p2) / sqrt(p (1 - p)(1/n1 + 1/n2))`. For the seeded case (38% of 50 rows on day 5 against 12% of 200 baseline rows) z = 4.36, ratio 3.17, delta 0.26: all three D-24 conditions hold. The seeded log therefore needs at least 50 rows per day in the cell so days 1 to 4 reach the baseline minimum of 200.

**Largest remainder:** quota_i = floor(cap * share_i), hand the remaining seats to the largest fractional parts, ties broken by stratum key; apply the "at least 1 per non-empty stratum" rule first and drop it, lowest share first, when the strata outnumber the cap.

**k-means sizes:** n = 30 gives k = 4, 200 gives 10, 800 gives 20, 3200 and above give 40. Spherical k-means means unit-normalised vectors, assignment by largest dot product, centroid = normalised mean. At 5000 vectors of 1536 dimensions, one iteration is 5000 × 40 × 1536 multiply-adds (about 3 × 10^8), well under a second in plain TypeScript with `Float32Array`; memory is about 31 MB for the vectors. Cap iterations (for example 50) and stop when no assignment changes.

## Common Pitfalls

### Pitfall 1: Making `--gates` mandatory on a fixture that is outside the ceilings
**What goes wrong:** `pr-smoke` fails on every pull request with exit 11 from the first run.
**Why it happens:** F-1. Retrieval-level false answer is 0.33 to 0.67 and legacy false refusal is 0.40.
**How to avoid:** A first task runs each CI smoke invocation (prechunked, ingest, both negative controls, and any legacy tier present on trunk) with the gates evaluated but not enforced, and writes the numbers into the plan summary. The plan that turns enforcement on depends on that task and on the owner's answer to Open Question 1.
**Warning signs:** `gate.json` `absolute.failed` non-empty on an unchanged trunk.

### Pitfall 2: Negative controls stop exiting 10
**What goes wrong:** `gate-negative-control` asserts `test "$code" -eq 10`, and `check-workflows.py` asserts that assertion. D-06 returns 12 and 11 before 10.
**How to avoid:** Measure the two negative-control runs against the ceilings. If a control crosses a ceiling, keep the workflow assertion on the noise-band result by reading `gate.json` (`.noise_band.passed == false`) and assert the exit code is one of the failing codes, and change the lint rule in the same plan; or keep the controls inside the ceilings. Add a third control that fails only the absolute gate (exit 11) so both rules have a negative control.

### Pitfall 3: Contract additions that are not optional
**What goes wrong:** every committed baseline, report sample and `tests/fixtures/contracts/samples.json` entry fails validation; the `schema-parity` job fails.
**Why it happens:** all contracts are `extra="forbid"`, and required fields have no default.
**How to avoid:** every new field on `SliceMetrics`, `EvalReport`, `RunManifest`, `RefusalCell` (`embedding_model`, D-18) and `GateResult` (`absolute`) is optional with a default; run `npm run gen:schemas` and commit the three generated outputs in the same commit. The 5.1.1 plan 01 test "loads every committed baseline and report JSON under eval/ and validates it unchanged" is the guard to keep green.

### Pitfall 4: A fixture change without its regenerated artifacts
**What goes wrong:** `gate` exits 2 (mismatch), `test_fixture_coverage.py` fails on hard-coded counts, `test_fixture_calibration_outputs.py` fails on the committed outcome.
**How to avoid:** one plan owns the golden file, the corpus, the split manifest, the two baselines (plus the legacy copies if Phase 4.1 created them), the fixture floor, the fixture refusal cells and the reports, in that order, each through its tool. No other plan of this phase edits `golden.jsonl`. Run it alone in the working tree (it builds PGlite databases).

### Pitfall 5: New Literal values and the gate population
**What goes wrong:** (a) an `implicit_condition` item written with `answerable: false` is rejected: the validator enforces `category in UNANSWERABLE_CATEGORIES` exactly when `answerable` is false [VERIFIED: `contracts/golden.py`, `_check_rules`]; (b) `paraphrased` items stored in a gated file enter the population, because in `legacy` mode `metrics.aggregate` uses every approved item of the gated split when no production item exists.
**How to avoid:** all `implicit_condition` items are answerable with a gold span, including the "condition not met" one. Exclude provenance `paraphrased` (and lifecycle status other than `active`) in `aggregate`'s population selection, with a test, or write paraphrases to their own file that no gate reads. D-03 notes that older checkouts reject files with the new values; land the contract change before any file uses them.

### Pitfall 6: Ungated writers and the auto-save
**What goes wrong:** `enforce` blocks the Config UI save button but the in-app settings page, the model list editor or "create from template" still change RAG-affecting keys; or every toggle in the Config UI shows "Failed to save".
**How to avoid:** F-5. One guard function per process, called by all five writers; one 409 handler in `saveConfig()`. A test per writer that an ungated RAG-affecting change returns 409 `rag_gate_required` in `enforce` and writes nothing, and that a save with no RAG-affecting change is never checked.

### Pitfall 7: Cross-process and cross-deployment assumptions
**What goes wrong:** the Vercel build fails on an import from `scripts/`; or the app route cannot see a check that lives in the config server's memory and rejects every prompt save.
**How to avoid:** F-4 and the file-based check result in Integration Map C. On Vercel the env file is not writable, so the app writers already fail there; the guard must fail closed (409) rather than throw when the generated list or the check file is missing.

### Pitfall 8: A pass that tested nothing, a URL that cannot be cleared, a check that times out
**What goes wrong:** (a) changing the chat model or the embedding model returns "pass" from the fixture layer, which uses the fake generator and the fixture embedder; (b) `RAG_MONITOR_WEBHOOK_URL` matches the secret-name pattern (it contains `WEBHOOK`), so the Config UI masks it and treats an empty value as "unchanged": the operator cannot remove the webhook through the UI [VERIFIED: `scripts/config-server-security.js`, `SECRET_NAME`; `scripts/config-server.js`, `POST /api/config` secret handling]; (c) the smoke tier's duration on an operator laptop is unknown and the D-14 limit is 600 seconds.
**How to avoid:** (a) return `not_evaluated` keys with reasons and show them in the dialog; (b) give the monitor card an explicit "remove webhook" action, or add the name to a benign list in both secret checks, and test it; (c) measure the smoke tier's wall time in the first task and record it. Spawn the child with an argument array and no shell, a server-generated overlay path, and an environment built from an allow-list, so `.env.local` secrets do not reach the harness.

### Pitfall 9: Workflow lint and name collisions
**What goes wrong:** `check-workflows.py` fails on top-level `statuses: write`, an unpinned action, or a missing lint function; a job named like the status context hides a failing gate.
**How to avoid:** F-3 and the anti-pattern list. Lint rules to add: `pr-smoke` has a job `pr-smoke` with `needs` equal to every other job and `if: always()`; `on.push.branches` contains `main` and `claude/ecstatic-hamilton-86gtwv`; `rag-release-gate.yml` has no `pull_request` trigger, `push` limited to `main`, job-level `statuses: write` only on the posting job, inputs passed through `env`, a `pending` post first, and no job named `rag-release-gate`; `promote-production.yml` is `workflow_dispatch` only; `judge-calibration.yml` has a skip notice. `PR_JOBS` gains the aggregate job, and `check_eval_smoke` gains the `--gates` expectation.

### Pitfall 10: The status can be forged, and the gate judges itself
**What goes wrong:** a user with write access posts `success`; or a commit weakens `quality-gates.json` and the release gate, which checks out that commit, passes on the weakened file.
**How to avoid:** the promotion script verifies the creator of the status (Actions bot or repository admin). The status-posting step lives in the workflow file and reads only the `ReleaseGateResult` JSON. The `ReleaseGateResult` records the sha256 of `quality-gates.json`, `release-gate.json` and `noise.json`, and prints a notice when any differs from the previous released commit. Requiring review on those paths (CODEOWNERS or a ruleset) is an owner setting to add to H-1.

### Pitfall 11: Two Vercel setups that exclude each other, and a paid run per merge
**How to avoid:** see the options table and Open Question 2. Build and test option B fully (it is in the repository); document option A for the owner.

### Pitfall 12: Kappa on a small, skewed or duplicated sample
**How to avoid:** balanced seed set, one row per independent base case in the agreement sample, `kappa: null` handling, `n` and an interval in the report (see "Statistics"). Draft seed cases (`review_status: draft`) are scored and reported but can never produce `gating`.

### Pitfall 13: Calibration cells that do not line up with the judge report
**What goes wrong:** the floor is applied to the wrong number, or never, because the cell key has no library while the report key is `<library>.<metric>`; or a judge change is not noticed.
**How to avoid:** cell carries `library`; the fingerprint hashes the judge model id, temperature, the library name and version (`importlib.metadata.version`), and the metric's prompt or rubric text where the library exposes it. Where it does not, the library version stands in for the prompt, and the report says so. A cell older than `max_age_days` or with another fingerprint is `uncalibrated`. GitHub disables scheduled workflows in repositories without recent activity [ASSUMED]; the effect is a visible demotion to report-only, which is the intended safe direction.

### Pitfall 14: Aggregating once, too early, or too late
**What goes wrong:** votes and online judge scores arrive after the day was aggregated (the online judge runs the next night, users vote later), so `helpful`, `not_helpful` and `judged` stay too low; or the log purge (30 days) runs before a missed day was aggregated and the day is lost.
**How to avoid:** `rag_monitor_aggregate(p_day)` is an idempotent upsert; each run re-aggregates a trailing window (for example the last 7 days) and every older day that has log rows but no aggregate. Use UTC days everywhere and say so in the alert. Run the aggregation before the purge in any shared schedule.

### Pitfall 15: One histogram for two kinds of score
**What goes wrong:** `top_score` is a rerank score when a reranker ran and a similarity otherwise; `local_bm25` scores are relative and unbounded. Mixing them makes PSI meaningless, and a reranker switch looks like drift.
**How to avoid:** derive the score kind per row (the top candidate has `rerank_score` or not) and keep one histogram per kind inside the jsonb; bins over 0 to 1 plus underflow and overflow bins; compute PSI per kind and only for kinds with a calibrated meaning. A change of kind is reported through the config correlation, not as PSI. Use the PSI sample sizes from "Statistics".

### Pitfall 16: The seeded refusal case raises more than one alert
**What goes wrong:** success criterion 3 expects exactly one alert; a refusal jump usually also moves the below-threshold rate, the top-score histogram or the tenant-wide cell.
**How to avoid:** build the seeded log so only the refusal rate moves (refusal reason not `below_threshold`, same score distribution, votes flat, one language). Test the roll-up rule of D-25 separately (two languages moving together give one `language = all` alert). Test that day 6 updates the open alert instead of adding one.

### Pitfall 17: Clusters and weights that silently change meaning
**What goes wrong:** assignments made with one embedding model are compared with centroids of another; a tenant with 30 queries gets 4 clusters of noise; pilot rows are oversampled and the weighted score is biased; queries already in the queue are skipped and the sample leans away from failures.
**How to avoid:** record the embedder on the cluster set and refit on change; skip sampling below a minimum number of queries (notice, no write); store each drawn item's inclusion probability and use its inverse as the weight; report how many candidates were excluded as already queued. Cluster ids are opaque; no label is derived from query text (CONTEXT specifics).

### Pitfall 18: Drift alerts from sampling noise
**How to avoid:** minimum test items and the permutation null (see "Statistics"); print the null level and the cluster ids.

### Pitfall 19: Stale detection that misses or over-fires
**What goes wrong:** the trigger keys on a document id but a new version is a new row; a bulk re-ingest flags thousands of rows; an item is stale but the baseline comparison exits 2 because the golden file hash changed.
**How to avoid:** the trigger fires on the old row's update (`is_current`, `superseded_by`, `status`) and on delete, which is where supersession is visible; it only sets a flag, and the scan decides. Add an index on `rag_golden_evidence_index (document_id)`. Marking an item stale changes the manifest, not the JSONL, so `golden_sha256` stays the same and D-47's "compare the items both have" works; `relabel` changes the file and needs a new baseline.

### Pitfall 20: CI has no private data and no lasting admin token
**How to avoid:** X-3 and X-8. Every step that needs `eval/golden/private/` or `RAG_ADMIN_BEARER` prints a skip notice on schedules and returns `skipped: <reason>` in the release gate. Do not design any acceptance criterion that needs a hosted runner to hold tenant data.

### Pitfall 21: Migrations that assume Phase 5.1.1 tables
**How to avoid:** 0960+ files that alter `rag_review_items` or reference `rag_retrieval_log` guard with `to_regclass(...) IS NOT NULL` so they apply on a database without 0531 to 0535, and the PGlite tests run in both modes with and without them. New SECURITY DEFINER functions carry their own grants and are also added to 0410 and the allow-list; STATE notes 0410 is re-run after later function migrations on live databases.

### Pitfall 22: Config drift
**How to avoid:** six switches in `.env.local`, `scripts/init-env.js`, `src/lib/env.ts`, `scripts/config-server.js`, `scripts/config-ui/index.html`, plus the manifest and `npx tsx eval/harness/eval-env.mts --write` for `eval/config/rag-eval-env.json` (`tests/eval-env-pin.test.ts` and `node scripts/check-config.mjs` check them). `RAG_MONITOR_WEBHOOK_SECRET` under 32 characters should be treated as unset, like the other secrets in the config server's length check.

### Pitfall 23: SUMMARY gate once the UI-SPEC exists
**How to avoid:** `05.3-UI-SPEC.md` was written by another agent while this research ran (status `draft`, untracked at the time of writing) [VERIFIED: phase directory listing and the file's front matter]. Because it exists, `scripts/ci/check-frontend-design-summary.mjs` checks every SUMMARY of the phase, so every plan's output needs the `## Design skills` table (non-UI plans state "no UI file touched"), as the 5.1.1 plan index records. ### Kappa and Jensen–Shannon divergence (standard library)
```python
# Source: definitions in "Statistics Used by This Phase"; checked by simulation in this research
import math

def cohen_kappa(pairs: list[tuple[bool, bool]]) -> float | None:
    n = len(pairs)
    if n == 0:
        return None
    p_o = sum(1 for judge, human in pairs if judge == human) / n
    p_j = sum(1 for judge, _ in pairs if judge) / n
    p_h = sum(1 for _, human in pairs if human) / n
    p_e = p_j * p_h + (1 - p_j) * (1 - p_h)
    return None if p_e == 1 else (p_o - p_e) / (1 - p_e)

def jsd_bits(p: list[float], q: list[float]) -> float:
    def entropy(x: list[float]) -> float:
        return -sum(v * math.log2(v) for v in x if v > 0)
    m = [(a + b) / 2 for a, b in zip(p, q)]
    return entropy(m) - (entropy(p) + entropy(q)) / 2
```

### Settings hash (shape)
```js
// src/lib/.../settings-hash.cjs — required by scripts/config-server.js, wrapped by a .ts file for the app
const crypto = require('node:crypto');
const sha256 = (text) => crypto.createHash('sha256').update(text, 'utf8').digest('hex');
function ragSettingsHash(values, ragAffectingNames, isSecret) {
  const pairs = {};
  for (const name of [...ragAffectingNames].sort()) {
    const value = values[name] ?? '';
    if (isSecret(name)) pairs[name] = value === '' ? 'unset' : 'set';
    else if (name === 'RAG_SYSTEM_PROMPT') pairs[name] = sha256(value);
    else pairs[name] = value;
  }
  return sha256(JSON.stringify(pairs));   // keys were inserted in sorted order
}
module.exports = { ragSettingsHash };
```
D-12 names only `RAG_SYSTEM_PROMPT` for hashing; `RAG_PRE_CONTEXT` and `RAG_POST_CONTEXT` hold the same kind of text and are what the prompt editor writes. Hashing all three the same way keeps prompt text out of records (see Assumptions A7).

## Open Questions

1. **How does the fixture tier count a false answer, and what about the legacy false-refusal rate? (blocks the plan that makes `--gates` mandatory)**

   - Recommendation: `nightly.yml` gains a `monitor` job that runs `npm run rag:monitor` when `SUPABASE_SERVICE_ROLE_KEY` and the Supabase URL are repository secrets (skip notice otherwise), next to the operator's own cron.    - Recommendation: no new credential in this phase; these calls are best effort in CI (notice when the token is missing or rejected) and authoritative when run by the operator. GitHub stays the record for overrides (D-36).

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| One tenant's counts, clusters, samples, labels or evidence reach another tenant | Information disclosure | `tenant_key` on every table with a per-mode check; two-tenant tests at SQL and route level for each object (D-55); cluster sets never span tenants |
| Forged `rag-release-gate: success` by a user with write access | Spoofing, Elevation | creator check in the promotion script; GitHub is the record; owner may require the check's source app in branch protection |
| A commit weakens its own gate files | Tampering | hashes of the gate files in `ReleaseGateResult`; review on those paths (owner setting) |
| Script injection through `workflow_dispatch` inputs | Tampering | inputs through `env`, validated; lint rule |
| Secrets in CI logs or in the harness child process | Information disclosure | step `env` only; lint for `echo ... KEY`; child environment from an allow-list |
| SSRF through `RAG_MONITOR_WEBHOOK_URL` | Tampering | `assertPublicUrl` on every delivery (DNS re-checked), HTTPS only, no redirects followed blindly |
| Webhook replay or forgery | Spoofing | HMAC-SHA256 over the body with a timestamp field; secret of 32+ characters |
| PII in imported questions that the masker does not match (names, addresses) | Information disclosure | masking, rejection of rows that still change under masking, expert PII checklist before promotion (5.1.1 D-22), private storage only |
| Text leaking into alerts, weekly report or logs | Information disclosure | contract tests that walk model fields; the override reason is the single operator-written text, capped |
| Prompt text stored in change records | Information disclosure | records hold key names and hashes only (D-16) |
| Local operator bypasses the gate by editing `.env.local` or host settings | Repudiation | out of scope to prevent; `record-change` for declared changes; `unrecorded_config_change` in alerts when a new `retrieval_config_hash` appears with no record (D-27) |
| Check runner abuse (many checks, long runs) | Denial of service | one check at a time, 600-second limit, loopback-only config server with the CSRF header rule |
| Trigger or function running with a hijacked `search_path` | Elevation | `SECURITY DEFINER` with `SET search_path = ''`, qualified names, 0410 lock, allow-list test, `definer-search-path-pglite` test |
| An expert reads another tenant's answer or chunk text through the calibration export | Information disclosure | admin Bearer route; text re-read under the item's tenant at request time; committed calibration file holds numbers only and no tenant id (D-31) |
