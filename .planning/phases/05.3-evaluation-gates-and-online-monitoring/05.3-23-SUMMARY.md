# Phase 05.3 Plan 23: Config-server save guard Summary

**The config server can no longer write a RAG-affecting setting in enforce mode without a passed check or a recorded reason. An end-to-end test with the real child process shows that a prompt without the refusal directive fails its check and is refused on save.**

## Accomplishments

- `guardEnvWrite` in `scripts/config-server-rag-gate.js` decides each save (`decideSave`), writes a `rag_config_change_records` row (actor `local-config-ui`, source `config_ui`, names and hashes only), and refuses an override that cannot be recorded with 503 `rag_gate_record_failed`.
- Guarded writers on the config server: `POST /api/config`, `POST /api/config/create` (when `force` would overwrite a file) and `POST /api/config/languages` (deviation 1). Nothing is written on 400, 409 or 503.
- The rag-prompt proxy forwards `ragGate` and returns the app's `ragGate` on success. The models proxy already forwarded the whole body; it now also passes 409 and 503 through for a chunked app response (deviation 2).
- `clear: ['RAG_MONITOR_WEBHOOK_URL']` empties that one name; any other name answers 400 `invalid_clear`.
- `POST /api/admin/setup` stays unguarded. The test asserts that `ADMIN_EMAIL` and `ADMIN_PASSWORD` are not in the generated RAG-affecting list.

## Behaviour changes

- With `RAG_CONFIG_GATE` off (the default): none. Files written and responses are the same as before. The one difference: when the request body itself is the value map, a `ragGate` or `clear` field is no longer written as an env line.
- warn: RAG-affecting saves are written and recorded. A failed record only logs.
- enforce: the 409, 400 and 503 answers described above.
- Models proxy: upstream `content-length`, `transfer-encoding` and `connection` headers are no longer copied onto the re-serialised JSON response.

## Deviations

1. **[Rule 2, security] `POST /api/config/languages` is guarded as well.** It writes `RAG_SUPPORTED_LANGUAGES` and `RAG_PRIMARY_LANGUAGE`, and both are in the generated RAG-affecting list. Research F-5 counted five writers and missed this one, so it would have bypassed enforce (T-05.3-231). It uses the same guard; `ragGate` is read from the request body. The Config UI Languages panel does not send `ragGate` yet, so in enforce it now gets 409. That is fail-closed, and the default is off. Plan 05.3-42 should give that panel the check dialog.
2. **[Rule 1, bug] Models proxy framing headers.** The proxy copied the upstream `transfer-encoding: chunked` and then `res.json` set `Content-Length`, so a chunked app response broke the proxy (including the 409 and 503 the plan needs passed through). The test reproduced it; the fix filters the framing headers. The MCP servers proxy has the same pattern and was not touched.
3. **Test console output silenced.** The config server logs each save at length (model lists). Under `node --test` the combined output of the save test made the runner fail with "Unable to deserialize cloned data". The save and e2e tests silence `console` while the server runs.
4. **`loadNames` option on `guardEnvWrite`.** Added so the missing-list case (research Pitfall 7) can be tested without touching the generated file.

## Open points (not changed)

- `RAG_CONFIG_GATE` is not in the RAG-affecting list. A save that only sets it from enforce to off therefore goes through unchecked. Every later save then follows the new mode. Whether lowering the mode itself should need a reason is a design decision for the phase owner, not this plan.
