# Phase 5.3 Plan 29: Alert routes and the online judge score mirror Summary

**Admins can list, acknowledge and resolve monitor alerts of their own tenants through three routes, and online judge scores reach `rag_online_judge_scores` through an app route whose tenant comes from the retrieval log, so the monitor never reads Langfuse.**

## Accomplishments

- `alerts-read.ts`: `listAlerts` resolves the admin's tenants with `rag_admin_tenant_keys`, counts open and acknowledged alerts, and reads one page by ordered segments (status, then severity) with a keyset cursor; every row is rebuilt into `MonitorAlertSchema` (observed and baseline from the count, total and rate columns; companions from the object keyed by rule back to the contract array) and dropped with a count when it fails. `monitorSummary` reports the switch, the configured `RAG_RETRIEVAL_LOG` level and the newest `rag_monitor_runs` row. `alertForAdmin` reads one alert only when its tenant is administered by the caller.
- `GET /api/rag/admin/monitor/alerts`: switch first, then `checkAdmin`, Zod (`zod/v3`) query validation, `{ monitor, counts, alerts, next_cursor }` with `Cache-Control: no-store`, `[Monitor]` log with counts only.
- `POST /api/rag/admin/monitor/alerts/{id}/{acknowledge|resolve}`: tenant check before `setAlertStatus` (actor = verified admin id), 200 with the alert, 404 for another tenant's or an unknown alert, 409 for a state that does not allow the transition.
- `POST /api/rag/admin/monitor/judge-scores`: strict body without any tenant, at most 500 scores, `rag_online_judge_scores_record` returns `{ stored, dropped }`.
- `rag_eval.online_judge`: `--base-url` and `--token-env` (default `RAG_ADMIN_BEARER`); `_mirror_scores` posts the same numbers after the Langfuse post with the lazy `httpx` client of `review_queue.py`.
- `@/lib/rag` index exports `monitorSettings`, `setAlertStatus` and the alert reader (the boundary check forbids deep imports from routes).

## Deviations from Plan

1. **[Boundary] `@/lib/rag` index.** The routes cannot import `@/lib/rag/monitor/*` (check-rag-boundary `deep-import`), so `monitorSettings`, `setAlertStatus` and the reader are exported from the index. Additive.
2. **[Contract] No actor field in the response.** `MonitorAlertSchema` has `acknowledged_at` but no `acknowledged_by`, `resolved_at` or `resolved_by`; the actor is stored by `rag_monitor_alert_set_status` (T-05.3-294) and the response carries only the contract fields.
3. **[Contract] baseline.** The alert table has no null baseline; the reader always returns `{ count, n, value }` from the baseline columns (zeros and null rate when the candidate had none).
4. **[Scope] `--token-env`.** Added next to `--base-url`, as in `review_queue.py`, with `RAG_ADMIN_BEARER` as the default.
5. No migration was needed; no migration number was claimed.
