## 0. Findings that shape this contract (read first)

Facts from the code and from CONTEXT. Each one changes what the UI can show or do.

1. **None of this phase's routes exists yet.** Section 8.1 lists what each view needs. Field and route names there that
   CONTEXT does not fix are **proposals to the backend plans**; the behaviour they support is the contract.
2. **Three browser paths write RAG-affecting settings, and CONTEXT D-15 names two.** `saveConfig()` posts the whole
   `this.config` to `POST /api/config` (header button and about ten auto-save handlers, `index.html` 10228 to 10724);
   `saveRagPrompt()` posts to `POST /api/config/rag-prompt` (the System Prompt tab's button, the template chooser's
   apply-and-save with retries at 15853 to 15997, and `saveConfig()` itself); "Save Model Configuration" posts to
   `POST /api/config/models`. The dialog and its guard are written once and used by all three (section 6.3). Research
   F-5 counts five writers in all and puts the server guard in front of each; the other two (`POST /api/config/create`
   with `force`, and the in-app admin settings page) have no caller in `scripts/config-ui/` and are outside this
   contract (section 14, row 3).
3. **The browser cannot know which keys are RAG-affecting.** That is the `ragAffecting` flag of the env manifest (D-11),
   read by the config server. The guard sends the proposed values and the server answers whether a check is needed.
4. **`RAG_CONFIG_GATE=off` must leave the save path byte-identical (D-10).** With the mode off the page makes no
   `rag-gate` request and shows no dialog. The mode is read from the last loaded or saved configuration, never from the
   unsaved value of its own select.
5. **A save may carry settings the admin changed minutes ago on another tab.** Inputs write `this.config` on `change`
   and many handlers call `saveConfig()` for an unrelated toggle. The dialog therefore always lists the changed
   RAG-affecting settings by name, so a check that "appears from nowhere" explains itself.
6. **Phase 3.2 defines a first save guard, `window.ragBeforeConfigSave(changed)`** (03.2-UI-SPEC 6.4.1), not on this
   branch yet. The two guards must run in a fixed order (section 6.3.1).
7. **A check can run for ten minutes (D-14: timeout 600 seconds, one at a time per machine, cached for 30 minutes by
   settings hash).** The dialog is built around waiting: elapsed time, the layer that is running, a way out that loses
   nothing, and a cached result that returns at once.
8. **Refusal cells already have a status called `uncalibrated`** (no threshold was fitted), shown as "Not calibrated" by
   `refusal-calibration.js`, next to a `stale` badge. D-18's derived marking is a third thing: a calibrated cell whose
   model changed afterwards. It gets its own badge and words (section 6.5) so the three are never confused.
9. **`refusal-calibration.js` reads the status route only when the RAG administration tab opens.** The standing warning
   of D-18 would be invisible on every other tab, so the count also appears in the page banner (section 6.6).
10. **The `/api/rag/*` proxy forwards JSON only, and `express.json()` on the config server keeps its 100 KB default.** A
    file of past questions cannot be sent as one multipart upload through it. The import view reads the file in the
    browser and sends it in batches (section 6.10.3), unless the backend plan adds a dedicated upload route.
11. **The Review queue panel (`review-labelling.js`) and the Feedback loop card (`review-admin.js`) belong to Phase
    5.1.1** and are not on this branch; `05.1.1-UI-SPEC.md` is not available here. Section 6.11 is an extension
    contract: it adds elements to that panel in that panel's own style and is not built when the panel is absent
    (CONTEXT dependency table).
12. **CONTEXT D-59 assigns no Config UI view to golden-set versions, the release gate or the list of overrides.** They
    are shown in reports, in GitHub and in the weekly report. What reaches the Config UI: the `re_review` reason tag
    (D-50), the tenant runs that were skipped for want of a test set (D-19), and the setting changes listed inside an
    alert (D-27), which include release overrides.
13. **Alerts hold no free text by contract (D-26),** and cluster names are never generated from questions (CONTEXT
    specifics). Every view of this phase shows ids, counts, rates, names of settings and dates. The one free text on any
    screen is the reason the admin types, shown back only while typing.
14. **All Config UI scripts are classic scripts in one global scope** (04-UI-SPEC finding 13), and the older panels bind
    their init to the first `[data-tab="rag-administration"]` link only. New files use the prefixes of section 6.1 and
    bind every link, as the Ingestion panel does.
15. **The built-in test questions cannot test every setting.** They run with a stand-in answer model and the fixture
    embedder, so a changed chat model, embedding model or reranker credential is not exercised by them (research
    Pitfall 8). A "Passed" that tested none of the changed settings would mislead, so the dialog lists the settings the
    check could not test and such a pass waits for a decision (sections 6.3.2 and 6.3.4).
16. **`RAG_MONITOR_WEBHOOK_URL` is a secret to the config server.** Its name matches `SECRET_NAME`
    (`scripts/config-server-security.js`, the pattern contains `WEBHOOK`): the value is never sent to the browser and an
    empty field means "unchanged". That is the right default, since many webhook URLs carry a token, but it leaves no
    way to remove the webhook. The field is therefore write-only and has an explicit Remove webhook action (6.12).

## 1. Design direction (frontend-design pass)

**Subject.** The checkpoint between a change and production, and the watch kept after release: was this change tried, did
it pass, what is drifting, and can the judges and the test set still be trusted.
**Audience.** A deployment admin at a desktop, in one of three moments: about to save a setting ("will this make the
system answer what it should refuse?"), arriving after an alert ("what moved, where, and what changed that day?"), or
doing the monthly round ("which judges count, does the test set still look like real questions?").
**Primary job.** Put the evidence for a decision on screen and make the safe choice the easy one.

**Mode.** Impeccable "Operate". These are working tools inside an existing dashboard. Sections, sub-tabs, tables,
badges, alerts and dialogs are the ones the Ingestion, Chunking profiles and Refusal calibration panels use. No new
navigation, no new control type.

**Organizing idea: a result is one word from a closed list, and "did not run" never looks like "passed".** A check
layer, a nightly run after an import, a judge, a delivery channel: wherever something reports an outcome, it is written
as a **verdict line** (section 6.2): an icon and one word (Passed, Failed, No result, Skipped, Not enough data, Report
only, Does not apply), then the reason, then the numbers as measured, count and limit. Only Passed is green. A row the
server gave no verdict for reads "No result". This is CONTEXT's "a skip must be visible everywhere" made into one form
the admin learns once.

**Signature element: the evidence row.** "False answers: 15.0% (3 of 20), limit at most 5.0%, Failed." Every number
that decides something is shown with its count and the limit it was held against, in the same three columns (Measured,
Limit, Result) in the dialog, the evaluation runs and the alert evidence. Nothing else on these screens is decorative.

**Review against generic defaults (what was changed and why).**
- Rejected a traffic-light dashboard of stat tiles (refusal rate, votes, latency as big numbers). The monitor's output
  is alerts, not readings; a tile per metric invites reading noise. The Alerts view lists what crossed a band, with its
  counts, and says how many groups had too little data.
- Rejected a line chart per metric and a sparkline for the eight-week trend. Eight values with a state word each are a
  table; the admin compares them with two limits, which a table states exactly.
- Rejected a bubble or scatter "topic map" for coverage. Clusters have ids, not names (finding 13), so position and
  size would carry nothing a reader can decode. Coverage is a table with two share columns and a thin bar in each
  (dataviz: more than seven classes that all matter is a table; several ratios on named rows is a meter list).
- Rejected a toast for the check result. A result that decides whether a save applies needs to stay on screen and be
  answerable; it is a dialog. Toasts keep their existing job (a save happened).
- Rejected a red "Override" button. Saving against a failed check is the one risky action here and is drawn in the
  warning colour with a required reason; red stays for things that are broken or failed.
- Rejected colouring judge and coverage numbers by the UI's own comparison. Colour follows a state the server names
  (a reason code, a verdict), never arithmetic done in the browser.
- Rejected auto-dismissing alerts and a "Dismiss all" button. An alert leaves the banner when a person acknowledges it.
- Rejected emoji, middle-dot meta strings, all-caps labels and arrows on buttons.

**Quality floor (built without announcing it).** Visible keyboard focus, `prefers-reduced-motion` respected, all text
at least 4.5:1, tabular numerals in number columns, usable down to 360px, every state in section 7 present, every
server string inserted with `textContent`.

Rules:
- Number columns, counts, rates, the elapsed time and the character count use `tabular-nums`; numbers are right-aligned
  in their columns.
- Description, alert and dialog paragraphs cap at `max-w-prose`.
- Ids, hashes, env names and model ids use `font-mono text-xs break-all` with `translate="no"`. Commands use
  `code.font-mono.text-xs.break-all`. Nothing else is monospace. A hash is shown as its first 8 characters with the
  full value in `title`.
- A rate is written with its count wherever the count exists: `38.0% (76 of 200)`. Percentages have one decimal;
  scores, kappa, divergence and deltas have two; the format comes from `Intl.NumberFormat(locale)`.
- No all-caps labels, no letter-spaced eyebrows, no label above a heading, no single emphasised word inside a heading.
- Each panel root, the banner and the dialog carry `lang="<locale>"`. Text left in English inside a localized view
  (unknown server codes) is wrapped in an element with `lang="en"`.

### 6.2 The verdict line and the evidence table (signature)

**Verdict line.** `span.badge.badge-sm.gap-1` (icon + word), then, when there is a reason, a 14px sentence after it.
The word list is closed; the builder maps every server value onto it and maps anything unknown to "No result".

| Server value (any contract) | Word key | Classes | Icon |
|-----------------------------|----------|---------|------|
| `pass`, `passed`, `success` | `verdict.pass` | `badge-success` | `bi-check-circle-fill` |
| `fail`, `failed` | `verdict.fail` | `badge-error` | `bi-x-octagon-fill` |
| `error`, a missing or unknown value | `verdict.error` | `badge-warning` | `bi-exclamation-triangle-fill` |
| `skipped` | `verdict.skipped` | `badge-warning badge-outline` | `bi-slash-circle` |
| `insufficient_n`, `insufficient_sample` | `verdict.insufficient` | `badge-ghost` | `bi-dash-circle` |
| `report_only` | `verdict.reportOnly` | `badge-ghost` | `bi-eye` |
| `not_applicable`, `not_required` | `verdict.notApplicable` | `badge-ghost` | `bi-dash` |
| `running` | `verdict.running` | `badge-info badge-outline` | `bi-arrow-repeat` (static) |
| `pending`, `queued` | `verdict.pending` | `badge-ghost` | `bi-hourglass` |

Rules: only `verdict.pass` is ever `success`. "Skipped" and "No result" always carry a reason sentence (`reason.*`,
section 12.2); a reason code the table does not know is shown in `code.font-mono` inside the sentence. The word is
never replaced by colour or icon alone.

**Evidence table.** `table.table-sm` with a visually hidden caption and these columns:

| Column | Content |
|--------|---------|
| Check | `check.*` label for the metric or rule (unknown name: the name in `code.font-mono`); `th scope="row"` |

### 6.3 The pre-save setting check (EVAL-23, D-10 to D-16, D-18)

#### 6.3.1 The save guard

`setting-check.js` exposes `window.ragSettingCheck.beforeSave(request)`, which returns a promise of
`{ proceed: true, gate?: { check_id } | { override: { reason } } | { skipped: true } }` or `{ proceed: false }`.

| Caller | `request` | What the caller does with the answer |
|--------|-----------|--------------------------------------|
| `saveConfig()` | `{ kind: 'config', config: this.config, changed: [names] }` | `proceed: true`: posts as today, adding `ragGate` to the body when `gate` is present. `proceed: false`: posts nothing |
| `saveRagPrompt()` | `{ kind: 'prompt', preContext, postContext }` | The same, on `POST /api/config/rag-prompt`. Returns the new value `'held'` (not `false`) when the guard holds the save |
| Save Model Configuration | `{ kind: 'models', models }` | The same, on `POST /api/config/models` (section 14, row 3) |

Rules:
- **Order of guards.** `saveConfig()` awaits `window.ragBeforeConfigSave` first when it exists (Phase 3.2, ingestion
  impact), then this guard with the values that remain after it. A value the first guard put back is not checked.
- **Mode off.** When the last loaded or saved `RAG_CONFIG_GATE` is `off` or unset, the guard resolves
  `{ proceed: true }` at once, with no request (finding 4).
- **Nothing changed.** When `changed` is empty the guard resolves `{ proceed: true }` with no request.
- **Held is not failed.** A caller that receives `proceed: false` or `'held'` shows no error toast and does not retry.
  The template chooser's retry loop (15923 to 15984) stops on `'held'`. The header indicators show `indicator.held`
  with `alert-warning` for 3 seconds instead of "Saving…".
- **The save is the caller's.** The dialog stays open in its "saving" state while the caller posts. The caller reports
  back through `window.ragSettingCheck.saved(response)` or `.saveFailed(status, body)`, and the dialog shows the outcome
  (6.3.4). No draft is ever put back to its saved value by this guard.
- **A 409 `rag_gate_required` with no dialog open** (the mode changed since the page loaded, or the guard resolved
  without a request) is not a failed save: the caller hands the same request to
  `window.ragSettingCheck.required(request)`, which opens the dialog and starts the check. `saveConfig()` has one such
  handler for all its callers, so an auto-saving toggle never shows "Failed to save" for this answer (research F-5).
- **Guard script missing or throwing.** The save is posted as today. In `enforce` mode the server answers 409
  `rag_gate_required` (D-15) and the caller shows the toast `error.required`; nothing was written.
- **One at a time.** A second save while the dialog is open is ignored (the dialog is modal; auto-save handlers cannot
  fire behind it).

#### 6.3.3 Waiting

`POST /api/config/rag-gate/check` with the proposed values. The answers:

| Answer | What happens |
|--------|--------------|
| 200 `required: false` | No dialog; the guard resolves `{ proceed: true }` |

### 8.2 Error and code mapping (exact)

Every script wraps its calls in `try/catch`. `error.signIn`, `error.network` and `error.generic` are read from the
shared table through `window.ingestLabel(key, locale, vars)`, with `{appUrl}` filled from
`window.getConfiguredMyRAGAppUrl()` when that function exists and from `window.location.origin` otherwise; the
placeholder must never reach the screen. When `ingestLabel` is missing, fall back to `authMessage(status)`.

| Status | `body.error` | Route | Key and behaviour |
|--------|--------------|-------|-------------------|
| thrown, or client timeout | n/a | any panel call | Shared `error.network` |
| thrown, or client timeout | n/a | start or poll of a check | Dialog state No result, `reason.no_answer` |
| 401, 403 | any | any app route | Shared `error.signIn`; panel content replaced by the sign-in alert. In the banner: the row is left out |
| 401, 403 | any | `rag-gate` routes | Dialog state No result, `reason.no_answer` (the config server's own sign-in rule applies to the page as a whole) |
| 404 | route off (`RAG_MONITOR`, `RAG_REPRESENTATIVE_SAMPLE`, `RAG_DOMAIN_EXPERT_REVIEW`) | monitor, sample, import, review routes | `error.switchedOffApp` when the saved switch is on; otherwise the view's "off" state |
| 404 | none held | `rag-gate/check/latest` | `last.empty.*` |
| 404 | unknown check id | `rag-gate/check/:id` | Dialog state No result, `reason.no_answer`; Run check again starts a new one |
| 404, 409 | alert changed | acknowledge, resolve | `error.alertGone`, list reloads |
| 404 | `user_not_found` | pilot users, add | `pilot.notFound` at the field |
| 404 | not found | pilot users, remove | `pilot.gone`, list reloads |
| 409 | `already_pilot` | pilot users, add | `pilot.exists` at the field |
| 409 | `rag_gate_busy` | start a check | Dialog state Busy |
| 409 | `rag_gate_required` | a save | Dialog: `error.changed`. Without a dialog (guard missing): toast `error.required` |
| 503 | `rag_gate_record_failed` | a save | Dialog: `error.recordFailed`; nothing was written |
| 400 | `invalid_reason` | a save | Dialog: `reason.tooShort` at the field |

## 9. Keyboard, screen reader and focus

1. **Headings.** Panel title `h3`; block titles inside a sub-view and the measure name of an alert entry `h4`; block
   titles inside an alert's evidence `h5`. Inside the dialog the title is `h3` and its blocks `h4`. No level is skipped.
2. **Sub-tabs.** `role=tablist` with an `aria-label`; each `button[role=tab]` has `aria-selected`, `aria-controls` and a
   roving `tabindex`. Left and Right move and activate, Home and End jump. Panels are
   `div[role=tabpanel][aria-labelledby][tabindex=0]`.
3. **The check dialog.** Native `<dialog>` with `showModal()`, `aria-labelledby` the title, `aria-describedby` the lead
   paragraph. Default focus on Edit settings; after each state change focus moves to the title (`tabindex="-1"`),
   unless the reason field has focus. Escape equals Edit settings, except during Saving, when Escape does nothing
   (`cancel` is prevented). The browser traps Tab. On close, focus returns to the control that started the save, or to
   the header's Save All Changes button when that control is gone.
4. **The reason field.** Visible `<label for>`, help and count tied with `aria-describedby`, `aria-invalid="true"` once
   touched and too short. The disabled save button keeps its label and its `aria-describedby` names the reason it is
   disabled. The character count is not a live region; `reason.tooShort` is announced through the dialog status region
   when it first appears.
5. **Waiting.** The `<progress>` has an `aria-label`. The elapsed time is `aria-hidden`; the dialog status region
   announces the layer when it changes and the elapsed time once a minute, then the verdict.
6. **Verdicts.** The word is text; the icon is `aria-hidden`. A flagged number in the judge table carries an `sr-only`
   phrase. No state is carried by colour alone anywhere in the phase.
7. **Alert entries.** Each is an `article` labelled by its measure name. `details` summaries are focusable and get
   `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2`. Action names include the measure
   and the language. After Acknowledge alert focus stays in the entry; after Resolve alert it moves to the next entry's
   heading (`tabindex="-1"`) or the status region.
8. **Confirmations** (Resolve alert, Remove pilot user, Remove webhook). Native `<dialog class="modal">` built with DOM calls (the
   Ingestion panel's pattern), `aria-labelledby` and `aria-describedby`, default focus on the "Keep…" button, Escape
   and the backdrop cancel, focus returns to the opening button or to the status region when it is gone.
9. **Radio groups** (answer check, status filter). `fieldset` with `legend`; arrow keys move within a group; no option
   is preselected in the answer check. Save answer check moves focus to the first unanswered group when incomplete.
10. **Forms.** Every control has a visible `<label for>`. The pilot-user form submits on Enter. The file input keeps
    its native control (no hidden input behind a styled button). The question column select is disabled, with its
    reason in `aria-describedby`, until a file is read. Number, URL and secret fields carry `autocomplete="off"`.
11. **Live regions.** One polite status region per panel and one inside the dialog. Announce: load finished with
    counts, action outcomes, errors. The gate outcome sentences in the dialog are also `role="alert"` when a save was
    refused, because they answer an action just taken. Warnings rendered on load (banner, calibration warnings,
    combination notes) have no alert role.
12. **Tables.** `caption` (visually hidden), `th scope="col"`, the first cell of each row `th scope="row"`. A table that
    can scroll sideways sits in `div.overflow-x-auto[tabindex=0][role=region][aria-label]`.
13. **Links and ids.** A trace id that is a link opens a new tab and says so in its accessible name. "Copy trace ids"
    keeps its text label; no icon-only button exists in this phase except the page's existing secret reveal button,
    which gets an `aria-label`. Dates use `<time datetime>`.
14. **Motion.** Only DaisyUI's spinner and the browser's own progress bar. Under `prefers-reduced-motion: reduce`,
    spinners are hidden (`motion-reduce:hidden`) and their text remains; the indeterminate progress bar is replaced by
    the text alone. Nothing slides, fades or pulses; the banner appears and leaves without animation.
15. **Zoom and text size.** At 200% zoom nothing clips: no fixed heights except the 4px share bar, the 8px progress bar
    and the 160px trace list; cells, toolbars, meta lines and button rows wrap; the dialog scrolls inside its box.
16. **Language.** `lang` on each panel root, the banner and the dialog; `lang="en"` on text left in English.

## 11. What must never be shown or done

These screens are admin-only and show **ids, counts, rates, dates, names of settings and model ids**. Nothing a user
wrote and nothing a document says.

1. Every view renders only the fields named in sections 6 and 8.1, through builder functions, never by iterating an
   object's keys. A field the server adds later stays invisible until it is added here on purpose.
2. **No question text, answer text, chunk text, document name or file name appears in any view of this phase,** and
   the Monitoring, Setting checks, Judge calibration and Question sources scripts call no route that returns one
   (D-26, D-51). The only place a question and an answer are on screen is the Phase 5.1.1 Review queue item view, which
   this phase extends without adding any text to it.
3. **No setting value is shown in the check dialog, the Last check view or an alert:** names of changed settings only.
   Never the prompt, a model list, a URL, a secret, or a before and after value.
4. **The override reason is shown only in the field while the admin types it.** It is not echoed in the Saved state,
   the Last check view, an alert's setting changes or anywhere else in the Config UI (it goes to the weekly report,
   D-17).
5. **Clusters are named by id.** No label, keyword, example question or summary is generated or shown for a topic
   group (CONTEXT specifics).
6. Never rendered, even though a response contains them: `rag_settings_hash` and `retrieval_config_hash` in full (the
   first 8 characters only, in an alert's setting changes), `actor` and `acknowledged_by` (user ids), `dedup_key`, the
   raw `breakdown` and `companions` JSON, a refusal cell's raw `key` (its model and language are shown), a judge
   fingerprint in full, sampling weights and strata of single items, the tenant hash of a private set in full.
7. Pilot users are shown as the masked e-mail the server returns or as a user id. The UI never unmasks, and never
   lists a user's questions.
8. The import view never shows a row of the file: not as a preview, not in an error message (errors name a line
   number), not in a count's tooltip. The file content is not written to `localStorage`, `sessionStorage` or
   `IndexedDB`.
9. No configuration value the config server treats as a secret is read back or rendered. That includes the webhook
   URL (finding 16) and the webhook secret: both fields are write-only and follow the page's empty-means-unchanged
   rule. An alert's delivery row says whether the webhook delivered, never where to.
10. Every server string (ids, model ids, setting names, slice names, rule ids, reason codes, column names read from a
    file) is inserted with `textContent`. Tests stub a rule id, a setting name, a cluster id, a trace id, a column name
    and a reason code containing `<img src=x onerror=alert(1)>` and assert that no element is created from them.
11. No `Authorization` header, no token in browser storage, no second sign-in form.
12. No view offers to edit a limit, a band, a threshold, a calibration result, a test-set item or a change record.
    Limits change through pull requests on the files of D-02; this UI only reads them.
13. **No domain content in any string** (REQUIREMENTS, domain-neutrality rule): no example question, topic, document
    type beyond the six existing type names, or sample value appears in copy, placeholders, empty states or test
    fixtures. Fixtures use neutral ids (`c-01`, `trace-0001`, `RAG_EXAMPLE_SETTING`).
14. With a switch off, the UI never suggests that the feature ran: an "off" state has no counts, no "0 alerts" and no
    green badge.

## 12. Copywriting Contract

Voice: plain verbs, sentence case, names from the admin's side of the screen. A message that reports a problem says what
happened and what to do next; errors do not apologize. One action keeps one name through its flow: the button, the
dialog's confirm button and the outcome message say "Resolve alert", "Resolve alert", "Alert resolved".
"Reload panel" always means reloading a view.

**Words used, and words avoided.** "Setting check" and "check" for the pre-save gate; the word "gate" is not shown (as
in the Chunking profiles panel). "Limit" for a ceiling or a floor, always with "at most" or "at least". "False answers"
for answering a question the documents cannot answer; "false refusals" for the opposite. "Usual" for the 30-day
baseline. "Group" for a monitored cell. "Topic group" for a cluster; "cluster" is not shown. "Real questions" for
production traffic; "test set" for a golden set; "golden" is not shown. "Test set coverage" for drift. "Judge" for an
LLM judge; "Enforced" for a judge that gates. "Starter set" for the seed calibration set. "Reason" for an override
reason; "override" is not shown. "Imported question" for provenance `historical`; "Weekly sample" for `representative`.
"Skipped" and "No result" are never softened into "OK", "n/a" or a blank.

**Action labels are verb + noun in every locale.** Accessible names extend the visible label and start with the same
verb ("Acknowledge alert: Refusal rate, Italian"). In-flight text ("Saving…") is status on a disabled button, not a
label. Not actions, so not verb + noun: sub-tab names, filter radios, select and radio options. No button is labelled
"Cancel", "OK", "Submit", "Close" or "Dismiss" alone: a button that backs out says what stays ("Keep alert open",
"Keep pilot user", "Keep webhook") or what it returns to ("Edit settings", "Close check").

**Counts are written as "label: number"** ("Open monitoring alerts: 3"), so no string needs a plural form in en, zh or
it.

**Where the strings live.** One `{ en, zh, it }` table per file (`GATES_UI_LABELS`, `SETTING_CHECK_LABELS`,
`MONITOR_LABELS`, `JUDGE_CAL_LABELS`, `QUESTION_SOURCES_LABELS`; additions to `REFUSAL_LABELS` and to the Review queue
panel's own table), read through one function per file that fills `{placeholders}` and falls back to English. Sign-in,
network and generic-failure sentences are not copied; they come from the shared `ingestLabel` table. Document-type
names come from `docTypeLabelForLocale`; language names from `Intl.DisplayNames`. A placeholder shown as `{command}`,
`{variable}`, `{code}` or `{id}` is replaced by a `code` element, not by text. Numbers use `Intl.NumberFormat(locale)`;
dates `Intl.DateTimeFormat(locale, { dateStyle: 'medium' })`; times of day `{ timeStyle: 'short' }`.

Commands named in copy: `python -m rag_eval.calibrate refusal`, `python -m rag_eval.judge_calibration run`,
`python -m rag_eval.tenant_nightly --drain`, `python -m rag_eval.drift`,
`npm run rag:monitor -- record-change --keys <names> --reason <text>`.

## 13. Color

DaisyUI theme tokens are the contract; hex values are the DaisyUI 4.4 defaults, for reference only, and are never
hard-coded. These views use no brand orange: in RAG administration, `myrag-primary` means "metered premium pages" in
the Ingestion panel and keeps that single meaning.

| Role | Token | Reference (dark / light) | Usage |
|------|-------|--------------------------|-------|
| Dominant (60%) | `base-100` | ≈ #1D232A / #FFFFFF | Tab card behind the panels; the check dialog and confirmation boxes; inline form regions |
| Secondary (30%) | `base-200`, `base-300` | ≈ #191E24, #15191E / #F2F2F2, #E5E6E6 | Panel cards; dividers between alert entries; table borders; the share-bar track; the progress track |
| Text | `base-content`, `/70` for secondary | ≈ #A6ADBB / #1F2937 | All text; muted lines use `/70`, never lower. The share-bar fill is `base-content/60` |
| Accent (10%) | `primary` (DaisyUI) | theme primary | See the reserved list below |
| Success | `success` | theme success | The Passed verdict (solid) and the Enforced judge status (outline). Nothing else |
| Info | `info` | theme info | The Running verdict (outline); the `none_enforced` notice and the `warn.enforceFirst` note (`alert-info`) |
| Warning | `warning` | theme warning | No result and Skipped verdicts; alert severity Warning; the banner; sign-in alerts; the threshold notice; coverage and judge states the server flags; the "Uncalibrated after a change" and "Possibly stale" badges; combination notes; the three buttons that save without a passed check |
| Destructive | `error` | theme error | No destructive action exists in this phase, so no button is ever `error`. Used only for states the server names: the Failed verdict, alert severity Alert (and the banner while one is open), unavailable alerts, field errors, `calibration_invalid` |

Accent reserved for: Save settings in the check dialog; Acknowledge alert; Add pilot user; Check file and Import
questions (one at a time); Save answer check; the confirm button of the three confirmations (Resolve alert, Remove
pilot user, Remove webhook); the fill of the two progress bars; focus outlines. Nothing else is `primary`: not headings, not links, not the
banner buttons, not Edit settings, Run check again, Close check, Run monitor now, Run sample now, Resolve alert in an
entry, Remove pilot user in a row, Remove webhook in Settings, Refresh or Reload (all neutral, outline or ghost), not badges, and never a number.

Rules:
- **Green means passed, and only that.** No count of zero, no "off" state, no skipped layer and no acknowledged or
  resolved alert is ever green.
- **Saving without a passed check is never primary.** Its three buttons are `btn-warning`; the safe way out, Edit
  settings, has the default focus.
- **A number is never coloured by the browser's own comparison.** Success, warning and error describe a verdict, a
  severity, a state or a reason code the server sent. Share bars have one neutral colour.
- Severity and verdict are always a word with an icon; colour repeats them and never replaces them.

## 14. Decisions made in this contract

No question was asked (`--auto`; the owner's standing rule is to take the recommended option and record it). Each row
is a recommendation adopted as the contract; the owner or the planner may override it. Rows 1 to 6 add behaviour that
CONTEXT does not spell out and need the backend plans to follow this file.

| # | Question | Decision and reason |
|---|----------|---------------------|
| 1 | After a passed check, does the admin confirm again? | No. The admin already asked to save; a pass with nothing else to decide is saved at once and the dialog stays open on the result with Close check. A pass with a notice waits for Save settings: when a changed setting was not tested by any layer (finding 15), or when refusal thresholds stop applying, the admin is told something the word "Passed" does not say |
| 2 | What does backing out of the dialog do to the edits? | Nothing is saved and nothing is put back: drafts stay in the form (Edit settings). The Phase 3.2 guard reverts ingestion inputs; here that would throw away a prompt edit the admin wants to fix and retry. The two guards run in a fixed order (6.3.1) |
| 3 | CONTEXT D-15 enforces `POST /api/config` and the prompt route. "Save Model Configuration" also writes RAG-affecting entries, and research F-5 finds five writers in all (finding 2). | The Config UI guards its three paths with the same dialog and handles a 409 `rag_gate_required` from any of them by opening it. Server enforcement of all five is the backend plans' job. The in-app admin settings page is an app surface outside this contract: in enforce mode it will receive the 409 and show it through its existing error path; a dialog there would be a separate UI contract |
| 4 | In warn mode, may the admin save before the result arrives? | Yes, with Save settings without result; the change is recorded as `skipped`. "Warn never blocks" (D-10) would otherwise mean waiting up to ten minutes, or longer while another check runs. Alternative: no early save in warn mode |
| 5 | Does warn mode ask for a reason? | No. A failed or missing result is recorded with the change; the reason field belongs to enforce mode only (D-15) |
| 6 | What does the dialog show of the change itself? | Names of the changed settings, never values (finding 5, D-16). A prompt or a model list does not fit a dialog, and the record holds names only |
| 7 | Can a click outside close the check dialog? | No. Escape and Edit settings close it. A stray click must not discard a typed reason or hide a result that decides a save |
| 8 | Colour of the save buttons that go against the check. | `btn-warning`, never `primary` and never `error`: the action is risky and reversible, not destructive |
| 9 | D-18's "uncalibrated" collides with the existing cell status of the same name (finding 8). | The derived mark is a separate badge, "Uncalibrated after a change", with the changed setting and date; the existing "Not calibrated" and "Stale" keep their words. The PSI case (D-24) is a fourth, milder mark, "Possibly stale", because those thresholds still apply |
| 10 | Where is the standing warning of D-18 visible? | In the Refusal calibration panel and as a row of the page banner (finding 9). One banner with at most two rows, instead of one banner per concern |
| 11 | When may the banner call the app? | Only when the loaded configuration has `RAG_MONITOR=true` (alerts row) or the setting check or the monitor on (thresholds row), so the page makes no new request with every switch off (D-21). A failed banner request shows nothing |
| 12 | Table or entries for alerts? | Entries. Alerts of different rules carry different evidence and are few (one per tenant, language and rule, D-25); each needs its sentence and its actions |
| 13 | Which alert actions confirm? | Acknowledge alert does not (it only moves the alert out of the banner). Resolve alert does, because it closes the alert for good |
| 14 | Charts? | None. The eight-week trend is a table; coverage is a table with a neutral share bar per cell (dataviz: more than seven classes is a table, ratios on named rows are a meter list). No categorical palette is introduced, so the palette validator has nothing to check |
| 15 | How are topic groups named? | By id only, with the fixed label "Not in any group" for the `novel` bucket (finding 13) |
| 16 | Judge status words. | `gating` is "Enforced", `report_only` is "Report only", `uncalibrated` is "Out of date"; the word "gating" is not shown. The panel is read-only and needs a status route like the refusal one (8.1) |
| 17 | Where do pilot users and the import live? | In a new Question sources panel with the weekly sample, not inside the Phase 5.1.1 Feedback loop card, whose contract is not available on this branch (finding 11). They are the three non-failure sources of the same queue |
| 18 | How is a pilot user named? | Entered as e-mail or user id, resolved by the server inside the workspace, listed as the masked e-mail or the id. Access groups wait for Phase 4.3 (CONTEXT deferred) |
| 19 | How does a file reach the import route? | Read in the browser and sent in JSON batches of at most 60 KB (finding 10), with client limits of 10 MB and 20,000 rows. Alternative: a dedicated multipart route on the config server; the view's states stay the same |
| 20 | Does the import show a preview? | No. Counts only, before and after (D-51). A preview would put unmasked questions on screen |
| 21 | Shape of the answer check. | Three radio groups with no default and its own Save answer check button, separate from the label form, so an expert can do one without the other and an untouched group is never read as a verdict |
| 22 | Golden-set version and stale status, the release gate, the list of overrides. | No Config UI view (finding 12). They stay in reports, GitHub and the weekly report. Alternative for a later phase: a "Setting changes" sub-view reading `GET /api/rag/admin/config-changes` |
| 23 | Where do the D-19 evaluation runs appear? | In Setting checks, Evaluation runs: EVAL-23 groups them with the pre-save check ("changes made outside CI") |
| 24 | Where do the six switches live? | In the Settings sub-view of the panel they control, moved from one hidden block, as the Ingestion panel does. None is RAG-affecting, so saving them starts no check |
| 25 | Is a trace id a link? | Only when the route supplies its URL. Otherwise ids are text with Copy trace ids. The UI does not build a Langfuse URL itself |
| 26 | Which workspace do the views use? | Question sources and Test set coverage follow `#workspace-selector`. Alerts list every tenant the admin administers and name the workspace per alert in multi-tenant mode |
| 27 | Panel language. | Follows the browser language (zh, it, otherwise en), like the sibling panels |
| 28 | The webhook URL is masked as a secret and cannot be cleared through an empty field (finding 16). | Keep it a secret (write-only field, state line "set" or "not set") and add Remove webhook with a confirmation. Alternative: add the name to the benign list in both secret checks and show the URL; rejected because webhook URLs often carry a token |

failures (04-UI-SPEC finding 12), so the new scripts wrap it and localize through `ingestLabel`. The header's two save
indicators and the page title use emoji; this phase changes only the indicator text while a save is held.
