# Phase 5.3 Plan 24: Refusal cells that stopped applying after a change Summary

**Derived "uncalibrated after a change" and "possibly stale" marks for refusal cells, a proposed-values CLI for the setting check, and a runtime rule that never applies a cell calibrated for another embedding model.**

## Accomplishments

- `pending.ts` computes, in one place, which calibrated cells a recorded change (reranker, embedding model, tokenizer) or an open or acknowledged `top_score_psi` alert made unreliable, and which cells stop applying under proposed values.
- `pending-cli.ts` prints `{ "uncalibrated_cells": [...] }` from two JSON env files. It prints cell keys only: config warnings are silenced while parsing, and errors name the option, never the content. Exit 0 on success, 2 on bad input.
- `refusalCalibrationStatus` takes an optional `pending` map. With it, every cell carries `pending` (null or `{ reason, since, changed_keys?, alert_id? }`) next to the stored `status` and `stale`, and the warnings gain `uncalibrated_after_change` and `possibly_stale_scores`. Without it the object is unchanged.
- `GET /api/rag/admin/refusal-calibration` reads change records of the last 400 days whose `changed_keys` overlap the pending categories, and open or acknowledged `top_score_psi` alerts, with the service-role client after the admin check. A missing table, read error, thrown read, missing admin client or malformed row answers exactly as before (200).
- `loadThresholdsFromData` skips a cell whose `embedding_model` is set and differs from the running model. The gate then takes its existing no-cell path. Cells without the field load as before, and the committed file loads the same cells. Nothing is logged per request.
- `eval/config/refusal-thresholds.json` is not written and no stored status changes.
