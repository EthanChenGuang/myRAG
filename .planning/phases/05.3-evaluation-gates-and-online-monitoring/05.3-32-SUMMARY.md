# Phase 5.3 Plan 32: Pilot users and the weekly representative sample Summary

**Admins name pilot users inside their own workspace (resolved and membership-checked in SQL, listed masked), and a reproducible weekly sample per tenant draws last week's masked questions into the review queue by cluster x language x channel, with capped pilot and drift_fill shares and stored inverse-inclusion weights.**

- **Duration:** about 110 min
- **Tasks:** 3
- **Files:** 8 created, 4 modified

## Accomplishments

- `0977_rag_pilot_user_resolve.sql`: `rag_pilot_user_resolve` (e-mail case-insensitive, or user id, accepted only inside the tenant) and `rag_pilot_users_list` (jsonb page, newest first, keyset on `(added_at, user_id)`). Both read `auth.users`, so they are SECURITY DEFINER with an empty search_path; revoked from PUBLIC, anon and authenticated, granted to service_role, and added to section 1 of `0410` so an upgraded database is locked too.
- `pilot-users.ts` and `/api/rag/admin/pilot-users`: tenant only from `admit()` (the `checkAdminOrOrgAdmin` admission of `organizationId`); strict Zod body `{ organizationId?, user }`, so a browser-sent `tenantKey` is a 400; answers carry the masked e-mail or the user id, `weight` and `cap_share` from `eval/config/monitor-alerts.json`, and `next_cursor`. Logs `[Monitor]` with counts only.
- `sample.ts`: pure `allocateStrata` and `planWeeklySample`, and `drawWeeklySample` (prerequisites, `refreshClusters`, last week's masked rows, cluster assignments of the current set, queued fingerprints, pilot ids, the latest drift report, then `rag_review_items_enqueue` per source with `mining_window` the week's Monday and reason `representative`). `sampleStatus` reads the latest sampled window's items and strata (by source and language, from the stratum code) and the current cluster set (count, refit date, novel count). `sampleTenants` lists tenants with masked rows in the week.
- `rag:monitor -- sample [--tenant <key>]` and `GET|POST /api/rag/admin/monitor/sample`: switch first (404 before the guard), then the admission; POST returns the status shape plus `run { written, week, added, excluded_queued, missing }`. CLI prints the tenant hash, the week and counts per source.

## Deviations from Plan

1. **[Rule 2 - Missing critical functionality] Migration 0977 added.** The plan lists no migration, but there was no server-side way to find a user by e-mail inside a tenant: `auth.admin.listUsers` pages through every user of the deployment and has no e-mail filter. A SQL resolver also keeps the membership check next to the data (brief rule: tenant resolved in SQL). 0976 was already taken on another branch, so 0977 was claimed (next free number in 0960-0979) and pushed first.
2. **[Rule 2] 0410 grant lock** gained the two definers (D-55); the phase53 function list gained kind `definer` (SECURITY DEFINER readers that are not triggers).
3. **[Rule 2] Same-week rerun tops up instead of doubling.** Items already in the week's window count against the cap, so a second run (CLI, schedule and Config UI can all start one) adds nothing once the week is full.
4. **[Interpretation] Pilot share base.** The pilot target is computed over the items left after drift_fill, not over the whole cap; the 40% cap still applies to the whole weekly cap. In the PGlite pilot plus drift test this gives 15 drift_fill, 10 pilot and 5 representative.
5. **Pure planner split out.** `planWeeklySample` is exported so the caps, weights and determinism are unit-tested without a database.
