# Phase 5.3 Plan 44: Monitoring panel (summary, Alerts, Settings)

Admins can now read monitoring alerts in the Config UI: what moved, where, against which baseline, and what settings changed in that window. They can acknowledge or resolve an alert and run the monitor on demand. Only ids, codes and counts are shown, and nothing is requested while `RAG_MONITOR` is off.

## Accomplishments

- **Chrome and summary.** `#rag-administration-monitor` sits after Judge calibration, leaving room for 05.3-42's Setting checks between the two. Its sub-tabs are Alerts (default), Test set coverage (an empty host for 05.3-45) and Settings, built with `gatesUiSubTabs`. Each tab carries `data-monitor-tab`, the attribute the banner's Review alerts button looks for. The summary is a `dl` of up to five rows: monitoring state, last run (a `<time>`, or "Not run yet"), retrieval log level (mono), groups checked, and groups with too little data. With the switch off it shows only "Daily monitoring: Off": no count, no request, no Run monitor now, and the off block in Alerts. Init is idempotent, bound to every `[data-tab="rag-administration"]` link, and runs on `DOMContentLoaded` when the tab is already active.
- **Alerts.**
  - **Toolbar:** the status filter (three radios in a `fieldset` with a hidden `legend`: active, resolved, all), a workspace `select` in multi-tenant mode built from the tenants seen in the answers, "Updated {time}", Refresh alerts and Run monitor now.
  - **Entries:** `ul.divide-y > li.py-4 > article[aria-labelledby]`, each with a severity badge, the measure as `h4` (unknown rule ids in `code`), a status badge (Acknowledged and Resolved carry their date), the actions and a meta line (language or "all", workspace in multi-tenant mode, day or widened window). Each entry has one measurement sentence by kind (`measure.rate`, `.distribution`, `.latency` with or without a budget, `.score`, `.drift` with the topic-group ids, else `measure.generic`) and the crossed conditions built from the band (ratio, points, z, drop).
  - **Paging and empty states:** pages of 20, then Load more alerts with the cursor. Empty: `alerts.empty.title` and body with the thin-group count, `alerts.empty.neverRan`, or `alerts.empty.filtered`.
  - **Actions:** Acknowledge alert asks no confirmation. It shows a spinner, replaces the entry in place, says `ack.done`, moves focus to the entry's Resolve alert button and refreshes the banner. Resolve alert goes through `gatesUiConfirm` with focus on Keep alert open; under the default filter the entry then leaves, focus moves to the next heading (or the status region) and the banner refreshes. A 404 or 409 reloads the list and says `error.alertGone`. Run monitor now shows a spinner with `run.running`, then `run.done` with the three counts, reloads the list and refreshes the banner; a failure says `run.failed`.
  - **Errors:** 401/403 put the sign-in alert in the Alerts view, and Settings stays usable. A 404 while the saved switch is on shows `error.switchedOffApp`. A retrieval log at `off` puts `needsLog` in the panel's alert host, with `RAG_RETRIEVAL_LOG` in `code`.
- **Evidence.** Inside a `details` ("Show evidence"), each block has an `h5` and its tables sit in focusable `role=region` scroll containers.
  - **Where it happened:** one table per dimension present (mode, channel, document type through `docTypeLabelForLocale`; `unknown` reads `breakdown.unknownType`).
  - **Other measures:** companions with measured and usual values, formatted per rule (rate, ms, score).
  - **Setting changes:** time, source, env names in `code`, the first 8 characters of each hash, and the record id. An unrecorded change carries the `record-change` command; no rows reads `changes.none`.
  - **Sample traces:** at most 10, in a `max-h-40` scrolling list, with Copy trace ids (one id per line, only when `navigator.clipboard.writeText` exists); no ids reads `traces.none`.
  - **Suggestion:** `recalibrate_refusal` shows the command and an Open refusal calibration button; `review_test_set` maps to `suggestion.sample_under_covered`.
  - **Delivery:** always three rows (banner, webhook, Langfuse), each delivered with a time, pending, or not set up. The webhook address is never shown.
- **Settings.** The `monitor` group moves once from `#rag-phase053-settings` and is localized through `data-rag-i18n`; the reveal button gets `settings.secret.reveal`. The state line "Webhook: set / not set" comes from `secretsSet` only. When a webhook is stored, the URL help reads `settings.webhook.set` and Remove webhook is shown. Remove webhook asks for confirmation (focus on Keep webhook), then sends `POST /api/config { clear: ['RAG_MONITOR_WEBHOOK_URL'] }` through the page's fetch, which adds the `X-Config-UI` header. On success the state turns to not set, the button leaves, and the status region says `webhook.removed`. A failure says `webhook.removeFailed` and keeps the state. `warn.monitorNeedsLog` and `warn.webhookHttps` are recomputed on `change` (and URL `input`); a non-https URL also gets `aria-invalid` and `input-error`.
- **Never rendered:** `dedup_key`, `acknowledged_by`/actor, full hashes, the override reason, raw breakdown or companions JSON, the webhook URL or secret. Builders read named fields only. Tests inject `<img onerror>` into the rule, kind, language, trace id, mode value, companion rule, change source, env name, hashes, record id and suggestion, and assert that no element is created.

## Deviations

- **One GREEN commit for three tasks:** `monitor.js` is one file built from one label table, so the three tasks landed together. Both RED commits came before any implementation and failed on assertions against a stub.
- **Label keys beyond UI-SPEC 12.4:** `count.item`, `status.acknowledged.plain` and `status.resolved.plain` (no date sent), `measure.latency.noBudget` (budget is null when no latency budget applies), `measure.generic.value` (no baseline), `measure.crossed.separator`, `value.ms`, `alerts.listLabel`, `settings.webhook.removeHint` (defined, not rendered). The banner keys stay in `GATES_UI_LABELS` (05.3-41), and Open refusal calibration reuses `banner.uncalAction`. The `cov.*`, `group.*` and `gap.*` keys are left to 05.3-45.
- **Rule and suggestion mapping:** the route's `top_score_psi` is labelled with `rule.top_score_shift`. `offline_online_gap` and `language_drop` have no UI-SPEC label, so they show as code with `measure.generic` (the unknown-rule path). The route's suggestion `review_test_set` reads `suggestion.sample_under_covered`.
- **Units:** a rate delta and its limit are fractions in the band and are shown as points (×100, one decimal), as in the UI-SPEC example ("26.0 points"). The ratio has one decimal, z and drop have two.
- **Run monitor now timeout:** 60 seconds instead of the 15-second default, because a run aggregates days and writes alerts (UI-SPEC 6.1 allows exceptions).
- **Full hashes:** the UI-SPEC typography rule puts the full hash in `title`, but section 11 rule 6 forbids rendering it. Rule 6 wins: only the first 8 characters are shown, with no `title`.
- **Resolved date:** the alert row has no `resolved_at`, so "Resolved {date}" uses `updated_at`.
- **Trace links:** the alert contract has no `trace_urls`, so trace ids are plain text (UI-SPEC decision 25).
