# Phase 5.3 Plan 22: Setting check runner, routes and the nightly overlay Summary

**The config server can now check a proposed setting change on the operator's machine before it is saved. It runs three layers, answers through asynchronous routes and caches each result by settings hash. A prompt that drops the refusal instruction ends the check `fail`.**

## Accomplishments

- `createRagGateRunner` builds the proposed values from the current `.env.local` plus the proposal (`config`, `prompt` or `models`). It then decides:
  - mode off: 200 `{ required: false, mode: 'off' }`, nothing spawned;
  - no RAG-affecting key changed: 200 `{ required: false }`, nothing spawned;
  - a check is running: 409 `rag_gate_busy` with `running_since`;
  - a finished check of the same hash is less than 30 minutes old and `force` is not set: 200 with that check and `cached: true`;
  - otherwise: 202 with a `check_id`, and the check runs in the background.
- The three layers:
  - **Deterministic** (always): `run-smoke.mts --env-overlay --gates eval/config/quality-gates.json --gates-mode report`, judged from `gate.json`. The O-1 baseline rule turns an already failing check into `report_only`/`baseline_failing`. `not_evaluated` comes from `overlay-report.json`.
  - **Live**: only with `RAG_CONFIG_GATE_LIVE=true` and an OpenRouter key. It answers a subset (every no-answer item plus ten answerable items per language, chosen by the sha256 of the item id) with `run-nightly.mts --generator live --env-overlay`, then scores the run and applies the absolute gate for the nightly tier.
  - **Real set**: up to three private sets under `eval/golden/private/domain/` are run against the app, folded into one layer.
- Uncalibrated refusal cells for the proposed values come from `pending-cli.ts`.
- A check ends `error` with `error_reason` `timeout` (the whole run is killed after 600 s), `crashed` or `toolchain_missing` (`node_modules/tsx` missing, `uv` not on PATH, or a spawn ENOENT). An error counts as not passed.
- Routes on the config server, behind the existing loopback and `x-config-ui` middleware:
  - `POST /api/config/rag-gate/check`, with the body validated by hand (400 `invalid_body`);
  - `GET .../check/latest`, matched before `:id`, with `saved_as`;
  - `GET .../check/:id`, which answers 404 for an unknown or malformed id.
  Responses carry only the fields of the UI-SPEC 8.1 check object.
- `run-nightly.mts --env-overlay <file>` validates and applies an overlay exactly as `run-smoke.mts` does and writes `overlay-report.json`.

## Deviations

- Any layer error makes the check `error`, and an invalid mode means enforce (see key decisions). Both are stricter than the plan text.
- A row missing from the measurement record fails closed instead of becoming `baseline_failing`.
- The real-set child also receives `RAG_EVAL_SECRET`, because the eval route needs it. Every child still gets at most one secret: the key of its own layer.
- The fake-spawn test helper resolves `--out` and the value files against the child's `cwd`. The runner passes repository-relative paths.
