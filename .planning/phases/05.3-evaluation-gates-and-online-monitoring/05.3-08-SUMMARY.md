# Phase 5.3 Plan 08: Monitor storage Summary

## Accomplishments

- `0962_rag_monitor_daily.sql`: `rag_monitor_daily` keyed by `(tenant_key, day, language, rag_mode, channel, doc_type)` with the D-22 counts, `judge_score_sums` (keys faithfulness and answer_relevance, numbers only), `top_score_hist` (keys rerank and similarity, each 22 non-negative numbers) and `latency_hist` (empty or 22 bins). Code columns are under CHECKs: language code (`und` for undetected, per the coordinator wording update), mode and channel lists with `unknown`, `doc_type` as a code without spaces. `rag_monitor_purge(p_keep_days integer DEFAULT 400)` deletes cells older than the window and rejects a window below 1 (22023).
- `0963_rag_monitor_alerts.sql`: `rag_monitor_alerts` with the D-22 columns plus `window_days`, `kind`, `observed_total`, `baseline_total`, `observed_rate`, `baseline_rate`, `acknowledged_at`/`_by`, `resolved_at`/`_by`, `created_at`, `updated_at`. CHECKs on rule (the 13 D-24/D-44 rule ids plus the reserved `language_drop`), kind, language (code or `all`), severity, status, `cardinality(sample_trace_ids) <= 10` with an id pattern, `suggestion` as a code, `dedup_key` as a code, and jsonpath CHECKs that keep every string and key in `band`, `breakdown`, `companions`, `config_changes` and `delivered` to a code without spaces. `rag_monitor_alert_upsert(jsonb)` checks the tenant key first (22023 for the other mode) and upserts on the partial unique index; `rag_monitor_alert_set_status(uuid, text, uuid)` allows open to acknowledged and open or acknowledged to resolved, false otherwise.
- `0964_rag_online_judge_scores.sql`: `rag_online_judge_scores` (primary key trace_id, metric, judge_id; score CHECK 0 to 1; metric CHECK) and `rag_online_judge_scores_record(jsonb) RETURNS TABLE (stored, dropped)`, which takes the tenant from `public.rag_retrieval_log` by trace id, ignores any payload tenant, drops and counts unknown traces, and is guarded by `to_regclass` so the file applies and the function stores nothing without the 5.1.1 tables. `rag_monitor_purge` is replaced to also delete scores older than the window. No cascade from the log.
- All three tables: RLS on, no policy, revoked from PUBLIC, anon and authenticated, granted to service_role. All four functions: `SECURITY INVOKER`, `SET search_path = ''`, schema-qualified, revoked from PUBLIC, anon and authenticated, granted to service_role (O-3). Files are idempotent and not folded (D-56).

## Deviations

1. Dedup uniqueness is `(tenant_key, dedup_key)` where status is not resolved, instead of `dedup_key` alone (security: no cross-tenant update through a reused key). The upsert's ON CONFLICT target follows it. Test: "two tenants keep separate alerts even when a dedup_key is reused".
2. The upsert returns NULL for a payload suppressed by a resolved alert of the same or a later day (the plan says it "returns the id"; there is no stored row to return for a suppressed alert). Callers (05.3-11, 05.3-27) must treat NULL as "nothing raised, nothing to deliver".
3. Added columns beyond the plan list: `observed_total`, `baseline_total`, `observed_rate`, `baseline_rate` (UI-SPEC 8.1 asks for counts and rates) and `resolved_by`. `delivered` merges on update (`old || new`) so a later day keeps earlier per-channel delivery records.
4. The monitor contract (`rag_sidecar/contracts/monitor.py`, plan 05.3-03) is not on this branch; column names follow D-22 and UI-SPEC 8.1. If 05.3-03 lands with different names, the aggregate/route plans map them.
5. Migration numbers 0962-0964 as planned; checked free on every origin branch before creation and pushed at once.
