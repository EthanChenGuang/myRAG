<objective>
Route chat and Config UI knowledge-base uploads through ingest() under unified (D-01, D-03, D-47 step 5), telling the two sources apart safely and accepting the per-file document type the picker sends (D-17).

Purpose: DATA-01 for the main upload path and the server side of DATA-03 (the picked type reaches ingest()).
Output: the switch in process-document, the Config UI proxy field, tests.

Runs after Phase 2 is complete (every 02-* plan has a SUMMARY).

Builds on the single-tenant-writes security fix (merged at af4dbe6): POST now returns 401 for a permanent upload with no session in single-tenant mode (503 when the lookup throws), keeps 401 without a session in multi-tenant mode, and refuses a non-member organization with 403, all before any parse or write; tests/rag/single-tenant-writes.test.ts covers it. Those checks protect both pipelines, so the unified branch goes after them and never moves a parse, ingest or write ahead of them. D-03 now locks the fixed legacy behaviour. The line numbers quoted in older notes predate the fix; re-read the route at HEAD.

Deviations from research (adopted): Open Question 4: both UIs post to the same route, so the Config UI proxy adds `upload_source=config_upload`, honoured only for verified admins; defaults (D-15) then resolve per source correctly.

Decision inside the plan (plan-check pass 3, W1 follow-up; coordinator decision): the config_upload decision uses checkAdmin from `src/lib/admin-route-auth.ts`, the guard of the config, MCP and RAG admin routes (a signed `admin_session` cookie of an admin_users user first, otherwise a Bearer token or the Supabase session through the plan 03-07 guard). The rule, precisely:
1. The single-tenant-writes fix's session lookup runs first and unchanged in both pipelines. A knowledge-base upload without a Supabase session gets its existing 401 (503 when the lookup throws) before anything else, whatever admin_session cookie or Authorization header it carries. The admin cookie never stands in for a missing session, so the 401-without-session rule holds for admins and non-admins alike, and tests/rag/single-tenant-writes.test.ts passes unchanged.
2. Only under unified, only after step 1 passed, and only when the form carries upload_source=config_upload, the route calls checkAdmin(request) once. Chat uploads never call it.
3. The upload is config_upload only when result.ok is true and result.userId equals the verified session user's id (both lowercased); the scope then comes from resolveAdminWorkspaceScope with that id and the form organization_id.
4. result.ok false with status 401 or 403, or ok for a different user (for example a valid cookie for admin A sent with the session of user B), gives chat_upload with the session scope, exactly as for a non-admin.
5. result.status 503 returns 503 with a JSON error and nothing parsed, ingested or stored, so an admin's upload never lands silently in a different workspace.
6. The legacy pipeline ignores upload_source and stays as HEAD has it.
Why the cookie does not replace the session: non-admins would still get 401 (a non-admin cannot hold a valid signed cookie, and admin_users is re-checked per request), but the change would alter the security fix's first check, which the pass-2 review locked as unchanged; it would make authentication depend on the pipeline switch, because legacy cannot accept it without changing legacy code; and the legacy user_id and plan 03-32's storage prefix would come from a non-session id. The Config UI admin signs in through the app's Settings, Admin tab, which requires the Supabase session and leaves it in the same browser, so the session normally travels with the cookie; when it does not, the upload gets the existing 401 and the Config UI shows its existing "sign in to the main myRAG app in this browser" message. checkAdmin does its own session lookup when no valid cookie is present, so a config_upload request may look the session up twice; chat uploads still look it up once.
