<objective>
Build the Config UI side of Phase 3 (D-17, D-18, D-31, D-36, D-45): the upload picker and document-list type change, and three panels (Document types, Quarantine, Embedding profiles) that call the admin routes with the admin session the Config UI already has.

Purpose: success criteria 1, 7 and 9 need admin actions in the Config UI (defaults, release, type change); D-31 requires an admin_users user, and the RAG admin routes (plans 03-37, 03-39, 03-40) accept the signed `admin_session` cookie that the Config UI's config and MCP panels already rely on.
Output: the /api/rag/ proxy through withAuthHeaders, a panel fetch helper, three panel scripts, upload and document-list changes, a test for the proxy, pure helpers and label parity.

Runs after Phase 2 is complete (every 02-* plan has a SUMMARY).

Decisions inside the plan:
- One auth path (plan-check pass 3, W1; orchestrator decision). The RAG panels use the admin session the Config UI already has, exactly as its config and MCP panels do since security fix S7: the browser sends the app's signed `admin_session` cookie (minted by the app's POST /api/admin/login, which the app's Settings, Admin tab calls, only for a verified Supabase user in admin_users) to config-server.js, whose existing withAuthHeaders helper forwards Cookie and Authorization unchanged to the app. The app's RAG admin routes check it with checkAdmin or requireAdminOrDeny from `src/lib/admin-route-auth.ts` (plans 03-37, 03-39, 03-40), with admin_users re-checked on every request. There is no second Supabase sign-in, no endpoint that serves the Supabase URL or anon key, and no token kept in browser storage, and none of them is kept as a fallback. The reach is the same as the existing config and MCP panels: the cookie reaches config-server.js when the app and the Config UI share a host, as in the local `npm run config` setup; otherwise the panels show the sign-in message.
- The existing admin and config routes are out of this plan's scope (D-31). This plan must not change those routes, loosen their checks, or remove any auth header their proxies forward.
- Panels are separate script files mounted from index.html (research constraint: large files carry regression risk), and plain DOM code matches the existing Config UI modules.

No model identifiers in code comments or commit messages; no keys or tokens in the browser, and Cookie and Authorization values are never logged.
