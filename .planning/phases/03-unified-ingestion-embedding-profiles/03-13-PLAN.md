TRACER for Phase 3: wire one Markdown upload through every layer the phase touches (scope, the D-02 stage runner, profile lookup, Markdown section chunking, embedding, the SQL writer, publish) to retrieval through the Phase 2 pipeline, and pin the duplicate, unreadable-file and writer-error branches of that one path.

Plan 03-13b then registers the other five stages (store_original, scan_injection, enrich, extract, images), adds deadline, state persistence and resume to the runner, adds the per-stage ingestion trace and the status and resume entry points, and exports everything from `@/lib/rag`.

Scope note (file count): the original tracer plan was split into 03-13 and 03-13b to fit the per-plan budget. This plan keeps 14 files because D-02 makes every stage its own module, so the one-path tracer has to touch six small stage modules plus the core once each; the trace, status, exports and the five remaining stages moved to 03-13b.

Design rules for every later Phase 3 plan (set here):
- Service clients a stage needs (object store, parser clients, captioner, invoice extractor, embedding targets) live in their own modules with a getter and test setters in the RagDeps style, so later plans add services without editing ingest/deps.ts; IngestDeps holds only db (the admin RpcClient, because writer RPCs are service_role only), embedDocuments, now, randomId and ingestEnv.
- IngestState is declared here with all slices later stages use (parse job, artifacts, doc-type detection, quarantine, invoice extraction, images cursor, embedding targets and gaps), so later plans fill their slice without changing the type.

Deviations from CONTEXT.md (research adjustments adopted):
- F-12 amends D-21: IngestInput carries one request deadline (default 50 s, Phase 3.1's worker passes a long one); this plan declares it and plan 03-13b makes every stage check the remaining time, not only parse polling.
- Research Pattern 1: embed and write run as one batched loop in one module (stages/embed-write.ts) so vectors never live outside the database; they still report separate `embed` and `write` stage outcomes (their spans arrive with plan 03-13b).
- The legacy profile embeds through the existing embedBatch path (D-13 Phase 2 re-home); multi-profile targets come with plan 03-28.
- Research Open Question 6 (resolved): for an `s:default` scope the writer never sends a user id, so single-tenant write paths stop passing fake user ids.
