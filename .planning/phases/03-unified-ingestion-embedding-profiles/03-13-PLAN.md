TRACER for Phase 3: wire one Markdown upload through every layer the phase touches (scope, the D-02 stage runner, profile lookup, Markdown section chunking, embedding, the SQL writer, publish) to retrieval through the Phase 2 pipeline, then complete the named stage list with deadline, state and resume, and the per-stage ingestion trace.

Design rules for every later Phase 3 plan (set here):
- Service clients a stage needs (object store, parser clients, captioner, invoice extractor, embedding targets) live in their own modules with a getter and test setters in the RagDeps style, so later plans add services without editing ingest/deps.ts; IngestDeps holds only db (the admin RpcClient, because writer RPCs are service_role only), embedDocuments, now, randomId and ingestEnv.
- IngestState is declared here with all slices later stages use (parse job, artifacts, doc-type detection, quarantine, invoice extraction, images cursor, embedding targets and gaps), so later plans fill their slice without changing the type.
- Stages switched off by default keep today's behaviour here: store_original records `no_object_store` until plan 03-17, scan_injection passes when RAG_INJECTION_SCAN=off and fails the run closed when it is set to quarantine before plan 03-20 lands, extract runs the profile extractors that exist and records `extractor_unavailable:<name>` for dates, financial and invoice until plans 03-18 and 03-29 add them, images passes when RAG_PDF_IMAGE_CHUNKS=false.

Deviations from CONTEXT.md (research adjustments adopted):
- F-12 amends D-21: ingest takes one request deadline (default 50 s, Phase 3.1's worker passes a long one) and every stage checks remaining time, not only parse polling.
- Research Pattern 1: embed and write run as one batched loop in one module (stages/embed-write.ts) so vectors never live outside the database; they still record separate `embed` and `write` spans.
- D-14 lists the `urls` extractor only for general and product_technical, but D-07 keeps the URL metadata unchanged and storeDocument extracts it for every document, so enrich writes URL metadata on every chunk (DATA-02 parity); the profile entry stays in the data.
- The legacy profile embeds through the existing embedBatch path (D-13 Phase 2 re-home); multi-profile targets come with plan 03-28.
