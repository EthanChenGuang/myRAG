Decision inside the plan (plan-check pass 3, W1; orchestrator decision): the three routes use the same admin guard as the config and MCP routes, checkAdmin or requireAdminOrDeny from `src/lib/admin-route-auth.ts` (security fix S7, merged). It wraps requireAdminRequest in `src/lib/admin-session.ts`: a valid signed `admin_session` cookie whose user is still in admin_users is admitted, and otherwise the plan 03-07 guard checks a Supabase session or Bearer token against admin_users; 401, 403 and 503 fail closed with the adminDenied bodies. This meets D-31 (the cookie is minted only for a verified Supabase user in admin_users, and admin_users is re-checked on every request) and lets the Config UI (plan 03-43) call these routes with the admin session it already has. requireAdminOrDeny returns only a response or null, so the list may use it; activate and rollback need the actor, so they call checkAdmin, return adminDenied(result.status) when result.ok is false, and pass result.userId (a lowercased UUID) as the actor otherwise.
