<objective>
Expose the doc-type defaults (D-15, D-17) and the admin type change (D-18) over authenticated routes, so the picker can be pre-selected and an admin can re-process a document as a new version with the right profile.

Purpose: DATA-03 (pre-selected default from DATA-10) and DATA-10 (admin defaults with precedence; type change re-processes through ingest() as a new version).
Output: migration 0317, the type-change operation, an admin document scope resolver, three routes, tests.

Runs after Phase 2 is complete (every 02-* plan has a SUMMARY).

Decision inside the plan: D-10 skips a same-identity, same-hash upload, which would also skip a type change; a dedicated force flag on the begin function is used only by changeDocumentType, so user uploads keep D-10 semantics.

Decision inside the plan (plan-check pass 3, W1; orchestrator decision): the admin routes use the same guard as the config and MCP routes, checkAdmin from `src/lib/admin-route-auth.ts` (security fix S7, merged). It wraps requireAdminRequest in `src/lib/admin-session.ts`: a valid signed `admin_session` cookie whose user is still in admin_users is admitted, and otherwise the plan 03-07 guard checks a Supabase session or Bearer token against admin_users; 401, 403 and 503 fail closed with the adminDenied bodies. This meets D-31 (the cookie is minted only for a verified Supabase user in admin_users, and admin_users is re-checked on every request) and lets the Config UI (plan 03-43) call these routes with the admin session it already has. Both admin routes need the admin's id (the membership check of resolveAdminWorkspaceScope and updated_by), so they call checkAdmin, return adminDenied(result.status) when result.ok is false, and use result.userId otherwise. The non-admin picker route keeps its session scope (resolveTenantScope) and is unchanged by this decision.
