<objective>
Give admins release and delete for quarantined documents (D-31) over fail-closed admin routes, with every action audited and release going through the publish swap.

Purpose: SEC-01's "can be released or deleted by an admin" and success criterion 7's "until an admin releases it"; the Config UI panel arrives in plan 03-43.
Output: migration 0316, the operations module exported from `@/lib/rag`, three admin routes, PGlite and route tests.

Runs after Phase 2 is complete (every 02-* plan has a SUMMARY).

Decision inside the plan: a quarantined new version never replaced the clean current one (plan 03-10's publish rule), so release performs the swap and delete only removes the quarantined version.

Admin scope (stated so the cross-tenant list is not mistaken for a leak): the admin guard checks admin_users on every request, so a RAG admin is a deployment admin who already manages every tenant's documents through the Config UI. The quarantine list therefore spans tenants and shows each item's tenant_key. Tenant owners and organization members are not RAG admins; they see their own document's quarantined status through plan 03-30's list, never the snippets or rule details.

Decision inside the plan (plan-check pass 3, W1; orchestrator decision): the three routes use the same admin guard as the config and MCP routes, checkAdmin or requireAdminOrDeny from `src/lib/admin-route-auth.ts` (security fix S7, merged). It wraps requireAdminRequest in `src/lib/admin-session.ts`: a valid signed `admin_session` cookie whose user is still in admin_users is admitted; a missing or invalid cookie falls through to the plan 03-07 guard (Supabase session or Bearer token, admin_users lookup); 401, 403 and 503 fail closed. This meets D-31's "Supabase session whose user is in admin_users": the app's POST /api/admin/login mints the cookie only for a verified Supabase user in admin_users, and admin_users is re-checked on every request. It is what lets the Config UI (plan 03-43) reach these routes with the admin session it already has. requireAdminOrDeny returns only a response or null; a handler that needs the admin's id (release and delete, for p_actor) calls checkAdmin, returns adminDenied(result.status) when result.ok is false, and uses result.userId (a lowercased UUID) otherwise.

No model identifiers in code comments or commit messages; snippets never logged.
