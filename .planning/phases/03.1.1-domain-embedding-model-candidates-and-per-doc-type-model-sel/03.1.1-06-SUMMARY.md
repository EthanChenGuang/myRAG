# Phase 3.1.1 Plan 06: Scoped re-embed Summary

**Migration 0442 makes the re-embed job fill a scoped profile only for its doc types. A scoped run starts only under a backfilling or active binding that covers its tenant scope, never changes the profile's status, cannot derive, and cannot be rolled back while an active binding depends on its vectors. Unscoped re-embed behaves exactly as before.**

## Accomplishments
- `rag_reembed_pick`, `rag_reembed_count`, `rag_reembed_remaining` and the total in `rag_reembed_start_run` carry `(p.doc_types IS NULL OR COALESCE(c.doc_type, d.doc_type) = ANY (p.doc_types))`. `next_batch`, `missing_batch` and `preview_batch` select through `pick`, so they are scoped too without being replaced.
- `rag_reembed_start_run` on a scoped profile: refuses `derive_unsupported` for a derive request, calls `rag_reembed_require_binding` (refuses `reembed_refused: no_backfilling_binding`) and skips the status change. `rag_reembed_resume_run` does the same; on the 0425 body a scoped resume would have failed on the 0440 scope trigger.
- `rag_reembed_derive_batch` refuses `derive_unsupported` for a scoped target.
- `rag_reembed_rollback_run` on a scoped profile refuses `reembed_refused: binding_active` while an active binding of the profile overlaps the run's tenant scope, and never changes the profile status.
- `rag_reembed_require_binding(text, text)`: invoker plpgsql helper, `SET search_path = ''`, revoked from PUBLIC, anon and authenticated, granted to service_role. It share-locks the binding row so it cannot be retired under a starting run. Activation already serialises with rollback through the `embedding_profiles` lock.
- `runReembed` returns `scope` and `profileStatus` (read after the run). Scoped runs skip the backfilling-set dual-write warning. `dryRunReembed` returns `scope` and refuses a derive for a scoped profile. `ReembedWriter.profileScope` reads `rag_list_embedding_profile_scopes`.
- The CLI prints `[Re-embed] scope: contract_legal` for a scoped dry run or run. Refusals now print `[Re-embed] refused: reembed_refused: no_backfilling_binding (55000)`.

## Deviations from Plan
1. **next_batch, missing_batch and preview_batch are not replaced.** They select only through `rag_reembed_pick`, so they need no change. The `ANY (p.doc_types)` grep therefore counts 5 (header, pick, count, remaining, start_run total), not the estimated ≥ 6.
2. **New helper `rag_reembed_require_binding`.** It keeps the coverage rule and the `no_backfilling_binding` refusal in one place for start and resume (the grep `== 1` holds). It is an invoker function, so the 0410 definer lock-down list does not need it. 0442 revokes it from PUBLIC, anon and authenticated itself.
3. **Rollback refusal prefix.** `reembed_refused: binding_active`, as the plan names it. The other rollback refusals keep `rollback_refused:`.
4. **CLI wording.** The CLI keeps its existing `[Re-embed]` prefix; the plan wrote `[Reembed]`. The refusal line now joins reason and detail with `: ` (it was a space), so it reads `refused: reembed_refused: no_backfilling_binding`. No existing test depended on the old form.
5. **`src/lib/rag/ingest/writer.ts`** gained `profileScope`; it is not in files_modified. The writer is the job's only door to the database.
6. **LEFT JOIN documents** in count, remaining and the start total. This keeps unscoped results identical even for a chunk with no document row. Pick keeps its 0425 inner join.
7. **Unscoped runs make no new RPC.** The Phase 3 test "the job makes no parser, sidecar, object-store or OpenAI call" allows only `rag_reembed_*` and `rag_list_embedding_profiles`. The runner reads the scope only when the run's profile is not `backfilling`.
8. **Tenant keys in tests.** The tests use `u:` keys from the fixtures; the plan's text said `o:A`. The tenant predicate is the same for both.

## Behaviour notes for later plans

- Until 03.1.1-08 writes binding targets at ingest, documents added during a scoped run are covered only by the run's sweep or a later top-up run. The binding gate's completeness check still enforces 100%.
