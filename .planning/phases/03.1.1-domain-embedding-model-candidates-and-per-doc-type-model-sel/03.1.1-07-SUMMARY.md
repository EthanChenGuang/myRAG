## Behaviour

- `RAG_DOMAIN_EMBEDDINGS=off` (default) or `RAG_EMBEDDING_PROFILES=off`: both reads return `[]` with no database call. Nothing in the app calls them yet (08 ingest and 09 query wire them), so no runtime path changes in this plan.
- On: registry read through the two list RPCs, cached at most 30 s, refreshed after every binding operation; an unreadable registry throws `ProfileUnavailableError`, never an empty list.
- A tenant row applies only to the exact tenant key; deployment rows apply to all tenants (T-3.1.1-07 tested with o:A vs o:B and a prefix-sharing key).
- CLI exit codes: 0 done, 1 refused (`[Embedding] refused: binding_refused: <code>`) or registry unreachable, 2 bad arguments. `bind-status ... active` exits 2 ("only activate-binding sets active"). The actor is `cli:<os user>` (T-3.1.1-07b). Output carries ids, statuses and counts only; the tests assert no chunk text and no key-shaped string.

## Deviations

1. [Rule 3 - blocking] The RAG boundary check (`doc-type-branching`) flagged `docType ===` comparisons. They were key lookups, so bindings are now indexed by doc type in the snapshot and matched by a `(doc type, tenant)` key; the checker was not changed.
2. Test fixture: the two-tenant corpus already holds contract_legal chunks, so the CLI test seeds binding vectors for every in-scope chunk.
3. Added `deriveBindingEvidence` unit tests (synthetic items never count as real, fixture-embedder comparisons never pass) beyond the plan's listed behaviours.
