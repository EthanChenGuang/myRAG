# Phase 3.1.1 Plan 10: Eval binding overrides and cache bypass

**The eval route can now run any binding arm and the control leg through `embedding_bindings` / `domain_control_leg`, recorded in the run manifest; an override that cannot take effect fails the request instead of measuring the global profile, and override turns never touch the semantic cache.**

## Accomplishments

- `route.ts`: `toBindingOverrides` checks the binding map keys against `BINDING_DOC_TYPES` (unknown doc type or more than 6 entries → 400 `{ success: false, error, details }`), then spreads `embeddingBindings` (non-empty map) and `domainControlLeg` next to `embeddingProfile`. Auth (`checkEvalAccess`) is unchanged and runs first.
- `pipeline.ts` (`dispatchRetrieval`): an eval request carrying either field returns `error/domain_embeddings_disabled` when no binding leg can run (switch off, legacy pipeline, non-v2 path, defaulted v2 falling back to legacy).
- `v2/pipeline.ts` + `binding-legs.ts`: `unresolvedEvalOverride(plan)`; an eval override leg whose profile cannot be resolved returns `error/embedding_profile_mismatch` (or `embedding_profile_unavailable`) with an `embed` stage record `detail: unknown_profile:<doc_type>`, before any embed or search call. `BindingLegPlan.resolveKind` carries the mismatch kind.
- `run-eval.mts`: `EvalRequestOptions.embedding_bindings` / `domain_control_leg` (typed from the generated `RagRunRequest` options); sent unchanged; `normalizedOptions` (manifest `request_options` and the run config hash) includes them only when set.
- `cache/bypass.ts`: `CacheRetrievalOptions` gains both fields; `retrievalOptionsAreDefault` returns false when either is present. The cache key already follows bindings through the retrieval config hash from plan 09; the new test proves it at key level.
- Acceptance greps: `embeddingBindings` in route.ts = 2, in bypass.ts = 2.

## Behaviour changes

- None for requests without the two fields: chat, embed, voice, strict "information not available", webSearch with Exa, `source_images` and `{{context}}` are unchanged; the eval route answers as before and existing run manifests and `run_config_hash` values are unchanged (fields omitted when unset).
- Eval requests with the fields: mapped to retrieval; invalid keys → 400; an override that cannot take effect → 500 `{ error: 'retrieval failed', reason: 'embedding_profile_mismatch' | 'embedding_profile_unavailable' | 'domain_embeddings_disabled' }`.
- Semantic cache: override turns bypass with `retrieval_options`.

## Deviations from Plan

- **[Rule 2 – correctness] No silent fallback** needed code outside the listed files: `src/lib/rag/pipeline.ts`, `src/lib/rag/v2/pipeline.ts`, `src/lib/rag/v2/stages/binding-legs.ts`. Plan 09 degraded an unresolvable override leg and ignored overrides with the switch off; either way an eval arm would have measured the global profile, which the must-have forbids. Tests went into the existing `tests/rag/v2/binding-legs-pipeline.test.ts` (its harness has the registry fakes).
- **Error trace shape:** `StageRecord.reason` only allows `failed | timeout | aborted`, so the stage record says `reason: failed` with `detail: unknown_profile:<doc_type>`; the result reason is `embedding_profile_mismatch`, as for the existing single-profile override.
- **Route key validation** is in the route, not the schema: the generated Zod drops the Pydantic `dict[DocType, …]` key enum and `max_length=6`. Regenerating contracts was out of scope.
- **Manifest test** went into `tests/eval-harness.test.ts` (it has the live-server fake for `runEval`), not the route test file.
- **Semantic cache stage not on trunk**: the third Task 2 case is a key-level assertion (fake store keyed by `computeCacheKeyHash`). The stage-level case is owed by 06-32 when the `semantic_cache` stage lands.
