# Phase 3.1.1 Plan 02: Binding contracts Summary

**The binding activation evidence, the per-doc-type comparison output and the two eval overrides each have one Pydantic definition. The Zod side is generated from it, and every committed config hash stays the same while no binding is used.**

## Accomplishments
- `BindingActivationEvidence` carries the fields that plan 05's SQL gate reads: `binding_id`, `target_profile`, `doc_type`, `tenant_key`, `baseline_global_profile`, `baseline_binding_profile`, `gate_passed`, `doc_type_slice {n, real_n, passed, by_language}`, `other_slices_passed`, `backfill_run_id`, `recorded_at`. `real_n > n` is rejected.
- `BindingComparison` (D-22, D-23) holds the baseline and control arms, the candidate results, the provenance counts, the hashes (corpus, golden, noise, retrieval params, catalog version), the re-embed run ids, the fixture flag, the verdict and notes.
- `RagRunOptions.embedding_bindings` (doc type → profile id, at most 6 entries) and `domain_control_leg`; both default to None.
- `RetrievalLegWeights.domain`: optional and must be greater than 0. A None value is left out of `model_dump`, out of the JSON schema default and out of the Zod default, so the committed `retrieval-params.json` hash and the TS v2 config hash are unchanged.

## Deviations from Plan
1. **[Additive] `BindingComparisonHashes` nested model.** The plan lists `hashes` with five named fields. A sixth, nested model gives that object the same extra=forbid typing. It is exported from `contracts/__init__.py` but is not a top-level schema.
2. **[Additive] `report_path` on `BindingArm` and `BindingCandidateResult`.** D-23 requires the arms' report paths in the comparison output.
3. **[Rule 2 – correctness] Schema hook on `domain`.** A plain `default=None` generated `.default(null)` in Zod. TS-parsed params would then contain `leg_weights.domain: null`, which changes `computeRetrievalConfigHash`. The field's JSON schema now has no default and no null branch, and `tests/rag/v2/leg-weights-domain.test.ts` failed on the old generated file before the fix.
4. **[Scope] JSON schemas and samples committed in Task 1.** The plan names only `contracts.generated.ts` for Task 2. The regenerated `rag-sidecar/schemas/*.json` and `tests/fixtures/contracts/samples.json` went into Task 1 so the sidecar drift test (`test_committed_samples_match_a_fresh_build`) is green at that commit.
