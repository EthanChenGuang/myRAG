# Phase 3.1.1 Plan 05: Binding gate Summary

**Migration 0441 adds the binding lifecycle as service-role-only SQL functions. A binding can be created, staged and given evidence. It activates only when its scope is fully indexed in the profile's model and the evidence passes on at least 30 real items. Rollback and deactivate are pointer flips that delete no vector. Every check counts only the binding's own tenant.**

## Accomplishments
- `rag_list_embedding_bindings()` returns id, doc_type, tenant_key, profile_id, model, doc_types, status, previous_binding_id, has_evidence, baseline_global_profile, activated_at, activated_by, created_at and created_by. `rag_list_embedding_profile_scopes()` returns (id, doc_types) for every profile.
- `rag_create_embedding_binding` returns `(binding_id, binding_status, created)`. It returns the existing row for the same triple. The 0440 guard still refuses an unscoped or out-of-scope profile and a tenant key of the other mode.
- `rag_set_embedding_binding_status` returns `(binding_id, binding_status)`. It accepts available, backfilling and retired. It refuses `active` (`use_activation_gate`) and any change to an active row (`binding_is_active`). A unique-index violation becomes `backfilling_exists`.
- `rag_record_binding_evidence` returns `(binding_id, recorded_at)`. The evidence must name this binding's id, profile, doc type and tenant (`evidence_mismatch`). An active row takes no evidence.
- `rag_activate_embedding_binding` returns `(activated_binding, previous_binding)`. It runs the D-09 checks in the order of the Phase 3 gate. On success, the previous active binding for the key becomes `available` and is stored in `previous_binding_id`.
- `rag_rollback_embedding_binding` returns `(restored_binding, rolled_back_binding)`. `rag_deactivate_embedding_binding` returns `(deactivated_binding)`.
- All eight functions are SECURITY DEFINER, `SET search_path = ''`, schema-qualified, revoked from PUBLIC, anon and authenticated, and granted to service_role. The six mutating functions take `SHARE ROW EXCLUSIVE` on `embedding_profile_bindings`. Activate and rollback also set `statement_timeout = '120s'`.

## Deviations from Plan
1. **[Rule 3, blocking] 0410 lock-down entries.** `search-rpc-grants-pglite` simulates an upgraded database with open grants and requires 0410 to close every definer function. All eight signatures were added to 0410 section 1, guarded by `to_regprocedure`. Plan 04 did the same for the bindings guard.
2. **The list functions take no table lock.** They are `STABLE`, and PostgreSQL does not allow `LOCK TABLE` in a non-volatile function. They are single-statement reads under one snapshot. The truth says every function takes the lock; the six mutating functions do.
3. **Codes beyond the truths.** `unknown_binding`, `invalid_status`, `invalid_evidence`, `already_active`, `binding_retired`, and `evidence_mismatch` at activation time (a re-check, in case `eval_evidence` was written directly). Each has a test.
4. **REVOKE/GRANT as one statement per group.** The acceptance grep `FUNCTION public.rag_record_binding_evidence == 1` also counts per-function REVOKE/GRANT lines. 0441 therefore uses one REVOKE and one GRANT with a comma-separated list for each half. The textual ACL simulator models this form.
5. **Concurrency test.** PGlite has a single connection, so two truly concurrent activations cannot run. Serialisation comes from the table lock, and a test asserts that every mutating function takes it. The test also checks the sequential case: a second binding whose evidence names no binding baseline is refused with `eval_binding_baseline_mismatch` once the first is active. Only one active row ever exists per key.
6. **Extra test: idempotent re-apply.** Applying 0441 a second time leaves every signature, body and ACL unchanged.
