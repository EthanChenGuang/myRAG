## Summary

The Phase 3 machinery is almost sufficient. Three gaps stop it from serving domain models per doc type:

1. **One model per provider.** `voyage.ts:75` hardcodes `model: VOYAGE_MODEL_ID` and always sends `output_dimension`; the registry (`registry.ts:150-166`) is keyed by provider id only; the startup check (`active-profile.ts:290-300`), the ingest guard (`embed-write.ts:82-91`) and the query guard (`query-embedding.ts:33-41`) compare `provider.model` with `profile.model`, so a `voyage-law-2` profile would fail as `model_mismatch` everywhere. Prices are per provider (`prices.ts:9-13`).
2. **One active profile, all chunks.** `embedding_profiles_single_active` (0307:27) allows one active row; completeness (0309:41-49), dual-write (`embedding-targets.ts:28-57`) and re-embed selection (0315:12-58, 509-535) are over **all** current chunks. There is no notion of a profile covering one doc type.
3. **One dense leg per variant.** `runSearchStages` (`v2/stages/search.ts:94-118`) searches exactly one profile per variant.

What already fits: `hybrid_search_chunks` takes any `p_profile_id` plus `p_doc_types` and does not check that the profile is active (0407:95-101, 141-147), so a doc-type-restricted dense leg over a second profile is a plain backend call. `rrf()` fuses any number of weighted lists (`fusion/rrf.ts:15-49`). The comparison harness (`eval/harness/run-profile-compare.mts`) and its scorer already compute per-doc-type slices (`EvalReport.by_doc_type`, `contracts/report.py:69`; `eval/src/rag_eval/metrics.py:185`).

**Primary recommendation:** additive, gated **bindings** from `(doc_type, tenant?)` to a **scoped** profile; one extra RRF dense leg per active binding; a binding-specific gate that reuses the Phase 3 evidence shape; a comparison with a control arm. Keep the Phase 3 global gate function untouched.

Voyage's own pages state that `voyage-3-large` (and so the 4 series) outperform its domain-specific models on legal and financial benchmarks; Voyage publishes no head-to-head table, and no independent evaluation was found. The `voyage-law-2` post reports NDCG@10 on three non-English legal sets (Chinese LeCaRDv2 72.75 vs 57.20 for OpenAI v3 large; German LegalQuAD 67.47 vs 57.47; GerDaLIR 44.91 vs 32.77). Nothing covers Italian. **Implication:** domain models may be weaker than `voyage-4-large` on our zh/it documents; only our own per-language comparison can tell, which is why D-22 requires every language sub-slice of the bound type not to regress.

Vendor API facts that change code: `output_dimension` is listed only for flexible-dimension models (law-2/finance-2 are 1024 only; behaviour when it is sent is undocumented → do not send it, D-02); `truncation` defaults to `true` (we keep `false` so oversized chunks fail loudly); max list length 1000 (our batches stay at 128); `input_type` prepends a retrieval prompt for `query`/`document`.

### Practice
- Multiple vector indexes per document class with rank fusion is standard (RRF does not need comparable scores; Cormack et al. 2009). Comparing raw cosine scores across models is invalid — hence D-20.
- Filtered HNSW over a small subset under-fills without iterative scan; `hybrid_search_chunks` already supports `p_iterative_scan` and the exact-scan cutoff (RET-10). A binding leg is a selective filter by construction (one doc type; and the partial index holds only that type), so its partial index is small and well-filled — less of a concern than a doc-type filter on the global index.
- Leaderboards (MTEB/RTEB) are aggregate and English-heavy; decisions must use the in-domain, in-language eval (user constraint).

## Architecture Patterns

### Pattern 1: Scoped profile + binding (data)
`embedding_profiles.doc_types` scopes where vectors may exist; `embedding_profile_bindings` says which scoped profile serves which (doc_type, tenant). The trigger on `embedding_profiles` (scoped ⇒ status ∈ {available, retired}) and the guard on `chunk_embeddings` (scoped ⇒ chunk type in scope) make invariants hold whatever TS does.

### Pattern 2: Binding targets at ingest
`resolveEmbeddingTargets({ docType, tenantKey })` → existing targets + binding targets (`active` or `backfilling` bindings for that type, tenant row and deployment row). Non-fatal failures as for `backfilling`.

### Pattern 3: Binding legs at query time
Embed (original text) per binding profile in parallel with the global embed; one backend call each with `p_doc_types=[type]`, `p_lexical_limit=0`; similarity nulled; list id `dense_domain:<type>`; weight `leg_weights.domain`; per-leg timeout; failures degrade.

### Pattern 4: Gate
Mirror of 0309 scoped to (doc_type, tenant): completeness, model consistency, evidence (target, baselines, gate, real-item slice, per-language passes, other slices, run, staleness), flip with previous pointer. Rollback/deactivate are pointer flips. Stale bindings (evidence baseline ≠ global active) are skipped at query time.

## Common Pitfalls
1. **Model mismatch everywhere** if any call site keeps `getEmbeddingProvider(profile.provider)`. Mitigation: plan 01 changes all six and adds a grep acceptance (`getEmbeddingProvider(profile.provider)` count 0).
2. **Sending `output_dimension` to a fixed-dimension model.** Undocumented behaviour; omit it (catalog flag).
3. **Token limits per model.** law-2 max input 16K (vs 32K): the catalog's `maxInputTokens` feeds the CHK-04 child-size validation and the provider; 120K per request is above our 100K estimated cap.
4. **Cross-model score comparison** in the similarity floor or calibration (D-20).
5. **Global dual-write picking up a scoped profile** via `backfilling` status (trigger refuses; re-embed start for scoped profiles does not move profile status).
6. **Re-embed over all chunks** for a scoped profile (0442 scope predicate; tests assert only in-scope chunks are picked and counted).
7. **Stale bindings after a global flip** (D-12).
8. **Fixture evidence mistaken for proof** (D-11; `FAKE_EMBEDDER_NOTE`-style note in every fixture comparison).
9. **HNSW index build lock.** `CREATE INDEX` on `chunk_embeddings` inside a migration transaction takes a SHARE lock and scans the table; on a large live table it blocks writes while it runs. The partial predicate means few rows are indexed but the scan is full. Live checkpoint: apply in a quiet window, or run the three `CREATE INDEX CONCURRENTLY` statements outside the transaction first (the migration's `IF NOT EXISTS` then skips them).
10. **Migration number collisions** with sibling phases planned in the same run (D-28).
