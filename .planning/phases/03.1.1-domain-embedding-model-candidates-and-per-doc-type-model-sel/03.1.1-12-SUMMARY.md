# Phase 3.1.1 Plan 12: Binding comparison harness Summary

The per-doc-type comparison now runs from one command, with baseline, control and candidate arms. The decision rule is Python code that writes a contract-validated `BindingComparison`. The domain pack has a recorded baseline. A test shows that fixture evidence cannot activate a binding.

## Accomplishments
- `rag_eval.binding_compare.compare(baseline, control, candidates, noise, doc_type, ...)` implements D-22:
  - A candidate is recommended only when, on the doc-type slice, Recall@10 and MRR beat both baseline and control by more than the noise band (the floor, because each arm is a single run).
  - It must also have no language sub-slice regression and no cross-lingual pair regression within the doc type.
  - It must have no regression on overall, on another doc type, on a whole-report language or on a whole-report pair, and no worse correct or false refusal rate.
  - Ties go to the larger gain, then the lower catalog price, then the lower profile id.
- Doc-type membership comes from the item's evidence doc type, overridden by the golden `doc_type:<type>` tag. No-answer domain items have no evidence document, so the tag is the only way to place them.
- Languages and pairs come from the items. No language code appears in the rule (a test greps for it).
- `provenance_counts` counts the items in the doc-type slice. Fixture runs, and slices with no production or human items, get `BINDING_FIXTURE_NOTE`.
- `BindingCandidateResult` gained `supported_languages` (from the catalog) and `undeclared_languages`. An undeclared language is reported in the result and in a note; it does not block a recommendation on its own.
- CLI: `python -m rag_eval.binding_compare_cli --doc-type T --baseline-profile P --baseline R --control R --candidate id=R... --golden G --noise N --reembed-run id=uuid... --hashes-json H --catalog-json C [--fixture-embedder] [--note ...] --out O`. Exit codes: 0 written, 2 invalid.
- Harness: `npx tsx eval/harness/run-binding-compare.mts --doc-type <type> [--candidates a,b] [--golden F] [--out D] [--live [--confirm-cost]]`. It runs these steps:
  1. Ingests the main corpus, the typed and parse fixtures, and the domain pack. Each domain document gets the doc type from its manifest, which must agree with its fixture-meta line.
  2. Per candidate: `rag_create_embedding_binding`, then `backfilling`, then a scoped `runReembed`, then a check that no vector was written out of scope, then `available`.
  3. Runs the baseline arm (`{}`), the control arm (`domain_control_leg`) and the candidate arms (`embedding_bindings`) under `RAG_PIPELINE=v2`, `RAG_EMBEDDING_PROFILES=on` and `RAG_DOMAIN_EMBEDDINGS=on`.
  4. Scores every arm with `rag_eval.runner score --rank-source candidates` and calls the CLI. The hashes cover corpus plus domain pack, golden, noise, retrieval-params file and `EMBEDDING_CATALOG_VERSION`.
- Exit codes: 0 written, 2 usage, 3 failure, 4 cost not confirmed.
- Fake mode: fixture embedders are registered as `voyage:<model>` for every Voyage model in the catalog. Process env carries only placeholder keys, and `.env.local` is never loaded.
- `--live`: loads `.env.local` and checks that `VOYAGE_API_KEY` is present without printing it. It prints the dry-run chunks, tokens and USD for each candidate, then exits 4 unless `--confirm-cost` is given. This path was checked with a placeholder key: exit 4, and the key never appeared in the output.
- Baseline: `--record-baseline <file> [--runs 3]` runs `--baseline-only` three times in separate processes, each on the domain golden. `rag_eval.baseline record-reports` (new) then writes `eval/baselines/fixture-domain-baseline.json`: 3 runs, spread 0, golden hash equal to `sha256(eval/fixtures/domain/golden.jsonl)`, and a corpus hash that covers the domain pack.
- `tests/rag-db/binding-compare-evidence.test.mts` reads `eval/out/p3.1.1-12/comparison.json`, or runs the harness into a temp dir when that file is missing (about 50 s, as in CI). It checks three things:
  - The file validates as a fixture comparison with 0 real items.
  - `record-binding-evidence` accepts it, and `activate-binding` is refused.
  - The same file, forged with `fixture_embedder=false` and a passing verdict, is recorded and then refused with `binding_refused: eval_insufficient_real_items`.

## Deviations from Plan
1. **The unmodified fixture comparison is refused with `eval_failed`, not `eval_insufficient_real_items`.** Plan 07's `deriveBindingEvidence` sets `gate_passed=false` for any fixture-embedder comparison, and 0441 checks `gate_passed` before the real-item count. Changing the order of an existing gate migration for a message is not worth it; both refusals block activation. The test also forges the same file (fixture flag off, verdict passing) and asserts `eval_insufficient_real_items`. That proves the provenance threshold (T-3.1.1-11) holds even against tampered evidence.
2. **Contract change** (`rag-sidecar/.../profiles.py`, generated schemas, Zod, samples): two defaulted list fields on `BindingCandidateResult`, so that the must-have "each candidate's row lists supportedLanguages and marks undeclared slices" holds. `npm run gen:schemas` leaves no diff.
3. **Files outside files_modified:**
   - `src/lib/rag/embeddings/catalog.ts`: new `EMBEDDING_CATALOG_VERSION = 1`. The contract requires a catalog version and none existed.
   - `eval/src/rag_eval/baseline.py`: new `record-reports` subcommand. The existing `record` only drives run-smoke, which cannot run the v2 binding arms.
   - `eval/tests/test_baseline.py`: tests for the new subcommand.
4. **Eval-only fixture floor.** The ingest fixture has no calibrated similarity floor; the committed fixture calibration covers prechunked mode only. Under v2 the legacy 0.65 floor refused 88% of answerable items, and `RAG_DISABLED_STAGES=refusal` does not help because v2 applies the floor anyway. Fake runs therefore call `setEvalScoreCalibration({context_threshold: 0.01})`, the eval profile's existing seam, which never applies outside eval. A note in the comparison records this. Fake-run refusal rates are not meaningful. Live runs keep the profile's own calibration.
5. **Arms are scored on the threshold-free candidate list** (`--rank-source candidates`). The floor reads only the global similarity (D-20), so this is what isolates the leg effect.
6. **table_split items are left out of the default merged golden.** They need the isolated table_split tenants, which this one-database build does not load.

## Findings from the fixture run (wiring proof only)
- `contract_legal`: baseline doc-slice R@10 0.53. The control arm and both candidates scored 0.33, and every arm other than baseline lowered overall R@10 from 0.83 to about 0.39. Verdict: not recommended, with other-slice regressions on every doc type and language.
- Cause: with leg weight 1.0, RRF interleaves the doc-type-filtered leg with the global leg for every query. On non-domain queries, about half of the top 10 goes to domain chunks. The decision rule correctly refuses this.
- Live evidence will probably show the same displacement until `leg_weights.domain` is tuned (Phase 4.1 sweep) or a Phase 6 router runs the leg only for matching queries. Worth knowing before the 03.1.1-15 live run.
- `voyage-law-2-1024` gets `undeclared_languages: ["it"]`, as the catalog says.
