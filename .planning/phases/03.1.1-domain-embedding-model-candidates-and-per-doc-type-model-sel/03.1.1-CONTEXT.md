<domain>
## Phase Boundary

Phase 3 made the embedding model a switchable, gated, rollback-able **deployment-wide** pointer (one active profile, EMB-01..05). This phase adds two things on top of that machinery, without changing it:

1. **Domain model candidates.** Voyage `voyage-law-2` and `voyage-finance-2` (and a scoped `voyage-4-large` control) become embedding profiles, served by the existing Voyage provider made model-aware, with prices, input limits and fixed dimensions from the official model table.
2. **Per-document-type selection ("bindings").** A document type (deployment-wide, or overridden for one tenant) can be *bound* to a scoped domain profile. Chunks of that type are embedded into that profile **in addition to** the global active profile, and v2 retrieval adds one dense leg per active binding, fused with RRF. A binding is activated only through a gate (complete, consistent, proven by evidence on our own test set) and rolled back by a pointer flip; removing a binding always returns exactly to global-only behaviour.
3. **A reproducible comparison** on our own golden set, per doc type, per language and per cross-lingual pair, with a control arm, whose output is the evidence the gate reads. Public leaderboards are a reference only.

With `RAG_DOMAIN_EMBEDDINGS=off` (default), or with no active binding, behaviour is byte-identical to today: no extra provider call, no extra index scan, no extra dual-write.

**In scope:** model catalog and model-aware provider registry; scoped profiles and their HNSW indexes; the bindings table and its gate/rollback SQL; doc-type-scoped re-embed; binding-aware ingest dual-write; binding legs in the v2 search stage; eval overrides and the comparison harness; a synthetic domain fixture pack; CLI, admin routes and a Config UI panel; env switches in all five locations; live verification as a human checkpoint.

**Out of scope (other phases):**
- **Phase 3:** the global pointer, its gate (`rag_activate_embedding_profile`), dual-write for backfilling profiles, the re-embed job itself. Reused, not redefined; the global gate function is not edited.
- **Phase 4 / 4.1:** hybrid search SQL (`hybrid_search_chunks` is called as-is), reranking, refusal calibration, the sweep tool (it may later sweep `leg_weights.domain`).
- **Phase 5.1.1:** the real domain test set (production/human golden items). This phase consumes it for live activation; it does not build it.
- **Phase 6:** a query router that decides per query whether a domain leg is worth running; this phase runs active binding legs for every v2 query in scope (bounded by `RAG_DOMAIN_EMBEDDING_MAX_LEGS`).
- **Phase 6.1:** fine-tuned embedding models. A fine-tuned model becomes a profile + binding through exactly this phase's machinery.
- **Phase 7:** external backends; their sync must carry binding profiles (recorded as a Phase 7 note, not done here).
- New provider adapters (Cohere `embed-v4.0`, Gemini `gemini-embedding-2`): researched, deferred (see Deferred Ideas).

</domain>

<decisions>
## Implementation Decisions

### Model catalog and providers

- **D-01:** A single model catalog (`src/lib/rag/embeddings/catalog.ts`) lists every model the app may embed with: provider, model id, native dims, supported dims, whether `output_dimension` may be sent, max input tokens, max tokens per request, input types, list price per million tokens and free-token note, languages note, domain. It is the only place model facts live; `prices.ts`, `registry.ts` `KNOWN_DIMS` and the Voyage provider read it. Values come from the official docs on 2026-11-24 (RESEARCH §External): `voyage-law-2` 1024 fixed, 16,000 input tokens, 120K tokens/request, $0.12/M; `voyage-finance-2` 1024 fixed, 32,000 input tokens, 120K tokens/request, $0.12/M; `voyage-4-large` 256/512/1024/2048, 32,000, 120K, $0.12/M.
- **D-02:** Providers become model-aware. `createVoyageProvider({ model })` sends `model`, sends `output_dimension` only when the catalog says the model has more than one supported dimension, keeps `truncation: false` and `input_type` `document`/`query`. The registry resolves a provider by `(provider, model)`; `getEmbeddingProvider(id)` keeps returning the default model so every Phase 3 caller and test fake keeps working. The six call sites that pass `profile.provider` (deps.ts, embed-write.ts, rechunk/run.ts, reembed/run.ts, query-embedding.ts, active-profile.ts) switch to `getEmbeddingProviderFor(profile.provider, profile.model)`. `canonicalModelId` learns the new ids. No new provider id and no new API key: Voyage domain models use `VOYAGE_API_KEY`.
- **D-03:** Seeded candidates (migration 0440): `voyage-law-2-1024` scoped to `{contract_legal}`; `voyage-finance-2-1024` scoped to `{financial_report, invoice_receipt}`; `voyage-4-large-1024-domain` scoped to `{contract_legal, financial_report, invoice_receipt}` as the general multilingual arm. Each gets its own partial HNSW index (`halfvec(1024)`, `m=64, ef_construction=200`). `voyage-code-4` is not seeded: none of the six doc types is source code (PO may override, Q-02). Every seeded row is `available`; nothing is activated by a migration.
- **D-04:** Adding any further candidate later is a migration (profile row + partial index), as in P3 D-35. A dynamic "register profile" SQL function that issues `CREATE INDEX` is rejected: index DDL stays reviewed.

### Scoped profiles and bindings (data model)

- **D-05:** `embedding_profiles` gains `doc_types text[]` (NULL = unscoped, today's meaning). A scoped profile holds vectors only for chunks whose `COALESCE(c.doc_type, d.doc_type)` is in its scope. A trigger refuses `status = 'active'` or `'backfilling'` on a scoped profile, so the global pointer and Phase 3 global dual-write can never pick one up; the Phase 3 gate function is not edited. The `chunk_embeddings` guard refuses a scoped profile's vector for a chunk outside the scope.
- **D-06:** Bindings live in a new table `embedding_profile_bindings` (`id uuid`, `doc_type`, `tenant_key` NULL = deployment-wide, `profile_id` → `embedding_profiles`, `status` in `backfilling | active | available | retired`, `previous_binding_id`, `eval_evidence jsonb`, `activated_at`, `activated_by`, `created_at`, `created_by`). At most one `active` row per `(doc_type, COALESCE(tenant_key, ''))` (partial unique index) and at most one `backfilling` row per same key. A binding's profile must be scoped and contain the binding's doc type. RLS on, no policies, service role only.
- **D-07:** Precedence at ingest and query time, per (tenant, doc type): an active tenant-specific binding wins over an active deployment-wide binding; otherwise none. Single-tenant uses tenant key `s:default` or deployment-wide rows; both work.
- **D-08:** Additive, never partitioning. Chunks of a bound type stay in the global active profile; the binding profile is a second index over the same chunks. Consequences: (a) an incomplete, failing or removed binding can only lose the extra leg, never recall that the global profile provides; (b) rollback needs no re-embed; (c) storage and embedding cost grow by the bound types' share. A "replace" mode (global leg excludes the bound type) is deferred.

### Gate, evidence and rollback

- **D-09:** `rag_activate_embedding_binding(p_binding_id, p_actor)` (a binding row is unique per doc type, tenant and profile) refuses (prefix `binding_refused:`) unless, in one transaction under a lock on `embedding_profile_bindings`: the binding row exists in `backfilling` or `available`; the profile is scoped and contains the doc type; every current ready chunk of that doc type (in that tenant, or in all tenants for a deployment-wide binding) has a vector of the profile with the profile's model and dims; evidence exists and names this profile, doc type and tenant, names the current global active profile and the currently active binding (or none) as baselines, has `gate_passed = true`, a doc-type slice with `n >= 30` items whose provenance is `production` or `human` (EVAL-14), `passed = true` for every per-language sub-slice that has items, `other_slices_passed = true`, a `completed` backfill run of this profile covering the scope, and `recorded_at` after the newest vector of the profile in scope. On success the previous active binding for the key becomes `available` and is recorded as `previous_binding_id`.
- **D-10:** `rag_rollback_embedding_binding(p_doc_type, p_tenant_key, p_actor)` restores the previous binding when it is still complete, otherwise refuses with `binding_refused: previous_incomplete`; `rag_deactivate_embedding_binding(p_doc_type, p_tenant_key, p_actor)` sets the active binding to `available` with no gate, because global-only is always complete (D-08). Both are pointer flips; no vector is deleted.
- **D-11:** Fixture evidence can never activate a binding (D-09 provenance and `n >= 30`). The fixture run proves wiring, the decision rule and the gate refusals; real activation needs the Phase 5.1.1 real domain items (live checkpoint).
- **D-12:** Stale baseline. A binding applies at query time only while its evidence's `baseline_global_profile` equals the current global active profile. After a global flip, every binding is skipped (trace detail `binding_stale`) until it is re-proven: deactivate, re-run the comparison, record evidence, activate. The CLI `status` and the Config UI show stale bindings. The global gate is not changed to know about bindings.
- **D-13:** Evidence is recorded with `rag_record_binding_evidence(p_binding_id, p_evidence, p_actor)`, refused for an `active` binding, validated by the Zod schema generated from the Pydantic `BindingActivationEvidence` before the call (same pattern as `record-evidence`, P3 D-40).

### Re-embed and ingest

- **D-14:** Re-embed is scoped by the profile's `doc_types`. Migration 0442 replaces the 0315 selection and counting functions (`rag_reembed_pick`, `_next_batch`, `_missing_batch`, `_remaining`, `_count`, `_preview_batch`) to add `(p.doc_types IS NULL OR COALESCE(c.doc_type, d.doc_type) = ANY(p.doc_types))`, and `rag_reembed_start_run` / `rag_reembed_rollback_run` so that for a scoped profile they require a `backfilling` binding covering the run's tenant scope instead of moving the profile's own status. Unscoped behaviour is unchanged (tests replay the Phase 3 re-embed suite).
- **D-15:** `resolveEmbeddingTargets` takes `{ docType, tenantKey }`. With `RAG_DOMAIN_EMBEDDINGS=off` it returns exactly today's list. With it on, it adds every binding profile whose binding is `active` or `backfilling` for that doc type and tenant (both the tenant row and the deployment-wide row, because either may become active), role `binding`. A binding target failing is non-fatal: its vectors are left out and each chunk is recorded as a gap against the binding's open run (same rule as `backfilling`, P3 D-39). Rechunk uses the same targets.
- **D-16:** Batch API backfill (3.1 D-35) embeds only OpenAI profiles in batch mode; binding profiles (Voyage) are always embedded synchronously. The publish guard `rag_vectors_complete` (03.1-49) checks the active global profile only; bindings are not part of it (D-08 makes that safe).

### Query time

- **D-17:** Only the v2 pipeline (`chat`, `embed`, `eval` profiles) runs binding legs. Voice and the legacy pipeline are untouched (voice is not a v2 profile).
- **D-18:** For each active, non-stale binding in scope (after D-07 precedence, intersected with the query's `docTypes` filter when one is set, capped at `RAG_DOMAIN_EMBEDDING_MAX_LEGS`, default 2, ordered by doc type id), the query (original variant only) is embedded with the binding profile in parallel with the global embedding, under its own timeout `RAG_DOMAIN_EMBEDDING_TIMEOUT_MS` (default 800). The backend is called with `p_profile_id = binding profile`, `p_doc_types = [doc_type]`, all other filters unchanged, `p_lexical_limit = 0`, `p_dense_limit = candidate_pool_size`. The resulting list is `dense_domain:<doc_type>` with weight `leg_weights.domain` (default 1.0) in the same RRF.
- **D-19:** A binding leg that times out, errors or meets a profile mismatch is dropped; the search stage is recorded `degraded` with detail `binding_leg_<reason>`; the global legs and the answer continue. A binding leg never makes a request fail.
- **D-20:** Scores from different models are never compared. Hits from a binding leg carry `similarity: null` (their own score goes to `ranks` only); the similarity floor and refusal calibration keep reading the global profile's similarity. Because RRF keeps the first-seen hit in list-id order and `dense:0` sorts before `dense_domain:*`, a chunk found by both keeps the global similarity.
- **D-21:** Latency: binding legs run concurrently with the global embed and search, so the target is the existing `embed` 200 ms and `search` 400 ms stage budgets (chat/embed); the eval report shows the per-stage latency against `eval/config/latency-budgets.json` (report-only, as today). No budget file change.

### Comparison and decision rule

- **D-22:** The comparison runs arms on the same ingest fixture DB and the same golden file: **baseline** (global profile only), **control** (global profile plus a second global-model leg filtered to the doc type, no new vectors; isolates the "filtered extra leg" effect), and one **candidate** arm per scoped profile bound to the doc type. A candidate is recommended only if, on the doc-type slice, Recall@10 and MRR beat **both** baseline and control beyond the noise band; no per-language sub-slice of that doc type (zh, en, it) and no cross-lingual pair drops beyond the noise band versus baseline; no other doc-type slice and no language slice drops beyond the noise band; refusal rates do not worsen beyond the noise band. The rule lives in Python (`rag_eval.binding_compare`), output is the Pydantic `BindingComparison`; `gate_passed` is its verdict.
- **D-23:** Reproducibility: the comparison output records corpus and golden hashes, the profile ids, model ids, catalog version, retrieval-params hash, noise file hash, golden provenance counts, arms' report paths and the re-embed run ids. Fixture runs use the fixture embedder for every model (wiring proof only, labelled as such like `FAKE_EMBEDDER_NOTE`); live runs use real keys and the real golden set.
- **D-24:** A synthetic domain fixture pack (`eval/fixtures/domain/`): contract/legal and financial-report documents in zh, en and it, with golden items (at least 6 per doc type per language, including cross-lingual and no-answer items), kept separate from the main corpus so no existing baseline is re-recorded. Its own baseline is recorded once. Synthetic content only.

### Switches, surfaces, tenancy

- **D-25:** New env: `RAG_DOMAIN_EMBEDDINGS` (`off`|`on`, default `off`), `RAG_DOMAIN_EMBEDDING_MAX_LEGS` (default `2`, 0..5), `RAG_DOMAIN_EMBEDDING_TIMEOUT_MS` (default `800`, 100..5000). Mirrored in `.env.local` template (`scripts/init-env.js`), `src/lib/env.ts`, `scripts/config-server.js`, `scripts/config-ui/index.html`, `scripts/rag/env-manifest.json`. `RAG_EMBEDDING_PROFILES=off` forces bindings off too (bindings need the registry).
- **D-26:** Management is operator/admin only, like global profiles: CLI `npm run rag:embedding -- bindings | bind <docType> <profileId> [--tenant <key>] | bind-status <bindingId> available|backfilling|retired | record-binding-evidence <comparison.json> --binding <id> | activate-binding <bindingId> | rollback-binding <docType> [--tenant <key>] | deactivate-binding <docType> [--tenant <key>]`, admin routes under `/api/rag/admin/embedding-bindings` (admin session + live Supabase session, as the Phase 3 profile routes), and a Config UI panel. Tenant admins cannot bind in this phase (Q-04).
- **D-27:** Tenant isolation: every binding leg passes the request's `TenantScope` tenant key to `hybrid_search_chunks`; tenant-specific bindings are read only for the request's tenant; completeness and re-embed for a tenant binding count only that tenant's chunks. Two-tenant tests for ingest targets, query legs, the gate and re-embed.
- **D-28:** Migrations `0440_embedding_bindings.sql` (scope column, trigger, guard, bindings table, seeds, indexes), `0441_binding_gate.sql` (list, set-status, record-evidence, activate, rollback, deactivate), `0442_reembed_scope.sql` (scoped re-embed). New SECURITY DEFINER functions use `SET search_path = ''` with schema-qualified names, REVOKE from PUBLIC, anon, authenticated, GRANT to service_role; folded into both setup files' lock-down block. Numbers chosen after 0420–0423 (queue-hardening) and 0413 (reserved); the orchestrator must re-check against sibling phases planned in the same run (04.1, 04.1.1, 05.1.1, 06.1).

## Open questions for the product owner

| # | Question | Default adopted (PO may override) |
|---|----------|-----------------------------------|
| Q-01 | Which domain candidates to seed? | `voyage-law-2` (contracts), `voyage-finance-2` (financial reports and invoices), and a scoped `voyage-4-large` control arm. Rationale: Voyage's own docs say its newer general models match or beat its 2024 domain models, and the domain models are English-centric (law-2 was evaluated on English, Chinese and German legal sets, never Italian), so the scoped general multilingual arm is needed to tell "domain" from "second leg". |
| Q-02 | Seed `voyage-code-4` for `product_technical`? | No: product/technical documents are prose manuals, not code. Can be added later by one migration. |
| Q-03 | Additive bindings (second index) or partition (domain model only)? | Additive (D-08): safer rollback, no recall loss on failure; costs extra embedding and storage for bound types only. |
| Q-04 | Per-tenant bindings and who may set them? | Schema supports deployment-wide and per-tenant rows (tenant wins); only the operator/admin can bind. Tenant self-service is deferred. |
| Q-05 | Minimum real evidence for activation? | 30 real (`production`/`human`) golden items in the doc-type slice; every language present in that slice must not regress beyond noise. Below that, activation is refused. |
| Q-06 | Cost ceiling for live comparison? | Live re-embed runs only after the dry run's token and cost estimate (catalog prices; law-2/finance-2 have 50M free tokens each) is shown and approved in the live checkpoint. |
| Q-07 | After a global profile flip, should bindings keep applying? | No: they are suspended as stale until re-proven against the new global profile (D-12). |

## Existing Code Insights

### Reusable Assets
- `hybrid_search_chunks(p_tenant_key, p_profile_id, …, p_doc_types, …)` already searches any registered profile with a doc-type filter and does not require the profile to be active: a binding leg needs no new search SQL.
- `rrf(lists, k)` fuses any number of weighted lists; the translate seam already feeds several dense lists per query.
- `chunking_profiles` (0406) is the precedent for "one active row per doc type" with a partial unique index.
- The profile comparison harness and its Python scorer (03-46) already produce slice metrics per language, category, pair and doc type (`EvalReport.by_doc_type`).

### Established Patterns
- Gate functions raise `<op>_refused: <code>` messages; TS maps them through a regex into `{ ok: false, reason, detail }` (`profile-ops.ts`).
- Registry reads cached 30 s, invalidated after operations; unreadable registry throws, never falls back (P3 D-37).
- Eval-only overrides bypass pointers (`embedding_profile` option, `embedQueryForEvalProfile`).

### Integration Points
- `resolveEmbeddingTargets` callers: `embed-write.ts:231`, `rechunk/run.ts:450,724`.
- Provider lookup call sites: `deps.ts:64,70`, `embed-write.ts:84,103`, `rechunk/run.ts:380,408`, `reembed/run.ts:283`, `query-embedding.ts:36`, `active-profile.ts:293`.
- v2 search: `runSearchStages` builds lists in `listsFromLegs`; 04-29 adds the exact-id list to the same function (ordering dependency).

## Specific Ideas
- The control arm (global model, doc-type-filtered extra leg) costs no new vectors and answers the question every domain-model claim leaves open: is the gain from the model or from searching that doc type separately?
- Stale-binding suspension makes a global flip safe without editing the Phase 3 gate (and without colliding with Phase 7's planned gate change 0706).
