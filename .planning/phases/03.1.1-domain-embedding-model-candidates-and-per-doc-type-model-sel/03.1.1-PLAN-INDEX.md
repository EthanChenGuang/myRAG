# Phase 3.1.1 Plan Index

16 plans in 8 waves (03.1.1-16 was split out of 03.1.1-01 after plan check; numbers are not wave order). Plans in the same wave share no file in `files_modified`, every later editor of a file transitively depends on the earlier one, every in-phase dependency is in an earlier wave, and each wave number is the minimum its dependencies allow (checked by script on 2026-11-24). Every plan runs after Phase 3 is complete; `depends_on` also names the Phase 3, 3.1 and 4 plans whose outputs it extends (03-xx, 03.1-xx, 04-29); those cross-phase ids do not affect wave numbers.

Migrations: 0440 scope, bindings table, seeds and indexes (plan 04); 0441 binding gate (05); 0442 scoped re-embed (06); folded into both setup files by plan 14. Re-check the numbers against sibling phases planned in the same run before plan 04 executes (D-28).

UI: plan 13 Task 2 (Config UI "Embedding bindings" panel) needs `/gsd-ui-phase 03.1.1` first; plan 03 adds three env fields to the existing form only. Because the phase will have a UI-SPEC, `scripts/ci/check-frontend-design-summary.mjs` treats every SUMMARY of this phase as a UI summary: **every SUMMARY must include a "## Design skills" table** (rows frontend-design, Impeccable, web-design-guidelines; `n/a` with outcome `none` for non-UI plans). Before the UI-SPEC exists the gate already matches plans 03, 10, 12 and 13 (their text names `scripts/config-ui/` or `src/app/`); those four plans carry the table in must_haves and check their own SUMMARY with a local grep. Because plan 13 creates the UI-SPEC, the gate then checks every SUMMARY, so every other plan's `<output>` also requires the table (frontend-design `n/a`, Impeccable `n/a`, web-design-guidelines `none`). The phase-wide gate runs only in plan 14 Task 3 and in `/gsd-verify-work` (plan-check pass 2). web-design-guidelines runs on `scripts/config-ui/index.html` in plans 03 and 13.

Newest-definition rule (revision 3): every SQL function this phase replaces starts from its newest body on trunk, found by name (`grep -l "FUNCTION public.<name>(" supabase/migrations/*.sql | sort | tail -1`), never by line number. At 8115886 that is `0425_search_path_empty.sql` for `rag_chunk_embeddings_guard` (plan 04) and every `rag_reembed_*` function (plan 06); 0308/0315/0410 are older, and no migration numbered after 0425 redefines them (checked: 0426, 0427, 05xx, 06xx, 07xx). Every new or replaced function follows the 0425 rule (`SET search_path = ''`, schema-qualified relations, types, functions and `OPERATOR(public.<=>)`, pgvector in `public`), and `tests/rag-db/search-path-empty.test.mts` is in the verify commands of plans 04, 05, 06 and 14. 0440–0442 sort after 0425–0427 and before 05xx–07xx; if a later-sorting file redefines a replaced function at execution time, the executor stops and reports (06.1's 0654 reads the 0440 table, so a renumbering involves 06.1-20).

Stable names for later phases (Phase 3.2 D-07/D-25, Phase 3.2.1 plan 03.2.1-01 checks they exist): `src/lib/rag/embeddings/catalog.ts` exporting `EMBEDDING_MODEL_CATALOG`, `EmbeddingModelEntry`, `catalogEntry`, `defaultModelFor`, with per-entry fields `supportedLanguages` (string[] data), `servingModes` (`'hosted' | 'sidecar'`), `hostedEndpoint` and `sidecarPath` (plan 01); the column `public.embedding_profiles.doc_types` (plan 04); the model-aware lookup `getEmbeddingProviderFor(provider, model)` in `src/lib/rag/embeddings/registry.ts` (plan 01, call sites switched in plan 16). The catalog declares which serving modes a model supports; the mode in use is chosen by the provider factory (Phase 3.2 D-26).

Domain neutrality (owner rule, top of REQUIREMENTS.md): the catalog holds vendor facts only (`vendorDomainNote` is free text no code reads); the seeded scoped profiles name only vendor model ids and existing Phase 3 doc type ids and nothing is bound or activated by default (plan 04); the fixture pack is specified by structure, with subjects invented by the executor and no reuse of the requirements' illustrations (plan 11, checked by its test); Config UI copy names no subject area (plan 13).

Languages (LANG-01, Phase 3.2 D-02): no product code in this phase names a language code list. The gate iterates the language keys present in the evidence (plan 05), the comparison takes its language and pair slices from the golden items (plan 12), and the live precondition counts per language over the deployment's chosen languages (plan 15). zh/en/it appear only in fixtures, tests and as catalog data values (`supportedLanguages`).

Human checkpoints: plan 15 (live model facts, live migrations and index builds, real-data comparison and activation decision). Everything else is automated.
