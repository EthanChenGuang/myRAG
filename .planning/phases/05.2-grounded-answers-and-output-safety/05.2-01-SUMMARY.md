# Phase 5.2 Plan 01: Answer-side and safety contracts Summary

**Every Phase 5.2 answer and safety shape now exists once as a frozen, extra-forbid Pydantic v2 model with generated Zod. Old answer records and route output are unchanged while the new fields are unset.**

## Performance

- **Duration:** about 75 min
- **Tasks:** 3
- **Files:** 42 changed (19 new schema files)

## Accomplishments

- `AnswerChecks` (D-23, D-89) validates from `{}`. Its sentence records carry `part`, UTF-16 offsets, `text_hash`, `kind`, `support`, `scorer` and `reason`. It also holds the output-guard summary with blocked ranges, the version conflict, the claims summary, `truncated`, `finish_reason` and `text_language`.
- `AnswerRecord.checks` uses a default factory and is omitted when empty. `textsSource` and `CitationRecord.versionLabel` are omitted when null. Verified: the generated `AnswerRecordSchema` parses an old record without adding `checks` or `textsSource`, so the answers routes return the same JSON as before.
- Claim-check contracts (D-22, D-25, D-27): a 40-claim cap, a 64-premise cap, unique premise refs and claim indexes, and every `premise_ref` resolves. The judge verdicts use a closed `verdict` list, and the judge threshold cells are unique per `(judge_model, judge_version, language)`. `GroundednessScorer` admits `llm_judge`.
- `OutputCaps` (D-29, D-34) holds exactly one cell per mode, and a sweep cell needs evidence. `OutputGuardRules` (D-39) uses the registry-based rule language and rejects back-references.
- The security event contracts (D-43 to D-47) have no text field at all, and a test asserts that a `text` key is refused. `LinkPreviewStatus` carries host names only.
- `ReviewReason` gains exactly `claim_unsupported`, `output_guard` and `version_conflict`. No calculation reasons were added.

## Deviations from Plan

1. **`ReviewReason` was extended, not set equal to six values.** The plan's behaviour line says `ReviewReason` "equals" six values. On this base it already holds the five Phase 5.1.1 mining reasons (`refusal_disputed`, `refused_high_score`, `zero_results`, `low_score`, `no_source_opened`). Removing them would break 5.1.1, so the three Phase 5.2 reasons were appended. The acceptance check (exactly 3 of the 5 names, no `calc_*` reasons) holds. `MiningReason` (feedback_loop.py) is unchanged; the `rag_review_items` check belongs to migration 0944 in a later plan.
2. **`CitationRecord.effectiveFrom` already existed.** Phase 3.2 added it as a `date` (ISO `YYYY-MM-DD`). It was kept as it is, and only `versionLabel` was added.
3. **The field-name pin test was updated.** `test_citation_record_field_names_are_exactly_d01` in `rag-sidecar/tests/test_answer_contracts.py` now includes `versionLabel`.
4. **One extra sample.** `ClaimsSummary` is also registered as a top-level schema, in addition to the list in the plan.
