# Phase 5.2 Plan 16: Security events with the uploader Summary

**Retrieval-time injection detections and output-guard findings are recorded per tenant with their uploader after the response, with id-only spans, logs, Langfuse counters and an alert signal. Nothing changes with `RAG_SECURITY_EVENTS` off.**

## Performance

- Tasks: 3, plus the 05.2-19 merge and a contract fix
- Files: 3 created, 20 modified

## Accomplishments

- `security-events.ts`:
  - `buildSecurityEvent` validates against the generated contract, so a text field is refused.
  - `recordSecurityEvents` makes one `rag_record_security_events` call per request through `scheduleAfterResponse`, with the threshold, window and auto-hold flag from `readAnswerConfig`. A failure logs one `[RAG Security]` line with code and trace id and never reaches the request.
  - After a write it posts the four per-tenant counters. Each new alert gives one `[RAG Security] alert` line and one Langfuse `security_alert` event, with ids and counts only.
  - `recordSecurityEventsInline` is the awaited variant for ingestion (05.2-17).
  - `recordOutputGuardEvents` attributes each finding to the context blocks that contain the target or phrase. It writes one event per source chunk (none found: one event with no document) and hands off one `output_guard` review item when `RAG_DOMAIN_EXPERT_REVIEW` is on.
- `fetchAssemblyRows` and `fetchOverviewDocuments` add `user_id` to their single documents read only while the switch is on. `buildContext` sets `ContextBlock.uploaderId` only when the row carries the column, so all-off blocks are deep-equal to before.
- `runInjectionStage` (every legacy graph and v2):
  - With the switch on, each flagged item becomes a `retrieval_injection` event carrying the action the stage took, recorded once per request.
  - The `injection_check` span gets `security_tenant`, `security_documents`, `security_chunks`, `security_uploaders` and `security_detectors`.
  - The `[RAG Security] Injection check` line gains `tenant` and per-event ids.
  - The uploader comes from the rows already read (overview, legacy chat, v2 context). Paths without document rows (media, voice) send a null uploader, and the SQL fills it from `documents.user_id`.

### Auto-fixed Issues

**1. [Merge] Phase 5.3's 0967 dropped the Phase 5.2 review reasons**
- **Found during:** the required merge of `exec/05.2-19`

It runs after 0944, so after a full migration run `rag_enqueue_review_item` and the mining of `claim_unsupported` were refused (23514). Six tests in `tests/rag-db/review-enqueue.test.mts` failed.
- **Fix:** both 0944 and 0967 now write the full list of reasons, which the Pydantic/Zod `ReviewReason` already had. The order in which they run no longer matters.

**2. [Contract] `SecurityEvent.document_id` was required**
- The plan requires an output-guard event with a null document when no block holds the target. The table column is nullable, but the Pydantic model was not. I widened it to `str | None`, regenerated the schemas and Zod, and added a sidecar test.

**3. [Langfuse] Score ids collided per trace**
- `scoreId(traceId, name)` would let output-guard counters overwrite the retrieval counters of the same request. I added an optional `idKey` to `LangfuseScoreInput`; the default id is unchanged. No Langfuse event helper existed, so I added `postLangfuseEvent` to `trace/scores.ts`.

**4. [Scope] Files outside the plan list**
- `pipeline.ts`, `v2/stages/context.ts` and `trace/collector.ts` are the stage driver, its callers and the collector, needed to pass the uploaders and record span attributes. `overview.ts` uses the same conditional select so overview detections carry the uploader.
