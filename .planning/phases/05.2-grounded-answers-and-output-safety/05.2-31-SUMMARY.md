# Phase 5.2 Plan 31: Eval answer path runs the production composition, cap and chain Summary

**The eval answer is now produced and filtered by the same code as the chat answer. The eval route composes the answer-rule block after the citation instruction, applies the output cap through the shared helper, and runs the whole-text version of the stream chain: sentinel, output guard, then notices. It records the Phase 5.2 trace fields. The retrieval config hash now covers every answer-rule switch. The fake edge serves the new reads, so both gated run configs complete on fixtures.**

## Accomplishments

- **Composition (D-04, D-07).**
  - The eval route creates one `AnswerTurn` per request (channel `eval`, answer language from the question).
  - The `decorateSystemPrompt` hook calls `answerTurn.composeSystemPrompt` on the citation-decorated prompt, only when there is context. This is the chat route's rule.
  - The direct Claude path composes the same block into its system text.
  - `tests/eval-answer-sentinel.test.ts` reads both sources and fails when either composer call is removed. A mutated-source test proves the check can fail.
- **Cap (D-29, D-30, D-33).**
  - The turn decides the cap before the composer runs, so the concise part and the limit follow one decision.
  - `generateEvalAnswerDetailed` uses `effectiveMaxOutputTokens(maxOutputTokensForModel(model), cap)` and returns `finishReason`.
  - The direct Claude call gets `outputCap` the way the chat route passes it.
- **Whole-text chain (D-16, D-35, D-11).**
  - `applyAnswerPipelineToText` now runs the output guard (`guardWholeText`) between the sentinel and the notice stage. Guard notices go into the same notice state that renders the final paragraph.
  - The eval route runs this chain only while a Phase 5.2 switch is on.
- **Residual findings (D-42).** A second pass of the same guard core runs in flag mode over the final answer. It gives `residual_output_findings` (links, credential matches, rule ids) whatever `RAG_OUTPUT_GUARD` says.
- **Trace (D-62 a).** `answerRulesTraceFields` adds these fields only while a 5.2 switch is on:
  - `answer_language`, `sentences`, `refusal_origin`, `output_guard` (counts, rule ids and attributed chunk ids), `residual_output_findings`, `mixed_versions`, `finish_reason`, `answer_rules_parts` and `notices`.
- **Hash (D-58, Pitfall 24).**
  - `answerRulesHashComponent` covers the seven switches `RAG_REGISTRY_TEXTS`, `RAG_PARTIAL_ANSWER_RULE`, `RAG_CONTEXT_RELEVANCE_RULE`, `RAG_CITATION_PER_SENTENCE`, `RAG_VERSION_LABELS`, `RAG_MAX_OUTPUT_TOKENS` and `RAG_OUTPUT_GUARD`, plus `registryPackVersion()`.
  - While the guard is on it adds `outputGuardRulesVersion()` and `TLD_SNAPSHOT_VERSION`. While the cap is `auto` it adds the version of the committed caps file.
  - The component is null while all seven switches are at their defaults, so the pinned off-hashes are unchanged.
- **Fake edge.**
  - `documents` gains `doc_date` and `effective_from`. `version_label`, `version`, `doc_type` and `user_id` were already allowed.
  - `rag_supersession_candidates` is readable with exactly the `fetchVersionPairs` shape. `status` in-lists accept status words only.
  - Every other column, filter or value is rejected and recorded.

## Behaviour changes

- **Every Phase 5.2 switch off:** the eval prompt, `maxOutputTokens`, answer and trace are unchanged. The default fixture smoke has no Phase 5.2 field on any of its 308 traces, and the pinned hashes are unchanged.
- **With a switch on, the eval answer changes:**
  - the composed rules reach the prompt;
  - a sentinel answer becomes the registry refusal, with `refused: true` and `refusal_origin: model_relevance`;
  - the guard rewrites links and credential sentences;
  - notices are appended as the final paragraph.
- **With any of the seven switches on, `retrievalConfigHash` changes.** It is the semantic-cache key and the `retrieval_config_hash` of v2 traces. Eval comparisons between all-off and switch-on runs will show different hashes. This is intended.
- Chat, embed, voice and WhatsApp behaviour is unchanged. The only shared-code changes are additive seams on `AnswerTurn` and the guard stage of the whole-text helper, which no caller passed before.
- No switch, env var, migration, purge hook or package was added.

## Deviations from Plan

1. **Files outside `files_modified`.**
   - `src/lib/rag/generation/answer-turn.ts`: new seams `composedParts`, `sentinelRefusalText`, `setGuardSources` and `guardPolicyFor`. The stream chain now reads the sentinel text through the same function.
   - `src/lib/rag/generation/answer-transforms.ts`: the guard stage. The plan assumed `applyAnswerPipelineToText` already ran the guard; it did not.
   - `src/lib/rag/index.ts`: exports for `applyAnswerPipelineToText`, `buildSentenceRecords` and `attributeSourceChunks`. Deep imports are banned by `check-rag-boundary`.
   - `src/lib/rag/v2/result.ts`: the hash call site.
   - `tests/fixture-edge.test.mts`: the fake edge's own tests.
   - New `tests/rag-db/eval-p52-smoke.test.mts`.
2. **Sentence reason (bug found by the p52 run).** `buildSentenceRecords` (05.2-07) writes `support: 'not_checked'` with `reason: null`. The generated Zod accepts that, but the Pydantic `AnswerSentence` validator rejects it, so the harness refused every trace. The eval route now sets `claim_check_off` or `claim_check_not_run`. **This is still open on the chat route:** `rag_answer_records.checks.sentences` is written with `reason: null` and would fail Pydantic validation when Python reads it. Fixing `buildSentenceRecords` itself changes rows and tests owned by 05.2-07 and the claim-check plans, so I left it for them (see Deferred).
3. **Smoke test shape.** Two in-process `runEval` calls in one process fail: the second run's embedder keeps the first fake edge's closed address (`embed_failed`). So the rules-on config runs in process and the sec config runs through the `run-smoke` CLI in a child process. The sec smoke uses `--citations`, because the repeating fake needs labelled blocks to repeat the planted link.
4. **Acceptance-criteria baseline.** `grep -c version_label eval/harness/fake-edge.mts` was already 1 on this base (an earlier plan added the column). The new opt-ins are `doc_date`, `effective_from` and the supersession table.
5. **Extra hash input.** The version of the caps file under `RAG_MAX_OUTPUT_TOKENS=auto`. The plan did not list it, but a rewritten caps file changes answers.
