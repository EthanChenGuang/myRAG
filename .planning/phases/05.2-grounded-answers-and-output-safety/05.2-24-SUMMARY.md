# Phase 5.2 Plan 24: Answer checks record and client carriers Summary

**Each answer record can now hold its Phase 5.2 checks (with the answer-text language), the text source and the question's language; the owner's read routes return them, and the chat client keeps the new finish fields through streaming, polling and reload, with every switch off unchanged.**

## Performance

- **Duration:** about 75 min
- **Completed:** 2026-11-26
- **Tasks:** 3
- **Files modified:** 8 (1 created)

## Accomplishments

- `finishAnswer` computes `text_language` from the existing answer-text detection, validates `checks` with `AnswerChecksSchema`, and writes `checks` and `texts_source` only when the input carries them. `answer_language` takes the turn's answer language when one is set (D-89).
- `store.ts`: conditional column list, `updateAnswerChecks`, and the `claim_unsupported` reason (constraint already widened by 0944).
- `read.ts`: `checks` and `textsSource` on the wire shape, validated by the existing `AnswerRecordSchema` check in both routes.
- `answer-metadata.ts`: new finish fields are extracted and persisted, record checks are merged, and `noticesOf` reads notices without the citation-aware gate.

## Behaviour changes (switch on only)

- With any Phase 5.2 switch on (`readAnswerConfig().anyNonDefault`), answer-record reads select `checks,texts_source`, so migration 0940 must be applied before such a switch is turned on. This was already true for the writes from 05.2-09.
- `answer_language` holds the question language (D-09) for 5.2 turns. The language detected from the answer text moves to `checks.text_language`. Groundedness scorer routing still detects from the answer text.
- With every switch off: insert payload, select string, route bodies and persisted chat metadata are identical to Phase 5 (tests pin each one).
- The server never patches `chats.messages`.

## Deviations from Plan

- **answerChecksColumnsEnabled condition:** uses `anyNonDefault` instead of the plan's six-switch list. The route writes checks under `anyNonDefault`, so a narrower read condition would drop written data, for example with only `RAG_PARTIAL_ANSWER_RULE` on.
- **No contract default on all-off reads:** the plan allowed `checks: {}` to appear in all-off responses. It is omitted instead, so the response is unchanged.
- **Files listed but not edited:** `src/types/chat.ts` and `src/app/api/rag/answers/[answerId]/route.ts` needed no change (see key decisions).
- No migration was added, and no packages were installed or upgraded.
