### Partial-answer rule and relevance rule (GEN-08, GEN-15)

- **D-13:** `RAG_PARTIAL_ANSWER_RULE` (`false` default), strict mode only for the full rule. The instruction says, in the answer language:
  - answer the parts of the question that the context covers;
  - for each part it does not cover, say so with the registry phrase `labels.not_covered`, naming the part;
  - never fill a gap with general knowledge or with a plausible value.
  It carries one worked example built from abstract placeholders (a question with part A and part B, a context that states a value for A and nothing for B, and the expected two-part answer). The example contains no subject matter, units or realistic values.
  - Balanced mode keeps its design. With the switch on it gets one sentence: anything not taken from the documents must be introduced by the registry label `labels.general_knowledge`.
  - Flexible and bypass modes get nothing.
- **D-14:** Strict mode with webSearch (existing rule, kept: when the context is insufficient strict mode may call the Exa tool). With the switch on and the tool offered, the instruction adds: keep what the documents say and what the web says in two separate parts headed by `labels.from_documents` and `labels.from_web`. The tool, its trigger and its result handling are not changed.
- **D-15:** `RAG_CONTEXT_RELEVANCE_RULE` (`false` default). The instruction tells the model that context about a neighbouring subject does not answer the question, and what to do then:
  - **strict, webSearch off:** output only the no-answer sentinel (D-16);
  - **strict, webSearch on:** call `webSearch` (the existing rule), and output the sentinel only if the web gives nothing;
  - **balanced and flexible:** do not present that context as the answer; a general-knowledge answer starts with `labels.general_knowledge`.
  The wording is abstract ("the context is about a related but different subject than the one asked") and gives no subject example.
- **D-16:** The no-answer sentinel. When the model itself decides the context does not answer the question, the user must get exactly the registry "information not available" text, in the right language, never cut by the length cap. The model is asked to output a fixed sentinel token and nothing else. A stream transform holds back the first characters of the answer until they either match the sentinel or diverge:
  - match at the start: the model output is dropped and the server streams `notices.no_information` in the answer language (the same text the server-side refusal uses), sets the trace `refusal_origin: 'model_relevance'` and the log outcome `refused_no_context`;
  - a sentinel later in the text is stripped and counted on the trace.
  The hold-back is a few characters, so time to first token is not affected in practice. The sentinel is used only when `RAG_CONTEXT_RELEVANCE_RULE` or `RAG_PARTIAL_ANSWER_RULE` is on. Groundedness, the claim check and feedback treat a sentinel refusal like the server-side refusal (not scored; Phase 5.1.1's refusal control applies).
- **D-17:** Interaction with the calibrated refusal. Nothing in D-13 to D-16 changes the server-side decision. Items whose top score is below the refusal threshold are still refused before generation; the relevance rule only acts on turns that reach the model.

### One citation per factual sentence and sentence marks (GEN-09)

- **D-18:** One sentence splitter, `splitAnswerSentences(text, language)` in `src/lib/rag/lang/sentences.ts`. It is rules-based on the registry's `sentence_end` characters and reuses the Phase 3.2 LANG-06 splitter where that exists. It treats as one unit: a list item, a table (whole), a fenced code block, a heading. It does not split inside decimals, abbreviations with a following lowercase letter, URLs, citation markers or quoted spans. It returns `{ index, start, end, text, kind }` with offsets into the raw answer text as persisted (markers included). Tests cover zh (full-width punctuation, no spaces), en and it (elision, abbreviations), and mixed-script sentences.
  - The eval does not re-implement it: sentence records travel on the trace, and the Python metrics read them. One implementation, no drift.
- **D-19:** "Factual sentence" is decided by fixed rules, not a model. A sentence is **exempt** when it is a heading, a question, a lead-in ending in a colon, a registry notice or label phrase (including the `not_covered` statement), inside a part headed by `labels.from_web` or `labels.general_knowledge`, or a code block. Every other sentence is factual. A sentence is **cited** when a validated marker (Phase 5 `AliasMap`) lies inside it or directly after its end punctuation; on the Claude path, when a `source` part's character range overlaps it. A table counts as cited when any cell row carries a marker.
- **D-20:** `RAG_CITATION_PER_SENTENCE` (`false` default; needs `RAG_CITATIONS` or `RAG_CLAUDE_CITATIONS`).
  - On: the citation instruction text becomes `instructions.citation_per_sentence` (every factual sentence ends with the marker of the block that supports it). On the Claude path the instruction asks the model to ground every factual sentence in the attached documents.
  - On: the server computes the sentence records at stream end (deterministic, a few milliseconds) and sends them in the `finish` message metadata as `sentences[]` with `cited: boolean` for factual ones.
  - Off: the Phase 5 D-04 instruction text and the finish metadata are byte-identical to Phase 5.
- **D-21:** Eval. `uncited_sentence_rate` = factual sentences without a valid citation over factual sentences, reported next to `citation_coverage`, per language, category and strategy, whenever citations are on. It is report-only in this phase (no gate), because a real model's rate is unknown until the nightly run.

### Claim-level grounding (GEN-10)

- **D-22:** `RAG_CLAIM_CHECK` (`false` default). It runs under exactly the Phase 5 D-14 conditions (web chat with the citations capability, strict or balanced, knowledge-base context present, not a refusal, not a ghost chat, no MCP tool output) and in the same post-stream `after()` job that `scheduleAnswerFinish` already schedules, after the answer-level score. The answer is never delayed.
  - Units: the factual sentences of D-19, capped at 40 per answer; beyond the cap the remaining sentences are `not_checked` with reason `too_many`.
  - Premise per sentence: its cited blocks first, then the other blocks sent, up to `RAG_GROUNDEDNESS_MAX_PREMISE_TOKENS`; markers stripped from the hypothesis; stored unescaped chunk text (Phase 5.1 A4).
  - Scorer: the sidecar gains `POST /v1/groundedness/claims` (`ClaimCheckRequest`: `request_id`, `language`, `premises[]`, `claims[{ index, hypothesis, premise_refs[] }]`, `allow_vectara`; `ClaimCheckResult`: per claim `status`, `scorer`, `score`, `reason`). One request per answer, batched inside the sidecar, routed per language exactly as Phase 5 D-11. Languages without HHEM go to the judge of D-25 when it is on, otherwise `not_checked`.
  - Label per sentence: `supported`, `unsupported` or `not_checked`, from the Phase 5 thresholds file for HHEM cells (`eval/config/groundedness-thresholds.json`) and from D-27 for the judge.
  - Timeout: it shares `RAG_GROUNDEDNESS_TIMEOUT_MS`; on timeout every unchecked sentence is `not_checked`.
  - **Reversibility:** costly — a new sidecar wire contract.
- **D-23:** Storage and delivery. `rag_answer_records` gains one column, `checks jsonb` (migration 0940), holding everything this phase and Phase 5.2.1 record per answer, validated by the Pydantic `AnswerChecks` contract:

  - `output_guard`: counts and event ids (D-41);
  - `version_conflict` (D-52);
  - `truncated` and `finish_reason` (D-33);
  - `calc` (Phase 5.2.1, D-75);
  - `prompt_budget` summary (Phase 5.2.1, D-86).

Old messages without the field keep loading. The server never patches `chats.messages`.
  - Sentence offsets are valid only for the answer text whose hash matches `text_hash`; when it does not match (edited or regenerated message) the client shows no marks.
- **D-24:** Never delete, never block; count and queue. Unsupported sentences stay in the text. ### LLM judge for languages without HHEM (GEN-11)

- **D-25:** `RAG_GROUNDEDNESS_LLM_JUDGE` (`false` default, which keeps "not checked") and `RAG_GROUNDEDNESS_JUDGE_MODEL` (empty default). The judge runs **in the app**, not in the sidecar, as a structured helper call through the existing model client: the app already holds the model key, the text goes to the same provider the generator already uses (no new data destination and no new secret in the sidecar), and GEN-04 allows structured output on helper calls. It is used only for sentences (and the answer-level label) whose language has no HHEM route.
  - Contract: `ClaimJudgement` (Pydantic, generated Zod): per sentence `verdict: supported | unsupported | not_enough_info` and `evidence_ref` (an alias or null). One call per answer; sentences and premise in the same call, inside the D-22 caps.
  - The judge must come from a different model family than the generator. The check mirrors `assert_judge_family_differs` in the eval; when the families match, or the model is empty, the result is `not_checked` with reason `judge_same_family` or `judge_not_configured`. It never falls back to the generator.
  - Failure, timeout or an invalid structured result: `not_checked`, reason recorded. Nothing is retried on the request's own budget.
  - **Reversibility:** costly — answer and chunk text of the affected languages go to a second model; listed in the Config UI and the ADM-04 egress inventory.
- **D-26:** Prompt safety of the judge. Premise and answer are passed as data inside the Phase 5.1 `<documents>` wrapping with the same notice; the judge prompt is a fixed English constant with a registry-language note. The judge prompt, model id and rubric version form `judge_version`, stored with every result.
- **D-27:** Calibration and label. The judge has its own file, `eval/config/groundedness-judge-thresholds.json` (Pydantic `GroundednessJudgeThresholds`), keyed by `(judge_model, judge_version, language)`. The calibrated quantity is claim-level (EVAL-24): the maximum share of unsupported sentences at which an answer is still `verified`, plus the judge's measured recall and precision on unsupported sentences.
  - Only `python -m rag_eval.calibrate groundedness-judge` writes it (fit on the dev split of labelled faithful and unfaithful answers, check on the test split, the Phase 4 D-18 and Phase 5 D-13 pattern). Never edited by hand.
  - A cell without a calibration record keeps the answer-level label `not_checked` with reason `judge_uncalibrated` in production; per-sentence verdicts are still stored and shown. Cells fitted on the fixture corpus apply only in eval runs (the AGENTS.md rule for fixture-fitted cells). So "a calibrated label for Italian" is proven in CI on fixtures and becomes live after the live calibration on the seed set (EVAL-24).
  - Any change of judge model, prompt or rubric changes `judge_version` and so invalidates the cell.
- **D-28:** Cost and latency. Every judge call records input and output tokens, latency and an estimated cost on the trace (`groundedness_judge` span) and in the eval report per language. `eval/config/latency-budgets.json` gains `groundedness_judge` (p95 starting value 10000 ms) and `claim_check` entries, report-only and outside the pre-first-token total.

### Output-length cap (LAT-05)

- **D-29:** `RAG_MAX_OUTPUT_TOKENS` = `off` (default) | `auto` | a positive integer.
  - `off`: `getMaxTokensForModel`, `MAX_COMPLETION_TOKENS`, the reasoning limits and the embed route's fixed limit behave exactly as today.
  - `auto`: the cap comes from `eval/config/output-caps.json` (Pydantic `OutputCaps`), per RAG mode (`strict`, `balanced`). Only `python -m rag_eval.sweep output-cap` writes that file.
  - An integer: that cap for both modes (operator override).
  - The effective limit is `min(model limit, cap)`; the cap never raises a limit.
- **D-30:** Where it applies and where it does not. It applies to turns that have knowledge-base context in strict or balanced mode, on the chat route and the embed route (embed: `min` with its existing fixed limit). It is **not** applied when:
  - the request carries its own `maxOutputTokens` (a user setting; the WhatsApp handler always sends `WHATSAPP_MAX_TOKENS`, which counts as set, so WhatsApp keeps its own limit and gets only the concise instruction);
  - reasoning is on for the turn (reasoning tokens share the output budget);
  - the mode is flexible or bypass, or the turn has no knowledge-base context;
  - the turn is a tool-approval continuation;
  - the channel is voice (the agent has its own limits).
- **D-31:** The refusal is never cut. The server-side refusal and the D-16 sentinel refusal are written by the server, outside the model's token limit, so no cap can truncate them. In addition the configuration loader rejects a cap smaller than a floor (the token count of the longest registry notice, times two, and at least 256). The effective cap is exported as the **answer reserve** that Phase 5.2.1's prompt budget subtracts (D-80).
- **D-32:** The concise-answer instruction (`instructions.concise`) is appended whenever the cap applies to the turn (D-05 part 7). It asks for the answer first, then only the supporting detail the question needs, and to keep every citation. It states no number of words.
- **D-33:** Cut-offs. `finishReason` is recorded on the trace for every turn. When it is `length`:
  - the Phase 5 marker parser is flushed, so citations streamed before the cut are validated and persisted (GEN-02, GEN-03); a marker cut in half is dropped and counted, never guessed;
  - the output guard (D-38) and the sentence splitter are flushed the same way; the last incomplete sentence is recorded as `kind: 'truncated'` and is exempt from the uncited count;
  - `notices.answer_truncated` is emitted (D-11) and `checks.truncated = true` is stored.
- **D-34:** How the eval chooses the defaults. `python -m rag_eval.sweep output-cap` runs the answer tier over candidate caps per mode and records, per candidate: judge answer correctness, citation recall, output tokens, generation latency and the truncation rate (`finishReason = length`). It picks, per mode, the smallest cap whose correctness and citation recall stay within the noise band of the uncapped run and whose truncation rate is below 2%; when no candidate qualifies the cell stays `off`. The decision is written with its evidence (run ids, config hash). On fixtures with the fake generator this proves the wiring and the 2% rule; the real choice is a nightly and live-verification result. Starting candidates are the planner's or researcher's choice; the committed file starts with every cell `off` and `source: default`.

### Output guard (SEC-06)

- **D-35:** One module, `src/lib/rag/security/output-guard.ts`, with a pure incremental core `createOutputGuard(policy)` exposing `push(delta)` and `flush()`, and two adapters:
  - a `StreamTextTransform` used through `experimental_transform` on the chat route (OpenRouter and Claude paths) and the embed route, placed **after** the citation marker transform so it sees the text the user would see;
  - a whole-text function for non-streamed uses (the WhatsApp reply, the approve route's summary text, eval).
  Tests feed every fixture answer split at every character boundary and require the same output as the whole-text function.
- **D-36:** Switch: `RAG_OUTPUT_GUARD` = `off` (default) | `flag` | `enforce`.
  - `off`: no transform is installed; streams are byte-identical.
  - `flag`: detection, trace and events only; the text is not changed (shadow mode, the Phase 5.1 `flag` precedent).
  - `enforce`: replace and block as decided below. This is the recommended setting for the Phase 7 regression.
- **D-37:** What is allowed. A URL, bare domain or e-mail address is kept only when one of these holds:
  1. its host is on `RAG_OUTPUT_LINK_ALLOWLIST`, through the unchanged Phase 3.2 parser `src/lib/rag/security/link-allowlist.ts` (subdomain match; the app's own domain from `NEXT_PUBLIC_SITE_URL` always allowed). If Phase 3.2 is not on trunk when this is executed, the plan that needs the parser depends on the Phase 3.2 plan that creates it; it is not re-implemented;
  2. it is, after normalization, exactly a result URL returned by the `webSearch` tool in the same turn, and that result was not flagged by the Phase 5.1 tool-result guard;
  3. it is exactly a URL the server itself issued in this turn (document links from the sources list, storage URLs that `isAllowedImageUrl` in `src/lib/safe-image-hosts.ts` accepts for images);
  4. it appears verbatim in the user's own message of this turn.
  A link that appears in retrieved document text is **not** allowed for that reason. For e-mail addresses the domain part is checked against rule 1 and the whole address against rule 4.
  - Hosts are compared after NFKC normalization, lower-casing and IDNA conversion; a host that changes under normalization, carries credentials (`user:pass@`), or uses a non-`http(s)`/`mailto` scheme is never allowed. Obfuscated forms listed as data (bracketed or spelled-out dots, a neutral-looking scheme variant) are detected as links.
  - Bare domains are recognized with a committed snapshot of the public top-level-domain list (data). A token equal to a document name in this request's context blocks is not treated as a bare domain (file names end in strings that are also top-level domains); this exemption never applies to a URL with a scheme.
- **D-38:** Streaming hold-back. The guard passes text through until a possible start of a link (a scheme prefix, `www.`, `mailto:`, an `@` inside a word, a label followed by a dot and letters, or `[` that may open a Markdown link). From there it buffers until the candidate is complete (whitespace, a CJK character or punctuation, a closing bracket not part of the URL, or the end of the stream) or a bound is reached (2,048 characters for a URL, 300 for Markdown link text), then decides. Citation markers resolve at `]` not followed by `(` and pass at once. At `flush()` (normal end, abort or `length`) a buffered candidate is decided as it stands; an incomplete candidate that is not allowed is replaced.
  - A removed target becomes the registry placeholder `notices.link_removed`. A removed Markdown link keeps its visible text followed by the placeholder; a removed image is replaced by the placeholder alone.
  - Tool-call and reasoning parts are not text deltas and are not filtered.
- **D-39:** Credential and account requests. Rules are data: `config/rag/output-guard-rules.json` (Pydantic `OutputGuardRules`, versioned), per language a set of patterns that pair a request form with a secret or log-in term inside one sentence, matched with the shared NFKC case-folded matcher of `src/lib/rag/security/injection-rules.ts`. The rules contain security vocabulary only, no subject-area words, and must produce zero matches on the clean fixture answers (gated).
  - The guard buffers a sentence only while a rule's first term has been seen in it, so ordinary text still streams token by token.
  - **Block** (the sentence is replaced by `notices.credential_request_blocked`) when the same answer has a removed link, or any context item of the turn was flagged (a Phase 5.1 `injection_check` flag, a Phase 3.2 quarantine release on the source document, or a flagged tool result).
  - **Warn** otherwise: the sentence is kept and `notices.credential_request_warning` is emitted through D-11.
  - If the link is removed after the credential sentence was already streamed, the sentence cannot be recalled: the block notice is emitted at the end, and `checks.output_guard` marks the sentence so the web UI shows it as blocked. Non-streamed channels (WhatsApp) are filtered on the whole text, so there the block is exact.
- **D-40:** Channels.
  - **Web chat and embed:** the stream transform.
  - **WhatsApp:** the reply text is filtered with the whole-text function in `WhatsAppWebhookHandler` immediately before `sendWhatsAppResponse`, in addition to the route transform, so a reply assembled from several parts is still covered.
  - **Baileys link previews (backlog 999.1, folded in):** the service already refuses server-side previews unless every URL in the text is on `WHATSAPP_LINK_PREVIEW_HOSTS` (`baileys-whatsapp/src/Service/link-preview-policy.ts`, default empty = never fetch). This phase keeps that code, adds an optional per-message `linkPreview: false` field to the send endpoints that the app sets whenever the guard is not `off`, exposes the configured preview hosts on the service's health endpoint so the Config UI can show whether they are a subset of `RAG_OUTPUT_LINK_ALLOWLIST`, and adds a test that a reply with a non-allowlisted URL is sent with `linkPreview: null`. The real no-fetch check is the live-verification item.
  - **Voice:** a spoken link cannot be clicked. Voice gets the output policy statement (D-07) and a post-hoc check: when the agent stores the turn through `/api/internal/voice-chat`, the whole-text function runs in `flag` behaviour and writes events (D-41). A real-time guard before speech is deferred.
- **D-41:** Trace, events and review. Every removal, block and warning:
  - is counted on an `output_guard` span (`links_checked`, `links_removed`, `credential_blocked`, `credential_warned`, rule ids, rule-set version) and logged as `[RAG Security]` with ids only;
  - is attributed to source chunks: the chunk ids of this turn's context blocks whose text contains the removed target or the matched phrase (a string search over the blocks sent; none found = `source: 'model'`);
  - writes a security event (D-43) per source chunk and sends it to the review queue with reason `output_guard` (D-55).
- **D-42:** SEC-04 accounting. On `injection` and `injection_evasive` items, `attack_success_rate` also counts as a success an answer that contains a link, domain or e-mail address outside the allowlist, or a sentence matching a credential rule. The fixture corpus gains items whose injection document carries a hidden link and a credential request (structure only; synthetic hosts under a reserved test domain). The absolute-zero CI gate of Phase 5.1 D-14 is extended: under the recommended configuration plus `RAG_OUTPUT_GUARD=enforce`, the rate is 0 with a scripted fake model that repeats the planted link and request, including when they are split across stream tokens; allowlisted links in the same fixtures pass through unchanged.

### Uploader tracing, alerts and holds (SEC-10)

- **D-43:** `RAG_SECURITY_EVENTS` (`false` default). One table, `public.rag_security_events` (migration 0942), one row per event from the five sources: ingestion injection rules (SEC-01), retrieval-time check (SEC-03), output guard (SEC-06), hidden text (SEC-07), link check (SEC-08).
  - Columns: `id`, `tenant_key` (checked by `rag_assert_tenant_key`), `source` (`ingest_injection | retrieval_injection | output_guard | hidden_text | untrusted_link`), `action` (`detected | quarantined | dropped | downweighted | removed | blocked | warned`), `detector`, `rule_ids text[]`, `document_id`, `chunk_id` (nullable), `uploader_id` (the document's `documents.user_id`; nullable when the document is gone), `trace_id` (nullable for ingestion), `created_at`. No text.
  - RLS on, no policy; all grants revoked from PUBLIC, anon and authenticated; service role only. Reads go through admin routes.
  - Written after the response through `scheduleAfterResponse` for request-path sources, and inline for ingestion. A write failure never fails the request or the ingestion.
  - Off: no row is written and results equal the baseline (success criterion 5).
  - **Reversibility:** one-way — a new table on real projects.
- **D-44:** The uploader on the trace and in logs. The batched document fetch that assembly already does (`src/lib/rag/context/fetch-rows.ts`) also selects `user_id`, so no per-chunk lookup is added. The `injection_check` and `output_guard` spans and the `[RAG Security]` lines carry `tenant`, `document`, `chunk`, `uploader` (the user id, never an e-mail or a name) and `detector`. Ingestion-side events take the uploader from the ingest input. Langfuse receives the same ids as span metadata plus per-tenant counters (`security_detected`, `security_quarantined`, `security_removed`, `security_blocked`) as scores, so its dashboards can chart them; the spike alert itself is the Phase 5.3 OBS-03 rule reading these counters.
- **D-45:** Alert. `RAG_UPLOADER_ALERT_THRESHOLD` (integer, `0` default = off) and `RAG_UPLOADER_ALERT_WINDOW_HOURS` (`24` default). After each event write, a service-role function counts that uploader's events in the tenant within the window; when the count first exceeds the threshold it inserts one row in `rag_security_alerts` (`tenant_key`, `uploader_id`, `event_count`, `window_start`, `window_end`, `status: open | acknowledged`, `held: boolean`), unique per uploader and window so it fires once. An open alert produces a Config UI banner, one `[RAG Security] alert` log line and a Langfuse event. Webhook and e-mail delivery are Phase 5.3's alert channel (OBS-03), which reads this table.
- **D-46:** Holding uploads. `RAG_UPLOADER_HOLD` = `off` (default) | `manual` | `auto`.
  - `manual` (recommended): an admin presses "hold uploads" on an alert or on an uploader row; a row in `rag_uploader_holds` (`tenant_key`, `user_id`, `created_by`, `reason`, `released_at`) is created.
  - `auto`: the hold is created when the alert fires.
  - Effect: in `submitIngest()`, an upload whose uploader has an active hold takes the Phase 3.2 D-36 `pending_review` path, whatever `RAG_UPLOAD_APPROVAL` is, and waits for the same approval action. Uploads of that uploader already waiting in the ingestion queue are held at `publish` the same way. Documents already published are not touched (quarantine and deletion stay explicit admin actions). Releasing the hold does not approve held documents.
  - Depends on Phase 3.2's `pending_review` status. Without it on trunk the hold plan depends on the Phase 3.2 plan that adds it.
- **D-47:** Who sees the uploader. Deployment admins see it for every tenant; organization admins and that tenant's domain experts see it for their tenant only (the Phase 5.1.1 D-16 access rule). Routes return the uploader's id and display name resolved server-side; e-mail addresses are shown to deployment admins only.

### Version-aware answers (GEN-14, EVAL-19)

- **D-48:** `RAG_VERSION_LABELS` (`false` default). Off: block headers and the context string are byte-identical.
- **D-49:** Where the version and date come from. No new extraction is built.
  - Effective date: `documents.effective_from` (Phase 3.2 D-43); when null, the document date already stored at ingestion; when neither exists the label says nothing about a date.
  - Version label: a new nullable column `documents.version_label text` (migration 0941), set by an admin in the Phase 3.2 "Versions and dates" panel or filled at ingestion from the title's version marker when the Phase 3.2 supersession detector parses one (registry `version_markers`); when null, the label is the integer `documents.version` (Phase 3 D-06) rendered through `labels.version`.
  - Both travel with the document rows that assembly already fetches in one batch.
- **D-50:** Rendering. `ContextBlock` gains `versionLabel` and `effectiveFrom`. They are written in the block's header line (the Phase 5 `[S3] …` label, or the legacy document line) through `labels.version` and `labels.effective_from` in the answer language, with the date in ISO `YYYY-MM-DD` form in every language. With `RAG_CONTEXT_TAGGING` on they are also `version` and `effective` attributes on `<doc>` (attribute-escaped, Phase 5.1 D-03). On the Claude path they go in the document block's title. The citation record already has `documentVersion`; it gains the optional label and date so a chip can show them.
- **D-51:** The version rule (`instructions.version`, D-05 part 5): when blocks give different values for the same thing, use the block with the latest effective date (or the highest version when dates are missing), name its version in the answer, do not present the two values as alternatives, and mention an older version only when the question asks about the past or about changes.
- **D-52:** Conflict detection is done by the server, with rules, before generation:
  - two blocks form a **version group** when they come from different documents of the same document type and either a `rag_supersession_candidates` or `rag_supersession_links` row connects the two documents, or their titles are equal after removing version markers (the Phase 3.2 D-41 rule (a), reused);
  - a group is a **conflict** when the two blocks' texts overlap strongly and differ in at least one number or date (the Phase 3.2 D-41 rule (b) applied to block text, thresholds from `config/rag/supersession-rules.json`).
  On a conflict:
  - the older block's header gets `labels.older_version` (the block is kept: the question may be about history, and RET-11 owns filtering);
  - the trace gets `version_conflict: { document_ids, latest_document_id, group_rule }`, and `checks.version_conflict` is stored;
  - a pending row is written to `rag_supersession_candidates` with origin `answer_conflict` (the origin Phase 3.2 D-41 reserved for this), deduplicated per document pair, and a review item with reason `version_conflict` naming both documents (D-55). Nothing is superseded without the Phase 3.2 confirmation.
  After generation a deterministic check sets `mixed_versions: true` on the trace when the answer contains a value that occurs only in the older block and a value that occurs only in the newer one, unless the question was classified as historical by the existing temporal detector. The answer text is not changed.

### Fixtures, fake models and gates (GEN-12, EVAL-19, GEN-15)

- **D-53:** Golden contract (Pydantic, generated Zod, parity tests). `Category` gains `partial_answer`, `stale_version` and `off_topic_context` (and, for Phase 5.2.1, `multi_step_calc` and `context_overflow`). `GoldenItem` gains optional structures, each required exactly for its category by a validator:
  - `partial`: `covered` (gold spans the answer must use), `uncovered_aspects[]` (short neutral descriptions of what the documents do not say), `forbidden_claims[]` (patterns an answer must not contain);
  - `versions`: `current` and `stale` (each a gold span plus the expected value string and version label), `historical: bool`;
  - `off_topic`: `adjacent_quotes[]` (gold spans of the neighbouring-subject text that must not be used), `score_band: 'below_threshold' | 'above_threshold'`.
  Evidence is always by span quote, never chunk id. `off_topic_context` joins the unanswerable categories.
  - **Reversibility:** costly — the committed golden files and the baseline change.
- **D-54:** Fixture content and gates. All synthetic, neutral and different from the examples used to motivate the requirements; at least 4 items per language per category; topics isolated so no new document enters an existing item's top-k (if one does, the document is rewritten). Additions follow the Phase 2 D-25 and Phase 5.1 D-13 sequence: parity on the unchanged set, then the additions, then a re-baseline in which every pre-existing item's paired difference is zero.
  - `partial_answer`: a document states one part of what the question asks and is silent on another. Metrics: `unsupported_addition_rate` (the answer matches a `forbidden_claims` pattern, or contains a number or date found neither in the context sent nor in the question) and `covered_part_answered` (a covered gold span's value is in the answer and cited).
  - `stale_version`: two versions of one synthetic rule as separate current documents with different values. Metrics: `current_value_rate` (current value present and its version named), `mixed_versions_rate` (both values present; a failure).
  - `off_topic_context`: a no-answer question whose top chunks are on a neighbouring synthetic subject, half scoring below and half above the refusal threshold through the fixture embedder. Metric: `adjacent_repurpose_rate` (the answer uses an `adjacent_quotes` value without the general-knowledge label, or fails to refuse in strict mode).
  - Fake models. `eval/harness/` gains scripted generators next to `fake-citation-generator.mts`: a **rule-following** fake that behaves correctly only when the corresponding instruction is present in the prompt it receives, and a **violating** fake per category (fills the gap, mixes both values, repurposes the adjacent text). CI asserts both directions: with the switch on and the rule-following fake the three rates are 0 (absolute-zero gate) and the covered part is answered; with the violating fake the metric reports the failure (so the metric is proven to detect it); with the switch off the strict characterization is byte-identical.
  - Nightly (skipped without keys): the same slices with a real generator and the judge, reported per language; the judge-based share for `off_topic_context` and `partial_answer` is measured, not gated, until EVAL-24 calibrates the judge.

### Calculation tool (GEN-16)

- **D-65:** `RAG_CALC_TOOL` (`false` default). A tool named `calculate` in the chat route's tool set next to `useDocument` and `webSearch`. Off: the tool set, the prompt and the stream are byte-identical. Embed and WhatsApp reach it through the routes they already call. The tool's implementation is a pure module, `src/lib/rag/calc/`, with no I/O.
- **D-66:** Contract (Pydantic, generated Zod; the tool's input schema is the generated Zod):
  - `CalcRequest`: `operands[]` and `steps[]` and `result` (a step id).
  - `CalcOperand`: `name`, `value` (a decimal string or an ISO date; for lists, `values[]`), `unit` (optional string), `source` (`{ kind: 'question' }`, `{ kind: 'chunk', alias }` where the alias is one of this request's context blocks, or `{ kind: 'fact_tool', tool, key }` reserved for the SEC-05 design).
  - `CalcStep`: `id`, `op`, `args[]` (operand names or earlier step ids only; a literal number is not a valid argument), optional `rounding { mode, places }`, optional `label`.
  - `CalcResult`: `value`, `unit`, `steps[]` (each with its inputs, operation, exact value and displayed value), `status: ok | rejected`, `reject_reason`.
  - **Reversibility:** costly — the tool schema is seen by every tool-capable model and by the eval traces.
- **D-67:** Operations, a closed set: `add`, `subtract`, `multiply`, `divide`, `min`, `max`, `sum` (over a list), `cap_each` (the per-item cap: each list item limited by a cap operand, returning the list), `percentage` (a value times a percent operand over one hundred), `round` (modes `half_up`, `half_even`, `up`, `down`, with stated places), `date_diff` (between two ISO dates, in `days`, `months` or `years`, with an explicit `inclusive` flag). There is no expression string, no `eval`, no function constructor, no dynamic import; a property test feeds code-like strings in every field and requires `rejected`.
- **D-68:** Arithmetic is exact. Values are parsed from decimal strings into rationals over `BigInt` (numerator and denominator); add, subtract, multiply and divide are exact; rounding happens only in a `round` step or in the final display (10 decimal places, half-even, flagged `display_rounded`). No floating-point number is used anywhere in the module, and no new dependency is added. Division by zero and a non-finite input are rejections.
- **D-69:** Units and limits. A unit is an opaque string compared after NFKC and case folding; the tool has no unit table and no currency table. `add`, `subtract`, `min`, `max`, `sum` and `cap_each` require identical units. `multiply` and `divide` accept one unitless side (a count or a percent), or a division of identical units (unitless result), or a **conversion operand**: an operand that declares `unit_from` and `unit_to` and is itself sourced. Anything else is `rejected` with `mixed_units`. Limits (data in `config/rag/calc-limits.json`): at most 50 operands, 200 list items, 30 steps, nesting depth 6. A source that is missing, an alias that is not in this request's `AliasMap`, or an argument that is not a declared name is `rejected` (`unsourced_operand`, `unknown_source`, `unknown_argument`).
- **D-70:** When it is offered. The tool is added to the tool set only when the model supports tools and a quantity signal fires: `scanProtected` (`src/lib/rag/query/protected.ts`) finds a number, amount, percentage or date in the question, or the query classifier (`src/lib/query-classifier.ts`) marks a computation intent through a registry lexicon of neutral function words and the context blocks contain quantities. When it is offered, `instructions.calculation` joins the D-05 block (part 6): extract the operands and the rule from the question and the cited passages into the tool, do not compute mentally, and list each item's step before the total. The tool holds no domain knowledge; every rule it applies is passed in from a cited passage or the question. Values from SEC-05 fact tools, once they exist, take precedence over document values (instruction text only in this phase).
- **D-71:** Claude Citations path. A turn where the tool is offered is eligible for the direct path only under the same proof Phase 5 D-10 requires for `webSearch` (citations and tool calls coexisting in a recorded stream). Until that proof exists, such turns use the chunk-alias path.
- **D-72:** Models without tool support. The instruction asks for the same structure as a trailing block delimited by a fixed tag; a stream transform holds the block back, removes it from the visible text, parses it with the `CalcTrace` Zod and hands it to the check. No JSON mode is used on the streamed answer (Phase 5 D-04).

### Calculation check (GEN-17)

- **D-73:** `RAG_CALC_CHECK` (`false` default). An answer that states a computed number carries a `CalcTrace` (operands with sources, steps, result): from the tool call of D-65, or from the trailing block of D-72. The check runs synchronously at stream end, before `finish` (it is deterministic and takes milliseconds), so its notice can be part of the same response.
- **D-74:** What is checked:
  1. the trace is recomputed with the D-68 module;
  2. every chunk operand's value occurs in the text of its cited block, and every question operand's value occurs in the question, after number normalization;
  3. the number the answer states equals the recomputed result within the rounding the trace declares.
  Number normalization is per language from a new registry field `number_format` (digit grouping characters, decimal mark, full-width digits, magnitude words): data, not code branches. A number written entirely in words cannot be located.
- **D-75:** Outcomes, stored in `checks.calc` (`{ status, stated, recomputed, unit, trace_hash }`):
  - `verified`: nothing is shown beyond the steps the model listed;
  - `corrected` (stated differs from recomputed): `notices.calc_corrected` with the recomputed value is emitted through D-11; both values are stored; the trace is marked; review reason `calc_mismatch`;
  - `not_verified` (an operand cannot be located, the trace is missing or invalid, or the stated number cannot be found): `notices.calc_not_verified` is emitted; review reason `calc_unverified`.
  Streamed text is never rewritten.
- **D-76:** Voice. The answer is generated in the voice agent, so the tool and the check are reached through one new internal route, `POST /api/internal/voice-calc`, authenticated like the other voice routes (`resolveVoiceScope`). The agent registers `calculate` as a function tool whose execution is that route, and on a turn where the tool was called it holds the turn's text back from speech, sends text and trace to the route's check, and speaks the recomputed value in place of a differing stated one (speech has not been delivered yet, so this is not a rewrite of delivered text; the stored transcript keeps both values). Turns without a tool call stream to speech as today. With the switches off the agent behaves exactly as today. App and agent are deployed together (AGENTS.md §8).

### Calculation fixtures (EVAL-26)

- **D-77:** `multi_step_calc` items (zh, en, it; synthetic and neutral): each combines values given in the question with a rule stated in a synthetic document; rule shapes covered are per-item cap, threshold, percentage, tiered rate and date difference. Each item has `calc`: `expected_value`, `unit`, `tolerance`, `paraphrase_group`, and at least three paraphrases per group. Metrics: `numeric_correctness` and `paraphrase_consistency` (all paraphrases of a group give the same number).
- **D-78:** Fakes and gates. A scripted fake that skips the per-item rule (applies the cap to the total) fails the CI gate with `RAG_CALC_CHECK` off and is corrected with it on (the correction notice carries the expected value, both values are in the metadata, a review item exists). A second fake cites an operand that is not in its chunk and must produce `not_verified`. The tool's rejections (free-form code, unsourced operand, mixed units) are unit-tested. With both switches off the answers equal the baseline. Nightly: the live error rate with and without the tool on real models; the switches are recommended for default-on only if numeric correctness rises and no other slice drops beyond the noise band.

### Whole-prompt token budget (RNK-08)

- **D-79:** `RAG_PROMPT_BUDGET` (`false` default). One planner, `planPromptBudget(input)` in `src/lib/rag/context/prompt-budget.ts`, used by the chat route, the embed route and voice-rag. Off: nothing is computed and requests are byte-identical.
- **D-80:** The computation: document budget = model window − system prompt (admin prompt, mode wrapper, D-05 block, fixed notices) − tool schemas − history − question − answer reserve − safety margin.
  - Window: the model's `contextLength` from the five model locations; when unknown, the conservative default from `config/rag/prompt-budget.json` and a `context_length_unknown` trace flag.
  - Answer reserve: the D-31 effective cap when `RAG_MAX_OUTPUT_TOKENS` applies, otherwise the limit `getMaxTokensForModel` gives the request.
  - Margin, the near-limit ratio and the default window are data in `config/rag/prompt-budget.json` (Pydantic `PromptBudgetConfig`), not env vars.
- **D-81:** Counting. Tokens are counted with the existing `tiktoken` dependency (`countContextTokens` in `src/lib/rag/context/budget.ts`) times a per-model-family factor from `eval/config/tokenizer-calibration.json`, plus the margin. The factors are written only by a calibration tool that compares the estimate with the provider-reported prompt tokens of recorded runs; families without a record use the conservative default factor with `source: default`. No provider tokenizer endpoint is called on the request path.
- **D-82:** Trimming order. History is trimmed oldest-first, whole turns, before any document is dropped; the condensed standalone query is kept when the query layer provides one (Phase 6), otherwise the most recent user and assistant turns are the last to go. The question is never trimmed and is always the last message of the request; a builder-level assertion and a test enforce it on every path. Tool-call and tool-result pairs are dropped together.
- **D-83:** Packing documents. Blocks are deduplicated by parent and packed in rank order (rerank score, else fused score, else similarity) until the document budget is reached, keeping the highest-ranked. In v2 the document budget is `min(RAG_CONTEXT_TOKEN_BUDGET, computed budget)` and feeds the existing `selectWithinBudget`. The legacy assembly, which has no budget today, gets the same packing step only while the switch is on. Aliases are assigned after packing (Phase 5 D-02), so a dropped block can never be cited.
- **D-84:** No silent truncation elsewhere. With the switch on, requests are sent with provider-side context transforms explicitly disabled, and no code path relies on the provider truncating. When the system prompt plus the question alone do not fit, the request fails before generation with a structured error `prompt_budget_exceeded` (JSON for non-stream callers, `formatErrorSSE` in-band for streams), never a partial prompt.
- **D-85:** `RAG_CONTEXT_OVERFLOW` = `truncate` (default) | `refine`. It is read only when `RAG_PROMPT_BUDGET` is on. `truncate` is D-83. `refine` answers over several calls when the ranked evidence exceeds the budget: evidence is split into budget-sized batches in rank order, intermediate calls are not streamed and produce a draft with its citations, the last call is streamed; aliases are assigned once over all batches so citations stay valid; at most four calls; chat route only (never voice, embed or WhatsApp); a failure of an intermediate call falls back to `truncate` for that turn. **It is its own optional plan, last in the phase**: success criterion 9 does not depend on it, and the plan checker may move it to the backlog without affecting the rest.
- **D-86:** Trace. `prompt_tokens` per part (`system`, `rules`, `tools`, `history`, `question`, `documents`, `reserve`), `window`, `estimator` and factor source, `dropped_documents`, `dropped_history_turns`, `near_limit`, and the overflow mode used. A summary is stored in `checks.prompt_budget`. These fields feed OBS-03 (Phase 5.3).
- **D-87:** Voice. The agent builds its own prompt, so voice-rag applies the planner to the context it returns: the agent may pass `modelContextLength` and `historyTokens` in its request; when it does not, voice-rag uses the fixed voice document budget from `config/rag/prompt-budget.json`. The agent trims its own history oldest-first when it passes the values.

## Summary

Three things decide how these phases must be planned.

**1. The stream mechanics work, with one hard limit.** A probe on the real `streamText` of `ai@6.0.3` with a mock model showed that a transform passed through `experimental_transform` can hold back text across deltas, replace it, drop the model's text and write its own, and append a notice. The UI message stream, later transforms and `createUIMessageStream`'s `onFinish` (`responseMessage`) all receive the transformed text, so what is persisted is what the user saw. `finishReason: 'length'` reaches the transform on the `finish-step` and `finish` parts, the `messageMetadata` hook and the UI stream's `onFinish`. A transform that holds back a `finish-step` part stalls the stream for good. The existing `aliasParserTransform` is only an observer: it forwards every part unchanged, so it is not a model for a transform that rewrites text. The guard, the sentinel, the trailing calculation block and the notice appender are new rewriting transforms and need tests on the real `streamText`.

**2. Several seams differ from what the decisions assume.** Each is small on its own; together they decide plan order.
- The composed block is appended to `systemPrompt`, but the chat route then appends a tool sentence to it and sends eight more system messages after it. "Security last" holds inside the block, not for the whole request.
- The strict and balanced mode wrappers in `src/lib/rag-mode.ts` already tell the model to include links from the context's links section and to state a fixed English sentence when information is missing. The wrappers cannot be edited (D-03), so the output policy statement and the sentinel instruction must be worded to take precedence over them.
- `rag_answer_records.review_reasons` has a CHECK constraint that allows two values. Appending `claim_unsupported` (and later `calc_mismatch`, `calc_unverified`) fails until a migration replaces it. D-02's plan for 0944 names only `rag_review_items`.
- `rag_answer_records.answer_language` is filled today with the language detected from the answer text. D-09 uses the same name for the language of the question.
- The eval answer is produced by `generateText` in `src/lib/rag-eval/answer.ts`, not by the chat route's stream. Gated slices therefore exercise the whole-text functions; split-token behaviour needs separate stream tests.
- The WhatsApp handler parses the legacy line format (`0:"text"`). The chat route emits the UI message stream as SSE `data:` lines. By reading the parser, no text is collected from the current format, and the handler falls back to a fixed apology. This must be checked with a test before the WhatsApp parts of SEC-06 and D-11 are planned.
- `fetchAssemblyRows` selects `id, filename, created_at, content, metadata`. It selects neither `version` nor `user_id`, so `ContextBlock.documentVersion` is null on the retrieved-chunk path today.
- The voice route on this branch returns `results`, and the voice agent builds its own context string. The `context` field that D-07 relies on is Phase 5.1 plan 05.1-20, not yet merged.

**3. Phase 5.2.1 has two structural constraints.** The step handler of the chat route sets the output of every tool result to null unless the tool is `webSearch` or `query_documents`, and puts every other tool call into the approval state; `calculate` must be added to that allow set and to `ANSWER_EVIDENCE_TOOLS`. Tools are removed entirely when the model id contains `claude-sonnet-4`, which includes the default model, so the trailing-block path of D-72 is the one the default model uses. And the v2 document budget is applied inside `runRetrieval`, before the route has built the system prompt or discovered MCP tools, so the budget planner must run before retrieval on estimates and be asserted after the request is built.

No new npm or Python package is needed in either phase.

**Primary recommendation:** Build the three pure cores first (text registry reader, sentence splitter, output guard), each with whole-text and every-split-point tests. Chain all text-changing transforms through one builder in the fixed order citation, sentinel, calculation block, guard, notice and collector. Keep every check after the stream in the existing `after()` job, with one deadline. Put the migration that widens `review_reasons` in the first wave.

### Pattern 3: Streaming output guard

**Verified mechanics** (probe on `ai@6.0.3`, real `streamText`, `MockLanguageModelV3`, transform order sentinel, guard, notice, observer; the "model deltas" notes are added, the other lines are probe output, shortened where "..." appears; the probe guard matched only `http(s)://` up to whitespace):

```
=== url split, stop                 model deltas: "See ht" | "tps://ex" | "ample.test/a?b=1" | " now. Done"
 text: "See [link removed] now. Done"
 onFinish: {"finishReason":"stop","isAborted":false,"text":"See [link removed] now. Done", ...}
 late saw: ["See ","[link removed] now. Done"]
=== url cut by length               model deltas: "Text before " | "https://exam", finish reason length
 text: "Text before [link removed]\n\nNOTICE truncated"
 onFinish: {"finishReason":"length", ... ,"meta":{"finishReason":"length"}}
=== tool step then text (length)
 types: start,start-step,tool-input-available,tool-output-available,finish-step,start-step,text-start,text-delta,text-delta,text-delta,text-end,finish-step,finish
 text: "Result is 2 [link removed] ok\n\nNOTICE truncated"
```

One transform instance sees all steps of a multi-step call. Transforms are piped in array order before the SDK's own output and event processing [VERIFIED: `ai@6.0.3` `dist/index.mjs`, `for (const transform of transforms) { stream = stream.pipeThrough(transform({ tools, stopStream() { ... } })) }` followed by `this.baseStream = stream.pipeThrough(createOutputTransformStream(...)).pipeThrough(eventProcessor)`].

**Algorithm (pure core, `push(delta)` returns the text that may be released):**

1. Work on text per text-block id. Keep a held tail; release everything before it.
2. **Word-level hold.** A run of label characters (ASCII letters, digits, `-`, `_`, and `%`) is held until the next character arrives. This is what makes a bare domain and an e-mail address detectable: the first label looks like any word until the dot or the `@` follows. In ordinary prose the hold lasts one word.
3. **Candidate starts** (D-38): a scheme (`[a-z][a-z0-9+.-]*://`, plus the opaque schemes listed as data: `mailto:`, `tel:`, `sms:`, `javascript:`, `data:`, `file:` and the like), `www.`, an `@` between label characters, a label followed by a dot and a label, `[` (possible Markdown link or citation marker), `![` (image), `<` followed by a scheme (autolink), and the obfuscation forms listed as data (bracketed or spelled-out dots, a look-alike scheme).
4. **Candidate ends** at whitespace, a CJK character, CJK punctuation, a closing bracket that is not part of the URL, sentence punctuation followed by whitespace or the end, or the bounds (2,048 characters for a URL, 300 for Markdown link text). Trailing `.,;:!?` and their full-width forms are trimmed from the candidate, as `TRAILING_URL_PUNCTUATION` already does in `src/lib/rag/query/protected.ts:19`.
5. **`[` handling:** hold from `[`. At `]`, look at one more character: `(` continues as a Markdown link (hold to the matching `)`); `[` continues as a reference link; `:` at line start is a link definition; anything else releases the bracket text at once. Citation markers (`[S3]`, `【S3】`, `［S3］`) are therefore delayed by one character only.
6. **Decision:** normalize the host (below), apply allow rules 1 to 4 of D-37, then keep or replace. At `flush()` decide the held tail as it stands.
7. **Credential sentences** (D-39): start buffering the current sentence only when a rule's first term has been seen in it; decide at the sentence end or at a bound (use the splitter's sentence-end set; cap the buffer, for example 600 characters, then decide on what is held).

**Worst-case held text:** 2,048 characters (URL) or 300 plus 2,048 (Markdown link text plus target), plus one credential sentence. In prose without candidates: one word.

**Host normalization, verified on Node 22.23.5 (ICU 78.3)** (probe output, columns aligned; the remarks in parentheses are added):

```
"ｅｘａｍｐｌｅ．test" -> nfkc "example.test" changed true  ascii "example.test"
"exаmple.test"      -> nfkc "exаmple.test" changed false ascii "xn--exmple-4nf.test"     (Cyrillic а)
"a。b.test"          -> nfkc "a。b.test"    changed false ascii "a.b.test"                (U+3002 becomes a dot in IDNA)
"https://example.test。" => https: example.test.
"https://user:pw@example.test/x" => https: example.test CREDS
"hxxp://example[.]test" => invalid
```

Rules that follow from this output:
- Compare hosts in their ASCII form (`domainToASCII` after NFKC and lower-casing). A look-alike host then has a different ASCII form and cannot match the allowlist.
- Reject a host whose NFKC form differs from its input (D-37).
- U+3002 is not changed by NFKC but IDNA maps it to a dot, and the WHATWG parser keeps it in the host. Because D-38 ends a candidate at CJK punctuation, `https://example.test。` is decided as `example.test`, and a host written with U+3002 between labels is cut at the first one and fails the allowlist. Never pass text beyond CJK punctuation to `new URL`.
- Strip one trailing dot from the host before comparing.
- Obfuscated forms do not parse; they are detected by the data-listed patterns and always replaced.

**False positives to design for:**
- Decimals and version numbers (`3.5`, `v2.1.0`, `1.234,56`) never match, because the last label must be alphabetic (or `xn--`) and in the TLD snapshot.
- File names do match: `md`, `py`, `sh`, `zip`, `mov`, `app`, `dev` are top-level domains in the IANA list read this session; `pdf`, `doc`, `txt`, `csv`, `json`, `html` are not. The mode wrappers ask the model to cite sources by file name, so D-37's exemption for tokens equal to a document name in this request's blocks is required, not optional.
- Two words joined by a period without a space can form `word.tld`. Measure this in `flag` mode on the clean fixture answers and gate "no removal on clean fixture answers" next to the credential-rule gate of D-39.

**Adapters:**
- Stream: release text as `text-delta` parts with the block's id; on `text-end` flush that block; on `finish` flush everything. Never hold `finish-step` (Pitfall 1).
- Whole text: `push(text)` then `flush()`; the property test of D-35 compares it with every split point of every fixture answer.

- On a match: drop that block's model text, write `fixedText('notices.no_information', answerLanguage)`, set `refusal_origin: 'model_relevance'` on the trace, set the retrieval-log outcome holder to `refused_no_context` (Phase 5.1.1 D-07), mark the turn so that citations, groundedness and the claim check treat it as a refusal.
- Form (Claude's discretion): an ASCII token of characters without Markdown meaning, two or more words joined by underscores between doubled delimiters, case-sensitive. ASCII is reproduced more reliably by models than rare Unicode brackets [ASSUMED].
- Neutralize the sentinel string inside block text before it is sent, the way Phase 5 neutralizes marker-like text in chunks, so a document cannot make the model echo it (Pitfall 13).
- The refusal control of Phase 5.1.1 D-08 reads `refusal: true` from the `start` metadata. A sentinel refusal is known only after `start` was sent, so it must travel in the `finish` metadata, and the client must read it from the merged metadata.

### Pattern 5: Sentence splitter

**`Intl.Segmenter` is available but not usable as the splitter** (Node 22.23.5):

```
en       ["The value is 3.5 units [S1]. ","See sec. 4 for more. ","Version v2.1.0 applies! ","Is it so? ","Yes."]
en-abbr  ["It applies e.g. to item A. ","Dr. ","X agreed [S2]. ","Next."]
zh       ["数值为3.5单位[S1]。","另见第4条！","是否如此？","是的。","没有标点的结尾"]
zh, marker after the full stop   ["数值为甲。[","S1]下一句是乙。【","S2】"]
en, marker after the full stop   ["Value is A. ","[S1] Next sentence is B.[","S2] Third."]
it       ["Il valore è 3,5 unità [S1]. ","Vedi l'art. 4 per altro. ","L'importo è 1.234,56. ","Va bene?"]
```

It keeps decimals and most abbreviations, but it cuts inside a citation marker that follows end punctuation, and it splits after a title abbreviation followed by a capital.

**Prescribed algorithm (rules-based, D-18):**
1. Block pass on the raw text: fenced code block, table (consecutive lines starting with `|`), heading line, list item line. Each is one unit with its kind.
2. Mask citation markers with `findCitationMarkers` from `@/lib/citations/marker-grammar` (same-length placeholder), so offsets are unchanged.
3. In paragraph text, split at the pack's `sentence_end` characters unless: a digit is on both sides; the next non-space character is a lowercase letter or a digit (Latin scripts); the position is inside a URL, a quoted span or a masked marker.
4. Attach to the sentence any whitespace and markers that directly follow its end punctuation (D-19).
5. Merge a unit with fewer than three letters into the next one (covers abbreviations followed by a capital). A per-pack abbreviation list as data is the stronger fix; it is a small addition to `LanguagePack`.
6. Return `{ index, start, end, text, kind }` with offsets in UTF-16 code units of the text as persisted.

**Existing splitters to reconcile:** `SENTENCE_END` in `src/lib/rag/ingest/chunkers/markdown-sections.ts:37` (`/(?<=[.!?;。！？；])\s+|(?<=[。！？；])/u`, which treats semicolons as sentence ends) and the `Intl.Segmenter` call in `src/lib/rag/context/compress.ts:53`. D-18 says to reuse the Phase 3.2 LANG-06 splitter where it exists (plan 03.2-20); if it lands first, `splitAnswerSentences` wraps it and adds the block pass, the marker rule and offsets.

**`text_hash`:** SHA-256 of the persisted answer text (the text parts of `responseMessage` joined, which is what `finishAnswerRecord` receives). The client recomputes it with `crypto.subtle.digest` before showing marks.

### Pattern 7: Claims endpoint

**What exists:** the scorer protocol scores one pair (`async def score(self, premise_texts, hypothesis) -> float`, `rag-sidecar/src/rag_sidecar/groundedness/scorer.py`); the local scorer calls `model.predict([(premise, hypothesis)])` under `asyncio.Semaphore(1)` (`local_hhem.py:105`, `:117`); the router allows Vectara for `{"en", "zh-hans"}` and the local model for `{"en"}` and caps the premise at 60,000 characters (`router.py:16-21`).

**Vectara takes one generated text per request.** The request has `generated_text` and `source_texts`; batching is not documented, nor are size or rate limits; the response is `{"score": ...}` [CITED: docs.vectara.com/docs/rest-api/evaluate-factual-consistency]. A 40-sentence answer is 40 requests.

**Prescription:**
- Add `score_many(pairs) -> list[float | None]` to the scorer protocol. Local: micro-batches of 4 to 8 pairs through `model.predict(list_of_pairs)` under the existing semaphore. Vectara: bounded concurrency (for example 4) over the existing client; no retry.
- `premises[]` is sent once; each claim names `premise_refs[]`; the sidecar builds the premise text per claim.
- The sidecar enforces its own deadline (a setting below the app's `RAG_GROUNDEDNESS_TIMEOUT_MS`, default `20000`) and returns every unfinished claim as `not_checked` with reason `timeout`, so the app gets partial results inside its own timeout.
- Per-claim premise: the cited blocks of that sentence; add other blocks only for an uncited factual sentence, and cap the per-claim premise well below `RAG_GROUNDEDNESS_MAX_PREMISE_TOKENS` (default `3000`). See Pitfall 9 for the arithmetic.
- The answer-level score and the claim step share one deadline, started when the `after()` job starts.

### Pattern 8: Judge and its calibration

- Helper call with `generateObject` and the generated `ClaimJudgement` Zod schema, the way `src/lib/rag/ingest/profiles/llm-detect.ts` and `src/lib/rag/ingest/invoice-client.ts` make structured helper calls [VERIFIED: both files import `generateObject` from `ai`].
- Family rule: Python has `generator_family` and `assert_judge_family_differs` in `eval/src/rag_eval/judge/config.py`. There is no TypeScript equivalent. Move the family table to a data file read by both sides, or mirror it in TypeScript with shared test vectors; an unknown family yields `not_checked`, never an assumption.
- Calibration tool: `python -m rag_eval.calibrate groundedness-judge`, next to the existing `refusal` and `groundedness` subcommands in `eval/src/rag_eval/calibrate/__main__.py`. The judge runs in TypeScript, so the tool spawns a harness script (the `harness_runner.py` pattern) that runs `judge.ts` over a labelled file and writes JSONL.
- Labelled data: a new file of synthetic answers with a label per sentence (`supported` or `unsupported`), dev and test splits, zh, en and it. A production lookup with the real judge model finds no cell and returns `judge_uncalibrated`.

### Pattern 9: Version labels and conflict rules

Number and date extraction can reuse the patterns of `scanProtected`.
- The candidate row uses origin `answer_conflict`, which Phase 3.2 D-41 reserves.

### Pattern 10: Fake models on the eval path

- The eval harness selects a generator by name (`export type EvalGenerator = 'stub' | 'live' | 'fake';`, `eval/harness/run-eval.mts:41`) and installs a factory that receives the model id (`installFakeCitationGenerator`). Add the new fakes to one factory that dispatches on the model id (`fake/rule-following-v1`, `fake/violating-partial-v1`, and so on), so a run config selects a fake through `generator_model`.
- A fake reads the system prompt and the question from `options.prompt`, as `promptParts` does today. The rule-following fake behaves correctly only when the instruction's marker line is present.
- The eval route does not generate for a refused item (`refused = result.refusalCandidate || result.refusal?.decision === 'refuse'`), so the below-threshold half of `off_topic_context` never reaches a fake; the above-threshold half does and must come back as a sentinel refusal. The trace needs a field that says the refusal came from the model.
- Run configs live in `eval/config/runs/` (`v2-all-off.json`, `v2-recommended.json` today) and are passed with `--run-config`. A run config may set only the variables in `RUN_CONFIG_ENV_ALLOWLIST` (`eval/harness/run-config.mts`); every switch of these phases that a gated run turns on must be added to that list, or the harness rejects the file. Add one run config per gated configuration.

### Pattern 11: Security events

- One builder; request-path sources write through `scheduleAfterResponse` (`src/lib/rag/trace/schedule.ts`), ingestion writes inline, failures are swallowed with one `[RAG Security]` line.
- Tenant key columns follow the 0502 pattern (generated column per mode) or carry a copied key checked by `rag_assert_tenant_key`, as D-43 says; the plan decides once and uses the same form for all three new tables.
- The alert function runs after the insert and relies on a unique index per uploader and window so concurrent events create one alert.

### Anti-Patterns to Avoid

- **Holding `finish-step` in a transform.** It stalls `streamText`.
- **Concatenating an instruction in the route.** Only the composer adds text.
- **Editing the mode wrappers or the admin prompt to resolve a conflict.** Word the appended part instead.
- **Recomputing sentence offsets in Python.** Offsets are UTF-16 code units; the eval reads the records.
- **A second per-language table.** Texts live in the registry; `check-language-literals.mjs` enforces it.
- **Passing a held candidate with CJK punctuation to `new URL`.**
- **Selecting new document columns unconditionally.** A column that the database lacks fails the whole assembly read.
- **Asserting stream behaviour through `createStreamTextCapture`.** It replaces `streamText`; transforms never run there.

## Common Pitfalls (Phase 5.2)

### Pitfall 1: A transform that holds `finish-step` stalls the stream
**What goes wrong:** the request never ends.
**Evidence:** a transform that buffered `text-end` and `finish-step` until `finish` produced `TIMEOUT tailHold` in the probe; the same transform holding only `text-end` and deciding at `finish-step` completed. The stall is an observed result on `ai@6.0.3`; the cause (the next step or the final `finish` is only produced after the downstream consumer has seen `finish-step`) is [ASSUMED].
**How to avoid:** a transform may hold `text-delta` and `text-end`. It must forward `finish-step`, `start-step`, tool parts and `finish` at once. Append end-of-answer text when the `finish-step` whose `finishReason` is not `tool-calls` arrives, into the held text block.
**Warning signs:** a stream test that needs a timeout to finish.

### Pitfall 2: The existing citation transform is an observer
`aliasParserTransform` calls `controller.enqueue(part)` for every part and only feeds a parser (`src/lib/rag/generation/citations/transforms.ts`). `claudeMarkerTransform` is the one existing transform that adds text. Neither holds text back. Do not plan the guard as "the same pattern"; plan it as new code with its own tests on the real `streamText`.

### Pitfall 3: The composed block is not the last instruction the model reads
After the composer's seam the route appends a sentence about an e-mail tool to the same string and sends eight further system messages (list in Pattern 1). Any test that asserts "the policy statement is the final system text" fails. Assert presence and order inside the block.

### Pitfall 4: The mode wrappers already instruct the model on links and on missing information
**Evidence:** `src/lib/rag-mode.ts:42-46` (strict) and `:83-87` (balanced): "IMPORTANT - Link Usage: When the context includes a "RELEVANT LINKS" section: - Include clickable links naturally in your response using markdown format: [descriptive text](URL)". Line 32 (strict): `You must explicitly state "This information is not in my knowledge base and web search is disabled."` The strict wrapper also asks for a source line with the file name.
**Consequences:**
- With the guard on, the links section must contain only targets that pass the allowlist (D-06), and `OUTPUT_POLICY_NOTICE` must say that targets listed in that section may be used; otherwise the two instructions contradict each other.
- The link instruction for the chat route is in the wrapper. `createLinkUsageInstructions` is used only by the embed route's default prompt (`src/app/api/embed/chat/route.ts:268`). Narrowing that function does not change the chat route.
- The sentinel instruction must state that it replaces any other wording for missing information.
- File names in source lines are why the document-name exemption of D-37 is needed.

### Pitfall 5: `answer_language` already has a meaning
**Evidence:** `src/lib/rag/generation/answer-finish.ts:379` writes `answerLanguage: detectLanguage(input.answerText)`: the language of the answer text. `answerGroundednessLanguage` uses the same detection to route the scorer. D-09 defines `answer_language` as the language of the question.
**How to avoid:** decide once (Open Question 1). Recommended: scorer routing keeps using the language detected from the answer text and stores it inside `groundedness` and `checks`; the column takes D-09's value only on requests where a Phase 5.2 switch is on, so the all-off insert stays identical.

### Pitfall 6: The switch-off refusal path is not "English by default" in a simple way
It is English for every UI language except when a Spanish heuristic fires on an English UI (Pattern 2). The registry has no Spanish. With `RAG_REGISTRY_TEXTS` on, a Spanish question follows D-09's fallback chain. The characterization tests must keep running with the switch off, and a second set must pin the switch-on behaviour for zh, en, it and a non-enabled language.

### Pitfall 7: `Intl.Segmenter` cuts inside citation markers
See the probe output in Pattern 5 (`"数值为甲。[","S1]下一句是乙。【","S2】"`). A sentence would lose its marker and count as uncited. Mask markers before splitting.

### Pitfall 8: Offsets are UTF-16 code units
JavaScript string indices count code units; Python counts code points. D-18 already says the eval must read the sentence records from the trace. Add a fixture answer with characters outside the Basic Multilingual Plane and assert the client can slice every sentence by its offsets.

### Pitfall 9: Per-sentence scoring multiplies the scorer's work
**Evidence:** the local scorer processes one pair at a time behind `asyncio.Semaphore(1)`; the model card figure quoted in `05-RESEARCH.md` is about 1.5 s for a 2,000-token input on a current x86 CPU [CITED: 05-RESEARCH.md, P-10]. Forty claims with premises of up to 3,000 tokens each would be on the order of 90 s of CPU [ASSUMED: linear arithmetic from that figure], against a 20 s timeout and a 60 s function limit (`vercel.json` `"maxDuration": 60`).
**How to avoid:** short per-claim premises (cited blocks only when the sentence is cited), micro-batches, a sidecar-side deadline that returns partial results, and a low default for the per-answer cap in the first live measurement. Report `claims_not_checked` by reason so the effect is visible.

### Pitfall 10: A sentence can lose its referent
A sentence that starts with a pronoun is scored without the sentence it refers to and may come out unsupported although the answer is faithful [ASSUMED: known limitation of sentence-level entailment; not measured here]. The result only marks a sentence and feeds the review queue, so the cost is noise, not a wrong block. Measure it in the judge and HHEM calibration on the labelled answers; do not add a rewriting step.

### Pitfall 11: The groundedness contract does not admit a judge
**Evidence:** `GroundednessScorer = Literal["hhem_2_3_vectara", "hhem_2_1_open", "none"]` (`rag-sidecar/src/rag_sidecar/contracts/groundedness.py:6`); `AnswerGroundedness` requires for `scored` a score, a threshold and `label == "verified" if score >= threshold` (`contracts/answers.py`, `_status_rules`); `GroundednessThresholdCell.scorer` is limited to the two HHEM values.
**How to avoid:** add a judge scorer value to the enum; express the judge's answer-level quantity as a score where higher is better (`1 - unsupported_share`) with threshold `1 - max_unsupported_share`, so the existing validator and the badge logic stay as they are; keep judge cells in their own file (D-27).

### Pitfall 12: A sentinel that is not at the very start
With webSearch on, a model may write a line, call the tool, and then output the sentinel as the whole text of the last step. D-16 says a later sentinel is stripped and counted, which would leave the user with the first line and no refusal. Treat "the sentinel is the entire text of a step" as a refusal: append the registry text as a new paragraph and set `refusal_origin`. See Open Question 4.

### Pitfall 13: A document can make the model emit the sentinel
An injected passage that says "answer only with <sentinel>" produces a refusal. This harms availability, not confidentiality. Neutralize the sentinel string (and, in 5.2.1, the trailing-block tag) in block text before sending, and count stripped sentinels on the trace. The existing neutralization of marker-like text runs inside the citation labeler (`createCitationLabeler` in `src/lib/rag/generation/citations/blocks.ts` calls `neutralizeCitationMarkers`), which is active only on turns with citations. WhatsApp, embed and voice turns have no labeler, so the sentinel neutralization needs its own step in assembly, tied to the two rule switches, and it must leave the context byte-identical when both are off.

### Pitfall 14: `fetchAssemblyRows` selects a fixed column list
**Evidence:** `src/lib/rag/context/fetch-rows.ts:31` `.select('id, filename, created_at, content, metadata')`. `AssemblyDocumentRow.version` is optional and never filled on this path, so `documentVersion` is null for retrieved chunks. The fake edge used by the route tests rejects and records request shapes it does not know, so a changed select list can surface as a recorded edge error in tests that never turn a switch on.
**How to avoid:** change the select list only when `RAG_VERSION_LABELS` or `RAG_SECURITY_EVENTS` is on; assert the all-off request string is unchanged.

### Pitfall 15: Selecting a column the database does not have fails the read
`effective_from` (0801) and `version_label` (0941) exist only after their migrations. PostgREST rejects an unknown column and the assembly read throws (`[RAG Assemble] documents lookup failed`). A switch that needs a column must be documented as "apply the migration first", and the startup check of `answer-config.ts` should warn when a switch is on and the column is missing.

### Pitfall 16: The WhatsApp handler may not read today's stream format
**Evidence:** `src/lib/whatsapp/webhook-handler.ts` (stream loop in `processMessageThroughMyRAG`) takes `line.substring(colonIndex + 1)` and continues only `if (contentPart.startsWith('"'))`. An SSE line `data: {"type":"text-delta",...}` gives a content part that starts with a space and a brace. By reading the code, no text is collected and the reply becomes the fixed fallback sentence. Not executed here (no test covers it in `tests/whatsapp`).
**How to avoid:** the first WhatsApp task is a test that feeds the handler the chat route's real stream. If it fails, fixing the parser is a precondition for D-40 and for the plain-text notice of D-11, and it changes WhatsApp behaviour with every switch off; that needs the owner's word (Open Question 2).

### Pitfall 17: The Baileys policy recognises only URLs with a scheme
`allowsLinkPreview` matches `https://…` and `scheme://…` patterns (`baileys-whatsapp/src/Service/link-preview-policy.ts`). With an empty `WHATSAPP_LINK_PREVIEW_HOSTS` (the default) `buildTextMessage` always returns `linkPreview: null`, so nothing is fetched. With hosts configured, a text whose only link is allowlisted allows the preview. The per-message `linkPreview: false` field of D-40 must force `linkPreview: null` regardless of the hosts. The health endpoint should return host names only.

### Pitfall 18: Review reasons are constrained in four places
1. `supabase/migrations/0501_rag_answer_records.sql:29-30`: `CHECK (review_reasons <@ ARRAY['feedback_negative', 'groundedness_flagged']::text[])`.
2. `src/lib/answers/store.ts:8` `export type ReviewReason = 'feedback_negative' | 'groundedness_flagged';` and `:57` `REVIEW_REASONS`.
3. `rag-sidecar/src/rag_sidecar/contracts/review.py:12` `ReviewReason = Literal["sampled", "feedback_negative", "groundedness_flagged"]`.
4. Phase 5.1.1 (not here): the reason check on `rag_review_items` and the priority order inside `rag_mine_failed_queries`.

A migration in the 0940 block must drop and re-add the constraint on `rag_answer_records` with the new values (idempotent: `DROP CONSTRAINT IF EXISTS`, then `ADD CONSTRAINT`). The setup files also define this table, but 094x files are applied on top and are not folded (D-02), so the migration alone carries the change. Phase 5.2.1 needs the same step for `calc_mismatch` and `calc_unverified`; adding all five values in one 5.2 migration avoids a second constraint rewrite (the planner decides; D-02 expects one 5.2.1 migration "at most").

### Pitfall 19: Items that do not come from a question do not fit the review item shape
`rag_review_items` (Phase 5.1.1 D-14) carries `query_masked`, `query_fingerprint` and a unique key `(tenant_key, query_fingerprint, mining_window)`. `output_guard` and `version_conflict` items come from the embed, WhatsApp and voice paths too, and a `version_conflict` item is about a document pair. `rag_enqueue_review_item` must define what goes into those columns (for example a fingerprint derived from the reason and the sorted source ids, and the week of the event as the window) so that repeated events deduplicate and the unique key still holds. Expert visibility follows the existing RLS helper on `tenant_key`.

### Pitfall 20: The uploader can be null
Single-tenant `documents.user_id` is nullable with `ON DELETE SET NULL`. Events without an uploader are stored, never counted towards an alert and never held.

### Pitfall 21: The eval path does not stream
`generateEvalAnswer` calls `generateText` (`src/lib/rag-eval/answer.ts`). Gated slices therefore prove the composer, the whole-text sentinel, the whole-text guard, the splitter and the metrics. "Split across stream tokens" (D-42, success criterion 4) must be proven by vitest tests on the real `streamText` with the same fixture answers (D-35's property test). Route tests built on `createStreamTextCapture` prove wiring only, because that helper replaces `streamText`.

### Pitfall 22: Sentence records must describe the final text
The citation session accumulates the text before the guard runs. Compute sentence records, `text_hash` and notices in a last transform (the collector) that sees the text after every rewriting transform, and use the same text that `onFinish` receives in `responseMessage`.

### Pitfall 23: Registry texts pass through the guard on plain-text channels
A notice appended as text on WhatsApp is filtered again by the handler's whole-text pass. No registry text may contain a link, a domain-like token or a credential-rule match. Add this to the registry completeness check: run the guard and the credential rules over every text of every pack and require zero findings.

### Pitfall 24: `retrievalConfigHash` exists only for v2
It is computed by `computeRetrievalConfigHash` in `src/lib/rag/v2/result.ts`. Under the legacy pipeline there is no hash to extend. D-58 is met by extending the v2 inputs; the retrieval-log column is nullable for legacy.

### Pitfall 25: Ghost chats and channels without an answer record
`finishAnswerRecord` returns early without `answerId`, scope or user. Embed, WhatsApp, voice and ghost chats have no row for `checks`. Their guard events use the security-event table and the direct enqueue route (D-55); nothing else of `checks` is stored for them.

## Code Examples

### Notice at the final step without holding `finish-step` (verified shape)

```ts
// Source: probe run this session on ai@6.0.3 (real streamText, MockLanguageModelV3)
import type { StreamTextTransform, TextStreamPart, ToolSet } from 'ai';

type Part = TextStreamPart<ToolSet>;

export function noticeTransform(textFor: (finishReason: string) => string | null): StreamTextTransform<ToolSet> {
  return () => {
    let heldEnd: Extract<Part, { type: 'text-end' }> | null = null;
    return new TransformStream<Part, Part>({
      transform(part, controller) {
        if (part.type === 'text-end') {
          if (heldEnd) controller.enqueue(heldEnd);
          heldEnd = part;
          return;
        }
        if (part.type === 'finish-step' && part.finishReason !== 'tool-calls') {
          const text = textFor(part.finishReason);
          if (text && heldEnd) controller.enqueue({ type: 'text-delta', id: heldEnd.id, text: `\n\n${text}` });
        }
        if (heldEnd) {
          controller.enqueue(heldEnd);
          heldEnd = null;
        }
        controller.enqueue(part);
      },
      flush(controller) {
        if (heldEnd) controller.enqueue(heldEnd);
      },
    });
  };
}
```

When the final step has no text block, write a new block (`text-start`, `text-delta`, `text-end`) before forwarding `finish-step`; the probe covered that branch only by code path, not by a case, so it needs its own test.

### Guard adapter around the pure core

```ts
// Source: pattern verified by the same probe; the core (createOutputGuard) is this phase's new module
export function outputGuardTransform(guardFor: (textId: string) => { push(delta: string): string; flush(): string }): StreamTextTransform<ToolSet> {
  return () =>
    new TransformStream<Part, Part>({
      transform(part, controller) {
        if (part.type === 'text-delta') {
          const out = guardFor(part.id).push(part.text);
          if (out) controller.enqueue({ ...part, text: out });
          return;
        }
        if (part.type === 'text-end') {
          const rest = guardFor(part.id).flush();
          if (rest) controller.enqueue({ type: 'text-delta', id: part.id, text: rest });
        }
        controller.enqueue(part);
      },
    });
}
```

## Phase 5.2.1 Research: Calculation Tool & Prompt Budget

This part is written for the Phase 5.2.1 planner. It assumes Phase 5.2 has delivered `fixedText`, `composeAnswerRules`, `emitNotice`, the transform chain builder, `rag_answer_records.checks`, the review-reason routes, the golden categories and the fake-model harness.

### 5.2.1 Architecture Patterns

#### Pattern A: Exact rationals over `BigInt`

- A value is `{ n: bigint, d: bigint }` with `d > 0n`, reduced by the greatest common divisor after every operation. Parsing accepts only `^-?\d+(\.\d+)?$` (no exponent, no grouping, no sign prefix other than `-`, no `NaN` or `Infinity` words).
- `add`, `subtract`, `multiply`, `divide` are exact. `min`, `max` and the comparison inside `cap_each` compare by cross-multiplication. `percentage` is `value * percent / 100`.
- `round(mode, places)`: scale by `10n ** places`, integer-divide, decide by the remainder. Fix the mode names to the definitions of Python's `decimal` module (`half_up`: ties away from zero; `half_even`; `up`: away from zero; `down`: toward zero) and state them in the contract docstring, because "up" is read in two ways.
- `date_diff`: convert a civil date to a day number with integer arithmetic (no `Date`, because `Date.UTC` returns a floating-point number and D-68 forbids floats in the module). Define `months` and `years` as complete units (the end day-of-month before the start day-of-month subtracts one) and `inclusive` as plus one day for the `days` unit.
- Display: 10 decimal places, half-even, `display_rounded: true` when the exact value has more.
- **Oracle:** generate test vectors with Python `fractions.Fraction` and `decimal` in the eval package and commit them as JSON (the `samples.json` pattern); the TypeScript tests replay them. This gives a second implementation without a new dependency.
- **Float ban as a test:** a test reads the files of `src/lib/rag/calc/` and fails on `Number(`, `parseFloat`, `Math.`, `Date.` and decimal literals.

Sanity check run this session: `0.1 + 0.2` gives `3/10` with this representation and `0.30000000000000004` with floats.

#### Pattern B: Tool registration and when it is offered

- Register `calculate` in the tool object the route calls `allTools`, next to `useDocument` (created in `baseTools`) and the conditional `webSearch`, with `tool({ description, inputSchema, execute })` and `z` from `zod/v3`, as the `webSearch` tool does. A probe with `generateText`, `MockLanguageModelV3`, a strict `zod/v3` object schema and `stopWhen: stepCountIs(3)` ran the tool and continued to a second step.
- `execute` closes over the request's `AliasMap` aliases and block texts and the question text; it validates sources, evaluates and returns `CalcResult`; it also stores the request and result in a per-request holder that the check reads.
- **One predicate for "this turn can use tools":** `SUPPORTS_TOOLS` is true for the `openai`, `openrouter` and `groq` providers, but the route deletes `tools` and sets `toolChoice: 'none'` when the model id contains `claude-sonnet-4` (variable `isClaudeSonnet4`). The default model id in `scripts/init-env.js` is `anthropic/claude-sonnet-4.5`, which matches. D-70 ("when the model supports tools") and D-72 (trailing block otherwise) both read this predicate.
- **Tool input schema without unions.** Model `CalcOperand.source` as one object with `kind` and optional `alias`, `tool`, `key`, validated by a Pydantic model validator, and `value` / `values` / `unit_from` / `unit_to` as optional fields. The generated JSON Schema then has no `anyOf`, which tool-calling providers handle unevenly [ASSUMED]. The shape still matches D-66.
- **Citations path:** add "calculation tool offered" to the facts that `selectCitationStrategy` reads, so such turns take the chunk-alias path (D-71).
- **Quantity signal:** `scanProtected` (`src/lib/rag/query/protected.ts`) already has patterns for currency amounts, numbers with units, explicit dates and versions. The query classifier has no computation category today (`category: 'conversational' | 'tool_required' | 'document_search' | 'complex' | 'multi_step'`, `src/lib/query-classifier.ts:12`), so the "computation intent" half of D-70 is new: a registry lexicon of neutral function words checked next to the classifier, not a new classifier category.

#### Pattern C: The check, and what it can and cannot detect

- It runs in the last transform at the final `finish-step` (same place as the truncation notice), so the notice is part of the response.
- It detects: a stated number that differs from the recomputed trace; an operand that is not in its cited block or in the question; a missing or invalid trace.
- It cannot detect a wrong rule that was extracted consistently: if the trace applies a limit to the total and the stated number equals that computation, the check verifies it. Only `numeric_correctness` on the fixtures measures that.
- **Consequence for the fake of D-78:** the "skips the per-item rule" fake must carry a correct trace (per-item limit, then sum) and state the number obtained by limiting the total. Then the recomputed value equals the item's expected value, the notice carries it, and with the check off the answer fails `numeric_correctness`.
- **Locating the stated number** needs a rule the decisions do not give (Open Question 6). Recommended: the answer is `verified` when the recomputed value, in any of the pack's number formats and at the declared rounding, occurs in the answer text; otherwise the stated number is the last number in the answer that is neither an operand value nor an intermediate step value; when there is none, `not_verified`.
- **Number normalization** (`number_format` in the pack): digit grouping characters, decimal mark, full-width digits, magnitude words. Normalize the text to canonical decimal strings first, then compare as rationals, never as text.

#### Pattern D: Budget planning before retrieval, assertion after assembly

**Why:** in v2 the document budget is applied inside the pipeline (`selectWithinBudget(budgetInput, settings.tokenBudget, …)` in `src/lib/rag/v2/stages/context.ts`), and the route builds the system prompt and discovers MCP tools after `runRetrieval` returns. Aliases are assigned during assembly, so nothing may be dropped afterwards.

**Sequence:**
1. Before retrieval: count the admin prompt and mode wrapper without context, the composed block (compose it against an empty context), the fixed notices, the static tool schemas (`useDocument`, `webSearch`, `calculate`), a reserve for MCP tool schemas when MCP is on for the request (a value in `config/rag/prompt-budget.json`, or the cached tool set when `getCachedTools` has one), the question, and the answer reserve.
2. Trim history oldest-first, whole turns, tool-call and tool-result pairs together, only as far as needed to give documents their target (`RAG_CONTEXT_TOKEN_BUDGET` in v2; the configured legacy target otherwise).
3. Document budget = `min(target, window - everything else - margin)`. Pass it to `runRetrieval` as an option; v2 uses `min(settings.tokenBudget, option)`; the legacy assembly packs with `selectWithinBudget` when the option is present.
4. After the request is built: assert the estimated total is within the window. If MCP schemas turned out larger than the reserve, trim more history; if nothing is left to trim, fail with `prompt_budget_exceeded`.
5. When the fixed parts and the question alone do not fit: `prompt_budget_exceeded` before retrieval.

History today: the chat route sends the whole converted history (`...citationSession.stripHistory(convertedMessages)`), the WhatsApp handler sends only the current message, the embed route sends the client's messages without system roles, the voice agent keeps an unbounded `history` array.

**"Question last" needs a precise definition.** In the second step of a tool loop the last message is a tool result (probe: `last role=tool`). Assert: the question is the last user message, and only this turn's assistant tool calls and tool results follow it. The chat route already rejects a request whose last incoming message is not from the user.

#### Pattern E: Counting and calibration

- Estimate = `countTokens(text)` (`cl100k_base`) times the family factor, plus the margin. Tool schemas are counted on their JSON serialization.
- Calibration data: the provider-reported prompt tokens. The OpenRouter provider maps `response.usage.prompt_tokens` to `usage.inputTokens` [VERIFIED: 1.2.0 `dist/index.mjs`, `inputTokens: (_a15 = response.usage.prompt_tokens) != null ? _a15 : 0`]. The non-streamed eval path always has usage (probe: `totalUsage.inputTokens` summed over two steps). Record the estimate per part and the reported total on the eval trace; the calibration tool reads recorded runs and writes a high quantile of reported over estimated per family. Whether streamed OpenRouter responses carry usage without an extra request option was not checked [ASSUMED: use the eval path for calibration].
- Families without a record use the conservative default with `source: default`; the fixture family (the small-window fake) gets its own cell so CI exercises a factor other than 1.

#### Pattern F: Fixtures and fakes

- **`multi_step_calc`:** the eval answer path has no tool loop (`generateText` without `tools` in `src/lib/rag-eval/answer.ts`). Add the shared answer-tools builder and `stopWhen` there, or the tool-following fake cannot call the tool. Move the construction of `calculate` into `src/lib/rag/generation/` so the chat route and the eval route build it the same way.
- **`context_overflow`:** `MockLanguageModelV3` records every call (`doGenerateCalls`, `doStreamCalls`), and the call options include `maxOutputTokens` (probe: `maxOutputTokens seen: 9`). The small-window fake counts its prompt with a factor different from the planner's and throws above its window. Route-level tests assert the message order for chat, embed and voice-rag; the eval slice asserts the trace fields and the kept parents in both pipelines.
- Paraphrase groups: at least three questions per group with the same `calc.expected_value`; `paraphrase_consistency` compares the stated numbers within a group.

#### Voice (D-76, D-87)

The agent calls the chat-completions API directly with `stream: true` and no tools (`voice-agent/src/voice_agent.ts`, the `this.llm.chat.completions.create` call) and sends text to speech sentence by sentence. Adding `calculate` means: a function tool in that call, handling of streamed tool-call deltas, a second completion with the tool result, holding the turn's text until the check route answers, and speaking the returned text. This is new control flow in the agent, not a parameter. `POST /api/internal/voice-calc` follows the pattern of `voice-rag` (`internalApiKeyMatches`, `resolveVoiceScope`, `zod/v3` body). #### `RAG_CONTEXT_OVERFLOW=refine` (optional, last)

Keep it behind its own plan as D-85 says.

### 5.2.1 Pitfalls

#### Pitfall C1: The step handler treats every tool except two as an approval-gated tool
**Evidence (chat route, `onStepFinish` of `startOpenRouterStream`):** results are cleared with `if (result && result.toolName !== 'query_documents' && result.toolName !== 'webSearch') { … result.output = null; }`, and a call skips the approval state only when `const isAllowedTool = call.toolName === 'webSearch' || call.toolName === 'query_documents';`. Separately, `const ANSWER_EVIDENCE_TOOLS = new Set(['webSearch', 'useDocument']);` decides whether a tool result marks the answer as built on tool output, which makes groundedness and the claim check `not_checked`.
**How to avoid:** add `calculate` to both places through one named set of server-executed tools, and test that a calculation turn creates no approval entry and keeps its result.

#### Pitfall C2: The default model never gets tools
See Pattern B. Any plan that verifies GEN-16 only through the tool path leaves the default configuration untested. The trailing-block path (D-72) needs the same fixtures and gates.

#### Pitfall C3: Unbounded integers are a cost
`BigInt` has no overflow, so a request can ask for very large powers of ten or long chains of divisions. Bound the digits per operand, the decimal places of `round`, and the bit length of any intermediate numerator or denominator; exceed a bound and the result is `rejected`. Put the bounds in `config/rag/calc-limits.json` next to the limits D-69 names.

#### Pitfall C4: Locating operands in text
A value in a block can carry grouping characters, a different decimal mark, full-width digits or a magnitude word. Compare normalized rationals, and treat a number written in words as not locatable (D-74). A value that appears in the block as part of a longer number must not match (digit boundaries on both sides).

#### Pitfall C5: The trailing block is seen by every later transform
The calculation-block transform must run before the guard and the collector, or the block's content is filtered, split into sentences and counted as uncited text. It is also the reason the chain order is fixed in one builder.

#### Pitfall B1: The budget is decided before the prompt exists
See Pattern D. A plan that computes the budget after assembly cannot drop anything without breaking aliases.

#### Pitfall B2: Most models have no `contextLength`
**Evidence:** in `src/lib/env.ts` only the three entries added by Phase 5 carry it (`contextLength: 1000000` on the `anthropic/claude-*-5.5` entries); `DEFAULT_OPENROUTER_MODELS` in `scripts/init-env.js` and `scripts/config-server.js` has entries without it. With the switch on, most requests would run on the conservative default window and set `context_length_unknown`.
**How to avoid:** a plan that fills `contextLength` for the listed models in the five model locations, with each value taken from the provider's model list at execution time; `check-config` already compares model fields across locations.

#### Pitfall B3: OpenRouter compresses by default on small-window endpoints
"All OpenRouter endpoints with 8k (8,192 tokens) or less context length will default to using context compression." With it disabled and the prompt too long, "the request will fail with an error message suggesting you either reduce the length or enable context compression." [CITED: openrouter.ai/docs/guides/features/message-transforms]. D-84 therefore needs the explicit disable (code example above) on every OpenRouter call the budget governs, and the planner's own error must come first.

#### Pitfall B4: Token estimates differ by model family
`cl100k_base` is one family's tokenizer. Until `eval/config/tokenizer-calibration.json` has a record for a family, use a default factor clearly above 1 and a margin from `config/rag/prompt-budget.json`; the starting values are [ASSUMED] and are replaced by the calibration tool's output.

### Known Threat Patterns

| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Injected document makes the answer carry a phishing link | Tampering, Spoofing | Output guard with allowlist; links section narrowed; policy statement; event and review item |
| Link split across stream tokens | Tampering | Hold-back state machine; every-split-point property test; stream tests |
| Look-alike host (full-width characters, mixed script, U+3002 as a dot, trailing dot, credentials in the URL) | Spoofing | NFKC plus IDNA to ASCII before comparing; reject hosts that change under normalization; end candidates at CJK punctuation; strip one trailing dot; reject user info |
| Obfuscated link the parser does not accept | Tampering | Data-listed patterns, always replaced |
| Credential request in the answer | Spoofing | Rule pairs as data on the shared matcher; block with a removed link or flagged content, warn otherwise |
| Server-side fetch through a link preview | Information Disclosure | Baileys policy default-off plus per-message `linkPreview: false`; live check |
| Markdown image as an exfiltration channel | Information Disclosure | Phase 5.1 image allowlist stays; the guard replaces a removed image with the placeholder alone |
| Catastrophic regular-expression backtracking on model or document text | Denial of Service | Linear scanning in the guard, bounded candidates, rule patterns without backreferences (the existing loader already rejects them), bounded sentence buffer |
| Unbounded hold-back buffer | Denial of Service | The bounds of D-38; decide at the bound |
| Document makes the model output the sentinel or a fake calculation block | Denial of Service, Tampering | Neutralize both strings in block text; count stripped occurrences; block contents validated by Zod |
| Injection through the judge's input | Tampering | Premise and answer inside the `<documents>` wrapping with the notice; enum verdicts only; invalid output is `not_checked` |
| Cross-tenant read of events, alerts, holds or uploader names | Information Disclosure | Tenant key on every row, `rag_assert_tenant_key`, service-role only, route-level tenant checks, two-tenant tests |
| Alert race or flood | Denial of Service | Unique index per uploader and window; alert rows carry counts only |
| Hold bypass through another ingestion path | Elevation of Privilege | The hold is checked in `submitIngest()` and at `publish` for queued jobs; paths that cannot hold follow Phase 3.2 D-37 |
| Tool input used as code | Elevation of Privilege | Closed operation set, no expression string, strict schema, property test with code-like strings |
| Resource exhaustion through huge numbers in the calculation tool | Denial of Service | Digit, place and bit-length bounds; limits file |
| Model states a number that the trace does not support | Repudiation | Recompute, compare, notice, both values stored, review reason |
| Prompt silently truncated by the provider, dropping the reference notice or the question | Tampering | Provider compression disabled; planner fails before generation |
| Stale client marks on edited text | Spoofing | `text_hash` comparison before marks are shown |
