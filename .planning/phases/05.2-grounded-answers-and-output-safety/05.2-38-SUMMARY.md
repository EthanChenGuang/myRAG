## Behaviour changes

- `rag_eval.phase_compare`:
  - The new `below_limit` check kind gates a measured report value strictly below a limit. A missing or unmeasured value fails.
  - A base run config's `generator_model` now reaches the harness. Only the `p52-*` run configs carry one, so no earlier comparison spec is affected.
- `rag_eval.metrics.answer_rule_metrics`: `truncation_rate` is now measured. It counts answers with a finish reason, scoring 1 when the reason is `length`, the output-cap sweep's rule. The contract already had the field; nothing filled it. It appears only in runs that already have an answer-rule section, so the all-off reports and the committed baselines are unchanged.
- `eval/harness/run-nightly.mts --phase52` rejects `--env-overlay`, and `run-smoke.mts --phase52` rejects `--rag-mode`. Both flags would otherwise be ignored silently.

## Decisions Made

- The dependency-merge choices listed above.
- The capped run gets its own run config, `p52-output-cap-512.json`. The spec validator rejects `RAG_MAX_OUTPUT_TOKENS` as a credential-like name because of `TOKENS`. That safety check was left unchanged rather than relaxed.
- The cap value is 512, the smallest sweep candidate and the hardest one to stay under.
- The truncation gate is a new `below_limit` check kind at < 0.02, which matches the requirement's wording. `absolute_zero` would be stricter than the requirement.
- The success-criteria map and the time-to-first-token section are appended by hand to the generated `comparison.md`, with a note that a tool rerun overwrites them.
- AGENTS.md documents 0940-0945. The plan names 0940-0944, but 05.2-18 added 0945.
- Time to first token is measured as the number of model characters released before the first UI delta, which is deterministic, plus the median over 200 streams compared with the chat first-token budget p50.
