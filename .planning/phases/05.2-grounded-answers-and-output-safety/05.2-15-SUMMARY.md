# Phase 05.2 Plan 15: WhatsApp stream parser fix Summary

**The WhatsApp handler now reads the chat route's UI-message SSE stream, so users get the real answer instead of the fixed fallback sentence. The guard pass also gets the turn's webSearch URLs and the answer language.**

## Decision (Task 1, checkpoint:decision)

**Option A: fix in this phase.** The 05.2-14 characterization showed that only the fallback sentence is sent. The owner delegated the decision to the orchestrator, which recorded it on 2026-11-27: APPROVED, fix the WhatsApp stream parser so it reads the UI-message SSE format the chat route emits, keep the legacy format if cheap, with tests (D-91).

## Accomplishments

- Task 2: `createChatStreamParser` reads the stream line by line. It handles `data:` JSON parts with a guarded parse, `data: [DONE]`, and legacy `0:"text"` lines. The handler's loop feeds it, stops at `[DONE]`, and flushes the last partial line at stream end. The facts it surfaces go through `sendWhatsAppResponse` into `guardChannelReply`.

## Behaviour changes

- **All switches off (intended difference for 05.2-38):** a WhatsApp reply is now the streamed answer text. Before, it was always `I received your message but couldn't generate a proper response. Please try again.` The stored assistant message is the same answer text. An empty stream, or one with no text parts, still sends the fallback sentence. Nothing else changes with the switches off: the request body, the send call and the arity are the same.
- `RAG_OUTPUT_GUARD` on: links that appear in the turn's webSearch results are kept (allow rule 2) unless the turn's context was flagged. Before, they were always replaced. The placeholder and notices use the answer language when it is a supported language.

## Tests that failed before the fix

RED commit 738ebe72. Nine tests failed on assertions; all received the fallback sentence:
- characterization: "collects the streamed text and sends it as the reply" (updated from the 05.2-14 outcome "collects no streamed text and sends only the fixed fallback sentence")
- stream-parse-ui-message: real SSE body, mid-line chunk split, CRLF/no-space, non-text parts and [DONE], text parts by id, web results kept (allow rule 2), placeholder in answer language, unsupported answer language ignored

The legacy format, empty/broken stream and flagged-web-results tests already passed on the old code. They pin behaviour that has to stay the same.
