## 0. Findings that shape this contract (read first)

Facts from the code and from research. Each one changes what the UI can show or do.

1. **Citation chips are produced by rewriting the answer's markdown, not by wrapping DOM ranges.** `renderCitationMarkers`
   turns a validated marker into a `[n](#cite-S<k>)` link and the `a` renderer in `chat-message.tsx` turns that link into
   `CitationChip`. A sentence mark that sits **at the end of its sentence** can be produced by the same mechanism. A mark
   that wraps the whole sentence (underline, highlight) would need range wrapping across inline nodes, and the `p` renderer
   sends single-string paragraphs through `dangerouslySetInnerHTML`. So the marks are end-of-sentence glyphs (section 6.2).
2. **Answer metadata is read only for citation-aware messages.** `answerMetadataKey` is empty unless `isCitationAware(metadata)`
   is true. Notices (truncation, sign-in caution, calculation correction) can occur on answers without citations, so
   `notices[]` needs its own reader that does not depend on that gate.
3. **The client does not know the RAG mode or the answer language from metadata.** `ragMode` and `answerLanguage` are on the
   answer record (store), which is absent in shared chats and before the first poll. The texts of this phase are shown in
   the answer language (LANG-09), so the finish metadata must carry it (section 8.1, **backend**).
4. **The client cannot tell whether `RAG_REGISTRY_TEXTS` is on.** D-12 forbids a new public env var and a server call, yet
   the badge must switch its text source. The answer record must say which source applies (section 8.1, **backend**).
5. **Sentence offsets need a named target string and a check the browser can run during render.** D-23 validates offsets by
   `text_hash`. `crypto.subtle` is asynchronous, a message can have several text parts, and `cleanToolCallMetadata` and the
   citation rewrite both change the string before it is rendered. The mark layer therefore has a "not verified yet" state
   that renders nothing, and it inserts marks on the raw part text before any other rewrite (section 6.2, 8.1).
6. **Copy and read-aloud use the raw text parts.** `handleCopy` and `handleTextToSpeech` do not go through the render path.
   A sentence the guard marked blocked after it was streamed (D-39) would still be copied and spoken unless all three use
   one display-text function (section 6.5).
7. **`notices.no_information` in English says that web search is turned off.** It must stay byte-identical (D-10). D-15 and
   D-16 also stream it when strict mode **has** web search and the web found nothing; there the second bullet is false. A
   second text is needed for that case (section 12.2, decision 9, **backend**).
8. **Registry texts pass through the output guard on plain-text channels** (research Pitfall 23). No text in section 12.2
   contains a link, a domain-like token or an imperative that asks for a secret. The two sign-in notices are worded as
   descriptions for that reason; if the registry completeness check still matches one, the text is reworded with the same
   meaning and the change is recorded in the plan summary.
9. **The embed window renders plain text with three inline forms** (`[text](url)`, `**bold**`, `*italic*`) inside
   `whitespace-pre-wrap`. It reads no metadata. Notices reach it as trailing text (D-11). Nothing is built there; section
   6.10 states what must hold.
10. **Two design systems, as in Phase 3.2.** The app is Next.js with local shadcn-style components over Radix and lucide. The
    Config UI is a static page with DaisyUI 4.4.24 over the Tailwind Play CDN and Bootstrap Icons. Tokens are declared per
    surface and never mixed.
11. **The switch cards of Phases 5 and 5.1 are static markup in the RAG Modes tab** ("Citations and groundedness",
    "Prompt-injection defense"), saved by the page's "Save All Changes". The injection-defense card shows a detector summary
    only; it has no list a column could be added to (section 6.14, decision 14).
12. **Three Config UI pieces this phase extends are planned but not on trunk:** `rag-ui.js` and the banner host (plan
    `03.2-56`), the extended Quarantine, Upload approvals and Versions and dates panels (plans `03.2-58` to `03.2-62`), and
    the review queue panel `review-labelling.js` (plan `05.1.1-17`). Per D-96 the UI plans of this phase name those plans in
    `depends_on` and build on their delivered code. Phase 3.2 already reserved the origin badge `answer_conflict` and the
    "Uploaded by" line.
13. **`rag_security_events` stores no text** (D-43). The Security events panel can show ids, rule ids, names and counts; it
    has no link target or snippet to show.
14. **The existing English app labels are in title case** ("Possibly Unreliable", "Cited in This Answer"). The registry
    texts of this phase are sentences and phrases used in prose on every channel, so they are in sentence case. The three
    badge labels keep their existing values byte for byte.

## 1. Design direction (frontend-design pass)

**Subject.** An answer that shows, sentence by sentence, how far the documents stand behind it, and an admin view of what
the safety checks caught and whose uploads were involved.
**Audience.** A reader deciding which sentences of an answer to rely on. An admin deciding which checks to turn on and
whether to hold an uploader.
**Primary job.** Let the reader tell apart what the documents say, what they do not say, what comes from elsewhere and
what the system added or removed, without the answer becoming harder to read.

**Mode.** Annotation, not redesign. The answer text stays the largest and darkest thing in the message. Everything this
phase adds is a proofreader's mark or a note under the text.

**Organizing idea: marks in the margin, never edits to the text.** The system has exactly three ways to speak inside an
answer, in a fixed order of loudness:
1. a **mark** in the citation slot at the end of a sentence (16px, no words until asked);
2. one **legend line** under the text that names the marks and counts them;
3. a **notice** under the legend, one block per kind, for the few cases where the server added or removed something.

Nothing else is added: no highlight, no strike-through, no coloured sentence, no banner across the message, no toast.

**Signature element: the empty citation slot.** A cited sentence ends with a filled, numbered chip. An uncited factual
sentence ends with a chip of the same size and position that is dashed and empty. The reader needs no explanation to see
that a source is missing where one would be. It is the one new shape in the chat; the unsupported mark reuses the amber
triangle the groundedness badge already uses for "possibly unreliable", so sentence level and answer level speak one
language.

**Config UI.** Working tools inside the existing dashboard, built from the Phase 3.2 kit: section cards, sub-tabs, tables,
badges, alerts, dialogs, and its **hold line** (state badge, reason sentence, the action that ends it) for alerts and held
uploaders.

**Review against generic defaults (what was changed and why).**
- Rejected a background highlight on unsupported sentences. Colour would be the only carrier, it reads like a search hit,
  and it needs range wrapping the renderer cannot do safely (finding 1).
- Rejected strike-through or greyed text. D-56 forbids changing the text, and a struck sentence reads as "false", which the
  check does not claim.
- Rejected a green tick on every supported sentence. It adds a mark to most sentences and promises more than a sentence
  check can.
- Rejected a toast for notices. A notice belongs to one answer and must still be there when the chat is reopened.
- Rejected a red frame around an answer with a blocked sentence. One notice says it; the answer is otherwise usable.
- Rejected percentages and scores anywhere (Phase 5 D-20 carries over).
- Rejected stat tiles and a chart for security events. An admin acts on an alert or reads rows; counts sit in the rows.
- Rejected colour-coded uploader rows. The state is a word in a badge.
- Rejected emoji, middle-dot meta strings in new markup, arrows on buttons and all-caps labels.

**Quality floor (built without announcing it).** Visible keyboard focus, `prefers-reduced-motion` respected (nothing new
animates), text at least 4.5:1 and mark glyphs at least 3:1 in both themes, usable down to 360px, every state in section 7
present, every server string inserted as a React text child (app) or with `textContent` (Config UI).

## 6. Layout and interaction

### 6.1 Anatomy of an answer

```
assistant message
  answer text (markdown, unchanged)
      **From the documents**                          part label, written by the model (6.6)
      A sentence with a source.[1]                    existing chip
      A sentence with no source.(o)                   uncited mark: dashed empty chip (6.2)
      A sentence the check did not confirm.[2](!)     unsupported mark: amber triangle (6.2)
      Text with a target taken out (link removed).    placeholder: plain text (6.5)
  mark legend     (o) No source cited: 1    (!) Not confirmed by the documents: 1          (6.3)
  notices         [icon] one block per kind                                                 (6.4)
  Sources button                                      existing
  action row      [badge] copy  thumbs  speak         existing; badge text source per 6.8
```

Order is fixed. The legend and the notices are always visible; they do not follow the action row's hover opacity.
With every switch of this phase off, none of the new elements renders and the message is exactly today's.

### 6.2 Sentence marks (GEN-09, GEN-10; D-19, D-20, D-22, D-23, D-56)

**When a mark shows.** All of the following hold:

| Condition | Source |
|-----------|--------|
| The message is finished (not streaming) | existing `markerPhase === 'final'` |
| The finish metadata carries `sentences[]` (the server sends it only with citations on, D-20) | message metadata |
| The record's `ragMode` is `strict` or `balanced`, or no record is loaded (shared chat), the same rule as `groundednessBadgeState` | answer record |
| The chat is not a ghost chat (`ghost-` id) and the answer is not a refusal (the server sends no records for one) | chat id, metadata |
| The sentence's offsets are verified against the text (finding 5) | 6.2 "Verification" |
| **Uncited:** the record is `factual`, not `cited`, and its kind is not `truncated` | `sentences[]` |
| **Unsupported:** the record's `support` is `unsupported` | `checks.sentences[]` after polling |

`supported` and `not_checked` sentences get no mark. A sentence that is both uncited and unsupported gets both marks,
uncited first.

**The two marks.** Both are superscript, inline, in the citation slot, after the sentence's own chips.

| | Uncited | Unsupported |
|---|---------|-------------|
| Shape | Empty circle with a dashed outline, the size of a chip | Triangle with an exclamation mark (`AlertTriangle`, the badge's icon) |
| Classes (glyph) | `inline-flex h-4 w-4 rounded-full border border-dashed border-gray-500 dark:border-gray-400` | icon `h-3.5 w-3.5 text-amber-700 dark:text-amber-300` centred in an `inline-flex h-4 w-4` box |
| Carriers besides colour | Shape (circle), stroke (dashed), emptiness | Shape (triangle), glyph (exclamation mark) |
| Text (tooltip, accessible name) | `notices.uncited` | `notices.not_confirmed` |
| Appears | When the answer finishes | When the claim check returns (seconds later), without animation |

Shared markup, following `GroundednessBadge`:

```
sup.ml-1.align-super.leading-none
  span[tabindex=0][data-sentence-mark="uncited|unsupported"][data-sentence-index=N][lang]
      .relative.inline-flex.h-4.w-4.items-center.justify-center.cursor-default.touch-manipulation
      .after:absolute.after:-inset-2
      .focus-visible:outline-none.focus-visible:ring-2.focus-visible:ring-[#FF6417]/60.rounded-full
    glyph [aria-hidden=true]
    span.sr-only   registry text
  Radix tooltip: delayDuration 200, side "top", sideOffset 6, collisionPadding 12, content = registry text,
                 content classes copied from GroundednessBadge (z-[99999] max-w-64 rounded-md px-2.5 py-1.5 text-xs …)
```

- The mark is not a button and does nothing on click. Hover, keyboard focus and tap (which focuses it) open the tooltip.
- The visually hidden text is in the reading flow, so a screen reader hears the sentence and then "No source cited"
  without focusing anything.

**Placement.**
- Insertion point: the record's `end`, moved past horizontal whitespace and citation markers that directly follow it, so
  the order on screen is sentence, chips, uncited mark, unsupported mark.
- Kind `list_item`: at the end of the item's text. Kind `table`: on its own line directly under the table. Headings, code
  blocks, questions, lead-ins, notice and label phrases are exempt on the server (D-19) and never carry a mark.
- Mechanism (finding 1): the mark layer inserts a link with a reserved href (proposal: `#mark-uncited-<index>`,
  `#mark-unsupported-<index>`) into the **raw** text part, from the last record to the first, before
  `cleanToolCallMetadata` and `renderCitationMarkers` run; the `a` renderer maps the href to `SentenceMark`. A link with
  that prefix whose index has no verified record renders nothing. Code spans and fences are never touched.

**Verification.** Marks render only for records whose slice of the text verifies against `text_hash` (D-23). Until the
check has run, and whenever it fails (edited or regenerated message, unknown text part), **no mark and no legend render,
and nothing is said about it**: the answer simply looks as it did before this phase. Offsets are UTF-16 code units
(research Pitfall 8). The result is cached per message id and text.

**Many marks.** There is no cap and no collapsing; every qualifying sentence is marked. The legend carries the count.

### 6.3 Mark legend

One line directly under the answer text, rendered only when at least one mark is shown.

```
div[data-mark-legend][lang].mt-2.flex.flex-wrap.items-center.gap-x-4.gap-y-1.text-xs.text-gray-600.dark:text-gray-400
  span.inline-flex.items-center.gap-1   glyph (aria-hidden) + "No source cited: 2"
  span.inline-flex.items-center.gap-1   glyph (aria-hidden) + "Not confirmed by the documents: 1"
```

- Text is the registry text, a colon and the count (`{text}: {n}`; in zh a full-width colon), so no plural form is needed.
  An item with count 0 is not rendered.
- The glyphs are the same shapes as the marks, not focusable. The legend is what makes the icon-only marks learnable.
- When the claim check returns later and adds the second item, the line updates in place. A visually hidden
  `span[role=status][aria-live=polite]` inside the legend announces only that addition (`Not confirmed by the documents: 1`).
  Nothing is announced when a saved chat is opened.

### 6.4 Notices (D-11, D-33, D-39, D-56)

| Tone | Classes |
|------|---------|

- One block per kind. Two notices of the same kind render as two blocks; an exact duplicate (`kind` and `text` equal) is
  shown once.
- Tone means: grey "could not be done or checked", amber "look at this", red "removed for safety". The icon and the
  sentence carry the meaning; colour only repeats it.
- A notice has no close button and no action. It is part of the message and persists with it.
- A notice of an unknown kind is never dropped.
- The container is a polite live region, so notices that arrive with the end of a stream are announced once. Messages
  loaded from history are not announced.

### 6.5 Link placeholder and blocked sentence (SEC-06; D-38, D-39, D-56)

- **Placeholder.** `notices.link_removed` arrives as ordinary answer text. It is rendered as plain text: no link, no
  button, no tooltip, no special style. Its parentheses keep it inert in markdown on every channel. The client never tries
  to recover, show or guess the removed target.
- **Sentence blocked during the stream.** The server already replaced it with `notices.credential_request_blocked`; it is
  ordinary answer text.
- **Sentence blocked after it was streamed** (`checks.output_guard` marks its offsets). After the answer finishes and the
  offsets verify (6.2), the client replaces that range with the same registry text, as plain text. The original sentence
  is then **not in the DOM**: not hidden with CSS, not in a `title`, not in an `aria-label`. This is the single exception
  D-56 allows.
- **One display text.** A pure function (`answer-display-text`) produces the text with blocked ranges replaced. The
  markdown render, the copy button and read-aloud all use it, so a blocked sentence is not copied or spoken (finding 6).
  Marks are never part of copied or spoken text.
- If the offsets do not verify, the sentence stays as streamed and the red notice under the answer is still shown. This
  can happen only for a message whose text changed after it was recorded (edited or regenerated); the client never
  guesses which sentence was meant.

### 6.6 Labelled parts (GEN-08, GEN-15; D-13, D-14, D-15)

The labels are written by the model on instruction; the UI does not create them.

- **Form the instruction must ask for** (planner: the instruction texts `partial_answer`, `web_separation` and `relevance`
  state it): the label alone on its own line, in bold, then the part: `**{label}**`. This renders correctly in the web
  chat, in the embed window and as plain text.
- **Web chat, light enhancement.** A `strong` whose whole text equals `labels.from_documents`, `labels.from_web` or
  `labels.general_knowledge` in any shipped language renders with a leading 16px icon: `FileText`, `Globe`, `Lightbulb`
  (`span[data-part-label="<key>"].inline-flex.items-center.gap-1`, icon `aria-hidden`). Anything else, including a label
  the model reworded, stays an ordinary bold run. No other parsing is done.
- **`labels.not_covered`** is a phrase inside a sentence. It gets no visual treatment; the sentence is the information and
  the server exempts it from marks (D-19).

## 9. Keyboard, screen reader and focus

1. **Marks** are focusable (`tabindex="0"`), in reading order after their sentence, with the registry text as visually
   hidden text inside them. The tooltip opens on focus and hover and closes on Escape and blur (Radix). They have no role
   of a control and no click action.
2. **Legend** glyphs are `aria-hidden`; its text is ordinary text. Its hidden status region announces only an item added
   after the answer finished.
3. **Notices** are `role="note"` inside one polite live region per message. Icons are `aria-hidden`. A notice is never
   `role="alert"`: nothing in it needs an immediate response.
4. **Blocked sentence.** The replacement is plain text in the reading flow. The original text is absent from the
   accessibility tree.
5. **Part label** icons are `aria-hidden`; the label text is read as written.
6. **Version line** is read after the title. Dates are `YYYY-MM-DD` inside `<time datetime>`.
7. **Language.** Elements showing registry text carry `lang` when it differs from the UI language, so zh and it are
   pronounced correctly in an English UI.
8. **Not colour alone.** Each mark differs in shape; each notice has an icon and a sentence; each Config UI state has a
   word and an icon.
9. **Focus visibility.** Marks use the badge's `focus-visible:ring-2 ring-[#FF6417]/60`. Config UI controls keep DaisyUI's
   outline. Never `outline: none` without a replacement.
10. **Motion.** Nothing new animates. Marks, legend items and notices appear in place. Spinners in the Config UI are hidden
    under `prefers-reduced-motion: reduce` and their text remains.
11. **Config UI.** Headings: card and panel titles `h3`, groups and alert titles `h4`. Sub-tabs, tables, dialogs, row-action
    names ("Hold uploads: Uploader A"), live regions and disabled-button reasons follow `03.2-UI-SPEC.md` section 9.
    The hold dialog starts with focus on **Keep uploads allowed** and returns focus to the opening button.
12. **Zoom.** At 200% zoom the legend and notices wrap; no mark is clipped; nothing has a fixed height.

## 11. What must never be shown or done

1. **No removed target.** The client never shows, stores, logs or reconstructs a link, domain or address the guard
   removed. The placeholder is the only trace in the answer.
2. **No original of a blocked sentence** in the DOM, in copied text or in read-aloud once it is marked blocked and verified.
3. **No score, share or threshold** for groundedness, claims or the judge, in the chat or in the Config UI.
4. **Nothing clickable from untrusted data.** Uploader names, e-mails, file names, host names, rule ids and allowlist
   entries are text. No `<a>`, no `mailto:`, no `href`, `src` or `title` built from them, no request to any of them
   (D-57). Tests stub each with `<img src=x onerror=alert(1)>` and `javascript:` and assert that no element is created.
5. **Every server string** is a React text child (app) or `textContent` (Config UI). No new string goes through the
   paragraph renderer's `dangerouslySetInnerHTML` path; notices, the legend and the version line render outside markdown.
6. **No text of a question, answer, chunk or document** in the Security events panel, and no route call that returns one.
7. **No e-mail address** unless the route returned one; the browser never derives it.
8. **Views render named fields only,** through builder functions, never by iterating an object's keys.
9. **No client-side translation or rewriting of a notice**; the server's text is shown as sent.
10. **No mark on a sentence the server did not record.** The client does not split sentences or decide what is factual.
11. **Nothing is logged** to the console from notices, sentence text, uploader names or hosts; logs carry counts and codes.
12. **No domain content** in copy, placeholders, examples or test fixtures of the UI.

## 12. Copywriting Contract

Voice: plain verbs, sentence case, the reader's or admin's side of the screen. A text that reports a problem says what
happened and what to do next; nothing apologizes. "The documents", not "your documents": the same texts are read in the
embed and on WhatsApp by people who do not own the knowledge base.

**Words used, and words avoided.** "Source" for a citation target; "the documents" for the knowledge base. "Not confirmed
by the documents" for an unsupported sentence, never "wrong", "false" or "hallucination". "Sign-in details" for passwords
and codes in reader-facing text. "Answer guard" for `RAG_OUTPUT_GUARD` in the Config UI; "claim", "premise", "sentinel" and
"HHEM" are not shown. "Uploader" and "hold uploads"; "ban", "block user" and "suspect" are not used. "Alert level" for the
threshold.

**Counts are written as "label: number"**, so no string needs a plural form in en, zh or it.

**Action labels are verb + noun.** No button reads "Cancel", "OK", "Submit" or "Close" alone.

**Where the strings live.** Reader-facing fixed texts: the language registry (`config/rag/language-packs.json`), read on the
server through `fixedText` and on the client through `texts.generated.ts` (D-08, D-12). No reader-facing string of this
phase is added to `src/translations/`. Config UI strings: one `{ en, zh, it }` table per file (`ANSWER_RULES_LABELS`,
`SECURITY_EVENTS_LABELS`), English fallback; additions to Phase 3.2 and 5.1.1 panels go into those panels' own tables.
