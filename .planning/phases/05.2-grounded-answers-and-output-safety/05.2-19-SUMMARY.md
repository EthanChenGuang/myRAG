# Phase 5.2 Plan 19: Review reasons, claim mining and the immediate enqueue — Summary

**Migration 0944 lets the review queue accept this phase's three reasons in both places they are checked. Weekly mining now collects answers flagged `claim_unsupported`. A new service-role function, `rag_enqueue_review_item`, puts security and version findings into the queue at once. It stores ids only, deduplicates per week and keeps tenants apart. `enqueueReviewItem` is the app-side client. It is off unless `RAG_DOMAIN_EXPERT_REVIEW=true`.**

## Deviations

- **New column `rag_review_items.snapshot`.** The plan says the item's snapshot holds the ids, but 0534 has no snapshot column. `candidates` keeps the mining shape (ranked chunk and document pairs), and a version conflict has no chunks. So 0944 adds `snapshot jsonb NULL` with an object check. Experts read it through the existing table grant and RLS.
- **`query_masked` is the empty string.** The plan asks for "a fixed neutral marker". I chose `''` because the training export skips an empty query, so these items can never become training pairs. 05.2-24 or the review UI may show a label for such items.
- **Extra hardening:**
  - every chunk and document id must belong to `p_tenant_key` (22023 otherwise);
  - ids must be UUIDs, at most 50 of each, at least one in total;
  - detector and trace id are shape-checked.
- `tests/helpers/security-definer-allow-list.ts` is listed in the plan, but I did not change it: the function must not be on the list, and a test asserts that.
- A test bug I fixed before the GREEN commit: the dedup count was not scoped to the item's fingerprint.
