# Phase 4.3: Document Access Groups - Context

**Gathered:** 2026-11-25
**Status:** Ready for planning
**Mode:** `--auto`. Every gray area was resolved with the recommended option, per the owner's standing rule "take the recommended option; never ask, record the decision". Each auto choice is logged in `04.3-DISCUSSION-LOG.md`.

<domain>
## Phase Boundary

Inside one tenant (an organization in multi-tenant mode; the deployment in single-tenant mode), documents can be restricted to **access groups**. A caller only retrieves, is answered from, or sees cached or logged content of documents their groups allow. Enforcement is in server code and SQL, before any ranking, never in the prompt.

Requirements in scope: **SEC-12** (groups, document labels, pre-ranking filter on every leg and backend, caller groups from verified identity only), **SEC-13** (cache, logs, traces, review queue and citation recheck respect groups), **DATA-22** (Nango connector sharing mapped to groups on every sync, fail closed), **EVAL-21** (same-tenant cross-group canaries on every backend, release gate).

Out of scope:
- Per-user ACLs beyond what group membership and the uploader rule express (no per-document user lists in the UI).
- New retrieval algorithms, fusion or rerank changes. The filter is added to existing legs; ranking code is not changed.
- New connectors (SharePoint/OneDrive is Phase 6.3), source deletion sync (Phase 6.3).
- Field-level redaction inside a document.

Dependencies:
- **Phase 4** (v2 stage graph, `hybrid_search_chunks`, `rag_fetch_parents`, exact-id lookup, `RetrievalBackend` contract, RET-08 cross-tenant canaries).
- **Phase 3.2** (planned, plans on trunk): upload and admin surfaces, `chunk_translations` / `hybrid_search_translations`, document tags and versions UI. This phase extends those surfaces; it does not create parallel ones.
- **Phase 4.2** (being planned on `claude/plan-04.2`, not on trunk at time of writing): table rows (RET-12), duplicate clusters (DATA-21) and diversity collapse (RET-13), identifier index and filter (RET-15, RET-16), version-aware retrieval (RET-11). Plans here are written against those requirement texts; the executor locates the concrete tables and functions by name at execution time.
- Later phases already on trunk as plans (5 citations, 5.1.1 retrieval log and review queue, 6 semantic cache, 7 Qdrant/Weaviate) are consumed through their seams; when a seam does not exist yet at execution time, the plan adds the access-group hook behind the seam's absence check (see D-30).

</domain>

<decisions>
## Implementation Decisions

### Data model (SEC-12)
- **D-01:** Groups are rows in a new table `rag_access_groups` (`id uuid`, tenant columns of the deployment mode, `key text` immutable slug, `name text` editable display name, `source text` `manual | connector`, `created_at`, `created_by`), unique on (tenant, key). Members are rows in `rag_access_group_members` (`group_id`, `user_id`, `added_by`, `added_at`, `source` `manual | connector`). RLS: server role only for writes; authenticated users may read their own memberships. A group never spans tenants: the tenant columns are NOT NULL in multi-tenant mode and the member insert path checks organization membership (D-04).
- **D-02:** Documents carry `access_groups text[] NOT NULL DEFAULT '{all}'` with a CHECK that the array is non-empty. Entries are principal keys:
  - `all` — every member of the tenant (today's behaviour);
  - `g:<group uuid>` — members of that access group (uuid, not slug, so renames never re-label documents);
  - `u:<user uuid>` — a single user (used only for the uploader fail-closed case, D-21, and connector user shares, D-19).
  A document visible to "all" never also carries other keys (normalised on write).
- **D-03:** The array is **denormalised** onto every retrievable row: `document_chunks`, `document_parents`, `chunk_translations`, and the Phase 4.2 table-row store and duplicate-cluster membership rows (whatever their final names). A GIN index on each `access_groups` column. A trigger on `documents` UPDATE OF `access_groups` propagates to all derived rows in the same transaction; writers copy the document's value on insert (ingest, rechunk, retranslate, relex, version replace). A consistency check function `rag_access_groups_drift()` returns rows whose array differs from their document (used by tests and the Config UI health view).
- **D-04:** Admins: multi-tenant → organization `owner`/`admin` roles; single-tenant → `admin_users`. Admins see every document of their tenant (`access_all`). Viewers and members are ordinary callers.

### Caller resolution (SEC-12)
- **D-05:** A new branded value `AccessScope` is minted only inside `src/lib/rag/tenant/` by `resolveAccessScope(scope, identity)`, alongside the existing `TenantScope`. Shape: `{ mode: 'off' | 'admin_all' | 'keys'; keys: readonly string[]; setHash: string }`. With `keys`, the set is `all` + `u:<caller>` + `g:<id>` for every membership; `setHash` = SHA-256 of the sorted keys (`off` and `admin_all` get fixed hashes). `runRetrieval` and every leg take `AccessScope` as a required argument; the RAG boundary check (`scripts/ci/check-rag-boundary.mjs`) is extended so `AccessScope` cannot be built elsewhere.
- **D-06:** Groups come only from the server: the verified Supabase session (chat, upload, documents APIs), the signed voice scope token's user id (voice: memberships are looked up at request time from that id, not embedded in the token, so a group change applies on the next turn), and the embed configuration (D-07). Any `accessGroups`/`groups` field in a request body is ignored and logged once per request as `[RAG Access] body_group_claim_ignored`.
- **D-07:** Embedded chat and WhatsApp visitors get `keys = ['all']` unless their configuration names a group: new env `RAG_EMBED_ACCESS_GROUP` (empty default; a group key that must exist in the embed tenant, else the embed fails closed to `all`-only and logs). Eval runs (`/api/internal/rag/run`) take groups from the fixture identity, never from the body.
- **D-08:** Membership is read with one indexed query per request (no cross-request cache), so a removal takes effect on the next request. Its latency is reported as stage `access_scope` on the trace against the existing latency budgets.

### Switch and off-behaviour (SEC-12, success criterion 1)
- **D-09:** `RAG_DOC_ACCESS_GROUPS=off|on` (default `off`), mirrored in all five config locations and the config manifest. Off → `AccessScope.mode = 'off'`, every SQL function receives `p_access_keys = NULL` and skips the predicate, the cache key part is the constant `off`, and traces/logs are unchanged. The columns, tables and default `{all}` exist regardless (migrations are not switch-gated), so turning the switch on needs no backfill.
- **D-10:** On → the filter applies in both pipelines: v2 legs (D-11) and the legacy search RPCs used by `RAG_PIPELINE=legacy` (they gain the same `p_access_keys` parameter). Groups on with any retrieval path that cannot apply the filter is a startup error that blocks retrieval (fail closed, structured "knowledge base temporarily unavailable" per AGENTS.md §14), never a silent fallback.

### Pre-ranking filter on every leg (SEC-12, success criterion 1)
- **D-11:** Every retrieval SQL function gains `p_access_keys text[] DEFAULT NULL` and `p_access_all boolean DEFAULT false`, applied in the same WHERE clause as the tenant predicate, before ORDER BY / LIMIT / RRF:
  `p_access_keys IS NULL OR p_access_all OR row.access_groups && p_access_keys`.
  Functions: `hybrid_search_chunks` (dense and lexical legs), the exact-id lookup, `rag_fetch_parents`, `hybrid_search_translations`, `match_chunks_by_profile`, the legacy workspace search RPCs, and the Phase 4.2 table-row lookup, identifier index/filter lookups (including the near-miss suggestion list, which must never suggest an identifier from a document the caller cannot see) and duplicate-cluster expansion (the "other sources" list under a collapsed citation lists only visible documents). All stay **service_role only**, `SECURITY DEFINER` with `SET search_path = ''`.
- **D-12:** The filter is on the denormalised row column and also re-checked by a join to `documents.access_groups` inside the same query (defence against trigger drift); a mismatch row is excluded and counted.
- **D-13:** HNSW with a selective filter: the dense leg relies on the Phase 4 `RAG_HNSW_ITERATIVE_SCAN` / `RAG_EXACT_SCAN_CUTOFF` machinery; when `AccessScope.mode = 'keys'` and the caller's visible share of the tenant is small, the pipeline forces iterative scan for that query. Research confirms the pgvector behaviour and the threshold; recall on restricted callers is measured in the canary suite.
- **D-14:** External backends (Phase 7 adapters): `access_groups` is added to the Qdrant payload (keyword index) and Weaviate property, written by the existing outbox drain (document `access_groups` updates enqueue like other synced columns), and a `MatchAny` / `ContainsAny` filter is injected on every query **and every prefetch** next to the tenant filter. The Phase 7 Supabase re-validation of returned ids also checks access groups. If an adapter cannot apply the filter, D-10 applies.
- **D-15:** Non-RAG read paths that expose document content or names to a caller apply the same scope in server code: document list and dashboard APIs, document/original download and preview, `source_images`, the `documentReferenceTool`, and folder listings. RLS gains a **restrictive** SELECT policy on `documents` and `document_chunks` for the `authenticated` role using a `SECURITY DEFINER` helper `rag_caller_can_see_document(access_groups)` that honours a DB-side enforcement flag (`rag_access_group_settings.enforced`, written together with the env switch by the Config UI/config server and checked against env at startup with a warning on mismatch). Restrictive policies only narrow access, so RLS cannot weaken.

### Assigning groups (SEC-12)
- **D-16:** At upload (Phase 3.2 upload surfaces, app and Config UI) the uploader picks `all` (default) or one or more groups they belong to; admins may pick any group of the tenant. In bulk backfill, `--access-groups <keys>` applies to the batch (default `all`).
- **D-17:** Admins change a document's groups from the document admin list (single and bulk). A change writes `rag_admin_audit`, propagates (D-03), bumps the cache generation of that document (D-24) and enqueues external sync.
- **D-18:** Deleting a group: documents whose array would become empty are set to `u:<uploader>` (fail closed, visible to the uploader and admins), never to `all`; the admin confirms with the count of affected documents. Removing a member is immediate (D-08).
- **D-19:** Re-upload / new version inherits the previous current version's `access_groups` unless the uploader explicitly changes it (within D-16 rules). Quarantine, release and version replace keep the array.

### Connector permission sync (DATA-22)
- **D-20:** On every Nango sync (Google Drive, Notion, Dropbox), the sync manager fetches the source's sharing for each document through the Nango proxy (Drive permissions, Dropbox shared members, Notion page/workspace sharing as far as the API exposes it) and maps principals:
  - a user principal whose verified email matches a tenant member → `u:<member id>`;
  - a group / team principal → the access group linked to it in a new mapping table `rag_connector_group_map` (tenant, provider, external principal id, `group_id`), maintained by admins; connector-created groups use `source = 'connector'`;
  - domain-wide or "anyone with the link" sharing → `all` only when an admin has enabled that mapping for that provider and domain in the tenant's connector settings; otherwise unmappable;
  - any principal that cannot be mapped → the document is set to `u:<uploader/connector owner>` (fail closed: uploader and admins only) and a sync warning is recorded per document.
  A permission change at the source updates `access_groups` on the next sync through the same write path (D-17 propagation, audit with actor `connector`).
- **D-21:** Notion: the public API exposes no per-page member list for most plans, so Notion documents are unmappable unless the admin maps the workspace (or teamspace) to a group; the default is fail closed. Research confirms the exact API surface per provider.
- **D-22:** Connector sync with `RAG_DOC_ACCESS_GROUPS=off` still records the mapped array (so turning on later is correct) but nothing enforces it.

### Derived stores (SEC-13)
- **D-23:** Semantic cache (Phase 6, `rag_semantic_cache`): `CacheKeyParts` gains `accessGroupSetHash` (the `AccessScope.setHash`); with the switch off it is the constant `off`, so baseline keys are unchanged in value semantics (key hash changes once, which only empties the cache). Entries also store the union of the source documents' `access_groups`; a lookup serves an entry only when the caller's set hash matches **and** every source document is still visible to the caller (re-checked in the lookup SQL).
- **D-24:** A change of a document's `access_groups` invalidates cache entries that used it (extends the existing `rag_semantic_cache_on_documents_update` trigger to fire on `access_groups`).
- **D-25:** Retrieval log, review queue and answer records (Phase 5.1.1 `rag_retrieval_log`, `rag_review_items`; Phase 5 `rag_answer_records`): rows store the union of `access_groups` of the content they hold; reads go through server code that shows restricted rows only to admins or members of every group the row's content needs (a reviewer who lacks a group sees the row with content masked). Langfuse and other external trace exports never carry text of restricted chunks: chunk ids and scores only (extends `trace/mask.ts`).
- **D-26:** Post-generation citation recheck: after the answer is final, every cited chunk id is checked in one batched query against the caller's `AccessScope` (and the tenant). A mismatch drops the citation, marks the answer `access_violation` on the trace and message metadata, and writes a row to a new `rag_security_events` table (tenant, user, event `citation_access_violation`, chunk/document ids, request id; no content). The prompt is never the control.
- **D-27:** Shared chats: creating a share link for a chat whose messages cite restricted documents is refused (`403 restricted_content`) while the switch is on; the share view re-checks at read time and requires an authenticated viewer who can see every cited document.

### Admin UI (SEC-12; UI hint yes)
- **D-28:** Two surfaces over one API (`/api/rag/access-groups/*`, Zod-validated, structured JSON errors):
  - in-app organization settings (multi-tenant owners/admins): groups list, create/rename/delete, members, connector group mapping;
  - Config UI (single-tenant and operator): the same, plus the `RAG_DOC_ACCESS_GROUPS` switch, `RAG_EMBED_ACCESS_GROUP`, the enforcement-flag sync status (D-15) and the drift check (D-03).
  The document admin list and upload dialogs gain an access-groups field (chip list) and a "restricted" badge. Copy and fixtures use neutral names (`group-a`, `group-b`).
- **D-29:** Members see which groups they belong to on their profile/settings page; non-admins never see the member lists of groups.

### Execution seams
- **D-30:** Where a dependency seam is planned but not yet on trunk at execution time (4.2 table rows/clusters/identifier index, 5 citations, 5.1.1 log, 6 cache, 7 adapters), the plan task first re-reads the newest definition by symbol name; if the seam is absent, the task adds the access-group hook in a guarded form (column/parameter added when the table/function exists, via `to_regclass`/`to_regprocedure` checks in the migration) and records the gap in its SUMMARY. A later re-run of the migration (idempotent) completes it.

### Migrations
- **D-31:** Block **0920–0939**, ordered, idempotent, common file first then `.single-tenant.sql` / `.multi-tenant.sql`. **Not folded** into the setup files. Loaded by PGlite tests. Every new `SECURITY DEFINER` function uses `SET search_path = ''` and schema-qualified names; every new function is service_role only except the RLS helper (D-15), which is `STABLE`, takes no caller-supplied identity (uses `auth.uid()`) and is granted to `authenticated`. Reversibility: one-way (new columns, tables, policies).

### Evaluation (EVAL-21)
- **D-32:** The RET-08 canary suite gains same-tenant cross-group cases, on pgvector (PGlite in CI) and through the Phase 7 adapters (fakes in CI, real backends in live verification): two members of one tenant, `group-a` and `group-b`, a synthetic neutral document restricted to `group-a` per language (zh/en/it); the outsider gets the information-not-available refusal with no restricted chunk id in candidates, context, cache, citations, retrieval log or security-event payload. Variants: after a group change (member removed, document re-labelled), after a re-upload/new version, with a request body claiming `group-a`, via embed and via voice token identity, and the member of `group-a` gets the answer. The suite is a CI release gate; no other slice drops beyond the noise band (switch off: identical to baseline).
- **D-33:** A drift test asserts every derived row equals its document's array after ingest, rechunk, retranslate, relabel and version replace.

<specifics>
## Specific Ideas
- One predicate everywhere: `access_groups && p_access_keys` with `all` always in the caller's keys — the off/on difference is only whether the predicate is applied.
- Fail closed by construction: unmappable connector permission, deleted group, missing seam with switch on, or an adapter without the filter never widens visibility.
- Fixtures: neutral synthetic content, group names `group-a`, `group-b`, users `member-a`, `member-b`, `outsider`.

## Adjustments after research (orchestrator, 2026-11-25)

The researcher found places where a locked decision, read literally, does not match the code. Each is resolved with the recommended option (owner rule) and **supersedes the decision it names**. Planner and checker treat these as locked.

- **A-01 (R-1, amends D-15):** the restrictive SELECT policy is `TO anon, authenticated` (single-tenant read policies have no `TO` clause) and covers `documents`, `document_chunks` **and `document_parents`**.
- **A-02 (R-2, amends D-15):** the policy uses argument-less `STABLE SECURITY DEFINER` helpers `rag_access_enforced()` and `rag_caller_access_keys()` (evaluated once per statement), plus a mode-specific admin bypass: multi-tenant `public.is_org_admin(organization_id)`, single-tenant an argument-less `rag_caller_is_access_admin()` reading `admin_users` for `auth.uid()`. Never `is_admin(uuid)` in a policy anon evaluates.
- **A-03 (R-3, amends D-15):** env `RAG_DOC_ACCESS_GROUPS` stays the single source of truth. At startup (`src/instrumentation.ts` checks) the app writes the DB flag through service-role `rag_access_set_enforced(boolean)` and reads it back; a failed write with the switch on blocks retrieval (D-10). The Config UI shows the status and can trigger the same sync.
- **A-04 (R-4, amends D-11):** every existing function keeps its current security mode (`hybrid_search_chunks`, `rag_fetch_parents`, cache functions are `SECURITY INVOKER`, service_role only). New functions are INVOKER unless they must read a table the caller cannot (RLS helpers, triggers); every function, INVOKER or DEFINER, has `SET search_path = ''`.
- **A-05 (R-5 + open question 3, amends D-05/D-23):** `AccessScope.keys` stays as D-05; the cache key part hashes the **effective** key set (the caller's keys that label at least one current document of the tenant, returned by the resolver RPC). Users without private documents share entries; correctness is kept by the live per-document visibility recheck at lookup.
- **A-06 (R-6, amends D-23/D-25):** derived rows store per-document label sets (`access_sets jsonb`, a list of arrays); a row is visible when every set overlaps the caller's keys (or the caller is admin).
- **A-07 (R-7, amends D-17/D-20):** audit goes to a new `rag_access_audit` table (tenant key, action, nullable actor uuid, `actor_kind` `admin | connector | system`, group id, document id, before/after arrays, no content). `rag_admin_audit` is untouched.
- **A-08 (R-8, amends D-12):** drift rows are excluded in the query; counting happens out of band (`rag_access_groups_drift()`, the D-33 test, a startup `[RAG Access] drift` log).
- **A-09 (R-9, resolves D-13 discretion):** fixed rule: with `mode = 'keys'` send `p_exact_scan_cutoff = max(configured, 1000)` and `p_iterative_scan = 'relaxed_order'` when the configured value is `off` and pgvector ≥ 0.8.0. The canary suite measures restricted-caller recall.
- **A-10 (R-10 + open question 1, scopes D-20):** connector documents stay in the owner's personal tenant in multi-tenant mode (`nangoOwnerScope`, unchanged; moving them is out of scope). The mapped array is always computed and stored, but visibility changes only in single-tenant mode; the criterion-4 canary runs single-tenant. Reported to the coordinator as a wording note.
- **A-11 (open question 2, D-30):** the first SQL plan greps trunk for the Phase 4.2 (and 3.2/5.1.1/7) objects by requirement and records what exists; absent seams use the D-30 guard, and a catalog sentinel test plus a SQL check (enforcement on and `p_access_keys` NULL → raise) catch overload drift from re-applied older migrations.
- **A-12 (open question 4):** extracted images live in the public `chat-images` bucket, so groups cannot protect their bytes; `source_images` URLs of restricted documents are never returned to callers outside the groups. Signed image URLs are deferred (backlog).
- **A-13 (open question 5):** a member who loses a group keeps their own already-delivered chat history; shared views (D-27), retrieval log, review queue and answer-record reads by others apply the live check.
- **A-14 (coordinator brief addition, 2026-11-25; amends D-05 and D-14):** Phase 7 plans 07-38 and 07-39 (on trunk) own the external-backend side: payload `access_groups`, Qdrant/Weaviate filter on every query and prefetch, `rag_validate_chunks_for_groups`, and the three-backend canary. Phase 4.3 therefore does **not** edit the Qdrant/Weaviate adapters or the vector-sync outbox; instead it ships two **stable seams**, named in `04.3-PLAN-INDEX.md`:
  1. **TenantScope carries the caller's access groups.** The server-resolved `AccessScope` is attached to the minted `TenantScope` as a readonly field `access` (set only inside `src/lib/rag/tenant/` when the scope is resolved for a caller), read through one exported accessor `scopeAccessFilter(scope)` returning `{ mode: 'off' } | { mode: 'admin_all' } | { mode: 'keys'; keys: readonly string[]; setHash: string }`. A scope that was never resolved for access, with the switch on, fails closed in `runRetrieval`. Phase 7 reads groups only through this accessor.
  2. **`document_chunks.access_groups text[] NOT NULL DEFAULT '{all}'`**, copied from the document and kept equal by trigger (D-03), with values `all`, `g:<group uuid>`, `u:<user uuid>` (D-02). The vector-sync outbox carries it via 07-38's `UPDATE OF access_groups` triggers.
  The pgvector legs, the `RetrievalBackend` request contract (passing the access filter to whatever backend runs) and the pgvector canaries stay in 4.3. Reported to the coordinator: Phase 7 should handle `admin_all` (no group filter) and the `g:`/`u:` key format when it reads HEAD.
