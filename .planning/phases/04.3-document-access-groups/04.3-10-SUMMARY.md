# Phase 04.3 Plan 10: access predicate on every other content function, in both modes and both pipelines

**Parents, exact id (both branches), profile search, invoices, the single-tenant legacy `match_document_chunks` and the multi-tenant `match_documents_by_workspace` now take `p_access_keys` / `p_access_all` and filter on the row and its document before ORDER BY and LIMIT. Every unused legacy content function refuses while enforcement is on. An outsider gets no restricted row (forged parent ids, an identifier found only in the restricted document, limit 1 with the restricted text as query), member-a and `admin_all` get it, and a member who sees 12 of over 1200 rows gets the brute-force top ten.**

## Behaviour changes

- With `RAG_DOC_ACCESS_GROUPS=off` (default) the TypeScript callers send no new argument. Each redefined function then runs the same query as before (in `match_chunks_by_profile` and `match_documents_by_workspace`, the no-keys branch is the 0425 text). The fake edge accepts the two arguments and still rejects unknown ones.
- With enforcement on (`rag_access_group_settings.enforced`), a call without keys raises `access_scope_required` (42501). An empty key array, or one holding NULL, always raises `access_keys_empty` (22023).
- **Grant changes (A-04, and the brief's rule that no insecure legacy path stays):**
  - single-tenant `match_document_chunks` is service_role only (the legacy pipeline already calls it on the admin client).
  - the unused INVOKER functions `match_documents`, `match_document_chunks_optimized`, `search_chunks_by_keywords`, `match_documents_by_organization` and multi-tenant `match_document_chunks` are now service_role only with an empty search_path. They were executable by anon and authenticated, and nothing in `src/` calls them.

## Decisions (for STATE)

1. **Exact path bound 1000** (D-13, A-09): restricted callers of `match_chunks_by_profile` and `match_documents_by_workspace` count their visible rows up to 1001. At or below 1000 the query is a materialized scan with no index order. Above it, `hnsw.iterative_scan = relaxed_order` (pgvector 0.8 or newer) and `hnsw.ef_search = least(greatest(k*2, 100), 1000)` apply, and the hits are re-sorted by exact distance. `admin_all` and the no-keys path keep the old query.
2. **Static-SQL predicate form:** `(NOT v_restrict OR (row.access_groups && keys AND d.access_groups && keys))`, where `v_restrict := keys IS NOT NULL AND NOT p_access_all`. When the row does not already join its document, the document check is an `EXISTS` semi-join, so the off state returns the same rows.
3. **Unused functions made service_role only.** At first I guarded the INVOKER ones behind `has_function_privilege` so client calls kept working. The Phase 3.2 apply check, though, holds every function defined from 0801 on to an empty search_path and service_role-only execute, and these functions have no caller. So they are revoked from clients and the guard calls `rag_access_enforced()` directly. Plan 06's RLS no longer has to cover them.
4. **0409/0410 entries** for the three new DEFINER signatures. `search-rpc-grants-pglite` showed that an upgraded database whose functions kept open grants left them executable by anon after 0409/0410 ran.
5. **No new store**, so no purge hook or store-inventory entry is needed.
6. **Migration numbers:** the plan's 0930 mode files, checked free on every origin branch before the first commit.
