# Phase 04.3 Plan 11: readiness, catalog sentinel, and the access filter on the Phase 3.2 and 4.2 legs

**`rag_access_readiness()` tells from the catalog whether every retrieval function can filter. A catalog sentinel test makes every content-returning function filtered, guarded, pending or exempt with a reason. The translation leg, table-row lookup, identifier resolve and suggestions, and the duplicate-cluster source list now filter by access group before ranking, and their TypeScript callers send the filter. An outsider never gets, is never suggested and is never listed a restricted document. Member-a and `admin_all` get it, and a call without keys raises while enforcement is on.**

## Gaps and instructions for the owning phase

1. **Phase 3.3 attribute resolver (1008): owner is Phase 3.3 or a 04.3 gap plan.** `rag_attribute_filter_values` builds a tenant-wide value lexicon from every current document, and `rag_attribute_documents` returns ids by attribute value. If a value occurs only in a restricted document, the query matches it and the filter narrows to that document. The outsider then gets "information not available" where they would otherwise get an answer, which shows that the value exists. 1008 runs after the 0920 block, so 0933 cannot redefine these functions. The instruction: in a file numbered after 1008, redefine both with `p_access_keys text[] DEFAULT NULL, p_access_all boolean DEFAULT false`, the 0930 guard and `d.access_groups && p_access_keys` in the documents join. Drop the old signatures. In `src/lib/rag/retrieval/attributes.ts`, send `accessRpcArgs(scopeAccessFilter(scope))` to both RPCs, and key the lexicon cache by tenant key plus access mode and `setHash` (`invalidateAttributeLexicon(tenantKey)` must then drop every entry of that tenant). Then move both names from PENDING to FILTERED in the sentinel. Until that lands, readiness reports `function_missing_access_parameters` and `function_missing_guard` for both, so `RAG_DOC_ACCESS_GROUPS=on` cannot reach `ready`.
2. **`rag_cache_check`: plan 04.3-12.** Readiness names it until 0931 adds the parameters. The readiness test then expects ready automatically, because it reads the catalog.
3. **`rag_bm25_search_chunks`: merge train 35.** The train's 0932 must satisfy the FILTERED checks: one overload, both parameters, `access_groups` in the source, and a raise for NULL keys while enforced.

## Behaviour changes

- With `RAG_DOC_ACCESS_GROUPS=off` (default) every caller sends the same request body as before. `accessRpcArgs` of an off filter is `{}`, and each redefined function runs its source file's query (tests: switch-off case equals member result; `context-stages` exact-args assertion unchanged).
- With keys, the five functions filter on the row and its document before ORDER BY and LIMIT. With no keys while enforced they raise `access_scope_required` (42501). An empty or NULL-holding key array raises `access_keys_empty` (22023).
- The TS callers take the filter computed once by the search stage (`ctx.access`, D-05). They fall back to `scopeAccessFilter(scope)`, which throws `AccessScopeMissingError` for an unresolved scope while the switch is on (fail closed). In `identifierSuggestions` the error is caught and no suggestions are returned. `resolveQueryIdentifiers` throws, and the existing stage handler skips the identifier filter. The search legs themselves still fail closed.
- New signatures for the five functions; all remain SECURITY INVOKER, empty search_path, service_role only.

## Decisions (for STATE)

1. **Migration number 0933**, not an edit of 0930: the brief forbids editing another plan's migration. 0931 is plan 12's and 0932 is train 35's BM25 file, found after my first commit. I renumbered in a new commit, with no force-push.
2. **The readiness answer uses parallel arrays.** `reasons[i]` is the code for `objects[i]`. The codes are `function_missing`, `function_overloaded`, `function_missing_access_parameters`, `function_missing_guard`, `table_missing` and `table_missing_column`. The guard check (`access_scope_required` in the source) goes beyond the plan, at low cost.
3. **Deployment mode inside SQL** is read by calling `rag_assert_tenant_key('s:default')` in an exception block: it is accepted only in single-tenant mode. The required legacy RPC is `match_document_chunks` (single-tenant) or `match_documents_by_workspace` (multi-tenant).
4. **Optional readiness list** = `hybrid_search_translations`, `rag_cache_check`, `rag_table_lookup`, `rag_identifier_resolve`, `rag_identifier_candidates`, `rag_dup_cluster_sources`, `rag_bm25_search_chunks`, `rag_attribute_filter_values`, `rag_attribute_documents`. Optional tables are `chunk_translations` and `rag_table_rows`.
5. **The sentinel classifies by name.** A function counts as a candidate when it is a non-trigger `public` function whose source names `documents`, `document_chunks`, `document_parents`, `chunk_embeddings`, `chunk_translations`, `chunk_translation_embeddings`, `rag_table_rows` or `rag_dup_clusters`, and whose result is a set, a row, text, text[] or JSON. FILTERED is checked for one overload. Lists are per mode where the legacy RPCs differ. The NULL-key raise check calls each function positionally with NULLs and the tenant key, inside a rolled-back transaction under enforcement. No seed rows are needed, because every guard runs before argument validation (plan said "seed the minimum rows").
6. **PENDING category** (not in the plan) for legs on trunk that the block cannot redefine. The test passes only if readiness names them, or once they pass the FILTERED checks.
7. **Translation predicate** also checks the source chunk's own label (`c.access_groups`), defence in depth next to the document label.
8. **No new store**, so no purge hook or store-inventory entry; no 0410 entries, since every new or redefined function is INVOKER.
9. **Readiness test without `verifyAccessGroupsStartup`:** plan 07, which writes it, is not in this plan's depends_on and is not on this branch, so the test calls `rag_access_readiness()` directly. Plan 07 calls it by name and treats a missing function as not ready.
