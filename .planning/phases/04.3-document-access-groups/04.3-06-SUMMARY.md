## Policy

```sql
CREATE POLICY rag_access_groups_restrict ON public.<table>
  AS RESTRICTIVE FOR SELECT TO anon, authenticated
  USING (
    (SELECT public.rag_access_enforced()) IS NOT TRUE
    OR access_groups OPERATOR(pg_catalog.&&) (SELECT public.rag_caller_access_keys())
    OR <single-tenant: (SELECT public.rag_caller_is_access_admin())
       | multi-tenant: (organization_id IS NOT NULL AND public.is_org_admin(organization_id))>
  );
```

- Every table carries `organization_id` itself in multi-tenant mode (documents, document_chunks, and document_parents from 0404), so no sub-select on `documents` was needed.
- `EXPLAIN` as `authenticated` shows the argument-less helpers as InitPlans on all three tables (asserted). `is_org_admin(organization_id)` depends on the row and stays a per-row call; it is only reached when the first two terms are false.
- No existing policy was changed or dropped; restrictive policies are ANDed with the permissive ones.
- `chunk_translations` and `rag_table_rows` have no client grant or policy (service_role only), so they need no client policy.

## Test coverage (`tests/rag-db/access-rls.test.mts`, both modes, 16 tests)

- Baseline: the same rows are read per caller before 0923 is applied; after 0923 with the flag off every caller (anon, admin, member-a, member-b, outsider, multi-tenant admin of another organization) reads exactly the baseline, for documents, chunks and parents.
- Flag on: single-tenant anon reads only `{all}`; member-a reads `{all}` and group-a; member-b `{all}` and group-b; outsider `{all}` and its own `u:` row; the admin reads all four. - InitPlan check, policy catalog check (one restrictive policy per table, roles `{anon, authenticated}`, permissive policy kept), helper grants, `rag_caller_access_keys()` output for anon / member / outsider, `rag_caller_is_access_admin()` for anon / admin / non-admin, idempotent re-apply.

## Decisions (for STATE)

- D-06-1: multi-tenant personal documents (`organization_id IS NULL`) get no admin bypass; their owner reads them through the `all` or `u:` key. Groups belong to organizations, so a personal document carries no group key.
- D-06-2: `rag_caller_access_keys()` returns the user's group keys from every organization; group ids are globally unique uuids, so a key never matches another tenant's row, and the existing permissive policies still decide tenant membership.
- D-06-3: the policies read the flag from `rag_access_group_settings` through `rag_access_enforced()`; `rag_access_set_enforced` (A-03 sync) is not on this branch yet, so the test sets the row directly as the table owner.
