# Phase 04.3 Plan 33: connector mapping, sharing rule and fallback count routes

**Admins can now map source groups, teams and workspaces to access groups, manage domain and link sharing rules, and read per-connection fallback counts over the shared `/api/rag/access-groups` API. Every route runs plan 22's guard → parse → workspace → operation order, uses strict `zod/v3` bodies, the plan 21 services through `@/lib/rag`, the shared response helpers (`Cache-Control: no-store`, `failureOf` codes), and the verified admin as the actor. No route starts a sync; every write answer says `appliesAt: 'next_sync'`.**

## Routes (request and response)

Failures are `{ success: false, error, details? }` exactly as plan 22 (401, 403 `Admin access required`, 403 `Forbidden`, 400 `Invalid request data` with `details`, 503 `access_groups_unavailable`). `organizationId` comes from the query or the body (both and different: 400). Path ids must be UUIDs.

| Route | Request | 2xx answer |
|-------|---------|------------|
| `GET /connector-map` | `?organizationId=&offset=` (integer ≥ 0) | `{ success, personal: false, visibilityApplies, rows: [{ id \| null, provider, kind, externalPrincipalId, groupId \| null, documents }], total, nextOffset \| null }`; unmapped rows first (SQL order), 50 per page. Personal workspace: `{ success, personal: true, visibilityApplies, rows: [], total: 0, nextOffset: null }`, no RPC |
| `POST /connector-map` | `{ organizationId?, provider: google-drive\|dropbox\|notion, kind: group\|team\|workspace, externalPrincipalId (trimmed, 1–512), groupId: uuid }` strict | 201 `{ success, mapping: { id, groupId, outcome: 'created' }, appliesAt: 'next_sync', visibilityApplies }` |
| `PUT /connector-map/{id}` | `{ organizationId?, groupId: uuid }` strict | `{ success, mapping: { id, groupId, outcome: 'changed'\|'unchanged' }, appliesAt, visibilityApplies }` |
| `DELETE /connector-map/{id}` | `?organizationId=` | `{ success, removed: true, appliesAt: 'next_sync' }` |
| `GET /connector-map/fail-closed` | `?organizationId=` | `{ success, connections: [{ connectionId, documents }] }` |
| `GET /sharing-rules` | `?organizationId=` | `{ success, personal: false, visibilityApplies, rules: [{ id, provider, kind: domain\|anyone\|public, domain \| null, enabled, documents }] }`; personal: `rules: []`, no RPC |
| `POST /sharing-rules` | `{ organizationId?, provider, kind, domain? }` strict (no `enabled` field: a rule is always created off) | 201 `{ success, rule: { id, enabled: false, outcome: 'created' }, appliesAt }` |
| `PUT /sharing-rules/{id}` | `{ organizationId?, enabled: boolean }` strict | `{ success, rule: { id, enabled, outcome: 'enabled'\|'disabled'\|'unchanged' }, appliesAt }` |

Codes: 409 `mapping_exists`, 409 `rule_exists`, 400 `unknown_group` (group of another workspace, raised by SQL), 400 `bad_domain`, 404 `not_found` (unknown id or another workspace's id), 400 `personal_tenant` for writes in a personal workspace (404 on id routes, as plan 22).

## Decisions (for STATE)

1. **`visibilityApplies` = `getDeploymentMode() === 'single-tenant'`** (A-10), returned by both list routes and by the mapping writes so the outcome message can say whether it changes visibility.
2. **Pagination by `offset`** (the service contract), with `nextOffset` computed from `total`; `rows` keep the SQL order (unmapped first).
3. **Personal workspace:** list routes answer empty with `personal: true` and no RPC; writes 400 `personal_tenant`; id routes 404. The fail-closed route does call the RPC in a personal workspace, because in multi-tenant mode connector documents live in the owner's personal tenant (A-10) and the Connectors card counts are meaningful there.
4. **Domain validation** stays in the plan 21 service (one pattern, lower-cased); the route's Zod schema only bounds the string (≤ 1000), so every malformed domain, including an empty or missing one for `kind: domain` and any domain on a non-domain rule, answers `bad_domain` rather than a generic 400.
5. **`enabled` is rejected on create** by the strict schema (400 `Invalid request data`), so no request can create a rule on (T-04.3-331).
6. **`deleteConnectorMap` returning false** is answered 404 `not_found` (the SQL already raises `mapping_not_found`; this is a second guard).
7. **Source group ids** are passed and returned exactly as given (trimmed only), never as names.
8. **Purge hook or store inventory:** none; no store added. **No migration**, so no migration number was claimed.

## Deviations

1. `_responses.ts` gains `connectorVisibilityApplies` and `mappingRowOf` (shared helpers stay out of route files, per plan 22's note).
2. Write answers carry `appliesAt: 'next_sync'` (and mapping writes `visibilityApplies`), not in the plan text, so the UI can end each outcome message with when it applies (UI-SPEC 6.5).
3. The fail-closed answer wraps the list as `{ connections: [...] }` instead of a bare array, to keep the `{ success, ... }` envelope.
