## User Constraints (from CONTEXT.md)

### Locked Decisions

### Data model (SEC-12)
- **D-01:** Groups are rows in a new table `rag_access_groups` (`id uuid`, tenant columns of the deployment mode, `key text` immutable slug, `name text` editable display name, `source text` `manual | connector`, `created_at`, `created_by`), unique on (tenant, key). Members are rows in `rag_access_group_members` (`group_id`, `user_id`, `added_by`, `added_at`, `source` `manual | connector`). RLS: server role only for writes; authenticated users may read their own memberships. A group never spans tenants: the tenant columns are NOT NULL in multi-tenant mode and the member insert path checks organization membership (D-04).
- **D-02:** Documents carry `access_groups text[] NOT NULL DEFAULT '{all}'` with a CHECK that the array is non-empty. Entries are principal keys:
  - `all` — every member of the tenant (today's behaviour);
  - `g:<group uuid>` — members of that access group (uuid, not slug, so renames never re-label documents);
  - `u:<user uuid>` — a single user (used only for the uploader fail-closed case, D-21, and connector user shares, D-19).
  A document visible to "all" never also carries other keys (normalised on write).
- **D-03:** The array is **denormalised** onto every retrievable row: `document_chunks`, `document_parents`, `chunk_translations`, and the Phase 4.2 table-row store and duplicate-cluster membership rows (whatever their final names). A GIN index on each `access_groups` column. A trigger on `documents` UPDATE OF `access_groups` propagates to all derived rows in the same transaction; writers copy the document's value on insert (ingest, rechunk, retranslate, relex, version replace). A consistency check function `rag_access_groups_drift()` returns rows whose array differs from their document (used by tests and the Config UI health view).
- **D-04:** Admins: multi-tenant → organization `owner`/`admin` roles; single-tenant → `admin_users`. Admins see every document of their tenant (`access_all`). Viewers and members are ordinary callers.

### Caller resolution (SEC-12)
- **D-05:** A new branded value `AccessScope` is minted only inside `src/lib/rag/tenant/` by `resolveAccessScope(scope, identity)`, alongside the existing `TenantScope`. Shape: `{ mode: 'off' | 'admin_all' | 'keys'; keys: readonly string[]; setHash: string }`. With `keys`, the set is `all` + `u:<caller>` + `g:<id>` for every membership; `setHash` = SHA-256 of the sorted keys (`off` and `admin_all` get fixed hashes). `runRetrieval` and every leg take `AccessScope` as a required argument; the RAG boundary check (`scripts/ci/check-rag-boundary.mjs`) is extended so `AccessScope` cannot be built elsewhere.
- **D-06:** Groups come only from the server: the verified Supabase session (chat, upload, documents APIs), the signed voice scope token's user id (voice: memberships are looked up at request time from that id, not embedded in the token, so a group change applies on the next turn), and the embed configuration (D-07). Any `accessGroups`/`groups` field in a request body is ignored and logged once per request as `[RAG Access] body_group_claim_ignored`.
- **D-07:** Embedded chat and WhatsApp visitors get `keys = ['all']` unless their configuration names a group: new env `RAG_EMBED_ACCESS_GROUP` (empty default; a group key that must exist in the embed tenant, else the embed fails closed to `all`-only and logs). Eval runs (`/api/internal/rag/run`) take groups from the fixture identity, never from the body.
- **D-08:** Membership is read with one indexed query per request (no cross-request cache), so a removal takes effect on the next request. Its latency is reported as stage `access_scope` on the trace against the existing latency budgets.

### Switch and off-behaviour (SEC-12, success criterion 1)
- **D-09:** `RAG_DOC_ACCESS_GROUPS=off|on` (default `off`), mirrored in all five config locations and the config manifest. Off → `AccessScope.mode = 'off'`, every SQL function receives `p_access_keys = NULL` and skips the predicate, the cache key part is the constant `off`, and traces/logs are unchanged. The columns, tables and default `{all}` exist regardless (migrations are not switch-gated), so turning the switch on needs no backfill.
- **D-10:** On → the filter applies in both pipelines: v2 legs (D-11) and the legacy search RPCs used by `RAG_PIPELINE=legacy` (they gain the same `p_access_keys` parameter). Groups on with any retrieval path that cannot apply the filter is a startup error that blocks retrieval (fail closed, structured "knowledge base temporarily unavailable" per AGENTS.md §14), never a silent fallback.

### Pre-ranking filter on every leg (SEC-12, success criterion 1)
- **D-11:** Every retrieval SQL function gains `p_access_keys text[] DEFAULT NULL` and `p_access_all boolean DEFAULT false`, applied in the same WHERE clause as the tenant predicate, before ORDER BY / LIMIT / RRF:
  `p_access_keys IS NULL OR p_access_all OR row.access_groups && p_access_keys`.
  Functions: `hybrid_search_chunks` (dense and lexical legs), the exact-id lookup, `rag_fetch_parents`, `hybrid_search_translations`, `match_chunks_by_profile`, the legacy workspace search RPCs, and the Phase 4.2 table-row lookup, identifier index/filter lookups (including the near-miss suggestion list, which must never suggest an identifier from a document the caller cannot see) and duplicate-cluster expansion (the "other sources" list under a collapsed citation lists only visible documents). All stay **service_role only**, `SECURITY DEFINER` with `SET search_path = ''`.
- **D-12:** The filter is on the denormalised row column and also re-checked by a join to `documents.access_groups` inside the same query (defence against trigger drift); a mismatch row is excluded and counted.
- **D-13:** HNSW with a selective filter: the dense leg relies on the Phase 4 `RAG_HNSW_ITERATIVE_SCAN` / `RAG_EXACT_SCAN_CUTOFF` machinery; when `AccessScope.mode = 'keys'` and the caller's visible share of the tenant is small, the pipeline forces iterative scan for that query. Research confirms the pgvector behaviour and the threshold; recall on restricted callers is measured in the canary suite.
- **D-14:** External backends (Phase 7 adapters): `access_groups` is added to the Qdrant payload (keyword index) and Weaviate property, written by the existing outbox drain (document `access_groups` updates enqueue like other synced columns), and a `MatchAny` / `ContainsAny` filter is injected on every query **and every prefetch** next to the tenant filter. The Phase 7 Supabase re-validation of returned ids also checks access groups. If an adapter cannot apply the filter, D-10 applies.
- **D-15:** Non-RAG read paths that expose document content or names to a caller apply the same scope in server code: document list and dashboard APIs, document/original download and preview, `source_images`, the `documentReferenceTool`, and folder listings. RLS gains a **restrictive** SELECT policy on `documents` and `document_chunks` for the `authenticated` role using a `SECURITY DEFINER` helper `rag_caller_can_see_document(access_groups)` that honours a DB-side enforcement flag (`rag_access_group_settings.enforced`, written together with the env switch by the Config UI/config server and checked against env at startup with a warning on mismatch). Restrictive policies only narrow access, so RLS cannot weaken.

### Assigning groups (SEC-12)
- **D-16:** At upload (Phase 3.2 upload surfaces, app and Config UI) the uploader picks `all` (default) or one or more groups they belong to; admins may pick any group of the tenant. In bulk backfill, `--access-groups <keys>` applies to the batch (default `all`).
- **D-17:** Admins change a document's groups from the document admin list (single and bulk). A change writes `rag_admin_audit`, propagates (D-03), bumps the cache generation of that document (D-24) and enqueues external sync.
- **D-18:** Deleting a group: documents whose array would become empty are set to `u:<uploader>` (fail closed, visible to the uploader and admins), never to `all`; the admin confirms with the count of affected documents. Removing a member is immediate (D-08).
- **D-19:** Re-upload / new version inherits the previous current version's `access_groups` unless the uploader explicitly changes it (within D-16 rules). Quarantine, release and version replace keep the array.

### Connector permission sync (DATA-22)
- **D-20:** On every Nango sync (Google Drive, Notion, Dropbox), the sync manager fetches the source's sharing for each document through the Nango proxy (Drive permissions, Dropbox shared members, Notion page/workspace sharing as far as the API exposes it) and maps principals:
  - a user principal whose verified email matches a tenant member → `u:<member id>`;
  - a group / team principal → the access group linked to it in a new mapping table `rag_connector_group_map` (tenant, provider, external principal id, `group_id`), maintained by admins; connector-created groups use `source = 'connector'`;
  - domain-wide or "anyone with the link" sharing → `all` only when an admin has enabled that mapping for that provider and domain in the tenant's connector settings; otherwise unmappable;
  - any principal that cannot be mapped → the document is set to `u:<uploader/connector owner>` (fail closed: uploader and admins only) and a sync warning is recorded per document.
  A permission change at the source updates `access_groups` on the next sync through the same write path (D-17 propagation, audit with actor `connector`).
- **D-21:** Notion: the public API exposes no per-page member list for most plans, so Notion documents are unmappable unless the admin maps the workspace (or teamspace) to a group; the default is fail closed. Research confirms the exact API surface per provider.
- **D-22:** Connector sync with `RAG_DOC_ACCESS_GROUPS=off` still records the mapped array (so turning on later is correct) but nothing enforces it.

### Derived stores (SEC-13)
- **D-23:** Semantic cache (Phase 6, `rag_semantic_cache`): `CacheKeyParts` gains `accessGroupSetHash` (the `AccessScope.setHash`); with the switch off it is the constant `off`, so baseline keys are unchanged in value semantics (key hash changes once, which only empties the cache). Entries also store the union of the source documents' `access_groups`; a lookup serves an entry only when the caller's set hash matches **and** every source document is still visible to the caller (re-checked in the lookup SQL).
- **D-24:** A change of a document's `access_groups` invalidates cache entries that used it (extends the existing `rag_semantic_cache_on_documents_update` trigger to fire on `access_groups`).
- **D-25:** Retrieval log, review queue and answer records (Phase 5.1.1 `rag_retrieval_log`, `rag_review_items`; Phase 5 `rag_answer_records`): rows store the union of `access_groups` of the content they hold; reads go through server code that shows restricted rows only to admins or members of every group the row's content needs (a reviewer who lacks a group sees the row with content masked). Langfuse and other external trace exports never carry text of restricted chunks: chunk ids and scores only (extends `trace/mask.ts`).
- **D-26:** Post-generation citation recheck: after the answer is final, every cited chunk id is checked in one batched query against the caller's `AccessScope` (and the tenant). The prompt is never the control.
- **D-27:** Shared chats: creating a share link for a chat whose messages cite restricted documents is refused (`403 restricted_content`) while the switch is on; the share view re-checks at read time and requires an authenticated viewer who can see every cited document.

## Summary

The codebase already has every pattern this phase needs, so the work is extension, not invention. Tenant isolation is a branded `TenantScope` minted in `src/lib/rag/tenant/`, passed to service-role SQL functions that take `p_tenant_key`; a CI boundary check forbids minting it elsewhere. Denormalised columns are kept equal to their document by triggers (`rag_chunks_legacy_defaults`, `rag_parent_currency_from_document`, `rag_sync_parent_currency`). A selective-filter recall harness (`eval/harness/selective-filter.mts`) and a two-tenant leak matrix (`eval/harness/two-tenant-v2.mts`) exist and run on PGlite in CI. `AccessScope` follows the first pattern, the `access_groups` column follows the second, and the EVAL-21 canaries extend the third.

Three facts found in the code change how the locked decisions must be implemented. First, `hybrid_search_chunks`, `rag_fetch_parents` and every semantic-cache function are `SECURITY INVOKER` today, not `SECURITY DEFINER` as D-11 states; they are safe because only `service_role` may execute them. Second, single-tenant read policies on `documents`, `document_chunks` and `document_parents` have no `TO` clause and admit `anon`, so a restrictive policy for `authenticated` alone (D-15) leaves restricted rows readable with the public anon key. Third, in multi-tenant mode every Nango document is written into the connection owner's personal tenant (`nangoOwnerScope` mints a `personal` scope), so connector group mapping only changes visibility in single-tenant mode. A PGlite probe run in this session confirmed the pgvector behaviour behind D-13: with 0.5% of rows visible, an HNSW scan without iterative scan returned 1 of the true top 10 (0 rows at the default `ef_search`), and `relaxed_order` or an exact scan returned all 10.

The largest risk is not the filter itself but function ownership across phases. `hybrid_search_chunks` is redefined whole by each phase that adds a parameter (0407, 0413, 0602 on trunk; 0802 planned by Phase 3.2; Phase 4.2 will add more). Adding a parameter creates a new overload, so the old one must be dropped, and whichever phase lands last must carry every earlier phase's parameters. A catalog sentinel test (every content-returning function has the access parameters, exactly one overload each) is what keeps a later phase from silently removing the filter.

**Primary recommendation:** Put the predicate into the existing filter string of each retrieval function only when keys are passed, send the two new arguments only when the switch is on, drop older overloads in the migration, and add three guards that fail closed: a SQL-side check that raises when enforcement is on and no keys arrive, a startup readiness check, and a PGlite catalog sentinel test. For restricted callers force the existing exact-scan probe (cutoff at least 1000) plus `relaxed_order` above it; no visible-share estimate is needed.

## Project Constraints (from CLAUDE.md)

Directives from `CLAUDE.md`, `AGENTS.md` and `.claude/CLAUDE.md` that bind this phase:

- All knowledge-base retrieval goes through `@/lib/rag`; `scripts/ci/check-rag-boundary.mjs` fails on embedding, retrieval-RPC or reranker use elsewhere. Tenant checks have no off switch.
- Retrieval RPCs are service-role only and called on the admin client with `scopeKey` as the only tenant input; `SUPABASE_SERVICE_ROLE_KEY` must be set.
- Every new env var goes into `.env.local`, `scripts/init-env.js`, `src/lib/env.ts`, `scripts/config-server.js` and the Config UI, plus `scripts/rag/env-manifest.json`; `node scripts/check-config.mjs` runs in CI.
- Every new component has a switch that restores current behaviour when off; each phase compares against the baseline and no slice may drop beyond the noise band.
- Behaviour to preserve: strict "information not available" only on a verified `empty`; a knowledge-base failure streams "knowledge base temporarily unavailable"; `source_images`; `{{context}}` in `RAG_SYSTEM_PROMPT`; voice and embed paths.
- Single-tenant and multi-tenant must both work; RLS and tenant isolation must not weaken.
- Migrations are ordered, idempotent, common file first then mode files; pgvector stays in schema `public`.
- Validate API inputs with Zod (`z` from `zod/v3`), return structured JSON errors, log with bracketed prefixes, never log content or secrets.

### Pattern 1: Brand minted in the tenant module

**What:** `AccessScope` is a frozen object registered in a module-private `WeakSet`, exactly like `TenantScope`.
**When to use:** The only way any code obtains access keys.
**Existing model:** `mintScope`, `isTenantScope`, `assertTenantScope` in `src/lib/rag/tenant/scope.ts`; boundary rule `mint-scope` in `scripts/ci/check-rag-boundary.mjs` ("mintScope used outside src/lib/rag/tenant/").

### Pattern 2: Predicate appended to the function's filter string

**What:** In `hybrid_search_chunks` the tenant predicate lives in one string, `v_filter`, that the exact-count probe, the dense query and the lexical query all embed. Append the access predicate to that string only when keys are passed.
**Why:** With no keys the generated SQL text is the same as today, so the off path is the baseline; with keys the same predicate reaches all three queries, so the exact-scan decision sees the caller's visible rows.

### Pattern 3: Copy-from-document triggers

**What:** `BEFORE INSERT` on each derived table sets `NEW.access_groups` from the document "whatever the writer sent"; `AFTER UPDATE OF access_groups` on `documents` updates derived rows.
**Existing model:** `rag_chunks_legacy_defaults` (comment in the function: "the chunk's tenant_key is always its document's, whatever the writer sent"), `rag_parent_currency_from_document`, `rag_sync_parent_currency` [VERIFIED: supabase/migrations/0425_search_path_empty.sql and 0413_chunking_activation.sql, read this session].
**Consequence:** No ingest writer needs to change to satisfy D-03's "writers copy the document's value". Add new trigger functions; do not edit `rag_chunks_legacy_defaults` (its body is owned by 0425 and by Phase 3.2).

### Pattern 4: Guarded DDL for seams

**What:** `DO` blocks that test `to_regclass('public.<table>')` and run literal `ALTER TABLE`, `CREATE INDEX`, `CREATE TRIGGER` statements.
**Limit:** This works for columns, indexes and triggers. It does not work for redefining a function that another phase authors: the body is unknown until that phase lands. For functions the guard is the readiness check plus the catalog sentinel test (see "Seams not on trunk").

### Anti-Patterns to Avoid
- **Filtering after the RPC returns:** loses recall at the LIMIT and reveals through timing and counts that hidden rows exist.
- **`p_access_keys => null` as a default code path while the switch is on:** NULL means unfiltered. Use one helper that returns either no arguments (off) or a non-empty array, and a SQL guard that raises when enforcement is on and keys are NULL.
- **Dynamic `EXECUTE` of `CREATE FUNCTION` inside `DO` blocks:** `tests/helpers/sql-function-acl.ts` replays SQL statically; a function created through dynamic SQL is invisible to the SECURITY DEFINER grant test.
- **Editing `0410`, `0425` or the setup files:** out of block; new functions carry their own `REVOKE` and `GRANT` in the 0920 block.
- **Relabelling only the current version:** superseded versions keep the old label and become retrievable again under RET-11 `versions: all`.
- **A per-row RLS helper that queries memberships:** runs once per row; use InitPlan helpers.

### 1d. Overload and signature rules (PostgreSQL and PostgREST)

- `CREATE OR REPLACE FUNCTION` cannot change the argument list. Adding parameters creates a second function with the same name. The 0602 migration shows the house pattern: `DROP FUNCTION IF EXISTS` for the old signature, `CREATE OR REPLACE` for the new one, then `REVOKE` and `GRANT` on the new signature, then `NOTIFY pgrst, 'reload schema'` [VERIFIED: 0602 header comment: "The 0407 signature is dropped first so exactly one function exists and PostgREST rpc() is never ambiguous (P-8); a new overload would otherwise get PUBLIC execute."].
- With two overloads present, a call that omits the new arguments fails: `ERROR 42725 function f(p_a => integer) is not unique`; a call that passes them resolves to the new function [VERIFIED: PGlite probe, output under Code Examples]. PostgREST reports the same situation as an ambiguity error and a missing function as a not-found error [ASSUMED: codes PGRST203 and PGRST202; the PostgREST page returned HTTP 429 in this session].
- On a full re-apply of the migrations (the idempotency test and the fixture path), 0407 and 0413 recreate the 20-parameter overload and 0602 recreates the 21-parameter one before the 0920 block runs. The 0920 migration must therefore drop **every** older signature it knows, and the list grows when Phase 3.2's 0802 lands (24 parameters with `p_scopes`, `p_scopes_include_untagged`, `p_effective_on`). Write the `DROP FUNCTION IF EXISTS` list from a grep of all definitions at execution time.
- A new function gets `EXECUTE` for `PUBLIC` by default on Supabase; always follow `CREATE` with `REVOKE ALL ... FROM PUBLIC, anon, authenticated` and `GRANT EXECUTE ... TO service_role` as literal top-level statements, so `simulateFunctionAcls` sees them.
- The 0425 precheck stops with SQLSTATE 55000 unless listed signatures exist, including `public.match_chunks_by_profile(text,text,integer,public.halfvec,integer,double precision,boolean)`, `public.rag_exact_id_documents(text,text[],integer)` and `public.match_documents_by_workspace(public.vector,integer,double precision,uuid,uuid)`. After the 0920 block has dropped those, re-running 0425 alone fails (safely, nothing changes). Operator rule for the migration header: after re-running any file below 0920, re-run the whole ordered sequence through the 0920 block.
- Re-running `0306` after the 0920 block recreates the five-parameter `match_documents_by_workspace` as a new function with default grants until 0409 and 0410 run. Same operator rule.
- Send the arguments only when the switch is on. Off: the RPC payload is unchanged, so the baseline and a rollback do not depend on the migration. On: both arguments are always sent; if the migration is missing the call fails and retrieval reports an error (fail closed).

## 2. pgvector HNSW with a selective access filter

**What pgvector does.** "With approximate indexes, filtering is applied after the index is scanned." "If a condition matches 10% of rows, with HNSW and the default `hnsw.ef_search` of 40, only 4 rows will match on average." "Starting with 0.8.0, you can enable iterative index scans." "Strict ensures results are in the exact order by distance." "Relaxed allows results to be slightly out of order by distance, but provides better recall." `hnsw.max_scan_tuples`: "Specify the max number of tuples to visit (20,000 by default)." [CITED: github.com/pgvector/pgvector README, sections "Filtering", "Iterative Index Scans", "Iterative Scan Options"].

**Measured in this session** (PGlite 0.5.17, PostgreSQL 18.7, pgvector 0.8.7; 20,000 rows, 100 visible to the caller through `access_groups && ARRAY['all','u:x','g:a']`, HNSW cosine, k = 10, index scan forced, `ef_search = 100` unless noted) [VERIFIED: PGlite probe]:

```
default-plan rows (no settings) 0            <- planner chose the HNSW index, ef_search 40: nothing returned
{ mode: 'off',           n: 1,  recall: 0.1 }
{ mode: 'relaxed_order', n: 10, recall: 1 }
{ mode: 'strict_order',  n: 10, recall: 1 }
{ mode: 'relaxed_order', n: 10, recall: 0.9 }   <- hnsw.max_scan_tuples = 2000
{ mode: 'relaxed_order', n: 10, recall: 1 }     <- hnsw.max_scan_tuples = 200000
defaults [ { mst: '20000', it: 'off', ef: '40' } ]
gin plan ... Bitmap Heap Scan on chunks ... Recheck Cond: (access_groups && '{all,u:x,g:a}'::text[]) ... Bitmap Index Scan
```

So a restricted caller on an untuned ANN scan gets almost nothing, iterative scan repairs it while the visited tuples stay under `hnsw.max_scan_tuples`, and GIN on `text[]` works in the fixture database.

**How the repository's machinery works** (all in `hybrid_search_chunks`, newest body 0602) [VERIFIED: 0602:85-90, 169-196]:
- `p_exact_scan_cutoff` (0 to 100000, from `RAG_EXACT_SCAN_CUTOFF`, default `0`): when above 0 the function runs `SELECT count(*)::int FROM (SELECT 1 FROM <from> WHERE <v_filter> LIMIT cutoff + 1) s`; if the count is at most the cutoff it sets `v_mode := 'exact'` and runs the dense query without `ORDER BY ... LIMIT` inside the materialized `hits` CTE, then sorts by `dist + 0`. The returned `dense_mode` column says `exact` or `ann`.
- `p_iterative_scan` (`off | relaxed_order | strict_order`, from `RAG_HNSW_ITERATIVE_SCAN`, default `off`): in ANN mode the function sets `hnsw.ef_search` to `least(greatest(p_dense_limit * 2, 100), 1000)` and, when the mode is not `off`, checks the extension version and raises `iterative_scan_unsupported` below 0.8, else sets `hnsw.iterative_scan` for the transaction.
- TypeScript: `config.v2.iterativeScan` and `config.v2.exactScanCutoff` in `src/lib/rag/config.ts` (`parseIterativeScan`, `parseNonNegativeInt`), passed by `buildRpcArgs` in `backend/pgvector.ts`; `verifyV2Startup` in `v2/startup.ts` records `pgvector_iterative_scan_unsupported`; both values are part of the retrieval config hash (`v2/config-hash.ts`, `v2/result.ts`).
- Harness: `eval/harness/selective-filter.mts` and `tests/rag-db/selective-filter.test.mts` already measure recall for `off`, `relaxed_order`, `strict_order` and `exact` on a small tenant and a rare document type.

**Recommendation for D-13 (fixed rule).** When `AccessScope.mode === 'keys'`, the backend sends:
1. `p_exact_scan_cutoff = max(config.v2.exactScanCutoff, 1000)`. The probe counts the rows the caller can see inside the tenant and the other filters; at or below the cutoff the dense leg is an exact scan, so recall is 1 by construction. 1000 is the value the existing selective-filter test uses (`EXACT_CUTOFF = 1000`) [ASSUMED as the right default for production sizes; the canary recall test measures it].
2. `p_iterative_scan = 'relaxed_order'` when the configured value is `off` and the startup verdict's pgvector version is 0.8.0 or newer; otherwise the configured value. The function already re-sorts by exact distance, so relaxed ordering does not change the final order.

For `mode: 'off'` and `mode: 'admin_all'` nothing changes. The forced values must not enter the retrieval config hash as configuration; record them on the trace (`access_exact_cutoff`, `dense_mode`).

**Limits to state in the plan.** Above the cutoff, iterative scan stops at about `hnsw.max_scan_tuples` visited tuples (default 20,000) [CITED: pgvector README]. The HNSW index on `document_chunks.embedding` is shared by all tenants, and for `halfvec` profiles the index is on `chunk_embeddings` while every filter column is on the joined `document_chunks`, so tenant and access filters are both applied after the index scan. A caller with more than 1000 visible rows in a very large shared index can still get fewer than k dense rows. This is the existing small-tenant problem of Phase 4, not new; the lexical and exact-id legs are unaffected. The canary must assert `recall@k = 1` against a brute-force ranking for the restricted member.

**Legacy RPCs.** `match_documents_by_workspace` and `match_chunks_by_profile` use `ORDER BY <distance> LIMIT` with a similarity threshold in WHERE and have no exact path. For restricted callers add the same two steps inside the function: a bounded count of visible rows, then either a materialized exact query or `set_config('hnsw.iterative_scan', 'relaxed_order', true)` with a raised `hnsw.ef_search`. Single-tenant `match_document_chunks` orders by the computed `similarity` and already scans exactly.

**GIN index.** Every caller's key set contains `all`, and most rows are labelled `{all}`, so the planner will rarely pick the GIN index for retrieval. Its value is in admin operations (`access_groups @> ARRAY['g:<id>']` for group deletion counts, drift checks) and in the probe for callers whose visible set is small. D-03 locks one GIN index per column; build them in the migration, and note that `CREATE INDEX` inside the migration transaction blocks writes on a large live table for the build.

**Evaluation of D-15's flag.** Three options were compared:

| Option | Behaviour | Verdict |
|--------|-----------|---------|
| A. Flag written by the Config UI with the env switch; startup warns on mismatch (D-15 as written) | Two sources of truth; deployments that set env on the host never write the flag; a mismatch means direct client reads are unfiltered while the app filters | Works only where the Config UI is the way env is changed |

**Shape of the mechanism (R-1, R-2, R-3).**
- `rag_access_group_settings`: one row (`id boolean PRIMARY KEY DEFAULT true CHECK (id)`, `enforced boolean NOT NULL DEFAULT false`, `updated_at`, `updated_by`), RLS on, no client grants.
- `rag_access_enforced()` and `rag_caller_access_keys()`: `STABLE SECURITY DEFINER SET search_path = ''`, no arguments, identity from `auth.uid()`, granted to `anon` and `authenticated`, both in the allow-list with `anon: true`. For anon the keys are `{all}`.
- Policies in the mode files: `AS RESTRICTIVE FOR SELECT TO anon, authenticated USING ((SELECT public.rag_access_enforced()) IS NOT TRUE OR access_groups && (SELECT public.rag_caller_access_keys()) OR <admin helper of the mode>)` on `documents`, `document_chunks`, `document_parents`. Every function the policy calls must be executable by both roles (R-2). The sub-selects are evaluated once per statement [VERIFIED: PGlite probe, plan shows `InitPlan 1` and `InitPlan 2`].
- The same flag gives a second fail-closed guard inside every retrieval function: `IF p_access_keys IS NULL AND public.rag_access_enforced() THEN RAISE EXCEPTION 'access_scope_required' USING ERRCODE = '42501'; END IF;`. A code path that forgets to pass keys then errors instead of returning unfiltered rows.
- Startup (D-10): a function such as `verifyAccessGroupsStartup` called from `src/instrumentation.ts` next to `verifyV2Startup`: sync the flag, then call a readiness RPC that checks through the catalog that every retrieval function has `p_access_keys`, that each has one overload, and that every derived table has the column. With the switch on and the verdict not ready, `resolveAccessScope` refuses and the routes answer with the existing "knowledge base temporarily unavailable" path.
- Column guard: `access_groups` on `documents` must not be writable by clients. Single-tenant policies let an authenticated owner insert and update documents and chunks directly. Add a `BEFORE INSERT OR UPDATE OF access_groups` trigger: for a session role other than the service role, force the default on insert and reject a change on update; on derived tables always overwrite from the document.
- Key validation: a CHECK through an immutable function that every element is `all`, `g:<uuid>` or `u:<uuid>`, plus the non-empty CHECK of D-02; normalisation (`all` alone) in the setter.

The durable guard for all function seams is one PGlite test, the **catalog sentinel**: enumerate public functions whose source mentions `document_chunks`, `document_parents`, `chunk_translations` or `documents` and whose result includes content; each must be in the "filtered" list (has `p_access_keys`, exactly one overload) or in an "exempt" list with a written reason (writers, admin tools, guarded legacy functions). ## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Recall under a selective filter | A visible-share estimator or over-fetch in TypeScript | The existing exact-scan probe and iterative scan in `hybrid_search_chunks` | The probe already counts the filtered rows; over-fetching cannot guarantee k |
| Scope branding | A new validation scheme | The `WeakSet` plus frozen object pattern of `scope.ts` and the `mint-scope` boundary rule | Proven and already tested |
| Keeping derived rows in sync | Changes to every writer | Triggers modelled on `rag_chunks_legacy_defaults` and `rag_sync_parent_currency` | Covers legacy writers and future ones in the same transaction |
| Admin checks | A new session mechanism | `checkAdmin`, `requireRagAdmin`, `isOrganizationMember(..., roles)`, `is_org_admin`, `is_admin` | Fail-closed helpers that are already allow-listed |
| Request validation | Manual parsing | `withValidation` / `validateRequest` from `src/lib/api-middleware.ts` with `zod/v3` | Project convention and error shape |
| Qdrant filter injection | Filters built in the adapter | `qdrantScopedRequest` and `assertScoped`, extended | The wrapper asserts every filter location |
| Function grant checks | A new audit script | `simulateFunctionAcls`, `AUTHENTICATED_ALLOW_LIST`, `assertNoClientCallableRagFunctions` | Existing CI gates |

## Common Pitfalls

### Pitfall 1: An older overload survives
**What goes wrong:** Two functions named `hybrid_search_chunks`; calls without the new arguments fail as ambiguous, or an unfiltered overload stays callable.
**Why it happens:** Adding parameters never replaces; older migrations recreate their signature on re-apply.
**How to avoid:** Drop every earlier signature in the 0920 file; sentinel test asserts one overload per name.
**Warning signs:** `function ... is not unique` (42725); the schema-equality "twice" test differs.

### Pitfall 2: A later phase redefines a function without the predicate
**What goes wrong:** The filter disappears from a leg with no error.
**How to avoid:** Catalog sentinel test plus the SQL guard that raises when enforcement is on and keys are NULL. The guard only helps if the body kept it, so the sentinel also checks that the function source mentions `access_groups`.

### Pitfall 3: NULL keys while the switch is on
**What goes wrong:** `p_access_keys IS NULL` skips the predicate.
**How to avoid:** One `accessRpcArgs` helper, the SQL guard, and a required `access` field so no call site can omit it.

### Pitfall 4: Anonymous reads in single-tenant mode
**What goes wrong:** A policy for `authenticated` leaves the anon key able to read every row.
**How to avoid:** R-1. Test with `SET LOCAL ROLE anon`.

### Pitfall 5: Permission changes hidden by the modified-time skip
**What goes wrong:** A file whose sharing changed is skipped; its groups never update.
**How to avoid:** Permission step before the skip, for every listed file.
**Warning signs:** A sync reports only skipped files and no permission calls.

### Pitfall 6: Relabel reaches only the current version
**What goes wrong:** Superseded versions keep a wider label.
**How to avoid:** The setter updates by `lineage_id`; the drift test includes non-current rows.

### Pitfall 7: A restricted upload is visible before its label is set
**What goes wrong:** A legacy writer inserts a `ready` document as `{all}`, then the label is applied.
**How to avoid:** Legacy writers send the array in the insert; the unified pipeline sets it before publish.

### Pitfall 8: The last migration has no function
**What goes wrong:** The "dump has teeth" test fails.
**How to avoid:** Order the block so the last file per mode defines a function.

### Pitfall 9: Functions created through dynamic SQL
**What goes wrong:** The static grant test does not see them; the live-catalog test may then fail for an unexpected reason.
**How to avoid:** Top-level `CREATE`, `REVOKE`, `GRANT`; guards only around DDL on tables.

### Pitfall 10: Deleting a cache row that is merely not visible to this caller
**What goes wrong:** One outsider's lookup evicts an entry that is valid for others.
**How to avoid:** Delete on "not current", miss without delete on "not visible".

### Pitfall 11: Re-running older migrations on a live database
**What goes wrong:** The 0425 precheck fails after signatures were dropped; `0306` recreates a function with default grants.
**How to avoid:** Header note in the 0920 files; `supabase/README.md` operator rule.

### Pitfall 12: The fake edge rejects the new arguments
**What goes wrong:** Route tests fail with "unsupported rpc argument(s)" or "unsupported operator".
**How to avoid:** Update `RPC_ARGUMENTS`, `TABLE_COLUMNS` and the operator table in `eval/harness/fake-edge.mts` in the first wave.

### Pitfall 13: Existence leaks through side channels
**What goes wrong:** Counts, file names in lists, identifier suggestions, "document not found" versus "forbidden", or share-link errors reveal that a restricted document exists.
**How to avoid:** Not-visible answers exactly like unknown; filter counts and suggestions; canary asserts no restricted id appears in any payload.

### Pitfall 14: `access_scope` in the optional stage list
**What goes wrong:** `RAG_DISABLED_STAGES=access_scope` turns the control off.
**How to avoid:** Record it directly; a config test asserts the name is not accepted as a disabled stage.

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Request body names a group | Elevation of privilege | Groups resolved only on the server; claim ignored and logged (D-06); canary variant |
| A retrieval leg without the filter (new leg, redefined function, stale overload) | Information disclosure | Required `access` field, SQL guard, readiness check, catalog sentinel, per-leg canary with negative control |
| Direct PostgREST read with the anon key or a user token | Information disclosure | Restrictive policy for `anon` and `authenticated` on documents, chunks and parents; content RPCs service_role only |
| Client writes `access_groups` on its own document or chunk | Tampering | Guard trigger; derived rows overwritten from the document; D-12 join recheck |
| Member plants content into another group's view by labelling an upload | Tampering | Server validates chosen groups against the uploader's memberships (D-16) |
| Cached answer served across group sets | Information disclosure | Access hash in the key; source visibility recheck; invalidation on relabel |
| Cached refusal served to a member, or a member's answer to an outsider | Information disclosure and denial of service | Same key part; canary case |
| Model cites a chunk the caller may not see | Information disclosure | Batched recheck after generation; citation dropped; security event |
| Restricted text in logs, traces, review queue, external exports | Information disclosure | Ids and scores only for restricted chunks; label sets on stored rows; restrictive policy on reviewer-readable tables |
| Existence oracle (counts, names, identifier suggestions, error differences, timing) | Information disclosure | Filter before counting and suggesting; identical not-found answers; pre-ranking filter |
| Stale membership after removal | Elevation of privilege | Per-request lookup; cleanup trigger on organization membership delete |
