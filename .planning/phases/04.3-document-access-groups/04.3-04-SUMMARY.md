## Behaviour changes

- With `RAG_DOC_ACCESS_GROUPS=off` (default) nothing a reader sees changes: every label stays `{all}` unless service_role sets one.
- A relabel of a document (service_role or any DEFINER writer) rewrites the label of its chunks, parents, translations and table rows in the same statement.
- A client role (anything other than `service_role`, `postgres`, `supabase_admin`) that inserts a document gets `{all}` whatever it sent; one that changes `documents.access_groups` gets `access_groups_server_only` (42501). Writing the unchanged value is allowed. On derived rows the copy triggers replace any client value with the document's; no error is raised there.
- A version created by `rag_begin_document_version` (or any insert with a lineage) and the default label inherits the label of the lineage's current version in the same tenant.

## Bug fixed (tests failed before the fix)

**Client inserts into `documents` and `document_chunks` failed on this branch.** Plan 03's CHECK constraints called `public.rag_access_keys_valid`, which is revoked from `anon` and `authenticated`; a CHECK runs with the writing role's privileges, so every PostgREST insert or update of those tables by a signed-in user (single-tenant owner uploads, multi-tenant member uploads) raised `permission denied for function rag_access_keys_valid`. The checks now spell the same rule without a function call (non-empty, no NULL, each key `all` / `g:<uuid>` / `u:<uuid>` via one anchored regex over the comma-joined array, `all` alone, a comma count that rules out an element holding a comma); a constraint of the earlier form is dropped and recreated by name, so a database that applied plan 03's 0921 is upgraded. `rag_access_keys_valid` stays service-role only. Failing before: `access-schema` "a client cannot set or change access_groups…" (`permission denied for function rag_access_keys_valid`) and "the access_groups checks call no function and agree with rag_access_keys_valid…" (constraint definition names the function), both modes. The new key-check case compares the constraint with the function on twelve arrays, including `['g:<a>,u:<b>']`, `['']`, upper case and `all` next to a key.

## Decisions (for STATE)

1. **Client = every role but the server roles.** The guard uses the 0320 allow-list (`service_role`, `postgres`, `supabase_admin`) rather than naming `anon` and `authenticated`, so a new API role is a client by default. DEFINER writers run as their owner and pass.
2. **Inheritance tenant check.** `documents.tenant_key` is generated and unset in a BEFORE trigger, so `rag_documents_access_inherit` computes the row's tenant the way the generated column does (`o:<org>` / `u:<user>` multi-tenant, `s:default` single-tenant; mode from `documents.user_id NOT NULL`, as `rag_begin_document_version` decides it) and copies only from a current row of the same lineage and tenant.
3. **Inheritance treats `{all}` as "default".** A writer that explicitly wants `{all}` on a new version of a restricted lineage gets the lineage label; the explicit choice is applied afterwards through plan 05's setter (plan 23), as the plan states. Any other explicit array is kept.
4. **Function-free CHECK** (bug above) instead of granting `rag_access_keys_valid` to clients, which would break the rule that new functions are revoked from anon and authenticated.
5. **One shared copy function.** Both optional stores link by `document_id`, so they reuse `rag_access_groups_from_document()`; no per-store copy function was needed.
6. **Drift counts every row**, current and superseded, through a join on `document_id`; optional stores are counted through `to_regclass` and `EXECUTE` only when the table and its column exist.
7. **0410 entries** for the four new DEFINER functions (`rag_access_groups_propagate`, `_propagate_table_rows`, `_propagate_translations`, `rag_documents_access_inherit`), per the standing rule. The INVOKER guard and drift functions are revoked and granted in 0921 only.
8. **Purge hook / store inventory:** none; no new store, only columns on existing ones.
