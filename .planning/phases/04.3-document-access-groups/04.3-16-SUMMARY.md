# Phase 04.3 Plan 16: restricted-caller recall on pgvector and the access conformance suite

**For an access filter in mode `keys` the pgvector backend now sends `p_exact_scan_cutoff = max(configured, 1000)` and, when the configured iterative scan is `off` and pgvector is 0.8.0 or newer, `p_iterative_scan = 'relaxed_order'`. On PGlite a restricted member's dense top-k equals the brute-force ranking over the rows they can see, below and above the 1000-row cutoff. `runAccessConformance` holds any backend to the same-tenant access contract, and pgvector passes it.**

## Behaviour changes

- `RAG_DOC_ACCESS_GROUPS=off` (default), and access modes `off` / `admin_all`: the request body is unchanged (tested: configured cutoff and scan, no leg meta added).
- Mode `keys`: the exact-scan floor is 1000, so a caller who can see at most 1000 rows (within the tenant and the other filters) gets an exact dense scan; above it, the relaxed iterative scan is asked for when pgvector ≥ 0.8.0. A larger configured cutoff or a configured `relaxed_order`/`strict_order` is kept.
- The retrieval config and its hash are unchanged (config object not mutated; `params-hash` tests pass). The values sent are recorded on `BackendLegs.meta` as `accessExactCutoff` and `accessIterativeScan`.

## Recorded values

- Recall fixture: one tenant, three labels: 60 rows (`g:` small group), 1100 rows (`g:` large group), 1340 rows (other group); HNSW m=16, ef_construction=64; index scan forced (`enable_seqscan`/`enable_bitmapscan` off).
- Small member (60 visible): `dense_mode` exact, top-10 identical to brute force. Large member (1100 visible): `dense_mode` ann, `relaxed_order`, recall@10 = 1. Negative control (configured `off`, cutoff 0) for the small member: recall < 1.
- Purge hook / store inventory: none; no new store.

## Decisions (for STATE)

1. **pgvector version source:** the startup verdict (`getV2StartupVerdict().pgvectorVersion`), injectable as `PgvectorBackendDeps.pgvectorVersion`. An unknown version (startup not run) keeps the configured iterative scan; the exact-cutoff floor still applies. Sending `relaxed_order` to pgvector < 0.8 would raise `iterative_scan_unsupported`, so the rule only forces it on a known ≥ 0.8.0 version.
2. **Trace recording:** the forced values go on the backend leg meta (`BackendLegsMeta.accessExactCutoff`, `accessIterativeScan`), set for every keys request. Today no v2 stage reads `BackendLegs.meta` into the trace (neither does `denseMode`); wiring meta into the stage record is left to the plan that owns the trace fields.
3. **Brute-force helper:** `exactFilteredRanking` now orders by `(embedding <=> q) + 0` so it never uses the HNSW index (with `enable_seqscan = off` it previously returned the approximate, post-filtered ranking — 0 rows for a restricted caller). `selective-filter.test.mts` still passes 7/7.
4. **Fixture vectors lean towards the query** by a seeded amount: with near-orthogonal random 1536-d vectors HNSW's own approximation gave recall 0.9 even with production index params, which measures HNSW noise, not the filter. With graded similarity the test is stable (two consecutive runs, 17 s each).
5. **Conformance suite shape:** the factory receives `ACCESS_DATASET` (one org tenant, member-a in group-a, an outsider, an admin; restricted `g:`, open `{all}` and member-a's `u:` row) and loads it into its store; scopes are minted in the suite with `mintScope` + `withAccess` + `mintAccessScope`. The negative control `ignoringAccess` searches the bare tenant scope with `access: off` (an adapter that applies only the tenant filter); the suite asserts it leaks on each leg. The pgvector-specific "mismatched access is refused" check stays in `pgvector-adapter.test.ts`, not in the shared suite.
