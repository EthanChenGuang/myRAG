## What was built

- **Route canaries** (`tests/rag/access/routes-access-canary.test.ts`). They use the `startRouteFixture` fake edge with the plan 51 seed (`seedAccessGroups`) loaded into the route fixture database. They run in both deployment modes and in zh, en and it, with `RAG_DOC_ACCESS_GROUPS=on`. After each route load, the database flag is synced through the product startup check (`verifyAccessGroupsStartup`). Only the readiness answer is filtered, and only for the two pending 1008 objects, as in the plan 51 matrix. Each leak check serialises the prompt, the whole response body and every console line, then looks for every restricted marker and id (`leakedMarkers`).
  - chat, legacy and v2, strict: the outsider gets the refusal, the model is never called and no marker appears. member-a's prompt carries the restricted text. An outsider body that claims `group-a` (`accessGroups`, `groups`) changes nothing and is logged exactly once (`body_group_claim_ignored`).
  - embed: with `RAG_EMBED_ACCESS_GROUP` unset, with a body claim and with an unknown key (`embed_group_not_found`), no marker appears. With the variable set to `group-a`, the prompt carries the restricted text.
  - voice-rag: the outsider's token and a body claim return no marker. A member-a token returns the restricted text. Then member-a is removed from group-a through `rag_access_member_remove`, and the second turn with the same token and the same route instance returns no marker.
  - eval run: the fixture identity (`options.user_id`) decides. A body claim answers 400 with nothing retrieved, and member-a gets the restricted text.
  - share: a chat citing the restricted document answers 403 `restricted_content` and writes no share id. A chat citing only the `all` control document gets a share id.
  - Negative control (run locally, not committed): with the switch forced off, all 18 cases selected by `-t "en "` (en routes, share, and the voice cases) fail.
- **Off baseline** (`defaults-equal-phase3.test.mts`, new case). With `RAG_DOC_ACCESS_GROUPS` and `RAG_EMBED_ACCESS_GROUP` unset, legacy and v2 retrieval runs through a recording admin client. The case asserts that no RPC argument starts with `p_access`, that no resolver RPC runs, that no `access_scope` stage is recorded and that the result has no `setHash`, `access_mode` or `access_set`. It also asserts that the captured `[RAG Trace]` lines (at least two) and all other console lines contain no `[RAG Access]` or access field, and that `cacheAccessKeyPart(scope)` is `off` (the one-time key part).
- **Run config.** `eval/config/runs/access-groups-on.json` sets `RAG_DOC_ACCESS_GROUPS: on`. The allowlist gains only that name, with the values `off` and `on`. `RAG_EMBED_ACCESS_GROUP`, any other value and any other name are still rejected.
- **Docs.** AGENTS.md section 6 has a new "Document access groups (Phase 4.3)" block. It covers both switches and their defaults, labels, verified identity, migration block 0920 to 0939 (not folded, idempotent, with the re-run rule including 0410, 0933 and 0934), the startup enforcement flag and readiness, the admin API under `/api/rag/access-groups`, the share and read paths, the two Phase 7 seams, A-12 and A-10, and the canaries. `agents-guide.test.ts` asserts 18 fragments, checks the defaults against `src/lib/env.ts` and checks that the documented names exist in the code. README_NANGO_INTEGRATION.md now lists `sharing.read` in the Dropbox permissions and the Nango scopes. It also has a "Permission sync scopes" note: Drive needs nothing beyond `drive.readonly`, Dropbox needs `sharing.read`, existing Dropbox connections must be re-authorized and stay owner-only until then, Notion maps the workspace principal, and A-10 applies.

## Deviations

1. **[Rule 3] `eval/harness/fake-edge.mts`** is outside `files_modified`. The share refusal reads `documents` by `lineage_id IN (…)` and `rag_answer_records.citations` by `chat_id`, and the fake edge refused both, so the share leg would have answered 503. I added `lineage_id: ['eq', 'in']` and a `rag_answer_records` entry (`citations`, filter `chat_id eq`). The change is additive; the fixture-edge tests pass 75/75.
2. **[Rule 3] `tests/eval-env-pin.test.ts`** is outside `files_modified`. It is the existing home of the run-config allowlist tests (the plan names "its rejection test"), so the RED case went there.
3. **Share user client.** The share route builds its user client with the anon key and the bearer token. The test mocks only that client (session user and chat row). The admin client and every label read go through the real fake edge.
4. **Localized refusal text.** For the outsider, the test pins "Information Not Available" only for en. For it, the route's language detection localizes the refusal as Spanish ("Información no disponible"). This is pre-existing behaviour unrelated to access groups, and I recorded it for the owner. For every language the test asserts that the model is never called and that no marker appears.
5. **Switch-on smoke.** As committed, the run fails closed because of the pending 1008 objects (see Smoke reports). The slice comparison was measured with a local, uncommitted readiness filter.
6. **pr-smoke wiring.** No workflow change was needed. `ts-vitest` runs the whole vitest include (`tests/**/*.test.ts`, which contains the new canary file), and `ts-db` runs `tests/rag-db/*.test.mts` (the plan 51 matrix). Both are required jobs of the final pr-smoke gate.
