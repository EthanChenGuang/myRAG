# Phase 04.3 Plan 15: shared chats and the non-retrieval read paths

**With `RAG_DOC_ACCESS_GROUPS=on`, a chat that cites a restricted document gets no share link, an existing link is re-checked against the current labels on every read (route, page and page title), and the document list, document by id, images, scraper status, ingest status and job status routes show only what the caller may see. A hidden document answers exactly like an unknown one. Two boundary rules make a new content-table read or an unresolved `runRetrieval` caller fail CI. With the switch off every route answers as before.**

## Behaviour (switch on)

- **Share link (D-27).** `POST /api/chats/share`, after the ownership check and before a share id is generated or an existing one returned: if any version of a cited lineage is labelled other than `{all}`, 403 `{ error: 'restricted_content' }`. A failed label lookup answers 503 `{ error: 'access_groups_unavailable' }` and writes no share id. The route keeps its `{ error }` shape.
- **Read check (D-27, A-13).** `GET /api/chats/[shareId]`, the shared page and its `generateMetadata` load the cited documents and check each lineage's current version (every known version when none is current). If all are labelled `all`, anyone reads the chat as today. Otherwise the viewer must be signed in, resolve to the documents' tenant, and see every one through `visibleDocumentIds`. An anonymous viewer, an outsider, a lookup failure or a tenant mismatch gets the unknown-share answer: the same 404 body on the route, `notFound()` on the page, and the generic title `Shared Chat` from `generateMetadata`.
- **Viewer identity (D-06).** `sharedViewerId` reads only the request's own session. When an `Authorization` header is present it validates the Bearer token with the admin client's `auth.getUser(token)`; otherwise it uses the cookie session (`createClient()` from `src/lib/supabase/server.ts`, `auth.getUser()`). A missing, malformed or invalid session means an anonymous viewer, never an error. The viewer is looked up only when a cited document is restricted. The page and `generateMetadata` each resolve the viewer themselves.
- **Cited documents.** These come from `metadata.citations[].documentId` and `alsoIn`, from `usedDocuments` and `documents` (document references) on messages, parts, part metadata and part data, from `source_images` / `images` URLs (resolved to documents through `document_chunks.metadata->>image_url`), and from the citations of the chat's `rag_answer_records`. Only UUIDs are used. More than 500 ids or 200 image URLs fails closed.
- **Document list (D-15, UI-SPEC decision 6).** `.overlaps('access_groups', keys)` on both list queries, so counts and the empty state never reflect hidden documents. Every returned document carries `restricted: boolean`. Access admins (`admin_all`, including the owner of a personal workspace) also get `audience` `{ kind, groups: [{ id, name }], peopleCount, fallbackReason }` and `connectorManaged`, from `documentAudiences`. `access_groups` is never returned. If access cannot be resolved, the route answers 503 `access_groups_unavailable`.
- **By id.** `PATCH` and `DELETE /api/documents/[id]` add the overlap to the lookup by id, so a hidden id answers the existing 404 `Document not found` and nothing changes.
- **Images.** `GET` leaves hidden image documents out; on `DELETE`, a hidden id answers 404 `Image not found` and nothing is deleted.
- **Scraper status.** A hidden scraped page reads as `scraped: false`.
- **Ingest status / job status.** A document (or a job's document) the caller may not see answers the route's own not-found, unless the caller uploaded it (`processing_state.uploaderId` or `user_id`) or is an access admin. A failed lookup answers 503 with the route's existing unavailable message.
- **Switch off (D-09).** No label, visibility or resolver call is made, no new column is selected, and no new field is returned. Every route answers as before; the off cases in both test files pin this.

## Known limits

- **Unverifiable messages (T-04.3-155, accepted).** A message that has no citation metadata, no used-document or document-reference part and no source images cannot be checked. Such a message carries no record of which documents fed it, so a chat made only of those messages shares and reads as before. The read check covers every message that carries any of these.
- **Image bytes (A-12).** Extracted images live in the public `chat-images` bucket. The checks keep their URLs out of the responses above, but anyone who already holds a URL can still fetch the bytes.
- **Own history (A-13).** The sharer's own chat history is not retracted. Only shared views by others apply the live check.
- **`src/lib/answers/read.ts`** relies on documents RLS through the session client. The label-aware restrictive policy is migration 0923 (plan 04.3-06), which is not on this branch; this plan does not change that file.

## Decisions (for STATE)

1. **Share and read checks take the chat, not a scope.** `shareRefusal(chat)` and `canViewShared(chat, viewer)` resolve the cited lineages first. Only then is the scope resolved, per tenant key of the cited documents, through `resolveTenantScope` with the viewer as user and `resolveAccessScope` with `{ kind: 'user' }`. The viewer is a lazy callback, so the session is read only when a restricted document is cited. A personal tenant of another user or an organization the viewer is not in fails `scopeKey` equality or the membership check, so it is refused.
2. **The share route also refuses an already shared chat** that now cites restricted content, instead of handing out its existing link again.
3. **Lookup failures fail closed:** 503 `access_groups_unavailable` on share and on the document routes; the unknown-share answer on the read paths; each ingest route's own 503.
4. **Labels are read directly** (`documents.access_groups`) for the share refusal and the ingest checks, because these answer "labelled other than all" and "uploader" questions that `rag_documents_visible` does not answer. The shared-view visibility uses `visibleDocumentIds`.
5. **Audience view** is returned only for `admin_all`. Group names never reach a non-admin.
6. No migration, so no number was claimed. No store was added, so no purge hook is needed.

## Deviations

1. **Signatures.** The plan named `citedDocumentIds(messages, answerRecordIds)`, `shareRefusal(scope, ids)` and `canViewShared(scope, ids)`. The shipped forms are `citedDocumentIds(messages, answerCitations)` (pure), `loadCitedDocuments(chat)`, `shareRefusal(chat)` and `canViewShared(chat, viewer)`. The scope cannot be resolved before the cited documents' tenant is known, and the viewer must be resolved lazily (see decision 1).
2. **[Rule 3] `src/app/api/rag/ingest/_lib/handlers.ts` and the new `src/app/api/rag/ingest/_lib/access.ts`** are outside `files_modified`. `src/app/api/rag/ingest/[id]/route.ts` only delegates to `handleIngestStatus`, so the check lives in the handler; the shared helper also serves the job route. `[id]/route.ts` itself is unchanged.
3. **`documents/[id]` has no GET handler**, only PATCH and DELETE, so the hidden-id rule is applied to those two.
4. **Images `DELETE`** also answers a hidden id as unknown (the plan listed only the list read).
5. **Boundary self-test.** Four existing writer tests asserted full rule lists for fixtures that read `documents` / `document_chunks`. They now filter out the new rule with `writerRulesFor`; the new rule has its own cases.
6. **Scope of `content-table-read`** is `src/` and `scripts/` outside `src/lib/rag/`. `run-retrieval-access` is `src/` only, since no script calls `runRetrieval`.
