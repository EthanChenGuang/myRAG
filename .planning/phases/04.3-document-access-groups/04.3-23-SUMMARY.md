# Phase 04.3 Plan 23: upload labelling on every write path

**An uploader can now choose who sees a new document. The choice is checked on the server against the uploader's own groups (an admin: any group of the workspace) before anything is stored, and it is on the document, and so on every chunk, before the document can be retrieved: the unified pipeline sets it right after the version begins (long before publish), and the legacy writers put it in the same INSERT that makes the document visible.**

## The form field (for plans 45 and 46)

- Name: `access`. One field, optional.
- Value: JSON, exactly one of `{"everyone": true}` or `{"groupIds": ["<group uuid>", ...]}` (1 to 50 UUIDs, any case; no other property).
- Multipart routes (`POST /api/upload`, `POST /api/process-document`, both Config UI proxies) take it as a string field. `POST /api/ai-to-rag` takes it as an `access` property of the JSON body (an object, or the same JSON as a string).
- Absent (or an empty string): untouched. Nothing is looked up and the request behaves exactly as before; a new document is everyone, a new version keeps its lineage's label (D-19).
- Never send keys (`all`, `g:…`, `u:…`): they are refused.
- Answers before anything is stored:

| Status | Body | When |
|---|---|---|
| 400 | `{"error": "group_not_allowed"}` | a group the caller may not assign (not theirs, not in the workspace, or the switch is off) |
| 400 | `{"error": "invalid_access"}` | malformed field: not JSON, keys instead of ids, extra properties, empty or more than 50 groups |
| 503 | `{"error": "access_unavailable"}` | the caller's access could not be resolved (switch on and not ready, lookup failed) |

## Behaviour changes

- None without the field: every upload path builds the same input, makes the same calls and writes the same rows as before (`checkUploadAccess` returns at once for an absent field; the queued record, the job snapshot and the inserts gain nothing).
- With the field: the label is validated and stored whatever `RAG_DOC_ACCESS_GROUPS` says, but with the switch off only `{"everyone": true}` can pass (a group choice is `group_not_allowed`, plan 07 decision 7); nothing is enforced while off (D-09).
- A label the database refuses (unknown group, a user outside the tenant) fails the version in file_hash_dedup with that reason; it is never published.
- `setUploadAccess` (plan 21) now accepts a `null` uploader: the audit row then has no actor (a backfill batch has no uploader).
- The sidecar job snapshot contract gained `access_keys` (default null, left out of the wire when null). Deploy the sidecar before the app starts writing it (only `--access-groups` writes it).

## Decisions (for STATE)

1. **One field, JSON.** `access` carries `{"everyone": true}` or `{"groupIds": [...]}`; group ids only (D-06). Keys are built server-side by `uploadAccessKeys`.
2. **Label point in the unified pipeline:** right after `rag_begin_document_version` in file_hash_dedup, next to the scope tags and attributes, so chunks are written with it and publish is far away. The setter relabels the whole lineage, so an explicit choice on a new version applies lineage-wide (D-19); untouched leaves inheritance to the 0921 trigger.
3. **Fail closed:** a writer without `setUploadAccess`, or any setter failure, fails the run; the reason word (`unknown_group`, `unknown_user`, `empty_access`, `not_found`, `actor_required`, else `access_label_failed`) is the only thing logged.
4. **Switch off:** group choices are refused (`group_not_allowed`) because the uploader's groups are not resolved while off; the UI shows no picker then (UI-SPEC 6.2.3). `{"everyone": true}` passes.
5. **Malformed field** gets its own word, `invalid_access` (UI-SPEC 8.2 only lists `group_not_allowed`; a malformed field is a client bug, not a permission answer). Resolution failure is 503 `access_unavailable`.
6. **Queued uploads:** enqueue runs file_hash_dedup in the app, so the label is set at enqueue; the record keeps `accessKeys` so the progressive final begin applies it again (actor null) instead of relying on inheritance only.
7. **Backfill:** `--access-groups` resolves group keys of the batch tenant through `rag_access_group_by_key` (`accessKeysForGroupKeys`, inside `src/lib/rag/access/`); an unknown or malformed key exits 2 naming the key before any batch is created. The keys are frozen in each ingest job's settings snapshot (`access_keys`); the begin callback applies them with no actor. No flag leaves labels untouched (everyone for new documents, the lineage label for new versions). `--access-groups` with `--resume` is refused; a resumed batch takes the label of its existing ingest jobs.
8. **Legacy writers:** the label is a column of the inserting statement (never metadata, never chunk metadata; chunks get it from the copy trigger). Legacy documents have no lineage, so there is no inherited label to widen and no post-insert setter call is needed. `storeDocument` also accepts a connector's `u:<owner>` key as given (for plan 32) and refuses a malformed label before any insert.
9. **Legacy image upload** (`/api/upload` with the legacy pipeline): the field is checked (resolving the scope the same way as the unified path) and the label reaches `storeDocument` through `processImageDocument` metadata. With `process_rag` off the field is ignored (nothing is ingested).
10. **Purge hook or store inventory:** none needed; no store was added.
