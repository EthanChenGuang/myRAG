# Plan 03.3-23 summary: Phase 3.3 switches in the fixture build, and the tpl fixture runs

When a run config sets a Phase 3.3 switch to a value other than its default, the ingest fixture build now holds what a deployment holds
after its documented steps. The fixture user is made the tenant's admin. The attribute schema, section rule set, boilerplate rules,
header template and attribute values are then written through the product services and `runAttributesImport` (apply mode, staged),
before the first document is ingested with the switches on. A config that only restates the defaults layers nothing: database and corpus
hash are unchanged in both modes, and both all-off comparison runs pass. All 22 tpl runs ran. Three feature gates fail on the fixture,
because the v2 similarity floor refuses most ingest-mode items. That refusal already happens on the base commit (see Gates).

## What was built (Task 2)

- `phase33BuildEnv(runEnv)`: `RAG_SECTION_RULES`, `RAG_PAGE_BOILERPLATE`, `RAG_DOC_ATTRIBUTES`, `RAG_ATTRIBUTE_HEADER` and
  `RAG_LEXICAL_QUANTITY` are layered only when their trimmed, lower-cased value differs from the default. `RAG_IDENTIFIER_INDEX`
  is layered only with `RAG_DOC_ATTRIBUTES` (the identifier-feed branch).
  - `tpl-all-off` and `tpl-v2-off` give `{}`.
  - `tpl-recommended` gives the five switches.
  - `tpl-only-identifier-feed` gives `RAG_DOC_ATTRIBUTES` and `RAG_IDENTIFIER_INDEX`.
- `run-eval.mts`: in ingest mode the layered env is merged with any caller `ingestBuildEnv` and passed to the build. In prechunked
  mode, a rule-data switch logs one line, `[Eval Harness] phase33_seed_skipped_prechunked`.
- `buildIngestFixtureDatabase`:
  - The two switches the app reads from the process environment (`RAG_LEXICAL_QUANTITY`, `RAG_IDENTIFIER_INDEX`) are also set in the
    build's process env (`phase33ProcessEnv`).
  - `seedTemplatedTenant` runs after the ingest fakes are installed and the scope is minted, before the first document, next to
    `seedChunkingProfiles`.
  - The seed parts are appended to `ingestCorpusSha256`.
  - A seeding build refuses `continueFrom`.
- `seedTemplatedTenant`:
  - In single-tenant mode it inserts the fixture user into `auth.users`. In both modes it inserts one `admin_users` row.
  - It then calls `upsertAttributeDefinition` (×4), `saveSectionRuleSet` (×1), `saveBoilerplateRule` (×4) and
    `setHeaderTemplate`, and runs `runAttributesImport` in apply mode on a temporary JSONL copy of `attributes.json`.
  - Each part runs only when a switch needs it. Any failure throws with the step and the reason code.
  - It logs counts only (`[Eval Harness] phase33_seeded`). It compiles and runs no pattern, which a static test checks.
- `seedFixtureFeatures` (prechunked): `RAG_LEXICAL_QUANTITY` joins the lexical switches, so the 4.2 relex path rewrites the current
  chunks to version 6 and records `lexical_effective_version:6` in the inputs hash. Superseded chunks keep version 2, as
  `rag:relex` leaves them.

## Decisions (for STATE)

- The admin is made through an `admin_users` row in both modes. `rag_admin_tenant_keys` admits the personal key `u:<id>` only for an
  `admin_users` row, so the plan's "personal key in multi-tenant mode" needs that row too. Single-tenant mode also inserts the
  `auth.users` row it lacks. Only seeding builds do this.
- Seeding runs before every document (at the `seedChunkingProfiles` point), not only before the first templated one. The earlier
  product_technical typed fixture (images-en) is then judged against the bound rule set and flagged `section_rules_not_satisfied`, which
  is the behaviour the plan describes.
- `RAG_IDENTIFIER_INDEX` is a Phase 3.3 build switch only together with `RAG_DOC_ATTRIBUTES`; alone it stays a Phase 4.2 switch.
- The prechunked quantity rebuild reuses `seedFixtureFeatures` (the 4.2 relex path and its `lexical_effective_version` inputs entry);
  `LEXICAL_SHA_KEY` keeps recording the plain build's version.
- Variant label: section_path[0] of a variant chunk is the restart heading line carrying the designation. The test asserts that it
  contains the designation.
- Fragment: the effective cap is min(rule max_length, `config/rag/boilerplate-rules.json` fragment_max_length = 12). The en and it
  fragments are 14 characters and stay. Recorded in handoffs/03.3-23-fragment-cap.md; nothing changed.
