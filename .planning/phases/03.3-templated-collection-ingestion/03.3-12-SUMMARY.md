# Phase 3.3 Plan 12: Section rules in ingestion — Summary

**With `RAG_SECTION_RULES` effectively on and a rule set bound to the document's type or source, the tenant's heading patterns run in the same single worker call as the boilerplate line patterns. A conforming document is cut by `rule_sections`, in the chunk stage, in the ingest dual-write of live chunking profiles and in `rag:rechunk`. A document that does not conform is cut by the profile's chunker, flagged `section_rules_not_satisfied`, and still published. A resumed run replays the snapshot. With the switch off nothing changes.**

## How it works

- **Candidates and the worker call.** The request lines are the 03.3-10 boilerplate candidates in their old order, then any heading text not already present. A heading text is the trimmed line with Markdown heading marks removed, so `## Part 1` and `Part 1` share one input and both keys become hits. Fenced lines, `|` rows and texts over the 200-unit window are never candidates. Heading patterns come first in the request, then the line patterns. A hit counts only when `start === 0`, and the first heading pattern in rule-set order wins. A boilerplate hit on a heading-only input is ignored.
- **Protection (D-13).** Hit keys go to `cleanBoilerplate` as `protectedLines`. The replay and the parser-chunk text map pass the same list.
- **Conformance.** The check runs on the cleaned Markdown, on the `scanRuleSections` walk. The required check runs per variant when the file has variants, otherwise over the whole document. Number order is compared within one variant and one parent: deeper levels are cleared at each heading, and a heading without a leading number is not compared. The leading-number scanner is a regular-expression literal; nothing is built from tenant data.
- **Selection.** A satisfied document gets `{ ...baseChunker, kind: 'rule_sections', section_rules }`, which parses with the generated chunker schema. In every other case the function returns the `baseChunker` object itself:
  - Unsatisfied: `section_rules_not_satisfied`.
  - Worker timeout: `tenant_pattern_timeout` only. The rule set was not judged.
  - Worker error or failed load: warning `tenant_rules_unavailable`, no section flag (same choice as 03.3-10).
  - Hit map over the caps: warning `section_rules_snapshot_too_large`, no hits used, `section_rules_not_satisfied`.
- **Snapshot fields used.** `sectionRules.{ruleSetId, ruleSetVersion, toc, headingHits, satisfied}`.
  - Replay rebuilds the chunker from `headingHits` and recomputes the counts.
  - `section_rules_not_satisfied` is re-derived from `!satisfied`, unless the warnings hold `tenant_pattern_timeout` or `tenant_rules_unavailable`.
  - `snapshot.fingerprint` is the loader fingerprint whenever a rule set was consulted, including in detect mode.
  - With cleaning off there is no `boilerplate` part. The existing `chunk_prep.section_rules` fingerprint sub-part is filled from this snapshot.
- **Identity override (key link).** When the returned chunker is not the profile's object, the chunk stage sets `ctx.identity = { ...identity, profile: { ...identity.profile, chunker } }`. `dualWriteProfiles` then reads `identity.profile.chunker` and cuts the same way, with `embed-write.ts` unchanged. A resume re-runs the chunk stage in `rehydrateFromStore` from the snapshot, so the override is restored. Profile id and version, and therefore the fingerprint, are unchanged.
- **Stage guard.** The stage prepares when the cleaning mode is not off or section rules are on. It loads rules when the mode is `rules`/`both` or section rules are on. The deadline-yield check includes heading calls. A picture (`image_caption`) is never prepared; with cleaning off it records no snapshot.
- **Re-chunk.** `prepareMarkdown` returns the effective chunker, and `prepare` passes it to `buildProfileChunks` in place of `processing.chunker`. `PrepOutcome` now carries `report | null`, the review codes and the `sectionRules` report, and `buildDocument` stores them after the profile write. The dry run writes neither a flag nor metadata.
- **Notes for later plans.**
  - Rule-section chunks carry no page numbers (`page_start`/`page_end` null).
  - Fixed-mode parents never call the chunker registry, so they are unchanged. Rule sections apply to parent modes `none` and `structure`.
  - Parent-child children keep the variant label first in `section_path` and carry no variant keys in metadata (D-19, as 03.3-06 built). Ingest-time legacy chunks carry `variant_index` and `variant_label`.

## Deviations

- **The chunk-stage wiring landed in the Task 2 GREEN commit.** Its unit cases live in `prepare-chunk-input.test.ts`, as in 03.3-10, and Task 2's verify runs them.
- **Rule sets in the DB tests are inserted into `rag_section_rule_sets` directly, not written through the 1002 upsert function.** The 1002 writers admit `u:` keys only for deployment admins (0816), and the fixture's personal users are not admins. Edits bump `version` the same way the upsert does. The writers have their own tests in `tenant-rule-functions.test.mts`.
- **The timeout case uses no stub.** node:test cannot mock the ESM module without an experimental flag, so the case stores a pattern that passes the static re-check but backtracks (`^(?:x|xx)+y` against a run of `x`). The loader runs only the static re-check, and the worker deadline produces a real `timeout` verdict. Save-time probing would reject such a pattern; the case simulates one that was slow only on real text.
- **The single-tenant run is in its own file**, `tests/rag-db/section-rules-single-tenant.test.mts`, because a process holds one fixture database.
- **Two choices the plan left open.** A worker `error` verdict gives `tenant_rules_unavailable` and no section flag. The report also stores `satisfied`.

## Decisions for STATE

- Heading patterns are sent with ids `h:<index>` in the same worker request as the line patterns. Boilerplate candidates keep their 03.3-10 order and heading-only texts are appended, so the request with the switch off is unchanged.
- The per-document chunker is carried on a copy of `ctx.identity`. The dual-write and the fingerprint read the identity unchanged.
- A rule set that could not be judged (timeout or worker error) is never reported as `section_rules_not_satisfied`.
