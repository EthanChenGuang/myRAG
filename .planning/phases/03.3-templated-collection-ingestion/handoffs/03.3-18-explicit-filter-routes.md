# 03.3-18 hand-off: route-level 400 for an explicit attributes filter

Date: 2026-11-26. For: the coordinator; owners of `src/lib/rag/index.ts` (plans 03.3-14 and 03.3-15) and plan 03.3-19.

What exists after 03.3-18:
- `parseRetrievalFilters` accepts `retrievalFilters.attributes` only while `RAG_ATTRIBUTE_FILTER` is effectively on and checks its shape
  (key pattern, 30 keys, 50 values, 1..200 characters). It cannot check that a key is a filterable definition of the caller's tenant: that
  needs the tenant scope and a database read.
- `resolveAttributeFilter` (`src/lib/rag/retrieval/attributes.ts`) throws `AttributeFilterError` (`code: 'unknown_attribute'`, `status: 400`,
  `details: [{ path: 'attributes.<key>', message: 'unknown_attribute' }]`, or path `attributes` when the key cannot be named) when the SQL
  resolver refuses a key. The module is not exported from the barrel.

What a route-level 400 needs:
1. Export `AttributeFilterError` and `resolveAttributeFilter` (or a thin check built on it) from `src/lib/rag/index.ts` (plans 14 and 15 own
   the barrel).
2. One call beside `resolveScopesFilter` in the chat, embed and eval routes (`src/app/api/chat/route.ts`, `src/app/api/embed/chat/route.ts`,
   `src/app/api/internal/rag/run/route.ts`), answering `error.status` with `{ success: false, error: error.code, details: error.details }`,
   exactly as the scope filter does with `ScopeFilterError`.

Until then: plan 03.3-19's `attribute_resolve` stage must fail closed on `AttributeFilterError` (no widening: the request matches nothing or
is refused), never ignore the explicit filter.
