# 03.3-19 hand-off: the exact-id leg under a hard attribute filter (pitfall 7)

For: the coordinator. Date: 2026-11-26.

A hard attribute filter reaches the backend as a document-id filter (`filters.documentIds`, built by
`buildRetrievalFilters({ attributeDocumentIds })`). `hasNarrowingFilters` therefore reports the request as narrowed, and the
`exact_id_lookup` stage stands down for it (`rag_exact_id_documents` takes no filter arguments, so running it would widen the
search). The search stage decides on the filters it finally applied: after the one fallback round the exact-id leg sees the filters
without the automatic ids.

Effect: with `RAG_EXACT_ID_LOOKUP=true` and `RAG_ATTRIBUTE_FILTER=hard`, a query that names both an identifier and an attribute value
gets no exact-id list. `hasNarrowingFilters` and `rag_exact_id_documents` were left unchanged (owned by other phases).

Revisit when the identifier filter of migration 0856 (Phase 4.2) is on trunk: an identifier lookup that accepts `p_document_ids` could
run inside the attribute filter instead of standing down.
