# Phase 3.3 Plan 11: Attribute value writers Summary

A document's attribute values now arrive with it on every write path (upload, queue, backfill manifest, a new version of a known source
key, and a setter for existing documents), reach every chunk through a copy trigger without touching a chunk writer, and are refused,
never dropped, when they are wrong or the feature is off.

Triggers:
- `rag_chunks_x_document_attributes` — `BEFORE INSERT … FOR EACH ROW` on `public.document_chunks`, function of the same name (INVOKER):
  `NEW.attributes := (SELECT d.attributes FROM public.documents d WHERE d.id = NEW.document_id AND d.tenant_key = NEW.tenant_key)`.
  Sorts after `rag_chunks_legacy_defaults` (which sets `NEW.tenant_key`) and `rag_chunks_profile_status`.
- `rag_documents_x_attribute_insert_guard` — `BEFORE INSERT … FOR EACH ROW` on `public.documents`: sets `attributes`,
  `attribute_header`, `attribute_header_stamp` to NULL unless `current_user` is `service_role`, `postgres` or `supabase_admin`.
  Updates stay guarded by `rag_guard_phase33_columns` (1001). Chunks have no update policy for `authenticated`, so a direct chunk update
  changes no row.

Purge: no new store; staged rows go with the 1009 hook (plan 03.3-24).

## Behaviour changes

With `RAG_DOC_ATTRIBUTES` effectively off (default): no new function is called and requests without an `attributes` field behave as
before; a request or manifest row that carries `attributes` is now refused (`attributes_not_enabled`) instead of the field being unknown.
Every newly inserted chunk passes through the copy trigger (NULL while documents have no value), and a document row inserted by a
non-service role gets NULL in the three attribute columns.
