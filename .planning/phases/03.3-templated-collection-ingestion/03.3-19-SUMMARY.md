# Phase 3.3 Plan 19: Attribute filter in the v2 pipeline Summary

A question that names a value of a filterable attribute is now answered from the documents carrying that value (hard mode) or with those
documents ranked higher (soft mode). A hard filter that finds nothing falls back once, and the trace records it. With the switch off, or
on a request that names nothing, nothing changes.

## What was built

**Stage position.** `attribute_resolve` runs inside the terminology closure, right after `terminology` and before `semantic_cache` and
`embed`. It runs on the standalone query (the condensed query when the query layer is on, otherwise the request query). It does not run
after a small-talk short circuit. It uses the per-profile timeout of 03.3-02 (1000 ms, voice 500 ms).

**Stage record** (`attribute_resolve`):
- counts: `explicit_keys`, `matched_keys`, `alias_matches`, `ambiguous`, `explicit_ids`, `hard_ids`, `soft_ids`, `too_broad`,
  `lexicon_truncated`, `explicit_rejected`
- detail codes, joined with `;`: `attribute_filter_too_broad`, `attribute_lexicon_truncated`, `attribute_lexicon_unavailable`,
  `attribute_alias_unavailable`, `attribute_explicit_rejected`

**Filters.** `filters.documentIds` is the request's document ids ∩ the referenced ids ∩ the explicit ids ∩ the automatic hard ids
(hard mode), built by `buildRetrievalFilters({ attributeDocumentIds })`. In soft mode no automatic id is intersected, and the
hard-eligible ids join the soft ids. `AttributeSearchInput` is `{ mode, softIds, softWeight, fallbackFilters }`. `fallbackFilters` is
the same filters built with only the explicit ids, or null when no automatic id was intersected.

**Search stage** (`search` record):
- counts `attribute_filter_applied` and `attribute_filter_fallback` (only while a hard automatic filter applied), and `attribute_soft`
- detail codes `attribute_filter_fallback` and `attribute_soft_leg_failed` (the latter degrades the stage)
- list id `attr:0`, weight `soft_weight` from `config/rag/attribute-filter.json` (0.5)

The soft search runs the standalone variant's vector and tokens (no embed call), limited to the soft ids ∩ the round's document filter.

**Hash block** `attribute_filter` (only while the stage is enabled for the request): `{ mode, rules_version, soft_weight, id_cap, state }`.
`state` is the resolver's `stateDigest`, or one of these fixed words:
- `attribute:none`: nothing resolved
- `attribute:skipped`: skipped, or enabled but not reached
- `attribute_explicit_rejected`: an unknown explicit key

The semantic-cache key uses this hash. A test proves that the check-time hash equals `result.retrievalConfigHash`, and that
`computeCacheKeyHash` differs between two requests that resolve different filters.

**Trace** (eval route): `attribute_filter = { mode, explicit, matched_attributes, resolved_documents, applied, fallback, too_broad }`,
present only when the stage record is not disabled. `resolved_documents` is `explicit_ids` + `hard_ids` + `soft_ids` (in soft mode,
`explicit_ids` + `soft_ids`).

**Startup.** `RAG_ATTRIBUTE_FILTER=hard` with `RAG_EXACT_SCAN_CUTOFF=0` and `RAG_HNSW_ITERATIVE_SCAN=off` logs one `[RAG Config]` warning
per process. Nothing is added to `reasons`, and the status is unchanged.

## Behaviour changes

- The switch is off by default, and so are its prerequisites `RAG_DOC_ATTRIBUTES` and v2. In that state the only difference is a
  `disabled` `attribute_resolve` stage record. Filters, backend requests, candidates, order and `retrievalConfigHash` are unchanged
  (tested against a run without the variable).
- With the switch on and nothing named, the stage record and the hash block are new. Backend requests, candidates and order are
  unchanged.
- `AttributeResolution` gained `explicitCappedIds`. The 03.3-18 test literal was updated.
