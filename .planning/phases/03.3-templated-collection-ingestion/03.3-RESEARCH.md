## Summary

Most seams exist. The chunker registry is a plain map from kind to a pure function, and parent-child structure mode calls that map, so a new kind is picked up by it without editing `parent-child.ts`. The hidden-text sanitiser is a working precedent for changing the parse text between parse and chunk. Scope tags (DATA-18) are a complete analog for "tenant vocabulary → document column → chunk column → retrieval filter". `hybrid_search_chunks` already filters every leg by `p_document_ids`. The effective lexical version, the tenant-pattern table and the identifier columns of Phase 4.2 are on trunk. No new package is needed.

Reading the brief against the code found four things that do not work as written. (1) `rag:rechunk` never reads the parse cache: it reads the `parse.md` artifact of the document version, and with the default `RAG_INGEST_ASYNC=off` there is no parse-cache row at all (F-01). (2) The stored Markdown has no page boundaries, so "lines that repeat at the top or bottom of most pages" cannot be computed from it; per-page text exists only inside `docling.json`, and not for the fixed LlamaParse chain or native text (F-02). (3) The RET-16 filter of plan 04.2-09 tests the chunk column `identifiers_norm`, so attribute codes stored only at document level would not be filterable; the identifier feed must go through plan 04.2-18's indexer, which is not started (F-13). (4) `rag:reembed` only fills chunks that have no vector in a profile; it cannot refresh vectors whose embedding text changed, so a header-template change is a side-by-side `rechunk`, not a re-embed (F-14).

Three more findings shape the plan. Docling already drops what its layout model labels as page header or footer, on every Docling tier, so cleaning targets only the residue that was labelled as body text (F-03). Docling's own chunks bypass the Markdown chunkers for two chunker kinds, so cleaning the Markdown alone changes nothing for those documents (F-04). An attribute hard filter added as a new SQL parameter would be the third redefinition of `hybrid_search_chunks` in three phases, with an ordering hazard that can silently drop Phase 4.3's access filter; resolving attributes to document ids and passing them through the existing `p_document_ids` avoids the redefinition entirely (F-16).

**Primary recommendation:** implement cleaning and section rules as one pure, deterministic "prepare chunk input" step shared by the chunk stage and by `rag:rechunk`, leaving `parse.md` and the version content hash untouched; run every tenant pattern in the 04.2-14 worker before any synchronous chunker; store attributes on the document, copy them to chunks by trigger, and filter by resolved document ids; gate the identifier feed on 04.2-18, the matcher on 04.1.1-06 and the lexical wiring on 04.2-19, each with a stated fallback.

`prepareChunkInput(input) → { markdown, parseChunks, chunker, report }` with `input = { markdown, parseChunks, pageLines | null, baseChunker, tenantRules | snapshot, config, signal }`. Order: clean lines; apply the same removal to Docling chunks; resolve heading hits in the worker on the cleaned lines; check the rule set (allowed headings found, numbering order, restart markers, TOC runs); choose `{ ...baseChunker, kind: 'rule_sections', <rule data> }` or keep `baseChunker` and return `review: 'section_rules_not_satisfied'`. With both switches off the function is not called. Callers: `stages/chunk.ts` (then sets `ctx.work.parseText`, flags review, writes counts) and `rechunk/run.ts:prepare` (then `buildProfileChunks`).

### Pattern 2: line removal rules (B)

Never remove: lines inside a fenced block (`FENCE`), table rows (`line.trim().startsWith('|')`), ATX headings (`HEADING`), and any line that is an allowed heading of the bound rule set. Compare lines after NFKC, whitespace collapse and digit runs replaced by one placeholder. `detect`: a normalised line is boilerplate when it is among the first or last N lines of at least a share of pages and is shorter than a token limit. Fragment rule: very short normalised fragments that stand alone on a line and repeat on a share of pages. All numbers come from `config/rag/boilerplate-rules.json` with a `rules_version`; the cleaner has its own `CLEANER_VERSION` constant. Report: `{ cleaner_version, rules_version, lines_removed, tokens_removed, share }`; above the review share the document is flagged.

### Pattern 3: `rule_sections` chunker (A)

Input is Markdown plus resolved data. Walk lines; outside fences, a line whose trimmed text is in the hit data opens a section with the canonical name and level (Markdown headings that are not allowed are body text). A restart marker seen again starts variant `n + 1`; the variant label is the first path element. A TOC block is a run of at least K consecutive heading lines with no body line between them, and is skipped. Each section is packed with `chunkSection` or `chunkTableSection` under the profile's budget, so over-cap sections split exactly as other chunkers do. The conformance check (required headings present, numbers increasing within a variant) runs in the preparation step, not in the chunker.

### Pattern 4: attributes (C1)

Schema rows per tenant (key pattern, type, four flags, limits in SQL). Validation in TypeScript against the loaded schema with structured errors (`unknown_attribute`, `invalid_attribute_type`, `too_many_values`, `value_too_long`), repeated in SQL. Storage: `documents.attributes jsonb`, `document_chunks.attributes jsonb` with a GIN index, copy trigger on insert, setter for existing rows with `rag_cache_invalidate`. Sources of values, in precedence: explicit on the request, staged by source key, previous current version of the lineage. Import command mirrors `rag:backfill`'s argument parser and exit codes, dry run first.

### Pattern 5: attribute header (C2)

`header = renderTemplateHeader(tenantTemplate, attributeRow)` where `attributeRow` holds only attributes flagged in_header (lists joined with the language's `list_separator`); unknown placeholders are rejected when the template is saved (the renderer throws on them, and `templateHeaderFor` would silently return an empty header). The tenant template replaces the profile header for that tenant. The rendered line and a stamp (`template version` + short hash of the header attributes) are stored on the document; call sites read them. Lexical text gets the same line as an extra prefix part.

### Pattern 6: attribute filter (C3)

`attribute_resolve` stage: load the tenant's filterable values (cached per tenant key, short TTL, as the terminology loader does), match the standalone query, merge with the explicit `attributes` filter, call the resolver for document ids. `hard`: ids go into `filters.documentIds`; when the fused result is empty, rerun once without them and record `attribute_filter_fallback`. `soft`, and any attribute flagged soft: no filter, one `attr:0` fused list. Stage detail and counts carry numbers only. The request's resolved state enters the retrieval config hash as a block that exists only when the switch is on.

### Pattern 7: quantity tokens (D)

Grammar on normalised text: number (digits with optional grouping and one decimal separator) + optional whitespace + unit symbol from the registry list, with a non-letter boundary after the unit. Canonical number: remove grouping, decimal point, strip trailing zeros. When one separator is followed by exactly three digits the reading is ambiguous: emit both canonical forms. Token: `_q_<number><unit>`, unit lower-cased.

### Pattern 8: a switch in every location

### Anti-Patterns to Avoid

- **Rewriting `parse.md` with cleaned text:** correct for the security sanitiser, wrong here; it makes a rule change need a parser call on the inline path.
- **Compiling a tenant pattern inside a chunker, a stage or a route:** the probe is the attack (4.2 F-14).
- **A 14th ingest stage, or a new `StageName`:** breaks the pinned stage list and every resume table.
- **Redefining `hybrid_search_chunks`, `rag_write_chunks`, `rag_set_document_fields` or the functions that build `template_row`:** each is owned by several phases; use a trigger, a new function or a batched read.
- **Bumping `LEXICAL_VERSION`, `EMBEDDING_TEXT_VERSION`, `HASH_NORMALIZATION_VERSION`, a profile `version` or a `pack_version`:** breaks off-identity for every tenant.
- **Writing chunk identifier columns before 04.2-18 exists.**
- **Tenant values in logs, traces, stage details, `JobSettingsSnapshot` or fixture files.**
- **Fixture or example text taken from an example domain.**

## Common Pitfalls

1. **Cleaning that does nothing.** Docling chunks are used instead of the Markdown for two chunker kinds (F-04). Check: a fixture whose parse result carries chunks loses the boilerplate lines from its stored chunks.
2. **Resume changes the chunk count.** Tenant rules edited between two calls of one run give `write_incomplete`. Avoid with the state snapshot (F-06). Check: a test that edits the rule set between yield and resume.
3. **Line indexes after the table-header carry.** `carryTableHeaders` inserts rows. Key heading hits by text (F-07).
4. **Stored fingerprint parts stop parsing.** A required new field in `FingerprintSwitches` makes `IngestFingerprintPartsSchema.parse` throw for every stored document (F-22). New parts are optional and omitted.
5. **A header suffix read as row serialization** (F-15).
6. **Hard filter with an approximate index.** With the default cutoff 0 a selective filter starves the dense leg (F-16). Check in the two-tenant test with `RAG_EXACT_SCAN_CUTOFF` at 0 and above 0, and report dense counts.
7. **The exact-id leg stands down** when a hard filter narrows the search; a query that names both an attribute value and an identifier loses that leg today. Record it on the trace; revisit when 0856 lands.
8. **Attribute update without cache invalidation** leaves cached answers built under the old values (F-12).
9. **Every-row backfills fire every trigger** (4.2 Pitfall 8): the lexical trigger recomputes only when `lexical_text` changes, but vector-sync statement triggers fire on any chunk update. Batch the pushdown and state the outbox effect in the command output.
10. **Rule-section chunks have no pages** while Docling chunks do (F-09); citations that show a page lose it for those documents.
11. **`matches_empty` and anchors.** A heading pattern must be anchored and must not match the empty string; the validator rejects the latter but not a missing anchor. Reject unanchored heading patterns in the wrapper.
12. **Two baseline re-records in flight** (this phase and 04.2-37) produce conflicting `corpus_sha256` and baselines (F-26). One owner per merge train.
13. **Sidecar copy drift.** Editing `config/rag/language-packs.json` without the copy fails `rag-sidecar/tests/test_image_config.py`.
14. **Soft boost that edits scores** moves refusal behaviour (F-18).
15. **Unknown placeholder in a tenant template** renders an empty header silently through `templateHeaderFor`; validate at save time.
16. **`rule_sections` selected in a repository profile** would run with no rules; reject in `checkProfile`.
17. **Query cap.** Quantity tokens share the 16 additive slots with dictionary and stem tokens; order them deterministically and test a long query.

## Open Questions (with a recommended resolution)

1. **Page structure source for `detect`.** Known: only `docling.json` has it. Options: (a) TypeScript reads the needed fields of `docling.json` with a tolerant schema; (b) the sidecar derives page lines (new endpoint or artifact). Recommendation: (a), with a tolerant reader limited to `texts[].text`, `label`, `content_layer`, `prov[].page_no` and page count, pinned by a test on the recorded fixtures and by the docling-core version in `eval/fixtures/ingest/manifest.json` (`recorded_with`), because `rag:rechunk` must work without a running sidecar. Use reading order, not coordinates.
2. **Should document-level duplicate detection compare cleaned text?** Recommendation: no; keep the version hash on raw text. Two files that differ only in boilerplate stay distinct versions, and DATA-21 handles near-duplicates.
3. **What re-cuts legacy-profile chunks after a rule change?** Known: only a new version does; `reparse` needs `RAG_INGEST_ASYNC=on` and then uses the parse cache. Recommendation: document that templated collections should run a non-legacy chunking profile (`rag:rechunk`), and that the legacy profile changes through `rag:rebuild start` with mechanism `reparse`; do not build a new mechanism.
4. **Variant keys on profile chunks.** Recommendation: variant label in `section_path` in every path; add the two-line metadata pass-through in `chunkParentChild` only if a downstream plan needs `variant_index` as a number.
5. **Version bit for the quantity switch.** Recommendation: +4; confirm with the Phase 4.2 owner (A4).
6. **Unit words and unit synonyms.** TPL-07 requires spacing, separators, grouping and letter case. Recommendation: symbols only in this phase; unit words through the tenant's TERM dictionary once Phase 4.1.1 is on trunk; no per-language unit-word table in the repository.
7. **Rule-set binding key.** TPL-01 says "bound to a document type or a source". Recommendation: binding rows `(tenant, doc_type | null, source | null)` with precedence source and type, then type, then source; at most one active rule set per binding; the same binding table serves boilerplate rules.
8. **Config UI in this phase.** Recommendation: ship the six switch controls (required by `check-config`) under a UI-SPEC, and admin routes plus import commands for rule sets, boilerplate rules, attribute schema and header template. Panels for editing them are one optional, `autonomous: false` plan at the end, or a follow-up phase. A UI-SPEC from `/gsd-ui-phase 3.3` must exist before the switch plan runs.
9. **Tenant deletion.** No flow exists (F-24). Recommendation: ship the delete function and a hand-off; do not invent a tenant-deletion workflow here.
10. **Soft weight and id cap ownership.** Recommendation: `config/rag/attribute-filter.json` (numbers only, hand-editable, hashed when the switch is on), not `eval/config/retrieval-params.json`, which only its tool may write.

|---------------|---------|------------------|

| V3 Session management | no | — |

| Threat | STRIDE | Mitigation |
|--------|--------|------------|
| Catastrophic tenant pattern | Denial of service | Static checks, worker with deadline, match window, pattern and length limits, fallback and review flag on timeout |
| Cross-tenant read of rules, values, templates | Information disclosure | Tenant in every predicate, `rag_assert_tenant_key`, per-tenant caches keyed by tenant key, two-tenant tests in both modes |
| Attribute value probing through the filter or the trace | Information disclosure | Counts and flags only in traces; resolver listed for Phase 4.3's access predicate |
| Header template as an injection carrier | Tampering | The header goes only into embedding and lexical text, never into the text sent to the model (TPL-05); 200-character cap; placeholders validated |
| Cleaning rules that delete real content | Tampering / integrity | Protected line classes, per-document counts, review threshold, raw `parse.md` kept, switch-off restores |
| Manifest or import file with hostile keys | Tampering | Key pattern, type checks, limits, dry run first, all-or-nothing import |
| A caller sets pipeline-owned metadata | Spoofing | Extend `PIPELINE_KEYS` |
