<domain>
## Phase Boundary

A *templated collection* is a set of many near-identical documents that follow one layout and differ by a few attributes. Phase 3.3 adds four generic capabilities so a tenant can ingest and search such a collection well. Each part has its own switch, default off, and switching it off gives back today's behaviour byte for byte:

1. **Section rule sets (TPL-01, `RAG_SECTION_RULES=off|on`):** a chunker kind `rule_sections` driven by a tenant-supplied rule set: allowed heading patterns, a numbering-order check, restart markers that split one file into logical variants, table-of-contents skipping, and a `needs_review` flag with fallback to the profile's chunker when a document does not satisfy its rule set.
2. **Page boilerplate cleaning (TPL-02, `RAG_PAGE_BOILERPLATE=off|detect|rules|both`):** between parse and chunk, on the stored parse output: repeated page lines, tenant line patterns, fragment rules, per-document counts, `needs_review` above a threshold.
3. **Document attributes (TPL-03..TPL-06):**
   - storage and import (`RAG_DOC_ATTRIBUTES`): tenant attribute schema, `attributes` on upload and manifest rows, copy to chunks, `rag:attributes --import` by `source_key`, `code` values into the RET-15 identifier index;
   - header template (`RAG_ATTRIBUTE_HEADER`): a tenant header template rendered into embedding and lexical text;
   - query side (`RAG_ATTRIBUTE_FILTER=off|hard|soft`): explicit `attributes` filter, automatic resolution of a value named in the query, hard filter with fallback or soft boost, before `diversify`.
4. **Quantity tokens (TPL-07, `RAG_LEXICAL_QUANTITY`):** one extra normalised lexical token for number + unit; an addition to LANG-07.

Cross-cutting: safe storage and execution of tenant rule data (TPL-08) and a synthetic templated collection in the fixture corpus with an all-off zero-difference proof (TPL-09).

**Domain neutrality (owner rule, binding on every artifact of this phase):** every rule, pattern, heading name, attribute key, attribute value, unit word and template of a real collection is tenant data, supplied at ingestion or through admin routes and import commands, stored per tenant and kept outside the repository. No requirement, plan, default, prompt, rule file, test, fixture or Config UI text contains a word, name, code system, heading list or pattern of any example domain. Tests and fixtures use invented neutral vocabulary and are described by structure ("a heading that appears again", "an attribute flagged as a code").

Not in this phase: section-level deduplication (DATA-21, RET-13), stemming and the tokenizer dictionary (LANG-07), the synonym dictionary (TERM), anything in the legacy retrieval pipeline, Config UI editing panels for rule sets and attributes (deferred), a tenant-deletion workflow, a new parser option.

### One shared preparation step (B and A)
- **D-06:** Cleaning and section rules run in one async function, `prepareChunkInput`, called at the start of the existing `chunk` stage and by `rechunk/run.ts:prepare` before the synchronous chunkers. No 14th ingest stage and no new `StageName` (the stage list is pinned; resume re-runs `chunk`). With both switches effectively off the function is not called at all.
- **D-07:** "The cached parse result" of the brief is read as **the stored parse output of the document version** (`parse.md`, `chunks.json`, `docling.json`): `rag:rechunk` reads `parse.md`, not the parse cache, and the inline path writes no cache row (F-01). `parse.md` is never rewritten with cleaned text, so a rule change, a threshold change or switching off needs no parser call.
- **D-08:** The version content hash and document-level duplicate detection stay on the raw parse text (F-05). Inside the chunk stage `ctx.work.parseText` is set to the cleaned text so `enrich`, `extract` and `documents.content` see what was chunked; only per-chunk `content_hash` changes.
- **D-09:** Resume safety: the resolved rule data (rule ids and versions, a fingerprint, the heading hits, the removed-line keys) is snapshotted in `ctx.state` on first use, with a size cap, as the hidden-text state is. A resumed run re-chunks from the snapshot even when the tenant edited its rules in between.
- **D-10:** `needs_review` is written through a new function `rag_flag_document_review(p_document_id, p_tenant_key, p_reason)` with fixed reason codes `section_rules_not_satisfied`, `boilerplate_above_threshold`, `tenant_pattern_timeout`. The first reason stays in `needs_review_reason`; every code is appended to `metadata.review_reasons`. A flagged document is still published (today's rule). Per-document counts go to `documents.metadata` under pipeline-owned keys added to `PIPELINE_KEYS`.

### Tenant patterns (TPL-08)
- **D-11:** Every tenant-supplied pattern (heading, boilerplate line) passes the 04.2-14 static validator when saved and runs only through the 04.2-14 worker with a deadline. Phase 3.3 adds one thin module, `src/lib/rag/patterns/tenant-line-pattern.ts`: flags `u` or `iu`, at most 200 characters, a heading pattern must be anchored at the line start, the `no_alphanumeric` probe rule is not applied (a boilerplate pattern may match punctuation only), lines are passed as worker inputs truncated to a 200-character match window, one worker call per document for all patterns. A timeout flags the document (`tenant_pattern_timeout`), falls back to the unruled path and never blocks ingestion. No chunker, stage, route or SQL function compiles a tenant pattern.
- **D-12:** Limits, enforced in SQL and repeated in the services: 10 section rule sets and 40 boilerplate rules per tenant; 60 heading patterns per rule set; names 80 characters; 30 attribute definitions per tenant; attribute key `^[a-z][a-z0-9_]{0,39}$`; a value 200 characters; a list 50 values; header template 200 characters; an import file 50,000 rows. Refusals use fixed code words (`limit_reached`, `name_exists`, `not_found`, `unknown_attribute`, `invalid_attribute_type`, `too_many_values`, `value_too_long`, `unknown_placeholder`) and ERRCODE 22023 for malformed arguments.

### Page boilerplate cleaning (TPL-02)
- **D-13:** The cleaner is pure and deterministic, with its own `CLEANER_VERSION`; numeric thresholds (page share, top and bottom line window, maximum line tokens, fragment length and share, review share) live in `config/rag/boilerplate-rules.json` with a `rules_version`, numbers only. Lines are compared after NFKC, whitespace collapse and digit runs replaced by one placeholder. Never removed: lines in a fenced block, table rows, Markdown headings, and any line that is an allowed heading of the bound rule set. The report `{ cleaner_version, rules_version, lines_removed, tokens_removed, share }` is stored on the document; a share above the review threshold flags it (D-10). The fingerprint gains one optional part, present only while the switch is on.
- **D-14:** Page structure for `detect` comes from a tolerant TypeScript reader of the stored `docling.json` (`texts[].text`, `label`, `content_layer`, `prov[].page_no`, page count), using reading order (first and last N lines of a page), never coordinates (F-02, F-03; Open Question 1 option a). The reader yields line keys only; removed text is always deleted by matching in `parse.md` text, never copied from `docling.json`. The fixed LlamaParse chain persists the per-page texts it already holds as a new artifact at parse time (no parser option changes, so no cache key changes). Where no page structure is stored, `detect` is skipped with the warning `boilerplate_pages_unavailable` and only `rules` apply.
- **D-15:** Docling already drops what its layout model labels as page header or footer on every Docling tier, so `detect` targets the residue labelled as body text; fixtures model it that way. The same line filter is applied to Docling's own chunks (`text`, `contextualized_text`, `headings`, `table_header`), and chunks left empty are dropped, because two chunker kinds use those chunks instead of the Markdown (F-04). Shipped thresholds are fixture-fitted starting values; the live plan measures real residue before a tenant relies on them.
- **D-16:** Tenant boilerplate rules are rows of kind `line` (a pattern) or `fragment` (maximum length and minimum page share, no pattern), each with an optional binding (D-18).

### Section rule sets (TPL-01)
- **D-17:** Two steps. Async, in `prepareChunkInput`: run the heading patterns over the cleaned lines in the worker and produce plain hit data keyed by **trimmed line text** (`→ { name, level, restart }`), then check conformance (at least the required headings found, numbers increasing within a variant when the rule set asks for it). Sync: the pure `rule_sections` chunker reads only that data, carried on an optional field of the effective chunker settings (precedent: `profileFor` overriding `kind` for images). Keying by text keeps the data valid after the table-header carry shifts line numbers.
- **D-18:** A rule set, and a boilerplate rule, binds to `(doc_type | null, source | null)`; precedence source and type, then type, then source, then the tenant-wide row; at most one enabled rule set per binding.
- **D-19:** Only allowed headings open a section; a Markdown heading that is not allowed is body text. A restart marker seen again starts variant `n + 1`. The variant label is the **first element of `section_path`** (it survives parent-child, which drops chunk metadata, and reaches embedding and lexical text through the existing path prefix); ingest-time chunks also carry `variant_index` and `variant_label` in `metadata`. A table-of-contents block is a run of at least K consecutive allowed-heading lines with no body line between them (K from the rule set, default 3) and is skipped. Sections are packed with the existing section packers under the profile's budget, so parent-child structure mode (CHK-03, CHK-04) takes them unchanged. Rule-section chunks carry no page numbers (documented).
- **D-20:** A document that does not satisfy its rule set is chunked by the profile's chunker and flagged `section_rules_not_satisfied`. `rule_sections` is never in `DOCLING_KINDS`.
- **D-21:** What re-cuts existing documents after a rule or cleaning change: a non-legacy chunking profile through `rag:rechunk`, or `rag:rebuild` with mechanism `reparse` for the legacy profile. No new rebuild mechanism (Open Question 3).

### Document attributes (TPL-03, TPL-04)
- **D-22:** The schema is rows of `rag_attribute_definitions`: key, type `text | text_list | code`, flags `filterable`, `in_header`, `in_identifier_index`, `soft`. Values are validated in TypeScript against the loaded schema with structured errors and again in SQL; an unknown key or a wrong type rejects the request, nothing is dropped silently. Storage: `documents.attributes jsonb` and `document_chunks.attributes jsonb` with a GIN index; a `BEFORE INSERT` trigger on `document_chunks` copies the document's value (one primary-key lookup; it copies NULL while a tenant has no attributes); a setter modelled on `rag_set_document_scopes` updates existing chunks and calls `rag_cache_invalidate`. No chunk-writer redefinition (F-12).
- **D-22a:** With `RAG_DOC_ATTRIBUTES` effectively off, a request or manifest row that carries `attributes` is rejected with the structured error `attributes_not_enabled`; it is never silently ignored.
- **D-23:** Sources of values, in precedence: explicit on the request (`IngestInput.attributes`, beside `scopes`), staged by `(tenant_key, source, source_key)` in `rag_staged_attributes`, the previous current version of the lineage. The manifest contract gains optional `attributes`; `rag:backfill` stages them before enqueue. Tenant values never enter `JobSettingsSnapshot`, `documentMetadata`, logs, traces or stage details (counts and codes only).
- **D-24:** `npm run rag:attributes -- --tenant <key> --import <file>` (dry run first; all-or-nothing validation; exit codes like `rag:backfill`) sets attributes of ingested documents by `source_key` without parsing or re-chunking, stages rows whose document does not exist yet, batches the chunk pushdown and prints the vector-sync outbox effect. A second identical run is a no-op.
- **D-25:** Identifier feed: plan 03.3-16 extends the 04.2-18 indexer so the normalised values of attributes flagged `in_identifier_index` are merged into every chunk's identifier arrays and the document union, original spelling kept, and `rag:identifiers` keeps them. Needs `RAG_IDENTIFIER_INDEX`. Nothing is written to an identifier column outside that indexer.

### Attribute header template (TPL-05)
- **D-26:** One template per tenant (`rag_attribute_header_templates`), at most 200 characters, placeholders validated against the tenant's `in_header` attributes when saved (`unknown_placeholder`). It replaces the profile's header for that tenant and is rendered by `renderTemplateHeader` (lists joined with the language's list separator; a segment with a missing value is left out). The rendered line and a text stamp (template version plus a short hash of the header attributes) are stored on the document (`attribute_header`, `attribute_header_stamp`); every embedding-text and lexical-text call site gets the header from one batched read, and `ChunkLexicalInput` gains an optional header. The functions that build `template_row` are untouched (F-14). The header never enters the text sent to the LLM.
- **D-27 (stamp):** The chunk stamp is its own text column `document_chunks.attribute_header_stamp`, filled from a metadata key by a trigger like `lexical_dict_version`; `embedding_text_version` arithmetic is left alone (F-15). A header change is classified `rechunk`: `rag:reembed` cannot refresh a changed text (F-14), so the rebuild is a side-by-side chunking profile; a stale listing function names the documents whose stamp differs. Chunking profiles are per document type, not per tenant, so in multi-tenant mode the rebuild covers every tenant's documents of the affected types (cost noted for the owner; no per-tenant rebuild mechanism is built here).

### Attribute filter and boost (TPL-06)
- **D-28:** **No `hybrid_search_chunks` redefinition.** Attributes are resolved to document ids by a new function `rag_attribute_documents` and intersected into `filters.documentIds`, which every leg already honours (F-16). The Phase 4.3 access predicate keeps applying inside the search; the new resolver functions are listed in a hand-off so 4.3 adds its two parameters to them. — **Reversibility:** costly to change later only if the owner wants a chunk-column predicate; 1019 is reserved for that and would have to land after 0856 and the 4.3 block.
- **D-29:** A new optional v2 stage `attribute_resolve` sits where the terminology stage sits (after the query transforms, before `embed`): load the tenant's filterable values and aliases (per-tenant cache keyed by the tenant key, short time to live), match the standalone query with `buildMatcher`, map TERM aliases through `terminologyMatcherFor`, merge with the explicit `attributes` filter of DATA-08, resolve ids. `hard`: ids go into `filters.documentIds`; when the fused result is empty the search runs once more without them and the trace records `attribute_filter_fallback`. `soft`, and any attribute flagged `soft`: no filter; one extra fused list `attr:0` (the same query restricted to the matched documents) with a weight from `config/rag/attribute-filter.json` (numbers only). A boost never rewrites a score the refusal gate reads (F-18). Both act in the search stage, so they run before `diversify` wherever that lands.
- **D-30:** Above the id cap (start 2,000, in `attribute-filter.json`) the hard filter is not applied; the soft path runs and the trace records `attribute_filter_too_broad`. `RAG_ATTRIBUTE_FILTER=hard` with `RAG_EXACT_SCAN_CUTOFF=0` and `RAG_HNSW_ITERATIVE_SCAN=off` logs one startup warning (a selective filter can starve the approximate dense leg); the recommended configuration sets the cutoff above zero. The resolved state enters the retrieval config hash as a block that exists only while the switch is on. The explicit filter works without the matcher; automatic resolution needs it (D-01).

### Quantity tokens (TPL-07)
- **D-31:** A pure matcher on normalised text, run where the dictionary tokens run (before identifiers are split): number (digits, optional grouping, one decimal separator) + optional whitespace + unit symbol, with a non-letter boundary after the unit. Canonical number: grouping removed, decimal point, trailing zeros stripped; when one separator is followed by exactly three digits both readings are emitted. Token `_q_<number><unit>`, unit lower-cased, added after the natural tokens on the index side and in the leading additive group on the query side (shared cap of 16, deterministic order). Original tokens are kept.
- **D-32:** Unit symbols and separators are general, language-neutral data in an optional block of the language-pack registry (both copies edited, `pack_version` not bumped); tenant unit words come only from the TERM dictionary. The rewrite-gate lexicon's unit list is not reused; a hand-off notes the two lists.
- **D-33:** The switch is the third bit of the effective lexical version (+4, values 6 to 9). Plan 04.2-02 says "versions 6 and 7 stay reserved" without naming a purpose; this phase takes them for this bit and **asks the coordinator to confirm with the Phase 4.2 owner** (hand-off from plan 03.3-02; the plan stops if a 4.2 plan on trunk already uses the values). After turning the switch on: `rag:relex`, then `python -m rag_eval.calibrate refusal` (refusal cells are keyed by the tokenizer version).

### Admin surface, purge, eval
- **D-34:** Writers of tenant rule data are admin routes (`/api/rag/admin/section-rules`, `boilerplate-rules`, `attribute-schema`, `attribute-header`; `checkAdminOrOrgAdmin`, tenant key from admission only, 404 while the switch is off, no-store) and two commands (`rag:rules` to import or export rule sets and boilerplate rules from a JSON file kept outside the repository, `rag:attributes`). The Config UI gets the six switch controls only, under `03.3-UI-SPEC.md` (static markup beside the neighbouring switches, mechanism-only labels). Editing panels are deferred.
- **D-35:** Purge: new columns go with their rows; `rag_purge_hook_doc_attributes(p_tenant_key, p_lineage_id, p_document_ids)` nulls them and deletes staged rows of the purged documents' source keys. Per-document results stay in `documents.metadata`, so no new table references a document. `rag_tenant_rule_data_delete(p_tenant_key)` deletes one tenant's rows from every 3.3 table; nothing on trunk calls it yet (no tenant-deletion flow exists), which goes to the coordinator as a hand-off.
- **D-36:** Eval (TPL-09): ingest-mode fixtures in zh/en/it built from specs and recorded with `record_parse_results.py`: one templated family per language, one multi-variant file, pages with a repeated body-labelled line near top and bottom, a line labelled page footer (already excluded today), short repeated fragments, one quantity in several spellings. Category `templated_collection` with tags `feature:attribute_named`, `feature:variant`, `feature:quantity`, `feature:boilerplate`. Fixtures and items are added with every switch off, pre-existing items must show zero paired differences, then the baseline is re-recorded once. Runs: `tpl-all-off` (`gate`, `paired_all_zero`), `tpl-recommended` (cleaning `both`, rules on, attributes, header, filter `hard`, quantity on, exact-scan cutoff above 0), report-only single-switch runs. New metrics: boilerplate token share in indexed chunks, named-document Recall@k and wrong-document rate at rank 1, variant accuracy, quantity match rate across spellings, filter fallback rate. Gates are pre-registered in `eval/config/phase33-gates.json` before the recommended run.
- **D-37:** A two-tenant test in both deployment modes covers every new table, function, cache and stage; `tests/rag-e2e/defaults-equal-phase3.test.mts` is extended so that with every switch off no new table has a row and no new column a value.
- **D-38:** The last plan is live verification (`autonomous: false`): migrations and grants on a real project, residue measurement on a handful of real tenant files before thresholds are trusted, one tenant import with rule and attribute files kept outside the repository.
