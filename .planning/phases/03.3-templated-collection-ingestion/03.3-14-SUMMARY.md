# Phase 3.3 Plan 14: Tenant rule-data writers Summary

Admins can list, create, replace and delete their own workspace's section rule sets and boilerplate rules, and list, upsert and delete its
attribute definitions, through three switch-gated admin routes; operators can import and export a tenant's rules with `rag:rules`. Every
pattern passes the save-time check before it is stored, and nothing tenant-typed reaches an answer, a log or command output.

## Routes

All routes: `export const runtime = 'nodejs'`; every answer (errors included) has `Cache-Control: no-store`; while the route's switch is
effectively off the answer is 404 `{ success: false, error: 'Not found' }` before any session lookup or rpc. Guard: `admit(request)` reads
`?organizationId=` (the only workspace input), calls `checkAdminOrOrgAdmin`, and returns the admitted `{ actorUserId, tenantKey }`; the
denial answers come from `adminWorkspaceDenied` (401/403/503). Bodies are `.strict()`, so a tenant key, tenant id or actor field is 400
`Invalid request data`. Invalid JSON is 400 with details `[{ path: '', message: 'Body is not valid JSON' }]`.

| Route | Switch (effective, also needs `RAG_INGEST_PIPELINE=unified`) | Methods |
|---|---|---|
| `/api/rag/admin/section-rules` | `RAG_SECTION_RULES=on` (`sectionRulesEnabled`) | GET, POST, PUT, DELETE |
| `/api/rag/admin/boilerplate-rules` | `RAG_PAGE_BOILERPLATE` not `off` (`pageBoilerplateEnabled`) | GET, POST, PUT, DELETE |
| `/api/rag/admin/attribute-schema` | `RAG_DOC_ATTRIBUTES=true` (`docAttributesEnabled`) | GET, PUT, DELETE |

section-rules:
- GET → 200 `{ success: true, items: [{ id, name, doc_type|null, source|null, enabled, version, headings, require_increasing_numbers, skip_toc, toc_min_run, updated_at }] }` (creation order).
- POST `{ rule_set: SectionRuleSet }` → 201 `{ success: true, item }`. PUT `{ id: uuid, rule_set }` → 200 `{ success: true, item }` (version raised).
- DELETE `?id=<uuid>` → 200 `{ success: true, id }`. A non-uuid id → 400 with path `id`. A 61st heading → 400 `Invalid request data` (contract).
- Refused heading pattern → 400 `{ success: false, error: 'invalid_tenant_pattern', details: [{ path: 'rule_set.headings.<i>.pattern', message: <finding code> }, ...] }`, no upsert.

boilerplate-rules:
- GET → 200 `{ success: true, items: [{ id, name, kind, pattern|null, flags|null, max_length|null, min_page_share|null, doc_type|null, source|null, enabled, version, updated_at }] }`.
- POST `{ rule: BoilerplateRule }` → 201; PUT `{ id, rule }` → 200; DELETE `?id=` → 200 `{ success: true, id }`.
- The body schema adds the kind split to the contract: `line` needs `pattern` and `flags` and refuses `max_length`/`min_page_share`; `fragment` the reverse → 400 `Invalid request data`.
- Refused line pattern → 400 `invalid_tenant_pattern` with path `rule.pattern` per finding.

attribute-schema:
- GET → 200 `{ success: true, items: [{ key, type, filterable, in_header, in_identifier_index, soft, updated_at }] }` (key order).
- PUT `{ definition: AttributeDefinition }` → 200 `{ success: true, item }`; `in_identifier_index` on a non-code type → 400 `Invalid request data`.
- DELETE `?key=<key>` → 200 `{ success: true, key }`; a key outside `^[a-z][a-z0-9_]{0,39}$` → 400 with path `key`.

Failure mapping (`tenantDataFailure`): `invalid_tenant_pattern` 400 with details; `invalid_attribute_type` 400; `invalid_argument` 400
`Invalid request`; `limit_reached` 409 `{ error: 'limit_reached', limit }` (`limit` null for attribute definitions); `name_exists` and
`unknown_placeholder` 409; `not_found` 404 `{ error: 'not_found' }` (one body for unknown and foreign ids); `not_admin` 403 `Forbidden`;
anything else 503 `Tenant rule administration is unavailable`. Success logs: `[RAG Admin] <action>` with id, version or count only
(attribute definitions log the type only, never the key).

## Command (`npm run rag:rules`)

```
npm run rag:rules -- import --tenant <key> --actor <uuid> --file <path> [--dry-run | --apply]
npm run rag:rules -- export --tenant <key> --actor <uuid> --out <path>
```
Exit codes: 0 done, 1 failed, 2 report only, 3 file refused, 64 usage. Usage (64): missing subcommand or required flag, non-uuid actor,
`--dry-run` with `--apply`, `--apply`/`--dry-run`/`--file` on export, `--out` on import, a repeated flag, a flag without value, an unknown
option; also both switches off (`SWITCH_OFF_LINE`, before any tenant check, file read or rpc), a file list whose switch is off (names that
variable, before any database call), a refused tenant (`backfillScope`), an unreadable file, an export path inside the working directory or
already existing, and `not_admin` during apply (`actor refused`). An unavailable tenant check, a failed list read, a write failure midway
and an interrupt exit 1.

Import order: switches → read file (≤ `RULES_FILE_MAX_BYTES` 2 MB, JSON, `TenantRulesFileSchema`, unique names per list, line/fragment
split, source in `INGEST_SOURCES`) → per-list switch → tenant → every heading (`heading`) and line-rule pattern (`boilerplate_line`)
through `checkTenantLinePattern` → stored rows of each list whose switch is on → `planRulesImport` (projected limits `rule_sets` 10,
`boilerplate_rules` 40, `binding` two enabled rule sets on one `(doc_type, source)`) → report → writes with `--apply`.

Output lines (prefix `[RAG Rules]`; never a pattern, rule name or heading name):
- Refused file (exit 3): `  <path>: <code>` per issue (paths like `section_rule_sets[0].name`, `(file)` for file-level codes
  `file_too_large`, `invalid_json`), then `file refused: <n> issue(s); nothing was written`. Pattern refusal: `  section_rule_sets[i].headings[j]: <codes>` /
  `  boilerplate_rules[i]: <codes>` then `file refused: <n> pattern(s) failed the save-time check; nothing was written`. Limits:
  `file refused: limit_reached: <limit>; nothing was written`.
- Report: `section rule sets: create a, replace b, unchanged c, kept d` and `boilerplate rules: create a, replace b, unchanged c, kept d`;
  without `--apply`: `report only: nothing was written; run again with --apply to write` (exit 2).
- Apply: `write k of n: <list>[<index>] created|replaced`, then `done: n of n writes applied` or `nothing to write: every row is unchanged` (exit 0).
  Failure: `failed at write k of n: <word>; k-1 of n writes applied` and `applied writes stay applied; running the same file again completes the import` (exit 1).
- Export: `exported: section rule sets n, boilerplate rules m`, or `nothing to export: the tenant has no rules; no file was written` (exit 0).

TypeScript: `readRulesFile(path, { signal }) -> { ok: true; file } | { ok: false; issues: { path, code }[] }` (throws `RulesFileError` when unreadable);
`planRulesImport(file, { ruleSets, boilerplateRules }) -> { report, writes, limit }` (pure; writes rule sets first, disabled results before enabled);
`runRulesImport({ scope, actorUserId, file, apply, sectionRules, pageBoilerplate }, { signal, io }) -> { exitCode, status, report, writesApplied }`;
`runRulesExport({ scope, actorUserId, out, sectionRules, pageBoilerplate, cwd }, { signal, io }) -> { exitCode, ruleSets, boilerplateRules }`.
`cli.ts`: `parseRulesArgs`, `USAGE`, `SWITCH_OFF_LINE`, `main(argv, io, signal, overrides)` with overrides `resolveScope`, `enabled`, `cwd`.
Export writes `{ schema_version: 1, section_rule_sets?, boilerplate_rules? }` (only the lists whose switch is on), keys sorted, each list sorted by
name, pretty-printed, exclusive create with mode 0600; no id, version, tenant key, actor or timestamp.

## Deviations

1. **Field names follow the generated contracts**, not the plan prose: `headings` instead of `heading_patterns` (answer field and refusal path
   `rule_set.headings.<i>.pattern`), and file lists `section_rule_sets` instead of `rule_sets` (report path `section_rule_sets[i].headings[j]`).
2. **attribute-schema PUT body** is `{ definition }` (the plan names no wrapper).
3. **Single-tenant `organizationId`**: a uuid value is ignored (calls carry `s:default`), but a non-uuid value is 403 for a deployment admin,
   as in every `checkAdminOrOrgAdmin` route (scope-vocabulary included). The test uses a uuid.
4. **Extra file checks before any write**: unique names per list (`duplicate_name`), the line/fragment split (`required_for_kind`,
   `not_allowed_for_kind`) and a known ingest source (`invalid_source`), so the service cannot refuse a write midway for a reason the file
   check could have caught.
5. **Order of the import**: the file is read and checked against the per-list switches before the tenant check, so a list whose switch is
   off exits 64 before any database call; a refused file exits 3 with no rpc at all.
6. **Export sorts lists by name** (the import writes disabled rows first, so creation order would differ between tenants).
7. `limit_reached` for attribute definitions answers `limit: null` (the schema service carries no limit name).
