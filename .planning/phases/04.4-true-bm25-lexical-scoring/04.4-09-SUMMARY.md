# Phase 4.4 Plan 09: rag:lexstats CLI Summary

**`npm run rag:lexstats` lets an operator build, compact, check, inspect and remove a tenant's BM25 statistics, before or after `RAG_LEXICAL_SCORING=bm25` is turned on. It prints only tenant-key hashes and counts.**

## Upstream gate

04.4-01, 04.4-02 and 04.4-04 have SUMMARYs on this branch. 04.4-09 adds no migration and no SQL.

## Usage

```
usage: npm run rag:lexstats -- <enable|rebuild|compact|check|status|disable> [--tenant <key> | --all] [--repair] [--max-rows <n>] [--json]
```

- Exactly one of `--tenant <key>` or `--all` is required. The key must match `isTenantKey`.
- `disable --all` is refused.
- `--repair` goes only with `check`. `--max-rows` (1..50000, default 5000) goes only with `compact`.
- A flag given twice, an unknown option or an unknown sub-command is a usage error.
- The command loads `.env.local` and needs `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. It works whatever `RAG_LEXICAL_SCORING` says.
- It reads the effective scoring mode through `loadRagConfig`, which `check` uses. If the RAG configuration cannot be loaded, it prints one `[Lexical Stats]` warning and treats the mode as `ts_rank_cd`.

## Sub-commands (per tenant)

| Command | What it does | Fails (exit 1) when |
|---|---|---|
| `enable` | enable (its own call, committed), then rebuild unless the tenant was already `ready`, then check; if the check is not clean, one more rebuild and check (D-18) | still not clean |
| `rebuild` | rebuild, then check | tenant not enabled, or not clean |
| `compact` | `rag_lexstats_compact` in a loop until it returns 0 | — |
| `check` | `rag_lexstats_check`; with `--repair` it rebuilds a drifting tenant and checks again | drift (`clean` false), or under `bm25` a tenant that is not `ready` |
| `status` | `rag_lexstats_status` | — |
| `disable` | `rag_lexstats_disable` (`--tenant` only) | — |

Any failed call also exits 1. Under `--all` the loop goes on with the next tenant.

`--all` sources: `enable --all` pages the distinct `tenant_key` values of member chunks (`is_current`, status `ready` or `variant`). It takes one keyset step per key (`gt` on the last key, `limit 1`), so no new RPC is needed. Every other command pages `rag_lexical_stats_state`.

## Exit codes

- `0`: every tenant passed.
- `1`: drift, a not-ready tenant under bm25, a failed RPC, missing credentials, or a failed tenant listing.
- `2`: bad arguments. The usage line is printed to stderr.

## Output format

Text: one line per tenant on stdout:

```
<sha256(tenant_key)[0:12]> <building|ready|not_enabled> chunks=<n> lexemes=<n> pending=<n> [df_mismatch=<n> chunk_count_diff=<n> total_len_diff=<n> clean=<bool>] [rebuilds=<n>|folded=<n>|repaired=<bool>|removed=<bool>] [tenant=<key>]
```

- The check fields appear for `enable`, `rebuild` and `check`. They are the `_with_pending` figures, and `-` means null.
- `tenant=<key>` appears only when `--tenant` named the key.
- Under `--all`, one summary line goes to stderr: `[Lexical Stats] <command>: <n> tenant(s)[, with failures]`.
- `--json` prints the same fields as JSON lines: `tenant` (hash), `tenant_key` (only with `--tenant`), `command`, `state`, `chunks`, `lexemes`, `pending`, plus the extra fields. It prints no summary line.

Errors go to stderr as `[Lexical Stats] <hash> <rpc> failed (<code>)`. The error message, the client and the raw key are never printed, and no lexeme is ever printed (D-19, D-34, T-04.4-27, T-04.4-29).

## Deviations

1. **Own service-role client.** `main` builds the client with `createClient(url, serviceKey, { auth: { persistSession: false, autoRefreshToken: false } })` instead of `getSupabaseAdmin()`. Importing `@/lib/supabase` pulls in `env.ts`, which throws when `OPENAI_API_KEY` is missing. That would break the must-have "needs `NEXT_PUBLIC_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`".
2. **Idempotent enable.** For a tenant that is already `ready`, `enable` checks first and rebuilds only on drift. The plan's sequence would rebuild on every run, and the behaviour list asks that a second `enable --all` be a no-op.
3. **`--max-rows` restricted to `compact`.** The plan lists the flag globally but uses it only for compaction, so I gave it the same rule as `--repair`.
4. **`LexstatsDb` interface.** The existing `RpcClient` has `rpc` only, and its request needs `abortSignal`. The new narrow interface (`rpc` returning a thenable, plus `from().select().eq().in().gt().order().limit()`) fits both supabase-js and `tests/helpers/pglite-rest-client.ts`.
