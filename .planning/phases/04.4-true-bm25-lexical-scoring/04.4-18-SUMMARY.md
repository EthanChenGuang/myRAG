# Phase 4.4 Plan 18: cluster-DF measurement in the eval harness and pre-registered gate spec Summary

**The eval harness can now measure document frequency counted per duplicate cluster in both fixture modes. When a run turns RAG_DUP_CLUSTERS on, the ingest fixture mode clusters as the prechunked mode does and records `dup_clusters:eval_run` plus the clustered count. A bm25 run with effective DF mode `cluster` gets cluster statistics enabled, rebuilt after clustering and checked clean. Gate (c) measures overlap on the statistics the run serves. The live compare tools take `--df-mode raw,cluster`. The derived gate spec is committed and pushed before any cluster-mode run exists. No default changes.**

## Behaviour

- **Ingest clustering.** `seedIngestDupClusters` runs after the ingest build, for the fixture tenant and the q62 tenant (through `withQ62Tenant`). It acts only when the run's effective config has `dupClusters` on and no chunk of the tenant has a `dup_cluster_id`. It runs the same `runDupBackfill({ evalRun: true })` step as the prechunked mode. That step is extracted into `runFixtureDupClusters`, and `seedFixtureFeatures` calls it too. The step adds `dup_clusters:eval_run` and `dup_clusters:clustered:<n>` to `sql_sha256` (the run manifest). The prechunked inputs are unchanged (tested: no `dup_clusters:clustered:` key there). A run without the switch reads one config value and writes nothing. Tested on `v2-default` in ingest mode: 0 clustered chunks, no `dup_clusters:` or `lexical_stats:` input, empty ledger. The `off` runs have no base config and also lack the switch, so they take the same path.
- **Statistics.** `seedRunLexicalStats` passes `cluster: true` to `seedFixtureLexicalStats` when the effective DF mode is `cluster`. The tenant is then cluster-enabled before the rebuild, the check (both corpora) must be clean, and `cluster_status` must be `ready`. `RunLexicalStatsReport.dfMode` is new, and each tenant entry gains `cluster_units` and `cluster_ledger_rows` (numbers only, cluster runs only). Cluster runs add the input `lexical_stats:cluster`. In the ingest fixture the main tenant counts fewer units than chunks, and its ledger is non-empty.
- **Gate (c).** `fixtureOverlapAtK` (capped and uncapped calls) and `fixtureLexicalTies` (bm25 arm) send `p_df_mode: 'cluster'` only for a cluster run. The overlap file gains `df_mode: "cluster"` only then. Tests for a raw run: no `p_df_mode` argument, and the file has exactly the pre-plan keys in the same order. For a cluster run, the tests check that the uncapped top k equals a direct cluster-mode `rag_bm25_search_chunks` call, and that at least one question ranks differently from raw on the clustered fixture. `phase44_gate.OverlapReport` accepts `df_mode`. `cap_agreement_gate` reports an offender when the file's mode differs from `expected_df_mode(run config)`: cluster only with bm25, `RAG_DUP_CLUSTERS=true` and `RAG_LEXICAL_DF_MODE=cluster`.
- **Compare tools.** `lexical-leg-run.mts --df-mode raw,cluster` computes every mode before writing anything. It writes `<out>/raw` and `<out>/cluster`, each manifest carrying `df_mode`. A cluster run first requires `cluster_status` ready (`lexical_cluster_stats_not_ready` otherwise, never a silent raw fallback). The default `raw` still writes to `--out` with today's manifest. `rag_eval.lexical_compare --df-mode raw,cluster` adds `lexical_bm25_cluster` and `rrf_bm25_cluster` (with the grid suffix for k1/b grids). It pairs them against the ts_rank_cd arms and against the raw bm25 arms (cluster minus raw), and reads the per-mode leg directories. Cluster RRF arms need `RAG_LEXICAL_DF_MODE=cluster` and `RAG_DUP_CLUSTERS=true` in the traces, and raw arms need DF mode raw. `--df-mode cluster` alone is refused. The default report is byte-identical: the sha256 of the JSON and Markdown report from the committed test arms is pinned, computed with the module before this plan.
- **Derived spec (D-50).** It differs from `phase44-comparison.json` only in the `base` of the three bm25 runs (the cluster-DF run config), the `env` of the three v2 reference runs (`RAG_DUP_CLUSTERS=true` added), and two appended notes. The test checks that every other key is equal, including `no_slice_drop_rule` v2. It also checks that both specs pass `Phase44GateSpec` and `_check_scoring`, and that each pair differs only in `RAG_LEXICAL_SCORING` and `RAG_LEXICAL_DF_MODE`. No cluster-mode gate result or harness output exists (`eval/reports/phase-04.4-cluster-df/` absent).

## Ingest-mode runs that already set RAG_DUP_CLUSTERS=true

None of the gated specs has one. `phase42-gates.json` pins the switch to false in ingest, and the diversity run configs are prechunked. The only committed ingest result with the switch is the report-only quick-44 diagnostic (`eval/reports/phase-04.4/diagnostics/dup-diagnostic.json`). Its README names this exact limitation ("in ingest mode the harness builds no duplicate clusters"). Committed reports are not re-run or re-judged. So the step was not restricted to cluster-DF runs: restricting it would give the ingest bm25 arm clusters that its reference lacks.
