# 04.4-07 hand-off to Phase 6.3: lexical statistics in the purge

`public.rag_purge_store_inventory()` (Phase 6.3, migration 0728) was not on trunk when 04.4-07 ran (branch b), so migration 0903 adds no inventory row. When Phase 6.3 creates or redefines the inventory, list these four relations:

| relation | store_id | handling | reason |
|---|---|---|---|
| `rag_lexical_stats_pending` | `lexical_stats` | `hook` | staged signed deltas, folded by `rag_purge_hook_lexical_stats` |
| `rag_lexical_df` | `lexical_stats` | `hook` | per-tenant document frequencies, no document id |
| `rag_lexical_corpus` | `lexical_stats` | `hook` | per-tenant chunk count and length, no document id |
| `rag_lexical_stats_state` | `lexical_stats` | `exempt` | tenant settings, no document reference |

Hook: `public.rag_purge_hook_lexical_stats(p_tenant_key text, p_lineage_id uuid, p_document_ids uuid[]) RETURNS bigint` (0903), service_role only. The counts key is `lexical_stats`; the return value is the number of pending rows folded.

## Call-order rule

The counters hold no document id. The purged versions' contribution is removed by folding the -1 rows that the 0901 delete trigger stages when their chunks are deleted. Phase 6.3 calls the hooks before the chunk delete, and at that point nothing of the purge is staged yet. Therefore:

1. Call `rag_purge_hook_lexical_stats` again after the chunk delete, in the same purge run (the first call is harmless: it folds only what is already staged).
2. `rag_purge_verify` must require `pending = 0` from `public.rag_lexstats_status(p_tenant_key)` for the tenant (and may require `clean` from `rag_lexstats_check` when the tenant's state is not null).

`tests/rag-db/lexical-stats-purge-hook.test.mts` ("Phase 6.3 order ...") shows both intermediate states: after the first call alone `pending = 0`, after the delete alone the removals are staged, and the second call folds them.
