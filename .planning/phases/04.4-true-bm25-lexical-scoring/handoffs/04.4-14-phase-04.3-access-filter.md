# 04.4-14 hand-off to Phase 4.3: access filter on the BM25 lexical leg

## What Phase 4.3 must do

`public.rag_bm25_search_chunks` (0904, Phase 4.4) is a sibling of `public.hybrid_search_chunks`: under `RAG_LEXICAL_SCORING=bm25` it serves the lexical leg instead of the `ts_rank_cd` leg, so it must apply every filter `hybrid_search_chunks` applies. When Phase 4.3 gives `hybrid_search_chunks` `p_access_keys text[]` and `p_access_all boolean` with the access-group predicate, `rag_bm25_search_chunks` needs the same parameters (same names, types and defaults) and the same predicate, inside the candidate pass, before its `ORDER BY` and `LIMIT`.

Owner of the access migration: plan **04.3-10** (`0930_access_retrieval_functions.sql` and its mode files, 04.3-PLAN-INDEX.md).

Both orders:

- **4.3 after 4.4** (0904 on trunk when 0930's executor runs): the 0930 executor, or a gap file of the 0920 block, adds the access parameters and predicate to `rag_bm25_search_chunks` with a `CREATE OR REPLACE` from its newest body.
- **4.4 after 4.3**: plan 04.4-05 would have carried the predicate into 0904 directly.

Status at the time of writing (2026-11-27): 0904 landed first, and the merge train `ci/merge-train-35` added **`0932_access_bm25_search.sql`**, which redefines `rag_bm25_search_chunks` from the 0904 body with `p_access_keys` / `p_access_all` (defaults NULL and false) and the 0930 predicate. So the first order applies, through 0932 rather than inside 0930. This branch (exec/04.4-14) does not contain 0932; it arrives when the trains merge.

## TypeScript caller

`src/lib/rag/backend/pgvector.ts`: the BM25 call takes `bm25ArgsFrom(buildRpcArgs(...))`, i.e. every `hybrid_search_chunks` argument except `p_dense_limit`, `p_iterative_scan` and `p_exact_scan_cutoff`, plus `p_k1`, `p_b` and `p_candidate_limit`. Phase 4.3 adds `...accessRpcArgs(req.access)` to `buildRpcArgs`, so the BM25 call passes the access arguments the same way the dense call does. Do not build the BM25 arguments separately, and do not strip the access keys in `bm25ArgsFrom`.

## Enforcing tests

- `tests/rag-db/bm25-filter-parity.test.mts`: catalog parity of `proargnames`, types and defaults between the two functions, and matched-set parity per filter. It fails until the parameter lists agree.
- The pgvector backend test that checks "a filter argument added to `buildRpcArgs` reaches the BM25 call" (plan 04.4-08, `tests/rag/backend/pgvector-bm25.test.ts`).
- Phase 4.3's same-tenant access canaries must include a run with `RAG_LEXICAL_SCORING=bm25` and ready statistics.

## If it is not done

Under `bm25` the lexical leg would return chunks the caller's access groups do not cover: a document-level leak inside a tenant. The parity test fails the merge first.

## Re-apply rule

After re-running 0904, re-run 0932 (and any later redefinition).
