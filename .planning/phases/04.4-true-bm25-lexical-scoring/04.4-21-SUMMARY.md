## What changed

**Read function** `rag_lexical_rerank_stats(p_tenant_key text, p_terms text[], p_chunk_ids uuid[])`.
- Function properties:
  - SECURITY INVOKER with an empty `search_path`.
  - `rag_assert_tenant_key` checks the tenant key.
  - Revoked from PUBLIC, anon and authenticated; granted to service_role.
  - Not in 0410, which holds definer functions only.
- What it returns: for each asked chunk of the caller's tenant, that chunk's own chunking profile and language (`'und'` when null), plus the compacted chunk count, total length and df of the asked terms for that bucket.
- What it never returns:
  - A row for a chunk id of another tenant or an unknown id.
  - A lexeme list.
- Reads and errors:
  - It reads the compacted counters only. Staged deltas are not folded in, the same as `rag_bm25_search_chunks`.
  - Term forms are filtered exactly as in that function.
  - Limits: 64 terms and 500 chunks (22023 beyond).
  - A tenant without ready statistics raises `lexical_stats_not_ready` (55000).

**Reranker** (`src/lib/rag/rerank/local-bm25.ts`). The module has no Supabase import; the provider is injected.
- Without a provider, scoring is today's `bm25Scores`, byte for byte, and returns `{ scores }` only.
- With a provider, `bm25ScoresWithStats` uses each candidate's tenant statistics: N, avgdl, and df clamped to [1, N] (D-20).
  - It keeps the same K1 = 1.2, B = 0.75 and idf formula as the pool path.
  - The raw score of a (query, chunk) pair depends on no other candidate; the pool maximum only normalizes.
  - It reports `localStats: 'tenant'` and model `bm25-v3-tenant`.
- Any of these makes the pool serve the whole request (`localStats: 'pool'`, model `bm25-v2`):
  - a read that fails, throws or answers null;
  - a candidate without statistics;
  - a bucket with no chunk;
  - an unservable term form.
- An aborted read rejects, so a stage timeout keeps RNK-06 behaviour.

**Provider** (`src/lib/rag/rerank/local-stats.ts`).
- One read per rerank call, on the admin client, with `scopeKey(input.scope)` as the only tenant input.
- It reuses the 04.4-08 readiness cache (`lexstatsReady`), so a tenant known not to be ready costs no read. A `lexical_stats_not_ready` answer drops the cached readiness.
- Logs: one `[Document Search]` warning with a tenant-key hash and the code `rerank_stats_unavailable`, never terms or text.

**Rank stage** (`runRerankStage`).
- It builds the provider only when `config.v2.rerankLocalStats === 'tenant'` and the reranker is `local_bm25`.
- The stage detail gets `;rerank_stats_tenant` or `;rerank_stats_unavailable` in tenant mode only.
- The served model goes to the stage output, the trace detail and the refusal-gate descriptor: `bm25-v3-tenant` only when tenant statistics served.

**Compaction** (`afterLexicalWrite`). It runs while bm25 scoring is effective or while tenant mode is effective. In pool mode with `ts_rank_cd` there is no new call. `afterDupClusterWrite` keeps its own bm25 + cluster condition.

## Token-form precondition (Task 1)

Every term `lexicalTokens(rerankText(...))` produces is a lexeme the statistics count, in the same form. This holds on neutral zh, en and it samples with and without section paths, computed against `rag_lexical_tsvector(chunkLexicalText(...))` in PGlite. For plain chunks the two sets are equal.

One difference is **scope, not form**. For a legacy-prefixed chunk (`Document: … Content:`), `chunkLexicalText` keeps the title as a path part, and `rerankText` strips it. So the statistics count the title lexemes, which the reranker never sees. The same holds by design for image extras, table-row serialization and the attribute header, which lexical_text adds. A test pins this difference.

I did not treat this as `rerank_token_form_mismatch`, for two reasons:
- The reranker's terms are counted under the same form, which is what df lookups need.
- The stop condition guards forms, and the order-independence property (D-56) does not depend on it.

The only effect is that a query term occurring only in such a title adds to df. That is the same corpus definition the BM25 lexical leg uses.

## Deviations

1. **The read is by chunk id, not by (doc type, language)** (2f3fe445e).
   - The first contract resolved each doc type's effective profile in SQL, as `rag_bm25_search_chunks` does.
   - The two-tenant matrix exposed a problem: a chunk served by the legacy fallback under a non-legacy active profile has no statistics in the effective profile. Tenant mode would then fall back throughout a profile transition.
   - Reading by chunk id uses the candidate's own profile and language, which is D-55's wording: "for the candidate's chunking profile and language".
   - It also drops the chunking-override plumbing.
   - Tenant isolation is still enforced in SQL: a foreign chunk id gives no row, so the pool serves (tested in both modes and in the matrix).
2. **The config hash keeps the configured reranker descriptor.** The plan-check revision asked that the config hash see `bm25-v3-tenant` only when tenant statistics served. But the hash is computed before retrieval as the semantic-cache key (`pipeline.ts`) and again in the result. The code requires the two never to disagree, and the cache key cannot know the outcome. So both hashes keep `bm25-v2` (from `describeReranker`), and tenant mode is separated by 04.4-20's `rerank_local_stats: tenant` block. The trace detail, the stage output and the refusal-gate descriptor carry the served model.
3. **Refusal cells.** `local_bm25` scores are `relative`, so the gate never applies a cell to it (`relative_scores`), in any mode, before or after this plan. No `local_bm25` cell exists in `eval/config/refusal-thresholds.json`. Details in the hand-off.
4. **Token-form precondition:** a form check plus a pinned scope difference (above), not a stop.
5. **Files outside `files_modified`:**
   - `src/lib/rag/rerank/select.ts` is not edited, because the model id is resolved in the rank stage.
   - `src/lib/rag/v2/pipeline.ts` was edited and then restored to its base body.

## Deferred

- **Classic BM25 idf can be negative** (`log((N - df + 0.5)/(df + 0.5))` when df > N/2). In tiny buckets, as in the two-tenant fixture, all scores can then be ≤ 0 and normalize to 0. Pool mode has the same formula. The 04.4-22 comparison should report how often a tenant-mode rerank returns all zeros. A `log(1 + …)` idf, as the SQL search uses, would be its own owner decision.
- **The rerank pool is capped at 500 chunk ids in SQL**; today's pool is 75.
