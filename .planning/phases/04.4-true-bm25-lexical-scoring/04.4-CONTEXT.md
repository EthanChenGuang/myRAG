## Phase Boundary

Today the lexical leg of `hybrid_search_chunks` (newest body: `supabase/migrations/0856_hybrid_search_42.sql`) ranks GIN matches with `ts_rank_cd(c.lexical_tsv, q, 1)`. Postgres ranking functions use no global information, so the leg has no inverse document frequency and no BM25 length normalisation. Phase 4 deferred "a true BM25 scorer in SQL" until an eval showed the lexical ranking limiting recall. The owner now has that evidence: on a real eval set (about 31k chunks, 407 answerable questions) an offline BM25 lexical leg fused by RRF with the dense leg gave doc@1 +4.7 points and Recall@50 +3.2 points over the dense leg alone.

This phase delivers:

- a switch `RAG_LEXICAL_SCORING=ts_rank_cd|bm25` (default `ts_rank_cd`) with `RAG_LEXICAL_BM25_K1` and `RAG_LEXICAL_BM25_B`;
- per-tenant corpus statistics (document frequency per lexeme, chunk count, total lexical length), kept by staged deltas and compaction, with a rebuild, a drift check and a purge hook;
- a BM25 search function for the lexical leg that reuses the GIN index, bounds the candidate set and scores candidates in SQL;
- the backend wiring, the fallback when a tenant has no ready statistics, and the trace fields;
- the eval proof on the fixture and the tool plus the human step for the comparison on the owner's real eval set.

It does not change the dense leg, RRF, rerank, refusal, the tokenizer, `lexical_text`, `lexical_tsv` or its GIN index, and it does not redefine `hybrid_search_chunks`.

### Switch and parameters (LEX-01)

- **D-05: Three variables.** `RAG_LEXICAL_SCORING` (`ts_rank_cd` | `bm25`, default `ts_rank_cd`), `RAG_LEXICAL_BM25_K1` (default `1.2`, accepted 0.5 to 3), `RAG_LEXICAL_BM25_B` (default `0.75`, accepted 0 to 1). An invalid value falls back to the default with one `[RAG Config]` warning. `bm25` is effective only with `RAG_PIPELINE=v2` and `RAG_LEXICAL_SEARCH=true`; otherwise it is ignored with one warning.
- **D-06: Why k1 = 1.2 and b = 0.75.** They are the Lucene, Elasticsearch and Weaviate defaults and the values Phase 7 already pins for Weaviate (`07-RESEARCH.md`: `bm25: { k1: 1.2, b: 0.75 }`), so all three backends start from one pair. The owner's offline run used k1 = 1.5; the live step (04.4-15) measures a grid (k1 0.9, 1.2, 1.5; b 0.5, 0.75) and a different default needs that evidence.
- **D-07: Classification.** All three are query-side in `config/rag/settings-classification.json`. Statistics are derived from `lexical_tsv`; changing the switch or the parameters re-ingests nothing and does not change `ingest_fingerprint`.
- **D-08: Config hash.** A `lexicalScoring` block `{ mode, k1, b }` enters the config hash only when the effective mode is `bm25` (the 04.2-06 "block only when on" rule), so committed baselines keep their hashes.
- **D-09: No candidate-cap variable.** The candidate cap is a code constant (`BM25_CANDIDATE_FACTOR = 5`, `BM25_CANDIDATE_MIN = 500`, SQL bound 2000) passed as `p_candidate_limit`. It becomes an env variable only if the live step shows a deployment needs to tune it.

### Corpus statistics (LEX-02)

- **D-10: Key.** `(tenant_key, corpus, lexeme, chunking_profile_id, language)` for document frequency and `(tenant_key, corpus, chunking_profile_id, language)` for chunk count and total length. `corpus` is `'chunks'` in this phase; the column exists so translations can be added later without a schema change (D-21).
- **D-11: Membership.** A chunk counts when `is_current AND status IN ('ready','variant') AND lexical_tsv IS NOT NULL AND lexical_tsv <> ''`. This is the row filter of the default lexical leg. Quarantined, pending-review, failed and superseded versions therefore never count, and a flip of `is_current` or `status` moves the chunk in or out through the update trigger.
- **D-12: Per tenant only.** Every read and write names the tenant key. IDF across tenants would leak that another tenant's vocabulary exists and would let one tenant's uploads move another tenant's ranking. The functions take `p_tenant_key` from the verified `TenantScope` (`scopeKey`) and call `rag_assert_tenant_key` first, as `hybrid_search_chunks` does.
- **D-13: Request statistics.** For a request, `N`, total length and `df` are summed over the effective chunking profile of each requested doc type (the same rule `hybrid_search_chunks` uses to build its effective-profile set) and over the requested lexical languages plus `'und'` (all languages when the request names none). Chunks served through the legacy-fallback clauses of the filter and superseded chunks under version scope `all` or `range` are scored with these statistics although they are not counted in them: counting superseded near-copies would double the document frequency of exactly the terms that tell versions apart.
- **D-14: Filter parity guard.** Two tests: (a) signature parity: every parameter name of `hybrid_search_chunks` except `p_dense_limit`, `p_iterative_scan` and `p_exact_scan_cutoff` exists on `rag_bm25_search_chunks` (read from `pg_proc`), so a later phase that adds a filter parameter to one function fails CI until the other has it; (b) matched-set parity: for every filter case of the existing hybrid filter tests, with limits above the match count, the set of chunk ids from the BM25 function equals the set from the `ts_rank_cd` leg.

### Maintenance (LEX-03)

- **D-15: Staged deltas, not counters on the write path.** Statement-level `AFTER INSERT`, `AFTER UPDATE` and `AFTER DELETE` triggers on `document_chunks` with transition tables (the 0702 pattern) append one row per changed member chunk to `rag_lexical_stats_pending`: tenant key, chunking profile, language, sign (+1 or -1), the chunk's distinct lexemes (`tsvector_to_array`) and its length. An update writes a -1 for the old state and a +1 for the new one only when membership, the vector, the tenant key, the profile or the language changed. No per-lexeme row is locked by a writer, so bulk ingest cannot contend on common lexemes.
- **D-16: Inert by default.** The trigger functions return immediately while `rag_lexical_stats_state` has no row, and write only for tenants that have one. The default deployment and every tenant that never enabled statistics get no row.
- **D-17: Compaction.** `rag_lexstats_compact(p_tenant_key, p_max_rows)` takes `pg_advisory_xact_lock` on the tenant, removes up to `p_max_rows` pending rows in id order, adds their signed counts to the counters with one `INSERT ... ON CONFLICT DO UPDATE` ordered by key, and deletes counters that reached zero. `rag_lexstats_compact_all(p_max_rows)` loops over tenants with pending rows. Callers: the publish stage and the relex run when scoring is `bm25` (best effort, never failing the write), the CLI, and the optional pg_cron file `supabase/optional/lexical-stats-schedule.sql`.
- **D-18: Rebuild and enable.** `rag_lexstats_enable(p_tenant_key)` inserts the state row with status `building` and must be committed before `rag_lexstats_rebuild(p_tenant_key)` is called. The rebuild takes the same advisory lock and, in one statement (one snapshot), deletes the tenant's pending rows and scans its member chunks into a staging temp table; a second statement replaces the tenant's counters and sets the state `ready`. A change committed before the snapshot is in the scan and its pending row is deleted; a change committed after it keeps its pending row. The remaining race (a write statement that started before the enable was visible and committed after the snapshot) is detected by the drift check; the CLI runs enable, rebuild, check and repeats the rebuild once when the check is not clean.
- **D-19: Drift check.** `rag_lexstats_check(p_tenant_key)` compares counters plus pending deltas with a recompute from `document_chunks` and returns the number of differing lexeme rows, the chunk-count and length differences and the pending backlog. `npm run rag:lexstats -- check [--tenant <key>] [--repair]` prints counts only and exits 1 on drift; `--repair` rebuilds.
- **D-20: Staleness is tolerated, never folded at query time.** Queries read the compacted counters only. IDF changes slowly, so a backlog of minutes changes rankings marginally; `status` reports the backlog size and the age of the oldest pending row. A lexeme with no counter (new term not yet compacted) is scored with `df = 1`; `df` is clamped to `[1, N]`.
- **D-21: Translations deferred inside the design.** `hybrid_search_translations` keeps `ts_rank_cd`. Reasons: no evidence on that leg yet; RRF fuses ranks, so lists scored differently fuse correctly; a translation row's membership depends on its parent chunk, so its statistics need cross-table triggers. The `corpus` column reserves `'translations'`. Revisit when the live step or a later eval shows the cross-language slice lagging.

### Query (LEX-04, LEX-07)

- **D-22: Function.** `public.rag_bm25_search_chunks(...)`: the tenant key, profile id, query embedding, lexical tokens, lexical limit and every filter parameter of 0856 under the same names, plus `p_k1`, `p_b` and `p_candidate_limit`. It returns the row type of `hybrid_search_chunks` with `leg = 'lexical'`, `lexical_score` = BM25 and `similarity` computed exactly as the 0856 lexical leg computes it (dense cosine of the hit under a `legacy_column` profile, else null). `SECURITY INVOKER`, `SET search_path = ''`, service role only. It uses no temp table (the effective-profile map is passed as a bound jsonb value), so it can run in the same transaction as `hybrid_search_chunks`.
- **D-23: Two passes.** Pass 1: rows matching `c.lexical_tsv @@ $tsquery` under the filter, ranked by `sum(idf_t * ts_rank(c.lexical_tsv, t, 0))` over the query terms, `LIMIT p_candidate_limit`. Pass 2: for each candidate, `unnest(c.lexical_tsv)` gives term frequencies (`cardinality(positions)`) and the length (sum over all lexemes); score = `sum(idf_t * tf * (k1 + 1) / (tf + k1 * (1 - b + b * dl / avgdl)))` with `idf_t = ln(1 + (N - df + 0.5) / (df + 0.5))`. Order `score DESC, chunk id`, `LIMIT p_lexical_limit`. Measured in PGlite on 30k synthetic chunks (research R-3): the two passes cost about what the `ts_rank_cd` leg costs today, while exact BM25 over every match costs about ten times more.
- **D-24: Exactness.** When the matches fit in the candidate cap the result is exact BM25 (test against a TypeScript reference). When they do not, pass 1 can miss rows only when no query term discriminates (research R-4); the eval reports the capped-versus-uncapped overlap and gates its mean at 0.95 on the fixture; the lever is the candidate cap.
- **D-25: Not ready means `ts_rank_cd`.** The function raises `lexical_stats_not_ready` (55000) when the tenant's state is not `ready` or the request statistics have `N = 0`. The pgvector backend keeps a per-tenant readiness cache (60 s) read through `rag_lexstats_status`; a tenant that is not ready, and any error of the BM25 call, is served by the unchanged `hybrid_search_chunks` lexical leg with trace code `lexical_stats_unavailable` or `lexical_bm25_failed`. This is degraded scoring, never a refusal, an outage message or an empty leg.
- **D-26: Budget.** The `search` stage budget stays 400 ms (chat, embed) and 300 ms (voice); no budget value is edited. With `bm25` the backend runs the dense call (`hybrid_search_chunks` with `p_lexical_limit = 0`) and the BM25 call in parallel. The benchmark plan records plans and timings; the live step repeats it on real Postgres at 30k, 300k and 1M chunks.
- **D-27: Scale lever recorded, not built.** Dropping near-ubiquitous terms from the match condition when rarer terms exist (document-frequency pruning) bounds the matched set at 1M chunks. It changes results, so it is not built here; the benchmark reports the matched-set sizes that would justify it.

### Security (LEX-06)

- **D-34: Logs.** `[Lexical Stats]` and `[Document Search]` lines carry tenant-key hashes, counts, codes and durations. Lexemes, tokens and query text are never logged, and the status and check RPCs return counts only.

## Existing Code Insights

### Reusable Assets
- The GIN index `idx_document_chunks_lexical_tsv` and the positional `lexical_tsv` already hold everything BM25 needs per chunk: term frequency is the number of stored positions of a lexeme and the length is their sum.
- `rag_assert_tenant_key` (0403) and the `scopeKey(scope)` helper give the one tenant input.
- `BackendCapabilities` and `backendForRequest` show how optional request fields reach a backend.
- `rag_eval.paired._bootstrap_interval` and `rag_eval.ship_check` give the seeded paired bootstrap.

### Established Patterns
- Service-role RPC header: `SECURITY INVOKER`, `SET search_path = ''`, schema-qualified names, REVOKE then GRANT on the full signature (0601, 0856, 0864).
- Triggers that must work for any writer are `SECURITY DEFINER` and inert until enabled (0702).
- Switches: five config locations, `scripts/rag/env-manifest.json`, `config/rag/settings-classification.json`, the eval env pin, a hash block only when on.
- Phase proof: a comparison spec under `eval/config/` run by `rag_eval.phase_compare`.

### Integration Points
- `createPgvectorBackend.search`: one RPC today; with `bm25`, a dense call and a BM25 call in parallel, merged into `BackendLegs`.
- `publish` stage and `runRelex`: best-effort compaction after the write.
- `eval/harness/pglite-supabase.mts`: statistics enable and rebuild for a `bm25` run.

</code_context>

<specifics>
## Specific Ideas

- The owner's offline reference used BM25Okapi with k1 = 1.5, b = 0.75 and Italian stemming. Stemming is already a separate switch (`RAG_LEXICAL_STEM_IT`, Phase 4.2); the live comparison runs with the deployment's own tokenizer settings and reports them.
- Lucene's IDF form is used instead of the classic Okapi form because it is never negative, so a term in more than half of the chunks cannot push a score below zero.
