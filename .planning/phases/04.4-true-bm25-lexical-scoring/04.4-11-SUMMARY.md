## Static scan (0900–0919, D-04 block)

- Every `CREATE OR REPLACE FUNCTION public.*` header has `SET search_path = ''`.
- The scan allows no unqualified `unnest`, `ts_rank`, `ts_rank_cd`, `cardinality`, `ln` or `quote_literal` (comments are stripped, dynamic SQL strings are included).

## Matrix scenarios covered (LEX-02)

- **Multi-tenant app path:** all 84 existing scenarios, which are 4 profiles (chat, embed, voice, eval) × 3 tenants × 7 paths. The tenants are `a` personal with a null organization, `b` personal, and `o` organization. The paths are all, exact_id, translated, table_lookup, identifier, versions and dup_cluster, and the four lookup paths include their cross-tenant asks. Each scenario runs a second time with `RAG_LEXICAL_SCORING=bm25`, after the statistics of all three tenants were enabled and rebuilt. Each bm25 row asserts that `rag_bm25_search_chunks` was called and that no stage detail carries `lexical_stats_unavailable` or `lexical_bm25_failed`. The existing own-rows and foreign-text checks then apply to the BM25-served result.
- **Removed member:** userA's membership of orgO is deleted, and the chat resolver then refuses the organization scope. A bm25 retrieval with the personal scope returns only `u:A` chunks. The membership is restored afterwards.
- **Direct SQL** (a fresh two-tenant database):
  - Each of a, b and o gets only its own rows for the same shared tokens.
  - These keys are refused: `s:default`, a malformed key, an unknown prefix, an empty key, and a tenant without statistics (55000).
  - Score stability: tenant a's ids and scores for three queries are deep-equal after each step while b ingests 50 chunks of a's tokens, then updates 10, then deletes 10. b is compacted after every step, and `rag_lexstats_check` is clean with nothing pending.
  - In tenant a, a deleted chunk and a superseded version (document and chunks `is_current=false`, then a new version) are absent after compaction. The new version is found, the check is clean, and b's result does not move.
- **Single-tenant:** the four lookup paths run again under bm25 with `s:default` statistics ready. Each asserts the BM25 call and that `u:`/`o:` keys are refused. A direct call serves `s:default` only and raises for `u:` and `o:` keys.
