# Phase 4.4 Plan 08: BM25 in the retrieval path Summary

**With `RAG_LEXICAL_SCORING=bm25` every lexical backend call of a request is scored by `rag_bm25_search_chunks`; a tenant without ready statistics, or a failed BM25 call, gets today's `ts_rank_cd` leg with the reason on the trace. With the switch off nothing changes.**

## Contract

- Request field: `BackendSearchRequest.lexicalScoring?: LexicalScoringRequest` = `{ mode: 'bm25'; k1: number; b: number }`. It is set from `config.v2.lexicalScoring` only (server config) and is absent under `ts_rank_cd`. `requiredCapabilities` and `backendForRequest` are unchanged (D-28).
- Meta field: `BackendLegsMeta.lexicalScoring?: LexicalScoringOutcome` = `'bm25' | 'stats_unavailable' | 'bm25_failed'`. It is present only for a request that carried the field and had a lexical leg (tokens and a lexical limit above 0).

## pgvector backend

- No field, empty tokens or lexical limit 0: the same single `hybrid_search_chunks` call with the same arguments, and no other RPC (D-02). There is no new await on this route.
- Field set: the backend calls `lexstatsReady(client, scopeKey, now, signal)` first.
  - Not ready: today's single call; meta `stats_unavailable`.
  - Ready: two calls run in parallel. One is `hybrid_search_chunks` with `p_lexical_limit: 0`, skipped when the dense limit is 0 (terminology leg). The other is `rag_bm25_search_chunks` with `bm25ArgsFrom(hybridArgs)`: the hybrid arguments minus `p_dense_limit`, `p_iterative_scan` and `p_exact_scan_cutoff`, plus `p_k1`, `p_b` and `p_candidate_limit`. A filter argument added to `buildRpcArgs` later reaches the BM25 call as well, and a test checks this. The result has the dense rows of the first call and the lexical rows of the second; meta `bm25`.
  - BM25 error `lexical_stats_not_ready`: the cache entry is dropped. The kept dense rows go out with the lexical leg of a second `hybrid_search_chunks` call (`p_dense_limit: 0`); meta `stats_unavailable`.
  - Any other BM25 error, or a rejected call: the same fallback; meta `bm25_failed`. One `logger.error('Document Search', 'rag_bm25_search_chunks failed', { rpc, code })`.
  - A dense-call error throws exactly as today (`EmbeddingProfileMismatchError` / `RetrievalBackendError`). An aborted signal rejects with no fallback call.
- Candidate-limit rule: `bm25CandidateLimit(n) = min(2000, max(500, 5 * n))`.

## Statistics client (`src/lib/rag/lexical/stats.ts`)

- `lexstatsReady` is ready when `state === 'ready'` and `chunk_count > 0`. The answer is cached per tenant key for 60 s (`LEXSTATS_READY_TTL_MS`), with at most 1000 entries; the oldest is evicted first.
- The client never throws: an error, a missing function (PGRST202, 42883) or a rejection reads as not ready and is cached. An abort is not cached.
- `dropLexstatsReady(tenantKey)` forgets one tenant.
- `countReadyLexstatsTenants(admin)` runs `rag_lexical_stats_state` with `count: 'exact', head: true` and `status = 'ready'`. It returns null on failure.

## Search stage

- `lexicalScoringArg(config)` returns `{ lexicalScoring }` for bm25, else `{}`. Under bm25, `runLegs` wraps the routed backend so every `backend.search` call carries the field: original and query variants, terminology leg, soft attribute leg, binding legs and the delegated port. `searchTranslations` is not wrapped (D-21).
- Detail codes (exported constants): `lexical_scoring_bm25`, `lexical_stats_unavailable`, `lexical_bm25_failed`. The stage adds one code per request, the worst of its calls, and only when the configured mode is bm25. The stage status is unchanged, so a fallback is never an error or a refusal (D-40).
- Startup line, logged once when the mode is bm25 and the admin client exists:
  `[RAG Config] RAG_LEXICAL_SCORING=bm25: tenants with ready lexical statistics: <n|unknown>; any other tenant is served by ts_rank_cd until npm run rag:lexstats rebuilds it`
  It contains no tenant key. Under ts_rank_cd there is no line and no query.

## Deviations

1. **`src/lib/rag/v2/stages/binding-legs.ts` is not edited.** The per-request backend view in `search.ts` reaches its `backend.search` call, and the stage test asserts that the binding-leg request carries the field. The same view also covers `src/lib/rag/v2/port.ts` (delegated search), which is not in `files_modified`.
2. **`src/lib/rag/deps.ts` is edited** (not in `files_modified`). This is the bug fix above; without it, the switch could not turn on in the app.
3. **Startup count.** It counts ready tenants (the plan's fallback), not "tenants with chunks and no ready statistics", because that count needs a new RPC.
4. **Pre-change snapshot.** The ts_rank_cd identity is asserted against explicit pre-change argument objects (three request shapes) and run-to-run equality. In the e2e test, the ts_rank_cd run is the baseline that the fallback run and a later ts_rank_cd run must equal.
5. **Status shape.** `lexstatsReady` also accepts `[{ rag_lexstats_status: {...} }]`. This is the fixture edge's scalar shape, found by the e2e test, and a unit test covers it.
