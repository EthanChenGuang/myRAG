# Phase 3.1 Plan 49: Batch API embeddings for backfill Summary

**With `RAG_EMBED_BATCH_MODE=batch_api`, a backfill job on an OpenAI profile now writes its chunks without vectors and parks at `embed_deferred`. `rag:backfill` then sends those chunks to the OpenAI Batch API (at most 50,000 inputs per batch), writes the vectors by `custom_id`, and publishes each job. A job is published only when every chunk has its active-profile vector; until then the previous version stays current.**

## Behaviour changes

- **Advance (`advance.ts`):** for a batch ingest job whose snapshot says `batch_api`, while the active profile is an OpenAI one:
  - the embed stage writes the chunks with `embeddings: null`;
  - publish does not run;
  - the job records stage `write` with its parser fields, then `rag_defer_ingestion_embed` parks it at `embed_deferred` and releases the lease;
  - advance replies `{ stage: 'embed_deferred', done: true }`. The worker treats this like the provisional reply: no fail, no retry.

  Incremental jobs, `sync` snapshots and non-OpenAI active profiles run the Phase 3 stages unchanged.
- **Publish guard:** `rag_publish_deferred_ingestion_job` checks `rag_vectors_complete` for the active profile, then runs the Phase 3 swap and sets the terminal ledger status (ready, needs_review or quarantined), all in one transaction. A missing vector raises `vectors_incomplete`: the job stays deferred and the previous version stays current.
- **`rag:backfill` (`orchestrate.ts`):** when the monitor reports deferred jobs:
  - for every target profile (active, backfilling, previous), the deferred chunks lacking that profile's vector are read with `rag_deferred_embed_chunks`;
  - OpenAI profiles go through `embedViaBatchApi`, which drains open batches first, submits, polls, maps by `custom_id` and resubmits missing inputs; other profiles are embedded synchronously;
  - vectors are written with `rag_write_deferred_vectors`, then `publishDeferred` runs per job;
  - the report prints chunks, tokens and USD per profile (Batch API at half price);
  - a job that is still incomplete leaves the batch running and the command exits 1, so `--resume` continues.
- **`openJobs` (`run.ts`)** no longer counts `embed_deferred`, so the monitor does not wait for the CLI's own work.
- With the default `RAG_EMBED_BATCH_MODE=sync`, nothing changes: no job is deferred and the CLI path is skipped.

## Known Limitations

- **Chunking-profile children:** under `RAG_PIPELINE=v2`, the children of chunking profiles are still embedded synchronously in the deferred embed stage. The Batch API path fills `document_chunks` vectors only.
- **Memory:** the CLI holds up to 100,000 chunk texts per Batch API round (two open batches at the provider limit). On `--resume`, an open batch whose chunks fall in a later round has its vectors dropped and those inputs are submitted again. This costs extra; nothing is lost.
- **Orphaned provider batch:** a kill between `batches.create` and `rag_record_embed_batch` can still orphan a provider batch. This is the 03.1-26 design; `EmbedBatchError` carries the provider id.
- **Non-active profiles:** a vector missing for a backfilling or previous profile does not block publish. The re-embed sweep picks those chunks up once they are current.
