## Task 3: real Batch API job and real parser numbers

### 3.1 Batch API (attempted live, blocked by the provider account)

- Harness: a throwaway script (not committed, deleted afterwards) called `embedViaBatchApi` from `src/lib/rag/ingest/backfill/batch-api.ts` with 20 synthetic neutral chunks, profile `text-embedding-3-small` / 1536 dims, a real `OpenAI` client and an in-memory RPC recorder standing in for `rag_record_embed_batch` / `rag_update_embed_batch` / `rag_open_embed_batches`. The plan was to check record-before-poll order, custom_id mapping (cosine of batch vectors against sync vectors for two probes) and duration.
- Result:
  - `files.create` (purpose `batch`): **succeeded** (one 4,781-byte JSONL file).
  - `batches.create`: **refused**, HTTP 400 `billing_hard_limit_reached`.
  - A sync `POST /v1/embeddings` probe: **refused**, `credit_balance_exhausted`.
  - No batch was created, so no row would have been recorded and nothing was billed. The orphaned input file was deleted (`deleted: true`).
- Transport note (environment only, not a product bug): the openai v4 SDK's default transport does not go through `HTTPS_PROXY`, so the proxy did not inject credentials (first attempts got 401). The harness passed `fetch` = Node's global fetch with `NODE_USE_ENV_PROXY=1` and `duplex: 'half'`. Production hosts call OpenAI directly with their own key, so this does not apply there.
- Observation for a follow-up (not fixed: this plan makes no code changes): when `batches.create` fails after `files.create` succeeds, `submitBatch` leaves the uploaded input file on the provider and rethrows the SDK error unwrapped (not as `EmbedBatchError`). The file holds chunk text, so a follow-up plan should delete it on that path (best effort) and wrap the error.
