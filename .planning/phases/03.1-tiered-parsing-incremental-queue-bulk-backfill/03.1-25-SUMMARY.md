# Phase 03.1 Plan 25: Backfill sources and inventory Summary

**Tenant-validated backfill sources (folder, bucket, manifest) with path and SSRF confinement, and a streaming sha256 inventory that dedupes inside the tenant and records skipped_duplicate ledger rows with counts that reconcile.**

## What existed and what was found

A previous executor left one WIP commit (7c5f7f8) with the three source files and a test file. Its test file did not type-check and hung when run (more than 120 s; most likely the bucket fake, which returned the same id-less rows for every prefix that the WIP source treated as folders, looping forever). The WIP was kept as the base and fixed, not restarted. Gaps found against the plan and fixed:

- Manifest lines were hand-validated (with the `doc_type` key assembled from string pieces) instead of using the generated `BackfillManifestEntrySchema` the plan names. Now parsed with the schema (`.strict()`), then the cross-field rules.
- SSRF: only A records were resolved (`dns.resolve`), IPv6 and IPv4-mapped IPv6 (`::ffff:127.0.0.1`), 100.64/10, multicast and reserved ranges were not blocked, IP-literal hosts were not handled, userinfo URLs were allowed. Now `getaddrinfo` (`dns.lookup all`) answers and literals go through a `net.BlockList`, mapped addresses are unwrapped, unparsable answers fail closed; the redirect limit is 5 hops, each hop checked before its request.
- Folder: symlinks were skipped silently (`lstat` is never `isFile` for a link, so the `realpath` confinement was dead code and a refusal was never reported); a file whose name merely contained `..` aborted the whole listing; order was filesystem order (a resumed batch could keep a different copy of identical files); a TOCTOU swap between listing and open was possible. Now symlinks are resolved and refused with `outside_root` (a link inside the root to a file inside it is listed under its own name), names are sorted, `open()` re-checks the real path.
- `listSource` defaulted to a 30 s timeout for the whole listing, which would cut off any large folder. Now the default signal never aborts; the 30 s limit applies per URL hop only.
- Bucket: no pagination past 1,000 objects, no size limit, and it would read any bucket including `rag-originals`. Now paged by offset, size-limited, and refuses internal buckets and invalid names.
- Manifest: duplicate `source_key` lines would be silently dropped by the ledger's unique key and break reconciliation; now refused with `manifest_duplicate_key`.
- Inventory: did not compile (`docType` not on the entry type), sent all skipped rows in one RPC, aborted on one unreadable file, kept every item (and for URL sources its bytes) alive in a map. Now chunked (1,000), unreadable files counted, only small records kept.

Against the WIP `inventory.ts`: 3 of the 10 vitest inventory tests fail (12-file totals shape with `unreadable`, chunking at 1,000, unreadable files); 3 of 7 PGlite tests fail (all on the totals shape). The tenant isolation and streaming behaviour of the WIP inventory was already correct; those tests pass against it and are kept as regression guards.

Mutations of the new inventory, each caught by exactly one test: hashing after gathering all chunks (streaming test: the hash is fed in 64 KiB pieces with at most 4 pieces read ahead, 240 pieces for 15 MiB), dropping the row-level tenant check (cross-tenant answer test), no chunking (1,000-chunk test), not catching unreadable files (unreadable test), and a hard-coded other tenant in the hash lookup (4 of 7 PGlite tests).

Tenant scoping (security-critical):

- `backfillScope`: multi-tenant accepts `u:<existing user>` and `o:<existing org>` (case-insensitive, lower-cased once by `parseTenantKey`), refuses `s:default`, unknown ids, a user id used as an org id and vice versa, garbage and injection shapes before any lookup; single-tenant accepts only `s:default` and never queries; a failing lookup refuses as `unavailable`. Three tenants yield three distinct scope keys.
- Inventory, multi-tenant (PGlite, real 0356 SQL as service_role): tenants A, B and organization O, with the same content owned by B and O only. A's inventory marks it new and writes no row for it; B's and O's mark it duplicate; every `skipped_duplicate` row carries the batch's own tenant key; the row-level tenant check also ignores a lookup row of another tenant.
- Inventory, single-tenant (PGlite): the 12-file scenario, non-current and non-ready documents are not duplicates, and the SQL refuses a `u:` or `o:` key for batch creation and for the hash lookup (the `tenant_key` column is generated, so a second tenant cannot exist in this mode).

## Known limits

- DNS rebinding: the address check and the connection use separate lookups (global `fetch` cannot pin an address without an undici dispatcher, and undici is not a dependency). The manifest is operator-written, so the residual risk is low; pinning would need a dependency and was not added.
- Memory: a manifest URL is fetched while listing (to give per-line redirect and size verdicts) and its bytes (at most 20 MiB) are held until the consumer drops the item; `inventory` drops each item after hashing, so peak is one body. Re-opening a URL item for upload reuses those bytes only while the item is held.
- Bucket downloads read the object into memory (bounded by the 20 MiB limit) before streaming it.
