- **Config sync:** the twelve D-42 variables go to env.ts, init-env.js, config-server.js, the Config UI and the manifest (03). There are no secrets; `.env.example` uses placeholders.
- **Toggle off-states:** every switch has a named proof (index toggle matrix). Fixed routing equals Phase 3 in 22 T3 and 52 T1.

## Blockers

### B1 [security / verification] Realtime channel authorization must be proven to deny another tenant's topic before execution, not only at the live check
- **Where:** Plan 03.1-08 Task 3 (and 03.1-38 Task 1, which relies on it through T-03.1-85).
- **Evidence:** The Task 3 behaviours only test that the DO block *creates* the select policy when a stub `realtime.messages` exists. No test evaluates the policy's predicate. Nothing shows that user B, or a non-member of org O, is denied topic `rag-ingest:u:<A>` or `rag-ingest:o:<O>`. The "s:default in single-tenant mode" condition is also unspecified in SQL: the database cannot see `NEXT_PUBLIC_MYRAG_DEPLOYMENT_MODE`.
- **Why it blocks:** plan 38 derives the topic on the client, and the status route returns no tenant key (self-declared choice 6). That design is safe only if the policy is the gate. A wrong predicate would leak job and document ids and status across tenants, and the only proof today is the live item in 54.
- **Required property:** an automated test shows that for a stubbed `realtime.topic()` and `auth.uid()`:
  - a user reads only `u:<self>`, `o:<member org>`, or `s:default` when the schema is single-tenant;
  - every other topic yields zero rows;
  - the multi-tenant setup never admits `s:default`;
  - no INSERT/UPDATE policy on `realtime.messages` is created.
- **Example fix (non-binding):** in the PGlite test, create stub `realtime.messages` and `realtime.topic()` (reading a GUC), plus an `auth.uid()` stub. Apply 0353, `SET ROLE authenticated`, and select under three topics for two users and an org non-member. Tie `s:default` to the existing single-tenant setup marker or tenant-key check, not to an env value.

## Warnings

### W1 [scope] 03.1-22 modifies 16 files (blocker threshold is 15)
- **Plan:** 03.1-22 (TRACER, 3 tasks).
- **Evidence:** It touches enqueue/runner/parse-cache/wake, two callback libs and two routes, three sidecar modules and four tests. Task 1 alone wires about 10 files.
- **Required property:** the tracer fits one executor context.
- **Example fix (non-binding):** move Task 2 (callback auth and wake) into its own plan in the same wave, or move `wake.ts` and the run_once script out.

### W2 [scope] 03.1-02 lists 28 files_modified
- **Evidence:** 18 of the 28 are generated `*.schema.json` files plus `contracts.generated.ts`. The hand-written code is about 9 files.
- **Required property:** the context load stays bounded.
- **Example fix (non-binding):** acceptable if the schemas come from `export_schemas.py`. State in the plan that the schemas are generated and never hand-edited, or collapse them under a glob.

### W3 [security hygiene] The test-only `RAG_INGEST_CONVERTER=recorded` is selectable in production
- **Plan:** 03.1-27 Task 3 (self-declared choice 7).
- **Evidence:** The setting is only *commented* as test-only in `.env.example`. If a deployed worker had it set, it would ingest recorded fixture outputs as real document content.
- **Required property:** the recorded converter cannot run in a deployed sidecar.
- **Example fix (non-binding):** refuse `recorded` at settings validation unless a test flag (for example `RAG_SIDECAR_ENV=test`) is set; have /ready report 503 otherwise; add a test. `RAG_INGEST_APP_RATE` is fine as an ordinary sidecar setting.

### W4 [research resolution] RESEARCH "## Open Questions (with recommended answers)" is not marked RESOLVED
- **Evidence:** All nine questions are in fact settled by CONTEXT A-1..A-10, but the section heading has no `(RESOLVED)` marker and the questions have no inline RESOLVED markers.
- **Required property:** every research question is visibly resolved.
- **Example fix (non-binding):** rename the heading to `## Open Questions (RESOLVED)` and add "RESOLVED: A-n" to each item.

1. **D-34 index widened to (batch_id, kind, source_key):** accepted. Within a kind it keeps the D-34 guarantee (resume never duplicates). It is needed so one sampled file can hold a `dry_run` job and an `ingest` job, and plan 01 tests the 23505 case.
2. **html/docx converted in the worker via the Phase 3 Docling adapter:** consistent with the Python sidecar constraint; no issue.
3. **Backfill document rows at first claim via an advance `begin` phase (46):** accepted. It dedupes per tenant at begin and is covered by T-03.1-102 and the resume test.
4. **Dry-run jobs end `ready`/stage `check` with no document row (40 T2):**
   - Choice accepted.
   - **INFO:** status filters and the admin list should not count dry_run "ready" as an ingested document. Show `kind` in the list (24) and exclude `dry_run` from success counts in the 48 report.
5. **Admin job list deployment-wide across tenants (24):** acceptable.
   - At HEAD, `requireRagAdmin` checks the deployment-level `admin_users` table, the same scope as 03-37 quarantine. Org admins are not RAG admins and get 403, so in multi-tenant mode an org owner cannot see other orgs' jobs.
   - **INFO:** the job list response should omit filenames and the original_ref unless needed, and document that the list is deployment-operator-only.
6. **Realtime topic derived on the client:** acceptable only with B1 fixed. The payload is limited to ids and status (tested), and the private flag is set.
7. **Sidecar settings:** see W3. They are sidecar-only and are not `.env.local` variables, so the five-place sync rule does not apply. They are documented in `rag-sidecar/.env.example`.

- **INFO [verify paths]:** greps on `src/app/api/rag/ingest/jobs/[id]/route.ts` are unquoted. They work under default bash (an unmatched glob stays literal) but would break under `failglob`. Quote such paths.
