## Implementation Decisions

### Ledger and its relation to Phase 3's stage state

- **D-01:** `ingestion_jobs` supersedes the document-row stage state of P3 D-02 for every job that goes through the queue, and Phase 3's state is kept unchanged for runs that do not.
  - **Queued jobs (async uploads, sync routes, backfill):** the ledger is the only authority for stage state. `documents.processing_state` is not written. `documents.processing_status` is kept as a coarse mirror, written by the same ledger transition function, so the P3 D-21 status route and the existing status monitors keep working.
  - **Inline runs (`RAG_INGEST_ASYNC=off`):** nothing changes. P3 D-02 state on the document row and `resumeIngest` stay as they are, and no ledger row is written.
  - **Rule:** one run has exactly one state authority. No stage reads both.

  **Reversibility:** costly. The worker, both runners, the Config UI job list and the backfill report all read this table.
- **D-02:** The stage functions of P3 D-02 are reused unchanged. Phase 3.1 adds two stages in front of `parse` (`preflight`, and `check` after each parse attempt) and maps the stage names to the ledger statuses of the spec:

  | Ledger `status` | Stages it covers |
  |---|---|
  | `queued` | waiting, or waiting for a retry (`run_after`) |
  | `preflight` | `preflight` |
  | `parsing` | `parse` (one attempt per tier tried) |
  | `checking` | `check` |
  | `chunking` | `content_hash_dedup`, `scan_injection`, `chunk`, `enrich`, `extract`, `images` |
  | `embedding` | `embed`, `write`, `publish` |
  | `ready`, `failed`, `quarantined`, `needs_review`, `skipped_duplicate` | terminal |

  The exact stage name is stored in a `stage` column, and `timings` is a jsonb keyed by stage name. `identify`, `file_hash_dedup` and `store_original` run in the route before the job is queued (D-13).
- **D-03:** Ledger columns are the spec's list plus these:
  - `kind`: `ingest | dry_run | delete`
  - `stage`, `run_after`, `locked_by`, `runner` (`worker | ray`)
  - `settings` jsonb: the routing settings snapshot (D-08)
  - `original_ref`: bucket and path of the original file
  - `needs_review_reason`, `provisional_published_at`, `trace_id`, `deleted_at`
  - the per-page fields of D-55: `page_ranges`, `tier_page_counts`, `detect_counts`, `preflight_ref`

  Tenant is stored as `tenant_key` with P3 D-06 semantics. RLS is enabled with no policy for `anon` or `authenticated`, so only the server role reads or writes it. Migrations follow P3 D-05 (`supabase/migrations/`, setup files updated, PGlite loads them).

  **Reversibility:** one-way. It is a migration on the user's Supabase project; applying it there is a live verification item.
- **D-04:** The ledger API is a set of SQL functions, callable only by the server role, and both the TypeScript app and the Python worker call them through PostgREST RPC. Nothing updates `ingestion_jobs` with ad-hoc statements.
  - `rag_enqueue_ingestion_job`, `rag_claim_ingestion_jobs` (`FOR UPDATE SKIP LOCKED`, sets `lease_until` and `locked_by`), `rag_claim_ingestion_job` (one named job, used by the Ray runner), `rag_heartbeat_ingestion_job`, `rag_advance_ingestion_job`, `rag_record_parse_attempt`, `rag_fail_ingestion_job` (retry or terminal), `rag_retry_ingestion_job`, `rag_delete_ingestion_job`
  - "Both runners write through the same ledger functions" in the spec means these functions.

  The boundary check of P3 D-04 gains a rule: a direct `.from('ingestion_jobs')` write outside the ledger client module fails CI.

  **Reversibility:** costly. It is a contract between the app, the sidecar and the Ray runner.
- **D-05:** `needs_review` is a terminal ledger status that means "published with the best result, and flagged". The document row stays `status='ready'`, so the P3 D-08 retrieval filter still returns it, and `documents.needs_review` plus `needs_review_reason` are set for the lists. If the best result has no text, nothing is published: the ledger row is `needs_review` and the document row is `failed` and retryable.

### Where each stage runs

- **D-06:** Stages are split by where their single implementation already lives. Nothing is implemented twice.

  | Runs in | Stages | Why |
  |---|---|---|
  | Upload or sync route (TS) | `identify`, `file_hash_dedup`, `store_original`, enqueue | fast, and the caller needs the job id |
  | Python worker (sidecar) | claim, `preflight` layers L1 and L2, the page-tier decision, range building, `parse` for `fast` and `structured` ranges (Docling in-process), merging the ranges, `check`, escalation, parse-cache read and write, lease heartbeat, retry scheduling | Docling, pypdfium2 and pdfplumber are Python, and the Ray runner needs these as local functions |
  | App, called back by the worker (TS) | `parse` for tier `native` (existing extractors) and for `premium` ranges (LlamaParse client), the L3 vision-model call, then `content_hash_dedup` to `publish` | P3 D-04 allows only `src/lib/rag/ingest/` to write chunks; the embedding registry, injection scan, profiles, model keys and the cloud guard are TypeScript |

  The worker never writes `documents` or `document_chunks`.
- **D-07:** The callback endpoints are internal app routes, authenticated with the existing `RAG_SIDECAR_SECRET` (constant-time compare, refuse all when unset, as in Phase 1 D-02 and D-21):
  - `POST /api/internal/rag/ingest/jobs/{id}/detect-vlm`: the L3 call of D-50 for a small batch of page images.
  - `POST /api/internal/rag/ingest/jobs/{id}/parse-external`: runs tier `native`, or `premium` for one page range, and writes the result to the parse cache. LlamaParse polling is sliced; the route returns `pending` with a continuation and the worker calls again.
  - `POST /api/internal/rag/ingest/jobs/{id}/advance`: runs the next post-parse stages inside a time slice (default 40 s, under Vercel's 60 s cap) and returns `{stage, done, wait?}`. The worker loops until `done`. Embedding is cursor-based, so a large document spans several calls.

  The tenant scope for these calls is minted server-side from the ledger row by a new function inside `src/lib/rag/tenant/` (`scopeFromIngestionJob(jobId)`). The worker never sends a tenant.

  **Reversibility:** costly. It is a wire contract between two separately deployed services.
- **D-08:** The app is the source of truth for routing settings. At enqueue, the effective settings are written into `ingestion_jobs.settings`: routing mode, cloud allowed, escalation, progressive, per-document cap, the profile id and version, the effective `min_tier` and `max_tier`, and the embedding mode. The worker obeys the snapshot and never reads these from its own environment, so the app and the sidecar cannot drift. The two hard constraints are also re-checked live at execution (D-18).
- **D-09:** The worker is a module of the sidecar, `rag_sidecar/ingest/`, started in the FastAPI lifespan when the sidecar's `RAG_INGEST_WORKER=on` (default `off`).
  - It needs `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and `RAG_APP_INTERNAL_URL` in the sidecar environment. `/ready` returns 503 when the worker is on and any of these is missing.
  - Docling runs in the P3 D-20 bounded process pool, so `/health` stays responsive.
  - This amends P3 D-20's "stateless towards Supabase": the parse job API stays stateless, and only the worker module talks to Supabase, through the D-04 functions and the storage REST API.
  - Several sidecar replicas are safe, because claiming is `SKIP LOCKED`. On shutdown the worker releases its leases.

  The sidecar holding the service-role key widens what a sidecar compromise can reach. The researcher evaluates a restricted database role that can only execute the ledger functions and read the originals bucket; the service role is the starting point.

### Tiered routing and the quality check

- **D-10:** `RAG_PARSE_ROUTING=fixed|tiered`, default `fixed`. `tiered` requires `RAG_INGEST_PIPELINE=unified` and `RAG_INGEST_ASYNC=on`, because an escalation chain cannot fit the 45 s request budget of P3 D-21. `check-config` reports an invalid combination as an error, and at run time an invalid combination falls back to `fixed` with one `[Ingest]` log line. A queued job under `fixed` runs the P3 D-19 chain as a single attempt and records it in the ledger.
- **D-11:** Routing data lives in `config/rag/parse-routing.json`, validated by a Pydantic `ParseRoutingConfig` with a generated Zod schema:
  - tier definitions and their option presets (D-48)
  - the L1 signal thresholds of the spec, the L2 and L3 trigger rules, and the L3 limits
  - the range-building rules (D-51)
  - quality thresholds
  - the escalation ladder per file format (PDF: `fast → structured → premium`)
  - estimated cost per page and seconds per page per tier and per detection layer

  Tier `fast` reuses the P3 D-20 Docling adapter with a `pdf_backend` option and a `page_range`, so its output format is the Docling one. PyMuPDF is not used; pypdfium2 and pdfplumber cover L1.
- **D-12:** The preflight probe is a set of pure functions in the sidecar, also exposed as `POST /v1/preflight`, returning a Pydantic `PreflightResult`: page count, encryption, per-page signals and tiers, the page ranges, a document class and the page share per tier. Per-page routing, the three layers, the page-tier mapping, range building and boundary tables are decided in D-48..D-56.
  - An encrypted PDF that cannot be opened fails at once with `encrypted_pdf`, with no retry.
  - txt, md, csv, html and docx skip the probe and use `native`. An image upload is class `image` and keeps the existing captioning path.
  - The document class is derived from the page shares: `scanned` when at least 90% of pages are scanned, `mixed` when scanned and digital pages both exceed 10%, `tables` when any page has a table, `layout` when the only structure is multi-column, otherwise `text_pdf`.
- **D-13:** The effective `min_tier` and `max_tier` of a document type are the admin override when one exists, otherwise the value in `config/rag/processing-profiles.json` (the fields P3 D-13 reserved). Overrides live in a small table, `rag_parse_tier_overrides` (`doc_type`, `min_tier`, `max_tier`, `updated_by`, `updated_at`; deployment-level; server role only), edited through `PUT /api/rag/admin/parse-tiers`. Starting profile values: `invoice_receipt`, `scanned_image` and `financial_report` have `min_tier=structured`; every type has `max_tier=premium`. `min_tier` raises every page and `max_tier` caps every page. Editing the rest of a profile in the Config UI stays OPS-03 (v2).
- **D-14:** The quality check is one pure Python function, used for every tier, including results that the app produced for `native` and `premium`. It runs per page range and reports the failing pages. It fails on any of the spec's six conditions. Details that the spec leaves open:
  - **Low characters:** a page whose parsed text has under half the characters of its text layer, or a scanned page with under 30 characters after OCR.
  - **Garbled ratio:** share of U+FFFD, private-use characters and mojibake patterns above 5%, the L1 threshold.
  - **Language mismatch:** the detected language is not the language of the document's text-layer sample when that one is confident, and otherwise is not in the profile's OCR language set. Ranges under 200 characters skip this test.
  - **Tables:** a page had a table signal after L1 to L3 and the result has no table on it.

  The check returns the failed conditions per page and a score, so attempts can be ranked.
- **D-15:** Escalation is per page range. The unit that is re-parsed one step up the ladder is each run of consecutive failing pages inside a range, plus any neighbour that D-52 pulls in; pages that passed keep their result. Limits: a page is escalated at most twice, never above `max_tier`, never past a hard constraint, and only when `RAG_PARSE_ESCALATION=on` (default `on`; it has no effect under `fixed`). Every attempt is recorded in `attempts[]` as `{tier, preset, parser, parser_version, pages, reason, ms, est_cost, check}`, where `pages` is the page range. For each page the kept result is the first passing attempt, or the best-scoring one when none passes. The job's `escalations` column counts escalation attempts.
- **D-16:** A job ends as `needs_review` when any of its pages is in one of two cases:
  - its check failed and escalation was blocked, for any reason (cloud not allowed, budget, page cap, `max_tier`, escalation off, two escalations used)
  - its page tier was `premium` (from `min_tier` or an L3 verdict) and the budget or the page cap blocked it, even if the lower tier passed the check. A budget block is temporary, and the reason tells the admin a retry may do better.

  The affected pages are marked in `page_ranges`. A document that cloud policy kept off `premium`, and whose lower tier passed the check, ends `ready` with a routing note in the ledger.

### Per-page routing and detection layers

- **D-48:** Page-tier mapping. Each page gets a tier and an option preset, and the preset is what a range is built from.

  | Page signals after detection | Tier | Preset |
  |---|---|---|
  | none | `fast` | `fast`: pypdfium2 backend, OCR off, table structure off |
  | `multi_col` only | `structured` | `structured_layout`: layout model on, TableFormer off, OCR off |
  | `tables` or `has_figure` | `structured` | `structured_full`: layout model, TableFormer, OCR only where a region has no text |
  | `scanned` or `garbled` | `structured` | `structured_ocr`: full-page OCR (zh/en/it), the text layer ignored, TableFormer on |
  | L3 verdict `complex` | `premium` | `premium` |

  Then the profile applies: `min_tier` raises every page (a `min_tier` of `premium` sends scanned pages to `premium`), and `max_tier` caps every page. A page capped to `structured` keeps the strongest structured preset its signals ask for. Pages needing `premium` pass the D-18 guard as one request per document.
- **D-49:** Layers L1 and L2.
  - **L1** runs on every page with the spec's thresholds. pypdfium2 reads the text layer, character counts and image boxes. pdfplumber (`find_tables`, ruling lines, word boxes) runs only on pages where pypdfium2 reports line or path objects or aligned number columns, because running it on every page would miss the target of under 1 s per 100 pages. Pages are probed in parallel. A benchmark test reports the time on a 100-page fixture.
  - **L2** runs the Docling layout model, with OCR and TableFormer off, on the pages L1 marked `uncertain`, batched as page ranges. A table, formula or chart found by L2 sets the page to `structured_full`. Nothing found clears the `uncertain` flag and the L1 result stands; a scanned page stays `structured_ocr`.
  - **Disagreement:** L1 and L2 disagree when one of them reports a table and the other does not. Without L3 the page takes the higher of the two tiers, because the quality floor comes before cost.
- **D-50:** Layer L3. `RAG_PARSE_VLM_DETECT=true|false`, default `false`; it needs `tiered`.
  - **When:** only for pages on which L1 and L2 disagree, at most 20 pages per document (a value in the routing data).
  - **How:** the worker renders the page image with pypdfium2 and calls the app's `detect-vlm` route (D-07). The app calls a vision model and validates the answer against a Pydantic `PageStructureVerdict` (`has_table`, `has_multi_column`, `is_scanned`, `has_formula`, `has_chart`, `complexity: simple | complex`, `confidence`). The verdict replaces the L1 and L2 signals for that page.
  - **Model:** `RAG_PARSE_VLM_MODEL`, defaulting to the vision model the existing image captioning uses, so no new entry is needed in the five-location model lists.
  - **Cloud:** it counts as cloud. The D-18 guard covers it, `RAG_PARSER_ALLOW_CLOUD=false` blocks it, and the test for success criterion 2 also requires zero requests at the vision-model stub.
  - **Budget:** one L3 page uses one page of the tenant's monthly premium budget (D-19), counted in its own column, and its estimated cost counts against a backfill's `--budget`. With a budget of `0` L3 does not run.
  - **When blocked or failing:** the D-49 disagreement rule applies. A blocked L3 call never fails the job and never causes `needs_review` on its own.
  - **Tests:** a recorded fake. Page images are never logged.
- **D-51:** Range building. Consecutive pages with the same preset form one range, parsed as one Docling conversion with `page_range`. To limit fragmentation, pages are only ever lifted, never lowered:
  - a run of fewer than 2 lower-preset pages between two higher ranges is lifted into them
  - when more than 20 ranges remain, or at least 60% of the pages are in a higher preset, the document is parsed as one range at the highest preset any page needs below `premium`

  `premium` pages are never added by these rules. The three numbers are starting values in the routing data.
- **D-52:** Tables that cross a range boundary. The page at the other side of the boundary is pulled into the higher preset, and the rule repeats until the table ends.
  - **Before parsing:** L1 flags a continuation when a table region reaches the bottom text margin of page *n* and page *n+1* starts with a ruled table or aligned number columns at matching column positions.
  - **After parsing:** the check flags a range whose last page ends inside a table while the next range starts with aligned numeric rows and no table. The neighbour page is re-parsed in the higher preset, recorded as an attempt with reason `table_boundary`. This does not use up one of the page's two escalations.

  Both pages then sit in one conversion, and the table handling is Docling's and P3 D-22's (header row repeated on every table chunk). No separate table stitcher is built.
- **D-53:** Merging. The ranges are merged in page order into one Docling document before chunking, and the HybridChunker runs once on the merged document.
  - **Invariants, each with a test:** page numbers equal the original file's; every page appears exactly once; the heading hierarchy continues across a range boundary, so the first chunk of a range inherits the open headings in `section_path`; the output is the same for the same inputs.
  - **Premium ranges:** the worker cuts the premium pages into a sub-PDF with pypdfium2, so only those pages leave the deployment and only those are billed. The LlamaParse markdown is converted into Docling items with the original page numbers and merged like any other range.
  - **One range:** a document that is a single range skips the merge.
  - The researcher confirms the Docling API for concatenating documents and for provenance on converted markdown; the invariants hold either way.
- **D-54:** Parser bookkeeping for mixed documents. Each chunk's `parser_used` (P3 D-07) is the parser of the range its first page came from. The document's `parser_used` is `mixed` when more than one parser contributed, with the list in `metadata.parsers`.
- **D-55:** Per-page fields on the ledger. Per-page data is stored run-length encoded, so a row stays small for long documents:
  - `page_ranges` jsonb: `[{start, end, tier, preset, parser, layer: L1 | L2 | L3, signals[], status: ok | escalated | needs_review, cache_id}]`, final state after escalation
  - `tier_page_counts` jsonb: pages per tier, which gives the page share per tier
  - `detect_counts` jsonb: pages examined by L1, L2 and L3
  - `tier`: the highest tier used; `parser_used`: as in D-54; `doc_class`: as in D-12
  - `preflight_ref`: the path of the full `PreflightResult` with the raw per-page signals, stored next to the parse cache under the file hash and the probe version

  `attempts[].pages` holds the page range of each attempt.
- **D-56:** Cache per range. Each range is one `rag_parse_cache` entry; the page set and the preset are part of `options_hash`, so the key of D-20 keeps its shape. The merged document is its own entry (parser `merged`, `options_hash` over the ordered range entries). An escalation re-parses only the failing pages and reads every other range from the cache. Re-chunking reads the merged entry.

### Hard constraints and budget

- **D-17:** Defaults:

  | Variable | Default | Note |
  |---|---|---|
  | `RAG_PARSER_ALLOW_CLOUD` | `true` | today's parser is LlamaParse, so `true` is today's behaviour |
  | `RAG_PARSE_PREMIUM_PAGE_BUDGET` | `0` | pages per tenant per UTC calendar month; `0` means tiered routing uses no premium pages until an admin sets a number |
  | `RAG_PARSE_PREMIUM_MAX_PAGES_PER_DOC` | `200` | |

  `RAG_PARSER_ALLOW_CLOUD=false` applies in every mode, including `fixed` and inline runs: the P3 D-19 chain then skips LlamaParse and uses Docling. The page budget and the page cap apply only to queued jobs under `tiered`; `fixed` keeps Phase 3's unmetered LlamaParse use. With per-page routing the cap counts the pages of one document that need `premium`: when they exceed the cap, none of them go to `premium`.
- **D-18:** The hard constraints are enforced in one place: one guard module in the app, called at the single entry of the LlamaParse client and at the L3 vision-model call (D-50), which every mode calls. It refuses with `cloud_not_allowed`, `budget_exhausted` or `over_page_cap` before any bytes leave the deployment. The worker also avoids proposing `premium` when the snapshot forbids it, but the guard is the authority. The test for success criterion 2 counts requests at the LlamaParse stub and requires zero for every fixture, including escalations.
- **D-19:** Budget use is counted in a table, `rag_parse_budget_usage` (`tenant_key`, `month`, `pages_reserved`, `pages_used`, `vlm_pages_used`), through one SQL function that reserves atomically before a premium call, settles after it and releases on failure. Pages are the pages sent to LlamaParse plus the pages sent to the L3 vision model. A document's premium pages are reserved together before its first premium range, and escalations reserve as they happen. Dry-run samples count too. Single-tenant mode uses `s:default`. The Config UI shows this month's use per tenant, with parse pages and L3 pages apart.

### Parse cache

- **D-20:** The parse cache is a table, `rag_parse_cache`, keyed by `(tenant_key, file_sha256, parser, parser_version, options_hash)`, plus objects in the private bucket of P3 D-18 under `rag-originals/<tenant_key>/_parse-cache/<file_sha256>/<parser>-<parser_version>-<options_hash>/`. A lookup always filters by `tenant_key`; a two-tenant test proves the same bytes in another tenant miss.
  - **What is stored:** the conversion output (Docling JSON, LlamaParse markdown, or native text) and its `ParseResult`, not the chunks.
  - **`options_hash`:** sha256 of the canonical JSON of the options that change the conversion (preset, OCR languages, table mode, PDF backend, page set). Chunker options are excluded, so a chunk-size change still hits. D-56 covers entries per range.
  - **Relation to P3 D-18:** this extends it. For queued jobs the per-version parse output of P3 D-18 becomes a pointer to the cache entry (`documents.parse_cache_id`). Inline runs keep P3 D-18's layout.

  **Reversibility:** costly. The key and the path layout are persisted, and Phase 4's re-chunk reads them.
- **D-21:** "Zero parser calls" counts conversions: a Docling convert, a LlamaParse upload, or a native extraction. Merging cached ranges and re-chunking from the cached merged document run the HybridChunker in the sidecar on the stored document and is not a parser call. A counter on the fakes proves zero conversions for: re-chunking after a chunk-size change, a changed document type with equal parse options, a retry after an embedding failure, and the Phase 4 sweep's read path.

### Queue, worker, retries

- **D-22:** `RAG_INGEST_ASYNC=off|on`, default `off`. It needs `RAG_INGEST_PIPELINE=unified`. When on, every write path calls a second public function, `enqueueIngest(input)`, with the same input as P3 D-01's `ingest()`. The route runs `identify`, `file_hash_dedup` and `store_original`, creates the document row for the new version (`status='processing'`, not current), inserts the ledger row and returns **202** with `{jobId, documentId, status}`. An unchanged file under the same identity returns `skipped_duplicate` with the existing document id and writes a ledger row with that status. `ai-to-rag` and image uploads go through the queue too, so there is one path.
- **D-23:** Claiming and leases:
  - order: `priority` descending, then `created_at`
  - lease 120 s, heartbeat every 40 s; an expired lease is reclaimed and counts as a retry, so a job that crashes the worker cannot loop for ever
  - the worker polls every 2 s with jitter when idle, and the app sends a best-effort `POST /v1/ingest/wake` to the sidecar after enqueue
  - `RAG_INGEST_WORKER_CONCURRENCY`, default `2`

  Incremental jobs have priority 100 and backfill jobs 10. The worker also keeps at least one slot for jobs without a `batch_id`, because priority alone does not help when every slot holds a long backfill job.
- **D-24:** Retries: retryable errors (network, 5xx, timeout, expired lease) back off 30 s × 2^n and stop after 3 retries with `failed`. Permanent errors (encrypted PDF, unsupported type, file missing) fail at once. A failed job raises an error-level ingestion trace and one `[Ingest Alert]` log line. An admin retry resets `retries` and keeps `attempts[]`.
- **D-25:** Idempotency is P3 D-02's rule plus one write rule: the `write` stage first removes the rows of that `(document_id, version)` that are not published, then inserts in batches of 300 rows (allowed range 200 to 500). A test runs every stage twice and requires identical chunks and no duplicates.

### Identity, change handling and deletion

- **D-26:** Identity and change handling are P3 D-10 and P3 D-11 unchanged. The Nango sync enqueues one job per changed file with the provider file id as `source_key`.
- **D-27:** A deletion at the source soft-deletes through one SQL function, `rag_soft_delete_document(lineage)`: the current version and its chunks become not current, the document status becomes `deleted`, rows are kept so stored citations still resolve, and a ledger row of kind `delete` records it. Under `unified` with async on, the Nango orphan cleanup (`deleteOrphanedDocuments` in `src/lib/nango/sync-manager.ts`) calls this function. With the defaults it keeps today's hard delete. The function is the seam for the RET-05 outbox and for semantic-cache invalidation; neither is built here.

### Status in the UI

- **D-28:** Polling is the default and the tested path: `GET /api/rag/ingest/jobs/{id}` (owner-scoped), and the P3 D-45 route `GET /api/rag/ingest/{documentId}` reads the ledger for queued jobs. The chat upload component and the Config UI monitor show the status until `ready`, and show `needs_review`, `failed` and "searchable, still improving" (D-30).
- **D-29:** Realtime is optional, behind `NEXT_PUBLIC_RAG_INGEST_REALTIME` (default `false`). DATA-14 keeps the ledger server-role only, so the client does not subscribe to table changes. The ledger transition function sends a Supabase Realtime **broadcast** on a private per-tenant topic, and the payload holds only the job id, document id, status, stage and the provisional flag. The call is skipped where the `realtime` schema is absent (PGlite). Polling stays as the fallback. The researcher confirms the broadcast-from-database API and its channel authorization on the project's Supabase version.

### Progressive mode

- **D-30:** `RAG_PARSE_PROGRESSIVE=true` applies only to incremental jobs in which some page needs more than `fast` and at least half the pages have a usable text layer. The whole document parsed with the `fast` preset is published first as a normal version whose document row and chunks carry `provisional=true`, and `provisional_published_at` is set on the job. The routed tier then runs, and its result is published as the next version through P3 D-11, so citations to the provisional version still resolve. The job stays non-terminal until the final publish. Every post-parse stage runs twice, so embedding cost doubles for these documents; that is why the default is off. Backfill never uses it.

### Bulk backfill

- **D-31:** `npm run rag:backfill` is a TypeScript module under `src/lib/rag/ingest/backfill/`, run through `tsx` like P3 D-38. Flags: `--tenant <tenant_key>` (required), `--source <folder|bucket|manifest>`, `--budget <USD>`, `--concurrency <n>`, `--dry-run`, `--resume <batch_id>`, `--runner worker|ray`. A batch is a row in `ingestion_batches` (tenant, source, budget, concurrency, runner, status, dry-run report, totals).
  - **Folder:** files are uploaded to `rag-originals` at enqueue.
  - **Bucket:** a Supabase storage bucket of the same project, read in place.
  - **Manifest:** a JSONL file validated by a Pydantic `BackfillManifestEntry` (`source_key`, `path` or `url`, optional `doc_type`).

  Backfill jobs get their document row when first claimed, not at enqueue, so an abandoned batch leaves no rows in `processing`.
- **D-32:** `--budget` is a cap in USD on the batch's estimated cost (premium parse pages and embeddings). The tenant's monthly premium-page budget still applies on top. When the batch budget stops a premium parse, the document keeps its best allowed tier and is marked `needs_review` with `batch_budget_exhausted`. When the projected embedding cost alone exceeds the budget, the run refuses to start.
- **D-33:** Order of work:
  1. **Inventory:** sha256 of every file. Duplicates inside the inventory and against the tenant's existing `file_sha256` values are recorded as `skipped_duplicate` ledger rows, so counts reconcile. Content-hash dedup (P3 D-09) still runs after parsing.
  2. **Sample dry run:** always runs first. The sample is 1% of files, stratified by extension and size, and it grows (up to 5% of the inventory) until every class seen by preflight has at least 20 files, or all of them when a class is smaller. Sample jobs have kind `dry_run` and stop after `checking`. Their parse results stay in the parse cache, and their premium pages count against the budget.
  3. **Report:** class shares, projected pages per tier (from the per-page tiers of the sample), projected L2 and L3 page counts, projected cost, projected wall time, and the sample size per class. It is stored on the batch row and printed.
  4. **Run:** only with `--budget`, and only when the projection fits it. Without `--budget` the command stops after the report with a non-zero exit code.
  5. **End report:** failures, `needs_review` documents with reasons, and actual against projected cost.
- **D-34:** The batch's `--concurrency` is enforced inside the claim function (leased jobs of that batch never exceed it), so both runners obey the same limit. `--resume` re-reads the inventory, skips terminal jobs and continues; a unique index on `(batch_id, source_key)` makes re-enqueueing safe.
- **D-35:** `RAG_EMBED_BATCH_MODE=sync|batch_api`, default `sync`; `batch_api` is used only by backfill jobs and only for OpenAI profiles. The `rag:backfill` process runs the Batch API work, because it is long-running and the embedding registry is TypeScript:
  - a table `rag_embed_batches` tracks each provider batch (profile, provider batch id, input count, status, error)
  - at most 50,000 inputs per batch; `custom_id` is the chunk id plus `embedding_text_version`
  - a failed or expired batch is resubmitted for the missing inputs only, and `--resume` picks up open batches

  In this mode the stage order for a job is `write` (chunks without vectors, not published), then `embed` (deferred), then `publish`, and `publish` refuses while any chunk lacks its active-profile vector. This reordering is the only change to P3 D-02's stage list. The incremental path and providers without a batch API always embed synchronously.
- **D-36:** A backfill has no special path into a new embedding profile. While a profile is `backfilling`, P3 D-39's dual-write applies to backfill jobs like any other, the report shows the embedding cost per profile, and activation happens only through the P3 D-40 gate. The CLI never activates a profile.

### Ray runner

- **D-37:** `--runner ray` starts `python -m rag_sidecar.ingest.ray_runner --batch <id>` through `uv run --project rag-sidecar --extra ray`. It uses `RAY_ADDRESS` when set and a local Ray instance otherwise.
  - Ray Data reads the queued job ids of the batch. Each task claims its job with `rag_claim_ingestion_job`, so leases, the batch concurrency, the budget and resume behave as with the worker, and a batch can switch runners mid-run.
  - The per-job function is the same `process_job` the worker runs. Docling stages run in a Ray actor pool. Calls to the app (LlamaParse, post-parse stages) pass a rate limiter.
  - `runner` is recorded on each job.

  `ray` is an optional dependency group in `rag-sidecar/pyproject.toml`. The default image does not install it, and a CI check proves the default locked environment has no `ray`. The equality test (same ledger rows and chunk hashes as `--runner worker`, budget respected, resume after a kill) runs in its own optional CI job with a local Ray instance.

### Parser evaluation

- **D-38:** The parse test set extends the deterministic fixture generator of P3 D-23 to the seven classes of DATA-17 (digital text, table, multi-column, scanned zh, scanned en, scanned it, invoice) and adds two fixtures for per-page routing: a mixed document (digital text pages, a few table pages and a scanned page) and a document with a table that crosses a page break at a range boundary. Each fixture has an expected-structure file validated by a Pydantic `ParserExpected` (table cell grids, reading-order anchors, headings with levels, and the expected signals and tier of every page). CI scores recorded outputs per tier; real Docling and real LlamaParse numbers are live verification.
- **D-39:** Scores per tier, computed in the `eval` Python project:
  - **Text similarity:** 1 minus the character error rate after NFKC and whitespace normalization.
  - **Table cell F1:** micro-F1 over cells matched by row, column and normalized text.
  - **Reading order:** the share of anchor pairs in the right order.
  - **Headings:** F1 over (level, normalized text).
  - **Seconds per page and estimated cost per page.**
  - **Page-tier accuracy:** the share of pages routed to their expected tier, for L1 alone, for L1 with L2, and with L3 from the recorded fake; pages routed below their expected tier are listed. This is report-only and is the evidence for the thresholds.

  The researcher may replace the table metric with a published one when it is cheap to add.
- **D-40:** End-to-end: the P3 D-42 `ingest` fixture mode runs once per forced tier and once per routing mode. At least three approved golden items per fixture class link to these documents, added through the Phase 1 review workflow. The report gives Recall@k per tier. The gate compares `tiered` with `fixed` as paired differences on Recall@k and correct-refusal against the Phase 1 D-10 noise band, and it fails when `tiered` is lower. The report also shows the premium page share and the projected cost per 1,000 pages for both modes.
- **D-41:** Routing thresholds are chosen on the dev split only, written to `config/rag/parse-routing.json` with a reference to the report that justified them, and the test split is reported once.

## Summary

Phase 3.1 is integration on top of a Phase 3 that is fully planned (48 plans, `03-01` to `03-48`) but not yet executed: `src/lib/rag/ingest/`, `supabase/migrations/` and `config/rag/` do not exist in the tree today [VERIFIED: `ls src/lib/rag supabase config/rag` this session]. The CONTEXT note "Phase 3 has a CONTEXT but no plans" is out of date; every 3.1 plan must name the Phase 3 plan that creates the file it extends (dependency map in "Architecture Patterns").

The decisions are detailed and mostly implementable as written. The research found that the key library behaviour matches them: Docling's `convert(..., page_range=(a, b))` keeps the original page numbers, and `DoclingDocument.concatenate` merges ranges with headings that continue across the boundary [VERIFIED: docling 2.152.0 source `pipeline/base_pipeline.py:363-366`; concatenate executed with docling-core 2.108.0]. pypdfium2 reads text, path objects and images on 100 pages in 0.18 s. pdfplumber `find_tables` costs 7.3 s on all 100 pages but 0.06 s when gated to the 3 pages with path objects [VERIFIED: benchmark executed this session on a generated 100-page PDF]. So the gate in D-49 is what makes the "L1 under 1 s per 100 pages" target reachable. A `FOR UPDATE SKIP LOCKED` claim function works in PGlite 0.5.17, and under 8 concurrent connections on a real PostgreSQL 16 it handed out 600 claims for 600 distinct jobs [VERIFIED: both executed this session].

Fifteen findings change details the plans need. They are listed under "Findings that need an orchestrator decision". The most important:

- **Docling presets.** Docling's standard PDF pipeline cannot switch the layout model off, so the `fast` and `structured_layout` presets run the same models and differ only in the PDF backend (F-1).
- **Merging.** `concatenate` silently renumbers pages when a part has no `pages` entries or when the parts leave a gap (F-2).
- **Stage state.** The ledger has no field for the cursor and non-deterministic outputs that a multi-call `advance` needs (F-3).
- **Docling pool.** The Phase 3 parse pool has one process by default, so a reserved claim slot alone cannot protect upload latency from a long backfill conversion (F-5).
- **Cloud switch.** `RAG_PARSER_ALLOW_CLOUD=false` has no enforcement point in the default `legacy` pipeline, which calls LlamaParse directly from two files (F-6).
- **Supabase keys.** Supabase deprecates the legacy `service_role` key by the end of 2026, so the worker's HTTP client must handle the new `sb_secret_…` keys (F-7).

**Primary recommendation:** Build the ledger, budget and cache as `SECURITY DEFINER` SQL functions granted to `service_role` only, and call them over PostgREST `POST /rest/v1/rpc/*` with `httpx` from the worker. Add only `pdfplumber==0.11.11` (preflight) and `ray[data]==2.60.1` (optional extra) as new Python packages, both behind a human legitimacy check. Add no npm packages. Run every routed step in the sidecar worker, and delegate `fixed` parsing and all post-parse stages to the app through the three internal callbacks. Prove "defaults = Phase 3" with a differential test before any other gate.

### Pattern 1: Ledger as SQL functions, claim with `SKIP LOCKED` and a lease

**What:** Every state change is one `SECURITY DEFINER` function. PostgREST runs each `POST /rpc/*` in one transaction: "POST is READ WRITE for VOLATILE and READ ONLY for STABLE and IMMUTABLE" [CITED: docs.postgrest.org/en/stable/references/transactions.html]. Every mutating function is therefore `VOLATILE` (the default) and is called with POST. Row locks end at commit; the durable claim is `lease_until` plus `locked_by`.

**When:** All ledger, budget and cache operations, from TS, the worker and Ray.

**Example** (status values quoted from CONTEXT D-02 lines 46-54: "`queued`", "`preflight`", "`parsing`", "`checking`", "`chunking`", "`embedding`", "`ready`, `failed`, `quarantined`, `needs_review`, `skipped_duplicate`"; the lease "120 s" from D-23 line 216):

```sql
-- Source: pattern verified this session in PGlite 0.5.17 and in PostgreSQL 16 (8 concurrent sessions, 600/600 distinct claims)
CREATE OR REPLACE FUNCTION public.rag_claim_ingestion_jobs(
  p_worker text, p_limit int, p_allow_batch boolean, p_runner text DEFAULT 'worker')
RETURNS SETOF public.ingestion_jobs
LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
BEGIN
  RETURN QUERY
  WITH candidates AS (
    SELECT j.id
    FROM ingestion_jobs j
    WHERE j.deleted_at IS NULL
      AND j.kind IN ('ingest', 'dry_run')
      AND (p_allow_batch OR j.batch_id IS NULL)
      AND (
        (j.status = 'queued' AND (j.run_after IS NULL OR j.run_after <= now()))
        OR (j.status IN ('preflight','parsing','checking','chunking','embedding')
            AND j.lease_until < now())                       -- expired lease: reclaim, counts as retry
      )
      AND (j.batch_id IS NULL OR rag_batch_has_room(j.batch_id))  -- locks the batch row (F-11)
    ORDER BY j.priority DESC, j.created_at
    FOR UPDATE OF j SKIP LOCKED
    LIMIT p_limit
  )
  UPDATE ingestion_jobs j
     SET status      = CASE WHEN j.status = 'queued' THEN 'preflight' ELSE j.status END,
         retries     = j.retries + CASE WHEN j.status = 'queued' THEN 0 ELSE 1 END,
         locked_by   = p_worker,
         runner      = p_runner,
         lease_until = now() + interval '120 seconds',
         updated_at  = now()
    FROM candidates c
   WHERE j.id = c.id
  RETURNING j.*;
END $$;
REVOKE ALL ON FUNCTION public.rag_claim_ingestion_jobs(text,int,boolean,text) FROM PUBLIC, anon, authenticated;
GRANT EXECUTE ON FUNCTION public.rag_claim_ingestion_jobs(text,int,boolean,text) TO service_role;
```

Notes for the planner:

- A reclaimed job whose `retries` would exceed 3 is set to `failed` inside the same function, not returned (D-24).
- `rag_batch_has_room(batch_id)` does `SELECT … FROM ingestion_batches WHERE id = $1 FOR UPDATE`, then counts leased jobs of the batch against `concurrency` (F-11). Calling it inside the `WHERE` with `SKIP LOCKED` can evaluate it for rows that are then skipped. The simpler, verified shape is a loop: claim one candidate at a time, at most `p_limit` times.
- Indexes:
  - `(priority DESC, created_at) WHERE status = 'queued' AND deleted_at IS NULL`
  - `(lease_until) WHERE status IN (<active statuses>)`
  - unique `(batch_id, source_key)` (D-34)
- `rag_heartbeat_ingestion_job(p_id, p_worker)` extends the lease only when `locked_by = p_worker`. It returns `false` when the lease was lost, and the worker must then stop the job without writing anything.
- `rag_advance_ingestion_job`, `rag_fail_ingestion_job` and `rag_record_parse_attempt` all check `locked_by = p_worker`. A worker whose lease expired cannot overwrite the new owner's state.
- Backoff in `rag_fail_ingestion_job`: `run_after = now() + (30 * 2^retries) * interval '1 second'`, status `queued`; after 3 retries, `failed` (D-24).
- `RAISE` uses SQLSTATE codes and short reason strings only, never document text. The fake edge already maps SQLSTATE to PostgREST-shaped errors (P3 03-10).

### Pattern 2: Worker loop, slots and callbacks

**What:** An `asyncio` task started in the FastAPI lifespan when `RAG_INGEST_WORKER=on`.

- **Slots.** It holds `RAG_INGEST_WORKER_CONCURRENCY` slots (default 2). It claims with `p_allow_batch = (free_slots > 1)`, so one slot is always free for non-batch jobs (D-23).
- **Polling.** It polls every 2 s with ±25% jitter. `POST /v1/ingest/wake` sets an `asyncio.Event` that ends the sleep early.
- **Heartbeat.** A per-job task heartbeats every 40 s.
- **CPU work.** Docling and preflight run in the P3 03-12 process pool through a priority queue (F-5). The event loop only does I/O, so `/health` stays fast.

**Callbacks:**

- `parse-external` and `advance` are idempotent per `(job_id, stage, cursor)`. The worker retries a timed-out callback with the same body.
- The app re-derives scope with `scopeFromIngestionJob(jobId)` (D-07).
- The secret is compared with `internalApiKeyMatches` from `src/lib/internal-api-key.ts`, which hashes both sides and uses `timingSafeEqual` [VERIFIED: `src/lib/internal-api-key.ts:8-11`]. It refuses everything when `RAG_SIDECAR_SECRET` is empty.

**Shutdown:** in lifespan exit, stop claiming, wait up to 10 s for in-flight callbacks, then call `rag_release_ingestion_job` for each held lease, which sets `lease_until = now()` and does not count a retry.

**Readiness:** `/ready` returns 503 when the worker is on and `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` or `RAG_APP_INTERNAL_URL` is missing (D-09), or when the last claim attempt failed for longer than 60 s.

### Pattern 3: L1 probe with gated pdfplumber

```python
# Source: APIs executed this session (pypdfium2 5.15.2, pdfplumber 0.11.11); timings 0.177 s / 100 pages (pypdfium2),
# 0.064 s for find_tables on 3 gated pages vs 7.300 s on all 100 pages
import pypdfium2 as pdfium
import pypdfium2.raw as pdfium_c
import pdfplumber

def l1_signals(path: str, cfg) -> list[dict]:
    pdf = pdfium.PdfDocument(path)          # raises PdfiumError "Incorrect password error" for user-password PDFs
    out = []
    for i in range(len(pdf)):
        page = pdf[i]
        w, h = page.get_size()
        tp = page.get_textpage()
        chars = tp.count_chars()
        text = tp.get_text_range()
        paths = [o.get_pos() for o in page.get_objects(filter=[pdfium_c.FPDF_PAGEOBJ_PATH], max_depth=1)]
        images = [o.get_pos() for o in page.get_objects(filter=[pdfium_c.FPDF_PAGEOBJ_IMAGE], max_depth=2)]
        out.append({"page": i + 1, "chars": chars, "text": text, "paths": paths, "images": images, "size": (w, h)})
        tp.close(); page.close()
    gated = [s["page"] for s in out if ruling_candidates(s["paths"]) >= cfg.min_ruling_paths or aligned_numbers(s)]
    if gated:
        with pdfplumber.open(path) as pl:
            for pn in gated:
                out[pn - 1]["ruled_tables"] = len(pl.pages[pn - 1].find_tables())
    return out
```

- **Gate on line-like paths, not on any path.** Real documents carry decorative rules, underlines and header bars. Count only path objects whose bounding box is thin (height < 2 pt or width < 2 pt), and gate on a minimum count (starting value 4, in `parse-routing.json`). Record the share of gated pages in `detect_counts`, so the 1 s target is visible on real samples.
- **Encryption.** Treat only a PDFium password error as `encrypted_pdf`. An owner-password-only PDF opened and returned its text [VERIFIED: executed with a reportlab-encrypted PDF].
- **Run preflight inside the process pool, with a time limit.** pdfminer and PDFium parse untrusted bytes (see Security).

### Pattern 4: Ranges (D-51, D-52) as a pure function

Input: per-page `(tier, preset, continuation_flags)` after `min_tier` and `max_tier`. Steps:

1. Run-length encode by preset.
2. Lift runs of fewer than 2 lower-preset pages between two higher runs.
3. Apply the boundary-table pull, repeated until the table ends.
4. If more than 20 ranges remain, or at least 60% of the pages are above `fast`, make one range at the highest non-premium preset.
5. Premium pages are never added or removed by these rules.

The output is `PageRange[]` and tiles `1..N`. Property tests: no page is lowered, the ranges tile `1..N`, and the result is idempotent and deterministic.

### Pattern 5: Merge (D-53) with `concatenate`

```python
# Source: docling-core 2.108.0 DoclingDocument.concatenate executed this session; Docling 2.152.0 keeps original page numbers
# for page_range conversions (Page(page_no=i + 1) for i in the range: pipeline/base_pipeline.py:363-366)
from docling_core.types.doc import DoclingDocument, Size

def premium_part(markdown_pages: list[tuple[int, str]], sizes: dict[int, Size]) -> DoclingDocument:
    doc = DoclingDocument(name="premium")
    for page_no, _ in markdown_pages:
        doc.add_page(page_no=page_no, size=sizes[page_no])   # REQUIRED, or later pages are renumbered (F-2)
    # convert each page's markdown into items (headings with level, tables, text) with prov.page_no = original page
    ...
    return doc

def merge(parts: list[DoclingDocument], n_pages: int) -> DoclingDocument:
    if len(parts) == 1:
        return parts[0]
    merged = DoclingDocument.concatenate(parts)               # parts in page order, tiling 1..N
    assert sorted(merged.pages) == list(range(1, n_pages + 1)), "merge_invariant:pages"
    return merged
```

Verified behaviour: three parts (pages 1-3 with "Chapter 1" and "1.1 Sub", page 4 plain text, page 5 "Chapter 2") chunked with `HierarchicalChunker` gave the page-4 chunk headings `['Chapter 1', '1.1 Sub']`. So the "first chunk of a range inherits the open headings" invariant holds without extra code, provided headings carry levels. In P3 03-15, heading-hierarchy inference is on for Docling. For premium parts, the LlamaParse v2 `items` give `heading {level}` (P3 research), which map to `add_heading(level=…)`.

Premium sub-PDF: `sub = pdfium.PdfDocument.new(); sub.import_pages(src, pages=[i-1 for i in premium_pages]); sub.save(buf)` [VERIFIED: executed, 3 pages extracted from 100]. LlamaParse numbers the sub-PDF from 1, so map `sub_page k → premium_pages[k-1]` before building the part.

For `json_docling` re-chunk (D-21), P3 03-15 already specifies that "a json_docling input re-chunks with no layout or OCR model". The merged cache entry is a Docling JSON, so the Phase 4 sweep reads it with zero conversions.

### Pattern 6: Quality check and escalation

`check(range_result, preflight_pages, profile) -> QualityCheckResult{per_page: [{page, failed: [conditions], score}], partial}` is pure and runs for every tier, including app-produced `native` and `premium` results sent back in the `parse-external` response.

- **Score** (for ranking attempts): `1.0 − 0.3·garbled_share − 0.3·low_char_flag − 0.2·missing_table_flag − 0.2·lang_flag`, clamped to 0..1 [ASSUMED: weights are starting values for the routing JSON].
- **Partial conversion:** Docling `ConversionStatus.PARTIAL_SUCCESS` [VERIFIED: enum values `pending`, `started`, `failure`, `success`, `partial_success`, `skipped` in docling 2.152.0 `base_models.py:88-94`]; LlamaParse `pages[].success: false` (P3 research).
- **Escalation unit:** each run of consecutive failing pages, plus any D-52 neighbour. Ladder `fast → structured → premium`, at most two escalations per page. Every step passes the guard first.

### Pattern 7: One guard, atomic budget

The guard lives in TS (`src/lib/rag/ingest/guard/cloud-budget.ts`). The order of its checks:

1. `RAG_PARSER_ALLOW_CLOUD` (live env, D-08)
2. tiered + queued only: `pages_needed > RAG_PARSE_PREMIUM_MAX_PAGES_PER_DOC` → `over_page_cap`
3. reserve

Reservation as one statement (no read-then-write race):

```sql
-- Single-statement conditional upsert; returns no row when the budget would be exceeded
INSERT INTO rag_parse_budget_usage AS u (tenant_key, month, pages_reserved)
VALUES (p_tenant_key, date_trunc('month', now() AT TIME ZONE 'UTC')::date, p_pages)
ON CONFLICT (tenant_key, month) DO UPDATE
   SET pages_reserved = u.pages_reserved + EXCLUDED.pages_reserved
 WHERE u.pages_reserved + u.pages_used + u.vlm_pages_used + EXCLUDED.pages_reserved <= p_limit
RETURNING u.*;
```

Two cases the plain upsert gets wrong:

- **First row of the month.** An `INSERT` of a new row is not checked by the `WHERE`, so the function first rejects `p_pages > p_limit`.
- **Lost reservations.** A crash between reserve and settle would strand the reserved pages. Keep a child row per reservation, `rag_parse_budget_reservations(job_id, attempt_no, tenant_key, month, pages, kind parse|vlm, created_at)`. Settle and release by `(job_id, attempt_no)`. The claim path releases a reclaimed job's open reservations. D-19's "reserve, settle, release" maps to these three functions.

With `p_limit = 0` (the D-17 default) every reservation fails, so `tiered` sends nothing to premium or L3. That is the intended default.

### Pattern 8: Tenant-scoped parse cache

**Key:** `(tenant_key, file_sha256, parser, parser_version, options_hash)` (D-20).

**Functions take a job id:** `rag_parse_cache_lookup(p_job_id, p_parser, p_parser_version, p_options_hash)` and `rag_parse_cache_put(p_job_id, …)` read `tenant_key` and `file_sha256` from the job row inside SQL, so neither the worker nor the app can pass another tenant's key (F-8 mitigation). For callers outside a job, such as the Phase 4 re-chunk, add an admin variant that takes `p_tenant_key` from a server-minted scope.

**Write order:** objects first, then the row (`ON CONFLICT DO NOTHING`). A reader trusts only rows. Orphan objects are garbage for the deferred GC.

**Path:** `rag-originals/<tenant_key>/_parse-cache/<file_sha256>/<parser>-<sha256(parser_version)[:16]>-<options_hash>/` (F-12). The colon in `u:<uuid>` is allowed by Supabase's key pattern (P3 research F-2).

**`options_hash`:** `sha256(json.dumps(opts, sort_keys=True, separators=(',', ':'), ensure_ascii=False).encode())`. It is computed only in Python (F-12). The page set is part of `opts` (D-56).

**Two-tenant test:** the same bytes under `u:A` and `o:B` → a miss for B, and B's conversion counter increments.

### Pattern 9: Backfill state machine (CLI)

`inventory → dedupe → sample (kind=dry_run, stops after checking) → report → [--budget fits?] → enqueue (priority 10, batch_id) → monitor → [batch_api: write → submit/poll → publish] → end report`.

- **`--resume <batch_id>`** re-reads the inventory and upserts by `(batch_id, source_key)`, so terminal jobs are untouched (D-34).
- **The CLI does not run jobs itself;** the worker or Ray does. The CLI only enqueues, monitors and drives the Batch API.
- **Folder source:** resolve every path with `realpath` and refuse paths outside the root (Security).
- **Projection formulas:**
  - wall time = Σ(pages_tier × s_per_page_tier) / effective_parallelism + callback overhead per document
  - cost = Σ(premium_pages × credits_per_page × usd_per_credit) + L3_pages × vlm_usd_per_page + est_tokens × embed_price (sync or batch)

### Pattern 10: OpenAI Batch API embeddings

**Facts** [CITED: developers.openai.com/api/docs/guides/batch]:

- "A single batch may include up to 50,000 requests, and a batch input file can be up to 200 MB in size."
- "/v1/embeddings batches are also restricted to a maximum of 50,000 embedding inputs across all requests in the batch."
- "the completion window can only be set to `24h`"
- "50% cost discount"
- Statuses: `validating`, `failed`, `in_progress`, `finalizing`, `completed`, `expired`, `cancelling`, `cancelled`.
- "the output line order may not match the input line order"; map results by `custom_id`.
- Output and error files expire after 30 days by default.

**Design:**

- One request line per chunk: `{"custom_id": "<chunk_id>:<embedding_text_version>", "method": "POST", "url": "/v1/embeddings", "body": {"model": …, "input": "<embedding text>", "dimensions"?: …}}`.
- Split by both limits (50,000 lines, and 190 MB as a margin under 200 MB).
- Upload with `purpose=batch`, then create the batch.
- Poll every 60 s from the CLI. Persist `provider_batch_id`, `input_file_id` and `status` in `rag_embed_batches` before the first poll, so a kill between submit and record cannot orphan a batch.
- On `completed`, stream the output file, validate dims against the profile, and write vectors through the P3 writer (03-28 path). Re-submit missing or errored `custom_id`s only.
- `expired` → resubmit the remaining inputs (D-35).
- Open risk: an org-level "enqueued tokens" limit per model may reject a large submission [ASSUMED]. Submit sequentially, at most `RAG_BACKFILL_OPEN_BATCHES` (CLI flag, default 2) open at once.

## Common Pitfalls

### Pitfall 1: Page renumbering on merge
**What goes wrong:** citations point to the wrong page after a mixed-tier merge.
**Why:** `concatenate` offsets each part by `max_page_so_far − min(part.pages) + 1` (F-2).
**How to avoid:** `add_page` for every page in every part, parts tile `1..N`, invariant assertion.
**Warning signs:** a premium page followed by pages whose numbers shift by one.

### Pitfall 2: pdfplumber on every page
**What goes wrong:** L1 takes seconds per 100 pages (7.3 s measured), and the latency target slips.
**How to avoid:** gate on thin path objects and aligned numbers; report the gated share.

### Pitfall 3: Upload latency starved by the Docling pool
**What goes wrong:** the claim slot is free, but the single conversion process is busy for minutes (F-5).
**How to avoid:** a priority queue plus backfill conversions sliced to ≤ 24 pages; a test with a long fake backfill conversion shows the upload's p95 stays under 60 s.

### Pitfall 4: A lost lease still writes
**What goes wrong:** a slow worker whose lease expired advances a job that another worker now owns; stages are duplicated.
**How to avoid:** every mutating ledger function checks `locked_by = p_worker AND lease_until > now()`; a heartbeat that returns `false` cancels the job task.

### Pitfall 5: Leaked budget reservations
**What goes wrong:** crashes between reserve and settle consume the month's budget.
**How to avoid:** per-attempt reservation rows, released by the reclaim path and by `rag_fail_ingestion_job`.

### Pitfall 6: Budget month in the server's local zone
**How to avoid:** `date_trunc('month', now() AT TIME ZONE 'UTC')` in SQL only; never compute the month in TS or Python.

### Pitfall 7: Progressive final skipped as a duplicate
See F-10. **Warning sign:** jobs stuck non-terminal with `provisional_published_at` set.

### Pitfall 8: Reaper fails queued documents
See F-15.

### Pitfall 9: Wake call delays the 202
**How to avoid:** send the wake in `after()` with a 1 s timeout and ignore every error. The poll loop is the guarantee.

### Pitfall 10: New Supabase keys sent as a Bearer token
See F-7. **Warning sign:** 401 from PostgREST only on projects that rotated to `sb_secret_` keys.

### Pitfall 11: `realtime.send` missing in PGlite
**How to avoid:** guard with `to_regprocedure` (verified). Never use `CREATE EXTENSION`-dependent code in the migration path PGlite loads.

### Pitfall 12: Batch output order
"the output line order may not match the input line order" [CITED]. Always join on `custom_id`; reject lines whose dims differ from the profile.

### Pitfall 13: `fixed` drift
Re-implementing the D-19 chain in Python changes the output (F-9). **Warning sign:** the defaults-differential test shows chunk-hash differences.

### Pitfall 14: Hostile PDFs in the worker process
**What goes wrong:** PDFium (C) and pdfminer parse untrusted input. A crafted file can hang or crash the parser.
**How to avoid:** run preflight and conversions in the pool processes with a wall-clock limit (`document_timeout` for Docling, a per-call deadline for L1), plus a size limit and the page cap. A crashed pool process fails the attempt as retryable (counted), not the worker.

### Pitfall 15: Callback storms during a large backfill
Each document costs at least one `advance` call, plus more for large documents and premium ranges. That is invocations and GB-seconds on Vercel.
**How to avoid:** a worker-side token bucket for app calls (shared with Ray), `RAG_APP_INTERNAL_URL` allowed to point at a self-hosted `next start` for big backfills [ASSUMED: acceptable operationally], and `batch_api` mode so `advance` does no embedding.

### Pitfall 16: Deployment protection blocks callbacks
Vercel preview deployments can require auth for every request [ASSUMED]. Point `RAG_APP_INTERNAL_URL` at the production domain, or at a protection-bypass URL; `/ready` checks reachability of `GET <app>/api/health`-style endpoints (or the callback route with a dry `HEAD`).

## Latency Budget

### Target

D-45: p95 from 202 to `ready` ≤ 60 s for a digital PDF of at most 20 pages, with fake providers.

### Per-step allocation

Ingestion is not on the chat or voice path, so the retrieval budgets of Phases 2 and 4 are unaffected.

| Step | Budget (p95) | Basis |
|---|---|---|
| Route: identify, hash, store original, enqueue, 202 | 3 s | 20 MB max upload; storage write |

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-tenant parse-cache hit leaking content | Information disclosure | Tenant in key and path; lookups take `job_id` and derive tenant in SQL; two-tenant test |
| Worker or caller forging a tenant in callbacks | Elevation of privilege | Worker never sends tenant; app mints scope from the ledger row |
| Stolen sidecar secret calls internal routes | Spoofing | Constant-time compare; secret ≥ 32 chars (sidecar settings rule); routes act only on existing job ids; rotate on suspicion |
| Service-role key exposure from the sidecar | Information disclosure / EoP | Secret store only; no header logging; backlog: restricted role (F-8) |
| PDF parser DoS / memory corruption | Denial of service | Process isolation, `document_timeout`, L1 deadline, size limit and page cap, retry counting so a poison file ends `failed` |
| Budget exhaustion by one tenant | DoS (cost) | Per-tenant monthly budget, per-document cap, batch `--budget` |
| SSRF through backfill manifest `url` | Tampering / info disclosure | https only, no redirects to private ranges, admin-run CLI; prefer `path` and bucket sources |
| Realtime eavesdropping on other tenants' status | Information disclosure | Private channels, RLS on `realtime.messages` by topic, payload ids/status only, "Allow public access" off |
| Replay of an `advance` call | Tampering | Idempotent per `(job, stage, cursor)`; lease owner check |
