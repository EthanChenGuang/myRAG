# Phase 03.1 Plan 43: Progressive mode Summary

**With RAG_PARSE_PROGRESSIVE on, an eligible incremental PDF is parsed fast end to end and published as a searchable provisional version, then the routed parse is published as version 2 through the Phase 3 swap. If the routed text matches the provisional one, the flags are cleared in place and no new version is created. With the switch off, or for a backfill job, nothing changes.**

## Accomplishments

- `progressive.eligible(preflight, snapshot, kind)` and `job_kind(job)`. A job is backfill when it has a `batch_id` or is not `ingest`. It is eligible only when `snapshot.progressive` is on, some page's tier is above fast, and at least half the pages have a text layer.
- **Worker flow:** `tiered._run_pdf` runs `progressive.publish_provisional` after preflight for an eligible job with no `provisional_published_at`. That step:
  - parses pages 1..N with the fast preset and records the attempt with reason `progressive_fast` and its cost;
  - merges the result and chunks it once into its own merged entry;
  - calls `_advance_until_done(..., provisional=True)`.

  The routed ranges then run as before. If the provisional run ends the job (for example quarantined or failed), the routed run is skipped. A reclaimed job that already published provisionally runs only the routed flow.
- **App (`handleAdvance`):**
  - `provisional:true` is accepted only when the snapshot qualifies. A repeated provisional call after the mark answers the same way.
  - After the publish stage (including a replay from cursor `publish`), `rag_mark_provisional` flags the document and its chunks, sets `provisional_published_at` and puts the job back at stage parse with no cursor.
  - On the routed run's first call, `startProgressiveFinal` runs the A-9 check and either clears the flags and ends the job, or begins version N+1 and moves the job to it.
- **SQL 0358:** three functions. Each is SECURITY DEFINER with `search_path = ''`, resolves the tenant from the job row (A-6), is revoked from PUBLIC, anon and authenticated, and is granted to service_role. All three are also added to the 0410 upgrade lockdown.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Two SQL functions beyond rag_clear_provisional**
- **Issue:** `rag_advance_ingestion_job` sets `document_id` only while it is null, and nothing could set `documents.provisional` or `document_chunks.provisional`.
- **Fix:** Added `rag_mark_provisional(job, worker)` and `rag_begin_progressive_final(job, worker, document)`. Both check the lease, take the tenant from the job and validate everything: same lineage, newer version, processing, not current, snapshot qualifies.
- **Commit:** f74ee263

**2. [Rule 3 - Blocking] Contract field `AdvanceRequest.provisional: bool = False`**
- **Fix:** Pydantic field added, JSON Schema, Zod and samples regenerated (`gen:schemas` leaves no diff). `handleAdvance` takes `AdvanceBody` (provisional optional) so callers that build the body without the route default still type-check.
- **Commits:** f74ee263, 9625e78a

**3. [Rule 3 - Blocking] 0410 lockdown**
- **Issue:** `tests/rag-db/search-rpc-grants-pglite.test.mts` replays an upgrade with open grants and requires 0410 to close every SECURITY DEFINER function, which is the 0357 precedent.
- **Fix:** The three functions are added to 0410's guarded list, in alphabetical order.
- **Commit:** 40d5b7e9

**4. [Plan difference] No version-2 row in the same-text case**
- **Issue:** The plan's flow begins the routed version and lets `content_hash_dedup` find the duplicate. That leaves a deleted version-2 row behind, and it moves the job off the provisional document id for the whole routed parse.
- **Fix:** The same-lineage check runs on the routed text before any row is begun, so "no version 2" holds literally.

**5. [Test environment] Broken recording of the scanned page**
- **Issue:** The recorded `fast/page-9.json` of mixed-routing has body references to texts that do not exist. Docling cannot load it, and only the full fast parse reads it.
- **Fix:** The e2e test uses a temporary copy of the recordings that keeps only the references that resolve. `eval/fixtures/parse` is left untouched.
- The same-text case uses a copy whose fast pages 7-9 equal the routed recordings. An empty OCR page would fail the routed check and end `needs_review`.

**6. [Test harness] One harness for the whole file**
- **Issue:** The Supabase admin client is a process singleton bound to the first edge, so a second harness in the same process could not store objects.
- **Fix:** The Task 1 jobs are enqueued with fixed routing through a `queueConfig` override.

**Total deviations:** 3 auto-fixed blocking issues and 3 plan, environment or harness differences. **Impact:** progressive mode needs all of them; nothing was added outside the plan's scope.

## Known Limitations

- **Routed duplicate of another lineage:** Phase 3 `skipped_duplicate` applies. The provisional version stays current with its flag, and the job is terminal.
- **Routed run fails or is quarantined:** the provisional version stays current with its flag. A retry runs the routed flow only.
- **`documents.parse_cache_id`:** reading the routed cache entry for the A-9 check links it to the provisional version through `rag_set_document_parse_cache` before the routed version is begun.
- **Status by document id:** once the job has moved to version N+1 (the routed post-parse stages only), the D-45 route by the provisional document id no longer finds the job. The job-id route reports `provisional` throughout.
- **processing_status mirror:** while the routed ranges are parsed, the ledger mirror sets the provisional version's `processing_status` to parsing while its status is ready, which matches "searchable, still improving".
