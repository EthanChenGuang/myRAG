# Phase 3.1 Plan 38: Chat upload status UI Summary

**Queued knowledge-base uploads now show a live status badge (polling, with optional private Realtime) until ready, instead of being failed by the dashboard timeout.**

## Accomplishments

- `useIngestJobStatus` polls `GET /api/rag/ingest/jobs/{id}` at 2 s (10 s after 60 s), stops on terminal states, aborts the in-flight request on unmount, and keeps polling through network errors and 5xx with a doubling delay capped at 10 s.
- With `NEXT_PUBLIC_RAG_INGEST_REALTIME=true` it also follows the private `rag-ingest:<tenant>` channel; with the default `false` it never calls `channel()`. One channel is shared per topic and closed with the last listener. A denied subscription drops the channel and polling continues.
- `IngestStatusBadge` and `TrackedIngestStatusBadge` render each status with zh, en and it labels, an accessible name, and the "searchable, still improving" text for a provisional job that is still running.
- A 202 with a `jobId` adds a processing row that carries the job and renders the badge; the upload loop moves on to the next file immediately. `ready` replaces the row with the normal row after a list refresh; `needs_review` and `failed` rows stay visible. The 45-minute processing safety timeout and the list refresh no longer fail or replace queued rows. A 200 response and a 202 without a `jobId` keep today's behaviour (the 03-42 document status poll).
- `unified-upload-button.tsx` shows the badge for a queued upload and clears it 4 s after ready.
