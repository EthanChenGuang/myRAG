# Phase 03.1 Plan 24: Admin ingest routes Summary

Five admin routes over the ingestion ledger, the monthly parse budget and the D-13 tier overrides, each gated by `checkAdmin` before any ledger call and scoped to the caller's workspace.

## Accomplishments

- `GET /api/rag/admin/ingest-jobs`: repeated `status`, `kind`, `limit` (1-100), opaque keyset `cursor`, optional `organizationId`. Rows are the 20-field operator allow-list (`projectJob`); `original_ref`, `settings`, `stage_state`, `source_key`, `file_sha256`, `locked_by`, `timings` and `trace_id` never leave. Every row carries `kind`, so a `dry_run` job that ended `ready` is labelled as such.
- `GET/DELETE /api/rag/admin/ingest-jobs/{id}` and `POST .../{id}/retry`: detail adds `attempts` and `page_ranges`. Retry and delete call `retryJob` / `deleteJob` with the guard's verified user id as actor (the body is never read). Not-retryable (status other than failed or needs_review) and not-deletable (current document) answer 409.
- `GET /api/rag/admin/parse-budget`: this UTC month's reserved, used and L3 pages for the workspace tenant plus the configured monthly budget and per-document cap.
- `GET/PUT /api/rag/admin/parse-tiers`: every doc type with profile bounds, override and effective bounds; PUT validated with zod/v3 (tier names, min not above max, both null clears, strict body so an `actor` field is rejected).
- All responses `Cache-Control: no-store`; failures are structured JSON; database messages are never echoed or logged.

## Deviations from Plan

**1. [Rule 2 - tenant isolation] Workspace-scoped instead of deployment-wide job list and budget**
- **Found during:** Task 1
- **Issue:** The plan text says the list spans every tenant ("deployment-scoped, as for quarantine in 03-37"). The 03-37 quarantine precedent and the SQL `rag_retry_ingestion_job` / `rag_delete_ingestion_job` actually limit the actor to `rag_admin_tenant_keys` (own tenant plus organizations the admin owns or administers). The executor brief also required every read and write to be tenant-scoped with two-tenant tests.
- **Fix:** List, detail, retry, delete and the budget read resolve a workspace with `resolveAdminWorkspaceScope` (personal or the single-tenant default, or `?organizationId=` after the membership check) and use `listJobs` / `getJobForScope` with that scope. The tenant filter the plan names is this `organizationId` choice. The route-level lookup runs before the SQL call, so a foreign id is a 404 identical to an unknown id and no retry/delete RPC is issued. T-03.1-124 is therefore mitigated more strongly than planned.
- **Files modified:** all five route groups, `_lib.ts`
- **Commit:** 6617ee0, 72f0769

**2. [Rule 3 - blocking] `readMonthlyUsage` from guard/cloud-budget.ts does not exist yet**
- **Issue:** Task 2 says to read budget numbers through the guard's `readMonthlyUsage()` (plan 03.1-19), which is not merged in this base; plan 03.1-19 is not in `depends_on`.
- **Fix:** `src/lib/rag/ingest/parse-admin.ts` calls the existing read-only `rag_parse_budget_month` RPC (not in the `budget-rpc` boundary list; the boundary check passes). Config numbers come from `queueConfigFromProcessEnv()`.
- **Follow-up:** when 03.1-19 lands, repoint `readBudgetView` at `readMonthlyUsage` and drop the duplicate RPC call.

**3. [Rule 3 - blocking] Pagination**
- The plan asks for keyset pagination, but `rag_list_ingestion_jobs` only takes limit and offset and no migration is in scope. The cursor is `(created_at, id)`, applied app-side by scanning pages until the cursor is passed (cap 10000 rows, then 400 "Cursor is too far back"). Comparison is at millisecond precision. A newer job arriving between pages does not shift the next page (tested).

**4. Retry and delete refusals**
- The ledger maps every SQLSTATE 22023 message to code `ingest_refused`, so job_not_found, invalid_status and document_is_current are indistinguishable after the call. The routes pre-check the job in the workspace (404) and, for retry, its status (409 `not_retryable`), then treat a later `ingest_refused` as 409 (`not_retryable` / `not_deletable`). One edge: a mere member (not owner/admin) of an organization sees the org's jobs in the list but gets 409 on retry/delete, because the SQL function requires owner or admin.
