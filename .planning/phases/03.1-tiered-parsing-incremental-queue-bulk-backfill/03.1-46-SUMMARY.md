# Phase 03.1 Plan 46: Backfill run engine Summary

**Backfill jobs are enqueued without a document row and get their processing version when the worker first claims them (advance phase begin). `enqueueRun`, `monitor` and `endReport` run a batch on the same worker and ledger as uploads. A worker killed mid-run is restarted and finishes the batch without touching ready jobs. Batch jobs now share the worker's slots instead of waiting for an idle worker.**

## Accomplishments

- **Advance phase begin (`advance.ts`).** For a batch ingest job without a document id, begin:
  - reads the staged original (rag-originals, job tenant prefix) and checks its sha256 against the job;
  - runs identify, file_hash_dedup and store_original for the job's tenant with its filename, MIME type and the snapshot's doc type;
  - stores the queued-input record and records `document_id` on the job (stage preflight).

  A file the tenant already has ends the job `skipped_duplicate` before any parse. A repeated call is safe.
- **Worker (`process_job.py`).** The worker calls begin before preflight for a batch ingest job without a document id. If begin ends the job, its outcome is returned. Dry runs, incremental jobs and reclaimed jobs that already have a document skip it.
- **`run.ts`:**
  - `enqueueRun(batch, entries, { snapshot, kind })` stages each file and enqueues backfill-snapshot jobs at priority 10. It is re-entrant per (batch, kind) and refuses files that changed or grew too large since the inventory.
  - `monitor` polls `rag_batch_progress` until no job is open.
  - `endReport` and `releaseStagedOriginals` close out the batch (see key-decisions).
  - Every entry point refuses a batch of another tenant.
- **`buildQueuedContext`** falls back to the version's own `original_path` when the job keeps its staged ref.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Embed mode in the job snapshot contradicted D-35**
- **Issue:** `buildJobSettings` gave every backfill job with an OpenAI profile `batch_api`, even with `RAG_EMBED_BATCH_MODE=sync` (the default). It also gave incremental jobs `batch_api` whenever the switch was on.
- **Fix:** `batch_api` only for backfill + `batch_api` + OpenAI; everything else is `sync`. Nothing consumes `embed_mode` yet (03.1-49 will).
- **Commits:** ea55497f, 6db1370f

**2. [03.1-43 follow-up, as briefed] enqueueIngest never marked a batch job as backfill**
- **Fix:** `isBackfill` is set when `batchId` is given, and the embedding provider comes from the active profile. A registry read failure gives `unknown`, so the job embeds in sync.
- **Test:** e2e "a batch job snapshot is a backfill snapshot".
- **Commits:** e823d07a, 09555953

**3. [Coordinator decision, after 03.1-45] Backfill starvation under steady uploads**
- **Issue:** `IngestWorker._claim_slots` allowed a batch claim only while `slots_left > 1`. With uploads waking the worker, the first slot took the upload and the second refused the batch job, so backfill throughput was zero. Also, a worker with concurrency 1 never claimed a batch job at all, not even when idle (`slots_left > 1` is never true).
- **Fix:** a batch job may be claimed whenever a slot is free and fewer than concurrency − 1 batch jobs run. Uploads still win each claim by priority. At concurrency 1, a batch job is claimed only when the worker is idle.
- **Commits:** 72035988, 592475ee

**4. [Rule 3 - Blocking] Fake edge storage bulk remove**
- **Issue:** `storage.from(bucket).remove([...])` sends `DELETE /storage/v1/object/<bucket>` with `prefixes`, which the fake edge answered with 404.
- **Fix:** added that route.
- **Commit:** bba7033a

**5. [Test environment] LlamaParse fake answers every upload the same way**
- **Issue:** The chain sends `.txt` files to LlamaParse before the plain-text parser, so every fixture version had the same text and became a content duplicate.
- **Fix:** the test queues 400 distinct page specs so each upload gets its own text.
- **Commit:** 09555953

**6. [Plan difference] Bucket sources are staged, not read in place**
- **Why:** begin and the worker read one private bucket under the tenant prefix, and every version keeps its own copy as in Phase 3.
- **Cleanup:** `releaseStagedOriginals` removes staged files after the run.

**7. [Plan difference] Plan signature `enqueueRun(batch, entries, snapshot)`**
- **Shape:** `enqueueRun(batch, entries: RunEntry[], { snapshot: () => QueueConfig, kind, signal })`. `RunEntry` is an `InventoryEntry` plus the source item's `open`.
- **Why:** the snapshot is built per doc type, and `kind: 'dry_run'` serves the 03.1-48 sample.

**Total deviations:** 4 fixes (one of them the coordinator item) and 3 environment or plan differences. No migration was needed; 0359 stays reserved for 03.1-49.

## Known Limitations

- **Chunk-write batches** are sized by bytes (about 1 MB, at most 33 rows at 1536 dims), not by a row count. The writer spy confirms at most 300 rows per call. A row cap would only bind for vectors under about 160 dims; none is added.
- **Profile dual-write (03-28)** applies to backfill jobs because they run the unchanged write stage. This plan's e2e does not set up a `backfilling` profile; it checks that nothing calls `rag_activate_embedding_profile`.
- **Doc type origin:** a backfill version records origin `picked` (the snapshot's type). A name-detected type is therefore not refined from the parsed text, as an `auto` upload would be.
- **Lineage columns:** `ingestion_jobs.lineage_id` and `version` stay null for backfill jobs, as they do for incremental jobs.
