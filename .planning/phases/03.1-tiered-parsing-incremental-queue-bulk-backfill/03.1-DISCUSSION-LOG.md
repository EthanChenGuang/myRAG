## Spec change during the discussion (commit 0f6c414)

The coordinator reported that the spec and DATA-12 now route per page with three detection layers. The areas below were added and the earlier per-file decisions (D-11, D-12, D-14, D-15, D-16, D-20, D-38) were rewritten; everything else was kept.

## Per-page routing and page-tier mapping

| Option | Description | Selected |
|--------|-------------|----------|
| Tier plus option preset per page (`fast`, `structured_layout`, `structured_full`, `structured_ocr`, `premium`) | Follows the spec's page-tier rule; ranges group pages with the same Docling options | ✓ |
| Tier only, one Docling option set for every `structured` page | Fewer ranges, but multi-column pages pay for TableFormer and scanned pages are not forced to full OCR | |

**Choice:** `[auto]` Tier plus preset (recommended default).
**Notes:** The spec sends scanned pages to `structured` with OCR unless `min_tier` is `premium`. ROADMAP success criterion 1 still says a fully scanned PDF goes to `premium`; the test reaches `premium` through a `min_tier` override.

## Detection layers L1 to L3

| Option | Description | Selected |
|--------|-------------|----------|
| pdfplumber only on pages with line objects or aligned columns; L2 on uncertain pages; L3 only on L1/L2 disagreement, through the app | Keeps the L1 speed target; the vision-model key and the cloud guard stay in one place | ✓ |
| pdfplumber on every page | Simplest reading of the spec, but likely misses "under 1 s for 100 pages" | |
| L3 called from the sidecar | One hop fewer, but a second cloud guard and model keys in the sidecar | |

**Choice:** `[auto]` First option (recommended default).
**Notes:** On disagreement without L3 the higher tier wins. One L3 page uses one page of the monthly premium budget, counted apart; a blocked L3 call never fails a job.

## Range building and boundary tables

| Option | Description | Selected |
|--------|-------------|----------|
| Lift-only smoothing, and pull the neighbour page into the higher preset before and after parsing | Limits fragmentation without lowering any page; relies on Docling for the table itself | ✓ |
| No smoothing | A document that alternates page by page becomes dozens of conversions | |
| Build a table stitcher across ranges | Handles tables without re-parsing, but is a new component with its own errors | |

**Choice:** `[auto]` First option (recommended default).

## Merging ranges

| Option | Description | Selected |
|--------|-------------|----------|

## Ledger versus Phase 3 stage state

| Option | Description | Selected |
|--------|-------------|----------|
| Supersede for queued jobs, keep Phase 3 state for inline runs | One authority per run; `processing_status` kept as a mirror; defaults write no ledger row | ✓ |
| Write the ledger for every unified run, inline included | Uniform reporting, but two copies of stage state in inline mode and a behaviour change with the defaults | |
| Keep state on the document row and make the ledger a log | Contradicts Phase 3 D-02, which says 3.1 moves the state | |

**Choice:** `[auto]` Supersede for queued jobs (recommended default).
**Notes:** Phase 3 D-02 already announced the move. Keeping inline runs untouched preserves the "switch off = Phase 3 behaviour" rule.

## Where stages run

| Option | Description | Selected |
|--------|-------------|----------|
| Split by where the single implementation lives | Worker does preflight, routing, Docling tiers and the check; the app does native and premium parse and all post-parse stages through callbacks | ✓ |
| Thin worker that only drives app callbacks | Simplest, but Docling could not run inside Ray actors, so the Ray runner would add nothing | |
| Re-implement chunking, embedding and writing in Python | Breaks Phase 3 D-04's single chunk writer and duplicates the embedding registry | |

**Choice:** `[auto]` Split by implementation (recommended default).
**Notes:** Phase 3's stages are TypeScript and the spec puts the worker in Python. The callback is the only way to honour both without duplicate code. Throughput of the callback under a very large backfill is a research question.

## Ledger access from the sidecar

| Option | Description | Selected |
|--------|-------------|----------|
| SQL functions over PostgREST RPC with the service-role key | Same call path in Supabase and in the PGlite fake edge; no database driver in the sidecar | ✓ |
| Direct Postgres connection from the sidecar | True `SKIP LOCKED` sessions, but a new driver, pooler issues and no PGlite test path | |
| Sidecar asks the app to claim jobs | Keeps the sidecar stateless, but adds a hop to every claim and heartbeat | |

**Choice:** `[auto]` SQL functions over RPC (recommended default).
**Notes:** This amends Phase 3 D-20's "stateless towards Supabase" for the worker module only. A restricted role is to be evaluated.

## Hard-constraint defaults and enforcement

| Option | Description | Selected |
|--------|-------------|----------|
| Cloud allowed `true`, premium budget `0`, cap `200`; one guard at the LlamaParse client | Defaults equal today; premium cost must be opted into under tiered | ✓ |
| Cloud allowed `false` by default | Would turn off today's default parser | |
| Unlimited premium budget by default | Cost could run away the first time tiered is switched on | |

**Choice:** `[auto]` First option (recommended default).
**Notes:** "Every switch defaults off" was read as "defaults to current behaviour". The cloud switch applies in every mode; the budget and cap apply to queued tiered jobs.

## Backfill

| Option | Description | Selected |
|--------|-------------|----------|
| USD budget, dry run always first, stratified sample that grows until each class has 20 | Known cost before the run; preflight is not needed on every file | ✓ |
| Preflight every file during inventory for exact class shares | Exact, but every file must travel to the sidecar before any decision | |
| Budget in premium pages | Ignores embedding cost | |

**Choice:** `[auto]` First option (recommended default).
**Notes:** The spec says "1% of files, at least 20, per class", but the class is only known after preflight. The sample is therefore stratified by extension and size and grown until each observed class reaches 20.
