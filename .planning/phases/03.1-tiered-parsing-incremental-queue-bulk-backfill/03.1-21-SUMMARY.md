# Phase 03.1 Plan 21: Legacy cloud-off guard Summary

RAG_PARSER_ALLOW_CLOUD=false now holds in the default legacy pipeline: the two LlamaParse call sites refuse before any request, with default behaviour unchanged.

## What was built

- `process-document/route.ts`: `assertCloudAllowed('parse')` before the LlamaParse block (knowledge-base uploads and `isTemporary` attachments) returns `503 { error: 'cloud_parsing_disabled' }`, logs `[Ingest] cloud parsing disabled` without a file name, and persists nothing. A second check inside `uploadToLlamaCloud` (defence in depth) maps a `CloudRefused` to the same 503. The 401/403 session and organization checks run first.
- `document-processor.ts`: `requireCloudParsing()` runs in `processDocument` for non-Markdown files before the temp file is written, and again at the top of `uploadAndParseDocument`. It throws `CloudRefused` with message `cloud_parsing_disabled`; Nango's existing per-file catch stores that as the failure reason and moves to the next file.
- `src/lib/rag/index.ts`: exports `assertCloudAllowed` and `CloudRefused` (the boundary check forbids deep imports from outside `src/lib/rag`).
- `tests/rag/legacy-cloud-guard.test.ts` (12 tests): fetch-spy counts show zero LlamaParse requests with cloud off for temporary (legacy and unified) and knowledge-base uploads, for `processDocument`, and for the Nango adapter under legacy; no copy of the file is left on disk; no session still returns 401; the log carries no file name; with the switch unset or `true` the route and processor still parse and store as before; Markdown stays local with cloud off.
