<domain>
## Phase Boundary

This phase builds an end-to-end, reproducible pipeline that fine-tunes an open embedding model on a deployment's own knowledge base and puts it into production only through the existing embedding-profile gate (EMB-02 to EMB-05):

1. **Training data**: an LLM writes about three queries per chunk (zh/en/it, tenant-scoped, opt-in per tenant), plus real expert-confirmed pairs mined in Phase 5.1.1.
2. **Filtering**: drop queries the chunk cannot answer (LLM answerability judge), near-duplicates, and queries that copy the chunk (character n-gram containment); drop anything that duplicates a golden question.
3. **Hard negatives**: mined with the current production model (its stored vectors plus query vectors from `@/lib/rag`) or any sentence-transformers model, with a relative margin and false-negative guards.
4. **Training**: `CachedMultipleNegativesRankingLoss` (GISTEmbed and Matryoshka optional) with sentence-transformers on an operator GPU box or a hosted GPU container; the repo holds the configs, the training image, the data export and the evaluation. Unit tests run on CPU with fakes or a tiny in-test model.
5. **Split and evaluation**: document-level split (never pair-level), offline Recall@10 / MRR@10 / nDCG@10 against the base and the production model, then the unchanged EMB-05 gate (`rag_record_eval_evidence` → `rag_activate_embedding_profile`) on the domain golden set.
6. **Serving**: two fixed fine-tune slot profiles (`ft-a-1024`, `ft-b-1024`, halfvec + partial HNSW), an OpenAI-compatible endpoint provider, a probe check that proves the endpoint serves exactly the registered model, full re-embed via `npm run rag:reembed`, activation and rollback by the profile pointer flip.
7. **Governance**: per-tenant consent (opt-in, recorded with an evidence reference), model registry and versions with the tenant list each model was trained on, revocation that taints models, retention and pruning of text-bearing bundle files.

In scope: FT-01 to FT-10 (new, see `REQUIREMENTS-ADDITIONS.md`), consuming EMB-01 to EMB-05, EVAL-14, XLG-02, Phase 3.1.1 bindings and Phase 5.1.1 `TrainingPair` exports.

Out of scope:
- A per-tenant *global* active-profile pointer. Tenant-private models are served instead through Phase 3.1.1's per-tenant, per-doc-type bindings (D-33); the global pointer stays deployment-wide.
- The binding mechanism itself (scoped profiles, `embedding_profile_bindings`, binding gate, binding legs in search): Phase 3.1.1 owns it; this phase only scopes a slot and guards which bindings a fine-tuned slot may get (D-33).
- Producing the mined pairs and the real test set: Phase 5.1.1. This phase consumes 5.1.1's `TrainingPair` export (`GET /api/rag/admin/feedback-loop/export?kind=training`, NDJSON, no chunk text) as is.
- Reranker fine-tuning, LoRA on Qwen3-Embedding-4B/8B, slots with other than 1024 dims, a Config UI consent panel, online/continual training.
- Changing `rag_activate_embedding_profile`, `rag_record_eval_evidence` or the re-embed functions: they are reused unchanged (Phase 7 plans 0705/0706 also extend the activation gate; this phase must not collide with them).

<decisions>
## Implementation Decisions

### Placement and switch
- **D-01:** The pipeline is an operator CLI, `uv run --directory eval python -m rag_eval.finetune <command>`, in a new package `eval/src/rag_eval/finetune/`. Its structured outputs are Pydantic v2 models in `rag-sidecar/src/rag_sidecar/contracts/finetune.py`, exported to JSON Schema and Zod by `npm run gen:schemas` and checked in CI like every other contract. The app never calls the pipeline at request time, so no sidecar HTTP route is added (the HTTP rule is for app→Python calls). TypeScript code is added only where the pipeline must touch embeddings or the database: `src/lib/rag/finetune/` (vector and query-vector export through `@/lib/rag`, so `scripts/ci/check-rag-boundary.mjs` stays green) and the slot provider in `src/lib/rag/embeddings/`.
- **D-02:** Master switch `RAG_FINETUNE=off|on`, default `off`. Off: the slot providers are not registered (a slot profile cannot pass the startup check and cannot be activated), `npm run rag:finetune` and every `rag:embedding -- ft-*` command except `ft-consent list` and `ft-models list` refuse, and the Python `export` refuses. The slot profile rows exist with status `available` and model `unbound` and are never searched. With the switch off, eval, chat, embed and voice behave exactly as today (parity test in 06.1-18).
- **D-03:** Commands. Python: `export`, `generate`, `filter`, `import-mined`, `mine`, `kit` (training kit), `train`, `evaluate`, `card`, `prune`, `run --fixture`. TypeScript (`npm run rag:finetune --`): `export-vectors`, `embed-queries`. TypeScript (`npm run rag:embedding --`): `ft-consent grant|revoke|list`, `ft-models register|list|retire`, `ft-bind`, `ft-clear`, `ft-release-rollback`, `ft-check`.

### Training data
- **D-04:** Generation writes `queries_per_chunk = 3` queries per chunk (config): one keyword-style short query, one natural question, one colloquial paraphrase that avoids the chunk's own terms. The query language is the chunk's language. A configurable share (`cross_language_share = 0.15`) of chunks gets one extra query in another of zh/en/it, so cross-lingual retrieval (XLG-02 pairs) is trained too. The LLM returns a Pydantic `SyntheticQueryBatch` through tool use. Chunks under `min_chunk_tokens = 40` are skipped and counted.
- **D-05:** The LLM client follows the existing Anthropic drafting client (`eval/src/rag_eval/draft/claude_drafter.py`) behind a `QueryLLM` protocol with a deterministic fake for tests. The model ids come from `eval/config/finetune.json` (`generator_model`, `judge_model`, both defaulting to the value `eval/config/draft.json` already pins). No model id is hard-coded in code.
- **D-06:** Cost control mirrors the backfill rule (DATA-16): `generate`, `filter` (judge) and the FN audit refuse to run without `--budget-usd`; `--dry-run` projects tokens and cost from character counts and the price table in `finetune.json`; a run stops cleanly when the budget is spent and resumes from a cache keyed by `(chunk content hash, prompt version, model)`.
- **D-07:** Filters run in this order and every drop is counted per reason and language in a `FilterReport`:
  (a) shape: language matches the requested one (existing `rag_sidecar.ingest.lang` detector), length within `[min_query_chars, max_query_chars]` per language;
  (b) verbatim copy: after NFKC + case folding + whitespace removal, the share of the query's character 5-grams found in the chunk is at least `verbatim_containment = 0.6`, or the longest common substring is at least `0.7 ×` the query length → `verbatim_copy` (character n-grams work for Chinese, which has no spaces);
  (c) near-duplicate: exact normalized duplicates inside a tenant, and character 3-gram Jaccard ≥ `near_dup_jaccard = 0.8` among the queries of one chunk → keep the first;
  (d) answerability: an LLM judge returns `AnswerabilityVerdict {answerable, confidence}` for (query, chunk); drop when not answerable or `confidence < 0.7`;
  (e) round-trip consistency (the production model must rank the query's positive within top-k) is available as `mine --round-trip-k K` (it needs the production query vectors, which exist only at mining time) and is **off** by default, because it keeps only queries the current model already finds and so removes the cases fine-tuning should fix.
- **D-08:** Real pairs: `import-mined` reads Phase 5.1.1's NDJSON export whose rows validate 5.1.1's `TrainingPair` contract (`{tenant_key, query_masked, language, positive {chunk_id, document_id, quote}, hard_negatives [{chunk_id, document_id, rank, score}] (≤ 10), document_group, split: train|held_out, source: production_feedback, review_item_id}`; 5.1.1 CONTEXT D-17). Text is resolved by chunk id from this phase's bundle of the same tenant. `held_out` pairs never train and go to the fine-tune test set; a `train` pair whose positive document falls in this phase's test split also goes to test (the stricter rule wins). The expert-rejected `hard_negatives` are used first as negatives (they are confirmed non-relevant), topped up by the miner. Mined pairs skip the answerability judge but pass filters (a) to (c) and decontamination, are up-weighted by repetition `mined_weight = 2`, and are reported as the "real" slice in every evaluation. This phase's own pair contract is named `FinetunePair` to avoid a Zod name clash with 5.1.1's `TrainingPair`.
- **D-09:** Decontamination: any training query (synthetic or mined) whose normalized text has character 3-gram Jaccard ≥ 0.8 with any golden question (all splits, all provenances, `eval/fixtures/golden.jsonl` plus the private golden file when present) is dropped as `golden_overlap`. Every document that holds gold evidence of a `test`-split golden item is forced into the fine-tune `test` split and never trained on.

### Split
- **D-10:** Document-level split. `bucket = int(sha256(f"{tenant_key}:{split_key}")[:8], 16) % 100` with `split_key` = the document's `content_hash` when present (so duplicate documents share a split) else the document id; `< 80` train, `80–89` dev, `90–99` test; D-09 forces test. A pair's split is its positive chunk's document's split; a mined query cluster (3-gram Jaccard ≥ 0.8) takes the split of its first member's document. Hard negatives of train pairs come only from train-split documents (test text never enters training, even as a negative). The rule string `ft-sha256-first8hex-mod100-80-10-10` is recorded in the dataset manifest.

### Hard-negative mining
- **D-11:** Default miner `vectors` = the current production model: corpus vectors are the active profile's stored vectors (`npm run rag:finetune -- export-vectors`), query vectors are the active profile's query embeddings through `@/lib/rag` (`embed-queries`); a NumPy implementation mirrors the semantics of `sentence_transformers.util.mine_hard_negatives` (`range_min`, `range_max`, `max_score`, `min_score`, `absolute_margin`, `relative_margin`, `num_negatives`, `sampling_strategy`). Defaults: `relative_margin = 0.05` (NV-Retriever TopK-PercPos 95%, the setting the sentence-transformers docs recommend), `range_min = 0`, `range_max = 50`, `num_negatives = 5`, `sampling_strategy = "top"`. It runs on CPU on this machine. Second miner `st`: delegates to `sentence_transformers.util.mine_hard_negatives` with any ST model (the base model, or the previous fine-tuned version for an iteration), `output_format="n-tuple"`, and the query/corpus prompts; a parity test checks both miners agree on a tiny in-test model.
- **D-12:** False-negative guards on top of the margin: exclude chunks of the positive's document within ±1 `chunk_index`, chunks with the positive's content hash, every positive of the same query and of its near-duplicate queries. Mining runs per tenant over that tenant's chunks only. FN audit: a sample (`fn_audit_sample = 50`) of mined negatives is judged with the answerability judge; the Clopper-Pearson 95% upper bound (`rag_eval.bounds`) of the answerable share must be ≤ `fn_audit_max_upper = 0.15`, else `mine` exits non-zero and suggests a larger margin or `range_min`.
- **D-13:** Output datasets: `train_ntuple` (anchor, positive, negative_1..n) for pairs with `num_negatives` valid negatives and `train_pairs` for the rest; both are trained with the same loss through the trainer's multi-dataset support.

### Training
- **D-14:** Base-model candidates, all 1024 dimensions and permissive licences: `Qwen/Qwen3-Embedding-0.6B` (Apache-2.0, MRL, 32k context, instruction-aware; **default**), `BAAI/bge-m3` (MIT, 8192 context), `intfloat/multilingual-e5-large-instruct` (MIT, 512 context). Each is pinned to a Hub revision sha in `finetune.json`. `evaluate --zero-shot` scores every candidate on the held-out split before training (step 0, cheap) and the operator trains the best one; Phase 3.1.1's candidate results are an input. Models with dims other than 1024 are refused by the slot rule (D-22).
- **D-15:** Default recipe in `eval/config/finetune.json`: loss `CachedMultipleNegativesRankingLoss` (`mini_batch_size = 32`), `per_device_train_batch_size = 256`, `BatchSamplers.NO_DUPLICATES`, learning rate `2e-5`, warmup ratio `0.1`, `num_train_epochs = 1`, `bf16`, `seed = 42`; optional `GISTEmbedLoss`/`CachedGISTEmbedLoss` with the base model as guide; optional `MatryoshkaLoss` (dims `[1024, 512, 256]`, off by default because slots are 1024). Dev-split `InformationRetrievalEvaluator` every `eval_steps`, `load_best_model_at_end` on dev nDCG@10. Query prompt per base model in the config (Qwen instruct line with a domain task sentence, e5 `query: `, bge-m3 empty), document prompt likewise; both are recorded on the model card and become the slot's prompts.
- **D-16:** Training runs where a GPU is: an operator GPU box (≥ 24 GB VRAM) or any hosted GPU container service. The repo provides `eval/finetune/Dockerfile.train` (CUDA base), `eval/finetune/requirements-train.lock` (exported from the eval lock with the `finetune` extra), and `kit` builds a training kit with **train and dev only**; `train` refuses a kit that contains test files. The data leaving the deployment for a hosted trainer is covered by the tenant consent (D-27), and the kit manifest lists the tenants.
- **D-17:** This machine has no GPU. Unit tests use a NumPy `FakeEncoder` and a fake trainer; one test marked `finetune_train` (skipped when the `finetune` extra is missing) trains a tiny `StaticEmbedding` built in the test from a WordLevel tokenizer for a few CPU steps, with no download.
- **D-18:** Reproducibility: `TrainingRunConfig` records base model id and revision, dataset manifest sha256, config sha256, seed, git commit, and library versions (torch, transformers, sentence-transformers, datasets); the output is the model directory plus `TrainingRunReport` and a `ModelVersionCard`.

### Evaluation and gate
- **D-19:** Offline evaluation (`evaluate`) on the fine-tune test split: per tenant, the corpus is that tenant's exported chunks only; metrics Recall@10, MRR@10 and nDCG@10 overall, per language, per language pair and per source (synthetic / mined); for the base model, the fine-tuned model and the production model (stored vectors). Paired bootstrap 95% intervals and the noise band from `eval/config/noise.json`. Offline promotion rule: fine-tuned ≥ production + noise band on Recall@10 overall, no language slice below production − noise band, and fine-tuned ≥ base on Recall@10. A card that fails is `rejected_offline` and cannot be registered.
- **D-20:** The online gate is EMB-05, unchanged: bind a slot, `npm run rag:reembed -- --profile ft-a-1024`, run the eval profile comparison (`rag_eval.profile_compare`), `rag:embedding -- record-evidence`, `activate`. Gated items are real (`production`/`human`) items once they exist (EVAL-14), otherwise the fixture items, which prove wiring only. The comparison must also show the cross-lingual pairs and the general (non-domain) slices with no regression beyond the noise band (forgetting check).
- **D-21:** Live GPU training, real-data generation, the real endpoint and real-data evaluation are live verification items (06.1-19).

### Serving
- **D-22:** Two fixed fine-tune slots: profile `ft-a-1024` (provider `ft_slot_a`) and `ft-b-1024` (provider `ft_slot_b`), dims 1024, storage `halfvec`, each with its partial HNSW index (`m = 64`, `ef_construction = 200`) created in migration 0652. No dynamic DDL. Binding a model version to a slot (`rag_finetune_bind_slot`) refuses when the slot is active, is the active profile's `previous_active_id`, has any `chunk_embeddings` row, has a running re-embed run, or the version is not `registered` or is tainted. `rag_finetune_clear_slot` deletes a free slot's vectors in batches and resets it to `unbound`; `rag_finetune_release_rollback` clears the active profile's `previous_active_id` (explicit acknowledgement) so the older slot becomes free. Bind sets the slot's `model` to the version id and `query_instruction` to the card's query prompt; nothing else may change a slot's `model` (trigger).
- **D-23:** Slot provider: OpenAI-compatible `POST {base}/embeddings` (text-embeddings-inference, vLLM, or a hosted endpoint running either), configured per slot by `RAG_FT_SLOT_{A,B}_BASE_URL`, `RAG_FT_SLOT_{A,B}_MODEL` (the model version id, which the existing EMB-03 checks compare with the profile's `model`), `RAG_FT_SLOT_{A,B}_QUERY_PROMPT`, `RAG_FT_SLOT_{A,B}_DOCUMENT_PROMPT`, and a shared secret `RAG_FT_EMBED_API_KEY` (may be empty on a private network). Vectors must be exactly 1024 long and are L2-normalized. Retries and timeouts as in the Qwen provider; no fallback host.
- **D-24:** Probe check (EMB-03 strengthened): the model card stores three fixed probe texts and their reference vectors (computed at the end of training with the card's prompts). `ft-check <slot>` and the provider's first call per process embed the probes through the endpoint and require cosine ≥ 0.999 with the references, else `EmbeddingProfileMismatch` and a loud failure. This proves the endpoint serves exactly the registered weights and prompts, which a same-dimension model swap behind the same URL would otherwise hide.
- **D-25:** Taint and evidence: instead of editing `rag_activate_embedding_profile` or `rag_record_eval_evidence` (shared with Phase 7), migration 0652 adds (i) a trigger on `embedding_model_versions` that, when a version becomes `tainted`, sets `eval_evidence = NULL` on its bound non-active slot (activation then refuses `eval_missing`), and (ii) a BEFORE UPDATE trigger on `embedding_profiles` that refuses a non-null `eval_evidence` for a slot whose bound version is tainted or missing, and refuses a slot `model` change outside the bind/clear functions.
- **D-26:** Latency and cost: the slot endpoint's query embedding must fit the `embed` stage budget in `eval/config/latency-budgets.json` (200 ms chat/embed); reported, report-only like the other budgets until live numbers exist. Cost formulas (generation, judge, GPU hours, re-embed) are printed by `--dry-run` and recorded in the reports.

### Governance
- **D-27:** Consent table `rag_finetune_consent (tenant_key PK, scope 'none'|'private'|'deployment', evidence_ref, granted_by, granted_at, revoked_at, updated_at)`; no row means `none` (opt-in). `private`: the tenant's data may train a model that serves only that tenant; `deployment`: it may also train a model shared across the deployment. Granting needs a non-empty `evidence_ref` (a ticket or signed-agreement reference, never a person's contact data). Python `export` and TS `export-vectors`/`embed-queries` take a purpose (`private` for exactly one tenant, `deployment` otherwise) and refuse any tenant whose consent does not cover it, re-checked at each command.
- **D-28:** Two model scopes. `deployment` (card scope `deployment`): trained on one or more tenants that each granted `deployment`; may be activated globally (EMB-05) or bound deployment-wide (3.1.1). `tenant` (card scope `tenant`): trained on exactly one tenant with `private` or `deployment` consent; may only be served through 3.1.1 bindings whose `tenant_key` is that tenant, never globally (D-33). Single-tenant: the one tenant `s:default`, either scope. `export` needs an explicit `--tenant` list (no "all"). Mining and evaluation are per tenant, so one tenant's chunks never appear in another tenant's candidate pool. Two-tenant tests cover export, vectors, mining, retrieval through the slot and the private-binding guard.
- **D-29:** Revocation (`ft-consent revoke`): in one transaction the consent row becomes `none`, every model version whose `tenant_keys` contains the tenant becomes `tainted` (which nulls its slot evidence, D-25), and the result says whether a tainted version is the active profile; the CLI then prints the rollback and clear steps. `prune --tenant <key>` deletes that tenant's bundle files. Deleting weights at the artifact location is an operator step listed by the CLI (the card records `artifact_uri`).
- **D-30:** Registry `embedding_model_versions` (service role only, RLS on without policies): id, base model and revision, scope (`deployment` | `tenant`), tenant keys, dataset manifest and config hashes, offline metrics (numbers only), probe vectors, query and document prompts, dims, `artifact_uri` (refused when it carries userinfo, a query string or a fragment), status `registered|bound|retired|tainted`, bound slot, created_at/by. `ft-models register <card.json>` refuses a `rejected_offline` card, a tenant without consent covering the scope, or a `tenant` card with more than one tenant.
- **D-31:** Retention: bundles live under `eval/out/finetune/<run_id>/` (gitignored) or an `--out` outside the repository. Text-bearing files (chunks, queries, pairs, kits) are deleted by `prune` after `retention_days = 30`; manifests and reports keep ids, hashes and counts only and stay. Reports, logs and exceptions never contain chunk or query text (tests grep for fixture sentences).
- **D-33:** Binding route (Phase 3.1.1). `ft-bind <slot> <version> --doc-types <list|all>` makes the slot a scoped profile (`doc_types`, 3.1.1 D-05), after which it can only be activated through 3.1.1 bindings (3.1.1's trigger refuses global activation of a scoped profile); without `--doc-types` the slot stays unscoped and uses the global EMB-05 path. A tenant-scope version must be bound with `--doc-types`. Migration 0654 adds a guard trigger on `embedding_profile_bindings`: a binding whose profile is an `ft-*` slot is refused unless the bound version is not tainted and either (a) the binding's `tenant_key` is NULL and the version is `deployment` scope, or (b) the binding's `tenant_key` equals the single tenant of a `tenant`-scope version, or (c) the binding's `tenant_key` is one of a `deployment` version's tenants or any tenant when every trained tenant granted `deployment`. Revocation (D-29) also deactivates (3.1.1 `rag_deactivate_embedding_binding` semantics) every active binding of a tainted version. If 3.1.1's merged binding SQL differs from its CONTEXT, 06.1-20 adapts to the merged names and records the mapping.
- **D-34 (UI-SPEC waived, orchestrator decision 2026-11-24):** the only UI change is one field group (switch, two slot groups, key) added to the existing Embedding profiles card of `scripts/config-ui/index.html` in 06.1-04, copying its neighbours; no new surface, layout or component (same reasoning as the 4.1 waiver, 04.1 D-23), so no UI-SPEC and no `/gsd-ui-phase` run. Still required: 06.1-04 runs the web-design-guidelines skill on `scripts/config-ui/index.html` and fixes all findings, and its SUMMARY ends with a `## Design skills` table (`frontend-design` n/a with reason, `Impeccable` n/a or pass, `web-design-guidelines` pass with findings resolved); `node scripts/ci/check-frontend-design-summary.mjs <phase_dir>` passes.
- **D-35:** Private models are refused on the global path in SQL: `rag_finetune_bind_slot` refuses a tenant-scope version (only the scoped bind of 06.1-20 binds one, setting `doc_types` in the same transaction), and trigger B refuses evidence, backfilling or activation of an unscoped `ft-*` slot holding a tenant-scope version, so no sequence of service-role RPCs can serve a private model to every tenant.
- **D-36:** Fixture mode (`export --source-dir`) accepts only directories under `eval/fixtures/` (resolved real path), so exported real data cannot be re-imported around the consent check.
- **D-32:** All new SQL objects are service-role only: functions are `SECURITY DEFINER`, `SET search_path = ''` with schema-qualified bodies, `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`, `GRANT ... TO service_role`, listed in `tests/helpers/security-definer-allow-list.ts`, and covered by `tests/rag/search-rpc-grants.test.ts` and `tests/rag/security-definer-search-path.test.ts`. Migrations 0651 to 0653 are idempotent and folded into both setup files at the end of the phase.

<open_questions>
## Open questions for the product owner

Each default is implemented by the plans. **Default adopted, PO may override.**

1. **Base model.** Default `Qwen/Qwen3-Embedding-0.6B`, with `BAAI/bge-m3` and `multilingual-e5-large-instruct` as zero-shot-compared alternatives (D-14). A small model has to beat a hosted Qwen3-8B or OpenAI production profile after fine-tuning; if the zero-shot gap is large, fine-tuning may not close it, and the gate will simply refuse. *Default adopted, PO may override.*
2. **Where the fine-tuned model is served.** REQUIREMENTS excludes self-hosted GPU for Qwen3-Embedding-8B; a fine-tuned model has no public host, so it needs an endpoint the operator runs or rents. Default: any OpenAI-compatible endpoint (a hosted text-embeddings-inference endpoint, or TEI/vLLM on an operator box; a 0.6B model also runs on CPU for queries) (D-23). *Default adopted, PO may override.*
3. **Where training runs.** Default: an operator GPU box or a hosted GPU container service using the repo's training image (D-16). Sending the training kit to a hosted trainer counts as data processing under the tenant's consent. *Default adopted, PO may override.*
4. **Consent mechanism.** Default: the operator records consent per tenant with a required evidence reference through the CLI (D-27); no self-serve UI in this phase. *Default adopted, PO may override.*
5. **Shared vs private models in multi-tenant deployments.** Default: both exist; a tenant-private model (one tenant's data, served only to that tenant through 3.1.1 bindings) needs `private` consent; a shared deployment model needs every trained tenant's `deployment` consent and an explicit tenant list (D-27, D-28, D-33). The stricter alternative is private-only in multi-tenant mode. *Default adopted, PO may override.*
6. **LLM for generation and judging.** Default: the Anthropic model already pinned in `eval/config/draft.json`, for both, with a required budget (D-05, D-06). A cheaper model is a one-line config change. *Default adopted, PO may override.*
7. **Held-out documents.** Default: documents with gold evidence of golden test items are never trained on, and the gated model is the model that ships (no retrain on all data after the gate) (D-09, D-20). *Default adopted, PO may override.*
8. **Retention.** Default 30 days for text-bearing bundle files (D-31). *Default adopted, PO may override.*
9. **Package approval.** Plan 06.1-01 adds optional eval extras with an exact package list (`anthropic==2.12.0`, `httpx==0.28.1`, `numpy` (one pinned release ≥ 14 days old), `sentence-transformers[train]==6.2.0`, `torch==2.15.0` CPU wheel); installing the `finetune` extra in the eval environment at execution time is needed so the `finetune_train` tests actually run. 06.1-01 Task 3 is a package-approval checkpoint. *Default: approve the listed pins; PO may override.*

</open_questions>
