# Phase 6.1 Plan 17: Fine-tune serving lifecycle, canary and parity on PGlite Summary

**The serving path of a fine-tuned slot is proven end to end on the real SQL and TypeScript code in both modes: bind, probe, re-embed, the unchanged eval profile comparison and gate, activation, serving, rollback, the three never-mixed checks, revocation, tenant isolation and switch-off parity. The test exposed one defect: the re-embed dry run could not price a slot.**

## Tests that failed before the fix
- `tests/rag-db/finetune-lifecycle.test.mts` "bind, ft-check, re-embed, …" in both modes: `npm run rag:reembed -- --profile ft-a-1024 --dry-run` threw in `estimateReembedCost` because `src/lib/rag/ingest/reembed/cost.ts` listed only openai, voyage and qwen3 (06.1-14 deviation 5).
- Task 2 tests passed on first run: they pin behaviour, no production change.

## Behaviour changes
- `rag:reembed --dry-run` on `ft-a-1024` / `ft-b-1024` now prints 0 USD per tenant and the note "A fine-tune slot is served by the operator's own endpoint and has no list price; …" instead of crashing. No other output changes; the real run never priced anything.
- Nothing else in production code. With `RAG_FINETUNE=off`, strict "information not available", webSearch with Exa, `source_images`, `{{context}}`, voice and embed are untouched (the parity test shows retrieval and traces are identical to a database without the fine-tune migrations).

## Deviations from Plan
1. **New shared helper `tests/helpers/finetune-lifecycle.mts`** (outside `files_modified`): both test files use the same harness, fixture slot model and comparison.
2. **`tests/helpers/fake-embedding-endpoints.ts`** gains `setFtEncoder` (default unchanged, so 06.1-14/15 tests are unaffected) so the slot can serve the fixture model.
3. **Like-for-like production model** (see key decisions): the lifecycle tests rewrite the legacy column with the 1024-dim fixture embedder padded to 1536. With the stock fixture vectors the slot is honestly worse and the gate refuses it; this is a property of the hash embedder, not of the pipeline. The parity test uses the stock fixture.
4. **"The eval run on the fixture golden set"** in the parity test runs every golden question through `runRetrieval` (profile `eval`) and compares per-item results and stage counts, rather than the `npm run test-rag` harness, which builds its own database and cannot point at a database without 065x.
5. **Edge keep-alive warm-up** in `harness.use()`: a fixture build outlasts the fake edge's keep-alive window, and the first request then hit a closed socket (`fetch failed`). Test-only.
