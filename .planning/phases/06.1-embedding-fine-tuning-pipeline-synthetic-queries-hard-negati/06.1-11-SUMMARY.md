# Phase 6.1 Plan 11: Hard-negative miner Summary

**`python -m rag_eval.finetune mine --bundle <run> [--miner vectors|st] [--model <path-or-id>] --budget-usd <x>` mines hard negatives per tenant and per split corpus, with the production model's stored vectors by default or any sentence-transformers model, applies the margin and the D-12 false-negative guards, writes `train_ntuple.jsonl`, `train_pairs.jsonl`, `dev.jsonl` and `mining-report.json`, and refuses to write training files when the audited false-negative bound is above 0.15.**

## Accomplishments
- `vectors_io` reads the 06.1-10 files (per-tenant chunk and query vector sets), checks sha256, dims, row count, tenant, profile and model, and writes the same format for fixture runs (06.1-16 can use `write_vector_set` with `FakeEncoder` vectors).
- `encoders`: one `Encoder` protocol over stored production vectors, a hashing fake and sentence-transformers (lazy import).
- `miner`: NumPy miner that mirrors `mine_hard_negatives` 6.2.0 (checked against its source), the st backend on top of `mine_hard_negatives`, the guards, expert-first top-up, optional round trip, the budgeted FN audit with the `rag_eval.bounds` upper bound, and `MiningReport`.
- Test session: Hugging Face libraries run offline in every eval test session; `FINETUNE_TRAIN_REQUIRED=1` makes a skipped `finetune_train` test fail. The parity and st tests ran (4 finetune_train tests, none skipped).

## Deviations from Plan
1. **st output format `labeled-list` instead of `n-tuple`.** In 6.2.0 `output_format="n-tuple"` drops every query that has fewer than `num_negatives` survivors, so after an over-fetch of `num_negatives x 3` a query with, say, 8 survivors would vanish instead of keeping them for the guards. `labeled-list` returns each query's survivors in score order; the n-tuple training rows are built by this plan's own output step. Everything else follows the must_have: per tenant and split corpus, the configured parameters, query/corpus prompts, over-fetch then the whole window, guards afterwards.
2. **st is called with `sampling_strategy="top"`** and the configured sampling (`top` or seeded `random`) runs after the guards, as in the vectors miner. A random draw inside `mine_hard_negatives` happens before the guards and could return guarded chunks; for `random` the whole window is fetched at once so both miners sample from the same pool (the parity test covers it).
3. **range semantics.** The plan text reads "ranks [range_min, range_max), drop by margin"; the pinned library applies the margins first and then skips `range_min` survivors. The vectors miner follows the library (D-11 says it mirrors it); the hand-built range test documents it.
4. **Exit code 6 writes mining-report.json** (with the failed audit) and removes stale training files, so a failed audit leaves no trainable output behind; the plan only named the exit code.
5. **Extra file** `eval/tests/_finetune_guard.py` holds the session hook so the FINETUNE_TRAIN_REQUIRED rule itself can be tested in a subprocess pytest.
6. Test sentences are neutral synthetic strings (records, codes, placeholder words) per the domain-neutrality rule.

## Integration gap found (not fixed here, outside this plan's files)
`src/lib/rag/finetune/bundle-io.ts` `readKeptQueries` (06.1-10) parses `queries.kept.jsonl` and `queries.test.kept.jsonl` as `FinetunePair`, but `filter` (06.1-08) writes `RawSyntheticQuery` rows there. A real `npm run rag:finetune -- embed-queries` over a filtered bundle therefore refuses with `rows_invalid` before any provider call. The miner accepts both shapes and matches query vectors by `pair_id` or `query_id` (with `pair_id = query_id` for synthetic rows), so either fix works with it: (a) `readKeptQueries` also accepts the RawSyntheticQuery shape (it is a Python-only model, not in `contracts.generated`), or (b) `filter` writes FinetunePair rows. Recommended: (a), writing `query_id` rows. 06.1-16's fixture run writes vectors in Python and is not affected.
