# Phase 6.1 Plan 09: Mined pair import Summary

**`python -m rag_eval.finetune import-mined --bundle <run> --input <training.ndjson>` reads Phase 5.1.1's `TrainingPair` export, keeps only rows of the bundle's tenants whose positive and hard-negative chunks exist in that tenant's bundle, resolves their text there, clusters near-identical queries per tenant, gives each cluster its strictest split, runs the 06.1-08 rule filters and golden decontamination (no judge), and writes `pairs.mined.jsonl` as `FinetunePair` rows with source `mined`, weight 2 and expert negatives. The report counts every drop by reason and holds no text.**

## Accomplishments
- Contract check against 5.1.1 first: the merged `TrainingPair` has exactly the D-17 field list, so the import consumes it unchanged.
- Tenant isolation (D-28): the tenant must be in the manifest, and every chunk is looked up by `(tenant_key, chunk_id)` with a document-id match, so another tenant's chunk with the same id never resolves.
- Leakage guards (D-08, D-10): held_out rows and positives in test documents go to test; clusters take the strictest split; negatives from stricter-split documents are removed from the pair.
- No change to `cli.py`: its dispatch table already pointed `import-mined` at `rag_eval.finetune.mined:main`.

## Deviations from Plan
1. **Strictest split instead of the first member's split.** CONTEXT D-10 says a mined cluster takes its first member's split; the plan's truths and PLAN-INDEX say strictest (test > dev > train). Strictest was implemented, because it never lets a member of a test cluster train. The plan's behaviour example (first member in a test doc, second in a train doc, both in the first member's split) holds and is tested; a second test covers the reverse order.
2. **Negatives across splits.** D-10 says hard negatives of train pairs come only from train documents. The import applies this as "a negative's document split must not be stricter than the pair's split", so dev pairs may carry train or dev negatives and test pairs any. Dropped negatives are counted, never the row.
3. **Extra reasons inside invalid_row:** a language code outside the registry (cannot become a `FinetunePair`) and a repeated `review_item_id` (pair ids must be unique). Both are counted as `invalid_row`.
4. **Report model.** `MinedImportReport` is a local Pydantic model in `mined.py` (counts only), like 06.1-08's `JudgeCacheEntry`; no sidecar contract was added, so `gen:schemas` is unaffected.
5. **Sample wording.** The sample query "which record has a trio of properties" replaced an earlier draft that the verbatim rule correctly flagged against its own positive chunk. All fixture sentences are synthetic and neutral.
