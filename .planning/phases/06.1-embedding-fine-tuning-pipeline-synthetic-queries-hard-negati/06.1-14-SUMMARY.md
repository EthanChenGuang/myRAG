# Phase 6.1 Plan 14: Fine-tune slot provider and probe check Summary

**A fine-tuned model can be served from any OpenAI-compatible `POST {base}/embeddings` endpoint as slot `ft_slot_a` or `ft_slot_b`, only while `RAG_FINETUNE=on`. Before its first vector in a process, the provider embeds the bound version's three probe texts and refuses to serve unless every cosine against the stored reference is at least 0.999.**

START: `6ba92d40`

## Accomplishments
- `types.ts`: provider ids `ft_slot_a`/`ft_slot_b`, `FT_SLOT_DIMS = 1024`, `FT_SLOT_UNBOUND_MODEL = 'unbound'`, `isFinetuneSlotProvider`. `mrl.ts`: mismatch kind `probe`.
- `catalog.ts`: one entry per slot (model `unbound`, 1024 dims, no list price, endpoint named by `RAG_FT_SLOT_{A,B}_BASE_URL` / `RAG_FT_EMBED_API_KEY`). `catalogEntry` resolves any version id of a slot to that entry, so `priceFor` and the dims rule work for bound versions.
- `registry.ts`: slot providers exist in `defaultProviders()` only with `RAG_FINETUNE=on`; shape rule halfvec 1024 only for slots.
- `active-profile.ts`: `KEY_BY_PROVIDER` maps the slots to their base URL (the key may be empty).
- `finetune-slot.ts`: the provider (D-23) and the probe (D-24) as described in key-decisions.
- `query-embedding.ts`: a provider `probe` mismatch is reported as a profile `model` mismatch; the batch path now translates provider mismatches too.

## Behaviour changes
- With `RAG_FINETUNE=off` (default): none. The slot providers are not registered; a slot profile fails the startup check with `provider_unconfigured`, as before (it already did, since the provider id was unknown). Strict "information not available", webSearch with Exa, `source_images`, `{{context}}`, voice and embed are untouched; the full vitest suite and both `test-rag` runs pass.
- Batch query embedding (`embedQueries` with several texts on a profile whose provider has `embedQueries`): a provider `EmbeddingProfileMismatch` (dims, zero norm, model) now becomes an `EmbeddingProfileMismatchError`, as on the single-query path. Before, it escaped unclassified, so `classifyProfileFailure` did not recognize it.
