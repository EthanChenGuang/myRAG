# 04.2-21 SUMMARY: version and duplicate-source facts reach sources and citation records

A kept chunk in a duplicate cluster now lists every other current, ready document of the cluster (`alsoIn`). The dropped candidates come first, then the cluster's other sources from one batched `rag_dup_cluster_sources` call. The list holds documents of the caller's tenant only and is capped at 30. The chat route's document source parts and the Phase 5 citation records carry `version`, `isCurrent`, `effectiveFrom`, `effectiveTo` and `alsoIn`, but only when the used document has them. Embedded chat sets `channel: 'embed'` on the server side, so a version scope from the embed widget needs both `RAG_VERSION_SCOPE` and `RAG_EMBED_VERSION_SCOPE`. With the switches off, payloads, stored messages and answer records are unchanged.

## Task 2: 0862 and the complete source list

- `rag_dup_cluster_sources(p_tenant_key text, p_cluster_ids uuid[], p_limit integer)` returns `(cluster_id, document_id, filename, chunk_id)`:
  - One row per cluster and member document. The member chunk is the one with the lowest chunk index, then the lowest id.
  - Only current chunks with status `ready` or `variant` that are not provisional, in current, ready, non-provisional documents.
  - The cluster itself must belong to the tenant.
  - At most `p_limit` documents per cluster, ordered by filename and then document id.
  - It raises 22023 for more than 50 ids or for a limit outside 1..30.
  - It is SECURITY INVOKER with `SET search_path = ''`, revoked from PUBLIC, anon and authenticated, and granted to service_role.
  - It is not a DEFINER function, so it needs no 0410 entry. It adds no store, so it needs no purge hook. It is not folded into the setup files.
- In `runContextStages`, the call starts before `expand_parents` and is awaited after it, so the two run in parallel. It runs only when the `diversify` stage is enabled and a candidate has a `dupClusterId` (at most 50 cluster ids).
  - Each kept chunk gets `alsoIn = mergeAlsoIn(own document, [dropped, cluster sources])`.
  - `withAlsoIn` merges the lists per used document, in kept order, and sets `UsedDocument.alsoIn` only when the list is non-empty.
  - The assemble stage counts gain `also_in_sources` (the number of rows), but only when the call succeeded.
- If the call fails, the context is still returned and `alsoIn` keeps the dropped candidates. The assemble stage becomes `degraded` with detail `also_in_sources_unavailable`. If the version lookup also failed, the detail is joined with a comma after `version_labels_unavailable`.

## Task 3: payload fields and citation records (names for plan 04.2-26)

**Payload fields.** The field names are final: `version` (number), `isCurrent` (boolean), `effectiveFrom` and `effectiveTo` (ISO date or `null`), and `alsoIn: { documentId, filename, chunkId }[]`. Each field is present only when it is set on the `UsedDocument`, and `alsoIn` only when it is non-empty. They are added by `sourceDocumentFields(doc)` (`@/lib/rag`). In `src/app/api/chat/route.ts` the helper is spread into three places:
- the `toolName: 'query_documents'` tool-result `output.documents` entries;
- the `type: 'metadata'` `usedDocuments` part in the same `onStepFinish` block;
- the streamed `metadata` `usedDocuments` chunk written next to `source_images` in `createUIMessageStream`.

**Citation records.** `buildCitationRecords` copies `isCurrent`, `effectiveFrom`, `effectiveTo` and `alsoIn` from `aliasMap.documents`, keyed by document id. `buildAliasMap(blocks, usedDocuments)` builds that map, and `CitationSession.attach(result)` now passes `result.usedDocuments`. The chat and eval routes already pass the full retrieval result, so neither needed a change.
- A `null` date is left out, because the contract field is `date().optional()` and not nullable.
- `documentVersion` still comes from the block, as before.
- The claude-citations path uses the same builder, so it gets the fields too.

**Embed route: changed only for the channel.** The embed route has no sources payload today: the stream carries only the answer and an optional `feedbackToken`, and the widget renders no sources. I added no payload, because one would start sending filenames to anonymous visitors with nothing to render them. See `handoffs/04.2-21-embed-sources.md`. A later plan can map the fields with the same helper.

## Task 4: embed and `versions`

- The embed route already passed the parsed `retrievalFilters` through to retrieval (plan 04.2-15), so no pass-through fix was needed. The route now sets `channel: 'embed'` on its `runRetrieval` input, on the server side only.
- The rule stays in one place, `effectiveVersionScope(config, profile, requested, channel)`, which `runSearchStages` and the query layer's cache facts both call. A request is the embed channel when `profile === 'embed'` or `channel === 'embed'`. On that channel a non-current scope also needs `config.v2.embedVersionScope`; otherwise the scope is current and the search records `versions_ignored`.
- Mutation check: replacing the embed condition with `true` fails the "RAG_EMBED_VERSION_SCOPE off" case of the e2e test and two `filters.test.ts` cases.

## Behaviour changes

- **Default (all switches off):** no change. Both smoke gates pass, and the chat, embed, strict, webSearch, `source_images` and roundtrip characterization tests pass unchanged.
- **With `RAG_RESULT_DIVERSITY` on and clusters present:**
  - One extra RPC per request.
  - `KeptChunk.alsoIn` now lists the whole cluster instead of only the dropped candidates. It is still not on the eval trace.
  - The chat source parts and citation records carry `alsoIn`.
- **With a non-current version scope:** the chat source parts and citation records carry the version fields.
- **Embed:** the `runRetrieval` input gains `channel: 'embed'`.

- `alsoIn` order (D-21): the dropped candidates in rank order, then the other cluster sources by filename. The own document is never listed, each document appears once, and the cap is 30, for both chunk and document.
