# Phase 04.2 Plan 27: identifier filter, near-miss guard and not-found result Summary

**With `RAG_IDENTIFIER_INDEX=true` and `RAG_IDENTIFIER_FILTER=true`, a question that names an identifier searches only the passages that carry it. Look-alike identifiers are removed after refusal. A missing identifier gives a strict refusal with same-tenant suggestions, or a suggestion line in balanced and flexible mode. With the switch off nothing new runs.**

## Records for plan 04.2-36

- **Strict route text:** when `result.reason === 'identifier_not_found'` (constant `IDENTIFIER_NOT_FOUND` in `src/lib/rag/v2/result.ts`), append `identifierSuggestionMessage(language, result.identifierSuggestions)` from `src/lib/rag/generation/messages.ts` to the "information not available" text. An empty string means there are no suggestions.
- **Result fields** (`src/lib/rag/types.ts`):
  - `identifierSuggestions?: string[]`: at most 3 raw spellings of the caller's tenant. It is set whenever the question names identifiers and none exists, in every mode.
  - `identifierFilter?: IdentifierFilterSummary`, `{ asked, resolved, fallback, nearMissDropped }`. Present whenever `identifier_resolve` succeeded. It maps to the RagTrace `identifier` block: `resolved` → `resolved`, `nearMissDropped` → `near_miss_dropped`, and the suggestions go to `suggestions`.
- **Not exported yet from `@/lib/rag`:** barrel exports and stage budgets are 04.2-36. The budgets already exist in `config.ts`: `identifier_resolve` and `identifier_guard` at 1000 ms (chat), 500 / 300 ms (voice).

## Stage order
- **`runSearchStages`:** `identifier_resolve` (optional), then the leg block (search, exact_id_lookup, table_lookup), with at most one unfiltered rerun of the block, then fuse, then dedupe.
- **`runRankStages`:** rerank, refusal, `identifier_guard` (only with the filter on and identifiers in the question), diversify, reservation. With diversify off, the reservation stays inside the refusal stage, as before.
- **`src/lib/rag/v2/stages/query.ts` was not touched**, so the slot for the 4.1.1 terminology stage is unaffected.

## Stage records (counts only)
- **`identifier_resolve`:**
  - detail is `asked=<n> found=<n> filtered=<bool>`, or `identifier_resolve_failed` with status degraded.
  - counts are `asked`, `found`, `missing`, `suggestions`.
- **`search`:** detail gains `identifier_filter_fallback` on the rerun, and `backend_field_unsupported` (degraded) when a backend without `identifierFilter` is replaced by pgvector.
- **`identifier_guard`:** counts are `{ dropped }`.
- No identifier, suggestion or pattern is logged or placed in a detail.

## Behaviour changes
- **Switch off:** none. No new stage, call or field. The request objects are unchanged because `identifiersNorm` is only spread when set.
- **Switch on, question without identifiers:** one `identifier_resolve` record (`asked=0`, with no resolve RPC; the tenant pattern loader is cached). Candidates and order are the same as with the switch off, which the test checks.
- **Switch on, question with identifiers:**
  - **Identifier found:** retrieval is filtered and look-alikes are guarded.
  - **None found, strict:** refusal `identifier_not_found`.
  - **None found, balanced or flexible:** look-alikes are dropped and a suggestion line is added.
- **Preserved:** web search with Exa, `source_images` and `{{context}}` are untouched. A knowledge-base failure still never reads as "information not available": a resolve failure only degrades.

## Deviations from Plan
1. **Files outside `files_modified`:**
   - `src/lib/rag/v2/pipeline.ts`: carries the identifier state from search to rank, context and result, and contains the strict short-circuit.
   - `src/lib/rag/v2/port.ts`: `identifiersNorm` on `variantSearchRequest` and the delegated port.
   - `src/lib/rag/v2/stages/binding-legs.ts`: `identifiersNorm` on the binding legs.

   04.1.1-05 also edits `pipeline.ts`; whichever plan lands second rebases.
2. **Two tenants, both modes:** the app reads its deployment mode once per process. So the two-tenant checks of resolve, suggestions and tenant patterns run at module level against PGlite in both modes, and the `runRetrieval` end-to-end block runs in single-tenant. This is the same approach as 04.2-18.
3. **Plain numbers are ignored as question identifiers** (see key decisions). The plan's behaviour list does not cover this case. Without it, a question with a year could be refused in strict mode.
4. **The guard fails open** (`onFail` skip): it is an in-memory function and was never seen to fail. The filter and the strict refusal still apply.
