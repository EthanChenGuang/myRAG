## The two fixes (decisions recorded)
1. **Diversity option 1.** The orchestrator chose it under owner delegation, from `handoffs/04.2-32-gate-diversity.md`.
   - Cause: the Phase 5.2 `stale_version` fixture holds v1 and v2 of one rule as two current documents. Their sections differ in one value ("15 metres" against "20 metres"). The SimHash cluster held both, so collapse kept the higher-ranked v1 chunk and the v2 gold chunk left the top 10.
   - Fix: collapse keeps one representative per (cluster, value signature) across documents. The value signature is the D-28 identifier normalization (`extractIdentifierEntries`: numbers, dates, identifiers; language-neutral, no new regex set) of the chunk body without its stored "Document: … Chunk i of n." header.
   - Unchanged: same-document variants still fold into their document's keeper, and identical copies across documents still collapse. The spec, the SimHash band and the MMR lambda are unchanged.
2. **Redundancy option 1.** Also chosen by the orchestrator under owner delegation.
   - `topkRedundancy` counts per (cluster id, value signature) with the same signature function, so collapse and the metric cannot drift.
   - The eval route (trace `topk_redundancy`), the context stage count (`topk_redundancy_permille`) and the `rag_retrieval_log` writer all call it.
   - `rag_eval.metrics._topk_redundancy` uses the trace value when present and falls back to cluster ids for traces without it. `RAG_RETRIEVAL_LOG` is off in production, so no live series breaks.

Tests that failed before the fixes:
- `tests/rag/v2/diversify.test.ts` › "keeps chunks of two documents in one cluster when their value tokens differ" (`expected ['v1'] to deeply equal ['v1','v2']`).
- `diversify.test.ts` › "counts top-k redundancy per cluster and value signature" (`expected 0.5 to be 0.25`).
- `eval/tests/test_metrics.py::test_topk_redundancy_reads_the_app_trace_value_when_present`.
