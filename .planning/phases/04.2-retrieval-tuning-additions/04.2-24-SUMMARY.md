# Phase 4.2 Plan 24: Structured table lookup leg Summary

**With `RAG_TABLE_LOOKUP=true`, a question naming two cell values of one table row finds that row by a deterministic SQL match of its tokens against the stored cells, inside the caller's tenant. The row's chunk is fused as the extra RRF list `table:0` with `TableLookupParams.weight`, and the model sees the matched row with its header. With the switch off, the stage is not run and candidates, order, context and trace are unchanged.**

## Function signature (0861)

`rag_table_lookup(p_tenant_key text, p_tokens text[], p_min_cells integer, p_limit integer, p_version_scope jsonb DEFAULT NULL, p_identifiers_norm text[] DEFAULT NULL)`
returns `(row_id uuid, document_id uuid, table_key text, row_index integer, header text[], cells jsonb, matched_cells integer, chunk_ids uuid[], chunk_id uuid, content text, metadata jsonb)`.

- SECURITY INVOKER, `SET search_path = ''`, `rag_assert_tenant_key` first; revoked from PUBLIC, anon and authenticated, granted to service_role.
- A cell matches when all its tokens are in `p_tokens`; a row is returned when at least `p_min_cells` distinct cells match. GIN pre-filter `cell_norm && tokens`.
- Order: matched cells descending, row index, document id, table key, row id.
- Caps (22023): more than 64 tokens, limit outside 1..50, min_cells outside 1..10, more than 100 identifiers, a malformed version scope (same validation as 0856).

## Behaviour changes (switch on only)

- Stage `table_lookup` (timeout 1000 ms, voice 500 ms, from 04.2-02's config): detail `tokens=<n> rows=<n>`, counts only. Tokens come from `queryLexicalTokens(query)` with default options (04.2-22 threads options later).
- One hit per matched row (its first qualifying chunk); a chunk two rows share is listed once with the better row.
- Stage failure or timeout: the stage is `skipped` and the other lists fuse exactly as without it (tested).
- The assemble stage counts `table_row_attached` among the selected chunks that got a header prefix; the key is absent otherwise.
- The eval route maps `retrieval_overrides.table_lookup` to `retrievalOverrides.tableLookup`; `evalTuningOverrides` passes it to `effectiveTuningParams` in the search stage and in `requestRetrievalConfigHash`, profile eval only. This closes the 04.2-06 hand-off for the table block (diversity and dup_cluster still pass `undefined` in rank.ts).
