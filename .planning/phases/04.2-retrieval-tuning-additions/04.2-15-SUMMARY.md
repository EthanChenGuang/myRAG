# Phase 4.2 Plan 15: version scope end to end

**A request can now ask for earlier versions with `retrievalFilters.versions`. With `RAG_VERSION_SCOPE` on (and the lexical leg), the search reaches superseded text of the caller's own tenant through the lexical, `term:0` and exact-id legs. The context labels each version, the sources carry version fields, and such answers never touch the semantic cache. Without the field, or with the switch off, nothing changes.**

## Task 1: upstream gate and branches

- **Gate: passed.** The 04.2-02, 04.2-06, 04.2-09 and 04.2-10 SUMMARYs exist, along with those of their dependencies (04.1-12, 03.2-13). Also present: `p_version_scope` in 0856, `backendForRequest` in the registry, and `versionScope` in `config.ts`. No `04.2-15-upstream.md` was needed.
- **Effective dates branch: present.** `0807_effective_dates.sql` adds `effective_from` and `effective_to`. Labels and source fields show the document's own dates and are null when it has none. The upload-date fallback is never shown (UI-SPEC A.11 row A4).
- **Cache wiring branch: present.** `checkBypassReason(` is called in `src/lib/rag/query/run-layer.ts`, and `storeBypassReason(` in `cache/store-after.ts` (from `ticket.turn`). The fact is set where the check facts are built. There is no skipped contract test.

## Task 2: `versions` filter and cache bypass

- The body schema takes `'current' | 'all' | { from?, to? }`, with strict ISO dates and at least one bound. It also checks that `from <= to`. Errors name the path `versions`.
- `'current'` parses to no field. A body with only `versions: 'current'` is no filter.
- The eval route maps snake-case `versions`. Chat and embed need no change; they already use the shared parser.
- `version_scope` sits next to `retrieval_options` in `checkRules`. Malformed facts still give `invalid_facts`.

## Task 3: search plumbing

- The effective scope is computed once. A non-current scope goes on every variant request, on the delegated port, the `term:0` call and the exact-id lookup (`p_version_scope`).
- The backend is chosen by `backendForRequest`. A backend without the capability is replaced by pgvector, and the stage is marked `degraded` with `backend_field_unsupported`.
- `buildFilters` strips `versionScope`, so `RetrievalFilters` stays `currentOnly: true`. `hasNarrowingFilters` does not see the scope, so the exact-id leg runs with a scope alone. It still stands down for a narrowing filter.
- Binding and translation legs stay current-only: they are dense or translation stores, and superseded rows have no vectors.

## Task 4: labels and source fields

- Example of the line in English: `[Version 1, superseded, in effect from 2026-01-01 to 2026-03-31]`. A current version reads `[Version 2, current, in effect from 2026-04-01]`. The zh and it texts follow the same pattern, and an unknown language falls back to English. The texts contain no domain words.
- `assemblyRowsFromHits` sets `version` from `hit.documentVersion`. v2 blocks therefore carry `documentVersion` for every scope; it is additive, and the context text is unchanged.
- If the lookup fails, the labels and source fields are skipped and `assemble` is marked `degraded/version_labels_unavailable`. The context is still returned.
- The source fields reach `UsedDocument`. Mapping them into the chat payload and the citation record is plan 04.2-21, and the eval trace's `used_documents` is unchanged.

## Behaviour changes

- None by default. The prechunked and ingest smoke gates show no paired difference.
- Only with an explicit non-current `versions` does a request change:
  - The search stage detail carries the codes. The eval `retrieval_strategy` mirrors this detail, so it reads `versions_ignored` when a `versions` ask is ignored.
  - Superseded candidates appear, the context carries version lines, and the semantic cache is bypassed.
- v2 context blocks now carry `documentVersion` (additive).

## Deviations

- **[Rule 2, security]** The embed opt-in is applied now, in `effectiveVersionScope`: the `embed` profile also needs `config.v2.embedVersionScope`. Without this, the embed route would serve superseded text on `RAG_VERSION_SCOPE` alone until plan 04.2-21 lands. Plan 04.2-21 Task 4 still adds `channel: 'embed'` and its test, and it should extend this function.
- **[Rule 3]** `RetrievalFilterInput` (`src/lib/rag/backend/types.ts`, not in `files_modified`) gains `versionScope`.
- **[Rule 3]** `src/lib/rag/v2/port.ts` and `src/lib/rag/query/run-layer.ts` were changed. They are not in `files_modified`, but the delegated port and the cache facts need the scope.
- **[Rule 3]** The assembly sentinel was re-pinned. The new code paths run only when `versionLabels` is set. Its re-check list (the differential test, `legacy-post-filter` and the chat characterization) passes unchanged.
- The cross-tenant case runs in multi-tenant mode only, where a second tenant exists. Single-tenant mode covers every other case.
- Voice is covered by the unit test, because the eval route always runs the `eval` profile.
- No migration, no new store and no new SQL function, so there is no purge hook and no 0410 entry.
