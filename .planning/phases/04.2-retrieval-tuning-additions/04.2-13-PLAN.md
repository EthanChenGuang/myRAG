<objective>
Group near-duplicate chunks of different documents inside one tenant into clusters at ingestion, keep the clusters correct when sources change, and backfill existing documents.

Purpose: DATA-21 (D-18, D-19, D-20, D-49, D-56). Every chunk row stays; only a cluster id is recorded. Retrieval uses the clusters in plan 04.2-20.
Output: SimHash, migration 0857, the cluster service, the publish sub-step, delete and supersede hooks, the backfill command.

Rules for every task:
- Locate code by symbol name and re-read the newest definition first. Read the newest definitions of `public.document_chunks`, `public.chunk_embeddings` and `rag_publish_document_version` for real column names and for where the vector of a profile is stored.
- SQL follows D-56: `SECURITY INVOKER`, `SET search_path = ''`, schema-qualified names, `PERFORM public.rag_assert_tenant_key(p_tenant_key)` first, the tenant in every predicate, `OPERATOR(public.<=>)` for cosine, REVOKE from PUBLIC, anon, authenticated, GRANT to service_role. Tables: RLS on, no policy. Idempotent. Not folded into the setup files.
- The tenant comes only from a verified `TenantScope` through `scopeKey(scope)`.
- Logs carry counts and error names only, never chunk text.
- Shipped threshold stays 0.95 (D-49); a fixture-fitted value applies in eval only and is written by the tool of plan 04.2-16, never by hand.
- Fixture passages are synthetic and neutral, generated in the test from one template; no 30 files are committed.
- PGlite plan: never run at the same time as another fixture-database plan in the same tree.
- Commit with plain `git commit`; the message ends with the attribution lines the executor's own session supplies. Hand-off notes go to `.planning/phases/04.2-retrieval-tuning-additions/handoffs/04.2-13-<topic>.md`.
