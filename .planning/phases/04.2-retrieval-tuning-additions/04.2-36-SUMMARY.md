# Phase 04.2 Plan 36: identifier not-found in the routes Summary

**A strict chat question that names a missing identifier now gets the fixed "information not available" text followed by up to three identifiers of the caller's own tenant, with no model call. The eval trace records `identifier_not_found` and the identifier block. With the identifier switches off nothing changes.**

## Route sites changed (by symbol)
- `src/app/api/chat/route.ts`, `POST`, inside the `shouldBlockNoContextResponse` branch: `responseText` is `noKnowledgeBaseResponse(fallbackLanguage)` plus `\n\n` and `identifierSuggestionMessage(fallbackLanguage, retrievalResult.identifierSuggestions)` when `retrievalResult.reason === IDENTIFIER_NOT_FOUND` and the message is non-empty. The same text goes to the review content and the refusal cache entry. Nothing else in the route changed: the `retrievalFailed` (knowledge base unavailable) branch runs before it and is untouched.
- `src/app/api/internal/rag/run/route.ts`: `RefusalReason` gains `identifier_not_found`; `refusalReasonOf` maps `status === 'empty' && reason === IDENTIFIER_NOT_FOUND`; new `identifierTraceOf(result)`; the trace spreads `identifier` when present.
- `src/app/api/embed/chat/route.ts`: not changed (see key decisions).
- `src/lib/rag/index.ts`: three added export lines, no existing line changed.

## Trace fields
`refusal_reason: 'identifier_not_found'`, and `identifier: { asked, resolved, near_miss_dropped, fallback, suggestions (≤3) }` from `identifierFilter` (`resolved` ← `resolved`, `near_miss_dropped` ← `nearMissDropped`) and `identifierSuggestions`. Both already existed in the RagTrace contract (`TraceIdentifier`), so `gen:schemas` is unaffected.

## Behaviour changes
- Switches off (`RAG_IDENTIFIER_FILTER` off): none. No `identifier` block, no suggestion text.
- Switch on, strict chat, identifier missing: refusal text + suggestion sentence, no `streamText` call, no sources. Without suggestions: the existing text exactly.
- Balanced and flexible chat, and embed: the model is called with the suggestion line from the context stage (unchanged code, now tested at the route).
- A knowledge-base error is still the "temporarily unavailable" message, never "information not available" and never suggestions (tested).
- Strict with web search on: unchanged (model called).
