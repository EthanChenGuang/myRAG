#### Pool sweep delta (RNK-02, LAT-01)
- **D-06:** Lower the cap minimum from 50 to **25** in the three places that enforce it: `CAP_MIN` in `eval/src/rag_eval/sweep/retrieval.py`, the `rerank_input_cap` check in `src/lib/rag/config.ts` and the one in `src/lib/rag/v2/retrieval-params.ts`. The cap may never exceed the pool. The sweep grid becomes pool 25/50/75/100 (the Phase 4 D-14 grid already lists 25; confirm it at execution) with the cap following the pool.
  - The shipped parameters in `eval/config/retrieval-params.json` change **only** by re-running the sweep tool (AGENTS.md: never by hand). The fixture re-run uses fake rerankers. The live re-run with real rerankers is a human checkpoint (D-36).
  - The selection rule stays Phase 4 D-14: the smallest configuration within noise of the best.
- **D-07:** nDCG@k is added to the sweep report and the eval report. k is the number of chunks **actually sent to the LLM** for that item: the final context count after `assemble`/`compress`, read from the trace. Relevance is binary, by gold-span match (EVAL-03), and the ideal DCG uses the item's gold evidence count capped at k.
  - It is report-only. It is not a selection criterion and not a CI gate, so the D-14 rule does not change.
  - It also appears per slice. When k is 0 the item scores nDCG 0 and is counted separately.

#### Tokenizer dictionary and stemming (LANG-07)
- **D-08:** With `RAG_LEXICAL_DICTIONARY=true`, the shared tokenizer (`src/lib/rag/lexical/tokenize.ts`, one function for chunks and queries, Phase 4 D-07) takes an optional per-tenant **compiled term list**: the canonicals and variants of the tenant's effective TERM dictionary (shared plus tenant layer, enabled entries).
  - Multi-character terms qualify: Han terms of 2 or more characters, and Latin terms of more than one word or with an elision.
  - `translation`-kind entries are included. XLG-05 glossary pairs live in the same dictionary (Phase 6.2 adds the editor), so whatever such entries exist are merged with no extra code.
  - `misspelling` entries and `identifier` entries are excluded. Identifiers go through D-31.
  - A matched term is emitted as **one additional token** (the normalized term with internal whitespace joined by `_`, prefixed so it cannot collide with a natural token). The existing words, bigrams and parts are kept, so recall can only gain.
  - Matching reuses the 4.1.1 matcher (longest match first, non-overlapping, D-10/D-11 there). There is no second matcher.
- **D-09:** Versioning (a LANG-04 ingestion-side change). `LEXICAL_VERSION` is bumped once for the dictionary-capable tokenizer.
  - Each chunk records the dictionary fingerprint its `lexical_text` was built with, in a new column `lexical_dict_version text` (null means no dictionary). The value is the effective TERM version string `s<shared>.w<tenant>` from 4.1.1 D-21.
  - `npm run rag:relex -- --tenant <key> --stale-dictionary` rebuilds only chunks whose stored value differs from the current one, using the same side-by-side relex path.
  - The query side always uses the current dictionary. Because dictionary tokens are additive, a chunk not yet relexed just lacks the bonus and is never excluded. The trace stage detail shows `dict=s12.w3 stale_chunks=<count or unknown>` and no term text (4.1.1 D-21 privacy rule).
  — **Reversibility:** costly — the relexed `lexical_text` of every affected tenant must be rebuilt again to undo it.
- **D-10:** Italian stemming. With `RAG_LEXICAL_STEM_IT=true`, Italian Snowball stemming adds the stem as an **additional** token for Latin words of chunks and queries whose language is `it`. The surface form is kept.
  - The stemmer is a small in-repo pure-TS port of the Snowball Italian algorithm with the official sample vocabulary as test vectors, unless research finds a maintained MIT/BSD package already in the lockfile. No new runtime dependency without that finding.
  - The switch bumps `LEXICAL_VERSION` through its own flag in the version string, so turning it on needs a relex.
  - Default on is decided by a pre-registered rule: on only if the `it` slice Recall@10 gains more than the noise band and no slice drops beyond it, recorded in `eval/decisions/04.2-lexical.json` / `.md`. If the rule passes, the plan flips the default in all config locations. If not, the default stays `false` and the record says why (4.1 D-02/D-13 pattern).
- **D-11:** Once the 3.2 registry exists, the tokenizer reads its per-language rules (stopwords, elision prefixes, accent folding, stemmer availability) from it, as 3.2 D-05 says ("tokenizer switches in 4.2"). An equality test proves the registry values equal today's constants. When the registry is absent, the constants stay (D-02).
  - Fixture tests use only synthetic, neutral content: a synthetic multi-character Han dictionary term that bigrams alone would mis-split, a multi-word Latin term, and one Italian singular/plural pair of synthetic neutral vocabulary.

#### Version-aware retrieval (RET-11)
- **D-12:** `retrievalFilters.versions` takes one of `'current'` (the default), `'all'` or `{ from?: ISODate, to?: ISODate }`. It is Zod-validated in the request body (Phase 4 D-05 filter path) and is accepted only when `RAG_VERSION_SCOPE=true`. When the switch is off the field is ignored and the trace says `versions_ignored`.
  - `currentOnly: true` stays the backend default. The new value travels as a separate `versionScope` field, so every caller that does not ask gets the current versions.
  - `status = 'ready'`, the quarantine filter (D-08 of Phase 3) and tenant scope always apply. Superseded **and ready** rows are the only addition.
  - A range matches a version whose period overlaps `[from, to]`. The period runs from `effective_from` (3.2 D-43), or the document's `created_at` when that is missing, to `effective_to`, or the successor version's start, or open-ended.
  - Callers: an explicit API filter (chat, embed and eval request bodies) now, and QRY-10 (Phase 6.2) later through the same field. Voice always uses current versions.
  - New parameter `p_version_scope` on `hybrid_search_chunks` (D-03 rule) and the same scope on the exact-id, term, table and identifier legs.
- **D-13:** Superseded chunks enter the context with a header line carrying the version number, the effective dates and a `superseded` marker. A current chunk carries the same line only when the scope is not `current`, so the model can compare versions.
  - The line text is localized through the existing localized strings of the assemble stage, with no domain words.
  - Citations and sources carry `version`, `isCurrent` and the effective dates. When Phase 5's `citations[]` record exists at execution time, these fields are added there. Otherwise they go on the source payload only and a hand-off note is written.
- **D-14:** The semantic cache adds a check-bypass reason `version_scope` (in `src/lib/rag/cache/bypass.ts`) whenever the effective scope is not `current`. Such answers are neither checked nor stored.

#### Structured table lookup (RET-12)
- **D-15:** New table `rag_table_rows`, created in migration 0852 (plus its tenant variants). Columns:
  - `id`, the tenant columns of the mode, `document_id`, `version`, `is_current`, `status`
  - `table_key` (document plus table ordinal), `row_index`
  - `header text[]`, `cells jsonb` (column name → cell text)
  - `cell_norm text[]` (normalized cell values via the lexical normalizer, GIN-indexed)
  - `chunk_ids uuid[]`

  RLS is on with no policies (service role only). Rows are written in the `write` stage when `RAG_TABLE_LOOKUP=true`, for chunks with `chunk_kind = 'table'`, by parsing the Markdown table the table-aware chunker already produces. No parser internals are used.
  - `is_current` and `status` follow the document through the existing DATA-07 supersession and delete paths, via cascade and trigger.
  - Backfill: `npm run rag:table-rows -- --tenant <key> [--dry-run]`.
  - The table layout leaves room for a later `access_groups` column (Phase 4.3 copies groups to table rows).
- **D-16:** New optional v2 stage `table_lookup`, after `exact_id_lookup` (Phase 4 D-24 pattern, `onFail: 'skip'`).
  - Query tokens come from `queryLexicalTokens()`. A service-role RPC `rag_table_lookup(p_tenant_key, p_tokens text[], p_min_cells int, p_limit int, p_version_scope ...)` returns rows where at least `min_cells` **distinct** cells match a query token, ranked by matched-cell count and then by row order.
  - The rows' chunk ids form the RRF list `table:0` with weight `TableLookupParams.weight`.
  - `TableLookupParams` defaults: `min_cells = 2`, `limit = 10`, `weight = 1.0`. Sweepable, eval-only overrides.
  - The tenant comes only from `scopeKey` (verified `TenantScope`). The RPC takes token arrays only, never SQL text, and **no LLM writes SQL anywhere**. A static CI check (extending `scripts/ci/check-rag-boundary.mjs`) fails on any call to `rag_table_lookup` outside `@/lib/rag`, and on SQL text built from model output in the lookup module.
- **D-17:** The matching row reaches the context together with its header. When the chunk text already carries the header (3.2 header repetition), nothing is added. Otherwise `assemble` prepends the header row and the matched row to that chunk's context entry, and the trace marks `table_row_attached`.
  - The cross-tenant canary suite (RET-08) gains a `rag_table_rows` case: a tenant B query whose cell values exist only in tenant A returns nothing, in both deployment modes.
  - The fixture table and its questions are synthetic and neutral. The fixture question names **two cell values of one row** (one from a key column, one from a second column).

#### Duplicate clusters and diversity (DATA-21, RET-13, EVAL-20)
- **D-18:** Schema (migration 0853):
  - New columns on `document_chunks`: `dup_cluster_id uuid` and `simhash bigint`.
  - New table `rag_dup_clusters`: `id`, tenant columns, `member_count`, `source_document_ids uuid[]`, `representative_chunk_id`, `updated_at`.
  - The cluster key always includes the tenant, so a cluster never spans tenants (SQL check plus a two-tenant test).
  - Every chunk row stays. Versioning, deletes and citations keep working per document.
- **D-19:** Grouping runs at ingestion when `RAG_DUP_CLUSTERS=true`. It is a non-fatal sub-step of `publish`, so the 13-stage list does not change (3.2 D-32 rule). Failures are logged with `[Ingest]` and repaired by the backfill.
  - **Exact duplicates:** same normalized chunk `content_hash` (Phase 3) within the tenant.
  - **Near duplicates:** a 64-bit SimHash over normalized word or Han-bigram shingles (pure TS) proposes candidates by LSH bands. A candidate is accepted when the cosine of the chunks' stored embeddings (same embedding profile) is at least the threshold.
  - The threshold starts at **0.95**, lives in `DupClusterParams`, and is calibrated by `python -m rag_eval.calibrate dup-clusters` on the fixture corpus (precision first). The calibration tool writes the threshold; it is never edited by hand.
  - Only chunks of current, ready documents of **other** documents are compared. Chunks inside one document are never clustered with each other.
- **D-20:** Keeping clusters correct:
  - Deleting or replacing (superseding) a source document recomputes the clusters it belonged to, through a trigger that marks those clusters dirty plus a service-role `rag_dup_clusters_recompute(p_tenant_key, p_cluster_ids)` called by the delete and supersede paths.
  - A cluster left with one member dissolves (`dup_cluster_id` set to null).
  - Backfill: `npm run rag:dup-clusters -- --tenant <key> [--dry-run]`.
  - The fixture test pastes one synthetic FAQ-shaped passage into 30 synthetic documents. The harness generates these at seed time from one template; 30 files are not committed. The test asserts one cluster per tenant, and checks that deleting one source updates `source_document_ids` and `member_count`.
- **D-21:** New optional v2 stage `diversify`, run after `rerank` and `refusal` and before `expand_parents` (and therefore before Phase 6 D-07 sub-question reservation, which happens at selection). Running after `refusal` keeps the refusal decision and its calibration (RNK-07) unaffected by diversity.
  - `collapse` keeps the best-ranked chunk of each duplicate cluster. The others are dropped from the final top-k and their documents are listed on the kept candidate as `alsoIn: { documentId, filename, chunkId }[]`, which shows under that citation (sources payload and, when present, Phase 5 `citations[]`).
  - `mmr` does `collapse` first, then greedy maximal marginal relevance over the reranked list. Relevance is the rerank score (or the fused score when there is no reranker), min-max normalised. Similarity is 1.0 for the same cluster and otherwise the Jaccard of the candidates' lexical token sets, so there is no I/O.
  - `lambda` is chosen by `python -m rag_eval.sweep diversity` (grid 0.5/0.6/0.7/0.8/0.9 on the dev split) and written to `retrieval-params.json` as `mmr_lambda` by the tool.
  - A chunk that is the only chunk of a sub-question (when Phase 6 tags candidates with a sub-question id) is never removed. Before Phase 6 this guard is a tested no-op.
  - Voice can use both modes. Stage budget: 2 ms chat/embed/voice in `latency-budgets.json`.
  - The existing legacy `src/lib/mmr-scorer.ts` is not reused, because it is a legacy module and needs embeddings.
- **D-22:** EVAL-20 `duplicate_flood` items: 3 per language (zh/en/it, 9 items), compound two-intent questions. Intent A's evidence is the passage duplicated across 30 generated documents with small surface variations; intent B's evidence is one document.
  - Per-item metrics: `topk_redundancy`, the largest share of top-k chunks belonging to one duplicate cluster, and `intent_coverage`, true when gold evidence for every intent is in the top-k.
  - Gates under run config `v2-diversity-collapse` (and `v2-diversity-mmr`): `intent_coverage` = 1.0 on the slice, and `topk_redundancy` at most 1/k (one chunk per cluster under collapse); no other slice drops beyond the noise band versus the 4.1 default config.
  - The default (off) run reports the slice only.
  - Production: `topk_redundancy` goes on the trace and, if Phase 5.1.1's `rag_retrieval_log` exists at execution time, into it as a numeric column. The FBK-10 weekly report row is added only if `rag_eval.weekly_report` exists then; otherwise a hand-off note goes to the coordinator (D-38).

#### Refusal operating points per mode (RNK-07)
- **D-23:** `eval/config/refusal-calibration.json` gains `targets_by_mode`:
  - `strict: { max_false_answer: 0.05 }`
  - `balanced: { target_false_refusal: null }`
  - `flexible: { target_false_refusal: null }`

  `null` means today's `target_false_refusal`. When the whole block is absent or unset, calibration produces exactly the Phase 4 D-18 cells (a test proves byte equality of `refusal-thresholds.json` on the fixture). The `config_hash` covers the new block.
- **D-24:** `python -m rag_eval.calibrate refusal` records for each cell the **full sweep**: every candidate threshold with its false-answer rate (no-answer items answered) and false-refusal rate, on dev and holdout.
  - Strict takes the lowest-false-refusal threshold whose false-answer rate meets the cap.
  - Balanced and flexible take the threshold that meets today's false-refusal target (Phase 4 D-18 rule).
  - The cell key gains `mode` (`strict | balanced | flexible | *`), where `*` is today's single threshold. The schema version is bumped, and a missing mode is read as `*`.
  - The runtime refusal stage looks up `(…, mode)` and falls back to `*`. Cells are still invalidated on reranker, embedding-model or tokenizer change (D-17). A LANG-07 `LEXICAL_VERSION` bump therefore invalidates them, and the plan re-runs calibration.
  - The report states which error each mode favours.
  - The RAG mode reaches retrieval from the existing `RagMode` in `RetrievalOptions`. There is no new request field.

#### TTFT (LAT-04)
- **D-25:** TTFT is measured server-side, from request receipt in the route handler to the first answer text delta written to the stream. It is recorded as `ttft_ms` on the Langfuse trace (and the eval trace) for text chat, embedded chat and voice.
  - For voice, it is measured at `/api/internal/voice-chat` (first text delta to the agent). Agent-side audio latency is out of scope.
  - Each record also carries `pre_generation_ms`, the time until the generator call starts, and `cache: hit | miss | bypass`.
- **D-26:** `eval/config/latency-budgets.json` gains TTFT p50/p95 per channel (chat, embed, voice) and per cache state, plus a `pre_generation` p95 per channel. They are report-only for live traffic (AGENTS.md: until live measurements ratify them).
  - CI gate: a deterministic test with the fake model runs N turns per channel and fails when the pre-generation p95 exceeds the documented budget.
  - A meta-test injects a delay through a test-only setter (`setPreGenerationDelayForTests`, `startup.ts` / `set*ForTests` pattern; **not** an env variable) and asserts that the gate then fails.
- **D-27:** Every answer streams, cache hits included. If the semantic-cache hit path (Phase 6, `src/lib/rag/cache/`) writes the answer in one block, it is changed to emit the stored answer as UI-message-stream text deltas in chunks, with the same final payload. The eval report shows hits and misses as separate rows.

#### Identifier index and filter (RET-15, RET-16, EVAL-32)
- **D-28:** Schema (migration 0854):
  - `document_chunks.identifiers_norm text[]` (GIN) and `identifiers_raw text[]`; `documents.identifiers_norm text[]` / `identifiers_raw text[]` (the union of their chunks).
  - New table `rag_identifier_patterns`: `id`, tenant columns, `name`, `pattern`, `flags`, `enabled`, `created_by`, `updated_at`. RLS on, service role only, written through admin routes.
  - Normalization: NFKC (width fold), case fold, and removal of separators (whitespace, `-`, `_`, `.`, `/`). Original spellings are kept in `_raw`.
  - Extraction uses `IDENTIFIER_PATTERN` (`src/lib/rag/ids/shapes.ts`) plus the tenant's enabled patterns, and runs at `write` when `RAG_IDENTIFIER_INDEX=true`.
  - Backfill: `npm run rag:identifiers -- --tenant <key> [--dry-run]`. Both columns are tenant-scoped like every chunk field.
- **D-29:** Admin patterns. Routes are under `/api/rag/admin/identifier-patterns` (list, create, update, delete, test), owner-or-admin as in Phase 3 D-17. Single-tenant mode uses the deployment layer; multi-tenant mode uses the organization's tenant key.
  - Validation: at most 20 patterns per tenant and at most 200 characters each; must compile with the `u` flag; rejected on nested unbounded quantifiers (static check); a 10 KB probe must run in under 50 ms; must match at least one character of digits or letters.
  - The test endpoint returns the matches and normalized forms for an admin-supplied sample text.
  - A Config UI panel "Identifier patterns" is part of the retrieval settings. It needs a UI-SPEC (`/gsd-ui-phase 4.2`) before its implementation task.
- **D-30:** The lexical tokenizer keeps every identifier whole, including tenant-pattern matches: the tenant's compiled patterns are passed in the same per-tenant options object as D-08. It also emits the normalized form as a token, so differently written forms match lexically.
- **D-31:** With `RAG_IDENTIFIER_FILTER=true` (and the index on), the query's identifiers are extracted and normalized, and a service-role RPC `rag_identifier_resolve(p_tenant_key, p_norm text[])` returns which exist in the tenant.
  - **When they exist:** every leg (dense, lexical, term, exact-id, table) gets `identifiers_norm && p_ids` in its WHERE clause **before ranking**, and parents are fetched for the matching documents. When the filtered search returns nothing, retrieval falls back to the unfiltered hybrid search and the trace says `identifier_filter_fallback`.
  - **Near-miss guard:** after rerank, candidates whose identifiers include an identifier within the near-miss distance of an asked one, and that do not also carry the asked identifier, are removed from the context. The guard always applies while the filter switch is on, and trace counts are recorded.
  - Near-miss distance on normalized forms: Damerau-Levenshtein ≤ 1 for length ≤ 6 and ≤ 2 for longer ones; separator-only and case-only differences count as equal. It is computed in TS over a candidate list from a service-role RPC that pre-filters the tenant's distinct identifiers by length ±2 and a shared prefix or suffix. Research may pick pg_trgm if it is available on both Supabase and PGlite.
  - **When the asked identifier does not exist in the tenant:** strict mode returns the localized "information not available" response plus up to 3 closest existing identifiers as suggestions, and never answers from them. Balanced and flexible modes drop the near-miss chunks and add the same suggestion note.
  - Suggestions only ever come from the caller's tenant.
  - Queries with no identifier take the normal hybrid path unchanged.
- **D-32:** EVAL-32 `identifier_near_miss` items, 6 per language (18 items):
  - 4 answerable, asked in different spellings (separator, case, width variants)
  - 2 whose asked identifier does not exist but has a near-miss

  The fixture documents carry synthetic identifiers that differ by one or two characters or only by separators or case.
  - Metrics: exact-identifier precision (share of answers and citations about the asked identifier only), near-miss leakage (share of items with a near-miss chunk in the context), and the descriptive-question slice.
  - Gates under run config `v2-identifier-on`: precision = 1.0, leakage = 0, the descriptive slice does not drop beyond the noise band, and no other slice drops.
  - A tenant-pattern case adds one synthetic admin-defined pattern to the fixture tenant.

## Summary

The v2 pipeline already has the seams most of this phase needs: an optional-stage runner with skip semantics (`runStage`, `stageSpec`), weighted RRF over named lists, the `exact_id_lookup` stage as a template for an extra deterministic leg, an integer `lexical_version` with a relex job, a refusal cell file read by a pure gate function, PGlite fixture databases that apply every migration, and per-stage latency budgets that are report-only. No new package is needed anywhere in this phase. [VERIFIED: files read this session, quoted in the sections below]

Reading the locked decisions against the code found two that cannot work as written and several that need a small amendment. The two blockers: (1) voice TTFT cannot be measured at `/api/internal/voice-chat`, because that route only saves a chat when a session ends and the voice answer is generated inside the voice agent, never by the app (F-1); (2) superseded chunks have no vectors, because the publish function sets `embedding = NULL` and deletes their `chunk_embeddings` rows, so the dense leg cannot return them under any `versions` value (F-2). The amendments that matter most for planning: the rerank cap is enforced in five places plus generated code, not three (F-3); `LEXICAL_VERSION` is an integer in the column, the trigger, the relex RPC, the refusal cells and the config hash, and an unconditional bump breaks the zero-diff rule and invalidates the live refusal cells (F-4); adding parameters to `hybrid_search_chunks` with `CREATE OR REPLACE` creates a second overload, and the 0850 block sorts after Phase 3.2's 0801–0839 block, which fixes the order in which the two phases may redefine that function (F-5); and the sub-question reservation of Phase 6 is planned inside `rank.ts`, so `diversify` must run there too to stay ahead of it (F-10).

Upstream state on this branch: none of the Phase 4.1, 4.1.1 or 3.2 symbols exist (`RAG_REFUSAL_FLOOR`, `rag_term_effective`, `src/lib/rag/terminology/`, `config/rag/language-packs.json`, `config/rag/settings-classification.json`, `RAG_TABLE_HEADER_REPEAT`, `effective_from`). From Phase 6, `src/lib/rag/cache/` holds only `bypass.ts`, `keys.ts` and `types.ts`; the cache stage, the hit stream (`streamCachedAnswer`) and `reserveSubQuestionCoverage` are planned (06-32, 06-36, 06-25) and not built. From Phase 5, `CitationRecord` and migrations 0501/0502 exist. From Phase 7, the canary suite directory `tests/rag/canary/` (07-14) does not exist yet. [VERIFIED: existence checks run this session]

**Primary recommendation:** plan this phase as a switch-and-contract foundation wave followed by one feature chain per shared file (`search.ts`, `rank.ts`, `context.ts`, the chat route), redefine `hybrid_search_chunks` exactly once for the whole phase, keep the effective lexical version at 2 while both lexical switches are off, deliver superseded versions through the lexical and deterministic legs only, and measure voice TTFT in the voice agent with the numbers posted back to the retrieval trace.

### Pattern 1: nDCG@k with k = chunks sent to the LLM (D-07)

**What:** per item, `k = len(trace.kept)` (the chunks that entered the context; plan 01-04 defines `kept` that way). Order `kept` by `rank`. Each gold unit (a span, or an evidence group when present) is credited once, at the position of the first kept chunk that matches it:

```python
# eval/src/rag_eval/ndcg.py (new). Source: definition in CONTEXT D-07, matching rule from rag_eval/matching.py
import math

def ndcg_at_context_k(first_hit_positions: list[int | None], k: int) -> float:
    """first_hit_positions: one entry per gold unit, 1-based position in kept (rank order) or None."""
    if k == 0 or not first_hit_positions:
        return 0.0
    dcg = sum(1 / math.log2(pos + 1) for pos in first_hit_positions if pos is not None and pos <= k)
    ideal = sum(1 / math.log2(i + 1) for i in range(1, min(len(first_hit_positions), k) + 1))
    return dcg / ideal
```

**Rules:** a refused item or `k = 0` scores 0 and is counted in a separate `k_zero` field; several chunks matching one span earn one credit (otherwise the value can exceed 1); the metric is added to `SweepCell`, `ItemResult` and `SliceMetrics` as an optional field so committed baselines still validate; it is **not** added to `metrics` in `eval/config/noise.json`, which keeps it out of every gate and out of `choose_configuration`.

### Pattern 2: one optional options object through the shared tokenizer (D-08, D-10, D-30)

**What:** every exported tokenizer function takes an optional last argument; omitted, the output is byte-identical to today.

```ts

```

**Call sites to thread (index side):** `chunkLexicalText` in `ingest/stages/enrich.ts`, `ingest/profile-chunks.ts`, `ingest/relex/run.ts`; `lexicalText` in `ingest/stages/images.ts` (two calls) and `ingest/extractors/invoice.ts`. **Query side:** `queryLexicalTokens(variant.text)` in `v2/stages/search.ts`, and the lookups in `retrieval/exact-id.ts`. **Leave on defaults:** `rerank/local-bm25.ts`, `context/compress.ts`, `eval/harness/fake-reranker.mts`, so rerank scores do not move when a lexical switch flips. [VERIFIED: grep of all callers this session]

**Resolver:** options are resolved once per ingest run and once per query by an async function (dictionary through the 4.1.1 loader and its per-tenant cache; patterns through an LRU with the same shape) and then passed to the synchronous tokenizer.

**Token forms:** a dictionary match adds one token, prefix plus the normalized term with whitespace and apostrophes replaced by `_`. Natural tokens start with a letter, a digit or a Han character (identifier tokens match `[A-Z0-9](?:[A-Z0-9._/-]*[A-Z0-9])?`), so any prefix that starts with another permitted character cannot collide; the prefix must not contain `'`, `\` or whitespace. Use a second prefix for stems so stemming never changes matches between non-Italian texts. Identifier normalized forms stay unprefixed: the built-in path already emits the whole and the joined form (`extractCodeTokens`), and matching differently written forms is the purpose.

**Qualifying dictionary terms (D-08):** Han terms of two or more characters; Latin terms of more than one word or with an elision; kinds `misspelling` and `identifier` excluded; `translation` included.

### Pattern 3: version scope as a separate request field (D-12, with F-2)

**What:** `RetrievalFilters` keeps `readonly currentOnly: true` [VERIFIED: `src/lib/rag/backend/types.ts:8`]; a new optional `versionScope` travels next to it. The body schema in `src/lib/rag/query/filters.ts` (`retrievalFilterBodySchema`, strict) gains `versions`; the Pydantic `RetrievalFilters` gains the same field so eval items can set it.

**SQL predicate (lexical leg and deterministic legs only):** the current filter text is `' c.tenant_key = $2 AND c.is_current AND c.status IN (''ready'', ''variant'')'` [VERIFIED: `0602_hybrid_include_undated.sql:132`]. For a non-current scope the lexical leg uses `(c.is_current OR (NOT c.is_current AND c.status = 'ready' AND NOT c.provisional AND <not a re-publish of the same content>))` and, for a range, an overlap test on the version period. Tenant, quarantine and every other filter stay as they are.

**Two exclusions the decision does not mention:** (1) provisional versions: progressive ingestion publishes a fast version flagged `provisional = true` and supersedes it minutes later [VERIFIED: `supabase/migrations/0358_progressive.sql:43-44`]; (2) re-publishes of unchanged content: a document-type change re-ingests the same text as a new version (DATA-10). Without both, `versions: all` returns a copy of the current text labelled as an earlier version. Rule: a superseded version is included only when it is not provisional and its document `content_hash` differs from its successor's.

**Period:** start is `effective_from`, else `created_at::date`; end is `effective_to`, else the successor's start (`documents.superseded_by`), else open. Probe `pg_attribute` for the effective-date columns and build the expression with `EXECUTE`, as `rag_publish_document_version` does for `content_type` and `slug` (`has_slug`), so the same migration works before and after Phase 3.2.

**Labels:** context blocks are grouped by `document_id`, and two versions of one lineage are two documents that can share a filename, so the label line is what tells them apart. Fetch labels with one batched RPC only when the scope is not `current`.

### Pattern 4: table lookup leg, modelled on `exact_id_lookup` (D-16)

export async function tableLookup(scope: TenantScope, tokens: string[], params: TableLookupParams, options: { client: RpcClient; signal: AbortSignal; versionScope?: VersionScope }) {

### Pattern 5: duplicate clusters and diversity (D-18..D-21, with F-10 and F-11)

- **SimHash:** 64-bit over normalized word shingles (Han: character bigrams). Send it to Postgres as a string and store it with `BigInt.asIntN(64, value)` semantics; a JSON number above 2^53 loses bits.
- **Band layout guidance:** the probability that one SimHash bit differs is the angle between the two shingle vectors divided by π. At cosine 0.95 that is about 0.10 per bit, about 6.5 of 64 bits. Four 16-bit bands guarantee a shared band only up to 3 differing bits; with 8 bands of 8 bits the chance that at least one band is equal at 0.10 per bit is about 0.99, at the price of larger buckets. Recommend 8 × 8 bands, then a Hamming filter, then the cosine check in SQL (`1 - (a.embedding <=> b.embedding)`) restricted to the same tenant, the same embedding profile, the same chunking profile, current and ready rows, and other documents. [ASSUMED: derivation from the standard SimHash collision property, not measured on the fixture]
- **Keeping clusters correct:** documents are hard-deleted by `DELETE /api/documents/[id]` (`document_chunks` delete, then `documents` delete by lineage), soft-deleted by `rag_soft_delete_document`, and superseded by `rag_publish_document_version`. A statement trigger on `document_chunks` (after delete, and after update of `is_current` or `status`) that marks the affected clusters dirty covers all three without editing those paths; the recompute RPC is then called by the delete and supersede callers and by the backfill.
- **Diversity:** pure function over the reranked list. `collapse` keeps the first member of each cluster and builds `alsoIn` from the dropped members, which already carry `documentId`, filename and `chunkId`; for the complete source list of a cluster use one batched lookup in the context stage, in parallel with `expand_parents`, with skip-on-failure.
- **Redundancy metric:** add an optional `dup_cluster_id` to the kept chunks of the trace; the eval computes `topk_redundancy` from it. That works with the diversity switch off, which D-22 needs for the report-only default run.

- **Budgets:** `LatencyBudgets` gains optional sections (`ttft` per channel and cache state, `pre_generation` p95 per channel) in the style of the optional `groundedness` section, so the committed file keeps validating. `Profile = Literal["chat", "embed", "voice"]` [VERIFIED: `rag-sidecar/src/rag_sidecar/contracts/latency.py:7`].
- **Cache state:** `hit | miss | bypass`. Until 06-32 and 06-36 land, every request reports `bypass`; the report still shows the three rows.

### Pattern 8: identifier index, filter and guard (D-28..D-31, with F-13, F-14)

- **Normalization (one function for index and query):** NFKC, case fold, remove whitespace and `-`, `_`, `.`, `/`.
- **Extraction:** the built-in pattern is `export const IDENTIFIER_PATTERN = /(?<![A-Z0-9._/-])(?=[A-Z0-9._/-]*\d)[A-Z0-9](?:[A-Z0-9._/-]*[A-Z0-9])?/giu;` [VERIFIED: `src/lib/rag/ids/shapes.ts:6`] plus the tenant's enabled patterns; overlapping matches resolve leftmost-longest.
- **Filter decision:** `rag_identifier_resolve` answers which normalized identifiers exist in the tenant's current, ready documents. Existing ones go to every search call as `identifiersNorm`; an empty filtered result triggers one unfiltered rerun with `identifier_filter_fallback`.
- **Guard:** after rerank, extract each candidate's identifiers from its content in memory, and drop a candidate that carries an identifier within the distance rule of an asked one and does not carry the asked one. Distance on normalized forms: at most 1 for length up to 6, at most 2 above.
- **Not found:** status `empty`, reason `identifier_not_found`, `refusalCandidate: true`, and up to three suggestions from the tenant-wide candidate RPC (skip on failure: no suggestions).
- **Patterns at match time:** validated patterns still run on every chunk and query, so cap the input length per call and the number of patterns (20, D-29).

## Common Pitfalls

### Pitfall 1: a second `hybrid_search_chunks` overload
**What goes wrong:** PostgREST answers PGRST203 (ambiguous function) or silently calls the older body, and the new overload is executable by `anon`.
**Why it happens:** `CREATE OR REPLACE` with an appended parameter is a new function; fixture databases also re-apply 0407, 0413 and 0602 on top of the folded setup, which recreates the old signatures on every run.
**How to avoid:** drop all overloads by catalog lookup, create, revoke, grant, in one transaction (Code Examples). Assert `count(*) = 1` after applying all migrations once and twice.
**Warning signs:** `hybrid-grants` or `search-rpc-grants` tests fail; a search test passes locally only when run alone.

### Pitfall 2: losing another phase's filter in a rebase
**What goes wrong:** `p_include_undated` (Phase 6), and later `p_scopes`, `p_effective_on` (Phase 3.2), stop working.
**Why it happens:** the body was copied from an older definition, or migrations of two phases sort in the opposite order to the one they were written in.
**How to avoid:** F-5 (c) and (d). The precondition task reads the newest definition by function name from the migration directory and from the folded setup files and refuses to continue when a lower-numbered unmerged block of another phase plans to redefine the function.
**Warning signs:** `tests/rag-db/hybrid-include-undated.test.mts` or `hybrid-filters.test.mts` fails after the new migration.

### Pitfall 3: off-identity broken by additive contract fields
**What goes wrong:** `refusal-thresholds.json`, `retrieval-params.json` or their `config_hash` change although no feature is on.
**Why it happens:** `model_dump(mode="json")` writes `null` for every new optional field, and `compute_config_hash` hashes the dump.
**How to avoid:** new optional fields drop out of the dump when unset; a test regenerates each committed config with the tool and compares bytes.
**Warning signs:** `eval/tests/test_config_files.py` or `test_fixture_calibration_outputs.py` fails; the thresholds hash in `retrievalConfigHash` changes and the paired run shows differences.

### Pitfall 4: history queries return a copy of the current text
**What goes wrong:** `versions: all` shows two "versions" with identical content.
**Why it happens:** provisional versions and re-publishes of unchanged content are superseded, ready rows.
**How to avoid:** Pattern 3 exclusions; a test with a provisional pair and a document-type-change pair.

### Pitfall 5: additive tokens pushed out by the 64-token query cap
**What goes wrong:** a long Chinese question matches without its dictionary term.
**Why it happens:** Han bigrams alone can fill the cap.
**How to avoid:** F-19 ordering and cap; a test with a query of more than 64 natural tokens.

### Pitfall 6: stemming on folded text
**What goes wrong:** the port passes hand-made cases and fails the official vectors, or stems accented forms wrongly.
**Why it happens:** the tokenizer removes accents before words exist.
**How to avoid:** F-20; vector test on the raw function, separate tokenizer test for the folded stem token.

### Pitfall 7: table rows of an inactive chunking profile
**What goes wrong:** with a non-legacy chunking profile active, the table leg adds legacy chunks to the context next to the profile's chunks.
**Why it happens:** each chunking profile has its own chunk rows; `hybrid_search_chunks` filters by the effective profile, a naive lookup does not.
**How to avoid:** F-7; a test with a `building` then `active` profile (helper `tests/helpers/chunking-profile-fixture.mts`).

### Pitfall 8: backfills that touch every row fire every trigger
**What goes wrong:** a backfill invalidates the tenant's semantic cache or fills the vector-sync outbox.
**Why it happens:** statement triggers exist on `documents` (semantic cache, vector sync) and `document_chunks` (vector sync, lexical tsv). The chunk vector-sync trigger compares a fixed column list that does not include the new columns, so chunk backfills do not enqueue; updates to `documents` (the identifier union columns) run the document triggers.
**How to avoid:** write document-level identifier columns in batches, check what `rag_semantic_cache_on_documents_update` compares before choosing the write shape, and state the cache effect in the CLI output.

### Pitfall 9: duplicate-flood fixtures perturb old items
**What goes wrong:** the paired check on pre-existing golden items is not zero after 90 near-identical documents join the corpus.
**Why it happens:** new documents are new distractors for the n-gram fixture embedder.
**How to avoid:** invented vocabulary that shares no content word with the existing corpus; run the paired check before recording anything; existing fixture tests (`eval/tests/test_fixture_quotes.py`, `test_fixture_coverage.py`, `test_fixture_pii.py`) must be extended for generated documents rather than bypassed.

### Pitfall 10: a flaky latency gate
**What goes wrong:** the TTFT gate fails on a slow CI runner.
**How to avoid:** F-18; never gate on p50; keep N small enough for the 60 s test timeout.

### Pitfall 11: shared generated files and shared route files
**What goes wrong:** two plans regenerate contracts or edit the 4,500-line chat route in the same wave and one result is lost.
**How to avoid:** the ownership table in the plan breakdown; contract changes only in P01.

### Pitfall 12: an identifier written with spaces
**What goes wrong:** a tenant pattern matches text containing spaces; the whole form cannot be a lexical token and is silently dropped, so the lexical leg never matches it.
**How to avoid:** emit the normalized form only (F-19) and test it.

### Pitfall 13: external backends do not know the new request fields
**What goes wrong:** with Weaviate or Qdrant selected (Phase 7 adapters; `src/lib/rag/backend/qdrant/` already exists), a request with a version scope or an identifier filter is answered as if the field were absent: superseded text is missing, or near-miss chunks pass the filter.
**Why it happens:** `versionScope` and `identifiersNorm` are new fields on `BackendSearchRequest`; an adapter that ignores unknown fields fails open.
**How to avoid:** a request that carries either field is served by pgvector (the RET-09 fallback path, reported `degraded` with a reason) until an adapter declares support; add a conformance case to `tests/rag/backend-conformance/` so an adapter that ignores the field fails. The table, exact-id and identifier-resolve legs always run on Supabase.

### First text delta on any UI message stream
```ts
// src/lib/rag/trace/ttft.ts (new). Chunk type 'text-delta' is the one the chat route writes today.
export function withFirstTextDelta<T extends { type: string }>(stream: ReadableStream<T>, onFirst: () => void): ReadableStream<T> {
  let seen = false;
  return stream.pipeThrough(
    new TransformStream<T, T>({
      transform(chunk, controller) {
        if (!seen && chunk.type === 'text-delta') {
          seen = true;
          onFirst();
        }
        controller.enqueue(chunk);
      },
    }),
  );
}
```

### Time-boxed probe of an admin pattern
```ts
// src/lib/rag/identifiers/probe-worker.ts (new). worker.terminate() stops a runaway match (Node 22 docs).
import { Worker } from 'node:worker_threads';

const WORKER_SOURCE = `
  const { parentPort, workerData } = require('node:worker_threads');
  const pattern = new RegExp(workerData.source, workerData.flags);
  let matches = 0;
  for (const probe of workerData.probes) { pattern.lastIndex = 0; for (const _ of probe.matchAll(pattern)) matches += 1; }
  parentPort.postMessage({ matches });
`;

export function probePattern(source: string, flags: string, probes: string[], deadlineMs: number): Promise<'ok' | 'too_slow' | 'invalid'> {
  return new Promise((resolve) => {
    const worker = new Worker(WORKER_SOURCE, { eval: true, workerData: { source, flags, probes } });
    const timer = setTimeout(() => void worker.terminate().then(() => resolve('too_slow')), deadlineMs);
    worker.once('message', () => { clearTimeout(timer); void worker.terminate(); resolve('ok'); });
    worker.once('error', () => { clearTimeout(timer); resolve('invalid'); });
  });
}
```
The deadline here must be larger than D-29's 50 ms to cover worker start-up; measure the match time inside the worker and compare that number with 50 ms, and keep the outer deadline as the kill switch.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes (admin routes, internal voice route) | `checkAdmin` with a live Supabase session; `internalApiKeyMatches` plus the signed scope token |
| V3 Session Management | no new surface | — |
| V4 Access Control | yes | Tenant only from `TenantScope` / `scopeKey`; `rag_assert_tenant_key` first in every function; RLS on with no policies; EXECUTE revoked from `PUBLIC, anon, authenticated` |
| V5 Input Validation | yes | Zod (`zod/v3`, strict objects) for `versions`, pattern bodies, the timing body; Pydantic contracts; token arrays as bound parameters; limits on pattern count and length |
| V6 Cryptography | no | SimHash and content hashes are not security controls |
| V7 Error Handling and Logging | yes | Counts only in traces and logs (D-34); structured JSON errors; no pattern, identifier, term or cell text logged |

### Known Threat Patterns for this phase

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Cross-tenant read through a new table, RPC, cluster or suggestion list | Information disclosure | Tenant column on every row and in every predicate; cluster key includes the tenant (SQL check); two-tenant tests in both modes for every table and RPC; suggestions read only the caller's tenant |
| New function overload executable by `anon` | Elevation of privilege | Drop-then-create with explicit `REVOKE`/`GRANT` (F-5); grants tests through PostgREST on the fake edge |
| A widening filter exposing withdrawn text | Information disclosure | `versions` only adds superseded rows that are ready, not provisional, not deleted, not quarantined; ignored unless the switch is on; cache bypass; open question 2 for the embed widget |
| Regular-expression denial of service from an admin pattern | Denial of service | Static rejection, worker-thread probe with termination, caps on count, length and input size (F-14) |
| SQL built from user or model text | Tampering | Token and identifier arrays only as bound parameters; dynamic SQL inside functions uses `format` with `%L` and `USING`; boundary check rule for the lookup module; no model writes SQL |
| Spoofed voice timing | Tampering | Internal key and scope token required; numeric bounds; score names fixed; write only for an id shaped like a trace id |
| Stored cross-site scripting through pattern names in the Config UI | Tampering | Text nodes only, as in `tests/ui/config-ui-xss.test.ts`; length limits |
| Dictionary or pattern cache served across tenants | Information disclosure | Cache keyed by tenant key with a two-key test (4.1.1 T-0411-13 pattern) |
| Identifier existence oracle | Information disclosure | Resolve and suggestions are scoped to the caller's verified tenant; nothing is returned for other tenants |
