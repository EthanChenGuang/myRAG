## Task 2: feature seeding

`seedFixtureFeatures(fixture, { deploymentMode, admin })` reads the run's typed configuration (`loadRagConfig(getRagDeps().ragEnv())`). It mints the fixture tenant's scope: `s:default` in single-tenant mode, `u:<fixture user>` in multi-tenant mode. Then it runs only the steps whose switch is on:

| Switch | Step (product code) | Inputs-hash entry |
|---|---|---|
| RAG_IDENTIFIER_INDEX | inserts `eval/fixtures/identifier-patterns.json` as the owner (checked by `validateIdentifierPattern`, fixed id), then `backfillIdentifiers` | `lexical_patterns:<p…>` |
| RAG_LEXICAL_DICTIONARY / _STEM_IT / RAG_IDENTIFIER_INDEX | `resolveLexicalOptions` for the stamp, then `runRelex({ config, tenantKey })` | `lexical_effective_version:<v>`, `lexical_dict_version:<s…>` |
| RAG_TABLE_LOOKUP | `backfillTableRows` | `table_rows:on` |
| RAG_DUP_CLUSTERS | `runDupBackfill({ evalRun: true })` | `dup_clusters:eval_run` = sha256 of `eval/config/dup-cluster-params.json` (empty when absent) |

Cache-key format: each entry is `<name>:<value>` → sha256(value), added to `sqlSha256`, like the existing `lexical_version:2` key. A step that fails to load its options, or a backfill that reports failed documents, throws. The run stops rather than measuring a half-seeded database.

Where it runs: `prepareInProcessEval` calls it for prechunked builds only, right after the re-embed step, once the fixture edge and the run's process env are in place. The ingest mode writes these stores during ingestion with its build env.

Product change: `DupBackfillInput.evalRun?` is passed to clustering only when it is `true`. The `rag:dup-clusters` CLI does not set it, so its call is byte-identical to before (the unit test checks the option keys).

Fixture pattern: `\b[A-Z]{2}-[A-Z]{3}-[A-Z]{3}\b` (flags `u`). It matches the no-digit codes QJ-XUV-QOR, KZ-OWA-FUD and WX-YEM-GIT, which the built-in rule skips because it requires a digit.

## Finding (not fixed here): one LSH miss

The chunk of `dup-passage-09.it.md` in the "Campane trenniche" section is never offered as a candidate. Its cosine with its siblings is 1.0. Its SimHash, computed over the content including the per-copy `Document: <file>` header, is 15 or more bits away from every sibling, so it shares none of the eight 8-bit bands. That section's cluster therefore has 29 members. The test pins this as `KNOWN_LSH_MISSES` and fails if it changes. This is a recall property of the 04.2-13 banding over header-prefixed content. A product fix would hash the content without the contextual header, which belongs to a 04.2-13 follow-up.

## Deviations from Plan

1. **[Rule 3] Seeding placement.** The plan puts the seeding inside `createFixtureDatabase`. The product loaders and backfills import `env.ts`, which caches at import, and the prechunked build runs before the fixture edge and the run env exist. So the seeding is the exported `seedFixtureFeatures` in `pglite-supabase.mts`, called by `prepareInProcessEval` right after the edge starts. The plan's greps (`resolveLexicalOptions`, `evalRun`) hit that file.
2. **[Rule 1] Calibration command.** `calibrate dup-clusters` has no `--fixture-mode` flag. It ran with the defaults (fixture source, prechunked pair harness). Its report is `dup-cluster-calibration.md`, not `report.md`.
3. **[Rule 2] Report contents.** Following the precedent of `retrieval-sweep-fixture`, only the summary JSON and MD are committed. The per-lambda cell runs (39 MB) and the 1.7 MB pair dump can be regenerated with the commands above.
4. **[Rule 1] 04.2-31 test expectation.** `test_phase42_gate.py` asserted that every feature run config has `overrides: null`. `v2-diversity-mmr` now carries the tool-written `diversity.mmr_lambda` and no other key.
5. **Cluster expectation.** The plan expected one cluster of 30 per language. The template has three sections plus a per-copy marker chunk, so the check is one cluster per section, and the marker chunks stay unclustered. One known LSH miss is pinned (see Finding).
