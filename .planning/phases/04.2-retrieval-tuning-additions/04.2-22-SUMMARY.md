## Behaviour changes (switches on only)

- `RAG_LEXICAL_DICTIONARY` / `RAG_LEXICAL_STEM_IT` / `RAG_IDENTIFIER_INDEX` on: one `resolveLexicalOptions` call per request from the request's verified scope; every query variant's lexical tokens carry the dictionary, identifier and stem tokens first (capped at 16 by the tokenizer, D-55).
- Search stage detail: `dict=<version> stale_chunks=<n|unknown>` while the dictionary is on and loaded, `dict=unavailable` when the load failed. Version strings and counts only.
- Hash keys: `tuning.lexical_dictionary_version` (dictionary on), `tuning.identifier_patterns` (identifier index on, next to the existing `identifier_index: true`). Both the result hash and the semantic-cache key read the same stamp.
- Resolver failure: default tokens, one `[RAG Lexical]` warning with code `lexical_options_unavailable`, request continues.

Off-state: the resolver is not called, tokens, detail, candidates and `retrievalConfigHash` are unchanged (unit identity test, pinned off-hash, e2e off-before/off-after comparison through the eval route). Strict "information not available", webSearch/Exa, `source_images`, `{{context}}`, voice and embed are untouched.

## Stale-count call cost

`rag_lexical_stale_count` on the single-tenant PGlite fixture (107 chunks): p50 0.47 ms, max 1.23 ms over 20 calls. It runs beside the search legs, bounded at 250 ms and cached 60 s per tenant and dictionary version, so the expected added latency is ~0 on a warm cache. Production cost on large tenants (a count over current ready chunks with `lexical_dict_version IS DISTINCT FROM`) is an operator measurement; the 250 ms bound keeps the stage safe either way.
