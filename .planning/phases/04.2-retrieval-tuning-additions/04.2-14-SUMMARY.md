# Phase 04.2 Plan 14: identifier pattern backend Summary

**Tenants can now store identifier patterns through tenant-bound service-role functions. Each pattern is checked statically and probed in a worker thread that is killed at its deadline, and ingestion and retrieval can load the compiled patterns per tenant. Nothing calls the new code yet, so runtime behaviour is unchanged.**

## Final SQL signatures (0858)
All six functions are `SECURITY INVOKER` with `SET search_path = ''`. Each one calls `rag_assert_tenant_key` first, is revoked from PUBLIC, anon and authenticated, and is granted to service_role.

The functions return this row type, written `PatternRow` below:

`(id uuid, name text, pattern text, flags text, enabled boolean, created_at timestamptz, updated_at timestamptz)`

| Function | Returns | Refusals (message starts with) |
| --- | --- | --- |
| `rag_identifier_patterns_list(p_tenant_key text)` | `PatternRow` in creation order | — |
| `rag_identifier_pattern_create(p_tenant_key text, p_name text, p_pattern text, p_flags text, p_enabled boolean, p_created_by uuid)` | the stored `PatternRow` | `limit_reached` (54000), `name_exists` (23505), `invalid_name` / `invalid_pattern` / `invalid_flags` (22023) |
| `rag_identifier_pattern_update(p_tenant_key text, p_id uuid, p_name text, p_pattern text, p_flags text, p_enabled boolean)` (NULL means unchanged) | the updated `PatternRow`, with `updated_at` always moved forward | `pattern_not_found` (P0002), `name_exists`, 22023 as above |
| `rag_identifier_pattern_delete(p_tenant_key text, p_id uuid)` | the deleted `uuid` | `pattern_not_found` (P0002) |
| `rag_identifier_resolve(p_tenant_key text, p_norm text[])` | `(norm text, raw text)`, one stored spelling per existing form | `too_many_identifiers` (22023, over 16 inputs) |
| `rag_identifier_candidates(p_tenant_key text, p_norm text, p_limit integer)` | `(raw text, norm text)`, ordered by length difference, then form | `invalid_identifier` (22023, over 200 characters) |

- The name is trimmed. The count for the limit of 20 and the name check run under `pg_advisory_xact_lock(hashtextextended('rag_identifier_patterns|' || tenant, 0))`.
- `resolve` and `candidates` read only rows where both the chunk and its document are current and ready. The tenant appears in the predicates for both tables. `identifiers_raw` is unnested alongside `identifiers_norm` with `ROWS FROM (...) WITH ORDINALITY`, because the multi-argument `unnest` form cannot be schema-qualified.
- `candidates` returns forms whose length is within 2 of the input and that share a 2-character prefix or suffix with it. The input itself is excluded. An input shorter than 2 returns no rows. The limit defaults to 10 and is capped at 50.
- No 0410 entry was added, because none of the functions is `SECURITY DEFINER`. No purge hook was added either: 0858 adds no store, and 0854 already registers `rag_purge_hook_identifiers`.

## Probe and limits
| Rule | Value |
| --- | --- |
| Outer deadline for the probe | 1000 ms |
| Outer deadline for the test run | 2000 ms |
| Probe time, measured inside the worker | at most 50 ms |
| Concurrent workers | at most 4 |
| Worker resource limits | 64 MB old generation, 16 MB young generation, 4 MB stack |
| Loader cache | 256 tenants, 60 s TTL; a failure is cached for 5 s |

Spans are kept per pattern and input, and counting continues past the cap.

The loader compiles patterns with `gu` or `giu` in creation order, ready to pass as `extraPatterns` (04.2-34). Matching on chunk and query text stays on the caller's thread. That is acceptable because it uses only validated patterns, at most 20 of them, on input capped by `extractIdentifierEntries`, as the plan describes.

The `@/lib/rag` barrel exports are left to 04.2-17, as planned.

## Deviations from Plan
1. **The nested-quantifier rule is narrower than its literal wording.** It rejects a quantified group whose maximum is above 1 when that group contains a quantifier. An optional group (`?`) counts as not repeating, so common shapes such as `[A-Z]{2}(?:-[0-9]{4})?` are accepted. The worker probe still catches patterns that are slow in practice, and it is tested with `(?:x|x)*y`.
2. **`matches_empty` is decided statically** rather than by running the pattern on an empty string. This keeps to the rule that no admin pattern runs outside the worker.
3. **`checkIdentifierPattern` is exported** in addition to the listed exports, so that the routes and later plans can reuse the full check.

## Decisions for STATE
- Admin identifier patterns run only in an inline `node:worker_threads` worker that is terminated at its deadline. The 50 ms probe rule uses the time measured inside the worker.
- The nested-quantifier rule applies to repeating groups (maximum above 1). Optional groups are allowed.
- The identifier-pattern code words are `limit_reached`, `name_exists` and `pattern_not_found`, and the nine finding codes are fixed as listed above.
