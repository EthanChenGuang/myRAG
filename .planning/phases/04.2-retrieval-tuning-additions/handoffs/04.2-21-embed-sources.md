# 04.2-21 hand-off: the embed route has no sources payload

For: coordinator, plan 04.2-26 (sources panel) and any later embed-widget plan.

## Finding

Plan 04.2-21 Task 3 asked to copy `version`, `isCurrent`, `effectiveFrom`, `effectiveTo` and `alsoIn` onto "the embed route's sources payload".
`src/app/api/embed/chat/route.ts` sends no sources to the client: its stream is `result.toUIMessageStream()` with at most a `feedbackToken` in the
start metadata, and the widget (`src/app/embed/window/page.tsx`, `src/app/embed/chat.js/route.ts`) renders no sources. `cacheSourcesFromResult`
is a server-side cache record, not a client payload.

## Decision taken (executor)

No sources payload was added to the embed stream. Adding one would send filenames of documents (including the other documents of a duplicate
cluster) to anonymous embed visitors for the first time, with no consumer to render them. The embed stream is therefore byte-identical with every
switch on or off. The embed route's only change in this plan is `channel: 'embed'` on its `runRetrieval` input (D-58, Task 4).

The fields are on `RetrievalResult.usedDocuments` for the embed profile too, so a later plan that gives the widget a sources panel can map them
with `sourceDocumentFields(doc)` from `@/lib/rag` (the helper the chat route uses), the same way.

## Open for the owner

Whether the embed widget should ever show sources (filenames) to anonymous visitors. If yes, that plan owns the payload, the widget UI and the
threat entry (T-04.2-80 scope grows from version fields to filenames).
