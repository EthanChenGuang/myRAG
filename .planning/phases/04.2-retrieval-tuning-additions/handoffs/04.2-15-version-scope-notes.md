# 04.2-15 version scope: notes for the coordinator

Plan 04.2-15 (RET-11) adds the `retrievalFilters.versions` request field, the effective version scope in the v2 search stage, the context version line and the source version fields.

## (c) "set by QRY-10"

RET-11 says the version scope is "set by QRY-10". Phase 6.2 delivers this through the same request field, `retrievalFilters.versions`. That field becomes `RetrievalFilterInput.versionScope` (via `parseRetrievalFilters`), and the search stage turns it into the effective scope with `effectiveVersionScope` (`src/lib/rag/query/filters.ts`).
- QRY-10 sets `versionScope` on the filter input. It does not need a second path.
- The rules for the switches, voice and embed are applied in one place, so QRY-10 inherits them.

## (e) Superseded vectors: decided (owner, 2026-11-25, D-58)

Superseded chunks keep losing their vectors at publish. History retrieval stays lexical and deterministic only:
- It reaches superseded text through the lexical leg, the `term:0` list and the exact-id lookup.
- The search stage records `superseded_dense_unavailable` for every non-current scope.
- History questions with little word overlap can miss. This is the confirmed design; no further decision is needed.

## (f) Embedded chat: decided (owner, 2026-11-25, D-58)

Embedded chat accepts `versions` only while `RAG_EMBED_VERSION_SCOPE` is also on. Plan 04.2-39 added the switch.

Plan 04.2-15 already applies it in the shared rule `effectiveVersionScope`:
- The `embed` profile honours a non-current scope only with `config.v2.embedVersionScope`.
- Otherwise the scope is current and the trace says `versions_ignored`.

I did this now so that the embed route never serves superseded text on `RAG_VERSION_SCOPE` alone in the window before plan 04.2-21 lands.

Plan 04.2-21 Task 4 still adds `channel: 'embed'` on `RunRetrievalInput` and its end-to-end test. It should extend the same function rather than add a second rule.
