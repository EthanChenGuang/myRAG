# 04.2-16 hand-off: where a fixture duplicate threshold applies (2026-11-26)

For plans 04.2-29 (fixture runs) and 04.2-33 (live runs).

- `dupClusterThreshold(profileId, { evalRun })` applies a `fixture` entry only when `evalRun` is true. Only
  `eval/harness/run-dup-pairs.mts` sets it today.
- In the in-process ingest fixture mode (`--fixture-mode ingest`), clustering runs in the publish sub-step through
  `clusterPublishedDocument(scope, documentId, { signal })`, which does not pass `evalRun`. So a fixture entry does **not** apply to
  those eval builds yet. If 04.2-29 needs the fitted value in ingest-mode eval runs, it must pass `evalRun: true` from the eval
  harness. Two ways: a harness-only ingest hook, or `clusterChunks(..., { evalRun: true })` after the build. Production callers must keep the default.
- The fixture database's active embedding profile is `openai-3-small-1536`, the same id as the legacy production profile. So the
  fixture entry is keyed by that id. Production ignores it because `evalRun` is false. A fixture run also never replaces a `live` entry
  of that id: it reports `write_skipped_reason` and writes nothing.
- Today's committed corpus has no `fixture_dup_template` documents (04.2-37 adds them). `calibrate dup-clusters` therefore ends
  `uncalibrated`, with the reason "no same_template pair with a cosine". The golden set has no `duplicate_flood` items, so every
  lambda ties in `sweep diversity` and the last tie-break picks 0.9. Run both after 04.2-37.
