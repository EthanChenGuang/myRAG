## Cause (diagnosed, not fixed: a failed gate is a result, not a reason to tune)
- The Phase 5.2 fixture loads `p52-rules-v1.*.md` and `p52-rules-v2.*.md` as two separate **current** documents (no lineage). The trace has no `is_current` or `document_version` on the kept chunks.
- Matching sections of v1 and v2 differ only in one value. Example from the `en-stale-version-003` trace: "spectators stand at least 15 metres" (v1) and "... 20 metres" (v2). The `diversify` stage puts them in one near-duplicate cluster (`collapsed: 20` of 75) and keeps the higher-scored representative. Here that is the v1 chunk, so the v2 gold chunk drops out of the top 10.
- Product effect: with `RAG_RESULT_DIVERSITY=collapse|mmr`, two documents that are near-copies but carry conflicting values can lose the correct one. That is the conflict case Phase 5.2 tests. Off (the shipped default) is unaffected.

## Options for the owner or coordinator (no option chosen here)
1. Diversity never collapses chunks of different documents when their texts differ in a number or another value token. The cluster key or the collapse rule would compare value tokens, not only the SimHash band.
2. Collapse only inside one document lineage or one source, never across distinct current documents.
3. Model the 5.2 fixture versions as one lineage (v1 superseded by v2) so the version scope removes v1 before diversify. This changes the fixture, not the product; it does not cover tenants that upload two current near-copies.
4. Exclude `stale_version` from the diversity slice check. That loosens the spec and needs an owner decision; the plan forbids it here.

Re-check after a fix: `--only diversity --reuse eval/reports/phase-04.2`. Then re-run 04.2-32 from Task 2.

## Decision and second re-run (2026-11-27)
- Orchestrator decision under owner delegation: **option 1**. Implemented in `src/lib/rag/v2/diversify.ts` (commits f60515de RED, then the fix). Chunks of different documents in one cluster whose value tokens differ are no longer collapsed. Value tokens are the D-28 identifier normalization of the chunk body, without the stored header. Same-document variants and identical cross-document copies collapse as before.
- Full gate re-run, spec unchanged: the `stale_version` offenders are gone (`en-stale-version-003` and `it-stale-version-003` keep their v2 gold chunk), and every other gate still passes. The diversity gate still fails, now with **one new offender**:
  - v2-diversity-collapse: `zh-duplicate-flood-002` topk_redundancy 0.2500 > 1/8 = 0.1250 (mmr: within the limit).
- Cause: the kept top 8 of that item now holds `p52-rules-v1.zh.md` and `p52-rules-v2.zh.md` "船体长度" (1.2 m against 1.6 m). They are one SimHash cluster with conflicting values, and option 1 keeps both by design. `topkRedundancy` (D-22, the same function feeds the gate and `rag_retrieval_log.topk_redundancy`) counts cluster ids only, so 2 of 8 kept chunks share a cluster. Before the fix the v1 chunk swallowed v2 and the item passed.
- This is a conflict between option 1 and the redundancy measure, not a tuning question. I did not change the spec or the metric. Options:
  1. Measure redundancy per (cluster, value signature), so value-distinct members that collapse would not merge count separately. This is consistent with option 1 and changes `topkRedundancy`, so the logged `topk_redundancy` follows too.
  2. Keep the cluster-only measure and accept the item as an expected offender. This needs a spec change, which needs an owner decision.
  3. Split value-distinct members into their own cluster at clustering time (`rag_dup_*` / `src/lib/rag/dedupe/cluster.ts`), so cluster ids already mean "same values". This is a larger change and needs a rebuild (`npm run rag:dup-clusters`).
