# 04.2-06 hand-off: eval tuning overrides do not reach the request hash yet

Date: 2026-11-26

`effectiveTuningParams(profile, config, overrides)` accepts the eval-only `table_lookup`, `diversity` and `dup_cluster`
blocks of the API `RetrievalOverrides` contract and applies them for profile `eval` only.

The internal `StageOverrides.retrievalOverrides` type (`src/lib/rag/types.ts`) has no fields for them, and the eval
route does not map them yet. `requestRetrievalConfigHash` therefore calls `effectiveTuningParams(..., undefined, ...)`:
the hash uses the contract defaults (or the committed `mmr_lambda`) for every profile.

Whoever first consumes an eval tuning override (the table leg in 04.2-1x, `diversify`, the dup-cluster sweep) should:

1. add `tableLookup`, `diversity` and `dupCluster` (or the snake_case blocks) to the internal `RetrievalOverrides`;
2. map them in `evalRetrievalOverrides` (`src/lib/rag/v2/overrides.ts`) or a sibling helper, profile eval only;
3. pass the mapped object as the third argument of `effectiveTuningParams` in `requestRetrievalConfigHash`
   and in the stage that reads the parameter, so the hash and the stage agree.

The test `min_cells moves the hash only while the table lookup is on` in `tests/rag/v2/params-hash.test.ts` already
covers the hash side through `tuningHashComponent`.
