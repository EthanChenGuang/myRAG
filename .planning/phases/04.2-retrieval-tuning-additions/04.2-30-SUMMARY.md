Every Phase 4.2 function that takes a tenant key rejects a key of the other deployment mode. This plan changes tests and the eval harness only. No product behaviour changes.**

## Task 2: seeds and the four paths

Each tenant (a, b and o in multi-tenant mode, and the default tenant in single-tenant mode) gets these seeds, all neutral invented words:
- a three-column Markdown table indexed by the write-time indexer;
- two identifier documents (`QX-<5 digits>` and a one-edit neighbour) indexed by the same indexer;
- a lineage with a superseded version 1 and a current version 2;
- four pasted copies of one shared passage, clustered by `clusterChunks`.

The markers are added to `V2TenantMarkers`, so `foreignMarkers` and every existing path now check them too.

| Path | Own markers | Another tenant's markers |
| --- | --- | --- |
| `table_lookup` | `table_lookup` ok, `rows=1`; the own table chunk heads `table:0` | `rows=0`, no `table:0` leg, no foreign chunk or text |
| `identifier` | `asked=1 found=1 filtered=true`; every candidate carries the identifier; no suggestions | `asked=1 found=0`; no suggestion equals the owner's identifier or its neighbour |
| `versions` | the superseded chunk comes back (not for voice) | neither of the owner's versions |
| `dup_cluster` | collapse keeps one own copy; `alsoIn` lists only own documents | same question from every tenant; `alsoIn` on kept chunks and used documents is own-only; `rag_dup_cluster_sources(<caller>, [<owner cluster>])` returns no row, while the owner gets 4 |

For every path, the foreign markers check covers candidates, kept chunks, used documents, source images, context, voice results, suggestions and rerank documents. A foreign chunk-id check covers all of the owner's lookup chunks. The single-tenant block runs the four paths for the default tenant, and the personal and organization scopes return `error`/`backend_error` with no candidates.

## Task 3: key-mode assertions

The test makes one assertion per function for 26 functions:
- purge hooks: `rag_purge_hook_table_rows`, `rag_purge_hook_dup_clusters`, `rag_purge_hook_identifiers`, `rag_purge_hook_dup_chunk_bands`;
- versions and exact ids: `rag_document_versions`, `rag_exact_id_documents`;
- duplicate clusters: `rag_dup_write_hashes`, `rag_dup_candidates`, `rag_dup_clusters_recompute`, `rag_dup_assign`, `rag_dup_backfill_candidates`, `rag_dup_cluster_sources`;
- identifiers: `rag_identifier_patterns_list`, `rag_identifier_pattern_create`, `rag_identifier_pattern_update`, `rag_identifier_pattern_delete`, `rag_identifier_resolve`, `rag_identifier_candidates`;
- relex: `rag_relex_candidates_stamped`, `rag_relex_batch_stamped`, `rag_lexical_stale_count`;
- write indexers: `rag_index_document_chunks`, `rag_write_chunk_identifiers`, `rag_write_table_rows`, `rag_index_backfill_documents`;
- table lookup: `rag_table_lookup`.

In single-tenant mode, `u:` and `o:` keys raise `tenant key not valid for this deployment mode`, and `s:default` is accepted. In multi-tenant mode, `s:default` raises, and a personal and an organization key are accepted. "Accepted" means the call succeeds, or it meets only that function's next, expected error: `pattern_not_found` for update and delete, and `tenant_mismatch: document not found in tenant` for the two writers given a nonexistent document. `hybrid_search_chunks` was already covered. The 0856 helpers `rag_version_history_ok` and `rag_version_period_ok` take a key but do not assert it (they filter by it), so they are not in the list.
