# Phase 4.2 Plan 07: Refusal operating points per RAG mode

**The calibration tool fits one threshold per RAG mode and records every candidate threshold with its false-answer and false-refusal rates on dev and holdout. The runtime gate uses the mode's cell when one exists and the shared cell otherwise. It judges staleness by the effective lexical version. With `targets_by_mode` unset, the cells and the thresholds dump are byte-identical to the pre-plan code. `eval/config/refusal-thresholds.json` is not rewritten.**

## Behaviour changes

- Calibration with `targets_by_mode` set adds `base|strict`, `base|balanced` and `base|flexible` cells. Each has its own holdout check and `holdout_evaluations`. The thresholds model would dump schema_version 2 (only with `--write-thresholds`, which this plan did not run).
- Every calibration result and report now carries the full candidate sweep, and the report has an "Operating points per mode" section. With targets unset, that section says so.
- At runtime, a request with `ragMode` strict, balanced or flexible uses `base|<mode>` if that cell exists. Voice (no mode), bypass, and any mode without a cell use the shared cell. The committed thresholds file has no mode cells, so every refusal decision is unchanged today.
- The rank stage and the status view compare `tokenizer_version` with `config.v2.lexicalVersion`. With both lexical switches off this is 2, the same as before. With either switch on, every cell calibrated at version 2 is `cell_stale` and the floor decides.
- **Bug fix:** an invalid `refusal-thresholds.json` that passes the Zod schema but breaks the Pydantic cross-field rules now disables threshold refusal with one `[RAG Config]` warning. An example is `{schema_version: 2}` with no mode cell. Before, it loaded silently. The failing test was the existing `tests/rag/refusal/gate.test.ts › warns once and returns empty cells for invalid file data`. It had been failing on the base branch since 04.2-01 widened `schema_version` to `1 | 2`, and it passes now.
