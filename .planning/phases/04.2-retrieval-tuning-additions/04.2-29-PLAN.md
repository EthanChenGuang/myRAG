<objective>
Make the fixture database reflect each Phase 4.2 switch when a run config turns it on, and produce the two eval-only tuning values on the fixture corpus.

Purpose: the eval runs of plan 04.2-32 measure the features only if the fixture database holds what a deployment would hold after the documented rebuild commands (D-09, D-15, D-19, D-28); the eval-only values come from the tools of plan 04.2-16 (D-48, D-49).
Output: feature seeding in `createFixtureDatabase`, the fixture pattern file, the fixture tool runs and their reports.

Rules for every task:
- Locate code by symbol name and re-read the newest definition first (`createFixtureDatabase`, `LEXICAL_SHA_KEY`, the 4.1.1 `terminologySeed` option, the backfill functions of plans 04.2-13 and 04.2-18).
- Reuse the product code paths (resolver, backfills) instead of a harness copy, so the eval measures what ships.
- Tool-owned files (`dup-cluster-params.json`, the lambda in the run config, `retrieval-params.json`) are written only by their tools; never by hand (AGENTS.md section 6).
- The fixture pattern is synthetic and matches an identifier shape with no digit (the one plan 04.2-28 placed in the corpus).
- PGlite plan: never run at the same time as another fixture-database plan in the same tree.
- Commit with plain `git commit`; the message ends with the attribution lines the executor's own session supplies. Hand-off notes go to `.planning/phases/04.2-retrieval-tuning-additions/handoffs/04.2-29-<topic>.md`.
</objective>
