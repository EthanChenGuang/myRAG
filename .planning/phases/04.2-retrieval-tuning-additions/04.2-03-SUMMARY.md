# Phase 4.2 Plan 03: Phase 4.2 storage schema Summary

**Four additive, idempotent migrations (0851–0854) create the dictionary fingerprint column, the typed table-row store, tenant-bound duplicate clusters and the identifier index schema, all service-role only and tested in both deployment modes.**

## Performance

- **Duration:** about 1 h
- **Tasks:** 3 of 3
- **Files:** 5 created, 1 modified

## Accomplishments

- Task 1 (upstream gate): passed. `04.1-12-SUMMARY.md` is present, `RAG_REFUSAL_FLOOR` is in `src/lib/env.ts`, and no file 0851–0854 existed. No hand-off note was needed.
- 0851: `document_chunks.lexical_dict_version text`. A separate `BEFORE INSERT OR UPDATE OF metadata` row trigger copies metadata `lexical_dict_version` into the column when it is a string matching `^s[0-9]{1,9}(\.w[0-9]{1,9})?$`. A write without the key leaves the column as it was. A malformed or non-string value is ignored. `rag_chunks_lexical_tsv` and `rag_write_chunks` are not redefined.
- 0852: `rag_table_rows` with the planned columns, the unique key `(document_id, chunking_profile_id, table_key, row_index)`, GIN on `cell_norm`, and an index on `(tenant_key, document_id)`.
  - FK to documents `ON DELETE CASCADE`.
  - A guard takes `tenant_key` from the document and refuses a different one with 42501. On insert it also fills `version`, `is_current` and `status` when they are left out.
  - The `AFTER UPDATE` statement trigger on documents writes only rows whose document's `is_current` or `status` changed.
  - No constraint fixes the column list, so Phase 4.3 can add `access_groups`.
- 0853: `dup_cluster_id uuid` and `simhash bigint` on chunks, plus `rag_dup_clusters` with a `dirty` flag. The tenant FK described above binds each chunk to a cluster of its own tenant.
  - There is a partial index on `dup_cluster_id`.
  - Statement triggers mark the former cluster dirty on chunk delete, or when a chunk's `is_current` or `status` changes, always naming the old row's tenant.
  - Deleting a cluster clears only `dup_cluster_id` on its chunks.
  - No band structure, recompute function or `hybrid_search_chunks` change is in this file; those belong to 04.2-13.
- 0854: `identifiers_norm` and `identifiers_raw` (`text[]`) on chunks and documents, with GIN indexes on both `identifiers_norm` columns.
  - `rag_identifier_patterns` checks: name 1–80 characters and not blank, pattern 1–200, flags `u` or `iu`, unique `(tenant_key, name)`.
  - `created_by` references `auth.users` with `ON DELETE SET NULL`.
  - The tenant key format guard is the shared one from 0853.
- All three new tables have RLS on, zero policies, everything revoked from `PUBLIC, anon, authenticated`, and `SELECT, INSERT, UPDATE, DELETE` granted to `service_role`. Existing rows keep null in every new column. Nothing is folded into the setup files.

## Records the plan asked for

- **Highest migration number below 0851 on this tree:** `0820_chunk_translation_producer.sql`. The newest file in each block is 0820 (3.2, 0801–0820), 0705 (Phase 7), 0603 (Phase 6), 0537 (Phase 5.x) and 0442 (3.1.1).
  - Operator order: apply 0851, 0852, 0853, 0854 after 0820. 0854 requires 0853 (it uses `rag_row_tenant_key_guard`) and stops with 55000 otherwise.
  - The known unmerged numbers 0707, 0821 and 0822 do not interact with these files.
- **Tenant-check mechanism:** a composite foreign key (no constraint trigger). The FK is `document_chunks (tenant_key, dup_cluster_id) REFERENCES rag_dup_clusters (tenant_key, id) ON DELETE SET NULL (dup_cluster_id)`, backed by a unique constraint `(tenant_key, id)` on clusters.
  - The check `dup_cluster_id IS NULL OR tenant_key IS NOT NULL` closes the MATCH SIMPLE null gap.
  - Cluster and pattern rows also pass `rag_assert_tenant_key` through a BEFORE trigger, so a malformed key or one from the other deployment mode is refused with 22023.
  - Table rows take their tenant from the document.
- **What `rag_semantic_cache_on_documents_update` compares** (newest definition 0603; no later redefinition): `is_current`, `status`, `version` and `tenant_key` of the old and new document rows.
  - An update that changes only `documents.identifiers_norm` or `identifiers_raw` fires the statement trigger but deletes no cache entry.
  - So the 04.2-18 identifier backfill does not flush the semantic cache.

## Deviations

1. **[Rule 2, missing critical] 0410 lock-down entries.**
   - `tests/rag-db/search-rpc-grants-pglite.test.mts` ("an upgraded database whose functions all kept their old open grants is locked by 0409 and 0410") failed in both modes. It opens grants on every SECURITY DEFINER function and expects re-applying 0410 to close them.
   - I added `to_regprocedure`-guarded REVOKE/GRANT entries for the six new definer functions to section 1 of `0410_security_definer_rpc_grants.sql`. This follows the precedent of 03.2-46 for 0807.
   - On a fresh install the guards find nothing, because 0410 runs before 0851, and the new files revoke their own grants. Production needs no 0410 re-run.
2. **Purge hooks added** (orchestrator rule for new 4.2 stores; the plan said "schema only"): `rag_purge_hook_table_rows`, `rag_purge_hook_dup_clusters` and `rag_purge_hook_identifiers`.
   - Same shape as the 0805/0806 hooks: SECURITY DEFINER, `search_path ''`, `rag_assert_tenant_key` first, service_role only.
   - The dup-cluster hook removes the purged documents from `source_document_ids`, marks the clusters dirty, and clears `dup_cluster_id` and `simhash` on their chunks.
   - No `rag_purge_store_inventory()` exists on trunk, so nothing was registered there.
3. **Trigger security mode.** The plan's style line says trigger functions are SECURITY DEFINER. Per D-56, only the cross-table writers are; `rag_chunk_lexical_dict_version`, `rag_table_rows_guard` and `rag_row_tenant_key_guard` touch only NEW or read the parent row, so they are SECURITY INVOKER. All of them have `search_path ''` and are revoked from client roles.
4. **Client-role access test.** The fake edge serves only an allow-list of tables, so its anon GET returns an error for any unlisted table. As in `answer-records-rls.test.mts`, the test asserts an error status and no row ids in the body.
   - The real privilege check is direct SQL under `SET ROLE anon` and `SET ROLE authenticated` (with a JWT sub): SELECT and INSERT fail with 42501 on all three tables, and `service_role` succeeds.
   - `has_table_privilege` is asserted for all four verbs.
5. **Single-tenant cross-tenant case.** In single-tenant mode a cluster of another tenant cannot be created at all (the guard refuses it with 22023, which the test asserts). To still exercise the FK, the test inserts one foreign-tenant cluster with `session_replication_role = replica` and asserts that pointing a chunk at it fails with 23503.

## Decisions for STATE

- The Phase 4.2 stores bind tenants in SQL: a composite FK for cluster pointers, the document's tenant for table rows, and `rag_assert_tenant_key` for cluster and pattern rows.
- Every new 4.2 store gets a `rag_purge_hook_<name>`. Tenant configuration tables (identifier patterns) have no lineage purge.
- New SECURITY DEFINER functions also get a guarded entry in 0410 section 1.

## Operator actions

- Apply `0851_lexical_dict_version.sql`, `0852_rag_table_rows.sql`, `0853_dup_clusters.sql` and `0854_identifier_index.sql`, in that order, after 0820. They are common files with no mode variants.
- 0853 and 0854 build indexes on `document_chunks` and `documents`. The partial index is empty and the GIN indexes cover all-null columns, so they are cheap, but `CREATE INDEX` takes a write lock, so apply them in a quiet window on large tables.
- 0853 adds a CHECK and a foreign key on `document_chunks`. Both validate with one scan and no table rewrite.
