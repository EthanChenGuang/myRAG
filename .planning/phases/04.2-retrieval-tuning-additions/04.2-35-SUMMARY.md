# Phase 4.2 Plan 35: Lookup backfill commands Summary

**Existing documents now get table rows and identifiers through `npm run rag:table-rows` and `npm run rag:identifiers`. Both commands run the 04.2-18 write-stage routine for each listed document, can be resumed, and write nothing on a dry run.**

## Accomplishments

- **Task 1 (upstream gate):** passed. The 04.2-13 and 04.2-18 SUMMARYs are on this branch, and so are those of every transitive dependency (04.2-01, 02, 03, 04, 06, 08, 14, 34 and 04.1-12). `indexDocumentForLookup`, `rag_index_backfill_documents` in 0860 and the `rag:dup-clusters` script all exist. No hand-off note was needed, and no file changed in this task.
- **Task 2:** two backfill runners, two CLIs and two `package.json` scripts, plus tests.
  - Both commands page through `rag_index_backfill_documents(kind)` and call `indexDocumentForLookup` with only their own part switched on.
  - The listing returns ready, non-provisional documents that are current or superseded, so a history query under a version scope also finds the old versions' rows and identifiers.
  - The writer is `createIngestWriter` bound to a scope from `backfillScope`, so the SQL functions assert the same tenant on every call.

### Output and exit codes

- The output has the prefixes `[RAG Tables]` and `[RAG Identifiers]`. It shows counts, tenant keys and document ids only.
- A dry run prints `dry run, nothing written`, then `<tenant>: would index N documents (C current, S superseded)` for each tenant, then a total.
- A real run prints the switch value (the backfill runs either way) and the cache line. After each batch it prints `<tenant> batch n: indexed x, failed y, cursor <documentId>`. At the end it prints a line per tenant and a `done` line.
- The identifier command prints once: `semantic cache: unaffected; writing document identifiers deletes no cached answer (the cache trigger compares only is_current, status, version and tenant_key)`.
- The table command states that each document's rows are replaced for each chunking profile and that the semantic cache is not flushed.
- Exit codes:
  - 0: done.
  - 1: a database failure, a document that failed to index, or a missing service-role key or admin client.
  - 2: bad arguments, a tenant key that does not resolve, or a key of the other deployment mode.
  - 130: SIGINT between batches. The command prints `--tenant <key> --resume-after <last cursor>`.

## Deviations

1. **Two shared modules that the plan did not list.** `src/lib/rag/ingest/lookup-backfill.ts` (runner, parser, tenant listing) and `src/lib/rag/ingest/lookup-backfill-cli.ts` (CLI driver) hold the logic. The four planned files are thin wrappers around them, so the two commands cannot drift apart.
2. **`--resume-after` needs `--tenant`.** The cursor is a document id within one tenant, so resuming an all-tenant run would be ambiguous.
3. **The all-tenant listing is tested only with a vitest fake.** It reads `documents.tenant_key` through the service-role REST client, one distinct key at a time (`gt`, `order`, `limit 1`). The PGlite fake edge serves neither `order` nor `gt`, so the PGlite cases always pass `--tenant`.
4. **The PGlite CLI cases replace the admin client with a fake auth admin.** `backfillScope` calls `auth.admin.getUserById`, which the fake edge does not serve. The fake knows the two fixture users and refuses any other id, so the unknown-tenant case still goes through the real `backfillScope`.
5. **Default batch size is 100 documents**, not the 500 chunks of the relex and dup-cluster commands. Each document is a full re-index of every profile.
6. **No migration.** The 0860 functions were enough.
