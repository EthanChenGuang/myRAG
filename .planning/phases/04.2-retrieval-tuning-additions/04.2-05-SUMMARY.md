# 04.2-05 Summary: rerank cap 25 and nDCG at context k

The pool and the rerank cap can now be as low as 25 in all five enforcers. The cap can never be larger than the pool. The fixture sweep reports nDCG@k, where k is the number of chunks kept in each item's context. nDCG only appears in the report: it plays no part in choosing a configuration and is not gated. `eval/config/retrieval-params.json` is unchanged.

## Task 1: upstream gate (D-01)
Passed with no hand-off note. The SUMMARYs for 04.2-01 and 04.2-02 exist, `src/lib/rag/config.ts` has `25..100`, and `rag-sidecar/src/rag_sidecar/contracts/retrieval.py` has `ge=25`. All 63 transitive dependency plans have a SUMMARY on this branch.

## Task 2: cap guard and clamp (D-06, D-41)
- `guardCap` now accepts 25..100 and warns `rerank_input_cap must be 25..100, entry ignored`.
- `effectiveRetrievalParams` clamps `rerank_input_cap` to `candidate_pool_size` after the `safeParse` step, and also on the parse-failure path. It warns once per (pool, cap) pair: `rerank_input_cap above candidate_pool_size, cap clamped to the pool`. The generated Zod does not carry the Pydantic `cap <= pool` validator, so this clamp is the TypeScript enforcement.
- **Behaviour note:** the clamp changes results only for an override (`RAG_RETRIEVAL_PARAMS_OVERRIDE` or eval-profile `retrieval_overrides`) that lowers the pool without lowering the cap. With no override, the committed 75/75 is returned unchanged.

## Task 3: CAP_MIN, nDCG, fixture report (D-06, D-07, D-50)
- `CAP_MIN = 25`, so `rerank_cap(pool) = min(100, max(25, pool))`. Pool 25 now runs with cap 25.
- `gold_unit_first_hits` returns one first kept position (by rank) per gold span, or per evidence group when `evidence_groups` is set. Each unit earns one credit. Spans outside every group are not counted when groups are present.
- `_first_hit_ranks` delegates to `gold_unit_first_hits`, so the sweep's recall and MRR count groups when the field is present. Recall divides by the number of units.
- `cell_scores` returns `CellScores(recall_at_k, mrr, n_items, ndcg_at_context_k, k_zero)`. A refused item, or one with no kept chunk, scores nDCG 0 and counts in `k_zero`.
- `SweepCell` gains optional `ndcg_at_context_k` and `k_zero`, and older cells still validate. The report gains `nDCG@k` and `k = 0` columns plus a note saying the metric is report-only. `noise.json` and `choose_configuration` are untouched, and a test asserts nDCG is not a gated metric.

### Fixture sweep
Command, the one recorded in 04-39 for this report: `uv run --directory eval python -m rag_eval.sweep retrieval --run-config eval/config/runs/v2-recommended.json --out eval/reports/retrieval-sweep-fixture`. It used fake rerankers, the default grid (pools 25/50/75/100, top-k 5/8/10/15/20) and no `--write-params`. The run took 5m17s.

**D-14 choice of the regenerated report:** pool 25, cap 25, top-k 10 (recall 0.8813, MRR 0.7793, band 0.02; best recall 0.8990, best MRR 0.7805). This differs from the committed parameters (pool 75, cap 75, top-k 8). Per D-06, nothing in `eval/config/` was changed. **For the live plan 04.2-33:** the fixture prefers the smallest pool. Fixture gains mostly reflect the lexical fixture embedder, so only the live sweep with real rerankers can move the shipped parameters. `sha256sum` of `retrieval-params.json` is identical before and after the run.
