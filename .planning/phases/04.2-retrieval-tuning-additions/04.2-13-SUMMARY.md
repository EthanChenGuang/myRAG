# Phase 4.2 Plan 13: Duplicate clusters Summary

**Near-duplicate chunks of different documents in one tenant are grouped at ingestion (switch on), kept correct through supersession, soft delete and hard delete, and backfilled by `npm run rag:dup-clusters`; every chunk row stays and only `dup_cluster_id` and `simhash` are recorded.**

Passed. The SUMMARYs of 04.2-01, -02, -03, -06 and -08 are on the branch (transitive 04.1-12 too). 0853 defines `rag_dup_clusters`, `DupClusterParamsSchema` is generated, `dupClusters` is in `src/lib/rag/config.ts`, and no 0857 file existed. No hand-off note was written.

## Records the plan asked for

- **Shingle size:** 3 default lexical tokens (`lexicalTokens(text)` without options; stopwords are already removed; Han text arrives as tokenizer bigrams). Fewer than 3 tokens: one shingle of all tokens. Shingles are weighted by count and hashed with the first 8 bytes of SHA-256.
- **Band layout:** 8 bands of 8 bits, band b = bits 8b..8b+7 (low band first), split in SQL as `(simhash >> 8b) & 255`. Two hashes within 7 differing bits always share a band.
- **Hamming cap:** 16 bits (`DUP_CLUSTER_MAX_HAMMING`). Cosine threshold 0.95 (`DupClusterParamsSchema` default). At most 50 candidates per source chunk.
- **Measured cosine of the 30 generated copies under the fixture embedder:** 0.9767 to 0.9934 pairwise on the passage text. Ingested through the pipeline (embedding text with the section path), the probe gave about 0.980 to 0.981. All copies stay above 0.95 with no change to the threshold.
- **Function signatures (0857):**
  - `rag_dup_write_hashes(p_tenant_key text, p_rows jsonb) RETURNS TABLE (written integer)`. `p_rows` is `[{id, simhash}]` with simhash as signed decimal text; at most 1000 rows.
  - `rag_dup_candidates(p_tenant_key text, p_chunk_ids uuid[], p_max_hamming integer, p_threshold double precision, p_limit integer) RETURNS TABLE (chunk_id, document_id, candidate_id, candidate_document_id, candidate_cluster_id, similarity, exact, hamming)`. Limits: ids ≤ 1000, Hamming 0..64, threshold -1..1, limit 1..200.
  - `rag_dup_assign(p_tenant_key text, p_chunk_ids uuid[], p_preferred_cluster_id uuid) RETURNS TABLE (cluster_id uuid, member_count integer, merged integer)`. Ids ≤ 1000; a preferred cluster of another tenant raises 22023.
  - `rag_dup_clusters_recompute(p_tenant_key text, p_cluster_ids uuid[]) RETURNS TABLE (recomputed integer, dissolved integer)`. Null means every dirty cluster of the tenant; at most 1000 ids.
  - `rag_dup_backfill_candidates(p_tenant_key text, p_after uuid, p_limit integer, p_document_id uuid, p_chunk_ids uuid[]) RETURNS TABLE (id uuid, document_id uuid, content text)`. Limit 1..1000.
  - `rag_purge_hook_dup_chunk_bands(p_tenant_key text, p_lineage_id uuid, p_document_ids uuid[]) RETURNS bigint`.
  - All of them are `SECURITY INVOKER` with `SET search_path = ''`. Each calls `rag_assert_tenant_key` first and names the tenant in every predicate. All are revoked from PUBLIC, anon and authenticated and granted to service_role. Array caps raise 22023.
  - `rag_dup_chunk_bands` has RLS on and no policy, and is guarded by `rag_row_tenant_key_guard`. Its rows cascade on chunk delete.
- **6.3 purge coverage:** `rag_purge_hook_dup_chunk_bands` was added for the new band table. The cluster fields remain covered by 0853's `rag_purge_hook_dup_clusters`.

## Behaviour

- **`RAG_DUP_CLUSTERS=false` (default):** publish, soft delete and the documents route make no `rag_dup_*` call and write no hash, band or cluster row. The stage list still has 13 names, and `defaults-equal-phase3` passes unchanged.
- **Switch on, publish:** after `ctx.writer.publish`, only for outcome `published`, the new version's chunks are hashed and clustered and then the tenant's dirty clusters are recomputed (0853 marked the superseded version's clusters dirty). A failure logs one `[Ingest] Duplicate clustering failed; the document is published` warning with `{ error: <class name> }` and the result is unchanged. An abort still propagates.
- **Soft delete (`softDeleteLineage`, outcome `deleted`) and `DELETE /api/documents/[id]`:** after a successful delete, `recomputeDirtyDupClusters(scope)` runs. It is switch-gated and never throws; a failure logs `[RAG Dedupe] cluster recompute failed` with the error name.
- **Recompute:** members that are not current and ready leave the cluster. A cluster with fewer than 2 members dissolves: its row is deleted and the remaining chunk's `dup_cluster_id` becomes null. Otherwise `member_count`, `source_document_ids` and the representative are refreshed (the representative is kept while it is still a member, else the earliest chunk), and `dirty` is cleared.
- **Backfill:** keyset over chunks without bands for the active profile. It prints the switch value and the note that the chunk statement triggers fire once per batch and the semantic cache is not flushed, then per-batch counts with a cursor, and finally the totals. A dry run prints `would hash N chunks` and writes nothing. SIGINT stops between batches and returns 130 with `--resume-after <last cursor>`. Running it again reports 0.

## Deviations from Plan

1. **A sixth function, `rag_purge_hook_dup_chunk_bands`.** The phase's standing rule needs a purge hook for every new 4.2 store, and the band table is one. Its test was added together with the function, not as a separate RED commit.
2. **`rag_dup_backfill_candidates` has two extra arguments, `p_document_id` and `p_chunk_ids`.** The publish sub-step and `clusterChunks(scope, chunkIds)` use them to read the text to hash, so no further listing function was needed.
3. **`clusterChunks` takes `rehash: false`.** It clusters from stored hashes; the exact-path and below-threshold tests write synthetic hashes through it.
4. **The hard delete of the documents route is tested in two places.**
   - The PGlite test runs the route's two statements directly in SQL, then the recompute. The fake edge serves no REST DELETE.
   - The route's own call is covered in `tests/rag/documents-route.test.ts`, with 4 new cases: switch off makes no call; switch on makes one recompute with the caller's tenant key; a failing recompute still answers 200; a refused delete makes no call. The on and failure cases fail on the old route.
5. **BigInt literals became `BigInt(...)` calls.** The root tsconfig targets ES2018, where `123n` is a type error.
6. **Migration number 0857** was free and is used as planned.

## Decisions for STATE

- DATA-21 is partial: ingestion, recompute and backfill are done. Retrieval use (04.2-20), cluster sources in payloads (04.2-21) and the eval tools (04.2-16) are still open.
- The threshold shipped at 0.95 (D-49). The service takes an explicit `threshold` option for eval tooling, and nothing reads a fixture-fitted value in production.
- The band table holds the embedding profile that was active when a chunk was hashed. After a profile flip, `npm run rag:dup-clusters` re-hashes for the new profile, and clusters of the old profile merge into new ones the next time a member is assigned.

## Deferred

- **Concurrent publishes of the same passage** can create two clusters. They merge the next time a chunk links both; nothing locks them across concurrent ingests.
- **Bucket sizes per band** grow with tenant size (about 1/256 of the tenant's chunks per band). They were not measured on a large tenant.
- **Live calibration of the threshold on real embeddings** is the optional live item of the final plan (F-11).
