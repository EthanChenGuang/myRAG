## Task 2: loader, corpus and routing

### Corpus (described by structure)

There are 12 Markdown files, four per language (zh, en, it). Each has a fixture-meta line, two sections and a chunk separator:

- **Two scope-tagged documents per language.** Each states the same two facts, a recalibration interval and a spare-part stock level, with different numbers. One is tagged `region:zone-oriel` + `department:unit-corvid`, the other `region:zone-pallas` + `department:unit-lumen`. All four values are invented. These documents serve `scoped_compound` items.
- **One glossary document per language.** Its answers depend on an invented term: the required translation of another language's source term in the glossary.
- **One adjacent document per language.** It covers a neighbouring field topic (probe readings and battery swaps) next to an off-domain topic that no fixture document covers (D-27).

No document reuses the REQUIREMENTS example domains. The q62 names do not collide with the main corpus, the ingest texts or the fixture dictionary (checked with grep).

### Loader and routing

- `q62-fixtures.mts` does the loading in both modes:
  - Prechunked mode uses the prechunked writer with the q62 owner, then relex, supersede, scopes and glossary.
  - Ingest mode uses inline `ingest()` as config uploads while the edge serves the q62 database.
  - Both modes then write the vocabulary and tags through the 3.2 writers and seed the glossary on the tenant's layer.
- `partitionIngestModeItems` now returns `{ main, tableSplit, q62 }`.
- `runEval` loads the tenant only when q62 items are present. It runs them last, with the edge pointed at the q62 database and, in multi-tenant mode, the q62 user as scope.
- `prepareInProcessEval({ q62 })` builds the tenant. It also runs the Phase 4.2 feature rebuilds on it.

## Deviations

1. **`eval/harness/pglite-supabase.mts` (not in files_modified).** Three additive changes:
   - `prechunkedWriter` takes an optional fourth parameter `ownerUserId`, defaulting to `FIXTURE_USER_ID`, so multi-tenant q62 rows get their own tenant key (chunk tenant keys come from the parent row on insert).
   - `createFixtureDatabase` takes a `q62` option.
   - `FixtureDatabase` carries `q62Tenant`.

   Without these the prechunked mode could not load the tenant.
2. **`eval/tests/test_fixture_pii.py` (not in files_modified).** The plan's mitigation T-06.2-63 runs `test_fixture_pii`, but that test scanned only `eval/fixtures/corpus`. It now also scans the 12 q62 documents and the manifest (count pinned at 13).
3. **Isolation test layout.** The prechunked "with" and "without" runs, and the ingest "without" run, go through `run-smoke` child processes, as in 03.2-30, because the app modules freeze the env and the edge URL on first import. The ingest "with" run runs in process, against `buildIngestFixtureDatabase({ q62: true })`. The probe item has two `sub_questions`, which the Pydantic contract requires for `scoped_compound`.
