## Behaviour
- **0981** `rag_tenant_doc_types(p_tenant_key text) RETURNS TABLE (doc_type text, docs bigint)`: distinct doc types of the tenant's current, ready documents, most frequent first. SECURITY INVOKER (no definer needed: service_role reads `documents` directly, as 0601), `SET search_path = ''`, schema-qualified names, `rag_assert_tenant_key` first (malformed or wrong-mode key: 22023), REVOKE from PUBLIC, anon, authenticated, GRANT to service_role, `NOTIFY pgrst`. Not folded into the setup files; idempotent. It is a read function, not a store, so no purge hook.
- **narrowFilters(base, proposed, vocabulary)** returns `{ status, filters, applied }`. Date ranges intersect. Scope, doc-type and language values outside the tenant's own vocabulary, doc types or enabled languages are dropped, and the rest are intersected with the base. In a scope dimension the base already filters, only base tags survive; a new dimension adds an AND narrowing. Document ids, sources, invoice fields, `includeUndated` and `scopesIncludeUntagged` come only from the base. The tenant scope is not an input. Any empty intersection drops the whole proposal (`dropped_empty_intersection`, base kept, never an empty search); a proposal with only unknown values is `dropped_unknown_values`; a contract failure is `dropped_invalid` (set by the finisher). A null proposal leaves the base, status `applied` with `filter: null`. A 500-case seeded property test checks that every field of the result is equal to or narrower than the base.
- **Addendum** `shared.subq-filters.v1` (neutral wording, no example values): the field list rendered from `SUB_QUESTION_FILTER_FIELDS` (`date_range, scopes, doc_types, languages`, so 06.2-25 can add `versions`), and the tenant's scope slugs, doc types and enabled languages as JSON, at most `subq_filter_vocab_cap` (default 20) per dimension and list. Only plain slugs and codes are listed; labels and aliases are never read into it, and a value that is not a slug (for example one that holds instruction text) is left out.
- **Decomposers (both frameworks)**: switch on, the prompt ends with the addendum (native: after the shared suffix; LangChain: at the end of the system message) and the schema is `SubQuestionsWithFilters` (wire list bound 16, as Phase 6). The shared finisher parses each spec's filter on its own, narrows it, then runs the D-15 checks and the 06.2-06 completeness check on the texts; kept sub-questions take the proposal of the spec with the same text (a repaired or added one has none). `DecomposeResult` carries `subQuestionSpecs` (contract shape, narrowed values only), `subQuestionFilters` (narrowed `RetrievalFilterInput` per spec, for 06.2-16) and `filterTrace` (one entry per spec, `retried`/`retry_skipped_cap` false until 06.2-16).
- **Switch off**: prompt text and JSON schema are byte-identical to Phase 6 (tested against `zodSchema(...).jsonSchema` and the rendered Phase 6 prompts). A filter-carrying output is stripped to its texts and traced `stripped_switch_off`; a plain Phase 6 output adds no spec and no trace, so the plan equals Phase 6. No RPC is made for doc types or vocabulary while the switch is off.
- **Native parse**: the native call's schema is `z.preprocess(normalize, strict)`. The JSON sent is exactly the strict contract; the preprocess keeps the raw output for the shared finisher, so both frameworks finish the same raw value and agree on every scripted case (parity tests).
- **Plan**: `buildQueryPlan` adds `sub_question_specs` and `filter_trace` only when given; texts equal `sub_questions` and the plan validates against `QueryPlanSchema`.
- **Tenant isolation**: `subqFilterContextFor` reads the vocabulary (only with `RAG_SCOPE_TAGS` on) and the doc types for the request's minted scope only; a read failure leaves that list empty (proposals then drop as unknown). Two-tenant tests cover 0981, the doc-type cache, the context and the addendum.
