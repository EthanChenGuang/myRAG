# 06.2-04 Summary: translation glossary on the TERM dictionary

Glossary pairs are TERM entries of kind `translation` with a required `target_language`. Phase 4.1.1 had already built most of what
this plan described, so the plan shrank to the parts that were still missing: Glossary list filters (SQL and route), the three
target-language issue codes the UI-SPEC maps, and one write-path normalization.

## Task 1: seam check (D-01)

Every depends_on plan, transitive ones included (248), has a SUMMARY on this branch. Seams as they exist now:

| Seam | Name now |
|------|----------|
| TERM table | `public.rag_term_entries` (0471), columns `language`, `kind`, `source_language`, `target_language`, `mode` |
| Translation CHECK | `rag_term_entries_translation_check` (0471, validated): source and target set only for `translation`, both concrete, different, `language = source_language`, `mode = one_way` |
| Writers | `rag_term_upsert_entry`, `rag_term_delete_entry`, `rag_term_set_suppression`, `rag_term_apply_import` (0472, SECURITY DEFINER) |
| Effective read | `rag_term_effective(text)` (0471, SECURITY INVOKER, `rag_assert_tenant_key` first, returns `target_language`) |
| Entries hash | `rag_term__refresh_sha` over `rag_term__entry_json` (0472; includes `target_language`) |
| Admin list | `rag_term_list_entries` (0472; now 0980) |
| Normalizer | `normalizeLexical` in `src/lib/rag/lexical/tokenize.ts` |
| Enabled languages | `getLanguageSettings()` in `src/lib/rag/lang/settings.ts`, read by `terminologyEnabledLanguages()` in admin.ts |

The newest definitions are the 0471/0472 bodies, folded verbatim into both setup files by 04.1.1-14; no later migration redefines them.

## Task 2: migration 0980

- 0980 adds **no column and no constraint**. `target_language` and a stricter, already validated translation CHECK exist since 0471,
  so `ADD COLUMN IF NOT EXISTS` would be a no-op and a `NOT VALID` CHECK would be weaker than what is there. Instead a guard raises 55000
  when the 0471/0472 shape is missing, so 0980 can never leave a half-built schema.
- It drops `rag_term_list_entries(uuid, text, integer, integer, text)` and creates the eight-argument form with `p_kind`,
  `p_source_language` (matched against `language`, which equals the source language for translation rows) and `p_target_language`,
  all defaulting to NULL, so every five-argument named call (preview, loadLayer, getVersions) works unchanged. Body copied from 0472:
  SECURITY DEFINER, `SET search_path = ''`, schema-qualified names, `rag_term__authorize` first, REVOKE from PUBLIC, anon, authenticated,
  GRANT to service_role, `NOTIFY pgrst`. Not folded.
- The header tells operators that re-running 0472 or a setup file brings the five-argument form back and that 0980 must be re-run after
  it (the q62 suite proves the re-run removes it again).
- 0410 got one guarded REVOKE/GRANT entry for the new signature (standing rule: every new privileged function has a guarded entry in
  0410; precedent 04.3-02, 05.3-32). `tests/helpers/security-definer-allow-list.ts` is unchanged (P-20).
- Number 0980 was free on every origin branch when claimed and was pushed at once.

## Task 3: validator, write paths, CSV, loader, list route

- Validator issue codes for translation pairs: missing target → `target_language_required`; target equal to the source or to the
  entry language → `target_language_same`; target not enabled → `target_language_not_enabled`. A missing source, `any` as language,
  language ≠ source and a non-one_way mode stay `invalid_translation`; a source not enabled stays `invalid_language`. Conflict key was
  already source language + target language + normalized variant with two canonicals; a new test pins that two targets for one source do
  not conflict.
- `withTranslationDefaults` runs on create, update (admin `writeEntry`) and import (`import.ts` candidates) before validation: mode is
  forced to `one_way` and `source_language` defaults to `language`. The target is never filled in (D-36).
- CSV: unchanged. The 4.1.1 nine-column format already has `source_language,target_language` after `note`, round-trips and is
  formula-safe; there are no older files without the columns.
- Loader: unchanged. `load.ts` already carries `targetLanguage`; the per-tenant cache key is unchanged.
- List: `admin.listEntries` takes `kind`, `sourceLanguage`, `targetLanguage`, passed to SQL so the filter applies before the page is
  cut. The route's strict Zod query adds `kind` (the contract's kind enum), `source_language` and `target_language` (language-code
  shape, max 35); anything else is a 400. The route stays admin-only and resolves the layer on the server.

## Decisions (for STATE)

1. **No new column or CHECK in 0980** (deviation from the plan's first must-have): the 0471 schema already stores the target with a
   validated, stricter CHECK. Consequence: "legacy translation rows without a target" (D-36) cannot exist; the list still returns
   `target_language: null` for every other kind.
2. **Only `rag_term_list_entries` is re-created.** `rag_term_upsert_entry`, `rag_term_apply_import` and `rag_term_effective` already
   read or return `target_language` and the hash already includes it, so re-creating them unchanged would only churn published
   functions. Their behaviour is pinned by the q62 suite (writer refusals, hash change on a target-only edit, two-tenant effective read,
   22023 on malformed and wrong-mode keys).
3. **0410 entry added** for the new signature despite the "don't edit another plan's migration" rule, because the standing 0410 rule
   and the upgrade-lock test (`search-rpc-grants-pglite`) require it.
4. **Three new issue codes** added to the contract (not in files_modified) because the UI-SPEC §8.2 and 06.2-07 map them; additive enum.
5. **Write paths normalize translation pairs** (`withTranslationDefaults`) so the Glossary form only needs language, terms, translation
   and target.
