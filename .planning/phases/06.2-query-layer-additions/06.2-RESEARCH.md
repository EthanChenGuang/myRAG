### Decomposition completeness (QRY-09)
- **D-03:** A pure function `checkDecompositionCompleteness()` in `src/lib/rag/query/` runs inside the shared Phase 6 D-15 post-checks after `decompose`, identically under both frameworks. Required terms = protected tokens (gate R4/R7) ∪ years and explicit dates (gate lexicon and `dates.ts`) ∪ relative-time spans the gate matched (R2) ∪ DATA-18 vocabulary values that occur in the query (tenant's `rag_scope_vocabulary`, normalized with `normalizeLexical`) ∪ TERM dictionary matches from the 4.1.1 terminology stage ∪ named entities found by a deterministic heuristic (Latin: capitalized tokens or runs not at sentence start and not stopwords; Han: only dictionary/vocabulary matches, no guessing). No NER model, no LLM call, no built-in domain list.
- **D-04:** Repair, in order: (1) for each missing term, clone the sub-question that contains a sibling term of the same class (period ↔ period, scope ↔ scope, entity ↔ entity) and substitute the missing term; (2) otherwise add the original question as a sub-question; (3) if adding would exceed four sub-questions, discard the decomposition and use the original query only. Matching uses `normalizeLexical` (so case, accents and elisions do not cause false misses). The trace records `completeness: { required_count, missing_count, action: 'ok' | 'added' | 'discarded' }` (counts and action only, never terms). Switch `RAG_QUERY_DECOMPOSE_COMPLETENESS=true`, inert under the master switch off.
  - Tests: a fake decomposer that drops one period, one scope or one protected token is corrected; one that would need a fifth sub-question is discarded.

### Per-sub-question filters (QRY-10)
- **D-05:** Contract: the decomposer output gains an optional per-item filter. Pydantic `SubQuestionSpec { text, filter?: SubQuestionFilter }` and `SubQuestionFilter` (`model_config = extra='forbid'`) with exactly the allowlisted fields: `date_range {from, to}`, `versions` (RET-11 values, `current | all | range` + range), `scopes` (DATA-18 dimensions → values), `doc_types`, `languages`. `QueryPlan` gains `subQuestionSpecs` next to the existing `subQuestions: string[]` (kept for compatibility, equal to the spec texts); variants gain `filterApplied: boolean` and the variant `kind` enum gains `history_fallback` (D-24). Additive Pydantic change, regenerated to Zod.
  - **Reversibility:** costly — trace, eval and both frameworks read it.
- **D-06:** Narrowing is a pure function `narrowFilters(serverFilters, proposed, tenantVocabulary)`: date ranges intersect (empty intersection → the filter is dropped, not an empty search); scope and doc-type values not present in the tenant's own vocabulary or document types are dropped; languages limited to `RAG_SUPPORTED_LANGUAGES`; `versions` only when the 4.2 filter exists. It never touches `TenantScope`, the RAG mode, tool use, webSearch or the caller's own filters except by intersection. Zod validation failure drops the filter and is traced. This is the only exception to Phase 6 D-15's "rewrite never changes filters other than R2", active only while `RAG_QUERY_SUBQ_FILTERS=true` (default `false`, inert under master off). With the switch off, the prompt does not ask for filters and any filter returned is stripped.
- **D-07:** Prompting: when the switch is on, the decomposer prompt (both frameworks) gets a versioned addendum (new prompt data file next to `shared.suffix.v1.json`) listing the allowed fields and the tenant's own vocabulary values and doc types (from the tenant's data, capped; no built-in examples, domain-neutral). Structured output via the existing `generateObject` path.
- **D-08:** Retrieval: a filtered sub-question variant is searched through `hybrid_search_chunks` with the narrowed filter (per-variant filters are added to the Phase 4 variant search input; the shared filters stay the base). A filtered search that returns zero candidates is retried once for the same sub-question without its filter. The retry counts toward the Phase 6 D-08 cap of 8 searches; when the cap is reached the retry is skipped and traced. Fusion, single rerank on the standalone query and Phase 6 D-07 sub-question coverage are unchanged.

### Comparison eval (QRY-11)
- **D-09:** Golden contract: `Category` gains `version_compare` and `scoped_compound`; `GoldenItem` gains optional `sub_questions: [{ index, gold_spans }]` (gold evidence per sub-question; the existing item-level spans stay the union). Fixture corpus gains synthetic, neutral documents in zh/en/it: for `version_compare`, one policy-like document in two versions with distinct effective dates (3.2 D-43 columns, superseded via 3.2 D-41/D-42 lineage); for `scoped_compound`, documents tagged with synthetic scope values (3.2 D-38). At least 3 items per category per language. Additions follow the Phase 2 D-25 pattern (parity with switches off re-confirmed first, re-baseline with zero paired differences on pre-existing items).
  - **Reversibility:** costly — persisted golden files and baseline.
- **D-10:** Metrics in `eval/src/rag_eval/`: `all_evidence_recall@k` (share of items where the gold span of every sub-question is in the retrieved top-k) and `subq_coverage` (share of sub-questions with ≥ 1 gold span retrieved), per language and category. Comparison runs: single-pass (layer on, decompose off) vs decompose vs decompose + completeness vs + sub-question filters. The decision record `eval/decisions/06.2-query-additions.json` (written by the tool, never by hand) records per switch whether it improved these slices and whether any other slice dropped beyond the noise band. "Ships" means the record marks it eligible; the env default stays off for Phase 7 to flip.

### Per-sub-question answers (GEN-13)
- **D-11:** When the final `QueryPlan` has ≥ 2 sub-questions, `createEnhancedRAGPrompt` appends one localized instruction block (never editing `RAG_SYSTEM_PROMPT`; `{{context}}` substitution unchanged; byte-identical prompt when not decomposed): the numbered sub-questions; answer each in its own part; when the gate fired R3 (comparison), parts in the order each period/object → differences → impact on the named scope; each part cites only its own blocks. Context blocks carry which sub-question(s) retrieved them (from fusion provenance), so the model knows which blocks belong to which part. Texts live in the language-pack data (3.2 D-04 registry), not in code.
- **D-12:** A sub-question with no supporting block after rerank and coverage reservation is known deterministically; the instruction names it and tells the model to state that the documents do not cover it, using the GEN-08 localized text (Phase 5.2). It is never dropped silently. A deterministic post-check on the final answer counts parts and per-part citations and records `answer_structure: { parts, cited_parts, uncovered_parts }` on the trace (report-only, no regeneration). For a routed or selected Claude model the same block goes into the GEN-01 Citations path. Switch `RAG_DECOMPOSED_ANSWER=true`, inert unless decomposition ran under the master switch.

### Translation glossary (XLG-05)
- **D-13:** Storage: one dictionary. Glossary pairs are TERM entries with `kind = 'translation'` (4.1.1 D-04). Migration 0980 adds nullable `target_language` to `rag_term_entries` with a CHECK (required for `translation`, must be an enabled-language code, ≠ `language`, NULL for every other kind); one row = source variants in `language` → required translation (`canonical`) in `target_language`; several rows give one source term its per-language translations. The 4.1.1 writers, validation (`validate.ts`: conflict = same normalized source variant + language + target language with two canonicals), CSV import/export (new `target_language` column, optional), audit and `rag_term_effective` are extended additively (newest definitions re-read at execution). Layering and tenant isolation are unchanged (shared vs workspace layer under `TenantScope`).
  - **Reversibility:** one-way — column and function changes on published TERM tables.
- **D-14:** Enforcement is one pure module `glossary.ts` (`requiredTranslations(text, sourceLang, targetLang, glossary)` and `enforceGlossary(output, required)`):
  - query translation (XLG-01 `translate` transform, both frameworks): required target terms are listed in the prompt; after generation, a translated query missing a required term gets one deterministic correction (replace the untranslated source surface form when it is still present) and is otherwise discarded like a dropped protected token (Phase 6 D-15), traced as `glossary_term_lost`;
  - document translation (XLG-04, Phase 3.2 D-29 glossary seam): same list and check; a chunk translation that cannot be corrected is not stored and is counted on the job;
  - same-language rewriting (`condense`, `expand`, `decompose`): glossary source terms in the query become protected tokens, so they survive verbatim.
  - Glossary target terms merge into the LANG-07 tokenizer dictionary automatically because they are TERM entries; a test asserts a multi-word glossary term is one lexical term once LANG-07 (4.2) is present.
  - Switch `RAG_TRANSLATION_GLOSSARY=false` (off: none of the above runs; on with no entries: no change).
- **D-15:** Admin UI: no new panel. The 4.1.1 Terminology panel gains a "Glossary" view (filter `kind = translation`, a target-language column, add/edit/import with the existing optimistic-version flow and routes). Golden `glossary` category: ≥ 3 items per language whose answer depends on an invented, neutral company term whose required translation differs from what a generic translation would produce (the fake query LLM in `eval/fixtures/query-llm/` scripts the generic translation so the eval shows the enforcement effect deterministically).

### Voice cross-language (XLG-07)
- **D-16:** The eval endpoint gains a `voice` entry-point option (or a harness that drives `/api/internal/voice-rag` in-process) so the `cross_lingual` slice runs through the voice profile, reported per language pair and gated by the same noise band as the text-chat slice. Two arms: voice without translate (multilingual embedding alone, today's `RAG_QUERY_VOICE_TRANSFORMS` default) and voice with `translate` added. The decision record (D-10 file) marks voice translate eligible only if the query-stage voice p95 stays within the Phase 6 D-29 voice budget (300 ms query stage within 800 ms) with the fake LLM's recorded latency profile and the slice improves; the default stays `condense_history,normalize_dates`. A voice `translate` timeout (code default 250 ms) is added to the voice profile; overrun skips translate (Phase 6 D-28).

### Query-language confidence (LANG-08)
- **D-17:** `src/lib/rag/lang/detect.ts` reports a numeric confidence in `[0, 1]` and chooses only among `RAG_SUPPORTED_LANGUAGES` (3.2 D-01; one enabled language → detection skipped, confidence 1). Low confidence = below a threshold in a committed params file (planner places it in `eval/config/query-params.json`), or ≤ 3 words, or code-dominated, or mixed scripts without a dominant one. Fallback chain for low confidence, first that answers wins: (1) sidecar fastText language ID `POST /v1/langid` behind `RAG_LANGID_SIDECAR=false`, constrained to enabled languages, timeout 30 ms chat/embed, never in voice; (2) the previous turn's language stored with the standalone query (D-23); (3) the request's UI language when enabled (chat and embed bodies send it; Zod-validated); (4) `RAG_PRIMARY_LANGUAGE`. Separately, when an LLM transform runs anyway (condense, translate), its structured output reports the language and that value overrides the detection for the answer-language instruction and translation targets only (no extra call). The chosen step is traced (`language_source`).
- **D-18:** The fastText model and package are a sidecar optional extra (`langid`); the researcher picks the package and model file (license, size, age ≥ 2 weeks). Installing it is a package-approval human checkpoint (same gate as Phase 6 D-21). Without it the chain skips step 1. Detection cases: `eval/fixtures/lang-detect/cases.jsonl` with short (2–3 words), accent-free and mixed-script cases in every enabled fixture language, synthetic and domain-neutral, run as unit tests and in the eval smoke tier.

### Auto model routing (LAT-06)
- **D-19:** An "Auto" model entry (`id: 'auto'`, `displayName: 'Auto'`) is added to the five model locations (AGENTS.md §7). `RAG_MODEL_ROUTING=off|auto` (default `off`); `RAG_ROUTING_FAST_MODEL` and `RAG_ROUTING_QUALITY_MODEL` name two IDs that must exist in the model lists (check-config verifies; the researcher proposes defaults from the current lists). With routing `off`, selecting Auto resolves to the quality model. A model the user picked explicitly is never replaced.
- **D-20:** Router: pure, no LLM call, after retrieval and before generation (it needs context size), in `src/lib/rag/generation/` (planner names the file). Inputs: the `classifyQuery` result already passed in (Phase 6 D-09), the gate result, the final `QueryPlan`, assembled-context token count. Fast tier only when all hold: classifier `document_search`, no R3/R5/R6/R8 fired, no decomposition, no translation, query below the R11 length, context below a token threshold in the params file. Everything else → quality. Trace `model_route: { tier, rule }`. A routed Claude model uses GEN-01 Citations when present. Applies to chat and embed; voice keeps its own LLM. The decision record marks Auto eligible only if judge answer correctness and refusal rates stay within the noise band per language and category against the fixed quality model while generation p95 drops (fixture runs report; the latency proof is live verification).

### Speculative retrieval (LAT-07)
- **D-21:** `RAG_SPECULATIVE_RETRIEVAL=false` keeps the Phase 6 D-05/D-32 order exactly. When on (v2, query layer on, chat/embed/eval; voice optional only if the eval shows a gain): after `query_gate` and the deterministic `normalize_dates` (sub-millisecond, so the R2 filter is ready), embedding and search of the original query start in parallel with `condense` and the parallel transform group. Each variant is embedded and searched as it arrives (batched where several arrive together); fusion runs once when all transforms finished or the Phase 6 D-27 group deadline fired, so RRF inputs are identical to the sequential order; a transform that overruns is dropped as in Phase 6 D-28. The semantic-cache check still runs after `condense`; a hit aborts all in-flight embedding and search through the shared `AbortSignal`. Rerank and refusal still use the standalone query (Phase 6 D-06). Trace: `speculative: { started_ms, overlap_ms, cancelled_by_cache, wasted_searches }`. Eval: pre-retrieval p95 with the fake LLM's latency profile; eligible only if lower with no slice beyond noise.

### Follow-up fallback (QRY-12)
- **D-22:** Every chat, embed and WhatsApp turn stores `rag: { standaloneQuery, queryLanguage }` in the persisted message metadata (the condensed query, or the original when no condensing was needed; capped at 1,000 characters; stored with the user message). The chat request reads the previous user turn's value from the request's message metadata (Zod-validated, length-capped; it is the caller's own text and cannot change scope); when absent (older messages) it uses the previous user message text.
- **D-23:** When the gate asked for `condense_history` and `condense` was skipped (`timeout | error | aborted | protected_token_lost`, Phase 6 D-28), the plan adds a deterministic variant of kind `history_fallback`: previous standalone query + newline + current follow-up. It is embedded in the same `embedBatch`, searched and RRF-fused next to the original, traced, not counted against the Phase 6 D-08 LLM-variant limit, counted toward the 8-search cap. Applies to voice when voice sends history. Switch `RAG_QUERY_HISTORY_FALLBACK=true`, inert under master off.

### WhatsApp history (QRY-13)
- **D-24:** Behind `RAG_WHATSAPP_HISTORY=false`, `src/lib/whatsapp/webhook-handler.ts` sends the last turns of the conversation it already stores (`chats.messages` for that sender's conversation in that session): Phase 6 D-16 window (6 turns, each ≤ 1,000 characters, assistant turns stripped of sources, citation markup and `source_images`). History is loaded only by the conversation id resolved from the same sender JID and session; a two-sender test asserts no crossing. The existing reset command (`reset`, `new chat`, `/reset`) clears `messages`, so the next turn has no history (test). With the switch off the handler sends only the current message, as today. The standalone query metadata (D-22) is stored on WhatsApp turns too. The eval harness runs the fixture `multi_turn` items through the WhatsApp entry point with a fake WhatsApp client and placeholder JIDs (no real phone numbers).

### Scope gate (QRY-14)
- **D-25:** Data: `rag_scope_centroids (tenant_key, embedding_profile_id, group_kind ('doc_type' | 'scope_tag' | 'tenant'), group_key, centroid halfvec, member_count, updated_at)` and `rag_scope_negative_examples (id, tenant_key, text, embedding_profile_id, embedding halfvec, created_by, created_at)`, RLS on with no client policies, service-role functions only (D-02). Centroids are the mean of current, ready chunk embeddings per group in the active embedding profile, maintained by a post-publish step in the unified ingestion path plus a rebuild CLI `npm run rag:scope-centroids -- --tenant <key>`. No built-in topic list anywhere; what is in scope comes only from each tenant's documents, doc types and DATA-18 tags. Admins add tenant-specific out-of-scope example texts in the Config UI (embedded at save time).
  - **Reversibility:** one-way — new tables and functions.
- **D-26:** New optional stage `scope_gate` after `embed` (and after the `semantic_cache` check), before search; pure in-process scoring on a per-tenant cached centroid set (LRU, 60 s TTL, like 4.1.1 D-22), p99 < 5 ms asserted by a unit benchmark. Score = max cosine similarity to the tenant's centroids, compared with the max similarity to its negative examples. Labels: `in_scope`, `out_of_scope` (only when the score is below the calibrated threshold with the calibrated margin, or a negative example is closer), `unsure` (everything else, and every case with no centroids, a missing calibration, a load error or a timeout). Only `out_of_scope` skips search: retrieval status `empty` with `skip_reason: 'out_of_scope'`, so strict mode gives the existing "information not available" response (or calls webSearch when on, AGENTS.md §14), and balanced/flexible answer without knowledge-base context with a localized label (language-pack text). `unsure` always retrieves. Label and score on the trace. Voice: hard-coded off until a voice latency measurement within budget is recorded. The cache does not store `out_of_scope` turns.
- **D-27:** Calibration `python -m rag_eval.calibrate scope` writes `eval/config/scope-gate.json` (Pydantic `ScopeGateCalibration`, per embedding profile and RAG mode) from fixture answerable and no-answer items, using the RNK-07 false-refusal target per mode from `eval/config/refusal-calibration.json` (Phase 4.2). Golden additions: synthetic off-domain `no_answer` items in zh/en/it (≥ 4 per language) about a topic no fixture document covers, against fixture passages that are topically adjacent. Eligible only if correct refusals rise and false refusals stay within the noise band; with the switch off nothing changes. Switch `RAG_SCOPE_GATE=false`.

## Summary

Phase 6.2 is twelve additive slices on a query layer that is only partly on trunk. The contracts (`QueryPlan`, transform outputs, `QueryParams`, eval overrides), the rewrite gate, the shared post-checks, the date normalizer, the cache key and bypass rules and migrations 0601 to 0603 exist. The orchestration that every 6.2 slice plugs into (`runQueryLayer`, `QueryTransformer`, the query LLM and its fake, the variant caps, the chat/embed/voice wiring, the eval overrides mapping, the "Query layer" panel) is still planned in Phase 6 plans 06-10, 06-13 to 06-16 and 06-18 to 06-46 (summaries exist on disk for 06-01 to 06-09, 06-11, 06-12 and 06-17). Nothing of Phases 3.2, 4.1.1, 4.2 or 5.2 is on trunk. Every 6.2 plan therefore opens with a precondition check (D-01), and the plan order below is driven by which foreign seam each slice needs.

Five findings change how the phase should be planned. (1) `checkSubQuestions` discards the whole decomposition when the kept sub-questions together lose a protected token, so the completeness repair (D-04) has to run before that union check, not after it. (2) `version_compare` items cannot retrieve a superseded version at all until the Phase 4.2 `versions` filter exists, because the filter contract pins `current_only` to true; that slice is gated on RET-11 and should be its own plan. (3) The chat client does not send per-message metadata and the persistence helper keeps an allowlist, so QRY-12 needs client, type and server changes, not only a server read. (4) The WhatsApp handler posts to `/api/chat` without a session and parses a stream format the chat route no longer emits (read, not run); QRY-13 must start with an end-to-end test that proves or disproves this. (5) A read-only spike on the committed fixtures suggests coarse centroids separate off-domain questions only partly and push cross-language questions below the threshold unless translated variants are scored too.

One new package is proposed: `fasttext-predict==0.9.2.4` with the model file `lid.176.ftz`, behind the D-18 human approval. Everything else reuses libraries already in the repository.

**Primary recommendation:** plan in the D-32 order, one vertical slice per plan, tracer first (eval route, fake decomposer that drops a term, completeness repair, trace), and give every plan a first task that checks its foreign seams by symbol and stops with the owning phase's name when one is missing.

        ▼

        │                                              └→ post-checks → *completeness repair → *per-sub-question filters (narrowFilters)
        ▼

        ▼

### Findings by question

#### F-1 Decomposition completeness (QRY-09)

- Post-checks run in `checkSubQuestions(sub, limits)` in `src/lib/rag/query/post-checks.ts`. The native decomposer that calls it is plan 06-15 (`src/lib/rag/query/llamaindex/decompose.ts`), the LangChain one is 06-37.
- Behaviour today `[VERIFIED: post-checks.ts:83-116]`: a sub-question that keeps none of the protected tokens is dropped with `protected_token_lost`; the list is cut to `maxSubQuestions` with reason `cap`; then, quoted: `if (kept.length > 0 && !keepsProtectedTokens(kept.join('\n'), protectedTokens)) { return { subQuestions: [], notCompound: false, skipped: [{ kind: 'decompose', reason: 'protected_token_lost' }] }; }`.
- Consequence: with the code as it is, a decomposition that loses one protected token never reaches a repair step. D-04 wants that case repaired. **Use this order when `RAG_QUERY_DECOMPOSE_COMPLETENESS` is on:** per-question checks → completeness repair → cap → union check. With the switch off, call `checkSubQuestions` exactly as today.
- Required-term sources and their state: protected tokens (`scanProtected`, on trunk; explicit dates are already among them through the lexicon's `patterns.explicit_date`); relative-time spans (`matchRelativeTime`, on trunk); bare years (no year pattern exists in the lexicon `patterns` keys `exact_code`, `zh_gai`, `zh_elliptical`, `comparison_between`, `relative_time_n`, `quoted`, `url`, `email`, `currency_amount`, `number_with_unit`, `explicit_date`, `version`; add one data key there, the range 1900 to 2100 matches what `timeframe.ts` accepts); DATA-18 vocabulary values (3.2); TERM matches (4.1.1 `QueryStagesOutput.terminology.matches`); entity heuristic (new, pure).
- Each class from a foreign seam is optional input: when the seam is absent or its switch is off, that class contributes no terms. The function stays pure: `collectRequiredTerms(query, gate, vocab?, termMatches?)` and `checkDecompositionCompleteness({ original, subQuestions, required, maxSubQuestions })` returning the repaired list and `{ required_count, missing_count, action }`.
- Matching uses `normalizeLexical` (4.1.1 exports it; on trunk `tokenize.ts` exports only `lexicalTokens`, `lexicalText`, `queryLexicalTokens`, `identifierLexicalLookupForms`, `LEXICAL_VERSION`). Protected tokens keep their verbatim rule (`keepsProtectedTokens`), so two match modes exist; keep them apart per class.
- Sibling substitution works on surface forms: replace the sibling's surface substring in the cloned sub-question with the missing term's surface as written in the original question.
- A cloned sub-question is a new variant: it counts toward the four sub-questions and the eight searches.

#### F-2 Per-sub-question filters (QRY-10)

- Filter object today `[VERIFIED: src/lib/rag/backend/types.ts:7-22]`: `currentOnly: true` (read-only), `dateRange?: { from?; to? }`, `sources?`, `documentIds?`, `docTypes?`, `languages?`, `invoice?`. The Pydantic twin `[VERIFIED: retrieval.py:88-128]` has `date_range` (`from`, `to`, `include_undated: bool = False`), `sources`, `document_ids`, `doc_types`, `languages`, `invoice`, `current_only: Literal[True] = True`. Request parsing accepts `dateRange`, `sources`, `documentIds`, `docTypes`, `languages`, `invoice` in a strict object, rejects empty lists and `from > to` (`[VERIFIED: src/lib/rag/query/filters.ts:18-41, 116-171]`). `buildRetrievalFilters` merges the explicit filter with referenced document IDs by intersection and uses a no-match UUID when the intersection is empty (`[VERIFIED: filters.ts:173-205]`).
- Tenant handling is structurally separate: the RPC argument `p_tenant_key: scopeKey(req.scope)` comes from the request scope and no filter field feeds it (`[VERIFIED: pgvector.ts:100-124]`). A per-variant filter therefore cannot change the tenant as long as it stays a `RetrievalFilters` value.
- Variant search today `[VERIFIED: src/lib/rag/v2/stages/search.ts:196-234]`: one `backend.search` per variant inside `Promise.all`, all with the shared `filters` constant. **Add an optional `filters` field to the variant and use `variant.filters ?? filters` in that call.** Plan 06-20 already adds per-variant fields (`legs`, `subQuestionIndex`, `denseText`) to the same type, so a field is the consistent choice over a parallel map.
- The exact-ID leg stands down when the shared filter narrows (`hasNarrowingFilters`), and it searches `input.query` only; per-variant filters do not touch it.
- No SQL change is needed in 6.2 for QRY-10: `p_scopes`, `p_scopes_include_untagged` and `p_effective_on` come from 3.2 migration `0802`, the version parameter from 4.2.
- `narrowFilters(base, proposed, tenantVocabulary)` rules: date ranges intersect, an empty intersection drops the proposal; `doc_types` and `scopes` values are dropped unless the tenant has them, then intersected with the base; `languages` are limited to the supported set and the base; `SubQuestionFilter` has no "include" flags, so `include_undated` and `includeUntagged` are inherited from the base and can never be switched on by the model; `documentIds`, `sources` and `invoice` are not in the allowlist and are copied from the base.
- The tenant's own doc types in use need a server-role read (reserve it in `0983`, same tenant-key checks as `rag_tenant_language_shares`), cached per tenant like the language shares. Scope values come from the 3.2 function `rag_scope_vocabulary_for`.
- **`versions` is the one allowlisted field that widens something:** RET-11 lets `all` or `range` include superseded versions of the same tenant. Treat it as narrowing-neutral for tenant scope but gate it: accept it only when the gate fired `R3_COMPARISON` or the question contains a period term, and make the semantic cache bypass such turns (RET-11 text). A caller filter that asks for current versions wins.
- LLM output shape: Phase 6 adjustment A-5 requires all fields of LLM-output models to be required and nullable. Add a second output model for the switched-on case (`questions: list[SubQuestionSpec]` with `filter` required-nullable) and keep `SubQuestions` untouched for the switched-off case, so requests, fake-LLM keys and the framework parity tests do not move when the switch is off.
- The prompt addendum lists slugs only (scope values are slugs in 3.2 D-38), capped per dimension; labels and aliases are admin text and must not be pasted into the prompt.
- Cap: `max_searches` (default 8, hard maximum 8) is enforced when the variant list is built (plan 06-20). Retry budget = `max_searches − variants.length`, consumed in sub-question order; a retry uses the base filters, never anything wider; a skipped retry is traced. Whether the 4.1.1 `term:0` lexical call and the 3.2 translation legs count toward the eight is not stated anywhere (Open Questions).

#### F-9 Speculative retrieval (LAT-07)

- Sequence today in `runV2Pipeline` (`[VERIFIED: src/lib/rag/v2/pipeline.ts:80-123]`): `runQueryStages` → one `embed` stage over all variant texts → `runSearchStages` (parallel search per variant, then `fuse`, `dedupe`). After Phase 6 the query stage calls `runQueryLayer` (gate → condense → parallel group → cache check) and returns a `QueryLayerOutcome`.
- Least invasive design: `runQueryLayer` starts the original query's embed and search as an unawaited promise right after the gate and the early date normalization, and returns a handle in its outcome. The `embed` stage then embeds only the remaining texts and the search stage accepts the precomputed legs for variant 0. Fusion code does not change, so list names and order are the same.
- Keep the speculative work outside `runStage` and adopt its result inside the normal `embed` and `search` stages. A failed or aborted speculation then falls back to the normal path and never creates an `error` record (`deriveStatus` turns any `error`, `timeout` or `aborted` record into status `error`: `[VERIFIED: src/lib/rag/pipeline.ts:191-197]`).
- **Filter equality:** the speculative search uses the R2 range computed from the original text. Condensing can bring a relative-time expression in from the history, which changes the range. Compare the filter object used speculatively with the final one before adopting; on a difference, search again and count a wasted search.
- **Embedding equality:** the original is now embedded alone instead of inside the batch. With the fixture embedder the vector is identical; a live provider may return tiny numeric differences between calls `[ASSUMED]`, which can reorder near-ties. State this in the plan; the "identical RRF inputs" proof is a fixture proof.
- Abort plumbing exists end to end: `BackendSearchRequest.signal`, `embedQuery(text, signal)`. Give the speculation its own `AbortController`, combine with the request signal through `AbortSignal.any`, abort on a cache hit, and attach a catch handler at creation so an aborted promise never becomes an unhandled rejection.
- **When it can pay off (reasoning, not measured):** variants produced by transforms still need embedding and search after their transform ends, so when the slowest transform yields a variant the wall time is unchanged. A gain appears when the last transform to finish yields nothing new (condense pass-through, "not compound", a skip or the group deadline), because the original's results are then already there. The fixture latency profile must contain such cases, and the report should split "new variant" from "no new variant" turns.
- "Pre-retrieval p95" in D-21 needs a definition that can show the effect; the query-stage time alone does not change. See Open Questions.
- A clock is injectable (`TraceCollector` takes `now`), and plan 06-10's fake LLM has `delay_ms` entries, so the overlap can be asserted with fake timers.

#### F-12 Scope gate (QRY-14)

- **Storage.** Embeddings live in two places. The legacy profile stays in `document_chunks.embedding` as `vector(1536)` (header comment of migration 0307). Every other profile is in `chunk_embeddings` (`[VERIFIED: supabase/migrations/0308_chunk_embeddings.sql:10-20]`, quoted: `embedding halfvec NOT NULL`, `dims integer NOT NULL`, `tenant_key text NOT NULL`, `PRIMARY KEY (chunk_id, profile_id)`), with no fixed column dimension. Seeded profiles are 1024 or 2048 dimensions; the fine-tune slots are 1024. Give the centroid column the same shape: `halfvec` without a fixed dimension plus `dims`, and compute the legacy profile's centroids from the cast column.
- **Computation.** `AVG(embedding) ... GROUP BY` in one statement per tenant and profile. Cost grows with the tenant's chunk count; no measurement exists `[ASSUMED]`. Record the time on the fixture and in live verification.
- **Maintenance.** Hook: `registerPostPublishHook` from 3.2 plan 14 (the hook has a time budget and never fails ingestion). A publish is not the only membership change: soft delete, doc-type change, scope-tag change, supersession, re-embedding and profile activation also change the set. Follow the 0603 pattern: single-event triggers on `documents` delete the tenant's centroid rows in the same transaction, and the hook or the CLI rebuilds. Missing rows mean `unsure`, so a stale gate fails open.
- **Profile changes (6.1, 3.1.1).** Centroids are per profile. After a profile flip there are none for the new profile until `npm run rag:scope-centroids` runs, so the gate is `unsure`; add the command to the activation runbook. With per-doc-type bindings (3.1.1, used by 6.1 D-33) one query embedding does not live in the space of every document. Treat a tenant with any scoped binding as `unsure` in this phase.
- **Scoring speed (measured here, Node 22.23.5, pure JavaScript dot product over unit vectors, 300 queries per row):**

  | dims | vectors | p50 | p99 |
  |------|---------|-----|-----|
  | 1536 | 50 | 0.171 ms | 0.239 ms |
  | 2048 | 50 | 0.099 ms | 0.116 ms |
  | 2048 | 200 | 0.413 ms | 0.456 ms |
  | 2048 | 1000 | 2.183 ms | 2.406 ms |

  One machine, one run, synthetic vectors. It supports the 5 ms target with a cap of a few hundred vectors per tenant (centroids plus examples). Cap both lists.
- **No I/O in the stage.** A cache miss must not wait for the database. Return `unsure` immediately and refresh in the background (stale-while-revalidate); otherwise the first request after each 60 s expiry breaks the budget.
- **Separation on the committed fixtures (exploratory spike, read-only).** Script: fixture embedder (`fixture-ngram`, 1536 dims), 13 documents, 71 chunks, centroids as normalized means, score = max cosine. Threshold = 5th percentile of answerable non-cross-lingual items. Four groupings were tried, once each, no tuning:

  | Grouping | centroids | existing out-of-domain items below threshold (n = 6) | near-miss no-answer items below (n = 24) |
  |----------|-----------|------------------------------------------------------|-------------------------------------------|
  | tenant | 1 | 1 | 1 |
  | doc type | 5 | 3 | 3 |
  | doc type × language | 10 | 4 | 4 |
  | document | 13 | 5 | 5 |

  Second run (doc-type centroids, threshold from the dev split only, 0.051): of 26 answerable `cross_lingual` items, 4 scored below the threshold with the original query alone and 0 when the maximum over the original and its fixture translations was used.

  What this does and does not show: it is six out-of-domain items, a lexical hash embedder and my own percentile rule, not `fit_threshold`, no margin, no holdout. A real embedding model will give different distributions. It does suggest (a) the D-25 grouping separates about half of the existing out-of-domain items at a 5% false-refusal point, (b) finer groups separate more, and (c) **scoring only the original query would refuse answerable cross-language questions**, so the gate should score every non-HyDE variant embedding and take the maximum. - **Status flow.** Strict mode blocks when, quoted, `ragMode === 'strict' && !webSearchEnabled && (retrievalResult === null || retrievalResult.status === 'empty') && usedDocuments.length === 0` and the context starts with "no relevant context found" (`[VERIFIED: src/app/api/chat/route.ts:2250-2256]`). Reuse the small-talk short-circuit of plan 06-19 to skip search, rank and context. The eval route must count the turn as refused, and the trace reason literal needs the new value (today `RefusalReason` is `"no_relevant_context"`, `"below_threshold"`, `"below_similarity_floor"`, `"injection_filtered"`: `[VERIFIED: eval_run.py:200]`).

### Anti-patterns to avoid

- **Changing `SubQuestions` or the decomposer prompt when the filter switch is off.** It moves fake-LLM keys, parity tests and the baseline. Use a second schema and an addendum file.
- **Appending glossary terms to `gate.protectedTokens`.** It silently turns off the semantic cache for those queries.
- **Awaiting a centroid load inside the stage.** Breaks the 5 ms rule on every cache expiry.
- **Running speculative work through `runStage`.** A cancelled speculation would be recorded as `aborted` and the request would become an error.
- **Sending `auto` to a provider or a helper.** Resolve it once at the top of each route.
- **Stubbing a missing foreign seam in `src/`.** D-01 allows fakes only under `tests/` and `eval/fixtures/`.
- **Hand-editing `eval/config/*.json` or `eval/decisions/*.json`.** Tools write them.

## Common Pitfalls

### Pitfall 1: The repair never runs
**What goes wrong:** completeness is added after `checkSubQuestions` and the dropped-token case is already discarded.
**How to avoid:** restructure the call order under the switch (F-1). **Warning sign:** the "drops one protected token" test passes only with a fake that bypasses the post-checks.

### Pitfall 2: A filter that widens
**What goes wrong:** the proposed filter sets or implies something the base did not allow (`versions: all`, untagged documents, undated documents).
**How to avoid:** the allowlisted model has no include flags; `versions` is accepted only under the rule in F-2; property test "result set of narrowed filter ⊆ result set of base filter" on the fixture database for every field except `versions`, which has its own two-tenant test.

### Pitfall 3: Variant index drift in provenance
**What goes wrong:** GEN-13 maps leg keys to sub-questions through the plan's variant order, but caps or de-duplication removed a variant before search.
**How to avoid:** carry `subQuestionIndex` on the searched variant and map through the list the search stage received.

### Pitfall 4: Switch-off parity broken by contract changes
**What goes wrong:** adding fields to LLM-output models or prompts changes requests even with every switch off.
**How to avoid:** additive nullable fields only where a change is unavoidable (condense language), separate schemas elsewhere, and the D-31 (a) run before any golden change.

### Pitfall 5: Cross-language false refusals from the scope gate
**What goes wrong:** the original query is far from every centroid in another language.
**How to avoid:** score all non-HyDE variant embeddings and take the maximum; label `unsure` when the gate asked for translation and it was skipped. **Warning sign:** `pair:` slices lose answers when the switch is on.

### Pitfall 6: Stale or partial centroids refuse valid questions
**What goes wrong:** a new document's topic is not in the centroids yet.
**How to avoid:** delete-on-change triggers so staleness means `unsure`; never keep centroids across a membership change.

### Pitfall 7: `auto` leaks or the citation path disagrees with the routed model
**What goes wrong:** a helper receives `auto`, or the labeler was decided for one model and the strategy for another.
**How to avoid:** single resolution point, session setter, both routing IDs with the same citation eligibility by default.

### Pitfall 8: Speculation that changes results
**What goes wrong:** the speculative search used a different filter or the adoption changes list order.
**How to avoid:** filter-equality check, adoption only for variant 0, a test that compares fused candidate IDs and scores with the switch on and off on every fixture item.

### Pitfall 9: History crossing people
**What goes wrong:** WhatsApp history from another session or a group participant, or client-supplied metadata treated as trusted.
**How to avoid:** per-message stamps, no group history, two-sender and two-session tests; the standalone value is query text only.

### Pitfall 10: Two PGlite migration plans at once
**What goes wrong:** every PGlite test applies all migrations; `use_worktrees` is false.
**How to avoid:** chain the migration plans with `depends_on` and never run two in one wave (same rule as Phase 6 and 4.1.1).

### Pitfall 11: Foreign functions re-created from an old body
**What goes wrong:** 0980 replaces a TERM function starting from the planned text instead of the newest migration, losing a later fix.
**How to avoid:** locate each function by name in the highest-numbered migration at execution time; the operator rule from 3.2 applies in reverse too (after re-running a lower file that defines a replaced function, re-run the 098x file).

## Open Questions (each with the recommended resolution)

1. **`calibrate scope` before Phase 4.2 exists.** Known: one false-refusal target exists today; RNK-07 says a mode without its own target uses it. Recommendation: read per-mode targets when present, otherwise the single target for every mode. QRY-14 is then not blocked on 4.2.
2. **`target_language` CHECK and legacy `translation` rows.** Recommendation: `NOT VALID` constraint plus writer and validator enforcement; show legacy rows without a target in the Glossary view as incomplete; never invent a target.
3. **Grouping for centroids.** D-25 fixes `doc_type`, `scope_tag`, `tenant`. The spike suggests language-split groups separate better. Recommendation: keep the three kinds and make the group key language-specific (`<doc_type>/<language>`, `<dimension>:<value>/<language>`), which stays inside "learned only from the tenant's documents"; confirm with the first QRY-14 task and record the measured separation. This is a refinement of D-25, so the plan should state it as such.
4. **Which query embeddings the gate scores.** Recommendation: maximum over all non-HyDE variants (original, condensed, translated, sub-questions, history fallback).
5. **The "label" for balanced, flexible and embed.** Recommendation: a deterministic localized notice from the language pack written at the start of the answer stream plus `rag.scopeGate` in the message metadata, and one sentence in the prompt telling the model not to repeat it. If the 5.2 label mechanism (GEN-08, GEN-15) exists at execution time, use that instead.
6. **Routing defaults: empty (D-28) or proposed IDs (D-19).** Recommendation: follow the Phase 6 precedent and write the two proposed IDs as defaults in the five locations; routing stays off through `RAG_MODEL_ROUTING=off`, and check-config verifies both IDs are in the lists.
7. **Auto entry for which provider list.** Recommendation: OpenRouter list only (the routing IDs and the Claude ID map live there); with another provider selected the entry is not offered.
8. **Cache key on Auto turns.** Recommendation: key part `auto:<fast>|<quality>`, because the routed model is unknown at check time and eligibility already requires the tiers to answer equally within noise.
9. **Definition of "pre-retrieval p95" for LAT-07.** Recommendation: time from request start to the end of `fuse`, reported for all turns and split by "transforms produced a new variant" or not; eligibility on the all-turns p95.
10. **Searches that count toward eight.** Recommendation: plan variants and their filter retries count; the 4.1.1 `term:0` call and the 3.2 translation legs keep their own caps. State it in the trace so the number is checkable.
11. **Native review of new zh and it items.** Recommendation: when the 3.2 field exists, mark executor-drafted zh and it items `llm_drafted`/`pending`; D-31 gates then run on English and approved items and report the rest; add a native-speaker review step to the human checkpoints. If 3.2 plan 31 is not on trunk at execution, add the items without the field as Phase 6 does.
12. **Where the standalone query is stored.** D-22 says with the user message; the server can only attach it to the assistant stream. Recommendation: stream it on the assistant message and let the client copy it to the user message, as described in F-10.
13. **Scope gate and per-doc-type embedding bindings.** Recommendation: `unsure` for any tenant with a scoped binding in this phase; a per-profile gate is a later item.
14. **Year pattern.** Recommendation: add one key to the lexicon file's `patterns` (four digits, 1900 to 2100, not adjacent to another digit); the locked spec keeps all word lists in that file and this is additive.
