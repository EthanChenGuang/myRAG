# Phase 06.2 Plan 24: Speculative original-query retrieval Summary

**With `RAG_SPECULATIVE_RETRIEVAL=true` (v2, query layer on, chat/embed/eval) the original query's embedding and search start right after `query_gate`, beside condense and the parallel transform group; the search stage adopts them for the original variant only when its request is identical, a cache hit aborts them, and the fixtures show no fused-result change.**

## Task 1: seams (D-01)

All six depends_on SUMMARYs exist (06.2-16/20/21, 06-19/20/32) and the full transitive closure (354 plans) has SUMMARYs. `groupDeadline` is in run-layer.ts (3 matches). Seams found:

## Accomplishments

- `speculative.ts`: handle with `embedding`/`promise` that never reject, `take(request)` (single use, adopt on `sameSearchRequest`), `discard()`, `abort(reason)`, `markTransformsEnded()`, `trace(requestStart)`.
- run-layer: starts the speculation after the route is known, with the R2 range of the original (`normalizeRelativeDates(input.query)`, only when `normalize_dates` is routed and enabled), exactly as the final `dateRange` falls back; marks the transforms' end after the group joins; the cache stage reuses the speculative vector when standalone equals the original; a hit aborts it; the handle is returned in the outcome.
- query.ts: `filtersFor(range)` builds the same base filters as the final ones (explicit, referenced docs, effective date, layer range), before the attribute stage; any later change makes the request differ and the stage re-searches.
- search.ts: `speculativeSearchApplies`, `runSpeculativeSearch` (the same `variantSearchRequest` arguments as `runRound`'s first round); in `runRound` the original variant of the first round, unfiltered, pgvector, no identifiers, no history scope, no BM25 scoring, calls `take(request)` and falls back to `backend.search(request)`. Fusion code is unchanged.
- pipeline.ts: `runV2Pipeline` wraps the body, attaches `result.speculative` (by assignment, so non-enumerable result properties survive) and aborts the speculation on every exit; embed stage adds the speculative vector to the precomputed map; `out_of_scope` discards.
- deps.ts: `readRagEnvInput` now reads `RAG_SPECULATIVE_RETRIEVAL` (it was missing, so the switch could never turn on from the process env).

## Behaviour changes

- Off (default): none. No seam is built, run-layer starts nothing, search adopts nothing, no `speculative` field.
- On: an extra concurrent backend search only when the speculative one is not adopted (counted in `wasted_searches`); embed calls never exceed off (the speculative embedding replaces the original's batch slot and the cache stage's embed of the same text).

## Deviations from Plan

1. **Only the original speculates.** D-21 also says each later variant is embedded and searched as it arrives; the plan's action limits the work to variant 0, and so does this implementation. Later variants still go through the one embed batch and the search stage (the "batched where several arrive together" case). A follow-up could stream them; the gain is limited to turns where the slowest transform yields a variant (research F-9).
2. **Adoption checks the whole request, not only the filters** (stricter; see key decisions).
3. **Eligibility gate** (`speculativeSearchApplies`): no speculation under external backends, history version scopes, the identifier filter or BM25 lexical scoring, because the original's request cannot be rebuilt before the search stage there. With the switch on under those settings the trace field is absent.
4. **Test query wording**: the filter-mismatch case uses "What changed in it last week?" so the gate routes condense (a pronoun is needed), and condense brings in "yesterday".
5. `[Rule 1 - Bug]` `readRagEnvInput` did not read `RAG_SPECULATIVE_RETRIEVAL`; fixed with a failing test first (as the brief asked).
