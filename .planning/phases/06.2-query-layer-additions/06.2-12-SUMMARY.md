## Behaviour changes

- `RAG_WHATSAPP_HISTORY=false` (default): the chat request carries only the current message, as before; no stamp is written. The one stored-data difference: when the chat stream carries `rag` (query layer on), the WhatsApp user turn keeps it in `metadata.rag` (D-22, as chat does). With the query layer off nothing changes.
- `RAG_WHATSAPP_HISTORY=true`: each stored user and assistant turn gets `metadata.whatsapp = { sessionId, senderJid }`. The request sends `buildHistoryWindow` (6 turns, 1000 characters each, assistant sources, citation markers and images stripped) over only the stored turns whose stamp equals the current session id and sender JID, then the current message. Unstamped older turns and non-individual JIDs (groups, broadcast, newsletter; only `@s.whatsapp.net`, `@lid`, `@c.us` qualify) get no history. The latest windowed user turn carries its stored `rag`, so the chat route also gets `previousStandaloneQuery`.
- The reset commands (`reset`, `new chat`, `/reset`) already empty `chats.messages`; tests now prove the next request has no history.
- Logging: one `[WhatsApp History] Window built: { stored, turns }` line per message with the switch on (counts only).
- The switch is read per request through `loadRagConfig(...).queryAdditions.whatsappHistory` (06.2-03), independent of `RAG_QUERY_LAYER` (D-24).

## Decisions

- Research A3 did not hold: the stream parser was already fixed in 05.2-15 (UI-message SSE). The first reply test passes on the old code and stays as the end-to-end guard; the parser change here is only reading `messageMetadata.rag`.
- Collaborators are injected through the handler constructor (defaults unchanged), so the vitest tests and the node eval runner share one harness without module mocks.
- History matching is by exact stamp, on top of the existing owner+JID conversation key; this also separates two sessions of one owner that share a JID's conversation.
- Gold retrieval in the eval runner is read by replaying the exact messages WhatsApp sent to the chat route through the eval route (eval profile): under the fixture embedder the chat profile always refuses at the production 0.65 floor, and the fixture floor is eval-only by rule. Condense is read from the real chat stream (the `rag` metadata stored on the WhatsApp user turn).
- The report gates only items the query gate routes to condense (`condense_history` in the plan's gate transforms). 5 of 27 items (it-multi-turn-001..003, zh-multi-turn-002, -003) are not routed there by the Phase 6 gate lexicon (no pronoun/ellipsis rule fires); they are reported, not gated, and are the history-fallback case of 06.2-20.
