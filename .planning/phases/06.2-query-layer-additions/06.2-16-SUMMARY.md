# Plan 06.2-16 Summary: per-variant sub-question filters, one retry, search accounting

With `RAG_QUERY_SUBQ_FILTERS` effective, each sub-question whose decomposer filter survived `narrowFilters` (06.2-11) is now searched through `hybrid_search_chunks` with that narrowed filter. When the filtered search finds nothing, it is retried once with the shared filters, as long as the retry fits inside `max_searches`. Fusion (one RRF under the same `dense:<i>` / `lexical:<i>` list names), the single rerank on the standalone query and Phase 6 D-07 coverage are unchanged. With the switch off, no variant carries a filter and every search request is the Phase 6 one.

## Behaviour
- **Plan** (`plan.ts`): `buildQueryPlan` sets `filter_applied: true` on a sub-question variant whose spec kept a filter (absent otherwise, so the plan is unchanged with the switch off). `planToVariants` maps that spec's applied values to `QueryVariant.filters` (`currentOnly`, `dateRange {from,to}`, `docTypes`, `languages`, sorted `dimension:slug` scope tags) and `filterApplied: true`. The contract has no tenant, document, source or include field, so none can reach a variant.
- **applyVariantFilters** (`port.ts`): the shared filters are the base. A variant's date range is intersected with the base range, its doc types and languages with the base lists, and its scope tags per dimension (OR within, AND across, as 0802). Every other field (current only, document ids, sources, invoice fields, effective date, `includeUndated`, `scopesIncludeUntagged`) comes from the base. An empty intersection returns the base object itself, so it is never an empty search and it is never counted as filtered.
- **Search stage** (`stages/search.ts`, native path): each variant searches `applyVariantFilters(roundFilters, variant)`. After the first round, every filtered variant with no dense and no lexical hit is retried once with the round's shared filters, in variant order, while `max_searches − variants − (term:0 searched ? 1 : 0)` leaves room. Otherwise it is marked `retrySkippedCap`. The retry's legs replace the empty ones under the same variant index. The term:0 call, binding, translation and soft legs and the exact-ID and table lookups keep using the shared filters. The exact-ID and table stand-down still reads `appliedFilters`, the shared base, so a variant filter never disables them.
- **Port** (framework delegate path): the same `applyVariantFilters`, plus the same single retry, drawn from the same budget, inline per variant search. `handle.filterRetries()` reports the outcomes.
- **Accounting (P-10)**: `SearchStagesOutput.searchesCounted = variants + retries` whenever `maxSearches` is given (the pipeline gives it whenever the query layer runs). The term:0 call and the translation legs are not counted. `filterRetries` is present only when some variant was filtered.
- **Pipeline/trace**: the pipeline passes `maxSearches` from `effectiveQueryParams` (eval overrides apply under the eval profile). It writes `retried` / `retry_skipped_cap` into the matching `query_plan.filter_trace` entry and sets `RetrievalResult.searchesCounted`. The eval route traces it as `searches_counted`. No new log line.
- **Tenant scope**: `scope` and `access` on every request are the request's own. No filter field feeds `p_tenant_key`.
