# 06.2-36 SUMMARY: two-tenant canary rows for the Phase 6.2 components

The two-tenant matrix now has a security canary row for each Phase 6.2 component that touches a tenant. Each row runs in both deployment modes and turns on only its own 6.2 switch, on top of `RAG_PIPELINE=v2`, `RAG_LEXICAL_SEARCH=true` and `RAG_QUERY_LAYER=true`. The existing rows are unchanged; the full file passes with 352 tests and 0 failures.

## Task 1: precondition (D-01)

- The 06-42 and 04.1-12 SUMMARYs are present, `V2_CANARY_PROFILE_ID` appears 7 times in `eval/harness/two-tenant-v2.mts`, and the matrix file exists. All 352 transitive depends_on SUMMARYs are on the branch.
- **Row shape of the 06-42 matrix:** one large multi-tenant `describe` over `createTwoTenantV2Database` (tenants a, b, o), with loops over profile × tenant label × path × scoring. Each row asserts with `assertOwnRows` (chunk, document, parent and image tenant keys) and `assertNoForeignText` (`foreignMarkers`). A separate single-tenant `describe` runs on `createFixtureDatabase`: `s:default` is served, and personal and organization keys are refused as `backend_error`. Deps go through `setRagDepsForTests({ ragEnv, adminClient })` over `startFakeEdge`.
- **q62 seed helpers:** the q62 tests keep their seeds as local, unexported functions: `seedRows` in q62-subq-filters, `upsertPair` in q62-translation-glossary, `insertDoc`/`insertChunk`/`serviceRpc` in q62-scope-centroids. The exported helpers are `createWhatsAppHarness`, `seedConversation`, `inboundText` and `settleTitles` in `tests/whatsapp/harness.ts`, and `seedTerminology` in `eval/harness/pglite-supabase.mts`. The new rows reuse the exported ones. The local seeds are re-expressed once as shared helpers in two-tenant-v2.mts, and the q62 files are left untouched because they are not in this plan's files.

## Task 2: canary rows (commit cf71c4a6)

These rows run per mode on `createEmptyFixtureDatabase`. In multi-tenant mode tenant A is `u:userA` and tenant B is `u:userB`, holding the same token under values tenant A lacks. In single-tenant mode tenant A is `s:default`, and the "other tenant" is a personal key, which every component must refuse.

## Switch read in readRagEnvInput (TDD; commits 6379b653 RED, 235c4bbe GREEN)

- **Bug:** `RAG_SCOPE_GATE` and `RAG_WHATSAPP_HISTORY` were missing from `readRagEnvInput`. As a result, `RAG_SCOPE_GATE=true` set in the process never reached `loadRagConfig(getRagDeps().ragEnv())`, so the scope gate stage and the centroid post-publish hook stayed off in production.
- **Fix:** both values are forwarded as plain `process.env.X`, without an `env.X` fallback. Unset stays `undefined`, so the off state and `ragConfigHash` are byte-identical to before. The WhatsApp handler still reads its switch through `whatsappHistoryEnabled(process.env)`, so its behaviour is unchanged.
- **Test:** `tests/rag/query-additions-env-input.test.ts` failed on its assertion (`[undefined, undefined]` for the two switches) at the RED commit and passes with the fix.
