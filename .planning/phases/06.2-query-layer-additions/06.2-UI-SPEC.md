## 0. Findings that shape this contract (read first)

Facts from the code and from research. Each one changes what the UI can show or do.

1. **The Terminology panel does not exist on trunk and has no UI-SPEC yet.** `scripts/config-ui/rag-panels/terminology.js` is
   created by plan 04.1.1-13, whose first task is its own UI-SPEC gate; `04.1.1-UI-SPEC.md` is not on disk. This contract
   therefore specifies the Glossary view completely for everything that is new (tab, filters, table, form fields, states,
   copy) and adopts the panel's shared shell (layer switch, workspace line, entry dialog frame, import flow, pagination).
   Precedence rule: for a shared shell piece, `04.1.1-UI-SPEC.md` wins when it exists at execution; for everything this file
   adds, this file wins. The UI plan opens with the D-01 precondition `test -f scripts/config-ui/rag-panels/terminology.js`.
2. **The Query layer card is static markup on trunk** (`index.html`, `<!-- Query layer -->`, `#query-layer-card`, in the RAG
   Modes tab), English only, built from `.form-control`, `checkbox checkbox-primary`, `select select-bordered w-full` and group
   boxes `border border-base-300 rounded-lg p-4 mb-4 space-y-3` with an `h4.font-semibold.text-sm`. Its script module
   `query-layer.js` is planned (06-40) and not on trunk. The additions of this phase are static markup in that card plus one
   own script, so they need only the card.
3. **The page writes every changed field that has an `id` into the saved configuration.** A `change` listener on `document`
   (`index.html`, `document.addEventListener('change', …)`) takes `e.target.id` as the key, calls `updateConfig(key, value)` and
   saves after one second. An env control whose `id` is the env name is therefore saved automatically. A panel-local field
   with an `id` (a glossary term, an out-of-scope example) would be written into `.env.local` as a junk key carrying tenant
   text. Section 6.1 fixes the rule that prevents it.
4. **Config values are applied once, at load, with `field.value = value`.** A `select` whose options are built by script after
   that moment shows the wrong value. The two routing selects are script-filled (section 6.4.3) and re-apply the saved value
   themselves.
5. **Nothing of the scope gate exists yet:** no `/api/rag/admin/scope-gate` route, no `eval/config/scope-gate.json`, no
   centroid table. Section 8.1 lists what each view needs; field names there are **proposals to the backend plans**, the
   behaviour they support is the contract.
6. **The scope gate fails open.** It skips retrieval only when the switch is on in the running app, the v2 pipeline and the
   query layer are on, a calibrated threshold exists for the active embedding profile and RAG mode, and scope data exists for
   that profile in the workspace (D-26, research F-12). In every other case the label is `unsure` and the question is
   retrieved. A gate that is "on" can therefore do nothing, silently. The panel's first job is to say which of the two it is.
7. **An env switch reaches the app only after it restarts with the saved value.** The Refusal calibration panel already
   shows this as a "settings show X; the app uses Y" note; the Scope gate panel repeats that pattern.
8. **The chat model selector is list-driven and picks the default as `models.find(isDefault) || models[0]`**
   (`model-provider.tsx`). An entry placed first in a list without an `isDefault` flag would become every new user's default.
   The `auto` entry is data, not a component change, and its position in the arrays is part of this contract (section 6.5).
9. **A deployment that already saved `NEXT_PUBLIC_OPENROUTER_MODELS` does not get the Auto entry** until an admin adds it
   (research F-8). The Auto entry is offered in the OpenRouter list only (research open question 7).
10. **The glossary works with `RAG_TERMINOLOGY=false`** and `translation` is already a legal entry kind in 4.1.1, so rows
    without a target language can exist before migration 0980 (research F-5, open question 2). The view shows them as
    incomplete and never invents a target.
11. **All Config UI scripts are classic scripts in one global scope** (04-UI-SPEC finding 13). Top-level names in the new files
    start with the prefixes of section 6.1.
12. **`rag-panels/rag-ui.js` (shared helpers of Phase 3.2) may or may not be on trunk at execution.** The new files use it when
    it is loaded and carry private helpers under their own prefix when it is not (as `refusal-calibration.js` does). They
    never define its global names.
13. **Domain neutrality (REQUIREMENTS.md, owner rule).** No label, help line, placeholder, empty state or example in these
    surfaces contains a domain word or value. Terms and example questions come only from what an admin types. This file
    itself uses `⟨term⟩` and `⟨question⟩` where a wireframe needs content.

## 1. Design direction (frontend-design pass)

**Subject.** What the query layer is allowed to do with a question before it reaches the documents: which terms must be
translated one fixed way, which questions the knowledge base should not try to answer, and which optional steps are on.
**Audience.** Three people at a desktop. A terminology owner who knows the company's words and arrives with "this term must
always be rendered like that". A workspace admin who arrives with "users keep asking about something we do not cover". A
deployment admin who arrives with "is this switch doing anything, and what will it cost me".
**Primary job.** Show what is in effect right now, then let the admin change one thing whose consequence is stated next to
it.

**Mode.** Impeccable "Operate". These are working tools inside an existing dashboard; every container, table, badge, alert
and dialog is one the sibling RAG panels already use. No new navigation, no new control type.

**Organizing idea: "in effect now" comes before "settings".** Every feature of this phase is off, partial or fail-open by
default: a glossary that is saved but not enforced, a gate that is on but still retrieves everything, an Auto entry that
answers with the quality model. Each surface therefore leads with one plain sentence about what is in effect, then the
conditions behind it, then the editable data. An admin never has to infer the effect from a list of switches.

**Signature element: the readiness list** of the Scope gate panel (section 6.3.2). One headline sentence, then four lines in
one grammar: what is required, its state (badge with icon and word), the reason, and the way forward. It reuses the
state-reason-action order of the Phase 3.2 hold line, so an admin who has read Quarantine reads this without learning
anything. It is the only composite this phase adds; everything around it is plain tables and forms.

**Review against generic defaults (what was changed and why).**
- Rejected a gauge, meter or score histogram for the gate. No per-question score is shown anywhere (section 11); a threshold
  is one number in a table row.
- Rejected stat tiles for "reference points" and "examples". They are two counts and sit in a table and a count line.
- Rejected a chip or tag-input widget for out-of-scope examples. An example is a whole question; rows read better and wrap.
- Rejected an arrow glyph between a source term and its translation. Direction is carried by the column headers "Source
  terms" and "Required translation" and by the two filters "Source language" and "Target language".
- Rejected flags for languages. Languages are named in the UI language with their code.
- Rejected DaisyUI `toggle` for the new switches. The card and the sibling panels use checkboxes; a second control for the
  same job would be decoration.
- Rejected a setup wizard for turning the gate on. The four conditions are prerequisites, not a sequence, so the list is
  not numbered.
- Rejected a badge, sparkle icon or tier hint on the Auto entry in the chat selector. D-33 fixes "no other visual change".
- Rejected colour on thresholds, rates and counts. Colour describes a state the server names, never a number.
- Rejected one more group box per switch. Four switches that depend on a transform are nested under that transform, which
  is information; only two new boxes are added to the card.

**Quality floor (built without announcing it).** Visible keyboard focus, `prefers-reduced-motion` respected, all text at least
4.5:1, tabular numerals in number columns, usable down to 360px, every state in section 7 present, every server and admin
string inserted with `textContent`.

## 4. Spacing Scale

Tailwind spacing utilities only; no arbitrary pixel values. Same scale as `03.2-UI-SPEC.md` and `04-UI-SPEC.md`.

| Token | Value | Tailwind | Usage |
|-------|-------|----------|-------|
| xs | 4px | `gap-1`, `mt-1` | Icon to label inside a badge or button; a value to its second line; a field to its help line |
| sm | 8px | `gap-2`, `mb-2`, `gap-y-2` | Buttons in a row, badges side by side, heading to its description, rows of the readiness list, stacked alerts |
| md | 16px | `gap-4`, `mt-4`, `mb-4`, `p-4` | Between form fields, toolbar to table, table to the line under it, padding of the group boxes and of the example form region |
| lg | 24px | `gap-6`, `mt-6`, `gap-x-6` | Between sibling panels (existing `grid gap-6`); between the blocks of the Scope gate panel; the two columns of the glossary form |
| xl | 32px | `.card-body` default, `py-8`, `pl-8` | Card padding (DaisyUI default); vertical padding of empty-state blocks; the indent of a help line or child switch under its checkbox (the card's shipped indent) |
| 2xl | 48px | `h-12` (DaisyUI `btn` height) | Touch-size row actions below 768px |
| 3xl | 64px | not used | Reserved for page-level spacing |

Exceptions: one, a multiple of 4. **12px** (`gap-3`, `space-y-3`) appears only where this phase repeats the Query layer card's
shipped control markup verbatim: the switch label `label.label.cursor-pointer.justify-start.gap-3` and the group box
`space-y-3`. New groups must be indistinguishable from the "Transforms" and "Semantic cache" groups beside them. No 2px, 6px
or 10px spacing appears in new markup, and 12px appears nowhere else.

Component internals outside the scale (not spacing tokens, do not restyle): DaisyUI `table-sm` cell padding, `input-sm`,
`select-sm`, `textarea-sm`, `checkbox-sm`, `btn-sm` (32px), `btn-xs` (24px, link buttons only) and `btn` (48px) are used as
shipped. Row actions are `btn md:btn-sm`: 48px tall below 768px, 32px from 768px up. The card's `select` and `checkbox` keep
their shipped default sizes (48px and 24px).

Sizes that are not spacing: description and alert paragraphs cap at `max-w-prose`; the example text cell caps at
`max-w-prose`; the new-example textarea has `rows="2"`; the source-terms textarea has `rows="3"`.

## 6. Layout and interaction

### 6.1 Placement, files and mount

```
RAG Modes tab (#rag-modes)
  Query layer card (#query-layer-card)        EXTENDED  static markup + rag-panels/query-additions.js   (6.4)

RAG administration tab (#rag-administration, .grid.gap-6)
  …existing and other phases' panels…
  Terminology (Phase 4.1.1 panel)             EXTENDED  one tab "Glossary"   rag-panels/glossary.js      (6.2)
  Refusal calibration   #rag-administration-refusal      existing
  Scope gate            #rag-administration-scope-gate   NEW       rag-panels/scope-gate.js             (6.3)

App
  Chat model selector                          DATA ONLY  one more row, "Auto"                          (6.5)
```

- **Scope gate placement.** Directly after `#rag-administration-refusal`. The two panels answer the same admin question
  ("when does the system decline to answer from the knowledge base?"), so they sit together. If another phase has added a
  panel after Refusal calibration, Scope gate still goes directly after Refusal calibration. The tab's intro sentence is not
  edited.
- **Scripts.** Three new files, loaded after `rag-fetch.js` (and after `rag-ui.js` when that file exists):
  `rag-panels/query-additions.js`, `rag-panels/scope-gate.js`, and `rag-panels/glossary.js` (after `terminology.js`).
  `terminology.js` is edited only to add the Glossary tab and to call `window.initGlossaryView(host, api)`; `query-layer.js`
  (06-40) is not edited.
- **Global names.** Every top-level `const`, `let`, `class` and function in a file starts with that file's prefix:
  `QueryAdditions` / `QUERY_ADDITIONS_`, `ScopeGate` / `SCOPE_GATE_`, `Glossary` / `GLOSSARY_` (finding 11).
- **Shared helpers.** When `window.ragUi` (Phase 3.2 `rag-ui.js`) is loaded, the new files use its element builder, alert,
  sub-tab keyboard handling, confirmation dialog, error mapper, locale resolver and `RAG_UI_LABELS`. When it is not, each
  file carries the same small helpers privately under its own prefix (finding 12).
- **Skeleton.** `index.html` gets, for the Scope gate panel, a `section` with heading (`h3#rag-scope-gate-title`,
  `tabindex="-1"`), description paragraph, the static switch (6.3.1), one alert host, one content host and one status region
  (`div.text-sm.mt-4[role=status][aria-live=polite]`). The script builds everything else.
- **Mount.** `initScopeGatePanel()` and `initGlossaryView()` are idempotent: the first call mounts, later calls refresh and
  keep typed form values and a running poll. `scope-gate.js` binds **every** `[data-tab="rag-administration"]` element and
  runs on `DOMContentLoaded` when the tab is already active.
- **Locale.** Scope gate panel and Glossary view: `navigator.language` first two letters, `zh` or `it`, otherwise `en`, as
  the sibling RAG administration panels resolve it. Everything inside `#query-layer-card` is English, as the card is today
  (section 14, decision 18). The one exception is the pointer to the Scope gate panel, which that panel's script localizes
  exactly as `refusal-calibration.js` localizes its pointer.
- **Workspace.** Scope data and out-of-scope examples belong to one workspace. The Scope gate panel follows
  `#workspace-selector` (as Document types and Ingestion do), shows a 12px line "Workspace: {name}" under the description and
  reloads on its `change`. The switch and the thresholds are deployment-wide and say so. In single-tenant mode the line is
  not rendered. The tenant is always resolved by the server; the browser sends `organizationId` only, never a tenant key.
- **Requests.** App routes go through `ragFetch` with the full path. No `Authorization` header, nothing written to
  `localStorage`, `sessionStorage` or a cookie. Every call is wrapped in `try/catch` and has a 15-second client timeout.
- **Change-event isolation (finding 3, hard rule).** The content host of the Scope gate panel, the Glossary view and the
  glossary dialog each register a `change` listener that calls `event.stopPropagation()` for every field that is not an env
  control. No panel-local field value may reach `window.configManager.config`. Fields keep their `id` so `<label for>`
  works. The env controls of this phase (`RAG_SCOPE_GATE` and the eleven of section 6.4) are the only fields whose `change`
  reaches `document`. A test dispatches a bubbling `change` from the example textarea and from every glossary form field and
  asserts that `updateConfig` is not called.

## 9. Keyboard, screen reader and focus

1. **Headings.** "Scope gate" is `h3`; its block headings are `h4`. The two new group headings in the Query layer card are
   `h4`, like "Transforms". No level is skipped.
2. **Glossary tab.** `button[role=tab]` with `aria-selected`, `aria-controls` and the tablist's roving `tabindex`. Left and
   Right move and activate, Home and End jump. Its panel is `div[role=tabpanel][aria-labelledby][tabindex=0]`.
3. **Forms.** Every control has a visible `<label for>`; the two halves of the glossary form are `fieldset` with `legend`.
   Help lines and messages are wired with `aria-describedby`; invalid fields carry `aria-invalid="true"`. Term fields and the
   example field have `autocomplete="off"`, `spellcheck="false"` (terms) and `translate="no"`.
4. **Submit.** Primary buttons of the two forms stay enabled until the request starts; an invalid submit moves focus to the
   first failing field. Enter saves from a single-line input; Ctrl+Enter or Cmd+Enter from a textarea.
5. **Dialogs.** Native `<dialog class="modal">` with `showModal()`, `aria-labelledby` and `aria-describedby`. In a
   confirmation, focus starts on the safe button ("Keep…"). Escape and the backdrop cancel; while a request runs they do
   nothing. On close, focus returns to the opening button, or to the status region when that button is gone.
6. **Readiness list.** A `dl`. The badge's word is text, not a `title`. DOM order equals reading order: requirement, state,
   reason, way forward. The headline is a paragraph, not a heading, and is not a live region; changes are announced through
   the status region as `status.loaded`.
7. **Row actions** carry the term or the start of the example in their accessible name (`action.editAria`,
   `action.deleteAria`). There is no icon-only button. Dates use `<time datetime>`.
8. **Live regions.** One polite status region per panel, plus the polite warning host of the Speed box. Announced: load
   finished with counts, action outcomes, errors, rebuild progress at most every 30 seconds. A version conflict is
   `role="alert"`, because it answers an action just taken. Warnings rendered on load have no alert role.
9. **Tables.** Visually hidden `caption`, `th scope="col"`, the first cell of a row as `th scope="row"`. A table that can
   scroll sideways sits in `div.overflow-x-auto[tabindex=0][role=region][aria-label]`.
10. **Not colour alone.** Every state and warning has a word and an icon. A dimmed nested switch also has its
    `nested.parentOff` sentence.
11. **Pointer buttons** ("Open glossary", "Open scope gate", "Open RAG Modes", "Open AI Models", "Open query layer settings")
    are `button` elements, move focus to the target's heading or control, and scroll instantly under
    `prefers-reduced-motion: reduce`.
12. **Copy command.** Writes the command with `navigator.clipboard.writeText` and announces `copy.done` in the status region.
    When the clipboard is unavailable the command stays selectable in its `code` element and nothing is announced.
13. **Focus visibility.** DaisyUI's `focus-visible` outline on every control; `summary` elements and scroll regions add
    `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2`. Never `outline: none` without a
    replacement.
14. **Motion.** Only DaisyUI's spinner. Under `prefers-reduced-motion: reduce`, spinners are hidden (`motion-reduce:hidden`)
    and their text remains. Nothing slides, fades or pulses.
15. **Zoom and text size.** At 200% zoom nothing clips: no fixed heights; cells, toolbars and button rows wrap.
16. **Language.** `lang` on each localized root; each term carries the `lang` of its language; text left in English carries
    `lang="en"`.
17. **App.** Nothing changes: the Auto row is a `button` like every other row of the selector.

## 11. What must never be shown or done

1. **No score of a question.** No similarity value, label (`in_scope`, `out_of_scope`, `unsure`) or text of any user question
   appears in these panels, and the panels call no route that returns one. The only question texts shown are the examples an
   admin typed.
2. **No vectors.** No embedding, centroid value, dimension count or distance is rendered even when a response carries it.
3. **Every server and admin string** (terms, translations, notes, example texts, display names, model names and ids, profile
   ids, codes, `details[].message`) is inserted with `textContent`; never `innerHTML`, never a template string that becomes
   markup. Tests stub each of them with `<img src=x onerror=alert(1)>` and `javascript:` and assert that no element and no
   link is created.
4. **No panel-local value in the configuration.** Section 6.1, change-event isolation.
5. **No admin text in a URL, a `title` attribute or the console.** Examples and terms travel in request bodies; deletes go by
   id. Panel logs carry counts and codes only.
6. **Views render named fields only,** through builder functions, never by iterating an object's keys.
7. Never rendered even when a response carries it: tenant keys, layer keys other than through the panel's own layer switch,
   `normalized_variants`, `entries_sha256`, user ids when a display name exists, the calibration target percentage, cost
   figures.
8. No value of a variable whose name matches `/(KEY|SECRET|TOKEN|PASSWORD)/i` is read or rendered by any new script.
9. No `Authorization` header, no token in browser storage, no second sign-in form.
10. The script never changes a saved routing value, never adds or removes a model-list entry, and never offers `auto` as the
    fast or quality model.
11. **No domain content.** No label, help line, placeholder, empty state or test fixture of these surfaces contains a domain
    word or value (finding 13).
12. The app shows no routing tier, no routed model name and no gate label to the chat user (D-33 item 4; the localized
    out-of-scope notice in an answer is language-pack text of the generation path, not UI of this contract).

## 12. Copywriting Contract

Voice: plain verbs, sentence case, names from the admin's side of the screen. A message that reports a problem says what
happened and what to do next; errors do not apologize. One action keeps one name through its flow: the row button, the
dialog's confirm button and the outcome say "Delete example", "Delete example", "Example deleted". "Reload panel" always
means reloading a view.

**Words used, and words avoided.** "Glossary" for the translation pairs; "source terms" and "required translation" for the two
sides ("variant" and "canonical" are not shown). "Scope gate" as D-33 names it; "scope data" and "reference points" for what
the gate learned from the documents ("centroid" and "embedding" are not shown, except "embedding profile", which the page
already uses). "Out-of-scope examples" for the admin's questions ("negative example" is not shown). "Retrieved" for a
question that goes to the documents; "skips retrieval" for the opposite. "False refusals" and "correct refusals" as the
Refusal calibration panel defines them. "Auto" for the model entry, the same word in every language.

**Action labels are verb + noun in every locale.** Accessible names extend the visible label and start with the same verb.
In-flight text ("Adding…") is status on a disabled button, not a label. No button is labelled "Cancel", "OK", "Submit" or
"Close" alone: a button that backs out says what stays ("Keep example", "Keep entry", "Keep editing") or what it closes
("Close form").

**Counts are written as "label: number"** ("Entries: 14", "Examples: 2 of 100"), so no string needs a plural form.

**Where the strings live.** `GLOSSARY_LABELS` and `SCOPE_GATE_LABELS`, each `{ en, zh, it }`, read through one function per file
that fills `{placeholders}` and falls back to English. `QUERY_ADDITIONS_LABELS` holds English only (section 14, decision 18).
A placeholder shown as `{command}`, `{variable}` or `{profile}` is replaced by a `code` element, not by text. Numbers use `Intl.NumberFormat(locale)`; dates
`Intl.DateTimeFormat(locale, { dateStyle: 'medium' })`; language names `Intl.DisplayNames`.

Accent reserved for: the one primary action of each view ("Add glossary entry", "Save entry", "Add example"); the checked

headings, not the readiness headline, not "Rebuild scope data", "Refresh status", "Reload panel", "Reload entries", "Copy
command", "Import glossary CSV", "Edit entry", "Set target language", "Clear filters", "Keep editing" or "Discard changes"
(all outline or ghost), not badges, not the "Use this entry" checkbox, and not the routing selects.

Success, warning and error colours describe states the server or the page names (a readiness state, an entry state, a
missing id), never a judgement about a number. A threshold, a margin, a rate and a count are never coloured.
