# 06.2-14 Summary: glossary enforcement in query translation

With `RAG_TRANSLATION_GLOSSARY` effective (raw switch on and `RAG_QUERY_LAYER=true`), every translated query carries the tenant's
required glossary terms, is corrected once, or is dropped with `glossary_term_lost`. The original query is always retrieved. With
the switch off nothing here runs: no glossary read, the translate request is byte-identical to Phase 6, and the hash is unchanged.

## Task 1: seam check (D-01)

All depends_on SUMMARYs are on the branch (06-16, 06-23, 04.1.1-05, 04.1.1-16, 03.2-51, 06.2-04, 06.2-10, 06.2-11). Seams:

| Seam | Name now |
|------|----------|
| Loader | `loadEffectiveDictionary(scope, options)` / `terminologyMatcherFor` in `src/lib/rag/terminology/load.ts`. The cache key is `scopeKey(scope)` (60 s TTL, LRU 256), filled from `rag_term_effective(p_tenant_key)` on the service-role client |
| Translation pairs | `getTerminologyLexicon(scope, { includeTranslations: true, kinds: ['translation'] })`: `sources` = variants, `target` = canonical, workspace rows win collisions |
| Matcher | `buildMatcher(entries, { minHanChars })` in `matcher.ts`. It skips `kind = translation` entries (D-32), so the glossary builds its matchers from the pairs recast as one-way non-translation entries. This is the same matcher, not a second one |
| Terminology hash block | `terminologyHashBlock(stage, params, dense)`, fed by `onTerminology` from `runQueryStages` into `requestRetrievalConfigHash` (cache key and result) |

## Task 2: pure module and tenant loader

- `requiredTranslations(text, sourceLang, targetLang, glossary)` keeps only the rows for that language pair and matches the text with the 4.1.1 rules: Han substrings, Latin word boundaries, elisions and accents folded by `normalizeLexical`, longest match first, and `min_han_chars` from TerminologyParams. It returns one requirement per entry. Matchers are memoized per glossary object and language pair.
- `enforceGlossary(output, required)` returns one of three results. If every target is present (same matcher rules), the result is `ok`. If a target is missing but its source surface is still in the output, the first occurrence is replaced by the target as written, mapped back to the original spelling through a per-character normalization offset map, and the result is `corrected` with one replacement per missing term. Otherwise the result is `lost`. When the offset map cannot be built (composition across characters), the result is `lost`.
- `loadTenantGlossary(scope)` reads through `getTerminologyLexicon`, so it uses the per-tenant loader keyed by scopeKey whatever `RAG_TERMINOLOGY` says. It returns `{ tenantKey, version, pairs }`, or null on failure. It never throws and logs no term.

## Task 3: translator, addendum, run-layer and hash

- `translateRequests` (shared by the native and LangChain translators) appends `shared.glossary.v1` after the Phase 6 prompt. It is added only for the targets whose required pairs are non-empty. Each pair is one JSON line inside `<glossary>…</glossary>`, with glossary and query tags escaped (T-06.2-38). No glossary, an empty glossary or no matching term leaves the request byte for byte.
- `finishTranslate` enforces after the schema and target checks and before the D-15 checks. A corrected text then passes `checkVariant`, and `lost` records `glossary_term_lost`. The query-layer translator treats that reason as a post-check skip, not a call failure. run-layer maps it into `plan.skipped`.
- run-layer loads the glossary inside the translate task, only when the switch is effective, a scope exists and translate has targets. It reports `onGlossary({ enabled: true, version })` before semantic_cache builds its key. `gate.protectedTokens` is untouched, so the cache bypass set does not change (research F-5).
- Config hash: `glossaryHashBlock` returns `{ version, prompt_version }` while the switch is effective. `version` is `GLOSSARY_UNAVAILABLE` when the glossary was not loaded for the request. Otherwise it returns undefined, and the payload is unchanged. Both the cache key and the result hash get it through `pipeline.ts`/`result.ts`. `shared.glossary` is listed in `SWITCH_GATED_PROMPT_IDS` and kept out of the query-layer prompt-version list, so the hash with the switch off keeps its value.
- `eval/fixtures/query-llm/transforms.json` gains three `q62-glossary-*` scripts. Two are generic translations that miss an invented term (en→zh, it→en) and one keeps the untranslated source surface (zh→en). A test runs them with and without a glossary.
