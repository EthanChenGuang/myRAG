# 06.2-20 Summary: history_fallback variant (QRY-12, D-22, D-23)

When condensing fails, a follow-up is no longer searched with only its bare text. The plan now also gets one deterministic variant: the previous standalone query, a newline, then the follow-up.

## Task 1: seam check (D-01)
- Every plan in depends_on, transitive ones included (342 plans), has a SUMMARY on this branch.
- The SUMMARYs of 06-19, 06-20, 06-27 and 06-28 are present, and `protected_token_lost` appears in run-layer.ts.
- run-layer records condense skips with `skip('condense_history', …)` in the condense block, before the parallel group. The variant list is finalized by `buildQueryPlan`, then by `planToVariants`, and the v2 query stage caps it with `buildQueryVariantSet`.
- No blocker.

## Task 2: the variant (commits 0e08b0b9 RED, 48b91eaf GREEN)
- `buildHistoryFallbackVariant({ gate, skipped, previousStandalone, previousUserText, followUp, limits })` returns the text or null.
  - It applies only when the gate asked for `condense_history` and condense was skipped with `timeout`, `error`, `aborted` or `protected_token_lost`.
  - `length`, `cap`, `disabled_for_profile` and `glossary_term_lost` add nothing.
  - The previous text is the stored `previousStandaloneQuery` (D-22). Without one it is the previous user turn of the history window. With neither, or when it equals the follow-up, there is no variant.
- run-layer calls the builder after the condense outcome is known, under `config.queryAdditions.effective.historyFallback`. It passes the result to `buildQueryPlan`, which adds the `history_fallback` variant right after the original.
- The fallback is embedded in the same batch, searched on both legs, fused with RRF and traced in `query_plan.variants`.
- It is not an LLM variant (no cap group) but it counts toward `max_searches`. It is protected in the terminology budget and placed after `condensed` in the preference order. At the cap it is cut with `{condense_history, cap}`.
- Voice gets the variant when it sends history.
- Bug fix: `readRagEnvInput` never read `RAG_QUERY_HISTORY_FALLBACK`, so the switch (default true) could not be turned off. This follows the 06.2-17 fix for `RAG_TRANSLATION_GLOSSARY`, and a test failed on the old code.

## Task 3: forced failure end to end (commit d1b37846)
- `transforms.json` gains a top-level `scenarios` section. It is applied only through `applyFakeQueryLlmScenario(table, name)`, which replaces base entries with the same key. Base `entries` and their unique per-query keys are unchanged, so the Python golden test, the LangChain fake and the duplicate-key checks are unaffected.
  - `condense_timeout`: a 1500 ms condense for en-multi-turn-001, zh-multi-turn-001 and it-multi-turn-005.
  - `condense_protected_token_lost`: en-multi-turn-004, whose condensed query drops FW-2.8.14.
- `tests/rag-db/q62-history-fallback.test.mts` runs these items through the eval route with `RAG_PIPELINE=v2`, `RAG_QUERY_LAYER=true` and `stage_timeouts_ms.condense=600` (the chat timeout). 5/5 pass.
  - In each case condense is skipped (timeout or protected_token_lost), `history_fallback` is variant 1, `dense:1` was searched and the gold passage is in kept.
  - With the switch off, only the original is searched. The recorded difference is that the gold passage is still kept for all three items, because the fixture corpus is small. The fallback adds recall headroom here but makes no measurable difference on the fixture.

## Deviations
- **Item choice:** it-multi-turn-001 and 002 do not trigger condense at the gate (R0_TOO_SHORT routes expand, and 002/003 have no rule). The Italian proof uses it-multi-turn-005 (R5_ELLIPTICAL).
- **Length rule:** the D-08 ratio cap is not applied, because the text is the user's own (the same reasoning as A-10 for HyDE). Only `variant_max_chars` applies: the follow-up is kept whole and the previous text is cut by code points, like the history window. If there is no room, there is no variant.
- **Fixture layout:** the fixture scripts live in `scenarios` rather than `entries`, because the fake keys on transform+query and the multi_turn questions already have entries.
- **Unplanned file:** `eval/harness/fake-query-llm.mts` (`applyFakeQueryLlmScenario`) was edited outside files_modified.
- **No migration** was needed.
