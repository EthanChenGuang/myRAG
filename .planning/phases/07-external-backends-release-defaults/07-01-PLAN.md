<objective>
Gate the two vector-store clients behind a human package check, have the orchestrator install them, then verify the exact pins and make the boundary check confine them to the adapter and sync folders (D-09 with A-1).

Purpose: RET-06 and RET-07 rely on one code path per store; a vendor client imported anywhere else could issue a query without the tenant wrapper. The package legitimacy gate flagged @weaviate/node and @weaviate/core [SUS] (too-new), so a blocking human checkpoint comes first.
Output: verified and exactly pinned packages (installed and committed by the orchestrator), a dedicated boundary rule with tests, and a digest-pinned compose file for local backend runs.

Install rule (orchestrator-only): executors never install packages. package.json and package-lock.json are in files_modified because this plan changes them, but only through the orchestrator's install between Task 1 and Task 2; no executor task edits them or runs npm install, npm ci, npm update or any other package-manager command.

Backend half: functionally depends only on Phase 3, 3.1 and 4 plans (04-09 last edited the boundary check; 04-33 last edited package.json in Phase 4; 04-42 closes Phase 4). File-order dependencies: 05-05 and 06-22 (the Phase 5 and Phase 6 package checkpoints and installs) also edit package.json and package-lock.json, and 06-18 edits the boundary check before 06-22: re-read all three files at HEAD before editing. Rollout position: before D-26 step 3 (the adapters need the packages).

This plan is non-autonomous: Task 1 is a package-legitimacy checkpoint that is never auto-approved (workflow.auto_advance is ignored for legitimacy checkpoints).

Commit rule for every task: plain `git commit`; the message ends with the attribution lines (Co-Authored-By and the session link) that the executor's own session supplies; never copy them from a plan. No model identifiers in code comments or commit messages; no secrets.
</objective>
