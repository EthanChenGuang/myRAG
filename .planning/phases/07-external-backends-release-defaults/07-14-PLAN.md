<objective>
Write the cross-tenant canary suite that runs on every backend and gates release (D-12, RET-08), including the planted foreign point that only re-validation can stop.

Purpose: cross-tenant leakage is the worst failure. Each isolation layer has its own unit test (plans 07-03, 07-06, 07-08); this suite proves the layers together through the real write path, sync and production selection, on all three backends. The semantic-cache case is added after Phase 6 in plan 07-28, and the voice and embed entry-point cases (resolveVoiceScope with the RAG_RETRIEVAL_BACKEND_VOICE switch, resolveEmbedScope), each with a filter-ignoring negative control, are plan 07-34; both reuse this plan's factory, seeding and guard.
Output: the canary factory and seed helper, the guard, tenancy, lifecycle and foreign-point tests. The CI job with the services is plan 07-16.

Backend half: depends on 07-07 and 07-08 (adapters and stores), 07-10 (activation gate), 07-11 (reconcile marks tenants ready), 07-12 (factory) and plans 04-41 (two-tenant v2 harness), 03-36 (re-embed), 03-37 (quarantine) and 03.1-39 (soft delete). Rollout position: D-26 step 7.

Baseline note: Phase 3 files (writer, re-embed, quarantine, soft delete) are still changing and the `[HEAD=…]` values here were measured at fc29de8. At plan start, re-run every count gate of this plan against the current tree, record the measured HEAD values in the SUMMARY (not in the plan), and stop and report if a gate already passes before any edit, because it would no longer discriminate.

Running the external legs locally: `docker compose -f docker-compose.backends.yml up -d`, then `RAG_CANARY_BACKENDS=pgvector,weaviate,qdrant QDRANT_URL=http://127.0.0.1:6333 WEAVIATE_URL=http://127.0.0.1:8080` with the compose keys. Without a Docker daemon, record it in the SUMMARY; the backend-canary job (plan 07-16) is then the gate.
