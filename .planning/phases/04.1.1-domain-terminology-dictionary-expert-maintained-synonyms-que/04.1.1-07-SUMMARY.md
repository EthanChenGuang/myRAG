# Phase 4.1.1 Plan 07: Dense terminology variant, cap accounting and glossary helper Summary

**With `RAG_TERMINOLOGY_DENSE=true` (and `RAG_TERMINOLOGY=true`) outside voice, the standalone query with its matched surfaces replaced by their canonicals joins the request's single embed batch as a dense-only variant. Its RRF list weighs `dense_weight` × the dense leg weight in force. The variant and `term:0` count against `MAX_QUERY_VARIANTS` without the query layer, and against `max_searches`/`max_llm_variants` with it. Phase 6 code can read the matched entries early through `terminologyGlossary`. With both switches off, behaviour is unchanged.**

## Phase 6 branch (D-40)

Phase 6's variant cap (plan 06-20) is on trunk: `buildQueryVariantSet` takes `VariantLimits` (`cap`, `order`, `groupLimits`) and returns `cuts`, and `QueryVariant.legs` exists. Both D-31 rules are implemented:
- **Without the layer (or `RAG_QUERY_LAYER` off for the request):** the variant is appended after the translations while fewer than `MAX_QUERY_VARIANTS` exist. `term:0` is one further lexical call and not a variant (`search_cut` always 0).
- **With the layer:** the preference order is `original, condensed, translated, sub_question, terminology, expanded, hyde`, and the variant is in the `generated` (`max_llm_variants`) group. `terminologyBudget` takes the protected count, `max_searches` and `max_llm_variants` from `effectiveQueryParams` at run time. When `term:0` runs it caps the variants at `max_searches − 1`. When the protected variants alone fill `max_searches`, it does not search `term:0` and keeps the full cap. An expanded text equal to the terminology text is dropped as a duplicate.

The variant uses `legs: 'dense'`. `variantSearchRequest` also treats kind `terminology` as dense-only.

## Accomplishments

- `substituteCanonicals` replaces matches left to right over normalized text. When several entries share one span, the first one wins.
- `terminologyBudget` is pure, takes every limit as an argument and covers D-31 items 1 to 4.
- `runQueryStages` builds the variant, applies the budget with the layer, and builds the final set. It then writes `search_cut` and `variant_cut` onto the terminology stage record, adding ` cut=cap` to the detail when either is 1. `QueryStagesOutput.terminology` stays present whenever the stage ended ok, whatever the dense switch (D-20).
- `listsFromLegs` takes a `denseFactor`. The native fuse and the retrieval port both apply `dense_weight` to a terminology variant's dense list. The original `dense:0`, `lexical:0` and `term:0` lists are unchanged.
- `terminologyGlossary` goes through `terminologyMatcherFor`, the same cache as the stage, keyed by `scopeKey(scope)`. It races the load against the timeout and aborts the load when the timeout wins. It never throws and logs nothing.
