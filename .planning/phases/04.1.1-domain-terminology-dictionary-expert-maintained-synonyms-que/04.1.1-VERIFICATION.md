**Phase Goal:** When users ask in their own words (informal terms, abbreviations, loosely typed codes and identifiers) in any enabled language, retrieval still finds the chunks that use the documents' own terms, through a dictionary that domain experts maintain per deployment and per tenant, that is versioned and audited, that never lets expansion outweigh the original query, that grows from reviewed candidates mined from missed queries, and that later phases read through one stable, tenant-scoped interface (tokenizer dictionary, translation glossary).

## 503 analysis (Config UI Terminology panel on the eval project)

**Verdict: an environment problem (a missing migration) together with a cross-phase deployment-ordering dependency. It is not a 4.1.1 code defect.** The chain is confirmed from the code:

1. The panel loads its entries with `GET /api/rag/admin/terminology` (`src/app/api/rag/admin/terminology/route.ts`). That route calls `listTerminologyEntries` (`listEntries as listTerminologyEntries`, `src/lib/rag/index.ts:142`), and the panel's other views wait on this load.
2. `listEntries` in `src/lib/rag/terminology/admin.ts` always calls `rag_term_list_entries` with eight named arguments: `listArgs(...)` (`p_actor`, `p_layer_key`, `p_limit`, `p_offset`, `p_search`) plus `p_kind`, `p_source_language` and `p_target_language`. The three filters are sent even when they are `null`.
3. PostgREST picks a function by the set of argument names. A DB without 0980 has only the 5-argument function from 0472, so the call fails with "function not found" (PGRST202).
4. `callTerminologyRpc` → `failureOf`: the message is not one of the `SQL_REASONS` words, so it maps to `UNAVAILABLE`. The app logs `[RAG Admin] terminology call failed { rpc: 'rag_term_list_entries', code }` with code PGRST202 in the logs. `_lib.ts` `failure()` then answers `default → fail(503, 'Terminology is unavailable')`.
5. Origin: the 8-argument call came in with **Phase 6.2** commit `bc6890c0` ("feat(06.2-04): glossary target codes, translation write defaults and list filters"). Its diff replaces the 4.1.1 line `callTerminologyRpc('rag_term_list_entries', listArgs(input.actorUserId, input.layerKey, limit, offset, search), ...)`. Migration `0980_term_translation_target.sql` (commit `4031c6a4`, Phase 6.2) drops the 5-argument signature and creates the 8-argument one with `DEFAULT NULL` filters. 0980 is not folded into the setup files and is not mentioned in AGENTS.md. The eval DB is migrated only to train 34, and 0980 arrived later (train 37), so the list route answers 503 there.
6. 4.1.1's own code path had no defect: the 4.1.1 version sent the 5 arguments that match 0472. The PGlite fixture applies every migration, 0980 included, so `terminology-admin-two-tenant` passes and could not have caught this.

Other paths: `loadLayer` (validator, import, export) and the `listArgs(..., 1, 0, null)` existence check still send 5 arguments. Those work on both schemas, because 0980's extra parameters have defaults. So only the list view, which is the panel's entry view, is broken.

**Cross-phase deployment-ordering risk:**
- 4.1.1 admin code on main now **requires 0980** (Phase 6.2). Any environment that deploys main's app without 0980 loses the Terminology panel's list view, even with every Phase 6.2 switch off.
- The 0980 header also warns about the reverse case. Re-running 0472 or a setup file brings back the 5-argument overload next to the 8-argument one. The 5-argument named calls (`loadLayer`) would then match two candidates and could fail with PGRST203, giving 503 on import, export and validation, until 0980 is re-run. AGENTS.md says nothing about this for 0980.
