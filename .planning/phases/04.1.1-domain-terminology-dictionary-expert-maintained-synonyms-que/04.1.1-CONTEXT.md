## Phase Boundary

Users ask in their own words: a short or informal form, an abbreviation, a loosely typed identifier. The knowledge base uses the documents' own terms. Phase 4 made the lexical leg strong on exact terms, which makes it weak exactly when the user does not use them. This phase adds a terminology dictionary that domain experts maintain, and uses it at query time.

Every example in this phase is a synthetic placeholder with no real-world meaning (D-37): a user writes `术语甲`, `termalpha`, `voce alfa` or `ab 1234 c`; the documents say `术语甲乙丙`, `term alpha beta`, `termine alfa beta` or `AB-1234-C`.

It delivers:
- a tenant-scoped dictionary in Postgres with a deployment-wide **shared** layer and a per-tenant **workspace** layer that can add entries and suppress shared ones; every change bumps a layer version and writes an append-only audit row;
- an admin API (Zod, `checkAdmin` + `resolveAdminWorkspaceScope`) for list, create, update, delete, suppress, versions, audit, expansion preview, CSV import (dry run, then atomic apply) and CSV export;
- validation that rejects conflicts, chains, cycles, one-character Han variants, stopword-only and empty variants, languages that are not enabled and malformed translation pairs before anything is written;
- a `terminology` stage in the v2 query group that matches dictionary entries in the standalone query and feeds a **separate, down-weighted lexical RRF list** (the original lexical list is unchanged), with hard caps and a small reservation so expansion-only hits reach the reranker whatever the pool and cap are; optionally (own switch) a dense variant with canonical terms substituted;
- the matched entries exposed for Phase 6 rewriting and HyDE (stage output and an earlier glossary helper);
- translation pairs (XLG-05) stored in the same dictionary, and a stable, tenant-scoped read API (`getTerminologyLexicon`) for the Phase 4.2 tokenizer dictionary (LANG-07) and the Phase 6.2 translation glossary;
- an opt-in, masked, tenant-scoped log of missed queries (empty, refused, low-confidence) and a miner CLI that proposes candidate terms for expert review; nothing is ever applied automatically;
- synthetic colloquial golden items in every fixture language with a fixture dictionary, an on/off comparison, and a Config UI panel (after a UI-SPEC).

In scope: TERM-01 to TERM-11 (see REQUIREMENTS-ADDITIONS.md), plus the storage and read side of XLG-05 and the dictionary side of LANG-07 (their use belongs to Phases 6.2 and 4.2).

Out of scope:
- Index-time synonyms (Postgres thesaurus dictionaries or canonical terms written into `lexical_text`): researched and rejected for now (D-14); revisit only if eval shows a gap query-time expansion cannot close.
- The legacy pipeline: untouched. The dictionary acts only when the effective pipeline is v2 (D-36).
- LLM query rewriting, HyDE, multi-query: Phase 6. This phase only hands Phase 6 the matched entries (D-20, QRY-01/QRY-03 amendment).
- Translating anything, enforcing a glossary term in a translation, and using the dictionary inside the tokenizer or a relex: Phases 6.2 and 4.2. This phase stores the pairs and exposes the read (D-32, D-33).
- Thumbs-down and feedback as a mining source, and real (production) golden items: Phase 5.1.1, which writes into the same candidate table (D-25).
- Feeding identifier aliases into the exact-id list or the identifier index: Phase 4.2 (RET-15, RET-16); identifier aliases go through the lexical expansion list here (D-12).
- Choosing the shipped default: stays off (D-30); Phase 7 / ADM-02 decides with real items.

<decisions>
## Implementation Decisions

### Storage, layers and tenancy
- **D-01:** Four tables in one migration (0471): `rag_term_layers` (one row per layer: `layer_key` primary key, `version bigint`, `entries_sha256`, `updated_at`, `updated_by`), `rag_term_entries`, `rag_term_audit` (append-only), and later (0473) `rag_term_misses` and `rag_term_candidates`. RLS is enabled with no policies, everything is revoked from `PUBLIC, anon, authenticated`, and only `service_role` gets table privileges (the `rag_admin_audit` pattern of the quarantine-admin migration). No browser path reads or writes these tables.
- **D-02 (Amended 2026-11-25: reference by symbol):** `layer_key` is `'shared'` (deployment-wide) or a tenant key (`s:default`, `u:<uuid>`, `o:<uuid>`), checked by a CHECK constraint that mirrors the constant `TENANT_KEY_RE` in `src/lib/rag/ingest/writer.ts` (re-read at execution time). The effective dictionary for tenant T = shared entries minus those T suppresses, plus T's own entries; on a conflict between a workspace entry and a shared entry for the same normalized variant and language, the workspace entry wins and the preview reports the override.
- **D-03:** Single-tenant deployments use only the shared layer. The API refuses `layer: "workspace"` in single-tenant mode (400 `workspace_layer_unavailable`), and the UI hides the layer switch. Multi-tenant: shared-layer writes require `admin_users` membership (every Config UI admin already has it); workspace writes require the layer key to be in `rag_admin_tenant_keys(p_actor)`, so an admin can only edit tenants they administer. Another tenant's entry id answers `not_found`, never `forbidden` (no probing, as in the quarantine-admin functions).
- **D-04 (Amended 2026-11-25: translation pairs and language rules; see D-32, D-35):** Entry shape: `id uuid`, `layer_key`, `canonical text` (1..64 chars), `variants text[]` (1..16, each 1..64 chars), `language`, `kind` (`synonym|abbreviation|alias|identifier|translation|misspelling`; the last two match Phase 5.1.1's `DictionaryCandidate.relation`), `source_language` and `target_language` (both null unless `kind = translation`), `mode` (`one_way|equivalent`, default `one_way`), `enabled boolean`, `note text` (≤ 500), `suppresses_entry_id uuid` (workspace rows only; a suppression row has no variants), `created_by/updated_by uuid`, timestamps, and `normalized_variants text[]` written by the writer RPC from the app-side normalizer (stored, not computed in SQL, so SQL and TS can never disagree on folding). Limits: 20,000 entries per layer.
  - **Language rules.** `language` is a code of the LANG-02 language registry that is enabled in the deployment (`RAG_SUPPORTED_LANGUAGES`), or the literal `any`. It names the language the variants are written in (and the canonical, for every kind except `translation`). `any` is for entries not tied to a language (identifiers, codes, names): it applies in every language and collides with every language in validation (D-24). `language` scopes uniqueness, validation, the import diff key and the language filter of the read API (D-33). Matching goes by script and normalization (D-10 to D-12), not by the detected query language; that is unchanged.
  - **Translation pairs (XLG-05).** `kind = translation` requires `source_language` and `target_language`: both enabled registry codes, never `any`, different from each other. `language` must equal `source_language`. `variants` are the source-language terms and `canonical` is the required target-language term. `mode` must be `one_way`. For every other kind both fields must be null.
  - **Uniqueness.** One entry per `(layer_key, language, target_language or '', lower(canonical))` among non-suppression rows; one suppression per `(layer_key, suppresses_entry_id)`.
  - SQL checks the shape of a language value and the translation-pair rules; whether a code is in the registry and enabled is checked in the app before the writer is called (D-35).
- **D-05:** Versioning: every write RPC increments `rag_term_layers.version` by exactly one in the same transaction (an import counts as one), recomputes `entries_sha256` over the canonical JSON of the layer's entries, and writes one audit row per changed entry carrying `layer_version`. Writes take an `p_expected_version` and fail with `version_conflict` (409) when it is stale: two experts cannot silently overwrite each other.
- **D-06:** Audit: `rag_term_audit(id, layer_key, entry_id, action, actor, before jsonb, after jsonb, layer_version, created_at)`, actions `create|update|delete|import|suppress|unsuppress|candidate_accept|candidate_dismiss`. Append-only via BEFORE UPDATE/DELETE/TRUNCATE triggers. No entry id is a foreign key, so audit outlives deleted entries. Point-in-time export of an old version is deferred (the audit holds enough to rebuild it; nothing reads it that way yet).
- **D-07:** Every new SQL function is `SECURITY DEFINER`, `SET search_path = ''`, schema-qualifies every name, `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE ... TO service_role`, and is added to the lock-down block when the migrations are folded into both setup files (plan 14). `tests/rag/search-rpc-grants.test.ts` and `tests/rag/security-definer-search-path.test.ts` stay green.
- **D-08 (Amended 2026-11-25: re-checked):** Migration numbers 0471 (schema + read RPC), 0472 (writers, import, suppression, audit read), 0473 (miss log, candidates, decisions). Re-checked on the tree of this revision: `supabase/migrations/` holds no `047*` file, and the sibling phases already name 0471 to 0473 as this phase's numbers (Phase 3.2 D-48, Phase 6.1). The three files create only `rag_term_*` objects and call functions defined in lower-numbered files (`rag_assert_tenant_key`, `rag_admin_tenant_keys`, the lexical tsquery builder), so it does not matter that 05xx to 08xx files exist on trunk when they are applied. The executor of plan 03 still re-checks `ls supabase/migrations` on trunk, `git ls-tree` on open branches and the sibling phase directories, and renumbers if any is taken: the three files and every file in this phase directory found by `grep -l 047`.

### Normalization and matching
- **D-09 (Amended 2026-11-25: reference by symbol):** One normalizer for dictionary writes and queries: the Phase 4 tokenizer normalization (the module-private function `normalize` in `src/lib/rag/lexical/tokenize.ts`: `NFKC`, lower case, apostrophe mapping, accent folding), exported as `normalizeLexical()` without changing `LEXICAL_VERSION`. Matching never re-implements folding. If Phase 4.2 (LANG-07) has moved folding into the language registry by execution time, `normalizeLexical()` is whatever that tokenizer's normalization is then; the rule "one normalizer, the tokenizer's" stays.
- **D-10 (Amended 2026-11-25: neutral wording):** Han matching is substring on the normalized query with longest-match-first, left-to-right, non-overlapping selection (a character trie, rebuilt only when the cached dictionary changes). Han variants must have at least 2 Han characters, because a one-character Han variant would match inside unrelated words. Segmentation (`Intl.Segmenter`) is not used for matching: short and informal Han forms are segmented unreliably, and the bigrams the index uses make substring matching the consistent choice.
- **D-11 (Amended 2026-11-25: neutral wording):** Latin-script matching is on token boundaries over the normalized text, supports multi-word variants (`alpha beta`, `voce alfa`), and respects elisions the same way the tokenizer does (an elided article before a vowel). A variant that is entirely stopwords, or that yields no lexical tokens, is rejected at write time.
- **D-12 (Amended 2026-11-25: neutral wording, 04-29 status):** `kind: identifier` entries match through `identifierLexicalLookupForms()` in `tokenize.ts`, so `AB 1234 C`, `ab-1234-c` and `ab1234c` all match an entry for `AB-1234-C`; their expansions are emitted as identifier forms. Plan 04-29's exact-id list is on trunk (the `exact_id` list in `runSearchStages`); feeding identifier aliases into it, or into the Phase 4.2 identifier index (RET-15, RET-16), stays out of this phase.
- **D-13 (Amended 2026-11-25: translation pairs excluded):** Expansion is never transitive (one hop only). `one_way`: a variant in the query adds the canonical. `equivalent`: any member adds the canonical and the other members. Expansion terms are tokenized with `queryLexicalTokens()` and deduplicated against the original query's tokens. Entries of `kind = translation` never expand a query: the matcher is built without them (D-32).

### Index time
- **D-14:** No index-time synonyms. (a) Postgres `CREATE TEXT SEARCH DICTIONARY ... TEMPLATE = synonym|thesaurus` reads files from `$SHAREDIR/tsearch_data`, which hosted Supabase does not let us write; (b) the Phase 4 lexical index bypasses the text-search parser and dictionaries entirely (`rag_lexical_tsvector` builds the tsvector verbatim from the app tokenizer), so a Postgres dictionary would not apply anyway; (c) writing canonical terms into `lexical_text` would make every dictionary edit a relex of every chunk containing any changed variant (the `rag:relex` job, `src/lib/rag/ingest/relex/run.ts`), coupling an expert's edit to a corpus-wide rewrite and to the lexical version. Query-time expansion of the whole equivalence class gives the same lexical recall without a relex, which is also Elasticsearch's recommendation (search-time synonyms, updateable without reindexing). RESEARCH.md records the relex cost estimate for a future decision. This is separate from LANG-07 (Phase 4.2), which uses dictionary terms as tokenizer vocabulary so a multi-character term stays one token; it writes no synonym into the index and reads the dictionary through D-33.

### Query-time use
- **D-15 (Amended 2026-11-25: position against Phase 6 D-05, input, stage names):** New optional stage `terminology`, `onFail: 'skip'`. Its name is added to `OPTIONAL_STAGES` in `src/lib/rag/config.ts` and to the Pydantic `StageName` and `StageTimeoutsMs` in `rag-sidecar/src/rag_sidecar/contracts/eval_run.py` (so the eval route can disable it or set its timeout), with generated Zod.
  - **Position with Phase 6's query layer on trunk:** `query_gate` → `condense` → (`normalize_dates`, `translate`, `expand`, `hyde`, `decompose` in parallel on the standalone query) → **`terminology`** → `semantic_cache` (chat, embed) → `embed` → the Phase 4 v2 graph. It starts when the parallel group has joined or hit its group deadline, and ends before `semantic_cache` and `embed` start.
  - **Position without it:** `refs` → `analyze` → `translate` → **`terminology`** → `embed`. This is the same relative place: after the last query transform, before embedding.
  - **Input:** the standalone query only. That is Phase 6's `condense` output when present, otherwise the request's query. Translated variants, LLM variants (expanded, HyDE, sub-questions) and caller-supplied variants are never matched. Reasons: (1) one hop: a variant that already holds a canonical term or a paraphrase would be expanded a second time; (2) no compounding with model output: a term an LLM invented must not pull dictionary terms into retrieval; (3) the cost is constant: at most one `term:0` list and one dense variant per request whatever the number of variants, so the caps of D-17 and D-31 stay predictable; (4) the rerank and refusal query is the standalone query (Phase 6 D-06), so expansion stays anchored to the same text.
  - **Why after the join:** the variant list is final then, which the accounting of D-31 needs, and the effective dictionary version is known before the semantic-cache key is built (D-21). It is not part of Phase 6's parallel group, so that group's deadline never aborts it and its own failure never touches a transform.
  - When `RAG_TERMINOLOGY=false` the stage is added to the disabled stages exactly as `translate` is (in `applyV2DisabledStages`) and the request is otherwise unchanged. A load failure or timeout records `skipped`, so the request continues without expansion and the retrieval status is `degraded` by the existing rule (`deriveStatus` in `src/lib/rag/pipeline.ts`); strict mode never answers "information not available" because of a dictionary failure.
- **D-16 (Amended 2026-11-25: weight and limit read at run time, D-34):** Expansion goes into its own RRF list `term:0` (an id with no `dense`/`lexical` prefix, so nothing that inspects list ids by prefix miscounts it), searched with one lexical-only backend call (`denseLimit: 0`, supported by `hybrid_search_chunks`) in parallel with the existing legs. Its lexical limit is the request's effective `candidate_pool_size`, read at run time. The original `lexical:0` list is byte-for-byte what it is today. Its RRF weight is `TerminologyParams.expansion_weight` (default 0.5) multiplied by the lexical leg weight in force for the request (`leg_weights.lexical` of the effective retrieval params), so the list stays at half the lexical leg whatever a sweep later writes there; a chunk found only through expansion can never outrank one found by an original leg at the same rank. Expansion is a no-op when `RAG_LEXICAL_SEARCH` is off (it then only produces the optional dense variant and the Phase 6 hint).
- **D-17 (Amended 2026-11-25: reserve_slots):** Caps (all in the Pydantic `TerminologyParams`, defaults): `max_matches` 8, `max_terms_per_match` 4, `max_expansion_tokens` 24, `expansion_weight` 0.5, `dense_weight` 0.5 (le 0.5; factor on the dense leg weight for the optional terminology dense variant), `min_han_chars` 2, `reserve_slots` 2 (ge 0, le 4; D-34). When a cap is hit the stage records `capped=true` in its detail. Defaults are tuned later with the retrieval sweep tool, never by hand.
- **D-18 (Amended 2026-11-25: Phase 6 accounting in D-31):** `RAG_TERMINOLOGY_DENSE=false` (own switch): when on, one extra query variant of kind `terminology` (the standalone query with canonical terms substituted for matched variants) joins the request's single `embedBatch` call and is searched dense-only; its list weight is `dense_weight` multiplied by the dense leg weight in force (≤ half of it), so it can never outweigh the original legs. How it counts against the variant and search caps is D-31. Never in voice. The terminology variant is not a query-plan output: it is never written into Phase 6's `QueryPlan.variants`; the trace shows it through the `terminology` stage and its `dense:<i>` list.
- **D-19:** Voice: the lexical expansion runs in voice (it is in-process plus one parallel lexical query); the dense variant never does. Stage budgets: `terminology` 5 ms chat/embed, 3 ms voice in `eval/config/latency-budgets.json`; the search stage budget is not raised, and the eval reports whether search p95 moved.
- **D-20 (Amended 2026-11-25: an earlier entry for prompts):** The query-stage output gains `terminology: { matches: TerminologyMatch[], version: string } | null`: what was applied to retrieval. `RunRetrievalInput` gains nothing. Because the stage now runs after Phase 6's transforms (D-15), the same request's rewrite and HyDE prompts cannot read that output, so this phase also exports `terminologyGlossary(scope, text, options)` from `src/lib/rag/terminology/glossary.ts`: it matches any text against the tenant's cached matcher and returns `{ matches, version }`, or null when the switch is off, the load fails or it times out. It never throws, records no stage and changes nothing in retrieval. Phase 6's prompt builders call it with the text they are about to send (QRY-01 and QRY-03 as amended); wiring it into those prompts is Phase 6 or Phase 6.2 work.
- **D-21 (Amended 2026-11-25: always present when on, semantic-cache key):** Trace and hash: the stage detail carries counts and the effective version only (`matches=2 tokens=7 capped=false version=s12.w3`), never the query, the variants or the canonicals. `computeRetrievalConfigHash` gains an optional `terminology` block (`{ version, params_sha256, dense }`). With the switch off the block is absent, so the hash is identical to today's. With the switch on it is always present: `version` is the effective version when the stage ended `ok`, and the literal `terminology:unavailable` when it was skipped (the `chunking:unavailable` precedent in `config-hash.ts`). One builder, `terminologyHashBlock()`, produces it and every caller of `computeRetrievalConfigHash` passes it: `buildV2Result`, and the code that computes the `retrievalConfigHash` part of Phase 6's semantic-cache key when that is on trunk. Because the stage runs before `semantic_cache`, an entry stored under one dictionary version is not found after an edit. A request whose stage was skipped looks up under `terminology:unavailable`, where nothing is ever stored (a `degraded` request is never stored), so it misses and retrieves.
- **D-22 (Amended 2026-11-25: loader shared with D-33):** Dictionary loading: `rag_term_effective(p_tenant_key)` returns the effective entries (translation pairs included) and both layer versions; the app caches the loaded dictionary and the built matcher per tenant key in-process (LRU of 256 tenants, 60 s TTL). An edit therefore reaches retrieval within 60 s; the preview endpoint always bypasses the cache. The cache key includes the tenant key, so two tenants never share a matcher. `load.ts` is the only module that calls `rag_term_effective`; the stage, the glossary helper, the preview and the read API of D-33 all go through it.

### Maintenance
- **D-23 (Amended 2026-11-25: two columns for translation pairs):** CSV columns: `canonical,variants,language,kind,mode,enabled,note,source_language,target_language` with `variants` separated by `|`; the last two are empty unless `kind` is `translation`. UTF-8 with or without BOM, RFC 4180 quoting, ≤ 1 MB and ≤ 5,000 rows per file. A small in-repo parser (no new dependency). Import is two calls: `dry_run` returns per-row errors (conflict, chain, cycle, limit, language, translation) and the diff (`create`, `update`, `unchanged`, `delete` for `replace` mode), keyed by `(language, target_language, lower(canonical))`; `apply` re-validates and writes atomically through `rag_term_apply_import` with the version the dry run saw. Export neutralises spreadsheet formulas (a cell starting with `= + - @` or tab/CR is prefixed with `'`); import strips exactly one leading `'` only when the next character is one of `= + - @ \t \r`, so the round trip is lossless.
- **D-24 (Amended 2026-11-25: language and translation rules):** Validation (pure TS in `src/lib/rag/terminology/validate.ts`, used by the write routes and the import): (1) a normalized variant maps to two canonicals in one layer and language → `conflict`; (2) an entry's canonical is a variant of another entry in the same layer and language, or vice versa → `chain` (with one-hop expansion a chain is ambiguous, so it is rejected with a "merge these entries" hint); (3) any closed loop through canonical/variant edges → `cycle`; (4) variant equals canonical → dropped with a warning; (5) Han variant shorter than `min_han_chars`, stopword-only or tokenless variant → `invalid_variant`; (6) overlapping `equivalent` sets → `conflict`; (7) `language`, `source_language` or `target_language` not an enabled registry code (or `language` neither that nor `any`) → `invalid_language`; (8) a translation pair that breaks D-04 (missing or equal languages, `any`, `language` different from `source_language`, mode not `one_way`, or the two fields set on another kind) → `invalid_translation`; (9) one normalized source term with two different required targets for the same `(source_language, target_language)` in one layer → `conflict`. Translation pairs take no part in rules 1 to 3 and 6, because they never expand a query: a term may be a same-language canonical and a translation source at once. Cross-layer collisions are not errors; they are reported as `overrides` in the preview and import report.
- **D-25:** Log mining: when `RAG_TERMINOLOGY_MINING=true`, the v2 finish path records a missed request (status `empty`, refusal decision `refuse`, or `degraded` with no candidates) for profiles `chat`, `embed` and `voice` (never `eval`) into `rag_term_misses`: tenant key, `maskPII` query cut to 500 characters, language, status, reason, top fused score, effective dictionary version, `retrievalConfigHash`, profile, time. Fire-and-forget with a 500 ms timeout; it never delays or fails the request. Retention holds without any schedule: `rag_term_record_miss` deletes the tenant's rows older than 30 days on each insert, reads ignore older rows, and the miner also purges. A `source` column (`miss_log` here; `feedback` and `langfuse` reserved) lets Phase 5.1.1 add thumbs-down and online-judge failures without a schema change.
- **D-25a (coordination with Phase 5.1.1; amended 2026-11-25 for translation rows):** Phase 5.1.1 adds `public.rag_retrieval_log` (every retrieval, privacy-minimised, retention, per-tenant opt-out) and an expert labelling flow that exports `DictionaryCandidate {tenant_key, language, observed_term, canonical_term, relation, example_review_item_ids, occurrences}` JSONL for this phase. Because 4.1.1 ships first, `rag_term_misses` is the minimal interim source. Once `rag_retrieval_log` exists, 5.1.1 (or a follow-up) points the miner's source reader at it (rows with status empty/refused) and turns `RAG_TERMINOLOGY_MINING` recording off; the miner's source is one function (`readMisses`) so this is a one-file change. The 5.1.1 `DictionaryCandidate` file is imported through this phase's import service (an adapter maps `observed_term → variants[0]`, `canonical_term → canonical`, `relation → kind`), never by writing the tables directly. A row with `relation: translation` becomes a translation pair: its `language` is the source language and the target language is read from the row's `canonical_language`; a row without it gets `invalid_translation` in the dry run and is never guessed (the field is proposed to Phase 5.1.1 in the plan index). The REQUIREMENTS-ADDITIONS amendment records this.
- **D-26:** Miner: `npm run rag:terms:mine` (CLI under `src/lib/rag/terminology/mine/`, run by the operator's scheduler; nightly recommended). Per tenant over a window (default 14 days): tokenize missed queries with `queryLexicalTokens` plus Han 2–4-grams; keep terms with support ≥ 3 distinct masked queries; drop stopwords, mask placeholders, digits-only terms and terms already in the effective dictionary; compute corpus document frequency in that tenant only (`rag_term_corpus_df`, service role, on `lexical_tsv`); keep df == 0 or df ≤ 2 as candidates with up to 3 example masked queries. Upsert into `rag_term_candidates` (status `pending`); a `dismissed` candidate is not resurfaced. Accepting a candidate opens the normal create form; the entry is written through the normal path with audit, and the candidate is marked `accepted` with the entry id.

### Evaluation and completion
- **D-27 (Amended 2026-11-25: synthetic content, D-37):** Fixture dictionary `eval/fixtures/terminology/dictionary.jsonl` (one TerminologyImportRow per line, so the harness does not depend on the CSV parser; plan 11 tests its CSV round trip) (shared layer, synthetic placeholder terms only), seeded by the eval harness into every fixture database regardless of the switch, so "switch off" is proven on a database that holds a dictionary. Its canonicals occur only in one new synthetic document per fixture language (`eval/fixtures/corpus/<lang>/synthetic-terms.<lang>.md`), written from placeholder terms and identifier-style codes; no entry maps to or from a term of the other fixture documents.
- **D-28 (Amended 2026-11-25: structure only, fixture languages):** New golden items, category `colloquial` (EVAL-14), ids `<lang>-colloquial-term-NNN` (answerable and identifier-alias items) and `<lang>-no_answer-term-NNN` (no-answer controls), for every fixture language (the harness's corpus language list, read at execution time; `zh,en,it` in CI): 4 answerable per language whose variant shares no lexical token with any corpus text while the canonical occurs in the gold span of the synthetic document (asserted by a test), 1 identifier alias per language, and 1 `no_answer` per language whose question contains a dictionary variant (expansion must not create a false answer). Questions, entries and gold quotes consist of placeholder terms. Provenance `synthetic_fixture`. The baseline is re-recorded with zero paired difference on every pre-existing item (05.1-17 procedure); if the new documents move a pre-existing item, the executor stops and reports and edits no item or threshold.
- **D-29 (Amended 2026-11-25: what the fixture can and cannot show):** Comparison: run configs `v2-terminology-off` / `v2-terminology-on` (both on top of the Phase 4.1 default run config `eval/config/runs/v2-default.json`, plus a lexical-only pair with refusal off to sidestep the similarity-floor artefact on the fixture embedder). Done means: Recall@k and MRR on the `colloquial-term` slice improve; no other slice, language or category drops beyond the noise band (`eval/config/noise.json`); the `no_answer` term items are still refused at the same rate; latency within budgets. Every bound is read from the files in force when the comparison runs; no plan quotes a baseline number or an item count. The fixture corpus is smaller than the candidate pool, so this comparison shows the boost, not reach beyond the pool; reach is proven by the plan 18 test with full lists (D-34).

### Added 2026-11-25
- **D-31 (variant and search accounting with Phase 6 D-08):** The stage adds at most two backend calls to a request whatever the number of other variants: the `term:0` lexical-only call and, with `RAG_TERMINOLOGY_DENSE` on, one dense-only variant (D-15 explains why only the standalone query is matched).
  - **Without Phase 6's query layer** (not on trunk, or `RAG_QUERY_LAYER=false`): the Phase 4 rule stays. The terminology variant is appended after translated variants only while fewer than `MAX_QUERY_VARIANTS` variants exist, so it never displaces the original or a translation. `term:0` is one further lexical-only call and is not a variant.
  - **With Phase 6's query layer on:** the hard cap is `QueryParams.max_searches` (Phase 6 D-08; read at run time from `eval/config/query-params.json`, never a literal in this phase), and both terminology calls count toward it. (1) `term:0` reserves one search when the stage produced expansion tokens and lexical search is on: the variant builder is called with a cap of `max_searches − 1`. (2) The terminology variant belongs to the multi-query group (QRY-02 as amended): it stands first in that group, before `expanded` and `hyde`, and counts toward the limit Phase 6 applies to that group (`max_llm_variants`), so with it present one fewer LLM paraphrase is searched. The preference order becomes `original, condensed, translated, sub_question, terminology, expanded, hyde`. (3) A cut is recorded the way Phase 6 records cuts (reason `cap`). (4) A multi-query output whose text equals the terminology variant is dropped as a duplicate; the terminology variant is kept.
  - **Why:** the expert's substitution and an LLM paraphrase solve the same problem (the user's words differ from the documents'), so they share one budget; the deterministic one goes first because it costs no model call and cannot invent a term. The original, the standalone query, translations and sub-questions are never displaced, because answers depend on them (Phase 6 D-06, D-07). Counting `term:0` keeps Phase 6's search cap a true upper bound on database calls per request.
  - Voice: no terminology variant (D-19); `term:0` counts as in (1).
- **D-32 (translation pairs are stored and read here, used elsewhere):** Entries of `kind = translation` (D-04) are validated, versioned, audited, imported, exported and returned by `rag_term_effective`, the admin list and the read API (D-33) like every entry. The `terminology` stage never uses them: same-language expansion ignores them, the matcher is built without them, and the preview lists none as a match. They exist for XLG-05: Phase 6.2's query translation and rewriting, and Phase 3.2's document-translation seam `glossaryFor(scope, source, target)`, read them through D-33 and enforce the required target term. Nothing in this phase translates. A cross-language pair that should expand queries now (the user writes a term in one language, the documents use another) is entered as `alias` or `synonym` with `language: any`; this phase's expansion uses that.
- **D-33 (stable read API for LANG-07 and XLG-05):** `getTerminologyLexicon(scope: TenantScope, opts?: { languages?, kinds?, includeTranslations? }): Promise<TerminologyLexicon>`, exported from `@/lib/rag`. `TerminologyLexicon` is a Pydantic contract with generated Zod: `{ version, entries_sha256, terms: [{ normalized, language, kind }], translations: [{ entry_id, source_language, target_language, sources, target, target_normalized }] }`.
  - **Tenant scope.** The only tenant input is a `TenantScope` (minted by the `resolve*Scope` functions); its key goes to `rag_term_effective` through the loader of D-22, on the service-role client. The result is the effective dictionary: shared entries minus the tenant's suppressions plus the tenant's own entries, workspace winning on a collision. Disabled entries are left out. No caller passes a tenant key string.
  - **Content.** `terms` holds every distinct `(normalized, language, kind)` among the canonicals and variants of the effective entries, sorted. Translation pairs appear only with `includeTranslations: true`: their source terms as `terms` in the source language, their target as a `term` in the target language, and each pair once in `translations` (for the glossary). `languages` keeps terms of those languages and `any`; `kinds` keeps those kinds. `version` is the effective version string (`s<n>.w<n>`, the one the trace and config hash record). `entries_sha256` is a sha256 over the canonical JSON of the returned `terms` and `translations`, so a caller can tell whether an edit changed what it consumes.
  - **Caching.** Per tenant key and version, on top of the loader's cache (60 s TTL); a new process starts with an empty cache, so a CLI reads fresh. The projection for one set of options is memoized per tenant and version.
  - **Independence.** It does not read `RAG_TERMINOLOGY` or any other switch: it returns what the tables hold, and the caller's own switch decides whether to use it. It rejects with the exported `TerminologyUnavailableError` when the load fails; it never returns a partial dictionary or another tenant's.
  - **Stability.** The function name, the options and the contract are an interface for Phase 4.2 (LANG-07: the tokenizer's custom dictionary; `version` and `entries_sha256` tell it when to bump `LEXICAL_VERSION` and relex) and Phase 6.2 (XLG-05: `translations` and `version` feed the glossary seam and its `glossary_version`). A contract test locks the shape; changing it means changing the Pydantic model, regenerating Zod and updating that test in one commit. `scripts/ci/check-rag-boundary.mjs` gains a rule: a `rag_term_*` RPC call outside `src/lib/rag/terminology/` fails.
- **D-34 (no assumed pool or cap; reach beyond the pool):** Phase 4's starting values for the candidate pool and the rerank input cap are no longer fixed points: Phase 4.2 lowers the cap's floor to 25 and the sweep grid includes a pool of 25 (LAT-01 and RNK-02 deltas). This phase therefore assumes neither.
  - Every limit and weight is read from the request's effective retrieval params at run time (`effectiveRetrievalParams`): the `term:0` lexical limit is `candidate_pool_size`; fusion, dedupe and the cap are the existing ones; the two terminology weights are factors on the leg weights in force (D-16, D-18). No terminology code, test or plan contains a pool size or a cap as a literal expectation; tests that need a value pass it explicitly as an override and assert against what they passed.
  - RRF arithmetic makes a chunk found only by `term:0` score below every chunk an original list ranks in its first `rrf_k` positions or so, so with full original lists it falls outside the rerank input at any cap, and expansion would only re-order chunks the original legs already found. To make the phase goal independent of pool and cap, at most `TerminologyParams.reserve_slots` (default 2) of the best-ranked `term:0` hits that fell outside the rerank input replace its lowest-ranked entries, after fusion and dedupe. They keep their fused score and their position at the end of the list, so without a reranker they never reach the context ahead of an original hit; with a reranker, the reranker decides on the standalone query. The count is recorded (`term_reserved`). With the switch off, with no expansion tokens, or with `reserve_slots` 0, nothing changes.
- **D-35 (languages come from the registry):** LANG-01 and LANG-02 (Phase 3.2) make the supported languages a deployment setting backed by a registry, and Phase 3.2 D-06 derives the `Language` type from that registry with a CI check against hand-written unions. This phase writes no `zh|en|it` union, tuple or list in contracts, SQL, code or the Config UI. The Pydantic contract imports the registry-derived language type from Phase 3.2's contracts module and adds the literal `any` for entries; TypeScript uses the generated type; SQL checks only the shape of the value; the validator checks that a code is enabled through Phase 3.2's settings module (the only reader of the two language variables). Tests and fixtures cover every fixture language by reading the harness's language list. If the registry-derived type or the settings module is not on trunk when a plan needs it, that plan stops and reports; it does not fall back to a literal list.
- **D-36 (consistent with Phase 4.1 as revised 2026-11-25):** This phase runs after Phase 4.1's last plan (04.1-12; 13 plans). (1) "Under v2" means the effective pipeline: the stage lives in the v2 graph that `runRetrieval` dispatches to through `resolveEffectivePipeline()`, so when an implicit v2 default falls back to legacy (supported languages not chosen, or a Phase 4 function missing) no terminology code runs, nothing is recorded and nothing fails. No terminology code reads `RAG_PIPELINE`. (2) Tests and run configs never rely on the shipped default: each sets the pipeline and the supported languages it needs explicitly (through the pinned eval env or its own overrides), so its result is the same before and after the flip; an explicit v2 without languages would answer `languages_not_configured`. (3) The three switches are sub-switches read only under v2, so the templates write them explicitly as `false` (unlike `RAG_PIPELINE`, which the templates leave empty), and the derived eval pin `eval/config/rag-eval-env.json` is regenerated when they are added. (4) If Phase 4.1 ends with `not_flipped`, the orchestrator decides whether this phase starts; its plans need only what plans 04.1-01 to 04.1-08 leave on trunk plus a settled set of config files.
- **D-37 (domain neutrality):** Plans, code, defaults, prompts, Config UI copy, tests and fixtures of this phase contain no domain content. Wherever a term is needed they use placeholders with no real-world meaning: Han `术语甲`, `新版术语甲`, `术语甲乙丙`, `术语丁戊己`; Latin `termalpha`, `alpha beta`, `term alpha beta`, `term gamma delta`, `voce alfa`, `termine alfa beta`; identifiers `AB-1234-C`, `CD-5678-E` and their loose spellings. Fixture items are described by structure (variant absent from the corpus, canonical in the gold span) and live in dedicated synthetic documents (D-27); tests that need a corpus use their own synthetic one under `tests/fixtures/terminology-corpus/`. Anything domain-specific comes only from a tenant's own import.
