## Phase Boundary

Users ask in their own words ("心梗了怎么办", "how long to send back a yearly plan", "ridare i soldi", "the X9 pump"); the knowledge base uses the domain's terms ("心肌梗死", "refund window", "rimborso", "XP-900"). Phase 4 made the lexical leg strong on exact terms, which makes it weak exactly when the user does not use them. This phase adds a terminology dictionary that domain experts maintain, and uses it at query time.

It delivers:
- a tenant-scoped dictionary in Postgres with a deployment-wide **shared** layer and a per-tenant **workspace** layer that can add entries and suppress shared ones; every change bumps a layer version and writes an append-only audit row;
- an admin API (Zod, `checkAdmin` + `resolveAdminWorkspaceScope`) for list, create, update, delete, suppress, versions, audit, expansion preview, CSV import (dry run, then atomic apply) and CSV export;
- validation that rejects conflicts, chains, cycles, one-character Han variants, stopword-only and empty variants before anything is written;
- a `terminology` stage in the v2 query group that matches dictionary entries in the query and feeds a **separate, down-weighted lexical RRF list** (the original lexical list is unchanged), with hard caps; optionally (own switch) a dense variant with canonical terms substituted;
- the matched entries exposed on the query-stage output as a hint for Phase 6 rewriting and HyDE;
- an opt-in, masked, tenant-scoped log of missed queries (empty, refused, low-confidence) and a miner CLI that proposes candidate terms for expert review; nothing is ever applied automatically;
- synthetic colloquial golden items in zh/en/it with a fixture dictionary, an on/off comparison, and a Config UI panel (after a UI-SPEC).

In scope: TERM-01 to TERM-11 (see REQUIREMENTS-ADDITIONS.md).

Out of scope:
- Index-time synonyms (Postgres thesaurus dictionaries or canonical terms written into `lexical_text`): researched and rejected for now (D-14); revisit only if eval shows a gap query-time expansion cannot close.
- The legacy pipeline (`RAG_PIPELINE=legacy`): untouched. The dictionary acts only under v2.
- LLM query rewriting, HyDE, multi-query: Phase 6. This phase only hands Phase 6 the matched entries (D-20, QRY-01/QRY-03 amendment).
- Thumbs-down and feedback as a mining source, and real (production) golden items: Phase 5.1.1, which writes into the same candidate table (D-25).
- Exact-id lookup list integration for identifier aliases: waits for plan 04-29 (unmerged); identifier aliases go through the lexical expansion list here (D-12).
- Choosing the shipped default: stays off (D-30); Phase 7 / ADM-02 decides with real items.

## Implementation Decisions

### Storage, layers and tenancy
- **D-01:** Four tables in one migration (0471): `rag_term_layers` (one row per layer: `layer_key` primary key, `version bigint`, `entries_sha256`, `updated_at`, `updated_by`), `rag_term_entries`, `rag_term_audit` (append-only), and later (0473) `rag_term_misses` and `rag_term_candidates`. RLS is enabled with no policies, everything is revoked from `PUBLIC, anon, authenticated`, and only `service_role` gets table privileges (the `rag_admin_audit` pattern of 0316). No browser path reads or writes these tables.
- **D-02:** `layer_key` is `'shared'` (deployment-wide) or a tenant key (`s:default`, `u:<uuid>`, `o:<uuid>`), checked by a CHECK constraint that mirrors `TENANT_KEY_RE` (`src/lib/rag/ingest/writer.ts:270`). The effective dictionary for tenant T = shared entries minus those T suppresses, plus T's own entries; on a conflict between a workspace entry and a shared entry for the same normalized variant and language, the workspace entry wins and the preview reports the override.
- **D-03:** Single-tenant deployments use only the shared layer. The API refuses `layer: "workspace"` in single-tenant mode (400 `workspace_layer_unavailable`), and the UI hides the layer switch. Multi-tenant: shared-layer writes require `admin_users` membership (every Config UI admin already has it); workspace writes require the layer key to be in `rag_admin_tenant_keys(p_actor)` (0316), so an admin can only edit tenants they administer. Another tenant's entry id answers `not_found`, never `forbidden` (no probing, as in 0316).
- **D-04:** Entry shape: `id uuid`, `layer_key`, `canonical text` (1..64 chars), `variants text[]` (1..16, each 1..64 chars), `language` (`zh|en|it|any`), `kind` (`synonym|abbreviation|alias|identifier|translation|misspelling`; the last two match Phase 5.1.1's `DictionaryCandidate.relation` so its expert-labelled pairs import without mapping loss), `mode` (`one_way|equivalent`, default `one_way`), `enabled boolean`, `note text` (≤ 500), `suppresses_entry_id uuid` (workspace rows only; a suppression row has no variants), `created_by/updated_by uuid`, timestamps, and generated `normalized_variants text[]` written by the writer RPC from the app-side normalizer (stored, not computed in SQL, so SQL and TS can never disagree on folding). Limits: 20,000 entries per layer.
- **D-05:** Versioning: every write RPC increments `rag_term_layers.version` by exactly one in the same transaction (an import counts as one), recomputes `entries_sha256` over the canonical JSON of the layer's entries, and writes one audit row per changed entry carrying `layer_version`. Writes take an `p_expected_version` and fail with `version_conflict` (409) when it is stale: two experts cannot silently overwrite each other.
- **D-06:** Audit: `rag_term_audit(id, layer_key, entry_id, action, actor, before jsonb, after jsonb, layer_version, created_at)`, actions `create|update|delete|import|suppress|unsuppress|candidate_accept|candidate_dismiss`. Append-only via BEFORE UPDATE/DELETE/TRUNCATE triggers. No entry id is a foreign key, so audit outlives deleted entries. Point-in-time export of an old version is deferred (the audit holds enough to rebuild it; nothing reads it that way yet).
- **D-07:** Every new SQL function is `SECURITY DEFINER`, `SET search_path = ''`, schema-qualifies every name, `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`, `GRANT EXECUTE ... TO service_role`, and is added to the lock-down block when the migrations are folded into both setup files (plan 14). `tests/rag/search-rpc-grants.test.ts` and `tests/rag/security-definer-search-path.test.ts` stay green.
- **D-08:** Migration numbers 0471 (schema + read RPC), 0472 (writers, import, suppression, audit read), 0473 (miss log, candidates, decisions). Rationale: 0413 is reserved for 04-33; 0420–0423 are taken by queue-hardening; the phases planned in parallel already claim 0440–0442 (Phase 3.1.1), 0531–0535 (Phase 5.1.1) and 0651–0653 (Phase 6.1), and 0414–0419 / 0450s are left to Phase 4.1. `047x` is free on trunk and every branch at e90d9cd. The executor of plan 03 re-checks `ls supabase/migrations` on trunk, `git ls-tree` on open branches and the sibling phase directories, and renumbers if any is taken: the three files and every file in this phase directory found by `grep -l 047`. Migrations sort by name, so 047x applies after 0440–0442 (no dependency on them).

### Normalization and matching
- **D-09:** One normalizer for dictionary writes and queries: the Phase 4 tokenizer normalization (`NFKC`, lower case, apostrophe mapping, accent folding: `src/lib/rag/lexical/tokenize.ts:18-31`), exported as `normalizeLexical()` without changing `LEXICAL_VERSION` (2). Matching never re-implements folding.
- **D-10:** Han matching is substring on the normalized query with longest-match-first, left-to-right, non-overlapping selection (a character trie, rebuilt only when the cached dictionary changes). Han variants must have at least 2 Han characters, because a one-character Han variant would match inside unrelated words. Segmentation (`Intl.Segmenter`) is not used for matching: colloquial Han terms such as 心梗 are segmented unreliably, and the bigrams the index uses make substring matching the consistent choice.
- **D-11:** Latin (en/it) matching is on token boundaries over the normalized text, supports multi-word variants ("send back", "ridare i soldi"), and respects elisions the same way the tokenizer does (`l'`, `dell'`). A variant that is entirely stopwords, or that yields no lexical tokens, is rejected at write time.
- **D-12:** `kind: identifier` entries match through `identifierLexicalLookupForms()` (`tokenize.ts:168`), so `XJ 9000 B`, `xj-9000-b` and `xj9000b` all match; their expansions are emitted as identifier forms. Feeding identifier aliases into the exact-id third list (04-29) is deferred until 04-29 merges.
- **D-13:** Expansion is never transitive (one hop only). `one_way`: a variant in the query adds the canonical. `equivalent`: any member adds the canonical and the other members. Expansion terms are tokenized with `queryLexicalTokens()` and deduplicated against the original query's tokens.

### Index time
- **D-14:** No index-time synonyms. (a) Postgres `CREATE TEXT SEARCH DICTIONARY ... TEMPLATE = synonym|thesaurus` reads files from `$SHAREDIR/tsearch_data`, which hosted Supabase does not let us write; (b) the Phase 4 lexical index bypasses the text-search parser and dictionaries entirely (`rag_lexical_tsvector` builds the tsvector verbatim from the app tokenizer, 0401 F-1), so a Postgres dictionary would not apply anyway; (c) writing canonical terms into `lexical_text` would make every dictionary edit a relex of every chunk containing any changed variant (the `rag:relex` job, `src/lib/rag/ingest/relex/run.ts`, batches of 500), coupling an expert's edit to a corpus-wide rewrite and to the lexical version. Query-time expansion of the whole equivalence class gives the same lexical recall without a relex, which is also Elasticsearch's recommendation (search-time synonyms, updateable without reindexing). RESEARCH.md records the relex cost estimate for a future decision.

### Query-time use
- **D-15:** New optional stage `terminology` (in `OPTIONAL_STAGES`, `src/lib/rag/config.ts:4`), run in the v2 query group after `translate`, `onFail: 'skip'`. When `RAG_TERMINOLOGY=false` it is added to the disabled stages exactly as `translate` is (`config.ts:380`) and the request is otherwise unchanged. A load failure or timeout records `skipped`, so the request continues without expansion and the retrieval status is `degraded` by the existing rule (`src/lib/rag/pipeline.ts:177`); strict mode never answers "information not available" because of a dictionary failure.
- **D-16:** Expansion goes into its own RRF list `term:0` (an id with no `dense`/`lexical` prefix, so nothing that inspects list ids by prefix miscounts it), searched with a lexical-only backend call (`denseLimit: 0`, supported by `hybrid_search_chunks`, 0407 `IF p_dense_limit > 0`) for the original variant only, in parallel with the existing legs. The original `lexical:0` list is byte-for-byte what it is today. Its RRF weight is `TerminologyParams.expansion_weight` (default 0.5, relative to `lexical` 1.0), so a chunk found only through expansion can never outrank one found by both original legs at equal rank. Expansion is a no-op when `RAG_LEXICAL_SEARCH` is off (it then only produces the optional dense variant and the Phase 6 hint).
- **D-17:** Caps (all in the Pydantic `TerminologyParams`, defaults): `max_matches` 8, `max_terms_per_match` 4, `max_expansion_tokens` 24, `expansion_weight` 0.5, `dense_weight` 0.5 (le 0.5; RRF weight of the optional terminology dense variant), `min_han_chars` 2. When a cap is hit the stage records `capped=true` in its detail. Defaults are tuned later with the 04-25 sweep tool, never by hand.
- **D-18:** `RAG_TERMINOLOGY_DENSE=false` (own switch): when on, one extra query variant of kind `terminology` (canonical terms substituted for matched variants) is embedded in the existing batched embed call and searched dense-only, its list weighted `dense_weight` (≤ 0.5, so it can never outweigh the original legs at weight 1); it counts toward `MAX_QUERY_VARIANTS` (3) after translated variants. Never in voice.
- **D-19:** Voice: the lexical expansion runs in voice (it is in-process plus one parallel lexical query); the dense variant never does. Stage budgets: `terminology` 5 ms chat/embed, 3 ms voice in `eval/config/latency-budgets.json`; the search stage budget is not raised, and the eval reports whether search p95 moved.
- **D-20:** The query-stage output gains `terminology: { matches: TerminologyMatch[], version: string } | null`, and `RunRetrievalInput` gains nothing. Phase 6 reads `matches` (surface form, canonical, kind, language) and passes them to the rewrite and HyDE prompts as a glossary (proposed QRY-01/QRY-03 amendment).
- **D-21:** Trace and hash: the stage detail carries counts and the effective version only (`matches=2 tokens=7 capped=false version=s12.w3`), never the query, the variants or the canonicals. `computeRetrievalConfigHash` gains an optional `terminology` block (`{ version, params_sha256, dense }`) added to the payload **only when the switch is on**, so with the switch off the hash is identical to today's.
- **D-22:** Dictionary loading: `rag_term_effective(p_tenant_key)` returns the effective entries and both layer versions; the app caches the built matcher per tenant key in-process (LRU of 256 tenants, 60 s TTL). An edit therefore reaches retrieval within 60 s; the preview endpoint always bypasses the cache. The cache key includes the tenant key, so two tenants never share a matcher.

### Maintenance
- **D-23:** CSV columns: `canonical,variants,language,kind,mode,enabled,note` with `variants` separated by `|`. UTF-8 with or without BOM, RFC 4180 quoting, ≤ 1 MB and ≤ 5,000 rows per file. A small in-repo parser (no new dependency). Import is two calls: `dry_run` returns per-row errors (conflict, chain, cycle, limit) and the diff (`create`, `update`, `unchanged`, `delete` for `replace` mode); `apply` re-validates and writes atomically through `rag_term_apply_import` with the version the dry run saw. Export neutralises spreadsheet formulas (a cell starting with `= + - @` or tab/CR is prefixed with `'`); import strips exactly one leading `'` only when the next character is one of `= + - @ \t \r`, so the round trip is lossless.
- **D-24:** Validation (pure TS in `src/lib/rag/terminology/validate.ts`, used by the write routes and the import): (1) a normalized variant maps to two canonicals in one layer and language → `conflict`; (2) an entry's canonical is a variant of another entry in the same layer and language, or vice versa → `chain` (with one-hop expansion a chain is ambiguous, so it is rejected with a "merge these entries" hint); (3) any closed loop through canonical/variant edges → `cycle`; (4) variant equals canonical → dropped with a warning; (5) Han variant shorter than `min_han_chars`, stopword-only or tokenless variant → `invalid_variant`; (6) overlapping `equivalent` sets → `conflict`. Cross-layer collisions are not errors; they are reported as `overrides` in the preview and import report.
- **D-25:** Log mining: when `RAG_TERMINOLOGY_MINING=true`, the v2 finish path records a missed request (status `empty`, refusal decision `refuse`, or `degraded` with no candidates) for profiles `chat`, `embed` and `voice` (never `eval`) into `rag_term_misses`: tenant key, `maskPII` query cut to 500 characters, language, status, reason, top fused score, effective dictionary version, `retrievalConfigHash`, profile, time. Fire-and-forget with a 500 ms timeout; it never delays or fails the request. Retention holds without any schedule: `rag_term_record_miss` deletes the tenant's rows older than 30 days on each insert, reads ignore older rows, and the miner also purges. A `source` column (`miss_log` here; `feedback` and `langfuse` reserved) lets Phase 5.1.1 add thumbs-down and online-judge failures without a schema change.
- **D-25a (coordination with Phase 5.1.1):** Phase 5.1.1 (planned in parallel) adds `public.rag_retrieval_log` (every retrieval, privacy-minimised, retention, per-tenant opt-out, 0531–0533) and an expert labelling flow that exports `DictionaryCandidate {tenant_key, language, observed_term, canonical_term, relation, example_review_item_ids, occurrences}` JSONL for this phase. Because 4.1.1 ships first, `rag_term_misses` is the minimal interim source. Once `rag_retrieval_log` exists, 5.1.1 (or a follow-up) points the miner's source reader at it (rows with status empty/refused) and turns `RAG_TERMINOLOGY_MINING` recording off; the miner's source is one function (`readMisses`) so this is a one-file change. The 5.1.1 `DictionaryCandidate` file is imported through this phase's import service (an adapter maps `observed_term → variants[0]`, `canonical_term → canonical`, `relation → kind`), never by writing the tables directly. The REQUIREMENTS-ADDITIONS amendment records this.
- **D-26:** Miner: `npm run rag:terms:mine` (CLI under `src/lib/rag/terminology/mine/`, run by the operator's scheduler; nightly recommended). Per tenant over a window (default 14 days): tokenize missed queries with `queryLexicalTokens` plus Han 2–4-grams; keep terms with support ≥ 3 distinct masked queries; drop stopwords, mask placeholders, digits-only terms and terms already in the effective dictionary; compute corpus document frequency in that tenant only (`rag_term_corpus_df`, service role, on `lexical_tsv`); keep df == 0 or df ≤ 2 as candidates with up to 3 example masked queries. Upsert into `rag_term_candidates` (status `pending`); a `dismissed` candidate is not resurfaced. Accepting a candidate opens the normal create form; the entry is written through the normal path with audit, and the candidate is marked `accepted` with the entry id.

### Evaluation and completion
- **D-27:** Fixture dictionary `eval/fixtures/terminology/dictionary.jsonl` (one TerminologyImportRow per line, so the harness does not depend on the CSV parser; plan 11 tests its CSV round trip) (shared layer, synthetic), seeded by the eval harness into every fixture database regardless of the switch, so "switch off" is proven on a database that holds a dictionary.
- **D-28:** New golden items, category `colloquial` (EVAL-14), ids `<lang>-colloquial-term-NNN` (answerable and identifier-alias items) and `<lang>-no_answer-term-NNN` (no-answer controls): 4 answerable per language whose colloquial variant does not occur anywhere in the corpus while the canonical occurs in the gold span (asserted by a test), 1 identifier alias per language, and 1 `no_answer` per language whose question contains a dictionary variant (expansion must not create a false answer). Provenance `synthetic_fixture`. The baseline is re-recorded with zero paired difference on every pre-existing item (05.1-17 procedure).
- **D-29:** Comparison: run configs `v2-terminology-off` / `v2-terminology-on` (both on top of the Phase 4.1 default run config, plus a lexical-only pair with refusal off to sidestep the known 0.65-floor artefact on the fixture embedder). Done means: Recall@k and MRR on the `colloquial-term` slice improve; no other slice, language or category drops beyond the noise band (`eval/config/noise.json`); the `no_answer` term items are still refused at the same rate; latency within budgets.
- **D-30:** `RAG_TERMINOLOGY`, `RAG_TERMINOLOGY_DENSE` and `RAG_TERMINOLOGY_MINING` default to `false` and stay off at the end of this phase. Synthetic items only report (EVAL-14); the switch can be proposed on once real colloquial items from Phase 5.1.1 pass the gate.
