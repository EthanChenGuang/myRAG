**Researched:** 2026-11-24

**Domain:** query-time synonym expansion for hybrid (pgvector + verbatim tsvector) retrieval in every fixture language; expert-maintained, tenant-scoped dictionaries; miss-log mining
**Confidence:** HIGH on the codebase findings, MEDIUM on default caps and weights (to be tuned by the retrieval sweep tool), LOW on real-domain effect size (no real items yet).

Trunk keeps moving while this phase waits (Phases 5, 5.1, 6 and 7 are executing). Every location below is named by function, constant or file, and every executor re-reads the newest definition before editing (CONTEXT D-38). Every example term is a synthetic placeholder (CONTEXT D-37).

## Summary

The v2 pipeline already has every seam this phase needs: an optional-stage runner with skip semantics, a variants list, a weighted RRF over per-variant lists, a lexical-only backend call, a per-request config hash, PGlite fixture databases that apply every migration and take a caller-chosen corpus directory, run configs, and a RAG Administration tab in the Config UI with a fetch helper and admin guard. Postgres cannot do index-time synonyms here, both because hosted Supabase does not allow dictionary files and because the Phase 4 lexical index deliberately bypasses the text-search parser. The recommended design is query-time expansion into a separate, down-weighted RRF list, with the dictionary stored in service-role-only tables, versioned and audited per layer.

**Primary recommendation:** query-time only; separate `term:0` RRF list at half the lexical leg weight; Han substring longest-match with a two-character minimum; one-hop expansion of the standalone query only; a small reservation so expansion-only hits reach the reranker at any pool and cap; per-tenant cached matcher with 60 s TTL; switch off by default and proven on synthetic colloquial items, with real items gating later (EVAL-14).

## Position against Phase 6 (CONTEXT D-15, D-31)

Phase 6 D-05 fixes the order `query_gate` → `condense` → (`normalize_dates`, `translate`, `expand`, `hyde`, `decompose` in parallel) → `semantic_cache` → `embed`. The earlier wording of this phase, "terminology runs after translate", is ambiguous there: `translate` is one member of a parallel group.

Options considered:

| Option | Verdict |
|--------|---------|
| Inside the parallel group | Rejected: the group has its own deadline and abort; a dictionary load would be cut by a deadline meant for model calls, and the variant list is not final yet. |
| Between `condense` and the group | Rejected: adds its latency in front of every transform, and the accounting against the search cap needs the final variant list. |
| After the group joins, before `semantic_cache` and `embed` | Chosen: the variant list is final, the dictionary version is known before the cache key is built, and without Phase 6 this is exactly "after translate". |
| Matching every variant | Rejected: translated and LLM variants may already contain a canonical or an invented term; matching them compounds expansion and makes the number of extra searches depend on the number of variants. |

The cost of the chosen position is that the stage output arrives after the transforms that would like a glossary. The matcher is in-process and cached, so a second, earlier entry (`terminologyGlossary`) serves prompts without making the stage run twice (CONTEXT D-20).

## Reach beyond the pool (CONTEXT D-34)

With `rrf_k` k, an original list weight w and the expansion weight w/2, a chunk found only by `term:0` at rank 1 scores `w / (2k + 2)`. A chunk an original list ranks at r scores at least `w / (k + r)`, which is higher whenever `r < k + 2`. With the committed `rrf_k` of 60, every chunk in the first 61 positions of either original list outranks the best expansion-only chunk. When the original lists are full, the rerank input (any cap up to the pool) therefore holds no expansion-only chunk, and the smaller the cap the more certain that is. The fixture corpus hides this, because it is smaller than the pool (F-25).

Mitigations considered: a higher weight (rejected: it breaks "expansion never outweighs the original"); merging tokens into the original lexical query (rejected in F-6); a bounded reservation of rerank-input places for the best `term:0` hits (chosen: the Phase 6 D-07 sub-question reservation is the precedent, the weight guarantee is untouched, and the reranker decides on the standalone query).

## External Best Practice

- **Search-time synonyms are the default recommendation.** Elastic: "Search time is recommended because you can update your synonym sets without reindexing"; synonyms API sets are search-time only, with `updateable: true` analyzers reloaded on change; `synonym_graph` handles multi-word synonyms at search time. The cost is more query terms, judged worth it. [Configure synonyms in Elasticsearch](https://www.elastic.co/guide/en/elasticsearch/reference/current/search-with-synonyms.html), [Synonyms API blog](https://www.elastic.co/blog/update-synonyms-elasticsearch-introducing-synonyms-api), [Boosting the power of Elasticsearch with synonyms](https://www.elastic.co/blog/boosting-the-power-of-elasticsearch-with-synonyms), [Synonym graph token filter](https://www.elastic.co/guide/en/elasticsearch/reference/master/analysis-synonym-graph-tokenfilter.html).
- **Postgres dictionaries are file-based and index-time.** The `synonym` template reads `$SHAREDIR/tsearch_data/<name>.syn`; `thesaurus` adds phrases but must be applied at index time and needs a reindex on change; neither works through our verbatim tsvector builders. [PostgreSQL: Text Search Dictionaries](https://www.postgresql.org/docs/17/textsearch-dictionaries.html), [dict_xsyn](https://www.postgresql.org/docs/17/dict-xsyn.html). Hosted Supabase gives no write access to `$SHAREDIR` (not confirmed by a Supabase doc page in this pass; irrelevant to the decision because of the parser bypass).
- **Query expansion drifts.** Classic IR work shows expansion raises recall but can hurt precision when expansion terms dominate; standard mitigations are down-weighting expansion terms relative to original terms and capping their number (Carpineto & Romano, "A Survey of Automatic Query Expansion in Information Retrieval", ACM CSUR 2012). Our separate weighted RRF list is the fusion-level form of that down-weighting (Cormack, Clarke & Büttcher, "Reciprocal Rank Fusion outperforms Condorcet and individual rank learning methods", SIGIR 2009).
- **Directional synonyms.** Elastic/Solr distinguish equivalent (`a, b, c`) and explicit one-way (`a => b`) mappings; one-way avoids flooding a precise query with informal forms. We keep both (`mode`), default one-way.
- **Chinese.** Word segmenters split short and abbreviated terms unpredictably (a two-character short form may stay one token or split); character n-gram indexing plus substring dictionary matching is the robust choice when the index is bigram-based, which ours is.
- **Expert-in-the-loop mining.** Mining zero-result queries for vocabulary gaps and routing them to curators (never auto-applying) is standard practice in site search (for example "no results" analytics feeding synonym curation). We mirror that: candidates only.
- **Translation glossaries.** Translation systems keep required term pairs per language pair, directional, separate from monolingual synonyms; storing them in one table with the two languages on the row lets one audit, one version and one import serve both uses (XLG-05 asks for one dictionary, not two).

## Index-time Cost Estimate (for D-14)

If canonical terms were written into `lexical_text`, every edit touching variant v would require relexing every chunk whose tsvector contains any token of v, per tenant; for the shared layer that is every tenant. `rag:relex` works in batches (`DEFAULT_BATCH_SIZE` in `src/lib/rag/ingest/relex/run.ts`); no throughput was measured in this pass (estimate unverified). A shared-layer edit would be a corpus-wide write across every tenant, and the effective `lexical_text` would then depend on a dictionary version, which the config hash and `lexical_version` do not capture today. Query-time expansion costs one extra parallel lexical query (≤ 24 OR terms) and an in-process trie lookup (microseconds) per request.

## Architecture

```
standalone query (Phase 6 condense output when present, else the request query)
   │
   │   Phase 6 present:  query_gate ─► condense ─► [normalize_dates │ translate │ expand │ hyde │ decompose] ─┐
   │   Phase 6 absent:   refs ─► analyze ─► translate ────────────────────────────────────────────────────────┤
   ▼                                                                                                           ▼
terminology (new, optional, skip on failure; matches the standalone query only)
   │  load effective dictionary (cache, 60 s) ; build matcher without translation pairs
   │  match (Han substring / Latin boundary / identifier forms)
   │  expansion tokens (capped) ; optional dense variant (counts against the caps, D-31) ; version for the hash
   ▼
semantic_cache (Phase 6; key includes the dictionary version) ─► embed (one batch, + optional terminology variant)
   ─► search: dense:i, lexical:i (unchanged)
              term:0 (lexical-only, limit = pool at run time, weight = 0.5 × lexical leg weight)   ◄── new
   ─► fuse (RRF) ─► dedupe + cap ─► reserve ≤ reserve_slots term:0 hits (new) ─► rerank ─► refusal ─► context
finish ─► trace (counts + version) ─► config hash (+terminology block when on) ─► miss log (opt-in)

read side (no switch):  getTerminologyLexicon(scope, opts) ─► loader ─► rag_term_effective   (Phase 4.2, 6.2)
```

## Risks

| Risk | Severity | Mitigation |
|------|----------|------------|
| Cross-tenant leak of dictionary entries or mined queries | critical | Service-role-only tables, `rag_term_effective(p_tenant_key)` asserts the key, cache keyed by tenant, two-tenant tests for read, write, preview, read API, mining df, candidates (plans 03, 04, 05, 09, 11, 12, 16, 17). |
| Expansion swamps original intent | high | Separate list, half the lexical weight, caps; reserved hits stay last; eval checks every non-term slice within noise. |
| Expansion never reaches the reranker on real corpora | high | Bounded reservation tested with full lists at several caps (plan 18). |
| Han false matches (one-character variants) | high | `min_han_chars` 2 rejected at write, property tests. |
| Dictionary failure turns strict mode into "temporarily unavailable" | medium | Stage is skip-on-fail → `degraded` with documents still answers; tested. |
| Off-switch changes behaviour (stage record, hash) | medium | Test asserts identical candidates, order, scores and hash with the switch off and a seeded dictionary. |
| A cached answer survives a dictionary edit | medium | The version is in `retrievalConfigHash`, which is part of the cache key; tested when the cache is on trunk. |
| The search cap of Phase 6 is exceeded | medium | Both terminology calls count toward `max_searches`; unit tests on the variant builder (plan 07). |
| A hard-coded language list slips in | medium | Registry-derived type, the Phase 3.2 literal check in plan 14's gate, stop-and-report when the registry is missing. |
| PII in miss log | high | Opt-in, `maskPII`, length cap, 30-day purge, service role only, no logging of text. |
| CSV formula injection on export | medium | Prefix neutralisation (OWASP CSV injection guidance). |
| Migration number collision | medium | 047x block, re-check before writing (D-08). |
| Synthetic items overfit the fixture dictionary | medium | Items are report-only; default stays off until real items (5.1.1). |
| Lost updates between two experts | medium | `p_expected_version`, 409. |
| A later phase reads the tables directly | medium | Stable read API with a locked contract and a boundary rule (plan 17). |
