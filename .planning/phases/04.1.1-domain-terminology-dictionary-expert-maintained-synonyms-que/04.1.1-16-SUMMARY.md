# Phase 4.1.1 Plan 16: Hash block, cache key, identity Summary

**The retrieval-config hash and the semantic-cache key now carry the dictionary version whenever the terminology stage is enabled for the request. With the stage disabled (switch off, or `terminology` in the config's or the eval request's disabled stages), the hash is byte-identical to before. PGlite end-to-end tests show that off is today's behaviour on a seeded database and that each tenant's request loads only the shared layer and that tenant's own workspace layer.**

## Phase 6 branch (D-40)

**Present.** Phase 6's semantic_cache stage is on trunk. Its key's `retrievalConfigHash` comes from `SemanticCacheSeam.retrievalConfigHash` in `runV2Pipeline`, which calls `requestRetrievalConfigHash`. `buildV2Result` calls the same function. Both now pass the terminology stage state, so the cached key and the result hash can never disagree. `src/lib/rag/query/run-layer.ts` did not need a change. Task 2's stage-level cases are in place.

Plan 06-32's wording change ("compute the cache key's retrievalConfigHash with terminologyHashBlock") is already met on trunk through `requestRetrievalConfigHash`. Any new caller of `computeRetrievalConfigHash` should go through `requestRetrievalConfigHash`, or pass `terminologyHashBlock(...)` itself.

## Deviations

- **`src/lib/rag/v2/stages/query.ts`** (not in `files_modified`) gained `QueryStagesInput.onTerminology`. The cache seam runs inside `runQueryStages`, before that function returns its output, so the pipeline needs the stage state earlier than the return value.
- **`src/lib/rag/query/run-layer.ts`** was not edited (see the Phase 6 branch above).
- **Task 3 runs in multi-tenant mode only.** One process cannot hold two in-process eval fixtures, because the app's clients keep the first edge URL. The plan's "single-tenant" identity cases therefore run as user A (the fixture user, who owns the synthetic corpus) in the same multi-tenant database. "Unseeded" is the same database queried before `seedTerminology` writes any row, so no second database is needed.
- **User C's version string is `s1`, not `s1.w0`.** Plan 05's loader leaves out the workspace part when the tenant layer version is 0. The test asserts `workspace_version` 0 and the string `s1`.
- **Version and matches come from `stage_counts.terminology`.** The eval route returns stage counts, not stage details. `matches=<n>` is checked through the same count.
- **Cross-tenant strength:** user A's workspace layer is bumped to version 3, so a loader that read B's layer would report `w1` and fail. Single-variant requests check that A never matches B1 and B never matches A1. The plan's "term:0 list present" is checked as `stage_counts.search.term` being defined; B owns no chunks, so its hit count is 0.
