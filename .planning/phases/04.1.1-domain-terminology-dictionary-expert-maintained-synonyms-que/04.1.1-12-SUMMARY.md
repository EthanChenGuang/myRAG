# Phase 4.1.1 Plan 12: Terminology candidate mining and review Summary

**Missed queries now become a review list. `npm run rag:terms:mine` proposes candidate terms per tenant from the masked miss log. Admins list the pending candidates of their own workspace, then accept one (with an entry they created through the normal create route) or dismiss it. Each decision is audited, and the miner never writes dictionary entries.**

## What was built

- **Miner (`mine/mine.ts`).**
  - `readMisses` is the only function that reads the miss source (D-25a). Phase 5.1.1 changes this one function to read `rag_retrieval_log`.
  - Terms are `queryLexicalTokens` of the masked query plus Han 2–4-grams. Mask placeholders (`[EMAIL]`, `[PHONE]`, …) are removed before tokenizing. Digit-only terms, single Han characters and stopwords are dropped.
  - A term needs `minSupport` distinct masked queries (default 3) in its language. Shorter Han grams of the same queries collapse into the longest one.
  - Terms already in the tenant's effective dictionary are dropped: canonicals, variants and normalized variants, translation pairs included. The dictionary comes from `loadEffectiveDictionary` with the cache bypassed.
  - Corpus df comes from `rag_term_corpus_df` for that tenant only, in batches of 200 tokens. Terms with df ≤ 2 are kept, at most 1,000 per tenant, each with up to 3 examples.
  - Rows go to `rag_term_upsert_candidates` in batches of 500. The SQL keeps a dismissed or accepted candidate's status.
  - A writing run first calls `rag_term_purge_misses(30)` (PO-4). A dry run only reads.
  - Logs carry counts only (`[RAG Terminology]`), with no tenant key, term or query.
- **CLI (`mine/cli.ts`).** `npm run rag:terms:mine -- [--dry-run] [--tenant <key>] [--window-days 1..30] [--min-support n]`.
  - Output is counts per tenant.
  - Exit codes: 0 when done, 1 on a database failure or a skipped tenant, 2 on bad arguments.
  - Without an injected client, it refuses to start unless `SUPABASE_SERVICE_ROLE_KEY` is set.
- **Candidate service (`candidates.ts`).**
  - `listTerminologyCandidates` calls `rag_term_list_candidates`, which checks the actor and layer in SQL, and returns the pending rows of the page.
  - `decideTerminologyCandidate` calls `rag_term_decide_candidate` with the verified actor. The SQL resolves the tenant, checks the entry layer (the candidate's tenant or shared) and writes the `candidate_accept` / `candidate_dismiss` audit row.
- **Routes.** Both routes use `checkAdmin` and send `no-store`.
  - `GET …/candidates?organization_id=&limit=&offset=` takes the workspace from `workspaceScope`: `s:default` in single-tenant mode, `u:<admin>` or an organization the admin belongs to. Any other organization is 403.
  - `PATCH …/candidates/[id]` takes `{ action: 'dismiss' | 'accept', entry_id? }`. The body is strict: `accept` requires `entry_id`, `dismiss` forbids it, and an actor or tenant key in the body is a 400.

## Deviations

1. **Files outside the plan's list.** `src/lib/rag/terminology/admin.ts` got the `not_pending` reason. `src/app/api/rag/admin/terminology/_lib.ts` got the two candidate schemas and the 409 mapping.
2. **Test fix after the RED commit (Task 2).** In the guard test, passing `undefined` for "no session" triggered the helper's default admin token. The helper now takes `null` for that. The code under test was not changed for this.
3. **PGlite tenant listing.** The fake edge serves a fixed table list without `gte`/`gt`/`order`. So the matrix test runs the miner's one table read (listing tenants with misses) on PGlite as `service_role`, and sends every RPC through the edge. `rag_term_record_miss`, `rag_term_read_misses`, `rag_term_corpus_df`, `rag_term_upsert_candidates`, `rag_term_effective`, `rag_term_list_candidates` and `rag_term_decide_candidate` all run as real SQL there.
4. **Scope resolution in tests.** `backfillScope` needs `auth.admin.getUserById`, which the fake edge lacks, so the tests inject `resolveScope`. Production uses `backfillScope`.
5. **List semantics.** The SQL list returns every status, with pending first. The route returns pending only, with `next_offset` instead of a total, because `total_count` counts every status.

## Known limitations

- Han df is an upper bound: `rag_term_corpus_df` counts one token at a time, so a Han n-gram takes the smallest df among its bigrams. A term whose bigrams appear in more than 2 documents, but never together, is dropped.
- Tenant listing without `--tenant` makes one small query per tenant. That is fine for the interim miss log. Phase 5.1.1 replaces the source anyway.
