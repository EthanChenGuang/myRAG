# Phase 4.1.1 Plan Index

18 plans in 9 waves (revised 2026-11-25; see "Revision 2026-11-25" below). Plans in the same wave share no file in `files_modified`; every file touched by two plans is ordered by a `depends_on` path (table "Shared files" below; checked with `gsd-tools phase-plan-index 04.1.1`). The phase tracer is 04.1.1-05 Task 1 (seeded dictionary → `terminology` stage on the standalone query → `term:0` list → RRF → eval route). Every plan runs after Phase 4.1's last plan, 04.1-12. Live checks are plan 15; everything else is automated (see `04.1.1-VALIDATION.md`).

Five rules hold in every plan:

- No pool size, rerank cap, leg weight, search limit, baseline value or item count is quoted as an expectation; values are read from the files and params in force at execution time, or passed explicitly by a test (CONTEXT D-29, D-34).
- Tests and run configs set the pipeline and the supported languages they need explicitly; "under v2" means the effective pipeline chosen by `resolveEffectivePipeline()` (D-36).
- Every term in plans, tests, fixtures and UI copy is a synthetic placeholder; no language list is typed out (D-35, D-37).
- Code and SQL are named by symbol and re-read at execution time, never by line number (D-38).
- A plan that touches a Phase 6 seam implements the branch that matches trunk and records it in its SUMMARY; no plan waits for Phase 6 (D-40).

Execution note: plans 03, 04, 05, 07, 08, 09, 10, 11, 12, 16 and 17 build PGlite fixture databases (`createFixtureDatabase` applies every migration). `.planning/config.json` has `use_worktrees: false`, so within one working tree never run two of them at the same time; run same-wave plans of that set one after another, or in separate worktrees. Plan 10 Task 3 and plan 14 run the smoke tiers and must run alone.

UI note: plan 13 is the only new UI surface. `/gsd-ui-phase 04.1.1` must produce `04.1.1-UI-SPEC.md` before plan 13 Task 2 (Task 1 is a blocking gate). The UI-SPEC can be produced any time after this index is approved; it does not block waves 1 to 6.

Migration numbers: 0471, 0472, 0473 (CONTEXT D-08). Plan 03 re-checks for collisions on trunk, open branches and sibling phase directories before writing, and renumbers everywhere if needed.

## Revision 2026-11-25

This revises the 16-plan set that passed plan-check on 2026-11-24. One planner session started the revision (CONTEXT, RESEARCH, plans 01 to 06) and stopped at a quota limit; this session finished it (plans 07 to 18, the pattern map, validation, requirement and roadmap drafts, this index) and re-checked plans 01 to 06.

Model: per `.claude/rules/gsd-model-roles.md` planners run on Fable; Fable quota is exhausted until 2026-12-02, so this revision was finished on Opus (owner's standing rule: take the recommended option).

### (a) Stage position against Phase 6 D-05

- CONTEXT D-15 (amended): `terminology` runs on the standalone query (Phase 6's `condense` output when present, else the request's query) after Phase 6's parallel transform group joins and before `semantic_cache` and `embed`; without Phase 6 it runs after `translate`, the same relative place. It never matches translated, LLM or caller-supplied variants: one hop, no compounding with model output, a constant cost of at most one `term:0` list and one dense variant per request.
- CONTEXT D-31 (new) defines the accounting. Without Phase 6: the Phase 4 rule (after translations, within `MAX_QUERY_VARIANTS`; `term:0` is not a variant). With Phase 6: preference order `original, condensed, translated, sub_question, terminology, expanded, hyde`; the terminology variant counts toward `max_llm_variants`; `term:0` counts toward `max_searches`, except when the protected variants alone fill it, where `term:0` is not searched, so no protected variant is ever displaced; the stage records `search_cut` and `variant_cut`. This session refined items (1) and (3): the exception for a full cap, and recording the cuts as stage counts because the terminology variant never appears in `QueryPlan`.
- The semantic-cache key includes the effective dictionary version through `retrievalConfigHash` (D-21 amended: one builder, `terminologyHashBlock`; `terminology:unavailable` when skipped; this session added that "off" includes a stage disabled through the disabled-stages lists).
- `terminology` is in `OPTIONAL_STAGES` (02) and in Pydantic `StageName` and `StageTimeoutsMs` (01).
- Plans: 05 places the stage and tests the order and the standalone-only rule; 07 implements D-31 with a pure `budget.ts` and the glossary helper (D-20); 16 wires the block into the hash and, when Phase 6's cache is on trunk, the cache key.

### (b) XLG-05 translation pairs

- CONTEXT D-04 and D-32: kind `translation` with required, different `source_language` and `target_language` (enabled registry codes, never `any`), `language` equal to the source, canonical = required target-language term, variants = source-language terms, `one_way` only; same-language expansion ignores them; the read API returns them.
- Languages come from Phase 3.2's registry-derived type and settings module, with stop-and-report when missing (D-35).
- Covered in contracts (01), SQL CHECKs and unique key (03), writers and audit (04), matcher exclusion (05, 06), validator rules 7 to 9 (06), admin routes with enabled languages (09), the fixture dictionary (10), CSV columns and the candidate adapter's `canonical_language` (11), the Config UI form (13), the read API (17), and the live walk-through (15).
- New requirement TERM-12 (D-39) makes this and (d) checkable; plans list TERM-12, never XLG-05 or LANG-07.

### (c) Phase 4 pool and cap values overtaken

- CONTEXT D-34: no pool or cap is assumed; the `term:0` limit is the effective `candidate_pool_size`, weights are factors on the leg weights in force; tests pass values explicitly.
- New plan 18: a bounded reservation (at most `reserve_slots`, default 2, never more than half the rerank input) puts the best expansion-only hits at the end of the rerank input, because RRF arithmetic keeps them out at any cap when the original lists are full (RESEARCH "Reach beyond the pool"). Its tests use the minimum, a middle and the maximum of the cap range the contract accepts at test time, so they follow Phase 4.2's floor of 25 without an edit.

### (d) LANG-07 stable read API

- New plan 17: `getTerminologyLexicon(scope, opts)` exported from `@/lib/rag`, returning `{ version, entries_sha256, terms, translations }` (Pydantic contract from plan 01, generated Zod), effective shared plus workspace layers with suppressions, through the plan-05 loader on the service-role client, memoized per tenant and version; it reads no switch; a contract test locks the shape; a two-tenant PGlite test proves isolation; the new `terminology-rpc` boundary rule fails on any `.rpc('rag_term_…')` or `.from('rag_term_…')` under `src/` outside `src/lib/rag/terminology/`.
