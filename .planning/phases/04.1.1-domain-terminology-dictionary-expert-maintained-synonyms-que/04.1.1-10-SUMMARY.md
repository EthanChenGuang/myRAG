# Phase 4.1.1 Plan 10: Synthetic term fixtures, term golden items, run configs and re-baselines Summary

**Every fixture database now holds a synthetic shared-layer dictionary. Its canonicals live only in three new synthetic-terms documents (zh, en, it), and its variants occur nowhere in the corpus. 18 colloquial-term and no-answer term items measure it, four run configs pair terminology off and on, and both baselines are re-recorded with zero change on every pre-existing item. The plan also fixes a bug that kept `RAG_TERMINOLOGY` from ever reaching the RAG config outside tests.**

## Accomplishments

- **Documents and dictionary.** Each synthetic document has five chunks: four `term … holds the placeholder marker N` chunks and one code chunk. The dictionary maps one-token variants (`termalpha`, `vocealfa`, `卯辰巳`, …) to the canonicals, plus one identifier alias per language and one it→en translation pair. `validateEntries` reports no error for the corpus languages.
- **Harness seeding.** `prepareInProcessEval` seeds `loadFixtureTerminologySeed()` by default, in prechunked and ingest mode, single- and multi-tenant. A caller-built fixture gets the seed too, unless it already has the layer. The switch is ignored, so every "off" run executes on a database that holds a dictionary.
- **Golden items.** Per language: four answerable items, one identifier-alias item and one `no_answer` item asking with a variant. All are `synthetic_fixture` and approved. They were appended to `golden.jsonl` without touching any existing line. Splits come from `freeze_splits`: dev for en 001-003, 005; it 001-005, no_answer; zh 002, 003. Test for en 004 and no_answer; zh 001, 004, 005 and no_answer.
- **Run configs.** `v2-terminology-*` = `v2-default.json` env and overrides plus `RAG_TERMINOLOGY`. `v2-lexical-terminology-*` set `RAG_PIPELINE=v2`, `RAG_LEXICAL_SEARCH=true`, `RAG_REFUSAL_THRESHOLD=false`, `RAG_RERANKER=none`, `RAG_REFUSAL_FLOOR=similarity` and `RAG_TERMINOLOGY`. All four load through `loadRunConfig`/`parseRunConfig`.
- **Baselines.** Both recorded with `RAG_PIPELINE=legacy`, three runs each (the 06-39 procedure): `RAG_PIPELINE=legacy npm run eval:baseline`, and `rag_eval.baseline record --runs 3 --fixture-mode ingest`. The pre-change copies are in `eval/out/p4110-10/` (git-ignored).
  - Prechunked: 229 → 247 items. `jq` per-item diff over pre-existing ids: `true` (0 differences).
  - Ingest: 290 → 308 items. Per-item diff: `true` (0 differences).

## Bug fixed (Rule 1, blocking)

`readRagEnvInput()` in `src/lib/rag/deps.ts` never passed `RAG_TERMINOLOGY`, `RAG_TERMINOLOGY_DENSE` or `RAG_TERMINOLOGY_MINING` into `loadRagConfig`. As a result:
- Setting the switch in the environment (production, or a run config) left the stage `disabled`.
- Only tests that override `ragEnv` through `setRagDepsForTests` could turn it on, which is why the plan 05/07 tracers passed.

My first `v2-lexical-terminology-on` run showed `terminology: disabled` on all 247 traces. The fix reads the three switches from `process.env`, so an unset switch keeps the input `undefined`, exactly as before. After the fix, the stage is `ok` on all 247 traces.
