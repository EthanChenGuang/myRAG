# Phase 3.2 Plan 17: Ingestion fingerprint and settings classification Summary

**Every version the unified pipeline publishes now carries `documents.ingest_fingerprint` (sha256 of canonical JSON) and the parts it was built from in `metadata.ingest_fingerprint_parts`. Every `RAG_*` variable of the env manifest is classified once as ingestion, query or both, and CI fails when one is not.**

## What changed

- **Fingerprint builder** (`src/lib/rag/ingest/fingerprint.ts`). `buildIngestFingerprint(parts)` validates with the generated `IngestFingerprintPartsSchema` (strict, integers only), then hashes the canonical sorted-key JSON. Key order and the order the languages were typed in do not matter. Each listed part changes the hash. Scope tags, effective dates and floats are refused, not hashed.
- **Parts at publish.** `collectFingerprintParts(ctx)` reads the following, with no database read:
  - the parser and its version;
  - the processing profile id and version;
  - the OCR engine codes of the parser named in `parser_used`;
  - `legacy` as the chunking profile;
  - `LEXICAL_VERSION` and `EMBEDDING_TEXT_VERSION` (plan 29 extends the effective one);
  - the active embedding profile id, which is the first embedding target;
  - the pack versions used;
  - the four switches as their raw values.
- **Publish write.** The publish stage calls `ctx.writer.setFields(id, { ingest_fingerprint, metadata: { ingest_fingerprint_parts } })` before the hold-for-review call and before the publish call. The inline and queued paths use the same stage. An inline run still writes no ledger row. The legacy pipeline never runs the publish stage, so it writes neither field. A test asserts that no file outside `src/lib/rag/ingest/` names the column.
- **`expectedFingerprintFor(parts, proposed)`** is for plan 18. Proposed switch values replace the switch parts. A proposed `RAG_SUPPORTED_LANGUAGES` / `RAG_PRIMARY_LANGUAGE` recomputes the OCR codes and packs for the version's own parser and profile. Every other part stays as stored.
- **Classification.** `config/rag/settings-classification.json` has 148 entries sorted by name. It validates against Pydantic `SettingsClassification` (pytest). `getSettingsClassification()` validates it once with the generated Zod schema. `ingestionKeysOf(proposed)` returns the proposed ingestion-side keys with their mechanisms.
- **CI.** `scripts/ci/check-settings-classification.mjs` runs in the pr-smoke "RAG boundary check" step beside the language-literal check, and `check-workflows.py` requires it. It exits 1 in any of these cases:
  - a manifest `RAG_*` variable has no entry;
  - an entry is absent from the manifest;
  - an ingestion or both entry has no mechanism;
  - a query entry has a mechanism;
  - a side or mechanism is unknown;
  - a name repeats;
  - the entries are not sorted.

## Behaviour changes

- Unified-pipeline publish makes one more `rag_set_document_fields` call per version, before publishing. Documents gain `ingest_fingerprint` and one metadata key, `ingest_fingerprint_parts`. With every switch off nothing else changes: `defaults-equal-phase3` compares parser, doc type, status and chunks, and all of those are unchanged.
- `IngestState` gains `parserVersion`, written by `applyParseResult`. An inline run's `processing_state` therefore carries one more key. Queued runs keep the state in the ledger, so `processing_state` stays `{}`.
- No characterization snapshot records document metadata, so none was regenerated.

## Judgement calls in the classification (D-09)

- **D-47's eighteen** are classified as the table says. The ten ingestion-side variables and their mechanisms:
  - `RAG_SUPPORTED_LANGUAGES`: reparse
  - `RAG_LANGUAGE_AWARE_INGEST`, `RAG_TABLE_HEADER_REPEAT` and `RAG_TABLE_ROW_SERIALIZATION`: rechunk, because D-11 delivers every chunk-level change through a new chunking profile
  - `RAG_CAPTION_LANGUAGE`: recaption
  - `RAG_DOC_TRANSLATION` and `RAG_DOC_TRANSLATION_MODEL`: retranslate
  - `RAG_HIDDEN_TEXT_CHECK` and `RAG_INGEST_LINK_CHECK`: rescan
  - `RAG_OUTPUT_LINK_ALLOWLIST`: both, rescan

  `rescan` is never an automatic rebuild (`AUTOMATIC_REBUILD_MECHANISMS` in the contracts).
- **Reparse:**
  - `RAG_INGEST_PIPELINE`, `RAG_PARSER`, `RAG_PARSER_ALLOW_CLOUD`, `RAG_PARSE_ROUTING`, `RAG_PARSE_ESCALATION`, `RAG_PARSE_PREMIUM_PAGE_BUDGET`, `RAG_PARSE_PREMIUM_MAX_PAGES_PER_DOC`, `RAG_PARSE_VLM_DETECT` and `RAG_PARSE_VLM_MODEL`: they decide which parser or tier produced the text.
  - `RAG_DOC_TYPE_LLM_DETECT`: the doc type selects the profile.
  - `RAG_INVOICE_LLM_EXTRACT`: extraction runs inside an ingest.
  - `RAG_PDF_IMAGE_CHUNKS`: the pictures come from the parse.
- **Rescan:** `RAG_INJECTION_SCAN`. It is an ingest-time scan like the two Phase 3.2 checks.
- **Both, reembed:** `RAG_EMBEDDING_PROFILES` and `RAG_DOMAIN_EMBEDDINGS`. They are read at ingest, where they pick the embedding targets, and at query time.
- **Both, retranslate:** `RAG_QUERY_LLM_MODEL`. It is the document translation model whenever `RAG_DOC_TRANSLATION_MODEL` is empty.
- **Query-side operational knobs.** These change no stored output, so a change takes effect on save:
  - `RAG_PARSE_PROGRESSIVE` (it only orders provisional versions; the final version is the routed one)
  - `RAG_PARSE_POLL_BUDGET_MS`, `RAG_INGEST_ASYNC` and `RAG_INGEST_WORKER_CONCURRENCY`
  - `RAG_INGEST_JOB_RETENTION_DAYS`, `RAG_INGEST_MAINTENANCE` and `RAG_INGEST_MAINTENANCE_INTERVAL_SECONDS`
  - `RAG_EMBED_BATCH_MODE` (same vectors)
  - `RAG_QWEN_EMBED_FALLBACK` (same model through another host)
  - `RAG_SIDECAR_URL` and `RAG_SIDECAR_SECRET`
- **Query, as the plan says:**
  - `RAG_PIPELINE`. Under v2, ingest also dual-writes chunking profiles, but `npm run rag:rechunk` repairs those, and the fingerprint does not record them.
  - `RAG_LEXICAL_SEARCH` and `RAG_PARENT_CHILD`.
  - `RAG_EXACT_ID_LOOKUP`, which is read only by retrieval.
- **Everything else is query**: retrieval, rerank, refusal, context, cache, query layer, citations, groundedness, security checks at answer time, eval, voice and embed.

## Fingerprint part decisions

- **`parser_version`:**
  - Normally the in-memory value from this run's parse.
  - On a resumed run, the runner leaves `'stored'` in memory, so the value comes from the new `IngestState.parserVersion`.
  - On an admin type change that reuses an earlier parse, the reused parser's version.
  - Otherwise `unknown`.

  The queued DB test asserts that the part equals `documents.parser_version`.
- **Pack versions** cover only the languages behind the OCR codes, plus every configured language when language-aware ingest is on. With that rule, dropping `en` from `zh,en,it` leaves a Docling document's fingerprint unchanged and changes a LlamaParse document's, which is what research F-4 and LANG-04 ask for.
