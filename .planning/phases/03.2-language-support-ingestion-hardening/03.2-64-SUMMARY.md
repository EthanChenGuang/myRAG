# Phase 3.2 Plan 64: App upload controls (tags, "Replaces…", awaiting approval) Summary

## Behaviour changes

- **pending_review**: the badge shows "Awaiting approval" (zh 等待批准, it In attesa di approvazione, other locales English) with the existing pending (sky) tone and a static `Hourglass` (`aria-hidden`, no spin). Its `title` is the label and the hint ("An admin must approve this upload before it can be searched."). The server's `reason` is never shown for this status, and nothing names an approver or a reason for rejection. It is terminal in `use-ingest-job-status` (TERMINAL_STATUSES) and in `pollIngestUntilTerminal` (doc-type-picker), so polling stops after the first answer. Before this, a held job would have been polled for 10 minutes and then marked as stalled.
- Rows awaiting approval settle as present (`settleQueuedRow`), and `mergeRefreshedDocuments` keeps them, both queued (job id) and inline (no job id; the inline/poll path now attaches `ingest: { status: 'pending_review' }`). The status cell renders `IngestStatusBadge` when a row has an `ingest` state even without a job id. That case only arises for pending_review. A held upload does not call `onProcessingComplete` or `onProcessingError`.
- **Upload refusals**: 503 `upload_approval_requires_unified_pipeline`, 503 `languages_not_configured` and 400 `unknown_scope_value` show the UI-SPEC 8.2 sentences on the failed row, in en/zh/it. Every other error keeps today's text, including the timeout sentence. On `unknown_scope_value` the picker-defaults answer is fetched again and the sentence is shown at the tag picker (`role="alert"`) until a tag changes.
- **Tag picker** (`tags.enabled` and at least one active value): an outline `h-8 text-xs` trigger with a `Tags` icon, reading "Tags" or "Tags: {n}". Its `title` lists the selected labels, and its accessible name is "{visible text}, Choose tags for {file}". The menu is `DropdownMenuContent align="end"` with `w-64 max-h-72 overflow-y-auto overscroll-contain`, one labelled group per dimension (dimension name in words), `DropdownMenuCheckboxItem`s that keep the menu open, wrapping labels, and "Clear tags" when something is selected. The selection is sent as one `scopes` field per `dimension:value`.
- **"Replaces…"** (`replaces.enabled`): an outline trigger with a `Replace` icon, plus an sr-only "(for {file})". It opens a `Dialog` with these parts:
  - title "Which document does {file} replace?", with the file name as a truncated span carrying `title`
  - a description: `replaces.admin` when `confirmedAtOnce`, else `replaces.member`
  - a labelled search `Input` that gets focus on open
  - a `ScrollArea` (`max-h-72`) holding a `role="radiogroup"` of `role="radio"` buttons with roving tabindex. Up, Down, Home and End move focus; Space or Enter selects; Escape closes and Radix returns focus to the trigger.
  - "Close chooser" (changes nothing) and "Choose document" (primary, disabled until a row is checked)

  The list holds the dashboard's loaded documents that are `ready` and not held. An empty workspace shows the empty sentence; a search with no result shows the no-match sentence with the query as text. After a choice, the row's left column shows "Replaces: {name}" (truncated, with `title`) and a ghost remove button whose sr-only name is "Clear replacement: {name}". The choice is sent as `replaces_document_id`.
- **Off state**: with tags and "Replaces…" not enabled, `UploadQueueRow` renders exactly the pre-plan markup (snapshot `tests/ui/__snapshots__/upload-queue-row.test.ts.snap` plus an exact-string test), and `buildChatUploadFormData` adds no new field. When the defaults answer has `enabled: false` (legacy pipeline), both blocks are treated as off.
- All file names, labels and queries are React text children; injection cases are in the component tests. No `dangerouslySetInnerHTML`.

## Deviations

1. **Extra files.** Plan 64 lists `src/components/ui/upload-queue-row.tsx` and `upload-queue-config.ts` nowhere. They exist so the queue row can be rendered in a test and the off state proven against a pre-plan snapshot. The row is otherwise inline in a 1900-line component. `ingest-document-rows.ts` also changed, so that a pending_review row settles as present and survives refresh. Without that change it would have been dropped or failed.
2. **The `pending_review` badge `title`** carries the hint, not `(reason)`, so a server reason can never reach the uploader (T-03.2-643).
3. **Replace choice display.** UI-SPEC 6.12.2 places the chosen file name on a "Replaces: {name}" line in the row's left column, with the remove button there. Plan task 2 says "on the trigger". I followed the UI-SPEC; the trigger stays "Replaces…".
4. **The confirm-at-once statement** sits in the `DialogDescription`, as UI-SPEC 6.12.2 says, rather than in the footer as plan task 2 words it.
5. **unknown_scope_value.** The dashboard uploads every queued file and then clears the queue. The sentence therefore appears on the failed row and at the tag picker of the next queue, until a tag changes. The vocabulary is reloaded.
6. **Lint.** `npm run lint` cannot exit clean on this repo: `.eslintignore` is ignored by ESLint 9, so it lints the whole tree and reports 29684 pre-existing problems. I compared counts before and after the change instead, and linted the touched files with `--quiet`.
7. **Tests.** The repo has no DOM test environment (vitest `environment: 'node'`, no jsdom or testing-library), so the tests use `renderToStaticMarkup` plus pure helpers. Keyboard behaviour is tested through `nextRovingIndex` and `replacesChooserKeyAction`, and "menu stays open" through `keepScopeTagMenuOpen`. Real focus movement and Escape-to-trigger are left to the human check.

- The client proposes tags and the replaced document only. The server validates both (03.2-43, 03.2-45); T-03.2-642 is transferred.
