# Phase 3.2 Plan 29: Table row serialization Summary

**With `RAG_TABLE_ROW_SERIALIZATION=true` a table chunk's embedding text and `lexical_text` end with one `column=value` line per data row; `content` keeps the Markdown table, `LEXICAL_VERSION` stays 2, and with the switch off every index text is byte-identical.**

## Accomplishments

- `serializeTableRows` turns each data row of a headed Markdown table into `<column>=<value>` pairs joined with the block language's list separator. Example zh line from the fixture: `地块=己区，测量批次=第02批，首测株高（厘米）=117.6，复测株高（厘米）=43.3，长势=良好`.
- `enrich` decides per chunk (table kind, switch on, block language) and builds the serialized `lexical_text`. `embed` appends the same lines to the embedding text and stamps those rows with the effective version 1001.
- `collectFingerprintParts` reports `effectiveEmbeddingTextVersion`, and `expectedFingerprintFor` moves it with a proposed switch value.
- `rag:relex` serializes in its version pass and runs a table pass (migration 0815, `rag_relex_table_candidates`) that rewrites table chunks whose stored text does not match the switch. The comment in `relex/run.ts` explains why text can differ under one `LEXICAL_VERSION`. The dry run counts these chunks too.

## Deviations from Plan

1. **Migration added (0815).** The plan expected `relex/run.ts` to change its selection. `rag_relex_candidates` selects by `lexical_version` only and returns no stored text, so no client-side change can find a table chunk whose text is stale under the current version. A new read-only, service-role-only function was the smallest secure fix. Changing the existing function's signature would have needed `DROP FUNCTION` and broken the 0402/0425 catalog tests.
2. **Files outside the plan's list:** `src/lib/rag/lexical/chunk-text.ts` (the lexical builder itself takes the separator, so ingest, relex and tests share one function), `stages/embed-write.ts` (the only place the ingest embedding text is built), `ingest/types.ts` (in-memory `table_row_separator` on the draft), `relex/cli.ts` (passes the switch), and the fixture snapshot JSON.
3. **Existing fingerprint test adjusted.** `a proposed switch value changes the matching part only` used `RAG_TABLE_ROW_SERIALIZATION`; that switch now also moves `embedding_text_version` by design. The test now uses `RAG_TABLE_HEADER_REPEAT`, and a new test covers the row switch moving both parts.
4. **enrich order.** Language detection now runs before the lexical loop so the separator can use the chunk and document language. The RPC call order is unchanged, since the loop makes no RPC.
5. **Test fixtures use `financial_report@1`.** It repeats table headers. Under `general@1` the continued table chunks have no header (plan 27's `always` is not on trunk yet), so they produce no lines. The off snapshot covers both profiles.

## Decisions for STATE

- D-21 effective `embedding_text_version` = base + 1000 while `RAG_TABLE_ROW_SERIALIZATION` is on; base stays `EMBEDDING_TEXT_VERSION`.
- Row serialization needs the table header inside the chunk; it does not carry headers across chunks.
- `rag:relex` always applies the configured `RAG_TABLE_ROW_SERIALIZATION`; migration 0815 must be applied before the CLI runs with the switch on.

## Operator actions

- Apply `supabase/migrations/0815_relex_table_candidates.sql` before running `npm run rag:relex` with `RAG_TABLE_ROW_SERIALIZATION=true`. With the switch off, relex runs without it and logs that the table pass was skipped.
- Turning the switch on for existing documents: `npm run rag:relex` updates the lexical leg in place. The dense leg of existing chunks needs re-ingest (see Deferred).

## Deferred

- **rag:rechunk / chunking-profile children** (`profile-chunks.ts`) and **rag:reembed / embedding backfill** do not yet serialize. Rechunk documents and re-embed chunks do not carry the document or chunk language (and re-embed chunks carry no embedding-text version), so those RPC rows need a column first. Until then D-21's "existing documents via rechunk" path and a re-embed into a new profile produce plain text for table chunks. The stamped version 1001 on serialized legacy rows lets a later re-embed tell which rows need the lines.
- Serialization of continued table chunks without a header waits on plan 27 (`RAG_TABLE_HEADER_REPEAT=always`, carry-forward).
- Whether the switch ships on is plan 32's `table_split`/`table` slice decision (D-21).
