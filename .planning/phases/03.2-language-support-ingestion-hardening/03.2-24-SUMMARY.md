# Phase 3.2 Plan 24: Legacy routes follow the configured languages (D-16)

**The two legacy LlamaParse call sites stop hard-coding `language: "en"` once languages are configured, and with `RAG_LANGUAGE_AWARE_INGEST=on` no knowledge-base upload reaches the legacy splitter. With the languages unset and the switch off, both files behave byte for byte as before.**

## Behaviour changes

- **Languages unset, switch off (default):** none. Both multipart bodies equal the recorded ones; the route and `processDocument` run as today; `getLanguageSettings()` is not called (trap test).
- **Languages configured (any ingest pipeline):** `src/lib/document-processor.ts` (`/api/v1/parsing/upload`) and `src/app/api/process-document/route.ts` (`/api/parsing/upload`, knowledge-base and temporary uploads) send `output_config={"result_type":"markdown"}` followed by a `language` field, e.g. `it,ch_sim` for `zh,it` with primary `it`, `en,ch_sim,it` for the CI pin. If no configured language has a LlamaParse code for the primary, the body stays today's.
- **`RAG_LANGUAGE_AWARE_INGEST=on`, `RAG_INGEST_PIPELINE=legacy`:**
  - process-document: a knowledge-base upload goes to the unified entry (`ingest()`, or `submitIngest()` when async is on — the same choice the unified branch makes); with the languages unset it answers `503 {"error":"languages_not_configured"}` and writes nothing. Temporary attachments keep today's LlamaParse call.
  - `processDocument` throws `LanguageAwareIngestError` (status 503, `code`/`reason` `language_aware_ingest_requires_unified_pipeline`, or `languages_not_configured` without languages) before any parse or temp file.
  - `scraperPipeline()` and `nangoPipeline()` return `unified` when the switch is on and languages are configured, so scrapes and syncs use their existing unified branches (scope from the route or the connection owner). Without languages they stay `legacy` and `processDocument` refuses loudly.
  - The unified run reads the language settings for its OCR request (`ingestLanguageSettings` now also reads with the switch on), so the parse request carries the configured OCR languages as it does under `unified`.

## Deviations

1. **[Rule 2] Files beyond `files_modified`:** `routing/language-aware-routing.ts` (new helper), `effective-settings.ts` (`legacyLlamaparseLanguages`, shared `llamaparseCodes`, `ingestLanguageSettings`), `lang/settings.ts` (`languageVariablesUnset`), `rag/index.ts` (exports), `scrapers/ingest-switch.ts` and `nango/document-adapter.ts` (switches). Without the adapter switches, the `processDocument` guard would make Nango and scraper ingestion fail under the switch; with them they use their tested unified branches.
2. **`getLanguageSettings().configured` is reached through a presence check.** The plan says to branch on it directly; doing so would read `settings.ts` on the default legacy path and break the D-02 trap. `languageVariablesUnset()` short-circuits only while both variables are blank; otherwise the reader decides.
3. **`submitIngest()` vs `ingest()`:** the language-aware branch reuses `uploadThroughIngest`, which calls `submitIngest()` when `RAG_INGEST_ASYNC=on` and `ingest()` otherwise (under the legacy pipeline async is forced off by queue-config). The test accepts either unified entry and checks the legacy writer records zero calls.
4. **Not rerouted:** `src/app/api/upload/route.ts` (images through `processImageDocument`, no legacy splitter) and `src/app/api/ai-to-rag/route.ts` (own writer for saved answers). D-16 names only the two files of this plan; both stay as today under the switch.
5. Under the legacy pipeline with the switch on, stages gated on `pipeline === 'unified'` (admin doc-type defaults, `assertProviderFits`) keep their legacy-pipeline behaviour inside the unified run.
