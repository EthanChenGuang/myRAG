# Phase 3.2 Plan 28: Effective header flag and header carry-forward on the Docling path

**The sidecar now uses the effective header flag from the job snapshot in the tiered Docling chunk request and in the chunker part of the merged-document version string. With `carry_table_header`, a table that continues on the next page without its own header takes the previous table's header before chunking. The carry runs on a copy, so the stored `docling.json` stays the original document. With every flag at its default, every key, version string, request and recorded chunk is byte-identical to before.**

## Behaviour

- **Defaults (snapshot `repeat_table_header_effective=null`, `carry_table_header=false`).**
  - The tiered chunk request carries the profile's flag.
  - The merged version string is `merged-v1/<docling>/mt<max_tokens>-rh<profile flag>`, as on trunk.
  - `to_parse_result` chunks the document it is given.
  - Chunks have no `table_header_carried` key. The recordings test re-runs the adapter and matches every committed file.
- **Effective flag forced (`RAG_TABLE_HEADER_REPEAT=always` in the app, frozen in the snapshot).**
  - On the four profiles whose own flag is false, the request asks HybridChunker to repeat headers. The version string changes to `-rh1`.
  - On `financial_report` and `invoice_receipt` the flag part is unchanged.
  - The per-range Docling conversion entries keep their version and options hash, so a cached conversion is reused and only the merged entry is rebuilt.
- **Carry (`carry_table_header=true`, set together with `always`).**
  - The version string gets `-ch1`.
  - `to_parse_result` chunks a deep copy in which each continuation table starts with the carried header row, flagged `column_header`.
  - `docling.json`, the Markdown and the pictures come from the original document.
  - Chunks holding an item of a carried table report `table_header_carried: true`. `fromDocling` in the app copies it into `metadata.table_header_carried`.
- **Inline path.** `POST /v1/parse/jobs` already received the effective flag and `carry_table_header` from the app (plan 21). It now acts on `carry_table_header`.

## Deviations

1. **[Rule 1] Fake ledger cache key.** `tests/ingest_fakes.py` keyed parse-cache rows by `(tenant, sha, parser, options_hash)`. The SQL key and `rag_parse_cache_lookup` also include `parser_version`. With the old fake, a forced-flag job found the default merged entry, so the reuse test could not tell the two apart. The fake now keys by `parser_version` too. The full sidecar suite passed with the change before any production code changed.
2. **[Rule 2] `-ch1` in the chunker key.** The plan names only the effective header flag for the key (D-22). Carry changes chunks on profiles that already repeat headers. Without its own key part, a cached merged entry would serve stale chunks after the switch (T-03.2-281). The part is added only when carry is on, so default keys are unchanged.
3. **[Rule 2] Contract and app changes outside files_modified.**
   - `ParseChunk.table_header_carried` was added to `contracts/ingest.py`, with regenerated schemas and Zod, so carried chunks can report D-20's `metadata.table_header_carried`.
   - The app's `fromDocling` (`src/lib/rag/ingest/chunkers/index.ts`) copies it into chunk metadata.
   - The key is omitted while unset, so contract samples and recordings did not change.
   - An older app parses sidecar results with `.strict()`. It never sends `carry_table_header`, so it never receives the key. Deploy the sidecar first, as the plan says.
4. **Header detection for the previous table.** Docling's Markdown always promotes row 0 to a header. The rule therefore takes the previous table's header from row 0 only when that row is flagged `column_header` or is header-like. A first table without a header carries nothing, which matches TS.

## Known limits

- Language fields (`language_aware`, `languages`, `primary_language`) are still not forwarded from the snapshot in the tiered `_parse_request`, and they are not in the merged version string. That is outside this plan, so queued tiered jobs chunk without the language rule. Reported for a follow-up.
- The same header-likeness limits as plan 27 apply: a mostly numeric real header row is not header-like, and an all-text unique first data row reads as a header.
- A continuation is detected only when the previous table is the item right before it in reading order. A page footer that Docling puts in the body layer between the two tables stops the carry. Furniture-layer headers and footers are skipped.
