# Phase 03.2 Plan 37: Hidden-text report in scan_injection (inline path) Summary

**On the inline path, hidden text that the sidecar finds in a PDF is removed before chunking and stays removed after a release, a re-chunk or a type change. The document is quarantined with the spans as evidence, formats with no checker are recorded `not_checked`, and a checker that cannot answer blocks publishing under quarantine.**

## Accomplishments

- `src/lib/rag/security/hidden-text.ts` holds the sidecar client. It sends the stored original as multipart (`file` + `HiddenTextRequest` as `request`, named `original.<ext>`) with the shared secret and a timeout. Every answer is validated with the generated `HiddenTextReport` schema and a consistency check. The client never throws and has a test seam. The module also has the span remover and the write-time assertion.
- The `hidden_text` check in `scan_injection` asks for the report for PDF and Word originals. On a resumed run with no upload it reads the stored original. It merges the report with the zero-width count.
  - Under `quarantine` it strips zero-width characters and removes the spans from the parse text and from every text field of the parser's chunks. It saves the state, rewrites `parse.md` and `chunks.json`, sets `metadata.hidden_text_sanitized`, and quarantines the document with one `hidden_text` reason. That reason holds the spans, the zero-width code points and the `unlocated` count.
  - `hidden_text_check` is written on every outcome.
- The embed stage, and the profile dual-write, refuse any chunk that still contains a removed span. The check runs before any embedding call (`hidden_span_in_chunk`).
- For a sanitized version, the doc-type change reuses only the sanitized parse output. It never runs a parser, never copies `docling.json` and never re-parses the original.
- `tests/helpers/fake-sidecar.ts` now serves `/v1/hidden-text`. It answers from the plan 35 manifest, checks that `sha256` and `size_bytes` match, and accepts queued error, report or delay specs.

- With `flag` or `quarantine`, documents now get `hidden_text_check`. Text, markdown, HTML, presentations, spreadsheets and images are `not_checked`. Plan 34 reported text documents with no zero-width characters as `clean`; they are now `not_checked`, as the D-34 prohibition requires.
- `quarantine` with a PDF needs a reachable sidecar: without one the run fails with `hidden_text_checker_unavailable` (fail closed, D-34). Plan 38 refuses to save `quarantine` without a sidecar URL and secret.

## Deviations from Plan

1. **[Rule 3] `src/lib/rag/ingest/types.ts`, `status.ts`, `stages/parse.ts`** (outside `files_modified`). These add the `hiddenText` state slice and its validated read-back, `TypeChangeState.sanitizedParse`, and the parse-stage guard. The guard skips `docling.json`, blocks a re-parse after a doc-type refinement, and fails with `sanitized_parse_unavailable` instead of parsing the original.
2. **`src/lib/rag/ingest/rechunk/run.ts` not modified.** It reads only `parse.md`, which is now the sanitized copy. The e2e test runs a real `runRechunk` profile build and checks the children.
3. **"removes each span once"** is read as idempotent. A long span is removed at every occurrence, because the write-time assertion would otherwise refuse a visible copy. A short span is removed once.
4. **Assertion threshold.** The assertion uses a code constant (`HIDDEN_SPAN_MIN_CHARS = 12`), not a new rules key, so the Pydantic contract and `gen:schemas` are untouched.
5. **Retry idempotency** is proven in a unit test (saved state plus sanitized text gives the same reasons and no second call) and in the resume path (`reapplyHiddenTextRemoval` now also removes the saved spans). There is no e2e crash injection.
6. **"fails retryably"** on the inline path means the version is marked failed with `hidden_text_checker_unavailable`, the same as `injection_scan_unavailable` today. Nothing is published and no chunk is written. A re-upload of the same file runs again; this is tested. Ledger retry classification is plan 38.
