# Phase 03.2 Plan 32: table_split metrics, answer check and gate Summary

**The eval now scores `table_split` items with row Recall@5/@10, `header_in_context_rate` and a deterministic answer check, and gates `category:table_split` in CI. The re-recorded ingest baseline equals the previous one on every slice and item. Under `RAG_TABLE_HEADER_REPEAT=always`, `header_in_context_rate` is 1.0 in all six processing profiles.**

## Accomplishments

- `table_split_report()` builds a `TableSplitReport` for every run whose golden set holds `table_split` items. It has an overall slice, one slice per language (zh, en, it, always present), and one row per item sorted by language then id. Each slice carries `status` (`gated` when at least one item counts in the gate, else `report_only`), `items`, `counting_items`, `row_recall_at_5`, `row_recall_at_10`, `header_in_context_rate` and `answer_correct_rate`. Rates are exact fractions (`fractions.Fraction`). An n of 0 has no value. The Markdown shows them with 4 decimals.
- `score_table_answer()` compares numbers as decimals and never as substrings. Text values are compared after folding. An answer with the gold value and a distractor is `ambiguous`, and ambiguous does not count as correct.
- `EvalReport.table_split` is omitted when unset, so reports of runs without `table_split` items keep their exact JSON (test `test_report_without_table_split_items_has_no_table_split_key`).
- `category:table_split` is gated. The ingest baseline was re-recorded with the recorder plan 30 used.
- The always check runs the fixture ingest under each processing profile with `--table-split-doc-type <doc_type> --table-header-repeat always`. It needed three harness changes:
  1. The switch is layered over the build's fixed ingest env (`ingestEnv`). The pinned eval env and the run-config overlay do not reach the build.
  2. The long tables can be loaded with any doc type.
  3. The fake sidecar serves a recording of the always request.

## Deviations from Plan

1. **[Rule 3, blocking] Header-repeat recordings and a fake-sidecar variant.**
   - **Why:** the must-have "header_in_context_rate is 1.0 with always in every processing profile" could not hold on the fixture. For the four Docling-kind profiles the app uses the sidecar's chunks unchanged, and the fake sidecar answered every request with the recording made under profile mode.
   - **What changed:**
     - `record_parse_results.py` also records the always request for the six long-table fixtures, from the same Docling document and the same `to_parse_result`. The existing 39 recordings are byte-identical.
     - The fake sidecar serves that recording when the request has `repeat_table_header` and `carry_table_header` true.
     - A sidecar test checks that the variants repeat the header in every table chunk and keep the Markdown.
   - **Naming:** the files are named `*.parse-header-repeat.json` because the profile-mode chunk snapshot tests (`tests/rag/table-header-repeat.test.ts`, `tests/rag/chunk-sentences.test.ts`) glob `*.parse.json`.
2. **[Rule 3] Harness check flags.**
   - `--table-split-doc-type` and `--table-header-repeat` (run-smoke → runEval → prepareInProcessEval → createFixtureDatabase → buildIngestFixtureDatabase → loadTableSplitTenants / installIngestFakes).
   - Both turn the gate off and enter the corpus hash. Without them every call is unchanged: the build's `processEnv` and ingest env are the same objects as before.
3. **[Rule 2] Contract change.** The block is `EvalReport.table_split` with three new models in `rag-sidecar/src/rag_sidecar/contracts/report.py`. The schema and the generated Zod were regenerated (`npm run gen:schemas`, no drift afterwards).
4. **Pins outside files_modified.**
   - `eval/tests/test_gate.py`: the gated prefixes.
   - `eval/tests/test_fixture_pii.py`: the ingest file count, 48 → 54.
   - `eval/tests/test_ingest_fixtures.py`: the manifest names the variant files.
5. **The re-baseline test lives in `eval/tests/test_metrics.py`** as the plan says. It compares the current file with a history copy of the previous one. That copy is the file `git show HEAD:` printed; nothing was edited by hand.
6. **The always-mode test runs the six builds one after another.** Six concurrent builds next to the rag-db suite failed one stage (`file_hash_dedup_failed`) on its time budget. Sequentially it takes about 2.5 minutes.
