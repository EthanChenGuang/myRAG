# Phase 03.2 Plan 30: table_split golden items on isolated tenants Summary

**Fifteen `table_split` items in zh, en and it. Their six long-table documents load into isolated fixture tenants, so the 210 items the ingest mode already scored keep the same chunks, the same order and the same metrics.**

## Accomplishments

- `eval/harness/table-split.mts` loads the six long-table documents through the unified `ingest()` into two isolated fixture databases. The plain tables go in one and the page-continued tables in the other. Both are served by the same fake edge (`FakeEdge.useDatabase`) only while a `table_split` item runs. In multi-tenant mode the documents belong to a dedicated fixture user, so the request scope is that tenant's key.
- `ingest-mode.mts` gains `partitionIngestModeItems`. `runEval` runs the other items first and unchanged, then each `table_split` item against its tenant, through the same `/api/internal/rag/run` route.
- The prechunked mode, `--base-url` runs and queued `--routing` builds leave `table_split` items out, and scoring stays consistent with that.
- 15 golden lines (5 per language). For each language: one item on the spec's target row (en 54, zh 51, it 48), one on the last row (59), one on the page-continued variant, and the three asked columns (first value, second value, category). Every answer row has index 30 or more. Each item has two evidence quotes, the row and the header, built from `specs.long_table_rows()`. Each quote matches the fixture text exactly once and matches a recorded parse chunk. The 10 zh and it items carry `native_review {origin: llm_drafted, status: pending}`. The en items carry none, and all keep `provenance: synthetic_fixture`.
- The split manifest gains only the 15 new ids, each assigned by the frozen rule (10 dev, 5 test).

## Deviations from Plan

1. **[Rule 3, blocking] The ingest baseline was re-recorded in this plan.** Plan 32 owns the re-baseline. But the new items change `golden_sha256`, and the tenant documents change `corpus_sha256`, so the ingest gate refused. This follows the 05.1-17 precedent. The old baseline was saved to `eval/out/03.2-30-pre/`. A run against it had 210 of 210 old items identical per metric. Then `uv run --directory eval python -m rag_eval.baseline record --runs 3 --fixture-mode ingest` re-recorded it with defaults (no `.env.local`) and zero spread, and every old item's values in the new file equal the old file's. Plan 32 still adds `category:table_split` to the gated slices and re-records again. Its "zero paired differences on old items" check runs against this baseline.
2. **Files beyond `files_modified`.** `eval/harness/run-eval.mts`, `run-smoke.mts`, `pglite-supabase.mts`, `fake-edge.mts` (`useDatabase`) and `tests/helpers/fake-sidecar.ts` (knows the `long_table_fixtures` recordings) carry the routing and loading. `tests/rag-db/table-split-multi-tenant.test.mts` is a second test file, because one process can hold one build. Four pins learned about the new category: `eval/tests/test_fixture_coverage.py` (split manifest ids), `rag-sidecar/tests/test_golden_contract.py` (table_split lines carry the new keys; every other line keeps the pre-Phase-3.2 key set), `tests/rag-db/ingest-mode-routing.test.mts` (added ids) and `eval/tests/test_ingest_golden.py`'s existing tests (fixture text, old-item hash, split rule).
3. **The isolation test's run without the documents is a child `run-smoke` process.** App modules freeze `@/lib/env` and the edge URL at first import, so a second build in the same process cannot serve the route. Chunk ids are minted per build, so the comparison uses document name, content hash, similarity and final score in order.
4. **Six documents, two tenants.** The plan says "a dedicated fixture tenant key". The plain and page-continued tables share their rows, so they are split into two tenants, each with that key.
