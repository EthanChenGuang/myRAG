## Behaviour

- **Unchanged with today's registry (zh, en, it):** `retrievalFilters.languages` accepts the same codes and refuses an unknown code with the same path and message (`Invalid enum value. Expected 'zh' | 'en' | 'it', received 'xx'`); label strings and English fallback are unchanged; eval defaults and CLI choices are unchanged; injection-rule counts in the config server keep the keys `zh, en, it, any`.
- **Changed:**
  - `DraftConfig.languages` refuses an unknown code with the registry type's message (`unknown language code 'xx'; expected one of zh, en, it`) instead of Pydantic's literal message. It is still refused, and the JSON Schema enum is unchanged.
  - The chunking-profiles report's slice select shows the language group only after `GET /api/config/languages` answers. If the request fails, the language group is left out (it shows no empty optgroup) and the next refresh tries again. Empty slice groups are now skipped in general. This came from the web-design-guidelines review.

## Tests that failed before the fix

- `tests/rag/language-literal-conversions.test.ts > takes its accepted codes from the language registry`: on the old code, a registry of zh and en still accepted `it` (`expected true to be false`).
- `tests/ui/config-chunking-panel.test.ts > shows the language slices only once the config languages answer has arrived`: I checked it by mutation. With the re-render after the answer removed, the test fails.

## Deviations

1. **`Language` export added to `src/lib/rag/lang/registry.ts`.** That file is not in files_modified. The plan names "the generated Language type", but the generated Zod has no standalone `Language` export, only the enum inside `LanguageSettingsSchema`. I derived the type from that enum in one place so that regeneration still drives it.
2. **`tests/ui/config-chunking-panel.test.ts` rule test T-04-77.** The old version of this test failed on any bare `fetch(` and on any `/api/` path other than the chunking-profiles routes. The plan requires the panel to call the config server's `/api/config/languages`. I tightened the test instead of deleting it: exactly one bare `fetch(` is allowed (the injectable `languagesFetcher` default), and the only extra path allowed is `/api/config/languages`. Every app admin route still goes through ragFetch.
3. **Remaining allow-list entries.** Besides the Phase 5.2 (LANG-09) and Phase 6.2 (LANG-08) entries, two entries added by other merged plans remain: `src/lib/rag/embeddings/catalog.ts` (owner "Phase 3.1.1") and `src/lib/rag/generation/groundedness.ts` (owner "Phase 5"). These are not files of this phase and their owner fields name no requirement id. I left them as they are. The plan's truth "remaining entries are owned by Phase 5.2 or Phase 6.2" holds for every entry except these two.
5. **`export type { Language }` added to `src/lib/rag/index.ts`.** The first version imported the type from `@/lib/rag/lang/registry` in the two components, and check-rag-boundary flagged those as deep imports. The import is type-only, so nothing reaches the client bundle.
4. **Empty optgroups.** `renderSliceSelect` now skips empty slice groups (the web-design-guidelines empty-state fix). This affects the question-kind group too when a report has no kinds.
