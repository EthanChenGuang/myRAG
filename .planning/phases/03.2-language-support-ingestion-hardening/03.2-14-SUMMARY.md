# Phase 3.2 Plan 14: Upload approval at identify and publish Summary

**With RAG_UPLOAD_APPROVAL on, a non-admin upload is processed completely and held as pending_review on both the inline and the queued path; with it off nothing changes.**

## Accomplishments
- `decideUploadApproval` (pure) and `resolveUploadApproval` (asks `rag_upload_exemptions_for` and, under `members`, `rag_is_tenant_admin` on the admin client with the scope's tenant key only). The decision is made in `identify`, which runs for `ingest()` and for `enqueueIngest()` through `runEnqueueStages`, so nothing depends on `submitIngest()` (D-56, F-7).
- `publish`: a required decision calls `rag_hold_document_for_review` and returns `pending_review` without calling the publish function. A resumed publish of an already held version reads the row (`not_holdable` handled). The writer accepts the guard outcomes `pending_review` and `held` (before, they would have thrown `bad_response`).
- Queued path: the snapshot carries `approval` (only when required) and `hold_publish` (backfill only); `applySnapshotDecisions` lays them over the run state on every advance slice; `pending_review` is terminal in `TERMINAL_JOB_STATUSES` and in the sidecar's `TERMINAL_SUCCESS`, and a replay at the publish position closes it.
- Batch hold: `metadata.publish_hold.batch_id` is written before publish; the guard returns `held`; the job ends `ready`; the previous version stays current.
- `afterPublish` seam with per-hook timeouts and id-only `[Ingest]` logs; started (not awaited) only after outcome `published`.
- Every write path passes the verified uploader: process-document and upload (session user), ai-to-rag (session user), scrape and crawl (session user through the adapter), Nango (connection owner).

- With `members` or `all`: as described above. A held document is in no retrieval result (legacy and v2 asserted), so it never reaches the semantic cache.

## Deviations
1. **[Rule 2] `IngestInput.uploaderId` and seven caller files** (process-document, upload, ai-to-rag, scrape, crawl, scraper-adapter, nango document-adapter), outside `files_modified`: a single-tenant scope carries no user, so without it every single-tenant upload would be `unknown_uploader` and `admin_users` could never be recognised. A scoped user always wins over it, so a multi-tenant caller cannot claim another user.
2. **[Rule 3] Also outside `files_modified`:** `approval/resolve.ts` (lookups kept out of the pure function), `writer.ts` (the RPC calls and the new publish outcomes), `runner.ts` (final state recorded for `pending_review`), `status.ts` (restore `approval`/`publishHold`; settled `pending_review`), `callbacks/common.ts` (terminal set), `enqueue.ts` (passes the decision and `holdPublish` to the snapshot), `tests/rag/ingest/settings-snapshot.test.ts`, `rag-sidecar/tests/test_ingest_process_job.py`.
3. **Queued end-to-end tests in their own file** (`tests/rag-e2e/upload-approval-queued.test.mts`): the queued harness needs its own fake edge, and the Supabase admin client is a per-process singleton, so it cannot share a process with the inline two-tenant fixture.
4. **Held batch version and document status:** the plan says "the document stays unpublished". It does (non-current, chunks not ready, direct publish answers `held`), but `rag_advance_ingestion_job` (0801) sets `documents.status = 'ready'` on a `ready` job. Changing that needs a migration; not done here. Activation (`rag_release_publish_hold` then publish) works from that state.
5. **Progressive:** added `progressive=false` for a snapshot whose approval is required (not in the plan).
