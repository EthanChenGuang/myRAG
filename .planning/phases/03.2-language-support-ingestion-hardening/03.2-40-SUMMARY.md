# Phase 3.2 Plan 40: Quarantine reasons in the admin route, explicit rescan, absolute fixture gate

**The admin route now shows why a document is held and which documents were not checked. Stored documents can be re-checked with `rag:rebuild -- rescan`. Every security fixture is caught with the right reason on both ingest paths, and no clean fixture is quarantined.**

## Accomplishments

- **Fixture gate (D-46).** `tests/rag-e2e/security-fixture-gates.test.mts` reads the four fixture folders (`pdf`, `docx`, `links`, `text`). It checks each file against its manifest digest. It ingests all 34 files with `RAG_HIDDEN_TEXT_CHECK=quarantine`, `RAG_INGEST_LINK_CHECK=quarantine` and the allowlist `example.com`, once inline and once through the queue with the real sidecar worker.
  - 18 bad fixtures: 7 PDF (near-background colour, tiny font, off-page, invisible render mode, covered text, white text in a form, link annotation), 6 Word (vanished run, style vanish, white text, tiny size, comment, tracked deletion), 4 link (URL, bare domain, e-mail, annotation) and 1 zero-width.
  - Each bad fixture must be quarantined with exactly the expected reason kinds, the right span reason and the right link targets. Every chunk must be quarantined, and no chunk `content` or `lexical_text` may keep the hidden sentence or a zero-width character.
  - The 16 clean fixtures must be ready, with no quarantine.
  - The test fails on a new folder, on a file without a manifest entry and on an entry without a file. Disabling the link check in the stage makes it fail (checked by mutation, then restored).
- **Faithful replay.** The fake sidecar now replays the Word manifest and the PDF link annotation targets; before, it answered `not_checked` for Word and gave no annotation targets.
  - The PDF manifest records `link_targets`. Only the manifest changed; the PDFs are byte-identical.
  - New sidecar tests pin each manifest to the real checker: every PDF entry's link targets, every Word entry's status and spans, and the link corpus PDFs' annotation targets.
- **Admin route (D-32, D-34, D-50).** `GET /api/rag/admin/quarantine` keeps today's fields. Each item also gets:
  - `reasons[]` as named fields only: kind, detail, spans with page, text and reason or targets, and unlocated;
  - `unlocated`;
  - `uploader {id, display}`;
  - `pending_approval`.

  Checker versions and bounding boxes are never returned; a stored span carrying a bbox fails the schema and is dropped. `view=not_checked` returns the file name, document type, source, upload time and a total. An unknown view gets 400. The guard is unchanged and logs carry counts only.
- **Rescan (D-47).** `npm run rag:rebuild -- rescan --check hidden_text|links [--tenant <key>] [--dry-run]` calls `rescanDocuments`.
  - It pages over current, ready documents through `rag_rescan_candidates` (0822). It runs the stage's checks on the stored parse output and, for PDF and Word, the stored original read only under the version's own prefix.
  - `quarantine`: quarantines through `rag_set_document_fields` and rewrites `parse.md`/`chunks.json` without the spans.
  - `flag`: records `hidden_text_report` or `link_check` and quarantines nothing.
  - `off`: refuses with exit 3.
  - Skips documents recorded clean for the current rules, and versions whose own quarantine for that check an admin released. A dry run writes nothing.
  - Nothing calls it except the CLI.

## Deviations from Plan

1. **Zero-width fixtures added.** The plan lists them in the gate, but the corpus had none. I added `eval/fixtures/security/text/` and its generator.
2. **Fixture and sidecar test edits outside the plan's file list:** `fake-sidecar.ts`, the PDF generator and manifest (`link_targets`), and three sidecar tests. Without them the gate would have tested the fake's defaults, not the checker.
3. **Migration 0822**, which the plan did not list. The CLI's RPC client cannot filter `documents` by id ranges, and the fake edge has no range filters.
4. **Two skip rules beyond the plan:**
   - a version whose own quarantine for this check an admin released;
   - the version's own `released_targets`, which `rag_released_link_targets` leaves out (it reads earlier versions only).

   Without them a rescan would quarantine again what an admin had just reviewed. Both are tested.
5. **`MECHANISM_COMMANDS.rescan` stays `npm run rag:rebuild -- rescan`.** The fingerprint route test only allows commands without shell metacharacters, so `<hidden_text|links>` cannot go in the string. The bare command prints the usage, which lists both values.
6. The plan's `npm run typecheck:new` does not exist. I ran the full `tsc` instead.

## Known limits (deferred)

- **A version quarantined by a rescan keeps its published chunk rows.** Only its stored parse output is sanitized. If an admin releases it, the chunks as they were, hidden text included, return to retrieval. The release dialog shows the spans first. A later version (type change, re-chunk, reparse) is built from the sanitized parse output. Follow-up: sanitize or rebuild the chunk rows on release of a rescan quarantine.
- **Word hyperlinks are not checked.** The Word checker reports no `link_targets`, so a hyperlink relationship (for example the `example.org` one in `clean-styled.docx`) is not checked unless its URL also appears in the text. This is outside SEC-08 as planned (D-35 names PDF annotations).
- External vector stores (Phase 7 sync) are not told about a rescan quarantine beyond what chunk status changes already trigger.

## Decisions for STATE

- The security rescan is `rag:rebuild -- rescan --check …`, never automatic. A finding under quarantine quarantines the published version in place and sanitizes its stored parse output, not its chunk rows.
- The fixture gate is the D-46 security acceptance test. Its sidecar answers are pinned to the real checker by the sidecar tests.
