# Phase 3.2 Plan 43: Scope tags at upload Summary

**Uploaders can attach scope tags at upload. The route checks them against the workspace's active vocabulary, the pipeline stores them on the document before any chunk is written so every chunk carries them, and the picker-defaults answer says whether tags are on and which values exist.**

## Accomplishments
- `POST /api/process-document` and `POST /api/upload` (images) read the `scopes` form field. Under the unified pipeline with `RAG_SCOPE_TAGS=true` the tags are validated before anything is stored and passed as `IngestInput.scopes`, both inline and queued.
- The pipeline writes them through `rag_set_upload_scopes` right after the version is begun. The 0801 chunk writers then copy them to every chunk. Tags are kept through a publish hold and approval, and the progressive final version gets them again from `queued-input.json`.
- With the switch off or under the legacy pipeline, a tagged upload is processed exactly like an untagged one, with one warning that gives the count only.
- `GET /api/rag/doc-type-defaults` returns `tags: { enabled, vocabulary }`. The vocabulary lists the caller's workspace only. All existing fields are unchanged.

## Deviations from Plan
1. **[Rule 2 - security/correctness] New migration 0817 `rag_set_upload_scopes` instead of calling `rag_set_document_scopes`.** Single-tenant documents have no `user_id`, so a single-tenant member could never be the "actor of record" for that setter, and every tagged member upload would fail. The new setter is narrower: it only accepts an in-flight version of the named tenant and only active values. 0817 is the next free number in the 3.2 gap range (0812-0816 are taken).
2. **[Rule 1 - plan text] `applyUploadScopes` is called in `stages/dedup.ts` (file_hash_dedup), not in `stages/identify.ts`.** The document row is created by `rag_begin_document_version` in file_hash_dedup, after identify. The acceptance grep `applyUploadScopes` in identify.ts is therefore 0. The key link's intent ("after the document row exists") holds.
3. **[Rule 3 - extra coverage] `callbacks/advance.ts`, `queued-context.ts` and `enqueue.ts` changed.** Without this, the progressive final begin (`RAG_PARSE_PROGRESSIVE`) would start a new untagged version.
4. **Existing test expectations in `tests/rag/doc-type-routes.test.ts`** now include the `tags` block (`TAGS_OFF`). This is the additive field the plan asks for, and the other fields are unchanged.
