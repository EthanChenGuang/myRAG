# Phase 3.2 Plan 08: D-02 unset-language rule, startup log, monolingual mode Summary

**A deployment without chosen languages keeps answering through the legacy pipelines and never reads the language settings. An explicit `RAG_PIPELINE=v2` or `RAG_INGEST_PIPELINE=unified` without languages fails loudly (`languages_not_configured`) without crashing. One supported language turns off query translation and the cross-lingual eval slices.**

## Behaviour

- **Resolver (`resolvePipelines`).** It works per path from the raw value and the shipped default.
  - Unset (empty or spaces) means "default".
  - The legacy pipeline (set or defaulted) is returned without reading the settings.
  - With languages configured, the requested pipeline runs.
  - With languages not configured, a defaulted v2 or unified serves legacy with `servedLegacyBecauseUnset`, and an explicit one gives `languages_not_configured`.
  - The settings reader runs at most once.
  - Retrieval matches `v2` exactly, as `parsePipeline` does. Ingest matches `unified` case-insensitively, as `parseChoice` does.
- **Retrieval.** `loadRagConfig` skips the resolver for `legacy` or an unset value while `DEFAULT_PIPELINE` is legacy, so it never calls `settings.ts`. Otherwise it sets `pipelineBlocked`.
  - `runRetrieval` returns `failure(collector, 'error', 'languages_not_configured')` for every profile before dispatch, and the trace records that reason.
  - Strict chat streams the existing "knowledge base temporarily unavailable" part, never "Information Not Available". With web search on, or in balanced or flexible mode, the answer continues without KB context, as for any `error`.
- **Ingest.** `loadIngestConfig` keeps `pipeline: 'unified'` and sets `pipelineBlocked`, so callers do not silently drop to legacy.
  - The upload, process-document and ai-to-rag unified branches answer `503 {"error":"languages_not_configured"}`.
  - `ingest()`, `submitIngest()` and `resumeIngest()` return `failed` with that reason before touching the database. This covers the scraper and Nango paths too, which go through `ingest`/`submitIngest`.
- **Startup.** `verifyLanguageSettingsAtStartup` joins the `Promise.all` in `register()`. It runs once per process and never throws.
  - It logs `[RAG Languages] not configured — serving legacy` when `servedLegacyBecauseUnset`.
  - It logs one `[RAG Languages]` warning per blocked variable, naming the variable and listing the validator error codes (codes only).
  - With today's shipped defaults (both legacy) the serving-legacy line cannot fire yet (research F-18). It is tested by passing the defaults parameter.
- **Monolingual (D-03).** `RagConfig.monolingual` is set only for a configured single-language set on a non-legacy pipeline.
  - It forces `v2.lexicalTranslation=false`, so the `translate` stage is `disabled`, not `degraded`, and `runQueryStages` uses `NONE_TRANSLATOR`.
  - The retrieval config hash gets `switches.monolingual: true` only in that case, so multilingual and legacy hashes are unchanged.
  - `RagConfig.monolingual` is a top-level field so that the D-46 all-off parity snapshot of `v2` stays intact.
- **Eval report.** The language set comes from `manifest.run_config.env.RAG_SUPPORTED_LANGUAGES`, else from `eval/config/rag-eval-env.json`.
  - With one code the report drops `by_category.cross_lingual`, every `by_language_pair` slice, and the language and language/category slices of other languages, and adds one note naming them.
  - The three-language pin gives a report identical to before (tested).

## Decisions for STATE

- `languages_not_configured` is checked before dispatch and applies to every retrieval profile (chat, embed, eval, voice, media, overview) when `RAG_PIPELINE=v2` is explicit.
- An explicit unified ingest keeps `pipeline: 'unified'` with `pipelineBlocked` set, so no write silently goes to legacy.
- Monolingual applies only when the retrieval path actually reads the settings (non-legacy pipeline). Legacy stays byte-identical.
