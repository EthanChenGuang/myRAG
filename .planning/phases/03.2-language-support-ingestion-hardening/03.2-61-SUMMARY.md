## Behaviour

**Panel (follows `#workspace-selector`, `organizationId` on every call, "Workspace: {name}" line).** Sub-tabs "Possible older versions: {count}" (default), "Effective dates: {count}" (dates awaiting confirmation) and Settings. One status announcement after the first load names both counts.

**Possible older versions.**
- One `article` per pending candidate: `h4` title from the two file names (`candidate.title`, or `candidate.titleUnknown` without a direction), the hold line (Both in use badge with `bi-files`, `hold.candidate`), the origin badge (Detected / Named by the uploader / Conflicting answers) and one signal sentence per matched rule. An unknown origin becomes `signal.other` with the code in `font-mono`. A stale candidate shows `candidate.stale`.
- Comparison in two `section`s headed Older and Newer (or Document A and Document B): File, Document type, Document date, Effective ("from … until …" or "No dates"), Uploaded (`time` + "by {display}"). Side by side from 768 px, stacked below.
- No similarity or overlap figure, raw signals object, run id, tenant key, user id or document text is rendered. The overlap and number fields only decide whether the content sentence shows (tested with values that would be visible).
- Direction: `document_newer` puts the published document under Newer, `candidate_newer` under Older. Without a direction a `fieldset` "Which document is the older one?" with two required radios sits above the buttons; Confirm replacement stays disabled with `candidate.pickFirst` referenced by `aria-describedby` until a choice is made.
- Confirm replacement opens the confirmation (`replace.title`, `replace.body`, focus on Keep both documents), then posts `{ olderDocumentId }` and reloads. Dismiss candidate acts at once. 404 and every 409 show `error.changed` and reload; a lost answer on confirm or undo shows `error.outcomeUnknown` and reloads.
- Under the list, `details` "Confirmed replacements: {count}" with a table (Older, Newer, Confirmed time and actor display, Undo replacement behind a confirmation). It renders with no pending candidate too. With detection off, `candidates.detectOff` shows above the list.

**Effective dates.**
- Filter radios Awaiting confirmation (default) and All with dates, a file-name search (Enter or 400 ms, max 200 characters), Refresh dates.
- Rows: File (`th scope=row`) with the state badge (Dates to confirm; or Read from the document / Set by an admin / "Read from the document, not applied" for a low-confidence proposal), From, To, Confidence as a percentage (`Intl.NumberFormat` percent, `tabular-nums`; under From below 1024 px), Effect today, Actions. A missing date is an em dash with a visually hidden "No start date" / "No end date". Dates are `time datetime` in YYYY-MM-DD.
- Effect today is computed from the shown window and today's UTC date with inclusive bounds: `effect.future`, `effect.expired`, `effect.inForce`, `effect.open`; `dates.utc` under the table.
- The evidence quote renders in the inert evidence block, tone `quote`, on its own row (invisible characters shown as `[U+…]`).
- Apply dates puts the proposed window; it asks first only when the window hides the document (`applyDates.bodyFuture` / `applyDates.bodyExpired`, focus on Keep document in use). Dismiss dates acts at once.
- Edit dates opens an editor row: two labelled `input[type=date]` with `min`/`max` tied to each other, `dates.order` and Save dates disabled when From is later than To, either or both dates may be empty (clearing sends `{ from: null, to: null }`), Escape or Cancel editing closes it and returns focus to Edit dates. A server 400 is shown at the fields and the editor stays open.
- With All with dates and no search, `dates.searchHint`; a search without a result shows `dates.noMatch`; no awaiting date shows `dates.empty.*`. With `RAG_EFFECTIVE_DATES` not `true`, the `dates.off` alert stands above the table.
- Below 768 px each row is a labelled stacked block with full-width 48 px buttons; no sideways page scroll at 360 px.

**Settings.** The `versions` group (`RAG_SUPERSESSION_DETECT`, `RAG_EFFECTIVE_DATES`, `RAG_EFFECTIVE_DATE_LLM_EXTRACT`) moves in, localized through `data-rag-i18n` (zh and it strings from UI-SPEC 12.9). Warnings in the alert host, recomputed on change: `warn.needsUnified` (detection on, ingest pipeline not unified) and `warn.datesNeedV2` (dates on, pipeline not v2).

**States.** First load spinner, refresh dims with `aria-busy`, 401/403 sign-in alert in place of the data views (Settings stays usable), 403 Forbidden workspace sentence, 503/network `versions.unavailable` alert with Reload panel, load more by 50 for both lists.

## Deviations

1. **No "Swap older and newer" button.** UI-SPEC 6.8 offers it for a candidate with a known direction, but `rag_confirm_supersession` (0806) refuses an `olderDocumentId` that contradicts the stored direction with `direction_conflict`, so the button could only produce an error. An admin who disagrees with the direction dismisses the candidate. A backend change (letting an admin override the direction) would be needed first.
2. **Hold line placement.** The plan lists Confirm replacement inside the hold line; the UI-SPEC 6.8 drawing puts the state and reason on the hold line and the two buttons under the comparison, after the direction choice. The buttons follow the drawing, so the choice comes before Confirm replacement in reading and tab order.
3. **"All with dates" without a search** lists the stored proposals (including low-confidence ones) and asks for a file-name search, because `GET effective-dates` without `query` returns proposals only. Any document found by the search offers Edit dates.
4. **Plan 60's deferred backend write** (persisting a dismissed tag suggestion) is not part of this plan's files and was not done; it stays deferred.
5. **Extra test files touched**: a binding row in `config-rag-panel-binding.test.ts` and an XSS row in `config-ui-xss-scripts.test.ts` (as plan 60 did). The harness lives inside the new test file, so no helper file was added.
6. **Contract wording**: the plan says "Possible replacements"; the copy contract (UI-SPEC 12.6) says "Possible older versions", which the panel uses.

## Decisions for STATE

- Effective-date rows stack as labelled blocks below 768 px; other date-heavy panels can reuse the pattern.
