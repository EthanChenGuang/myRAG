## What changed

- **Migration 0808.** It adds three functions. Each is `SECURITY INVOKER` with `SET search_path = ''` and schema-qualified names. Each is revoked from PUBLIC, anon and authenticated and granted to service_role. A given tenant key passes through `rag_assert_tenant_key`.
  - `rag_fingerprint_groups(p_tenant_key DEFAULT NULL)` counts current ready documents per (doc_type, fingerprint, parts). It returns aggregates only: no id, tenant key or text. NULL counts every tenant, because the settings are deployment-wide.
  - `rag_fingerprint_backfill_page(p_tenant_key, p_limit, p_after)` returns the stored parts of current ready or quarantined documents that have no fingerprint, in id order. The parts are the parser columns, profile columns, chunking profile ids, min lexical and embedding-text versions, vector profiles and legacy-vector presence. It also returns the OCR languages from the latest ledger snapshot.
  - `rag_fingerprint_backfill_write(p_tenant_key, p_document_id, p_fingerprint, p_parts)` stamps a document only while `ingest_fingerprint IS NULL` and the tenant matches. The parts are merged into `metadata.ingest_fingerprint_parts`.
- **`computeFingerprintImpact(proposed)`** loads the groups and, for each mechanism of the proposed ingestion keys, recomputes the expected parts with `expectedFingerprintFor`.
  - A group counts when the effective view of the parts changes.
  - The answer lists every doc type for each mechanism, zeros included, and is validated with `FingerprintImpactSchema`.
  - Groups with no fingerprint or unreadable parts go to `without_fingerprint`. They are never counted as affected or as unaffected.
- **Routes.**
  - `POST …/ingest-fingerprint/impact` is admin-only (`checkAdmin`). The body is strict: `{ proposed: Record<string,string> }`, with keys limited to the classified `RAG_*` names, at most 200 keys, and values of at most 2048 characters. The answer is the bare `FingerprintImpact` object.
  - `GET …/ingest-fingerprint` is admin-only. It returns `pending` for all seven mechanisms, each with `affected`, `by_doc_type`, `start` and `command`, plus `without_fingerprint { count, command }` and `total_current`.
  - On a read failure both routes answer 503 `fingerprint_unavailable`, without the database message.
- **Start and commands.**
  - `rechunk` and `recaption` start from the UI, through the existing chunking-profile build route.
  - `reparse` starts from the UI only when `RAG_INGEST_ASYNC=on`; otherwise it is `needs_async`.
  - `relex`, `reembed`, `retranslate` and `rescan` are `cli`.
  - Commands are fixed strings: `npm run rag:rebuild -- start --mechanism <m>` for reparse, rechunk, reembed and recaption; `npm run rag:relex`; `npm run rag:translate`; `npm run rag:rebuild -- rescan`. The backfill command is `npm run rag:fingerprint -- backfill`.
- **Backfill.** `npm run rag:fingerprint -- backfill [--tenant <key>] [--dry-run] [--page-size n]` builds parts with `partsFromStoredRow`.
  - These parts take assumed default values and are listed in `assumed_defaults`, in contract order: the switches, the OCR codes and packs of inline runs (the profile's OCR languages), a missing profile (the doc type's profile), a missing parser, chunks or vectors.
  - It makes zero parser, sidecar, embedding or network calls; the test fails any `fetch`.
  - A second run updates 0 documents. A run stopped after one page resumes, and a document that already has a fingerprint is never rewritten.
  - Exit codes: 0 done, 1 database failure, 2 bad arguments.
- `fingerprint.ts` now exports `ocrLanguagesUsed`, `languagePackVersions` and `switchesOf`, which were private. `@/lib/rag` exports the impact functions for the routes.

## Deviations

1. **Backfill write path.** The plan says to write through `buildIngestFingerprint` and `setFields`. The backfill instead calls the new `rag_fingerprint_backfill_write`, which writes only while the fingerprint is NULL. This makes "never rewrites a finished one" hold in SQL, even against a concurrent publish. `rag_set_document_fields` writes unconditionally.
2. **`rag_fingerprint_backfill_page` has a third parameter, `p_after uuid DEFAULT NULL`.** It is a keyset cursor, needed so a dry run, which writes nothing, still advances page by page.
3. **Header repeat uses the effective flag, as the plan's "four profiles" truth requires.** The comparison does not include the D-20 carry-forward, which `always` also turns on for `financial_report` and `invoice_receipt`. Those documents can differ only when a table continues across pages, and neither the fingerprint nor the stored columns can see that.
4. **Files outside the plan's list:**
   - `src/lib/rag/index.ts`: exports for the boundary rule.
   - `src/lib/rag/ingest/fingerprint.ts`: three helpers exported.
   - `src/app/api/rag/admin/ingest-fingerprint/_responses.ts`.
5. **Settings the fingerprint cannot predict count 0.** A proposed key such as `RAG_PARSER` or `RAG_EMBEDDING_PROFILES` is listed in `ingestion_keys`, but its affected count is 0, because no stored part depends on the configured value. The coverage route therefore covers only the five recorded variables. Plan 19 or 29 can add the active embedding profile and `EMBEDDING_TEXT_VERSION` comparisons.
