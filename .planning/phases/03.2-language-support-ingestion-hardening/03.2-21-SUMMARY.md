# Phase 3.2 Plan 21: Effective ingestion settings in the snapshot and both parser requests

**One function, `effectiveIngestSettings`, decides the effective OCR languages and the table and language-aware switches. The job snapshot, the inline Docling request and the LlamaParse v2 configuration all take their values from it, and every new key is left out while it holds its default.**

## Behaviour

- **Languages unset, every switch at its default.** The inline Docling request, the LlamaParse v2 configuration and the job snapshot are byte-identical to the bodies recorded before this plan. Tests compare the raw strings.
- **Languages configured.**
  - Docling `ocr_languages` and the snapshot get the supported set in registry order: `it,zh` and `zh,it` both give `['zh','it']`.
  - LlamaParse gets `processing_options.ocr_parameters.languages` with LlamaParse codes, primary first. For example, `zh,it` with primary `it` gives `['it','ch_sim']`.
  - A set equal to the profile list gives the profile's Docling list.
  - A single supported language gives a one-element list.
  - The profile is never edited.
- **Frozen at enqueue.**
  - `enqueueIngest` and the backfill enqueue pass the ingest config and the language settings into `buildJobSettings`.
  - The queued premium LlamaParse callback builds its request from `effectiveIngestSettingsFromSnapshot(job.settings, profile)`, so a later change of the language variables does not reach a queued job.
  - The sidecar's parse-cache key reads the snapshot's `ocr_languages`.
- **`RAG_TABLE_HEADER_REPEAT=always`.**
  - The inline request carries `repeat_table_header: true` and `carry_table_header: true` for every profile, including those whose own flag is false.
  - The snapshot carries `repeat_table_header_effective: true` and `carry_table_header: true`.
  - In `profile` mode, neither payload gains a key.
- **`RAG_LANGUAGE_AWARE_INGEST=on`** adds `language_aware`, `languages` (registry order) and `primary_language` to both payloads.
- **`RAG_TABLE_ROW_SERIALIZATION=true`** adds `row_serialization` to the snapshot. The parse request has no such field.
- **Validation.** `buildJobSettings` checks the snapshot against the generated `JobSettingsSnapshotSchema`, then drops fields that hold their defaults.

## Deviations

1. **[Rule 2] Contract field `JobSettingsSnapshot.ocr_primary_language`** (Python, schemas, generated Zod, samples, `wire-defaults.ts`). From the snapshot alone, "configured `zh,en,it`" cannot be told apart from "unset, profile fallback `zh,en,it`", and the primary is lost. Without this field, the queued premium LlamaParse call could not honour the "frozen at enqueue" truth.
   - It defaults to null and is omitted on the wire.
   - Python rejects a value that is not one of `ocr_languages`.
   - `npm run gen:schemas` leaves no diff.
2. **[Rule 2] Callers outside `files_modified`.** The effective settings would otherwise never reach a real request. These are:
   - `stages/parse.ts` (inline chain)
   - `enqueue.ts` and `backfill/run.ts` (snapshot inputs)
   - `callbacks/premium.ts` (queued LlamaParse from the snapshot)
   - `parsers/shared.ts` (`ParseRequest.settings`)
3. **`ingestLanguageSettings` gate.** The backfill enqueue does not check the pipeline. To keep the plan-08 rule (the legacy path never reads `settings.ts`), language settings are read only for an unblocked unified config. Otherwise they count as unset.
4. **Effective header flag in Task 1.** It was wired into the inline request together with the OCR languages, because both come from the same object. Task 2 added the remaining fields.
5. **Inline request with `RAG_LANGUAGE_AWARE_INGEST=on` and no configured languages.** The request carries `language_aware: true` with empty `languages`. Under D-02, the unified pipeline cannot run unconfigured, so this case is not reachable in production.

## Decisions for STATE

- `effectiveIngestSettings` (`src/lib/rag/ingest/routing/effective-settings.ts`) is the only place that decides the effective OCR languages and the ingestion table and language switches. No caller builds them by hand.
- A queued job's effective settings are rebuilt from its snapshot (`effectiveIngestSettingsFromSnapshot`), never from the current environment.
- `JobSettingsSnapshot.ocr_primary_language` records the primary of the configured languages. When it is null, the snapshot's `ocr_languages` came from the profile.
