# Phase 3.2 Plan 15: Upload approval on every ingestion path Summary

**With RAG_UPLOAD_APPROVAL on, every ingestion source either holds a non-admin upload (unified, inline and queued) or refuses with 503 `upload_approval_requires_unified_pipeline` (legacy) before writing anything; a boundary test keeps it that way, including for a future WhatsApp path.**

## Accomplishments
- `legacy-refusal.ts` with the predicate, the route response and a typed error; exported from `@/lib/rag`.
- Routes refuse on their legacy branch: process-document (knowledge-base uploads only), upload (`process_rag=true` only, before storage), ai-to-rag, scrape and crawl (also mapping the typed error in their catch).
- Legacy writers and adapters refuse in code: `processDocument`, `processImageDocument`, the Nango adapter's legacy branch and the scraper adapter's legacy scrape/crawl.
- Path matrix e2e over the real route handlers in a Next.js request scope, on the two-tenant database, plus a single-tenant Nango file.
- D-57 boundary test with self-tests.

## Behaviour changes
- `RAG_UPLOAD_APPROVAL=off` (default): none. `legacyWriteRefused()` is false and every branch runs as before (`tests/rag-e2e/defaults-equal-phase3.test.mts` and the off cases of the path matrix pass).
- `members`/`all` with `RAG_INGEST_PIPELINE=legacy` (or legacy served because languages are unset): every knowledge-base write answers 503 `{ error: 'upload_approval_requires_unified_pipeline' }`; Nango sync items fail with `UploadApprovalRequiresUnifiedError` (code and reason set to the same string, status 503) and are retried by the next sync; temporary attachments still work.

## Tests that failed before the fix
- `tests/rag-e2e/upload-approval-paths.test.mts`: the two legacy-refusal tests (`502 !== 503`, then `cloud_parsing_disabled` vs the refusal code) and the Nango legacy test (`code` undefined), RED commit `cc0c8a2`.
- `tests/rag/approval-gate-boundary.test.ts` against the pre-15 `src/`: names six unguarded legacy callers (process-document, ai-to-rag, upload, document-processor, Nango adapter, scraper adapter).
- `tests/rag-e2e/upload-approval-paths-single.test.mts` "legacy pipeline with approval on" fails on the old adapter (the Markdown legacy path parses locally and writes).

## Deviations
1. **[Rule 2] Scrape and crawl routes** (`src/app/api/scrapers/{scrape,crawl}/route.ts`), outside `files_modified`: the plan asks for a 503 from every route entry; the crawl legacy path swallows per-page errors, so the adapter error alone would answer 200 with failed pages.
2. **[Rule 3] Test mocks updated**: `tests/rag/single-tenant-writes.test.ts`, `tests/rag/ingest/write-path-nango.test.ts` and `write-path-scraper.test.ts` mock `@/lib/rag` completely; they gain the new exports in their approval-off form.
3. **Extra e2e file** `tests/rag-e2e/upload-approval-paths-single.test.mts`: the "member's connection held, admin's not" truth only exists in single-tenant mode (multi-tenant connections sync into the owner's personal workspace), and the Supabase admin client is a per-process singleton, so it needs its own process.
4. The e2e harness answers two reads the fake edge does not serve (`admin_users`, `organizations?select=*`) from the fixture database in its fetch wrapper, and runs with `RAG_PARSER_ALLOW_CLOUD=false` so the legacy LlamaCloud client (node-fetch) never leaves the machine.
5. `src/lib/supabase.ts` (the storeDocument host) is not changed: browser code imports it. Its only caller, `document-processor.ts`, asserts.
