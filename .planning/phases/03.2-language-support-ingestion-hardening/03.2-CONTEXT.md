# Phase 3.2: Language Support & Ingestion Hardening - Context

**Gathered:** 2026-11-25
**Status:** Ready for planning
**Mode:** `--auto`. Every gray area was resolved with the recommended option, per the user's standing instruction "all questions follow your recommendations".

<domain>
## Phase Boundary

This phase makes the supported languages an explicit deployment setting, makes every ingestion step work per language, and keeps hidden text, untrusted links and unapproved uploads out of retrieval. It builds on the single `ingest()` path (Phase 3), the queue and settings snapshot (Phase 3.1) and the model catalog (Phase 3.1.1). It delivers:

- **Language setting and registry (LANG-01, LANG-02, LANG-03):** `RAG_SUPPORTED_LANGUAGES` and `RAG_PRIMARY_LANGUAGE`, chosen in a first-run picker (`scripts/init-env.js` and the Config UI), validated against a language-pack registry that is Pydantic data with generated Zod. A CI check forbids hard-coded `zh|en|it` literals outside the registry and fixtures.
- **Ingestion fingerprint (LANG-04):** every setting is classified once as ingestion-side or query-side. An ingestion-side change shows the affected document count and rebuilds only those documents side by side, with rollback.
- **Language-aware ingestion (LANG-05, LANG-06, DATA-05 delta, XLG-06):** per-chunk language with confidence (`und` when undetected), sentence splitting by the chunk's language, OCR languages from the supported set, no hard-coded LlamaParse `language: "en"`, captions written in the document's language.
- **Tables (CHK-06, CHK-07, EVAL-18):** the header row is repeated in every table chunk in every processing profile and carried across pages; optional "column = value" row serialization for the embedding and lexical text; a `table_split` golden category.
- **BGE-M3 (EMB-11):** an open-source fallback embedding profile, served by a hosted API or by the sidecar with the same vectors.
- **Document translation (XLG-04):** optional retrieval-only translations of chunks; a hit returns the original chunk.
- **Ingestion security (SEC-07, SEC-08, SEC-09):** hidden-text detection, link allowlist check, upload approval; quarantine reasons shown to the admin.
- **Scope and versions (DATA-18, DATA-19, DATA-20):** scope tags as a retrieval filter, cross-document supersession with admin confirmation, effective dates.
- **XLG-02 delta:** machine-translated or drafted zh/it golden items count only after native-speaker review.

Every new switch defaults to off or to today's behaviour. With all of them off, the characterization tests pass and no eval slice moves beyond the noise band.

**In scope:** LANG-01 to LANG-06, XLG-04, XLG-06, EMB-11, SEC-07, SEC-08, SEC-09, DATA-18, DATA-19, DATA-20, CHK-06, CHK-07, EVAL-18, and the DATA-05 and XLG-02 deltas.

**Out of scope (other phases own these):**
- The lexical tokenizer using the terminology dictionary and Italian stemming (LANG-07), version-aware retrieval `versions: current | all | range` (RET-11), the table lookup leg (RET-12): Phase 4.2. This phase only stores what they need (registry fields, effective dates, supersession links).
- Refusal and fixed-notice texts chosen by answer language (LANG-09), the output link guard (SEC-06), version labels in context blocks and `stale_version` answers (GEN-14, EVAL-19): Phase 5.2. This phase stores the texts in the registry and defines the allowlist variable and parser that Phase 5.2 reuses.
- Query-language confidence and the stronger detector (LANG-08), the translation glossary (XLG-05), voice cross-language (XLG-07), per-sub-question filters (QRY-10): Phase 6.2. This phase leaves a glossary seam and accepts a `scopes` filter in the request contract.
- Per-language monitoring and gradual rollout per tenant or traffic share (LANG-10, LANG-11), the cross-tenant canary suite over new tables (RET-08), shipped defaults (ADM-02): Phase 7.
- ML injection detectors at ingestion. Ingestion stays rules-only (Phase 5.1 Deferred, A-12).
- Adding a fourth language. The registry ships zh, en and it only (D-05).

## Implementation Decisions

### Language setting and registry (LANG-01, LANG-02, LANG-03)

- **D-01:** Two deployment-level variables. `RAG_SUPPORTED_LANGUAGES` is a comma-separated list of registry codes (default empty). `RAG_PRIMARY_LANGUAGE` is one of them (default empty). Both are read through one module, `src/lib/rag/lang/settings.ts`, which returns `{ configured: boolean, languages, primary, monolingual }`. No other code reads the two variables. Tenants cannot widen the set; every tenant-level language setting (D-31) is validated as a subset.
- **D-02:** Unset behaviour (owner decision 2026-11-25). With both unset, `RAG_PIPELINE=legacy` and `RAG_INGEST_PIPELINE=legacy` behave byte for byte as today and never call `settings.ts`. When the languages are unset and `RAG_PIPELINE` / `RAG_INGEST_PIPELINE` are also unset (so v2 or unified would only be active as a shipped default, e.g. after Phase 4.1 DFLT-01), the process serves the legacy pipelines and logs `[RAG Languages] not configured — serving legacy` once at startup (`src/instrumentation.ts`), and the Config UI shows a persistent banner "Supported languages not chosen" linking to the picker; questions keep being answered. Only when an operator explicitly sets `RAG_PIPELINE=v2` or `RAG_INGEST_PIPELINE=unified` with the languages unset does it fail loudly (same rule as DFLT-04 for an explicit `RAG_PIPELINE=v2`): retrieval returns status `error` with reason `languages_not_configured` (strict mode shows the existing "knowledge base temporarily unavailable" message, never "information not available"), unified ingestion answers 503 `languages_not_configured`, and the app does not crash (Phase 3 D-37). Phase 4.1 adopts this as the order between its default flip and LANG-01. CI, the eval env pin (`eval/config/rag-eval-env.json`) and all fixtures set `zh,en,it` with primary `en`.
- **D-03:** Monolingual mode is `languages.length === 1`. Then: `detect.ts` returns that language without detecting; the Phase 6 translate stage and `RAG_LEXICAL_TRANSLATION` are no-ops; document translation (D-28) is off; the eval harness skips the `cross_lingual` slices and the slices of languages that are not enabled. Per-chunk detection at ingestion stores the single language (never `und`, D-13).
- **D-04:** The registry is a Pydantic v2 contract in `rag-sidecar/src/rag_sidecar/contracts/languages.py` (`LanguagePack`, `LanguageRegistry`) and a data file `config/rag/language-packs.json` read by the app (`src/lib/rag/lang/registry.ts`) and the sidecar. Zod is generated into `src/lib/rag-eval/contracts.generated.ts` by the existing export. `LanguagePack` fields: `code`, `name`, `native_name`, `script`, `sentence_end` (characters), `segmentation` (`intl_segmenter_han_bigrams | whitespace`), `stemmer` (name or null), `folding` (`accents`, `elision`), `stopwords` (detection list and lexical list), `ocr_codes` (`docling` per engine, `llamaparse`), `rewrite_gate_lexicon` (key into `src/lib/rag/query/rewrite-gate.lexicon.json`), `texts` (strict refusal, fixed notices, groundedness badge texts), `groundedness` (`hhem_2_3 | hhem_2_1_open | none`), `effective_date_patterns`, `version_markers`, `fixtures` (`corpus: bool`, `golden_slices: bool`), `pack_version`. A pack is **complete** when segmentation, OCR codes for every parser, lexicon, refusal text, fixture corpus and golden slice are all present. — **Reversibility:** costly — the registry becomes the type source for the golden contract, the eval corpus, the drafting tools and the rewrite gate.
- **D-05:** The registry ships zh, en and it only, all complete. Values are copied from today's constants, and a test per consumer asserts equality with the current behaviour: the detection stopwords in `src/lib/rag/lang/detect.ts` and `rag-sidecar/src/rag_sidecar/ingest/lang.py`, the Docling OCR mapping (`to_ppocr_code`), the lexical tokenizer's folding and stopwords, the refusal and notice texts. In this phase the registry is **consumed** by: language settings and validation, `detect.ts` and `lang.py`, the chunkers (D-15), OCR code selection (D-17), captions (D-23), the golden contract, eval corpus and drafting tools, and the rewrite-gate `Lang` type. The tokenizer (LANG-07, Phase 4.2) and the refusal texts (LANG-09, Phase 5.2) switch to the registry in their own phases; until then the equality tests keep both in step. No `LEXICAL_VERSION` bump in this phase. Incomplete packs exist only in test fixtures.
- **D-06:** The `Language` type is derived from the registry. `export_schemas.py` builds the language enum from `config/rag/language-packs.json` at export time, so the generated JSON Schema and Zod carry the codes and the existing contract drift check fails when the registry changes without regeneration. `golden.py`, `eval/src/rag_eval/corpus.py`, `eval/src/rag_eval/draft/config.py` and the other hand-written modules import that type. A new CI check `scripts/ci/check-language-literals.mjs` fails on a hard-coded `zh|en|it` union, tuple or list in `src/`, `rag-sidecar/src/`, `eval/src/` and `scripts/`. Exempt: the registry file, generated files, fixtures, tests, and an allow-list file where every entry names the plan that removes it (the Phase 3 D-04 pattern). Files owned by this phase's requirements are converted here; files of phases still executing (5, 5.1, 6, 7) may sit on the allow-list with their owner plan.
- **D-07:** One validator, `validateLanguageSettings(candidate, context)`, with one implementation shared by `scripts/init-env.js`, `scripts/config-server.js` and the app startup check (a test feeds the same cases to all three entry points). Hard errors: empty set; primary not in the set; a language without a complete pack; the active embedding profile or the active reranker not declaring every chosen language. Warning only: a language whose `groundedness` is `none` (recorded as "not checked", GEN-05). Language support is declared as `supported_languages: string[]` on each model in the Phase 3.1.1 catalog (`src/lib/rag/embeddings/catalog.ts`) and on each reranker adapter in `src/lib/rag/rerank/`; `local_bm25` declares every language whose pack has a segmentation method. Every model that exists today declares `zh, en, it` (they are evaluated on those slices). When the database cannot be reached (first run), the embedding check uses the default profile and the result says "not verified against the active profile".
- **D-08:** First-run picker in two places.
  - **`scripts/init-env.js`:** when stdin and stdout are TTYs, `CI` is unset and `RAG_SUPPORTED_LANGUAGES` is unset, it asks with Node `readline` (no new dependency): a multi-select over complete packs, then the primary language. An empty answer leaves both unset (legacy keeps working). It suggests the languages found in existing documents only when Supabase credentials are already in `.env.local`. Non-interactive runs never prompt.
  - **Config UI:** a first-run step shown before the RAG administration panels whenever the two variables are unset, plus a permanent "Languages" panel. It lists only complete packs, pre-selects the languages present in `documents.language` with their document counts, and saves through `scripts/config-server.js`, which runs D-07 and refuses with the error text.
  - Vercel and CI set the two variables directly.

### Ingestion fingerprint and side-by-side rebuild (LANG-04)

- **D-09:** Settings are classified once in `config/rag/settings-classification.json` (Pydantic `SettingsClassification`): each `RAG_*` variable is `ingestion` or `query`, and each ingestion-side entry names its rebuild mechanism: `reparse`, `rechunk`, `relex`, `reembed`, `recaption` or `retranslate`. A CI check fails when a `RAG_*` variable in `scripts/rag/env-manifest.json` has no classification. Query-side settings take effect on save. The supported-language set itself is ingestion-side (`reparse`, because OCR languages change) for the documents it affects.
- **D-10:** The fingerprint is one builder, `src/lib/rag/ingest/fingerprint.ts`. It hashes (sha256 over canonical JSON) the existing parts, not new ones: `parser_used` and parser version, processing profile id and version, `ocr_languages` (Phase 3.1 settings snapshot), chunking profile id, `lexical_version`, `embedding_text_version`, embedding profile id and version, the language pack versions used, and the state of this phase's ingestion-side switches (D-13, D-19, D-21, D-23). It is stored as `documents.ingest_fingerprint` with the parts in `documents.metadata.ingest_fingerprint_parts`, written at publish. Inline runs use the same builder and still write no ledger row (Phase 3.1 D-01). Documents published before this phase get their fingerprint from stored columns through `npm run rag:fingerprint -- backfill` (zero parser and embedding calls, resumable, dry run). — **Reversibility:** costly — the part list is persisted on every document; changing it means a new backfill.
- **D-11:** Impact and rebuild. `POST /api/rag/admin/ingest-fingerprint/impact` takes proposed values and returns, per mechanism and doc type, the number of current ready documents whose stored fingerprint differs from the expected one. The Config UI shows that count and a warning before saving an ingestion-side setting, then offers "Start rebuild". The rebuild reuses existing mechanisms only:
  - `reembed`: the Phase 3 re-embed job (D-38) into a backfilling profile.
  - `relex`: `npm run rag:relex`.
  - `rechunk`, `recaption`: a new chunking profile built by `npm run rag:rechunk` from stored parse output (Phase 4 D-21), zero parser calls. Every chunk-level change of this phase (D-13, D-15, D-19, D-21) is delivered this way for existing documents.
  - `reparse`: re-ingest from the stored original through the queue as a new document version (the Phase 3 D-18 path), run as a Phase 3.1 batch. Needs `RAG_INGEST_ASYNC=on`; with it off the UI lists the documents and the CLI command instead of starting.
  - `retranslate`: `npm run rag:translate` (D-29).
  Only affected documents are selected.
- **D-12:** Activation and rollback. `rechunk` and `reembed` rebuilds are activated by the existing pointer flips (`rag:chunking activate`, `rag:embedding activate`) with their existing completeness and eval gates, and rolled back the same way. A `reparse` batch writes the new versions unpublished; `npm run rag:rebuild -- activate <batch_id>` publishes them through `rag_publish_document_version` after the eval passes, and `rollback <batch_id>` republishes the previous versions (Phase 3 D-11 keeps the old rows). The researcher confirms whether the Phase 3.1 provisional-version machinery (D-30) can hold the publish, or whether a batch-level `hold_publish` flag is needed. — **Reversibility:** costly — batch-held publishing touches the publish path of every queued job.

### Language-aware ingestion (LANG-05, LANG-06, DATA-05 delta)

- **D-13:** One switch, `RAG_LANGUAGE_AWARE_INGEST` (`off` | `on`, default `off`), covers per-chunk detection, per-language sentence splitting and registry OCR codes. With `off`, `enrich` writes exactly what it writes today (document language or null, chunks mirror it). With `on`: `enrich` detects each chunk among the enabled languages with `detectLanguageWithConfidence`, extended to return a numeric `confidence` (0..1) while its `confident` flag and its results for zh, en and it stay identical. `document_chunks.language` holds the chunk's own language, the new `document_chunks.language_confidence real` its confidence, and `und` marks a chunk below the confidence floor or without letters (tables of numbers, codes). A `und` chunk is processed with the primary language's pack. `documents.language` is the dominant language weighted by tokens; the new `documents.languages text[]` lists every language with at least 10% of the tokens. `rag_tenant_language_shares` (migration 0601) keeps reading `documents.language`, so the XLG-01 shares follow automatically. The sidecar detector `lang.py` reads the same registry and a cross-language test keeps it equal to `detect.ts`.
- **D-14:** The `languages` filter (Phase 4 D-05) treats `und` as the document's language: a chunk matches when `c.language = ANY(p_languages)`, or when `c.language = 'und'` and its document's language matches. This is added to `hybrid_search_chunks` in this phase's migration; with the switch off no `und` row exists, so results are unchanged.
- **D-15:** Sentence splitting. With D-13 on, the chunkers (`markdown-sections.ts`, `legal-clauses.ts`, `table-aware.ts`, `parent-child.ts`) take the sentence-ending characters from the pack of each block's language (detected per block at chunk time, `und` → primary): `。！？` for zh, `.!?` for en and it. Semicolons stop being sentence ends. With it off, the shared `SENTENCE_END` set is used unchanged. Token counting stays `cl100k_base` on both sides (Phase 3 D-22). On the Docling path the single chunking pass after the merge (Phase 3.1 D-53) must follow the same rule; the researcher checks whether HybridChunker's splitter accepts the delimiters, and otherwise over-long text items are re-split in TS with the shared splitter.
- **D-16:** Legacy routes. With the languages unset or `RAG_LANGUAGE_AWARE_INGEST=off`, `src/lib/document-processor.ts` and `src/app/api/process-document/route.ts` are byte-identical to today (Phase 3 D-03), including LlamaParse `language: "en"` and the four-characters-per-token estimate. With the switch on, the legacy writers are not patched: their uploads go through `submitIngest()` (the unified path), which already counts with `cl100k_base`. The two LlamaParse call sites send the registry code(s) of the supported set instead of `"en"` whenever the languages are configured, even under the legacy ingest pipeline; the researcher confirms how LlamaParse accepts several languages.
- **D-17:** OCR languages. When the languages are configured, the effective `ocr_languages` in `buildJobSettings` (`src/lib/rag/ingest/routing/settings-snapshot.ts`) and in the inline Docling request (`parsers/sidecar-docling.ts`) is the supported set mapped through `ocr_codes`; the profile's `ocr_languages` field stays as the fallback for the unset case and is not edited. The sidecar's engine mapping (`to_ppocr_code`, presets) reads the registry. `ocr_languages` is already part of the parse-cache key (`cache_keys.py`), so a changed set is a `reparse` change (D-09).
- **D-18:** Character-exact scan fixture. The parse test set (Phase 3.1 D-38) gains a class `scan_zh_it`: a generated scanned page with Chinese text and Italian accents (è, più, già), with a `ParserExpected` exact-text file. CI asserts on recorded Docling and LlamaParse outputs that the text is character-exact and that the request carried the registry OCR codes (Phase 3 D-23 pattern). Real OCR runs in the optional nightly job and in live verification.

### Tables (CHK-06, CHK-07)

- **D-19:** Header repetition is a switch, `RAG_TABLE_HEADER_REPEAT` (`profile` | `always`, default `profile`). `profile` reads `repeat_table_header` from `config/rag/processing-profiles.json` as today; the JSON is not edited, so `general`, `contract_legal`, `product_technical` and `scanned_image` keep `false` and all existing chunk fixtures stay identical. `always` forces repetition in every TS chunker and in the Docling request for every profile. Existing documents are rebuilt as a new chunking profile (D-11). Owner decision 2026-11-25: the default does not wait for Phase 7. Inside this phase, after the eval shows the `table_split` slice improving with no other slice dropping beyond the noise band, the default of `RAG_TABLE_HEADER_REPEAT` changes to `always` in the five config locations and the env manifest, with the numbers recorded in `eval/decisions/03.2-table-header-default.json`; if the gate fails, the default stays `profile` and the failure is recorded. Setting `profile` restores today's behaviour.
- **D-20:** Header carry-forward. Under `always`, a table that continues on the next page without its own header row gets the last header: a continuation is a table that starts a page, follows a table that ended the previous page, has the same column count and whose first row is not header-like. On the Docling path this runs on the merged document before chunking (Phase 3.1 D-52, D-53 already join tables across range boundaries); on the LlamaParse path it runs in the markdown table parser (`chunkers/markdown-tables.ts`). Each carried header is recorded in `metadata.table_header_carried = true`.
- **D-21:** `RAG_TABLE_ROW_SERIALIZATION` (`false` default). When on, for `chunk_kind = 'table'` the embedding text and `lexical_text` get one line per row, `列名=值` pairs joined with the pack's list separator (for example `城市=米兰，职级=P5，住宿上限=180，币种=EUR`), appended after the existing path prefix. `content` (the LLM text) keeps the Markdown table with its header. It is a new version of the embedding text template (`embedding_text_version`, Phase 3 D-24), not a tokenizer change, so `LEXICAL_VERSION` is not bumped; existing documents get it as a `rechunk` change. It ships on only if the `table_split` and `table` slices gain Recall or answer correctness.
- **D-22:** Both table switches feed the existing keys. The effective header flag (after `RAG_TABLE_HEADER_REPEAT`) is what goes into the Docling chunk request, the chunker part of the parse-cache key (`rag-sidecar/src/rag_sidecar/ingest/cache_keys.py`) and the merged-document version string (`tiered.py`), so a cached conversion is reused while chunks are rebuilt. The effective flag and the row-serialization state are fingerprint parts (D-10). Rows are never split and tables stay parents under parent-child chunking, as today.

### Captions (XLG-06)

- **D-23:** `RAG_CAPTION_LANGUAGE` (`en` | `document`, default `en`). With `en` the prompt is byte-identical to `IMAGE_CAPTION_PROMPT` (the existing test stays). With `document` the same English instruction gets one appended sentence: write the description in `<native language name>` and quote any text visible in the image in its original language. The target language is the document's language, else the tenant's largest language share (`rag_tenant_language_shares`), else `RAG_PRIMARY_LANGUAGE`. The caption chunk's `language` is the language detected on the caption actually written. Both callers use it: the unified `images` stage and standalone image upload.
- **D-24:** Regenerating existing captions is a mode of the re-embed CLI: `npm run rag:reembed -- --recaption [--tenant <key>] [--dry-run]`. It selects current image chunks whose language differs from the target, re-captions from the stored image (`metadata.image_url`), and rewrites content, `lexical_text` and the vectors in one upsert. Zero parser calls are asserted. It uses the `embedding_backfill_runs` cursor, shows a dry-run cost, keeps the previous caption in `metadata.previous_caption` and supports `--rollback <run_id>`.

### BGE-M3 (EMB-11)

- **D-25:** BGE-M3 joins the Phase 3.1.1 catalog (D-01) as provider `bge-m3`, model `BAAI/bge-m3`, 1024 fixed dimensions, 8192 input tokens, MIT licence, `supported_languages: zh, en, it`, dense output only. One unscoped profile `bge-m3-1024` is seeded `available` by migration with its own partial HNSW index over `halfvec(1024)` (`m=64, ef_construction=200`, Phase 3 D-35). Nothing is activated by a migration; activation goes through the EMB-05 gate unchanged (Phase 3 D-40). No query instruction prefix; vectors are L2-normalized.
- **D-26:** One profile, two serving modes, chosen by `RAG_BGE_M3_SERVING` (`hosted` | `sidecar`, default `hosted`). `hosted` calls DeepInfra's OpenAI-compatible embeddings endpoint with the existing `DEEPINFRA_API_KEY` and `DEEPINFRA_BASE_URL`. `sidecar` calls a new `POST /v1/embed` on the sidecar (Pydantic `EmbedRequest`, `EmbedResponse`, shared-secret auth), served on CPU behind an optional `bge-m3` extra. "Identical" is defined as: after L2 normalization, cosine ≥ 0.9999 and every component within 1e-3 (below `halfvec` precision). CI compares committed recorded vectors of both modes for fixture text in zh, en and it, plus adapter contract tests (pooling, normalization, truncation off). An optional nightly job runs the real sidecar model against the recorded hosted vectors. No live call in CI.
- **D-27:** Comparison. BGE-M3 is one more arm of the Phase 3 per-profile comparison (D-43): every slice, `cross_lingual` per language pair, plus ingestion throughput, query latency and cost for both serving modes. Fixture runs use the fixture embedder and are labelled wiring proof; the real comparison is live verification.

### Document translation (XLG-04)

- **D-28:** Storage is a separate table, not extra rows in `document_chunks`. `chunk_translations` (`id`, `chunk_id` FK with cascade delete, `document_id`, `tenant_key`, `language`, `content`, `lexical_text` with its tsvector and GIN index, `source_content_hash`, `model`, `glossary_version`, `created_at`) and `chunk_translation_embeddings` (`translation_id`, `profile_id`, `tenant_key`, `embedding halfvec`, `embedding_model`, `dims`, partial HNSW per profile). RLS on with no policies; service role only. Existing readers of `document_chunks` (context assembly, citations, legacy RPCs, counts) are untouched. Translations are embedded with the active global profile only. After a global profile flip the translation legs are skipped (trace detail `translation_stale`) until `npm run rag:translate -- --reembed` completes; the Phase 3 D-40 gate is not edited. Translation is additive: losing it can only lose extra recall (the Phase 3.1.1 D-08 rule). — **Reversibility:** costly — two new tables with per-profile index DDL.
- **D-29:** Producing translations. `RAG_DOC_TRANSLATION` (`off` | `on`, default `off`) is the deployment master switch. Each text and table chunk whose language is known and differs from a target is translated; image captions and `und` chunks are skipped. The model is `RAG_DOC_TRANSLATION_MODEL` (empty: `RAG_QUERY_LLM_MODEL`), with a Pydantic `ChunkTranslation` structured output. Protected tokens (`src/lib/rag/query/protected.ts`) must appear verbatim in the translation; one retry, then the chunk is skipped and recorded as a gap. The glossary is a seam, `glossaryFor(scope, source, target)`, that returns nothing until XLG-05 (Phase 6.2); `glossary_version` is stored so stale translations can be found later. Translation runs after publish and never delays or fails ingestion: with `RAG_INGEST_ASYNC=on` as a ledger job of kind `translate`; with it off, inline after publish within a time budget, the rest picked up by `npm run rag:translate -- --tenant <key> [--dry-run] [--budget <USD>] [--resume]`. A new or re-chunked version gets new translations; old ones go with their chunks (cascade).
- **D-30:** Query side. Only the v2 pipeline (`chat`, `embed`, `eval` profiles) uses translations; voice and legacy do not (Phase 3.1.1 D-17 rule). When the tenant has translations in the query's language, one extra RPC `hybrid_search_translations` (service role only, `p_tenant_key` checked by `rag_assert_tenant_key`, same current-and-ready filter through the source chunk, same DATA-08 filters) runs in parallel with the main search and reuses the query embedding. Its hits are mapped to their source chunk and enter RRF as extra lists `dense_tr:<lang>` and `lexical_tr:<lang>`. Dedupe is by source chunk id; a translation-only hit carries `similarity: null` (Phase 3.1.1 D-20). The LLM, citations, snapshots and `source_images` always use the original chunk. A failed or timed-out translation leg is dropped and recorded `degraded` with detail `translation_leg_<reason>`; it never fails a request.
- **D-31:** Tenant settings and gate. Targets live in `rag_translation_settings` (`tenant_key`, `target_languages text[]`, `enabled`, `updated_by`), edited by admins in the Config UI and validated as a subset of the supported set. The eval compares, on the `cross_lingual` slice per pair, XLG-01 alone against XLG-01 plus translations, and reports the Recall gain next to added rows and bytes, translation cost and ingestion time. Fixtures use a fake translator fed from `eval/fixtures/translation-table.json`. The recommended configuration turns it on only if the gain is beyond the noise band.

### Ingestion security (SEC-07, SEC-08, SEC-09)

- **D-32:** The 13-stage list does not change. The `scan_injection` stage runs three independent checks, each with its own switch and outcome: injection rules (`RAG_INJECTION_SCAN`, unchanged), hidden text (D-33) and links (D-35). `metadata.quarantine` gains `reasons[]`, a Pydantic `QuarantineReason` (`kind`: `injection_rule | hidden_text | untrusted_link | invoice_extraction`, `detail`, `spans` or `targets`, `checker_version`); the existing `rule_ids` and `snippets` keys stay. The admin list function (migration 0316) returns the reasons. Ingestion stays rules-only: no ML detector, no Prompt Guard 2 (Phase 5.1 Deferred, A-12).
- **D-33:** Hidden-text checker. `RAG_HIDDEN_TEXT_CHECK` (`off` | `flag` | `quarantine`, default `off`). The check runs on the stored original, independently of which parser produced the text:
  - **PDF:** a sidecar function over character-level data (pdfplumber and pypdfium2, already used by preflight, Phase 3.1 D-49): fill colour equal or near the background, font size below the minimum, text outside the page box, text covered by another object, invisible render mode.
  - **Word:** vanished runs (`w:vanish`), white or near-background colour, tiny sizes, comments and tracked deletions.
  - **Every text:** zero-width characters, checked in TS.
  It is exposed as `POST /v1/hidden-text` (Pydantic `HiddenTextRequest`, `HiddenTextReport` with `status`, `spans[{page, text, reason, bbox}]`, `checker_version`); under tiered async routing the worker runs it during preflight and stores the report with the job. Thresholds are data in `config/rag/hidden-text-rules.json` (Pydantic `HiddenTextRules`), chosen by the researcher on the fixtures.
- **D-34:** Handling. `flag` records the report and changes nothing else. `quarantine` removes the hidden spans from the parse text and the parsed chunks before chunking, so they never reach the embedding text, `lexical_text` or `content`, and sets the document to `quarantined` with the spans as the reason. After an admin releases the document the spans stay removed. Zero-width characters below the threshold are stripped with a warning and do not quarantine. The new column `documents.hidden_text_check` is `clean`, `hidden_found` or `not_checked`. Formats without a checker (text-only connector content, HTML from scrapers, presentations, spreadsheets) get `not_checked`, are indexed, and are listed in the Config UI. If the checker is unavailable under `quarantine`, the stage fails retryable (fail closed, as Phase 3 D-30).
- **D-35:** Links. `RAG_INGEST_LINK_CHECK` (`off` | `flag` | `quarantine`, default `off`) and `RAG_OUTPUT_LINK_ALLOWLIST` (comma-separated domains, default empty). The allowlist variable and its parser, `src/lib/rag/security/link-allowlist.ts` (subdomain match, the app's own domain from `NEXT_PUBLIC_SITE_URL` always allowed), are introduced here and reused unchanged by SEC-06 in Phase 5.2. The check extracts every URL, bare domain and e-mail address from the parse text (extending `src/lib/url-extractor.ts`), plus PDF link annotation targets when the hidden-text report carries them. Any target outside the allowlist quarantines the document under `quarantine` with the targets as the reason. Releasing records the reviewed targets on the document (they are skipped on the next version, as Phase 5.1 D-10 does for rule ids) and never edits the allowlist. The Config UI warns that an empty allowlist quarantines every document with an external link.
- **D-36:** Upload approval. `RAG_UPLOAD_APPROVAL` (`off` | `members` | `all`, default `off`). A new status value `pending_review` is added to the `documents` and `document_chunks` status checks; the unconditional `is_current AND status = 'ready'` filter (Phase 3 D-08) already keeps it out of every retrieval, so the semantic cache never sees it. The document is processed fully (parse, scans, chunk, embed, write) and held at `publish`: approval is then one call to `rag_publish_document_version`, and a pending new version never replaces the current one before approval. `IngestResult.status` gains `pending_review`. Quarantine wins over pending; an admin's quarantine release counts as approval. Reject is the soft delete (Phase 3.1 D-27). Approve and release go through the existing publish seam, so cache invalidation follows. — **Reversibility:** one-way — a new status value in two check constraints and in the `IngestResult` contract.
- **D-37:** Who and where. `members` gates uploads to an organization's documents by users who are not admins of it (in single-tenant mode: users not in `admin_users`); a personal workspace's own uploads are not gated. `all` gates every upload. Approvers: organization admins for their organization, deployment admins (`admin_users`) for single-tenant and personal documents, with the same access rule as the Quarantine panel. The gate sits in `submitIngest()`, so it covers chat and Config UI upload, Nango sync, scrapers, image upload and WhatsApp; the uploader of a connector item is the user who owns the connection or session. Exemptions live in `rag_upload_approval_exemptions` (`tenant_key`, `kind`: `connector | uploader`, `ref`, `created_by`). `documents.user_id` stays the uploader; new columns `approved_by` and `approved_at` on documents and `approved_by` on chunks are stamped at publish. Temporary chat attachments that are not written to the knowledge base are not affected. Notifying admins is not in this phase; the panel shows a pending count.

### Scope tags, supersession, effective dates (DATA-18, DATA-19, DATA-20)

- **D-38:** Scope vocabulary. `RAG_SCOPE_TAGS` (`false` default) gates the pickers, the admin routes and the filter. Three fixed dimensions: `region`, `legal_entity`, `department`. `rag_scope_vocabulary` (`tenant_key`, `dimension`, `value` slug, `label`, `aliases text[]`, `active`) is edited per tenant in the Config UI. A tag is stored as `dimension:value` in `documents.scopes text[]` and copied to `document_chunks.scopes text[]` (GIN index). Tags are a filter column only: `rag_set_document_scopes` updates the document and its chunks in one transaction with no re-embed, and tags are not part of the fingerprint. — **Reversibility:** costly — the tag format is stored on every tagged chunk.
- **D-39:** The `scopes` filter is a DATA-08 filter (Phase 4 D-05): `retrievalFilters.scopes` in the request body, Zod-validated, values checked against the tenant's vocabulary (unknown value: 400), narrow-only. Semantics: OR within a dimension, AND across dimensions. By default only tagged documents match; `includeUntagged: true` also admits documents with no tag in that dimension. `hybrid_search_chunks` (and `hybrid_search_translations`) gain `p_scopes text[]` and `p_scopes_include_untagged boolean DEFAULT false`. No chat UI for choosing the filter in this phase; QRY-10 (Phase 6.2) sets it.
- **D-40:** Setting tags. At upload: a tag picker next to the doc-type picker in chat upload and Config UI upload (Phase 3 D-17), hidden when the switch is off or the pipeline is legacy. Afterwards: an admin edits tags in the Config UI. Suggestions (`RAG_SCOPE_TAG_SUGGEST`, `false` default): vocabulary labels and aliases matched in the title and first page, then an optional small-model call (the model the doc-type LLM detector uses) with a Pydantic `ScopeTagSuggestion` limited to vocabulary values. Suggestions are stored in `documents.metadata.scope_suggestions` and are never applied without admin confirmation.
- **D-41:** Supersession candidates. `RAG_SUPERSESSION_DETECT` (`off` | `on`, default `off`). After publish, without blocking ingestion, a rules-only detector compares the new document with current ready documents of the same tenant and doc type: (a) titles equal after removing year and version markers (`version_markers` from the registry: years, `v2`, `第二版`, `修订`, `rev.`, `edizione`), or (b) high content overlap with different numbers, computed from stored document content. Thresholds are data in `config/rag/supersession-rules.json`. Direction comes from the year marker, `doc_date` or `effective_from`; when unknown the candidate has no direction and the admin chooses. Candidates go to `rag_supersession_candidates` (`tenant_key`, `document_id`, `candidate_document_id`, `signals`, `direction`, `status`: `pending | confirmed | dismissed`, `origin`: `detected | uploader | answer_conflict`, `decided_by`, `decided_at`). At upload, "Replaces…" lets the uploader name a document: by an admin it is confirmed at once, by a member it is a pending candidate. Phase 5.2's `stale_version` conflicts write to the same table with origin `answer_conflict`.
- **D-42:** Confirmation. `rag_confirm_supersession(p_candidate_id, p_actor)` (service role) sets the older document and its chunks to `is_current = false` and `superseded_by` to the newer document in one transaction, the DATA-07 way, and records the link between the two lineages in `rag_supersession_links`. `rag_publish_document_version` keeps a later version of a superseded lineage non-current and raises a new candidate instead. `rag_undo_supersession` restores the older document. Nothing is superseded without a confirmation. — **Reversibility:** costly — the publish function learns about lineage links.
- **D-43:** Effective dates. New columns `effective_from date`, `effective_to date`, `effective_dates_origin` (`extracted | admin`) and `effective_dates_confidence` on `documents`; the two dates are copied to `document_chunks`. They are a filter column only (`rag_set_document_effective_dates`, no re-embed, not in the fingerprint). Extraction is rules-first with the registry's `effective_date_patterns` (for example "自 2025 年 1 月 1 日起施行", "effective from", "in vigore dal"); `RAG_EFFECTIVE_DATE_LLM_EXTRACT` (`false` default) adds a small-model call with a Pydantic `EffectiveDateExtraction` (`effective_from`, `effective_to`, `confidence`, `evidence_quote`), accepted only when the quote is found verbatim in the text. An extracted date is applied automatically only when confidence ≥ 0.8 **and** the document stays usable today; a date that would hide the document (future start, past end) waits for admin confirmation. An admin-set date always wins.
- **D-44:** `RAG_EFFECTIVE_DATES` (`false` default) is query-side. When on, v2 retrieval passes today's UTC date as `p_effective_on` to `hybrid_search_chunks`: a chunk matches when `effective_from` is null or not after it and `effective_to` is null or not before it. A future policy is not used yet; an expired one is excluded from default retrieval and reachable only through RET-11 (Phase 4.2). The date joins the semantic-cache key (`src/lib/rag/cache/keys.ts`) and `retrievalConfigHash`. The legacy pipeline and the legacy RPCs are not changed.

## Specific Ideas

- The table example is fixed by the roadmap: "米兰的 P5 员工住宿上限是多少？" must be answered with the lodging limit, not the meal allowance of the same row. A serialized row looks like `城市=米兰，职级=P5，住宿上限=180，币种=EUR`.
- The scan fixture must contain the Italian words è, più and già next to Chinese text.
- The supersession example is a 2023 policy uploaded as a separate file next to its 2025 version; after confirmation only the 2025 version is current.
- The effective-date examples: a policy that starts next month is not used yet; an expired one is historical.
- The document-translation example: an Italian question hits a translation while the answer cites the original Chinese chunk.
- The scope example: a question limited to documents tagged for the Italian branch.
- The hidden-text fixture set is fixed: white-on-white text, tiny fonts, off-page text, zero-width characters and hidden Word runs.
- The owner prefers changes proven by eval before they become defaults; nothing in this phase changes a shipped default.
