# Phase 3.2 Plan 19: Side-by-side rebuild, activation and rollback Summary

**An ingestion-side setting now reaches stored documents only through an explicit rebuild of exactly the documents it affects. A `reparse` rebuild writes new versions that stay unpublished until an activation with recorded passing evidence, and a rollback makes the previous versions current again with the vectors they had.**

## What changed

- **Selection (D-11).** `rag_rebuild_candidates` lists the current ready documents with their stored fingerprint parts. `selectAffected` runs the coverage comparison (`countImpact` under the saved values of the five recorded variables) per document. A document is selected when its stored parts differ from what the saved settings expect for that mechanism. Documents without a fingerprint are never selected; the CLI says to run the backfill first.
- **Plans (`planRebuild`, pure).**
  - `reparse`: a held batch with `RAG_INGEST_ASYNC=on`; otherwise `needs_async` with the count and `npm run rag:rebuild -- start --mechanism reparse`.
  - `rechunk`: one chunking profile `rb-<first 12 hex of the settings hash>` per affected doc type, with the legacy `child_tokens` read from the registry, `parent_mode: 'none'` and `preset: 'custom'`.
  - `relex`, `reembed`, `recaption`, `retranslate`: one fixed command per tenant of the affected documents: `npm run rag:relex -- --tenant <key>`, `npm run rag:reembed -- --tenant <key>`, `npm run rag:reembed -- --recaption --tenant <key>`, `npm run rag:translate -- --tenant <key>`.
  - `rescan` is refused here; it is the separate action of plan 03.2-40.
- **Reparse run.**
  - `rag_rebuild_start` stores the items (only pairs whose document exists, is current and ready, and belongs to the tenant named with it) and opens one `ingestion_batches` row per tenant with `hold_publish = true` and `source_ref = 'rebuild:<run id>'`.
  - The runner loads each stored original and enqueues it as a forced new version at backfill priority (10). The 0803/plan-14 hold keeps the version non-current with `metadata.publish_hold`.
  - `rag_rebuild_settle` marks an item done when its job is `ready` and its version carries the run's hold. Any other terminal job status is a gap (`job_<status>`).
- **Activation (D-12).** `rag_rebuild_activate` locks the run row, then checks after the lock: not a batch run (`not_batch`), `already_activated`, `already_rolled_back`, `eval_missing`, `eval_failed`, `incomplete`. For each done item it takes the lineage lock and saves the replaced version's vectors. It then calls `rag_release_publish_hold` and `rag_publish_document_version`. The app runs `afterPublish` for every published version.
- **Rollback.** `rag_rebuild_rollback` (only from `activated`) takes each rebuilt version out of retrieval: not current, chunks not current, vectors deleted, as the publish function does to a superseded version. It makes the previous version current again, moves the content type and slug back, and restores the saved legacy vectors and `chunk_embeddings` rows. The app runs `afterPublish` for each restored version.
- **Evidence.** `record-eval` reads a `GateResult` (`gate.json` from `npm run test-rag`), validated with the generated `GateResultSchema`. It stores `{ passed, offenders, report_sha256, recorded_at }`.
- **Rechunk run.** Creates the profiles unless they exist, then runs `runRechunkBatch` per profile until the deadline. It reports the summed counts with `rag_rebuild_report`. Activation stays with `rag:chunking activate` (its completeness and eval gates); the run row records `activation: 'chunking_profiles'`, and the activate route answers 409 `not_batch` for it.
- **Idempotency and resume.** There is one open run (`running`, `complete` or `incomplete`) per mechanism and settings hash, enforced by a partial unique index and an advisory lock. A second start returns the first run. Starting an `incomplete` run puts its gaps back to pending, so only those documents are submitted again.
- **Routes** (all `checkAdmin`, `no-store`):
  - `POST …/rebuild` takes the strict body `{ mechanism }`. It runs within a 45 s budget, with `more: true` when items are left. It answers the run row, or `needs_async` / `command` with the fixed command (no tenant key), or `nothing`.
  - `POST …/rebuild/[id]/activate` and `…/rollback` take no body. A refusal is 409 `{ error: 'activation_refused' | 'rollback_refused', reason }`; an unknown or malformed id is 404; a database failure is 503 `rebuild_unavailable`. Success answers counts only.
  - `GET …/ingest-fingerprint` adds `rebuilds: [{ id, mechanism, done, total, gaps, state, started, activation }]`. The state is mapped to the UI-SPEC badges: `complete` becomes `built` (`completed` when the activation is `none`), and `activated` becomes `active`.

## Deviations

1. **Tables.** Besides `rag_rebuild_runs` there are `rag_rebuild_items` (per document: replaced version, held version, batch, job, state) and `rag_rebuild_saved_vectors`. The run row has no `batch_id` or `previous_versions` column: a reparse run spans tenants and a batch has one tenant, so the batch is per item, and the previous versions are the items.
2. **Extra functions:** `rag_rebuild_report` (counts of a rechunk run), `rag_rebuild_settle`, `rag_rebuild_list`, `rag_rebuild_items_page`, `rag_rebuild_candidates`, `rag_purge_hook_rebuild`. All follow the 0425 rule and are service_role only.
3. **Saved vectors.** Not in the plan: without them a rollback would make the previous version current with no vectors, because `rag_publish_document_version` deletes the superseded version's vectors.
4. **The unique open run covers `running`, `complete` and `incomplete`, not only `running`.** So a start after the jobs finished, but before activation, still returns the same run instead of opening a duplicate.
5. **recaption.** It is a command (`rag:reembed -- --recaption`), not a chunking profile; see key decisions. `tests/rag/ingest-fingerprint-routes.test.ts` was updated for `recaption: 'cli'`.
6. **rechunk scope.** It is the whole doc type, not only the affected documents; see key decisions. The plan's "limited to the affected documents" holds for the doc types: documents of other doc types are never rebuilt (asserted).
7. **Files outside the plan list:**
   - `src/lib/rag/ingest/change-doc-type.ts`: `optionsOf` exported.
   - `src/lib/rag/ingest/fingerprint/impact.ts`: `coverageProposal`, and the recaption start.
   - `src/lib/rag/index.ts`: exports for the boundary rule.
   - `_responses.ts` and `rebuild/_rows.ts`.
   - `tests/rag-db/rebuild-runs.test.mts`.
8. **Migration number.** 0809 as planned, which was free.

## Purge hooks (06.3 coverage)

`rag_purge_hook_rebuild(p_tenant_key text, p_lineage_id uuid, p_document_ids uuid[])` is service_role only and uses `SET search_path = ''`. It deletes the tenant's `rag_rebuild_items` rows that name the given documents (as the replaced or the rebuilt version) or lineage, and the matching `rag_rebuild_saved_vectors` rows. `rag_rebuild_runs` holds no document data.
