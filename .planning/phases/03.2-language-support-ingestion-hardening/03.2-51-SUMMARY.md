# Phase 03.2 Plan 51: chunk translations as additive retrieval legs

**Under v2 (chat, embed, eval), a tenant's stored chunk translations into the query language now add `dense_tr:<lang>` and `lexical_tr:<lang>` lists to RRF. The lists hold source chunk ids, so only original text reaches the context, citations, snapshots and `source_images`. A failing leg can only degrade the stage. With the switch off, or for a tenant without translations, the search request, fused list and hash are unchanged.**

## Accomplishments
- `translation-legs.ts`: gating and the one state lookup (`planTranslationLegs`); parallel legs with their own timeout inside the search stage budget (`runTranslationLegs`). `translationLists` clears the translation's scores, renumbers ranks and drops any hit on a chunk already in the query language. `preferOriginalHits` makes a chunk that both kinds of leg found keep the original leg's hit.
- `search.ts`: translation legs start next to the main and binding legs in both the native and the delegated path. Their lists are appended after the main, exact-id and domain lists. Counts get `translation` only when legs are planned. Status and detail are combined with the binding-leg rules, and the ICU-skip path appends the translation detail.
- `pipeline.ts`, `result.ts` and `config-hash.ts`: the plan is memoised per embedding profile, and the cache key and the final result hash both read it.
- `pgvector.ts`: `searchTranslations` calls `hybrid_search_translations` with the request's tenant key and the filter arguments unchanged. It validates each row (`TranslationRowInvalidError`).
- Eval: `translation_compare.py` writes the per-pair report as JSON and Markdown. `run-translation-compare.mts` builds the fixture tenant, enables `s:default` for zh, en and it, then runs the producer with the fixture translator and records rows, bytes, estimated USD and wall time per direction. It scores arm A (v2 + `RAG_LEXICAL_TRANSLATION=true`) and arm B (+ `RAG_DOC_TRANSLATION=on`) and calls the report.

## Behaviour changes
- None with `RAG_DOC_TRANSLATION=off` (default): no new request, and the search stage record and hash are byte-identical (unit and e2e tests).
- With the switch on, a multilingual deployment and v2 chat, embed or eval: one `rag_translation_query_state` call per request. If the tenant is enabled and has translations in the query language, one `hybrid_search_translations` call per language runs in parallel with the main search. Voice, legacy, strict "information not available", webSearch with Exa, `source_images` and `{{context}}` are untouched: translation hits enter as source chunks before assembly.
- Translation-only hits have similarity null. Under the v2 similarity floor they never lift a refused query over the floor (Phase 3.1.1 D-20, as the plan requires). The e2e tracer therefore uses the eval profile with a fixture floor: with the fixture embedder, cross-language similarity is near zero.
