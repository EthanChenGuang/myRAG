# Phase 05.1.1 Plan 08: Tenant opt-out, retention purge and CLI — Summary

**A tenant can lower or switch off retrieval logging (fail closed), and expired log rows and expired open review items are purged on demand (CLI, admin route) or by an opt-in pg_cron schedule.**

## Accomplishments

- `settings.ts`: `effectiveLogMode` combines `RAG_RETRIEVAL_LOG` with `rag_tenant_feedback_settings` (inherit keeps it, ids lowers masked_query to ids, off disables; never raised). The tenant row is cached for 60 s per process. A failed read gives off for that request, with one `[Feedback Loop]` line. `setTenantFeedbackSettings` upserts with `updated_by` and drops the cached copy.
- `retrieval-log.ts`: `writeRetrievalLog` resolves the effective mode before the insert. An off tenant gets no row; an ids tenant's row has no `query_masked` or `query_fingerprint`.
- `purge.ts`: `purgeRetrievalLog` loops `rag_purge_retrieval_log(days, 1000)` until a batch comes back short (bounded), then deletes `rag_review_items` with status open and `expires_at` in the past. Returns `{logRows, reviewItems}`.
- Routes: `GET`/`PUT /api/rag/admin/feedback-loop/tenant-settings` and `POST /api/rag/admin/feedback-loop/purge`. The admin guard runs first; responses are `Cache-Control: no-store`.
- CLI: `npm run rag:feedback-loop -- purge` with `RAG_RETRIEVAL_LOG_RETENTION_DAYS`; prints counts only.
- `supabase/optional/feedback-loop-schedule.sql`: commented, opt-in pg_cron jobs (weekly purge, then optional mining). No secret. No setup script or migration test applies it.
- `src/lib/rag/index.ts` exports the new functions, so the routes pass `check-rag-boundary`.
