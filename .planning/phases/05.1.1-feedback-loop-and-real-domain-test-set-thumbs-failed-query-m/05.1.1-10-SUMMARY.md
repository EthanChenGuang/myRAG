# Phase 05.1.1 Plan 10: Embed feedback token and vote route — Summary

**Anonymous embed visitors can rate an answer when `RAG_EMBED_FEEDBACK` is on with a usable secret. A signed token ties each vote to one retrieval of one tenant. With the defaults, the embed response is unchanged.**

## Accomplishments

- `src/lib/rag/feedback-loop/embed-token.ts`: `mintEmbedFeedbackToken` and `verifyEmbedFeedbackToken`, modelled on `voice-token.ts`. Audience `embed-feedback`, 24 h expiry, 30 s clock skew, 4096-character cap, `timingSafeEqual`. A trace id must be 32 lowercase hex, and a tenant key must match the strict tenant-key pattern. The secret is `RAG_EMBED_FEEDBACK_SECRET`, used only while the switch is on.
- `src/app/api/embed/chat/route.ts` (edit points found by symbol): `feedbackTraceId` is set from the collector beside `pendingTrace`. After the `answered` outcome, the route mints a token when `readFeedbackLoopConfig().embedFeedbackEnabled` is true and `effectiveLogMode(scopeKey(embedScope.scope))` is not off. Only then does `toUIMessageStreamResponse` get `messageMetadata`, which sets `{ feedbackToken }` on the `start` part.
- `src/app/api/embed/feedback/route.ts`: `OPTIONS` copies the embed route's preflight. `POST {token, vote, reasons?}` validates the body with the generated `EmbedFeedbackRequestSchema`, which accepts the chips `wrong`, `incomplete` and `not_relevant` and rejects any other key. It reads no cookie or session. It updates `feedback_vote` (1 or -1), `feedback_kind='embed'`, `feedback_reasons` and `feedback_at` only on the row matching the token's `trace_id`, the token's `tenant_key` and `channel='embed'`.
- `src/lib/rag/index.ts` exports the token functions, so the routes import through `@/lib/rag`.

## Behaviour changes

- None with the defaults. With `RAG_EMBED_FEEDBACK=false`, or a secret shorter than 32 characters, the embed chat route makes no settings read. It passes `toUIMessageStreamResponse` the same options as before, so the stream bytes are identical (tested). `/api/embed/feedback` answers 404.
- With the switch on, a usable secret and the tenant's log mode not off, the embed stream's `start` part carries `messageMetadata.feedbackToken`. The new route then stores one changeable vote per embed row.
- Strict "information not available", webSearch with Exa, `source_images`, `{{context}}`, voice and web chat are untouched (the full vitest suite passes).

## Deviations

1. **One extra test file.** The stream-side tests are in `tests/rag/feedback-loop/embed-stream-token.test.ts`, not in `tests/api/embed-feedback-route.test.ts`. The stream tests need the route fixture with module mocks of `ai` and the feedback-loop settings. The route tests need a fake `@/lib/supabase` admin client. Keeping them apart stops one file's mocks from leaking into the other.
2. **Origin and embed-enabled checks on the vote route.** The plan did not ask for them. They copy the embed chat route's checks and answer the same 404, so the vote route is never open where the embed is closed.
3. **Separate rate-limit bucket.** The key is the chat route's identifier with the prefix `embed-feedback:`, with the same limit and window. Votes do not use up the visitor's chat quota.
4. **The token is minted only when the tenant's effective log mode is not off,** as the must-haves require. No row exists for an off tenant, so its votes would always 404.
