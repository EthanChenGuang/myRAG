# Phase 5.1.1: Feedback Loop & Real Domain Test Set - Research

**Researched:** 2026-11-24
**Domain:** production feedback capture, retrieval logging with privacy, failed-query mining, expert labelling with tenant isolation, real-user evaluation sets and release gating
**Confidence:** HIGH for codebase findings (read at e90d9cd), MEDIUM for external practice (sources below were not re-fetched in this session; claims are the stable, widely documented parts)

## Summary

Every building block except the log and the expert queue already exists or is planned: one trace seam that runs for every retrieval (`finishTrace`), an `after()` scheduler, a TypeScript and Python PII masker pair, a frozen hash split, gate-population logic that already prefers production items, a review queue CLI with a private-path guard, and Phase 5's answer record, vote route and UI control. What is missing is (1) a durable, queryable record of each retrieval that does not depend on Langfuse sampling, (2) feedback where Phase 5 does not reach (refusals, embed), (3) a database queue whose rows are visible only to the tenant's experts, (4) a split rule that keeps a document's questions on one side, and (5) a gate mode that refuses to pass on synthetic items once a real set exists.

**Primary recommendation:** write one row per retrieval from `finishTrace` after the response, behind `RAG_RETRIEVAL_LOG=off` by default; mine it weekly into `rag_review_items` protected by an RLS helper over `rag_domain_experts`; keep promotion in Python (`review_queue promote-db`) with a document-group split; and gate on real items only through an explicit `gate-population.json` switch with a minimum size.

## External Best Practice

| Topic | Practice | Source |
|-------|----------|--------|
| Feedback as trace scores | Attach explicit user feedback to the trace as a score (numeric or categorical) with an optional comment; keep your own store as the system of record | Langfuse docs, "User feedback" and "Scores" (langfuse.com/docs/scores/user-feedback) |
| Data minimisation and retention | Collect only what the purpose needs, keep it no longer than necessary, honour erasure; pseudonymise where possible | GDPR Art. 5(1)(c), 5(1)(e), 17, 25 (eur-lex.europa.eu/eli/reg/2016/679/oj) |
| Implicit clicks are biased | Clicks are strongly position-biased; treat them as relative, weak evidence and combine with other signals | Joachims et al., "Accurately Interpreting Clickthrough Data as Implicit Feedback", SIGIR 2005 |
| Hard negatives | Mine negatives from the retriever's own top results, exclude likely false negatives (items close to the positive or labelled relevant) | Moreira et al., "NV-Retriever: Improving text embedding models with effective hard-negative mining", arXiv:2407.15831 (2024); Karpukhin et al., DPR, EMNLP 2020 |
| Training format | (anchor, positive, negative...) rows for MultipleNegativesRankingLoss | sentence-transformers docs, "Losses: MultipleNegativesRankingLoss" (sbert.net) |
| Split leakage | Split by group (document, source, near-duplicate cluster), not by row, when rows share content; otherwise test scores are inflated | scikit-learn `GroupShuffleSplit` docs; Kapoor & Narayanan, "Leakage and the reproducibility crisis in ML-based science", Patterns 2023 |
| Real versus synthetic eval | Synthetic test sets are coverage tests; gate releases on items sampled from real traffic and labelled by people who know the domain | Ragas docs, "Testset generation" caveats (docs.ragas.io); Shankar et al., "Who Validates the Validators?", UIST 2024 |
| Paired comparison | Compare systems on the same items with paired bootstrap confidence intervals rather than two independent means | Koehn, "Statistical Significance Tests for Machine Translation Evaluation", EMNLP 2004; Dror et al., "The Hitchhiker's Guide to Testing Statistical Significance in NLP", ACL 2018 |
| Row-level tenant isolation | Enforce tenant visibility in the database (RLS with a definer helper that pins `search_path`) and not only in the API | Supabase docs, "Row Level Security" and "Database functions: security definer" (supabase.com/docs/guides/database/postgres/row-level-security) |

## Architecture Patterns

### Pattern 1: Log on the trace seam, after the response
`finishTrace(collector, result, { query, log: { userId, chatId, ragMode, skip } })` builds a pure `RetrievalLogRow` (masked, capped, mode-filtered) and schedules the insert with a 2 s timeout. `runRetrieval` passes `input.logContext` when it owns the trace. Failures write one `[Retrieval Log]` line with the trace id hash and error class.

### Pattern 2: Outcome holder
`result.logOutcome = { value: 'unknown' }` is created by the pipeline; routes assign `.value` in their refusal, unavailable and degraded branches; the row builder reads it inside the scheduled task.

### Pattern 3: RLS-scoped expert reads, admin-scoped text
Expert routes read `rag_review_items` with the SSR client (RLS: `rag_is_domain_expert(tenant_key)`); then, with the admin client, they fetch only `document_chunks` whose ids are in the item snapshot (or the expert's review search result for that item) and whose tenant key equals the item's. Both checks are tested with two tenants and with an expert of one tenant asking for the other tenant's item id (404).

### Pattern 4: One Python promotion
TypeScript validates labels and exposes an admin export; Python promotes, dedups, splits and writes the private file. This keeps Phase 7 D-22's "single implementation" rule.

### Anti-patterns
- Writing the log on the request path (adds latency; violates OBS-01's never-block rule).
- Storing chunk text or answers in the log (unbounded PII; Langfuse already has masked content when enabled).
- Taking a tenant from the request body in expert, embed-feedback or search routes.
- Re-splitting an existing manifest under a new rule (silently moves items between dev and test).

## Risks

| ID | Risk | Likelihood | Impact | Mitigation |
|----|------|------------|--------|------------|
| R-1 | Cross-tenant exposure through the expert queue | low | critical | RLS helper, SSR client for reads, tenant-restricted chunk fetch, two-tenant tests per route, 404 not 403 |
| R-2 | PII in stored queries (names are not masked) | medium | high | off by default, `ids` mode, masking, 30-day retention, tenant opt-out, expert PII check and paraphrase before promotion, no text in logs |
| R-3 | Log write slows responses or fails requests | low | high | `after()`, 2 s timeout, never-throw, latency test with a hanging fake |
| R-4 | Table growth | medium | medium | ~1 KB per row (50 candidate ids), purge in batches, `created_at` index |
| R-5 | Embed vote abuse | medium | low | signed per-trace token, one changeable vote, chips only, rate limiter |
| R-6 | Leakage between training export and domain test split | medium | high | shared document groups; `held_out` marking; test that no test-group pair is exported as `train` |
| R-7 | Real set too small or skewed, so the gate is noisy | high initially | medium | `min_items`, mode stays `legacy` until the live plan switches it; per-language counts in the report |
| R-8 | Sibling phases (4.1.1, 6.1, 4.1, 3.1.1) pick overlapping migration numbers or define their own query log | medium | medium | block 0531-0535, re-check at execution; the contract files for dictionary and training hand-offs are shared (A-3, A-4) |
| R-9 | Phase 6 edits the same route files concurrently | high | medium | ROADMAP note: Phase 6 plans that edit `route.ts`, `index.ts`, `finish.ts` or the five config files run after this phase's closing plan |
| R-10 | Mining thresholds are uncalibrated (the fixture embedder refuses almost everything under v2) | high | low | thresholds are report-only config; reasons are recorded per item so experts see why it was picked |
