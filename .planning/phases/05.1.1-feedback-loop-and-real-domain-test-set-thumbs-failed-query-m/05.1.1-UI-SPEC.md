## 0. Findings that shape this contract (read first)

Facts from the code at `03512b5`. Each one changes what the UI can show or do.

1. **Three design systems, four surfaces.** The Config UI is a static page with DaisyUI 4.4.24 over the Tailwind Play CDN and
   Bootstrap Icons. The web chat is Next.js with local shadcn-style components, Radix and lucide. The embed widget is a
   script string served by `src/app/embed/chat.js/route.ts`: inline styles, light colours only, no library. The embed window
   is a Next.js page with Tailwind's gray palette, light only. Tokens are declared per surface and never mixed.
2. **`rag-panels/rag-ui.js` does not exist.** The approved 03.2 contract plans it, but Phase 3.2 is held and not executed.
   The two new panel scripts carry their own helpers, as `chunking-profiles.js` and `refusal-calibration.js` do.
3. **The RAG Modes settings cards of Phases 5 and 5.1 are static English markup** (`Citations and groundedness`,
   `Prompt-injection defense`); the page has no `data-rag-i18n` mechanism yet. Panel scripts carry `en`, `zh` and `it`.
4. **The web chat drops the refusal flag today.** `src/app/page.tsx` reads the stream with its own reader;
   `extractStreamAnswerMetadata` in `src/lib/chat/answer-metadata.ts` keeps only `ragTraceId` and the citation fields, and
   `persistedMetadataOf` in `src/types/chat.ts` saves only `ragTraceId` plus the fields `pickAnswerMetadata` knows. A
   `refusal: true` sent by plan 09 never reaches `chat-message.tsx`, and a stored `refusalFeedback` would not survive a
   reload. Neither file is in plan 15's `files_modified` (section 15, item 1).
5. **The knowledge-base-unavailable stream is an `error` event.** The page turns it into assistant text beginning with a
   warning sign, so an assistant message exists for that turn and the control can sit under it like under a refusal.
6. **The action row under an answer is hidden until hover** (except on the last message) and renders only for finished
   messages with text. The Phase 5 thumbs live in it. A question to the user must not be hidden behind hover.
7. **`ragFetch` answers 401, 403 and 503 with fixed English sentences**; the 401/403 one begins "Admin sign-in required".
   A domain expert does not need the admin role, so that sentence alone would send experts the wrong way.
8. **Review routes say "switched off" and "not yours" with the same 404** (plans 12 and 13). The panel tells them apart by
   which call returned it: the list call means the feature is off; a call for one case means that case is gone.
9. **The review routes return no workspace names**, and the panel sends no tenant parameter (threat T-0511-62).
10. **Grants are made by user ID.** `POST /api/rag/admin/domain-experts` takes `{tenantKey, userId}`; `GET` lists user ids with
    e-mail addresses masked to the domain. No plan adds a user search.
11. **`#workspace-selector` lists organization ids and exists only in multi-tenant mode.** An organization's tenant key is
    `o:<id>`; a personal key `u:<uuid>` cannot be derived in the browser; single-tenant is always `s:default`. The page reads
    the mode from `window.currentConfig`.
12. **The purge route returns two totals** (`{logRows, reviewItems}`, plan 08), not rows per workspace and reason. Only the
    mining result has that shape (plan 11). Plan 18 describes one table shape for both buttons (section 15, item 3).
13. **The embed widget has no language handling and English text only** ("Assistant", "Typing..."). The server already
    picks the language of its fixed messages from `Accept-Language`.
14. **The embed widget logs every received chunk to the console.** With plan 10 the first chunk carries `feedbackToken`.
15. **The widget reuses the ids `myrag-assistant-response` and `myrag-response-bubble` for every answer**, so an id lookup
    finds the first answer, not the newest.
16. **The embed window uses `useChat`**, so the start metadata arrives as `message.metadata.feedbackToken`.
17. **English button labels in the app are Title Case** since the web-design-guidelines pass of plan 05-23
    (`answer-quality.ts`: "Not Helpful", "Send Feedback"). Config UI panels are sentence case, recorded by plan 04-36 as
    "intentional per the approved UI-SPEC, not a defect".
18. **Panel scripts are classic scripts loaded in `<head>` into one global scope**, before the menu links exist, and the
    older panels bind only the first `[data-tab="rag-administration"]` link, so the drawer link never starts them.
19. **Mining answers 404 when it is disabled** (expert review off, or the log not at `masked_query`); the purge route has no
    such gate.
20. **Passage text is tenant document text.** It can hold markup, instructions or control characters. The label route
    checks every quote as an exact substring of that text after NFKC and whitespace collapsing (plan 13), so the panel
    must show the text unchanged.

## 1. Design direction (frontend-design pass)

**Subject.** The way from "this answer failed" to "this test question proves the fix": a user says a refusal was wrong, a
visitor says an answer did not help, and a person who knows the documents points at the sentence that answers it.

**Audiences and their one job.**

| Who | Where | Arrives with | The job of the surface |
|-----|-------|--------------|------------------------|
| Chat user | Web chat, under a refusal | "I know this is in my documents" | Take that statement in one click |
| Anonymous visitor | Embed widget or window | An answer just read | Take helpful or not helpful, nothing more |
| Domain expert | Config UI, Review queue, desktop | A queue of failed questions | Find the passage, quote it, say what the case is for |
| Operator admin | Config UI, Feedback loop and RAG Modes | A deployment to run | Decide who reviews, what is logged, when mining runs |

**Mode.** Impeccable "Operate" for the two Config UI panels and the settings card: working tools inside an existing
dashboard, built from its sections, tables, badges, alerts and dialogs. The chat and embed controls are one quiet row each
inside an existing conversation.

**Organizing idea: one failure, one question, one action.** Every surface asks exactly one thing and takes the answer in
one action. The chat asks whether the refusal was right. The widget asks whether the answer helped. The panel asks which
words in the documents answer the question. Everything else on screen is evidence for that one decision.

**Signature element: the quote slip** (section 6.6.5). The expert selects words in a retrieved passage and they become a
slip in the label: a block with a left rule, the passage it came from, the quoted words in an editable field and one line
that says whether those words stand in the passage word for word. It is the only composite this phase adds, it appears
nowhere else, and it makes the phase's central rule visible: evidence is quoted from the documents, never retyped from
memory. Everything around it stays plain.

**Review against generic defaults (what was changed and why).**
- Rejected thumbs on a refusal. A thumb under "information not available" can mean "bad that you refused" or "bad that
  the documents lack it". The two choices are written as sentences (D-08).
- Rejected a popover, modal or toast for the refusal vote. There is no free text (D-08), so nothing needs a form; the
  pressed button is the confirmation.
- Rejected the operator's brand colour for the embed rating. Its contrast against white is unknown, so the chosen state
  is a dark filled icon.
- Rejected stars and five-point scales in the embed. D-11 is binary with three chips.
- Rejected a kanban board for the queue (open, labelled, skipped, exported). Cases are comparable rows; one table with a
  status filter lets fifty be read at once.
- Rejected a three-pane annotation studio with resizable panes. The panel is a list, then one case: evidence on the left,
  the label on the right from 1024px, stacked below that.
- Rejected a stepper for the label (answer, evidence, type, outputs, personal data). The parts are not a fixed sequence;
  the personal-data block appears only when the case goes to the test set.
- Rejected colouring retrieval scores red or green. The mining thresholds are uncalibrated (research R-10); a score is a
  plain number.
- Rejected monospace for passages. Experts read them; only ids, codes and keys are monospace.
- Rejected highlighter colours per quote and a highlight painted into the passage. The slip names its passage and can
  scroll to it.
- Rejected stat tiles and charts in the admin card. A mining run returns counts; they are a table. Trends live in the
  weekly report file (D-25), not in this UI.
- Rejected emoji, middle-dot meta strings, arrows on buttons, all-caps labels and a label above a heading.

**Quality floor (built without announcing it).** Visible keyboard focus, `prefers-reduced-motion` respected, all text at
least 4.5:1, tabular numerals in number columns, usable down to 360px, every state of section 7 present, every server and
document string inserted with `textContent` (Config UI, widget) or as a React text child (app).

## 4. Spacing Scale

Same scale as the earlier contracts. Config UI and embed window: Tailwind utilities only. Embed widget: pixel values in

| sm | 8px | `gap-2`, `mt-2`, `mb-2`, `p-2`, `px-2` | Buttons in a row; badges side by side; chat control to the bubble above it; chip gap; padding inside a quote slip; horizontal padding of chips |

uses `px-2.5` and `gap-1.5`; the new control uses `px-2`, `px-4`, `gap-1` and `gap-2` instead and is not required to match

- DaisyUI `table-sm` cell padding, `input-sm`, `select-sm`, `textarea-sm`, `checkbox-sm`, `radio-sm`, `toggle`, `btn-sm`

- Each panel root carries `lang="<locale>"`. The masked question, the masked answer, passages and quotes carry
  `dir="auto"` and `translate="no"`; a passage with a known language code also carries `lang="<code>"`.

- **Check line**, recomputed on every input:

  | State | Rule | Looks like |

  | Found | After NFKC, whitespace collapsing and trimming of both sides, the quote is a substring of the slip's passage text and has at least 2 characters | `bi-check2` and `quote.ok` in `text-base-content/70`; left rule `border-base-300` |

- A label holds at most 20 quotes; at 20, every "Add evidence quote" is disabled with `evidence.max` referenced by

- The body sent for a slip is `{chunk_id, document_id, document_name, section, quote}` with the field's text as typed; the
  normalised form is used only for the check.

## 9. Keyboard, screen reader and focus

1. **Headings.** Panel titles are `h3`; blocks inside a panel are `h4`; passage and result titles are `h5`. No level is
   skipped. The chat and embed controls add no heading.
2. **Chat control.** The two choices are buttons with `aria-pressed` inside `role="group"` named `refusalGroupLabel`. The
   chips are buttons with `aria-pressed` inside a `fieldset` with a visible `legend`. One polite live region announces
   saved and failed. Tab order: first choice, second choice, chips, "Try Again", then the existing Sources button and
   action row.
3. **Embed control.** The thumbs are icon buttons with `aria-label`, `title` and `aria-pressed` inside `role="group"`; the
   chips are buttons with `aria-pressed` inside a named group. The status text is `role="status"`.
4. **Queue.** The filters have visible labels. The table has a visually hidden `caption`, `th scope="col"`, and the
   question cell as `th scope="row"`. It sits in `div.overflow-x-auto[tabindex=0][role=region][aria-label]`.
5. **Case.** Text regions that can scroll (passage, result, masked answer) are focusable (`tabindex="0"`, `role="region"`,
   an `aria-label` that names them). Row and block actions carry what they act on in their accessible name ("Add
   evidence quote from passage 3", "Remove quote 2", "Revoke access: ***@example.org").
6. **Keyboard path to a quote.** A quote never needs a pointer: "Add evidence quote" without a selection adds an empty
   slip and focuses its field, where the words can be pasted or typed; the check line says whether they match.
7. **Forms.** Every control has a visible `<label for>`; radio and checkbox groups are `fieldset` with `legend`. Help lines
   and messages are wired with `aria-describedby`; invalid fields carry `aria-invalid="true"`. Enter in a single-line field
   of the label form does not save the label; in the search field it runs the search.
8. **Primary buttons are not disabled to signal missing input.** "Save label", "Grant access", "Load workspace" and "Run
   mining now" stay enabled; pressing them with invalid input marks the fields and moves focus to the first. Buttons are
   disabled only while a request runs, on an exported case, and at the 20-quote limit (reason referenced by
   `aria-describedby`).
9. **Dialogs.** Native `<dialog class="modal">` with `showModal()`, `aria-labelledby` and `aria-describedby`. Focus starts on
   the safe button (the "Keep…" one). Escape and the backdrop cancel; while a request runs they do nothing. On close,
   focus returns to the opening button, or to the status region when that button is gone.
10. **Live regions.** One polite status region per panel. Announced: load finished with the count, action outcomes,
    errors. The result of a refused save (`save.blocked`) is `role="alert"`, because it answers an action just taken.
11. **Not colour alone.** Every status, reason, chosen state and error has a word or an icon as well.
12. **Focus visibility.** DaisyUI's `focus-visible` outline on every Config UI control; `summary`, text regions and the
    panel headings add `focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2`. The chat control
    uses the shipped `focus-visible:ring-2` in the Phase 5 orange; the embed uses a 2px dark outline. Never `outline: none`
    without a replacement.

## 11. What must never be shown or done

1. **Document and user text is inert.** The masked question, the masked answer, passages, search results, quotes,
   document names, sections and e-mail addresses are inserted with `textContent` (Config UI, widget) or as React text
   children (app, window). Never `innerHTML`, never `dangerouslySetInnerHTML`, never a template string that becomes markup,
   never an `href`, `src` or `title` built from them, never auto-linked. Tests stub each of them with
   `<img src=x onerror=alert(1)>` and a `<script>` tag and assert that no element is created (threats T-0511-58,
   T-0511-61, T-0511-66).
2. **Passage text is shown unchanged** (finding 20). No trimming, replacement or highlighting inside the text region.
3. **Views render named fields only,** through builder functions, never by iterating an object's keys.
4. **Never rendered, even when a response carries it:** trace ids, user ids other than in the experts table, chat ids,
   answer ids, `labelled_by`, `retrieval_config_hash`, query fingerprints, `split` and `split_group`, `expires_at`, the raw
   `candidates` or `label` object, `fused_score`, the mining config hash, tenant keys in mining results (hashes only,
   plan 18), tenant keys in the queue except as 6.6.1 says.
5. **Secrets and tokens.** The value of `RAG_EMBED_FEEDBACK_SECRET` is read and rendered by no new script. The embed
   feedback token is never written to the DOM, to storage or to the console (6.5).
6. **No free text from end users.** The chat and embed controls have no text field (D-08, Q-08). The request bodies carry
   only the vote and chip codes; never the question, the answer, a tenant or a chat id.
7. **No `Authorization` header, no token in browser storage, no second sign-in form, no cookie on the embed vote.**
8. **Nothing is logged** to the console from questions, answers, passages, quotes, e-mail addresses or tokens; panel logs
   carry counts and codes only (D-27).
9. **No workspace is chosen for an expert.** The Review queue sends no tenant key and offers no workspace filter.
10. **No domain content in product copy.** Labels, help lines, placeholders, empty states and test fixtures of this phase
    use neutral wording ("document-a.pdf", "Section 2.1", "example.org"); nothing names a business domain, a document
    type of a customer or an example question (REQUIREMENTS.md, domain neutrality).
11. **No export, promotion, split change, deletion of a case or statistics view** in either panel (plans 17 and 18).

## 12. Copywriting Contract

Voice: plain verbs, names from the user's side of the screen. A message that reports a problem says what happened and
what to do next; errors do not apologize. One action keeps one name through its flow: the button, the dialog's confirm
button and the outcome message say "Grant access", "Grant access", "Access granted".

**Casing.** Config UI: sentence case, as every sibling panel; plan 04-36 recorded this against the Title Case rule of
web-design-guidelines as "intentional per the approved UI-SPEC, not a defect", and the UI plans of this phase record it the
same way. Web chat and embed: English button, chip and group labels are Title Case, as plan 05-23 left
`answer-quality.ts`; sentences (status and error lines) are sentence case. Chinese and Italian have no Title Case.

**Words used, and words avoided.** "Case" for a review item; "queue" for the list. "Passage" for a chunk; "chunk" is not
shown. "Evidence quote" and "quote" for a span; "span" is not shown. "Workspace" for a tenant; "tenant key" only where
the admin types one. "Test set" for golden; "golden" is not shown. "Knowledge-base gap" for `kb_gap`. "Mining" for the
weekly job. "Expert" for a domain expert. "Rewritten question" for the paraphrase. "Personal data" for PII.

**Action labels are verb + noun in every locale.** Accessible names extend the visible label and start with the same verb.
In-flight text ("Saving…") is status on a disabled button. No button is labelled "Cancel", "OK", "Submit" or "Close" alone:
a button that backs out says what stays ("Keep editing", "Keep access", "Keep data", "Keep queues as they are").

**Counts are written as "label: number"** ("Asked: 3", "Search results: 4"), so no string needs a plural form.

**Where the strings live.** Config UI: one `{ en, zh, it }` table per file (`REVIEW_LABELLING_LABELS`,
`REVIEW_ADMIN_LABELS`), read through one function per file that fills `{placeholders}` and falls back to English; the
reason labels are in the first table and reused by the second. A placeholder shown as `{tab}`, `{card}` or `{command}` is
replaced by an element, not by text. Web chat: new keys in `src/translations/answer-quality.ts`. Embed: one local table in
each of the two files, same keys and copy. Settings card: static English in `index.html`. Numbers use
`Intl.NumberFormat(locale)`; dates `Intl.DateTimeFormat(locale, { dateStyle: 'medium' })`. Copy uses curly apostrophes and
quotation marks and the single-character ellipsis.
