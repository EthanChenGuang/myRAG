# Phase 05.1.1 Plan 07: Route wiring for the retrieval log — Summary

**Chat, embed and voice retrievals now write one log row per request when `RAG_RETRIEVAL_LOG` is on. Each row carries the requesting tenant, the user, the outcome the user saw and the answer's language code. With the switch off, nothing changes.**

## Accomplishments

- `src/app/api/chat/route.ts` (edit points found by symbol):
  - After the scope and chat id are known, the route builds `ragLogContext` when the log is on.
  - `finishRagTrace` passes `{ logContext, logQuery }` to `finishTrace`.
  - The outcome is set before `finishRagTrace` runs for that path. `kb_unavailable` is set in the strict knowledge-base-unavailable branch with `knowledgeBaseUnavailableLanguage(fallbackLanguage)`. `refused_no_context` is set in `if (shouldBlockNoContextResponse)` with `noKnowledgeBaseResponseLanguage(fallbackLanguage)`. `degraded_answer` is set where retrieval failed and the answer continued. `answered` is set once the stream starts.
  - The answer language comes from `detectLanguage` in streamText's `onFinish: async (event)` and, for the direct Claude path, in the UI stream's `onFinish`. It is null on abort or failure.
- `src/app/api/embed/chat/route.ts`:
  - The log context is `{channel:'embed', userId, organizationId, ragMode:'balanced'}`, built from the verified embed scope.
  - `kb_unavailable` is stored with the rendered language of the message for `preferredLanguage(request)`.
  - `answered` is set after `streamText` returns. The answer language is set in `onFinish: (event)`.
- `src/app/api/internal/voice-rag/route.ts`: the `{channel:'voice', userId, organizationId}` log context from the verified voice scope is passed into `runRetrieval`. The route sets `kb_unavailable` or `answered` and never an answer language.
- `src/lib/rag/generation/messages.ts`:
  - New `knowledgeBaseUnavailableLanguage` and `noKnowledgeBaseResponseLanguage` return a code from each builder's own table.
  - The builders use these helpers. Message text is unchanged, and `tests/rag/prompt.test.ts` passes unchanged.
- `src/lib/rag/trace/finish.ts`: new `logQuery` option, read only by the retrieval log.

## Deviations

1. **Imports go through `@/lib/rag`, not by path.** The plan said to import the new helper by path. `node scripts/ci/check-rag-boundary.mjs` (a required gate) rejects deep imports below `@/lib/rag` from routes. So `knowledgeBaseUnavailableLanguage`, `noKnowledgeBaseResponseLanguage` and `readFeedbackLoopConfig` are exported from `src/lib/rag/index.ts`. This adds three lines to the index, which the plan reserved to plan 05. The index already pulls in `node:` modules, and no client component imports it.
2. **The plan names `buildNoKnowledgeBaseResponse` "in the chat route".** At execution time it is `noKnowledgeBaseResponse` in `src/lib/rag/generation/messages.ts`, moved there by an earlier plan. It is the same function under a new name in a new place, so I did not stop. Its language helper lives beside it in messages.ts.
3. **`finishTrace` gained `logQuery`** (src/lib/rag/trace/finish.ts, not in files_modified). The 05 SUMMARY asked routes to pass `query`. That option also feeds Langfuse content capture, so passing it would change Langfuse output with the log off.
4. **Voice outcomes.** The plan sets no voice outcome. I set `kb_unavailable` on the 503 path and `answered` when results are returned (D-07), so voice rows are not all `unknown`.
5. **Two-tenant scenario.** The plan's "member of org B" uses the fixture's organization O, with user A as a member. The rows cover u:A (chat), o:O (chat), u:B (embed) and u:A (voice), plus o:O for embed and voice in the language test. The insert client emulates the 0532 multi-tenant generated column, and the real `writeRetrievalLog` checks it.
6. The plan's verification names `npm run typecheck:new`. I ran the brief's `npx next typegen && npx tsc --noEmit -p tsconfig.json` instead (0 errors).
