# Phase 5.1.1 Plan 04: Review queue, expert RLS and weekly mining Summary

**Tenant-scoped review queue enforced by Postgres RLS (`rag_is_domain_expert`), expert grants, tenant opt-out settings, and an idempotent, tenant-correct `rag_mine_failed_queries`.**

## Accomplishments

- 0534 creates `rag_tenant_feedback_settings`, `rag_domain_experts` and `rag_review_items`. All `tenant_key` columns carry the `ingestion_jobs_archive` tenant-key check. RLS is on for all three tables. `REVOKE ALL` from PUBLIC, anon and authenticated, `GRANT ALL` to service_role; authenticated gets only `SELECT` and `UPDATE (status, triage, label, labelled_at)` on review items.
- Policies `rag_review_items_expert_select` and `rag_review_items_expert_update` (USING and WITH CHECK) call `public.rag_is_domain_expert(tenant_key)`.
- Guard trigger: sets `labelled_by = auth.uid()` for clients. A client may only set the status to `labelled` or `skipped`, and cannot change an exported item. `split` and `split_group` are frozen once either is set, for every caller.
- The review-item snapshot keeps `query_language`, `query_language_confidence`, `answer_language` and `chunk_languages`, with the same checks as 0531. `tags text[]` (pattern `^[a-z_]{1,32}$`, no null or empty element) is outside the client column grant.
- `rag_feedback_loop_on_chat_delete()` is redefined with SECURITY DEFINER and `search_path ''` restated. Deleting a chat as its authenticated owner removes its log rows and review items in both modes.
- 0535 `rag_mine_failed_queries`: one plpgsql function. Filter CTEs run on the window and masked query, the reason flags join answer records on trace and tenant, then the rows are grouped by fingerprint, ranked by priority and capped per tenant. The insert uses `ON CONFLICT ... DO NOTHING`, and the function returns counts per tenant and reason.
- 0410: `rag_mine_failed_queries` is locked in section 1 and `rag_is_domain_expert` in section 2 (no anon). The allow-list has an entry for the helper; its doc comment names the mining function as deliberately absent.

## Deviations from Plan

1. **Chat delete through `SET ROLE`, not the fake edge.** The plan says to delete a chat through the fake edge with the user's JWT. The fake edge's table route does not switch roles (05.1.1-03 deviation 3), so the test runs `DELETE FROM chats` as `authenticated` with `request.jwt.claim.sub` set to the owner. This is the same mechanism the fake edge uses for RPCs, and the chats RLS policy applies.
2. **"labelled_by becomes E_A's id even when the update sets another id."** The column grant the plan requires excludes `labelled_by`, so an expert's UPDATE that sets it is refused with 42501. The test asserts that refusal. It also asserts that after a label update by E_A, `labelled_by` is E_A even though the service role had seeded another user's id.
3. **Additions beyond the plan:**
   - Mining skips opted-out tenants.
   - The answer-record join also matches `tenant_key`.
   - `p_config` is validated and errors raise 22023.
   - `reasons` is checked against the D-13 reason names.
   - Clients cannot change an exported item.
   - Each addition is covered by a test.
4. Migration numbers 0534 and 0535 were free and were taken as planned.
