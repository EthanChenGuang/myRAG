## Planner resolutions (not covered verbatim by CONTEXT)

- Routes import feedback-loop modules by path (`@/lib/rag/feedback-loop/<module>`), not through `src/lib/rag/index.ts`, so only plan 05 edits the barrel and later plans do not serialize on it. `check-rag-boundary` concerns embedding, retrieval RPC and reranker use; the review search still goes through `runRetrieval`.
- The review search mints its scope with the existing `backfillScope(tenantKey)` (it validates the tenant against the deployment mode and checks the user or organization exists), so no new scope-minting path is added.
- Chunk text for evidence is read with the admin client after an RLS read of the item, restricted to the item's tenant and the D-08 current/ready/non-quarantined filter, because the Phase 7 `rag_validate_chunks` RPC (0704) does not exist yet.
- The single-tenant expert rule is implemented in the helper as `p_tenant_key = 's:default'` plus `admin_users` membership; no multi-tenant row can carry that key, so no mode detection is needed in SQL.
- Mining joins Phase 5's `rag_answer_records` by `trace_id` in SQL, so web votes reach the queue even if the mirror (plan 25) missed one.
- Sibling coordination: Phase 4.1.1 (planned in parallel) reserved `source = 'feedback'` in its miss log and an import adapter for `DictionaryCandidate` (its D-25a, 04.1.1-11); Phase 6.1 consumes the `TrainingPair` export as is (its D-08) and uses `confirmed` negatives first. Plan 24 is the only plan that touches a 4.1.1 object, through its service-role recorder.
- httpx is already pinned in the eval `online` extra; Python tests that use it run with `--extra online`.
- Answer language of the two fixed messages (D-03a): the stored code is the language the message was rendered in, not the requested one, because the builders fall back when they have no text for the requested language (RESEARCH F-22). Plan 07 adds one exported helper beside `knowledgeBaseUnavailableMessage` in `src/lib/rag/generation/messages.ts` and imports it by path; no message text changes.
- Query language confidence (D-03a): null when the detector's language differs from the `queryLanguage` the pipeline set, because the detector then says nothing about the stored code.
- Unknown languages (D-03a): a kept chunk without a valid language counts as `und` in `chunk_languages`, so an empty array always means that no chunk was kept; the two scalar columns use null for unknown.
- The language fields use a `LanguageCode` pattern type, not the three-value `Language` Literal of the golden contracts, because a row may hold `und` or a language outside the fixture set.
- `GoldSpan.document_id` (D-29) is optional and is left out of the serialised span when unset, because `golden_sha256` hashes file bytes (RESEARCH F-23). The docgroup rule groups by that id, as D-21 says, and keys a span without one by its document name.
- A domain set has its own manifest, `eval/golden/private/domain/<tenant_hash>/split-manifest.json`; the item-rule manifest at the private root is never switched to the docgroup rule.
- `candidate_count` and `source_opened_count` are in the frozen column list of D-29, because the zero-result rate and the source-open rate are computed from them.
