## Phase Boundary

This phase closes the loop between production use and evaluation. It does five things:
- records every knowledge-base retrieval (chat, embed, voice) in a tenant-keyed, privacy-minimised Postgres table, `rag_retrieval_log`, with retention, deletion with the user's data and a per-tenant opt-out;
- collects explicit feedback where Phase 5 does not: "this should have been answered" on refusals in web chat, thumbs up/down in the embed widget, and one implicit signal (a source or citation was opened);
- mines failed queries every week (thumbs down, refused but probably answerable, zero or low-score retrievals, answered with no source opened) into a tenant-scoped review queue in the database;
- lets domain experts, each limited to the tenants they were granted, label those cases in a Config UI panel (correct documents and evidence spans, expected answer) and triage them into three outputs: dictionary candidates for Phase 4.1.1, training pairs for Phase 6.1, and golden-set candidates;
- turns approved golden candidates into a real domain test set (provenance `production`, or `human` when an expert wrote the question), with a split frozen by document group and near-duplicate cluster, and switches the eval gate to real items (EVAL-14) behind a config switch, with a ship check and a weekly trend report.

In scope: FBK-01 to FBK-10 (new, see `REQUIREMENTS-ADDITIONS.md`); the embed and refusal halves of EVAL-16 (the web-chat answer control stays in Phase 5); EVAL-17, pulled forward from Phase 7 (D-02).

Out of scope:
- The helpful / not-helpful control on web-chat answers, `rag_answer_records`, the Langfuse `user_feedback` score and the Phase 5 review reasons: Phase 5 (05-06, 05-09, 05-13, 05-15, 05-21, 05-23). This phase builds on them and changes one file of theirs (05-21's `feedback.ts`, to mirror the vote onto the log row).
- The dictionary table, its import, query expansion and index-time synonyms: Phase 4.1.1. This phase only writes candidate files in a contract both phases share (D-17).
- Fine-tuning, synthetic queries and model switching: Phase 6.1. This phase only exports production training pairs (D-17).
- Drafting golden items from a real knowledge base with Claude and Ragas (EVAL-05): Phase 1. Those items keep provenance `claude_draft` / `ragas_generated` and never gate.
- Voice feedback controls (D-09 defers them); voice retrievals are logged.
- An in-app (Next.js) expert page for tenant staff without Config UI access (D-21 defers it; the routes are built so a page can be added later without server changes).
- Choosing shipped defaults for any switch: Phase 7 (ADM-02). Every switch added here is off by default.

### Scope against Phase 5 and Phase 7
- **D-01:** Phase 5 keeps EVAL-16 for web-chat answers exactly as planned (D-15 to D-19 of `05-CONTEXT.md`); no Phase 5 plan is repeated or replaced here. This phase adds:
  - the embed thumbs control (D-11) and the refusal control (D-08), which Phase 5 excludes (Phase 5 D-05: web chat only; refusals carry no answerId);
  - one edit to Phase 5's `submitAnswerFeedback` (05-21) that copies the vote onto the matching `rag_retrieval_log` row by `trace_id`, after the database write and best-effort, so mining reads one table (D-10).
  - **Reversibility:** cheap. The mirror is one guarded call.
- **D-02:** EVAL-17 moves from Phase 7 to this phase. Reason: Phase 7 D-21 puts the review queue in files on the operator's machine, which cannot give a tenant A expert a queue that excludes tenant B; the multi-tenant isolation this phase must deliver needs a database queue with row-level security. This phase therefore implements, once, what Phase 7 plans 07-22 (promotion with near-duplicate confirm and append-only safety), 07-23 (chunk text for evidence, here read from the retrieval log instead of Langfuse), 07-26 (failure report) and 07-29 (Config UI panel) describe, and Phase 7 drops those four plans and the review and failure-report contracts of 07-17 (`ReviewPromotion`, `ReviewEvidenceSpan`, `ReviewRetrievedChunk`, `FailureReport`, `FailureEntry`). The change to Phase 7 is listed in `REQUIREMENTS-ADDITIONS.md` for the orchestrator; no Phase 7 file is edited here. "Never run a plan twice" holds because the Phase 7 plans are retired before execution.
  - The single Python promotion implementation (Phase 7 D-22) is kept: `review_queue promote` gains a database source instead of a second implementation in TypeScript.
  - **Reversibility:** costly at planning level (two phases' indexes change), cheap in code (nothing is executed yet).

### Retrieval log (FBK-01, FBK-02)
- **D-03:** One row per knowledge-base retrieval in `public.rag_retrieval_log`, written after the response through `scheduleAfterResponse`, never on the request path. Columns:
  - `id uuid` default `gen_random_uuid()`, `trace_id text not null unique` (the `RetrievalResult.traceId`, so Langfuse, `rag_answer_records.trace_id` and the log join on it);
  - `user_id uuid null references auth.users on delete cascade`, `organization_id uuid null references organizations on delete cascade`, `chat_id uuid null` without a foreign key (the web client creates a new chat's row only after the first answer, Phase 5 planner resolution, so a foreign key would reject the first row; an `AFTER DELETE` trigger on `public.chats` deletes log rows and review items with that `chat_id` instead), `answer_id uuid null` (no foreign key; Phase 5 rows are linked by `trace_id`);
  - `tenant_key` generated per mode exactly like `rag_answer_records` (0502 pattern: single-tenant constant `s:default`, multi-tenant the 03-01 CASE expression);
  - `channel text check in ('chat','embed','voice')`, `rag_mode text null`, `pipeline text check in ('legacy','v2')`, `retrieval_config_hash text null`, `query_language text null` (D-03a adds the other language columns);
  - `query_masked text null`, `query_fingerprint text null` (sha256 hex of the normalised masked query; both null in `ids` mode, D-04);
  - `status text` (`ok|empty|error|degraded`), `refusal_decision text null`, `refusal_reason text null`, `outcome text check in ('answered','refused_no_context','kb_unavailable','degraded_answer','unknown')`;
  - `candidates jsonb not null default '[]'`: at most 50 entries `{chunk_id, document_id, rank, similarity, rerank_score?, fused_score?, kept, language?}` (`language` per D-03a), never content;
  - `candidate_count int`, `top_score real null` (rerank score when present, else similarity), `latency_ms int`, `stage_latency jsonb` (the existing `toStageLatency()` map);
  - `feedback_vote smallint null check in (-1, 1)`, `feedback_kind text null check in ('answer','refusal','embed')`, `feedback_reasons text[] not null default '{}'`, `feedback_at timestamptz null`, `source_opened_count int not null default 0`;
  - `created_at timestamptz not null default now()`.
  - Indexes: `(tenant_key, created_at desc)`, `(created_at)` for the purge, a partial index on `(tenant_key, created_at)` where `feedback_vote = -1`.
  - RLS enabled with no policy; `REVOKE ALL` from PUBLIC, anon and authenticated; `GRANT ALL` to service_role. All reads go through server routes.
  - **Reversibility:** one-way (new table, grants and RLS on real projects).
- **D-03a:** Language columns on the log (FBK-01; read by LANG-10 in Phase 7 and OBS-03 in Phase 5.3, which this phase does not implement). `query_language text null` stays, and 0531 adds next to it:
  - `query_language_confidence real null check (query_language_confidence between 0 and 1)`;
  - `chunk_languages text[] not null default '{}'`: the distinct languages of the kept chunks, ordered by first appearance in rank order; a kept chunk without a valid language counts as `und`; `{}` means no chunk was kept;
  - `answer_language text null`;
  - each entry of `candidates` gains an optional `language` (from `Candidate.language` in `src/lib/rag/types.ts`), left out when the candidate has none.
  - Every language value is a code, never text: it matches `^[a-z]{2,3}(-[A-Za-z0-9]{2,8})?$` (`und` is the code for undetermined). The table checks `query_language`, `answer_language` and every `chunk_languages` element against that pattern. The writer never stores a value that does not match (null for the two scalar columns, `und` for a kept chunk, omitted for a candidate entry) and never stores the text a code was derived from.
  - Sources (existing code, verified at 8115886; verify again at execution):
    - query language: `RetrievalResult.queryLanguage` when set (the v2 pipeline sets it), else the language of `detectLanguageWithConfidence(query)` from `src/lib/rag/lang/detect.ts`, run inside the after-response writer on the query held in memory. It also runs in `ids` mode: only the code is stored.
    - confidence: the detector's result on the same query mapped to a number: 1 when it is confident, 0.5 when it found a language without being confident, null when it found none. It is also null when the detector's language differs from the stored `query_language`, because then the stored code came from the pipeline and the detector says nothing about it. The detector returns a boolean today; Phase 7 may replace this mapping with a calibrated score between 0 and 1 without a schema change.
    - chunk languages: `Candidate.language` of the kept candidates.
    - answer language: the D-07 holder also carries `answerLanguage`, and routes set it where the final answer text is known, always before they finish the trace for that path. Chat: streamText's `onFinish` with `detectLanguage(text)`, the detector Phase 5's `answer-finish.ts` already applies to the answer text. Strict no-context and knowledge-base-unavailable branches: the language the message was rendered in. That is the requested `fallbackLanguage` (chat) or `preferredLanguage(request)` (embed) when the message builder has text for it, and the builder's own fallback language otherwise (at 8115886 `knowledgeBaseUnavailableMessage` has text for en, zh, it and es and falls back to en; `buildNoKnowledgeBaseResponse` has text for es and falls back to English). Embed: its `onFinish`. Voice: null, because `/api/internal/voice-rag` returns retrieval results and the answer is produced in the voice agent. An aborted or failed generation leaves it null.
  - Only the code is stored. Answer text is never stored and never passed to the writer; D-05 is unchanged.
  - Review items copy `query_language_confidence`, `answer_language` and `chunk_languages` into their snapshot (D-14), so the values survive the log purge.
  - Limit: `detectLanguage` knows zh, en and it today; text in another language gives null or the nearest of those three. A detector for the full `RAG_SUPPORTED_LANGUAGES` set changes the values, not the schema.
  - **Reversibility:** one-way for the columns (they ship with the D-03 table); cheap for the sources.
- **D-04:** `RAG_RETRIEVAL_LOG=off|ids|masked_query`, default `off`. `off` writes nothing and leaves every response byte-identical. `ids` writes everything except `query_masked` and `query_fingerprint`. `masked_query` adds the query passed through `maskPII` (the Phase 2 D-26 masker) and capped at 2000 characters. Mining needs `masked_query`; with `ids` only counts and rates exist.
- **D-05:** What is never logged:
  - the `eval` and `media` profiles (only chat, embed and voice are user questions);
  - ghost/incognito chats (`ghost-` ids), as in Phase 5;
  - tenants that opted out (D-06);
  - answer text, chunk text, document names, system prompts, IP addresses, user agents.
- **D-06:** Opt-out and retention:
  - `rag_tenant_feedback_settings(tenant_key primary key, retrieval_log text check in ('inherit','off','ids'), updated_by uuid, updated_at)`. A tenant can only lower the global level (`ids` turns `masked_query` into `ids`; `off` disables). It is read by the writer with a 60 s in-process cache and changed through `PUT /api/rag/admin/feedback-loop/tenant-settings` (operator admin guard).
  - Per-user opt-out is ghost mode, which already exists. A per-user "do not use my conversations" setting is an open PO question (Q-03).
  - `RAG_RETRIEVAL_LOG_RETENTION_DAYS=30`. `rag_purge_retrieval_log(p_retention_days, p_batch_size)` deletes expired rows in batches; it runs from the weekly mining job, from `npm run rag:feedback-loop purge`, and from an optional `pg_cron` file in `supabase/optional/` (the Phase 7 07-13 precedent). Review items keep their own copy of what reviewers need (D-14), so purging the log never breaks the queue.
  - Deletion with the user's data: every table here has `user_id ... on delete cascade`, and the chat-delete trigger removes rows by `chat_id`; deleting a chat or a user removes their log rows and review items. Promoted golden items are expert-paraphrased and carry no user link (D-20, Q-04).
- **D-07:** Outcome. The pipeline cannot know whether the route refused or answered, so `RetrievalResult` gains an optional mutable `logOutcome` holder that routes set before they return (`refused_no_context` in the strict no-context branch, `kb_unavailable` in the knowledge-base-unavailable branch, `degraded_answer` when retrieval failed and the answer continued, `answered` otherwise). The write runs in `after()`, so it sees the final value; a missing value is `unknown`. The same holder carries `answerLanguage` (D-03a).

### Feedback signals (FBK-03, FBK-04, EVAL-16 extension)
- **D-08:** Refusal control (web chat). Behind `RAG_REFUSAL_FEEDBACK=false`:
  - the strict "information not available" stream and the knowledge-base-unavailable stream additionally send `start` metadata `{ ragTraceId, refusal: true }`; with the switch off both streams stay byte-identical (characterization tests);
  - the client shows "I expected an answer" / "Correct, not in my documents" under refusal messages;
  - `POST /api/rag/retrieval/{traceId}/feedback` (SSR session; the row's `user_id` must equal the session user; otherwise 404) stores `feedback_vote` (-1 for "expected an answer", +1 for "correct"), `feedback_kind = 'refusal'`, optional reason chips (`answer_exists`, `wrong_language`, `other`) and nothing else. There is no free text on refusals.
- **D-09:** Voice feedback is deferred. The voice overlay has no stable per-answer surface and the agent is a separate deployment; voice rows are logged (`channel = 'voice'`) and mined on retrieval signals only.
- **D-10:** Web answer votes stay Phase 5's. The 05-21 service mirrors `{vote, reasons}` onto the log row with the same `trace_id` (`feedback_kind = 'answer'`) after its own database write; a missing row (log off) is a no-op.
- **D-11:** Embed control. Behind `RAG_EMBED_FEEDBACK=false` and a valid `RAG_EMBED_FEEDBACK_SECRET` (at least 32 characters, secret):
  - the embed stream's `start` metadata carries `feedbackToken`, an HMAC-SHA256 token `{aud:'embed-feedback', traceId, tenantKey, exp: now+24h}` (the Phase 2 voice-token code is the pattern, with its own audience and secret);
  - `POST /api/embed/feedback {token, vote, reasons?}` (CORS as the embed route, the existing embed rate limiter, no cookies) verifies the token, then updates only the row whose `trace_id` and `tenant_key` both match the token; one changeable vote; `feedback_kind = 'embed'`; reasons are chips only (`wrong`, `incomplete`, `not_relevant`), no free text from anonymous visitors.
  - Either switch off, or the secret too short: no token, no control, the route answers 404.
- **D-12:** Implicit signal. Behind `RAG_SOURCE_OPEN_SIGNAL=false`, opening a source in the web sources panel or a citation chip sends `POST /api/rag/retrieval/{traceId}/signal {kind:'source_opened'}` (session, owner only, at most 20 increments per row). It is a weak signal: mining uses "answered and no source opened" only together with another signal (D-13).

### Mining and the review queue (FBK-05)
- **D-13:** Weekly mining selects, per tenant, rows in the window with `query_masked` present and at least one reason:
  - `feedback_negative`: `feedback_vote = -1` on an answer or embed row, or a Phase 5 `rag_answer_records.feedback` vote of not_helpful on the same `trace_id`;
  - `refusal_disputed`: refusal vote -1;
  - `refused_high_score`: outcome `refused_no_context` or a refusal decision while `top_score` is at or above `refused_high_score_floor`;
  - `zero_results`: `candidate_count = 0` with outcome not `kb_unavailable`;
  - `low_score`: answered with `top_score` below `low_score_ceiling`;
  - `no_source_opened`: answered, `source_opened_count = 0`, the signal switch was on, and at least one other reason is present (never alone);
  - `groundedness_flagged`: the Phase 5 record's label is `possibly_unreliable`.
  Thresholds live in `config/rag/feedback-mining.json` (versioned, per scorer kind: similarity vs rerank) and are reported, not tuned automatically. Rows are deduplicated by `(tenant_key, query_fingerprint)` within the window (most recent kept, occurrence count recorded). At most `per_tenant_limit` (default 50) items per tenant per run, ordered by reason priority (feedback_negative, refusal_disputed, groundedness_flagged, refused_high_score, zero_results, low_score).
- **D-14:** The queue is `public.rag_review_items`, one row per mined case:
  - `id uuid`, `tenant_key text` (copied from the log row, checked by the tenant-key regex), `retrieval_log_id uuid null references rag_retrieval_log on delete set null`, `trace_id text`, `user_id uuid null references auth.users on delete cascade`, `chat_id uuid null` (no foreign key; covered by the chat-delete trigger of D-03);
  - a snapshot that survives the log purge: `query_masked`, `query_language`, `query_language_confidence`, `answer_language`, `chunk_languages` (D-03a), `channel`, `outcome`, `candidates` (ids, ranks, scores, optional language), `retrieval_config_hash`, `reasons text[]`, `occurrences int`;
  - `tags text[] not null default '{}'`, each tag matching `^[a-z_]{1,32}$`, no value list; this phase writes none (D-29);
  - `status text check in ('open','labelled','skipped','exported')`, `triage text[]` contained in `('dictionary','training','golden','kb_gap','not_a_failure')`, `label jsonb` (validated by the `ExpertLabel` contract), `labelled_by uuid`, `labelled_at`, `split text null check in ('dev','test')` and `split_group text null` (set once at approval, immutable afterwards through a trigger, D-16);
  - `mined_at`, `expires_at` (open items expire after 90 days and are purged with the log; labelled items stay until exported).
  - Unique `(tenant_key, query_fingerprint, mining_window)` so re-running a week inserts nothing twice.
  - **Reversibility:** one-way.
- **D-15:** Mining runs as `npm run rag:feedback-loop mine --since <date>` (tsx CLI with the service-role client, the `rag:reembed` pattern) and as `POST /api/rag/admin/feedback-loop/mine` (admin guard, for the Config UI button and for Vercel cron or `pg_cron` through `supabase/optional/feedback-loop-schedule.sql`). The SQL is one service-role function, `rag_mine_failed_queries(p_since, p_until, p_config jsonb)`, that inserts the items and returns counts per tenant and reason. Mining requires `RAG_DOMAIN_EXPERT_REVIEW=true` and the log in `masked_query` mode; otherwise it exits with a notice and writes nothing.

### Expert access and labelling (FBK-06, EVAL-17)
- **D-16:** Domain experts:
  - `public.rag_domain_experts(tenant_key text, user_id uuid references auth.users on delete cascade, granted_by uuid, created_at, primary key (tenant_key, user_id))`, service-role only.
  - RLS on `rag_review_items`: `SELECT` and `UPDATE` (label columns only, through a column-limited update route) for `authenticated` where `public.rag_is_domain_expert(tenant_key)`, a `SECURITY DEFINER` helper with `SET search_path = ''` that checks `auth.uid()` against `rag_domain_experts`. It goes into section 2 of `0410_security_definer_rpc_grants.sql` (authenticated-callable RLS helper) and into `tests/helpers/security-definer-allow-list.ts`.
  - Expert routes read and label items with the caller's SSR client, so RLS proves the tenant; chunk text and document names for evidence come from the admin client restricted to the item's `tenant_key` and to the chunk ids in the item's snapshot (or in a review search the expert ran under that tenant, D-19), and are re-validated as current and servable.
  - Single-tenant: admins (`admin_users`) are experts of `s:default` without a grant row. Multi-tenant: nobody is implicitly an expert, operator admins included; every grant is explicit, logged with the granting admin's id (Q-01).
  - Grants are managed only by operator admins through `GET/POST/DELETE /api/rag/admin/domain-experts` (Q-02 for org owners).
  - Every expert read of chunk text logs `[Review] chunks` with the expert id, a hash of the item id and the count, never text.
- **D-17:** Triage outputs (FBK-07), each a Pydantic contract with generated Zod:
  - `DictionaryCandidate {tenant_key, language, observed_term, canonical_term, relation: 'synonym'|'abbreviation'|'translation'|'misspelling', example_review_item_ids[], occurrences}`. The expert types the term pair in the label; this phase never writes Phase 4.1.1's dictionary table. Export writes JSONL into the private directory; when Phase 4.1.1's import exists at execution time the export plan adds a thin adapter to it, otherwise the file is the hand-off (A-3).
  - `TrainingPair {tenant_key, query_masked, language, positive {chunk_id, document_id, quote}, hard_negatives [{chunk_id, document_id, rank, score, confirmed}], document_group, split: 'train'|'held_out', source: 'production_feedback', review_item_id}`. Hard negatives are, first, logged candidates the expert explicitly marked not relevant (`confirmed: true`), then other logged candidates ranked above the lowest-ranked positive that the expert did not cite (`confirmed: false`), preferring other documents, at most 10 (Phase 6.1 D-08 uses confirmed ones first). No chunk text is exported; Phase 6.1 resolves text by id under the tenant at training time. Any pair whose `document_group` is in the frozen test split of the domain set is marked `held_out` and must never be trained on (leakage guard, tested).
  - Golden candidates feed D-20.
  - Phase 4.1.1 coordination (its D-25 and D-25a): when its `RAG_TERMINOLOGY_MINING` is on, each mining run also writes the run's `feedback_negative`, `refusal_disputed` and `zero_results` items into 4.1.1's `rag_term_misses` with `source = 'feedback'` through its service-role recorder, so its miner sees thumbs-down failures without a schema change; the expert-labelled `DictionaryCandidate` file goes through 4.1.1's import adapter (04.1.1-11), never into its tables directly.
- **D-18:** Labels (`ExpertLabel` contract): `answerable`, `category` (the GoldenItem categories), `language`, `expected_answer` (required when answerable), `evidence` spans `{chunk_id, document_id, document_name, section, quote}` where `quote` must be an exact substring of the current chunk text after `normalize_text` (checked by the route and again by the Python promote), `triage[]`, optional `not_relevant_chunk_ids[]` (snapshot candidates the expert marked not relevant), optional `dictionary_terms[]`, optional `paraphrased_question` (required when the expert's PII check flags the masked question, D-22), `pii_checked: true` required for `golden`.

### Real domain test set (FBK-08, FBK-09)
- **D-19:** Review search. The expert can search the item's tenant for evidence the retrieval missed: `POST /api/rag/review/items/{id}/search {query}` resolves the item's tenant scope server-side (never from the body), runs `runRetrieval` with profile `chat` and `ragMode: 'flexible'`, a pool of 30 and logging suppressed (`logContext: { skip: true }`), and returns ids, document names, sections and text of the hits. All retrieval stays inside `@/lib/rag` (`check-rag-boundary` stays green).
- **D-20:** Domain set export. `python -m rag_eval.review_queue promote-db --tenant <key> --base-url <url>` (single Python promotion implementation, extended from Phase 1/2 `review_queue.py`, Phase 7 D-22 rules) pulls labelled `golden` items through `GET /api/rag/admin/feedback-loop/export?kind=golden&tenant=` (admin Bearer from `--token-env`; the export carries each evidence span's current chunk text, re-read under the item's tenant, so quotes can be re-checked without an expert session), and for each:
  - builds a `GoldenItem` with `provenance = 'production'` (or `'human'` when `paraphrased_question` replaced the user's wording), `review_status = 'approved'`, span evidence (document, section, quote; never chunk ids);
  - detects near-duplicates with character 3-gram Jaccard at least 0.85 on `normalize_text(question)` (Phase 7 D-22), requiring `confirm_near_duplicate_of` in the label;
  - writes it to `eval/golden/private/domain/<tenant_hash>/golden.jsonl` (gitignored) with `assert_private_path`, append-only (no delete command; the scorer fails when a manifest id is missing);
  - marks the review item `exported` through the export route.
- **D-21:** Split by document group. `GoldenSplitManifest` gains the rule `docgroup-sha256-first8hex-mod100-lt70-dev` and `group_assignments`. The group of an item is the union (union-find) of items sharing a gold document id or forming a near-duplicate pair; a new item joining a group that already has a frozen split inherits it; a brand-new group gets `sha256(min document id of the group)`. The item-id rule stays for existing manifests; a manifest never switches rule. The assignment is written back to `rag_review_items.split` and `split_group`, which a trigger makes immutable once set. Training export reads the same groups (D-17).
- **D-22:** PII review before promotion. The masked question is shown with a checklist (names, addresses, account numbers, health data); the expert either confirms `pii_checked` or writes `paraphrased_question`. `promote-db` re-runs `mask_text` and refuses an item whose question still changes under masking (exit EXIT_INPUT). No raw customer text enters git; fixtures in this phase are synthetic.
- **D-23:** Gate population (EVAL-14). `eval/config/gate-population.json` `{ "mode": "legacy" | "real", "provenances": ["production","human"], "min_items": 100 }`, default `legacy` (today's rule: approved production items of the gated split when any exist, else all). In `real` mode the gate is computed on approved `production` and `human` items of the gated split; fewer than `min_items` fails the run with `real_set_too_small` instead of falling back silently. Reports gain `gate_population: "real"`; synthetic, `claude_draft` and `ragas_generated` items stay report-only. A baseline recorded under one population never gates a run under another (`_require_same` already enforces this).
- **D-24:** Ship rule ("improvement must be proven on the domain test set before going live"). `python -m rag_eval.ship_check --baseline <report.json> --candidate <report.json> --target <metric>` passes only when both reports are `gate_population: "real"` on the same frozen manifest hash, no metric in overall, per-language or per-category slices drops beyond the noise band (existing paired logic), and the paired bootstrap 95% interval of the target metric's difference is above zero. It writes a `ShipCheckResult` JSON to the private directory. From the moment the gate population is `real`, turning any `RAG_*` switch on by default or activating an embedding profile requires a passing ship check (documented in AGENTS.md; Phase 7 07-17 `DefaultsDecision` consumes `ShipCheckResult`).

### Weekly report (FBK-10)
- **D-25:** `python -m rag_eval.weekly_report --since <date>` combines:
