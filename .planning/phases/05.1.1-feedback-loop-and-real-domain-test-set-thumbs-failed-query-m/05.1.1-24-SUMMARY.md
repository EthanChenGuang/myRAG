# Phase 05.1.1 Plan 24: Bridge feedback failures to the terminology miss log - Summary

**With Phase 4.1.1's `RAG_TERMINOLOGY_MINING=true`, each completed mining run copies its new thumbs-down, disputed-refusal and zero-result review items into `rag_term_misses` (source `feedback`) through `rag_term_record_miss`, per tenant, so 4.1.1's miner sees real failures without a schema change. Off (default) nothing is read or written.**

## Accomplishments

- `src/lib/rag/feedback-loop/terminology-bridge.ts`: `bridgeToTerminologyMisses`, which reads the run's items back per tenant, builds a fixed-field miss row per eligible item and calls the recorder under that item's tenant key. It never rejects.
- `runMining` calls it after the mining RPC and result build, inside try/catch, with the per-tenant insert counts from the report rows.

## Behaviour changes

- None with defaults (`RAG_TERMINOLOGY_MINING=false`): mining logs one extra `[Feedback Loop] terminology bridge skipped (terminology_mining_off)` line and sends no query.
- With it on: after each completed run, one `rag_review_items` select per tenant with new items, and one `rag_term_record_miss` call per eligible item, then one counts-only log line.

## Deviations

1. **Bridge input.** The plan writes `bridgeToTerminologyMisses(run)`. `MiningRunResult` names tenants by hash only, so the bridge takes `{until, tenants:[{tenantKey, inserted}]}` built from the report rows inside runMining, plus `{client, enabled, log}`.
2. **profile field.** must_haves lists the copied fields without `profile`, but `rag_term_record_miss` requires it; the bridge sends the item's `channel` as `profile` and skips items without one.
3. **Extra test file.** `tests/rag-db/terminology-bridge-end-to-end.test.mts` (not in files_modified) runs the real 0473 recorder and 0537 mining on PGlite for two tenants. The fake edge serves no embedded selects, so that test's client answers the bridge's one read with SQL shaped like the PostgREST embed.
4. The plan's "calls the recorder twice per eligible item" is read as one call per eligible item, per must_haves ("one row per newly inserted review item").
