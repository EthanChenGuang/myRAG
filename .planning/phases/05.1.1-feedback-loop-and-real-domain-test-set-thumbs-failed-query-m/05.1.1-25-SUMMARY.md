# Phase 05.1.1 Plan 25: Mirror Phase 5 answer votes onto the retrieval log - Summary

**A web-chat answer vote is now copied onto the matching `rag_retrieval_log` row (same `trace_id`, same tenant), after Phase 5's own write and best-effort, so mining and stats read one table. With `RAG_RETRIEVAL_LOG=off` (default) nothing changes.**

## Accomplishments

- `mirrorVoteToRetrievalLog` in `src/lib/rag/generation/feedback.ts` updates `feedback_vote` (1 / -1), `feedback_kind = 'answer'`, `feedback_reasons` and `feedback_at` with `.eq('trace_id', …).eq('tenant_key', …)` on the admin client. A missing row is an update of zero rows; it never throws.
- `reportFeedback`, the after-response task 05-21 already schedules, runs the mirror alongside the Langfuse score and the review export. It runs only when the record has a `trace_id` and the retrieval log is on. The mirror's outcome does not feed the `[RAG Feedback]` line, so Langfuse reporting is unchanged.

## Behaviour changes

- None with the defaults: `RAG_RETRIEVAL_LOG=off` sends no log query.
- With the log on, each vote sends one extra admin `UPDATE rag_retrieval_log` after the response.

## Deviations

1. **Signature.** The plan names `mirrorVoteToRetrievalLog(traceId, vote, reasons)`. It takes a fourth `options` argument `{client, tenantKey, at, timeoutMs?, log?}`, because the plan also requires the record's tenant_key filter and the call has to use the admin client already in hand.
2. **Gated on `RAG_RETRIEVAL_LOG`.** The plan says a missing row is a no-op. I also skip the query entirely while the log is off, so the default sends exactly the Phase 5 queries. Mining still sees those votes through its SQL join on `rag_answer_records` (plan 04).
3. The plan's verification line names `npm run typecheck:new`. I ran the brief's `npx next typegen && npx tsc --noEmit -p tsconfig.json` gate instead (0 errors).
