# Phase 05.1.1 Plan 11: Weekly failure mining (runMining, CLI, admin route) — Summary

**An operator, the Config UI or a scheduler can turn a window of logged retrievals into each tenant's review queue once, with output that names tenants only by hash and carries counts only.**

## Accomplishments

- `mining.ts`: `runMining` checks the switches first (`RAG_DOMAIN_EXPERT_REVIEW=true` and `RAG_RETRIEVAL_LOG=masked_query`). A disabled run returns `status: 'disabled'` and touches nothing. An enabled run loads `config/rag/feedback-mining.json`, resolves and caps the window, runs `purgeRetrievalLog`, then calls the mining function with the config plus `source_open_signal` from `RAG_SOURCE_OPEN_SIGNAL`. It maps the rows into a `MiningRunResult`: tenant hashes, per-reason counts, per-tenant item counts, the config sha256, the purge counts and the window. The result is checked against the generated schema, and one `[Feedback Loop] mining` line logs counts.
- `0536_rag_feedback_mining_report.sql`: `rag_mine_failed_queries_report` wraps `rag_mine_failed_queries` and adds `tenant_inserted`, so the report has exact item counts (see Deviations). It is SECURITY INVOKER with `search_path = ''`, revoked from PUBLIC, anon and authenticated, and granted to service_role.
- `cli.ts`: `mine [--since YYYY-MM-DD] [--until YYYY-MM-DD]` prints the result JSON on stdout. This plan is the CLI's second and last editor.
- `POST /api/rag/admin/feedback-loop/mine`: runs the admin guard first, then answers 404 while mining is disabled. It validates the body strictly, refuses a window longer than 31 days with 400, and returns `{success: true, result}`.
- `@/lib/rag` exports the mining functions, so the route passes `check-rag-boundary`.

## Deviations

1. **Migration 0536 (not in files_modified).** `rag_mine_failed_queries` returns one row per (tenant, reason), and an item counts under every reason it carries. Summing those rows overstates a tenant's items: in the end-to-end test tenant A gets 6 items but 7 reason hits. The wrapper runs the mining function and then, in a second statement of the same transaction, counts the review items with `mined_at = now()` in the run's window. 0535 is unchanged. 0536 was free. Plan 22 must fold it into both setup files. It is SECURITY INVOKER, so it needs no 0410 or allow-list entry.
2. **Disabled shape.** The plan says `{ok:false, reason:'disabled'}`. The plan 01 contract has `status: 'disabled'` with `disabled_reason`, and the code follows the contract.
3. **`--since` is optional** in the CLI, and the route accepts an empty body. Both default as the plan describes for `until` and `since`.
4. **End-to-end client.** The fake edge serves RPCs and reads only, and it answers a scalar function as `[{fn: value}]`. The test therefore wraps the fake-edge client: RPCs go through the edge with the service-role key (scalars unwrapped as PostgREST would), and the purge's one table delete (`rag_review_items` `delete().eq().lt()`) runs on the database directly. Log rows are built with `buildRetrievalLogRow` and inserted as `service_role`.
5. `src/lib/rag/index.ts` was modified for the route import (boundary rule), as in plan 08.
6. The plan's verification line names `npm run typecheck:new`. I ran the brief's `npx next typegen && npx tsc --noEmit -p tsconfig.json` instead.
