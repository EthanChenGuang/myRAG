# Phase 5.1.1 Plan 06: Gate population switch Summary

**The eval gate can now run on real items only, behind `eval/config/gate-population.json` (default `legacy`, unchanged behaviour). In `real` mode the gated slices cover the approved items of the configured provenances, and a set smaller than `min_items` fails the run with `real_set_too_small` instead of falling back.**

## Accomplishments
- `eval/config/gate-population.json` validates as `GatePopulationConfig`. `load_gate_population()` returns it with the sha256 of the file bytes, and `write_gate_population()` writes the same bytes as the committed file.
- `aggregate(..., population=)`: `select_gate_population` keeps the legacy rule as it was and adds `real`. `by_provenance` and `by_provenance_category` stay on the whole gated split.
- Runner: `--gate-population` (default is the committed file). It prints `gate_population=<label> sha256=<hex> (mode <mode>)`, adds the config note to the report, and exits 3 with `real_set_too_small`, the count and min_items when the real set is too small.
- Report: a real run notes the item count, per-language counts, provenances and min_items, and lists the other provenances as report-only under By provenance. The header already prints `Gate population: real`.
- `paired.py` and `parse_gate.py` no longer treat a `real` report as `all` (that would have paired synthetic items).

## Deviations from Plan
1. **`paired.py` and `parse_gate.py` changed** (not in files_modified). Both branched only on `production`, so a `real` report would have been paired over every gated item, including synthetic ones. They now use `report_gate_items`. Tests: `test_paired_report_under_real_pairs_only_the_configured_provenances` and `test_parse_gate_selects_real_items_from_the_committed_config_provenances`.
2. **New snapshot file** `eval/tests/data/gate-population-legacy-aggregates.json`. It holds the saved legacy aggregates that the plan's regression test compares against.
3. **The sha256 goes in a report note**, not a new contract field (see key-decisions). Smoke reports from `npm run test-rag` gain that one note. Metrics, slices and `gate_population` are unchanged.
4. **One RED commit for both tasks.** The runner and report tests share fixtures with the metrics tests. The RED commit carries only stubs (the loader, the `RealSetTooSmall` class, ignored keyword parameters, and the runner flag), so every new test failed on an assertion. The runner wiring is committed with Task 2 because it depends on `build_report(gate_population_config=)`.
