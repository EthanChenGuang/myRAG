# Phase 05.1.1 Plan 09: Refusal vote and source-open routes — Summary

**Signed-in users can dispute or confirm a refusal and report an opened source, on their own retrievals only. The chat refusal streams carry a trace id only when `RAG_REFUSAL_FEEDBACK` is on and a log row will exist.**

## Accomplishments

- `votes.ts`: `setRefusalVote` stores -1 for `expected_answer` and +1 for `correct_refusal`, plus `feedback_kind='refusal'`, the reason chips and `feedback_at`. It runs as one update filtered by `trace_id`, `user_id` and a refusal outcome. `recordSourceOpened` calls `rag_record_source_opened`.
- `0536_rag_retrieval_log_source_opened.sql`: adds one in a single statement, stops at 20, and only touches the row of that user. Service role only, idempotent.
- `retrieval-route.ts`: the shared entry for both routes (session, JSON content type, parse, schema) and the shared 404 and 503 bodies.
- Routes: `POST /api/rag/retrieval/{traceId}/feedback` returns 200 `{vote, reasons, at}`. `POST /api/rag/retrieval/{traceId}/signal` returns 204. Both use `runtime = 'nodejs'` and `Cache-Control: no-store`, return no 403 and send no CORS headers.
- Chat route: a `refusalStartMetadata()` closure inside `POST` is read before `finishRagTrace()` in the knowledge-base-unavailable branch and in the `shouldBlockNoContextResponse` branch. When set, the branch writes a `start` part before its existing parts.

## Behaviour changes

- None with the defaults (`RAG_REFUSAL_FEEDBACK=false`, `RAG_SOURCE_OPEN_SIGNAL=false`, `RAG_RETRIEVAL_LOG=off`). Both refusal streams stay byte-identical (characterization), both routes return 404, and strict "information not available", webSearch with Exa, `source_images`, `{{context}}`, voice and embed are unchanged.
- With the switch and the log on, the two refusal streams start with `{"type":"start","messageId":…,"messageMetadata":{"ragTraceId":…,"refusal":true}}`. The AI SDK adds the generated `messageId` to a start part that has none. The parts after it are unchanged.
